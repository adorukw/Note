# 第一章：美术管线总览

---

## 第 1 讲 游戏美术管线的定义与价值

### 概念

**游戏美术管线（Game Art Pipeline）** 是指从美术需求产生到最终资产进入游戏引擎并被渲染出来之间，所经历的全部标准化流程、工具链与规范的集合。它本质上是一条"生产流水线"：原材料（需求文档、参考图）经过一道道工序（原画→建模→贴图→绑定→动画→导入→优化），最终产出可被引擎直接使用的游戏资产（Prefab、Material、Animation Clip 等）。

更具体地说，美术管线不仅包含"怎么做美术"，更包含"怎么让美术可复用、可维护、可扩展、可协作"。一个成熟的管线会明确规定：文件命名规则、目录结构、资产规格（三角面数、纹理分辨率）、工具版本、交接格式、检查清单等。这些规定让十个人做出的资产看起来像一个人做的，让三个月后接手的人能立刻看懂。

### 原理

美术管线的核心原理可以用"**质量—效率—一致性**"三角来理解：

1. **质量（Quality）**：单个资产要达到项目定义的视觉标准。这需要工具支撑（如 Substance 智能材质保证贴图风格统一）、规范约束（如统一的灯光与色调参考）和评审流程（如 Lead 审核与迭代反馈）。

2. **效率（Efficiency）**：在有限的人力与时间内产出尽可能多的合格资产。这依赖自动化（批处理脚本、模板预设）、并行化（多人同时制作不同资产而不冲突）和复用（材质库、模型库、组件库）。

3. **一致性（Consistency）**：所有资产在风格、规格、技术参数上保持统一。这是管线区别于"个人创作"的关键——个人可以靠手感，团队必须靠规范。一致性通过命名规范、检查工具（如 Validator）、模板文件和中央资产库来保证。

这三个目标常常互相制约：追求极致质量会降低效率；追求效率可能牺牲一致性。管线设计的本质就是在这三者之间找到适合项目规模与预算的平衡点。3A 项目偏重质量与一致性，独立游戏则更看重效率与灵活性。

### 例子

以一个简单的"木箱道具"为例，展示完整管线流程：

```
需求文档（尺寸/风格/用途）
    ↓
原画师 → 概念图 sketch.png（3 个视角 + 细节标注）
    ↓
建模师 → low_poly.fbx（≤1500 三角面）+ high_poly.fbx（百万级面）
    ↓
UV 展开 → uv_layout.png（打包率 ≥70%）
    ↓
烘焙 → normal_map.png / ao_map.png / curvature_map.png
    ↓
Substance Painter → basecolor / metallic / roughness（PBR 贴图集）
    ↓
导入引擎 → 配置材质 → 制作 Prefab → 加入碰撞体
    ↓
QA 检查 → 命名/规格/性能通过 → 入库
```

每一步都有明确的输入、输出和检查标准。如果某一步出问题（比如 UV 打包率太低），可以回溯到具体环节修改，而不必推倒重来。

### 总结

- 美术管线 = 流程 + 工具 + 规范，三者缺一不可。
- 核心目标是平衡质量、效率、一致性，不同项目侧重不同。
- 管线的价值在于"可复现"——同样规格的资产，任何人按流程做都能达到相近水准。
- 常见误区：把管线等同于"会用某几个软件"。工具只是手段，规范与流程才是灵魂。
- 实践建议：小团队也应尽早建立最小化管线（哪怕只是一个命名规范文档 + 一个模板文件），随项目成长逐步完善。

## 第 2 讲 美术团队角色与协作流程

### 概念

游戏美术团队由多个专业角色组成，每个角色负责管线中的特定环节。理解角色分工，才能理解管线为什么这样设计——管线的每一步都对应一个或多个角色的职责边界与交接点。典型的中大型项目美术团队包含以下角色：**概念美术师（Concept Artist）、3D 建模师（3D Modeler）、材质师（Texture Artist）、技术美术（Technical Artist / TA）、动画师（Animator）、UI 美术师（UI Artist）、美术总监（Art Director / AD）与美术组长（Lead）**。

小团队或独立项目中，一个人可能身兼数职，但"角色"本身的概念依然存在——你只是在不同时刻切换身份。理解角色划分有助于明确"此刻我应该用什么标准工作"。

### 原理

角色分工背后的原理是**专业化分工**与**接口标准化**：

1. **专业化分工**：每个环节的技能树差异巨大。原画师需要扎实的绘画功底与色彩理论；建模师需要空间造型能力与拓扑学理解；TA 需要同时懂美术与编程。让一个人精通所有环节不现实，分工让每个人在自己领域做到极致。

2. **接口标准化**：分工必然带来交接问题。原画师交给建模师的图必须包含足够信息（多视图、比例标注、材质说明）；建模师交给材质师的模型必须 UV 干净、法线正确。这些"交接物"的格式与质量标准，就是管线中最实际的规范。

协作流程通常遵循"**需求 → 设计 → 制作 → 审核 → 迭代 → 交付**"的循环：

```
AD/Lead 定义风格与规格
    ↓
Concept 出概念图 ← 评审反馈
    ↓
Modeler 建模 ← 评审反馈
    ↓
Texture 材质 ← 评审反馈
    ↓
Rigger 绑定 / Animator 动画 ← 评审反馈
    ↓
TA 导入引擎 + 技术检查
    ↓
入库 / 集成到场景
```

TA 是这条链上的"润滑剂"——既帮美术解决技术问题（写工具、修 Shader），又帮程序理解美术需求（优化性能、配置渲染）。好的 TA 能让管线效率提升数倍。

### 例子

以角色制作流程为例，展示角色间的交接物与检查点：

| 交接环节 | 产出物 | 接收方检查点 |
|---------|--------|-------------|
| AD → Concept | 风格参考板、角色设定文档 | 是否符合世界观、是否有明确剪影 |
| Concept → Modeler | 正/侧/背三视图、细节特写 | 比例是否对齐、结构是否可建模 |
| Modeler → Rigger | 绑定用低模（T-pose/A-pose） | 关节布线是否支持变形、面数是否达标 |
| Rigger → Animator | 绑定完成文件（含控制器） | 控制器是否齐全、权重是否合理 |
| Animator → TA | 动画 FBX（含帧范围标记） | 帧率是否统一、是否有冗余关键帧 |
| TA → 程序 | 引擎内 Prefab + 配置文档 | 性能是否达标、参数是否可调 |

一个常见的协作痛点：建模师做的模型关节处没有足够的循环边，导致绑定后弯曲时出现"糖果纸"撕裂。如果管线规范中明确要求"肘膝等关节至少 3 圈循环边"，并在交接时由 Rigger 检查，就能避免返工。

### 总结

- 美术角色按专业分工，但通过标准化接口协作。
- TA 是连接美术与程序的关键桥梁，价值常被低估。
- 交接物的质量决定管线效率——垃圾进，垃圾出。
- 常见误区：角色间缺乏沟通，各自为战。应建立定期评审与同步机制。
- 实践建议：制作"交接检查清单（Checklist）"，每个环节交付前逐项打勾。

## 第 3 讲 主流工具链与技术栈

### 概念

美术管线的每一步都依赖特定工具，这些工具组成的集合就是**工具链（Toolchain）**。当前业界主流的美术工具链以 Autodesk Maya / Blender（建模绑定）、ZBrush（高模雕刻）、Substance Painter & Designer（材质）、Marvelous Designer（布料）、Marmoset Toolbag（烘焙与预览）为核心，配合 Unity 或 Unreal Engine 作为最终集成平台。2D 方向则常用 Photoshop、Aseprite（像素）、Spine（2D 骨骼动画）。

工具链的选择不是随意的，它需要满足三个条件：**格式互通、版本可控、团队共识**。一个工具再强大，如果导出的格式下游工具读不了，或者团队成员不会用，就不能进入管线。

### 原理

工具链设计的核心原理是**格式兼容性**与**数据无损传递**：

1. **格式兼容性**：不同工具之间通过中间格式传递数据。3D 模型常用 FBX（Autodesk 的事实标准）或 glTF（开源新标准）；贴图用 PNG/TGA（无损）或 DDS/ASTC（压缩）；工程文件用各软件原生格式（.ma/.blend/.zpr/.spp）。管线的健康度很大程度上取决于格式转换的损耗——每次转换都可能丢失信息（如顶点色、自定义属性、UV 通道）。

2. **数据无损传递**：理想情况下，从高模到最终引擎资产，所有有用信息（位置、法线、UV、顶点色、材质 ID）都应完整保留。实际中需要明确哪些信息在哪个环节产生、哪些环节消费。例如：顶点色通常在建模阶段绘制，在引擎中用于 Shader 控制（如风吹草动、积雪范围）。

工具版本管理也是关键。同一项目内所有成员应使用相同版本（至少相同大版本），否则文件打不开或行为异常是常态。许多工作室使用"工具快照"（如 Maya 的 Maya.env 配置 + 版本锁定脚本）确保一致性。

### 例子

一个典型的 3A 角色制作工具链与数据流：

```
[ZBrush]          高模雕刻 → .zpr 工程文件
    ↓ 导出 .obj/.fbx
[Maya/Blender]    低模制作 + 拓扑 + UV → .ma/.blend 工程文件
    ↓ 导出 .fbx（含低模+UV）
[Substance Painter] 烘焙 + 材质绘制 → .spp 工程
    ↓ 导出贴图集（PNG/EXR）
[Marmoset Toolbag] 实时预览 + 截图交付 → 截图 .png
    ↓ 最终资产打包
[Unity/Unreal]    导入 FBX + 贴图 → 配置材质 → Prefab
```

各环节的版本与格式约定示例（项目规范文档片段）：

```yaml
# 工具版本
maya: 2024.2
zbrush: 2024.0
substance_painter: 10.0
unreal: 5.4

# 资产格式
mesh_format: fbx          # FBX 2020
texture_format_lossless: png   # 16-bit for normal/height
texture_format_compressed: dds # BC7 for color, BC5 for normal
uv_channel: 0             # 主 UV 在 channel 0
normal_space: tangent     # 切线空间法线
```

### 总结

- 工具链 = 核心软件 + 中间格式 + 版本管理，三者构成数据通路。
- FBX 是当前最通用的 3D 交换格式，但有信息损耗，需测试验证。
- 团队必须统一工具版本，避免兼容性问题。
- 常见误区：盲目追新工具。新工具引入成本高（学习、迁移、排错），应评估收益。
- 实践建议：维护一份"工具链文档"，记录每个环节用什么工具、什么版本、导出什么格式、注意什么事项。

## 第 4 讲 概念设计与原画创作

### 概念

**概念设计（Concept Design）** 是美术管线的第一道工序，目的是在正式制作前将抽象的需求（"一个废土风格的机械守卫"）转化为可视化的具体形象。概念美术师（Concept Artist）通过快速草图、剪影探索、色彩试验等方式，为下游的建模师、动画师提供明确的视觉参考。概念图不是"最终成品"，而是"沟通工具"——它的价值在于传递信息（造型、比例、材质、色彩、氛围），而非本身多么精致。

原画（Original Painting / Key Art）则更偏向成品级表现，常用于宣传、加载界面或风格定调。在管线语境下，我们更关注"制作向概念图"——即服务于生产的概念稿，而非宣传向的 Key Art。

### 原理

概念设计的核心原理是**快速迭代**与**信息分层传递**：

1. **快速迭代**：概念阶段最重要的是"试错成本低"。一张草图 30 分钟，一个完整模型 3 天。在草图阶段多探索几个方向，比做完模型再推翻高效得多。业界常用"剪影法"——先画几十个纯黑剪影，快速筛选造型轮廓，再对选中的剪影细化。这背后的认知原理是：人类对物体的第一识别依据是轮廓（Silhouette），轮廓立住了，设计就成功了一半。

2. **信息分层传递**：一张概念图无法传递所有信息，因此需要分层制作：
   - **造型层**：正/侧/背三视图，传递比例与结构
   - **材质层**：材质球标注或局部特写，传递质感（金属/布料/皮肤）
   - **色彩层**：色彩脚本（Color Script），传递整体色调与氛围
   - **细节层**：局部细节放大图，传递纹样、磨损、配件

这种分层让下游各角色各取所需：建模师看三视图，材质师看材质标注，灯光师看色彩脚本。

### 例子

一个角色概念图的交付包示例：

```
concept_character_guard_001/
├── 01_silhouette_exploration.png   # 20 个剪影方案
├── 02_front_view.png               # 正视图（带比例尺）
├── 03_side_view.png                # 侧视图
├── 04_back_view.png                # 背视图
├── 05_detail_head.png              # 头部细节特写
├── 06_detail_weapon.png            # 武器细节
├── 07_material_guide.png           # 材质标注图（编号对应材质说明）
├── 08_color_variation.png          # 3 套配色方案
└── README.md                       # 设计说明文档
```

剪影探索的伪代码思路（实际用 Photoshop/Procreate 手绘）：

```
步骤 1：画布上随机画 20-30 个纯黑剪影，不纠结细节
步骤 2：标记其中 5 个"有感觉"的
步骤 3：对这 5 个各画 3 个变体（加/减/改元素）
步骤 4：从中选 1-2 个进入线稿细化
步骤 5：细化时始终保持剪影清晰可辨
```

材质标注图的做法：在概念图上用不同颜色色块标记区域，旁边编号，对应一个材质说明表：

| 编号 | 区域 | 材质 | PBR 参数参考 |
|------|------|------|-------------|
| M01 | 胸甲 | 锈蚀钢板 | metallic=1, roughness=0.7 |
| M02 | 内衬 | 旧皮革 | metallic=0, roughness=0.85 |
| M03 | 关节 | 拉丝金属 | metallic=1, roughness=0.4 |
| M04 | 发光眼 | 自发光 | emissive=#00ff88 |

### 总结

- 概念图是沟通工具，不是展示品，信息传递优先于画面精致度。
- 剪影法是快速探索造型的利器，先立轮廓再抠细节。
- 分层交付（造型/材质/色彩/细节）让下游各取所需。
- 常见误区：只画一个帅气角度，没有三视图，建模师只能猜。
- 实践建议：概念阶段多花 1 天探索，能省下游 1 周返工。

## 第 5 讲 2D 精灵与图集制作

### 概念

**精灵（Sprite）** 是 2D 游戏中最基本的视觉单元，指一张包含角色、道具或特效的位图，通过引擎在屏幕上绘制并移动。**图集（Sprite Atlas / Texture Atlas）** 是将多张小精灵合并到一张大图上的技术，目的是减少 Draw Call、提升渲染效率。在 2D 游戏（横版动作、像素游戏、卡牌游戏）和 UI 系统中，图集是不可或缺的优化手段。

精灵与图集的制作看似简单（"不就是切图吗"），但其中涉及纹理尺寸、压缩格式、内存占用、打包算法等多个工程考量。一个糟糕的图集可能让游戏内存翻倍、加载变慢。

### 原理

图集的核心原理是**减少状态切换**与**空间利用率最大化**：

1. **减少 Draw Call**：GPU 每次切换纹理（绑定新纹理对象）都有开销。如果 100 个 UI 元素各自独立纹理，需要 100 次 Draw Call；合并到一张图集后，只需 1 次（前提是材质相同）。Draw Call 是 CPU-GPU 通信的瓶颈，移动端尤其敏感（建议控制在 100-300 以内）。

2. **空间利用率**：图集的打包算法决定了空间利用率。常见算法有：矩形装箱（Rect Packing）、MaxRects、Skyline。好的算法能让打包率（有效像素 / 总像素）达到 80%+。同时需注意：
   - **POT 纹理（Power of Two）**：宽高为 2 的幂（256/512/1024/2048/4096），因为 GPU 纹理压缩格式（如 ETC2、ASTC、BC7）要求 POT 或 4 的倍数对齐。
   - **Padding**：精灵之间需留 2-4 像素间距，防止采样时邻图渗透（Bleeding），尤其在 Mipmap 开启时。
   - **Mipmap 注意**：2D 精灵图集通常关闭 Mipmap（避免缩小采样时精灵模糊），但 UI 在多分辨率下可能需要。

### 例子

Unity 中使用 Sprite Atlas 的配置示例：

```csharp
// 创建 SpriteAtlas 资产（Editor 脚本）
using UnityEngine;
using UnityEditor;
using UnityEngine.U2D;

public class AtlasCreator
{
    [MenuItem("Tools/Create Sprite Atlas")]
    static void CreateAtlas()
    {
        var atlas = new SpriteAtlas();

        // 设置打包参数
        var settings = new SpriteAtlasAssetSettings();
        settings.variantMultiplier = 1.0f;       // 变体缩放
        settings.maxTextureSize = 2048;           // 最大尺寸
        settings.textureCompression = TextureImporterCompression.Compressed;
        settings.useCrunchCompression = true;     // Crunch 压缩，体积更小

        atlas.SetAssetSettings(settings);

        // 设置平台特定压缩
        var iosSettings = new TextureImporterPlatformSettings();
        iosSettings.name = "iPhone";
        iosSettings.format = TextureImporterFormat.ASTC_6x6;  // iOS 用 ASTC
        atlas.SetPlatformSettings(iosSettings);

        var androidSettings = new TextureImporterPlatformSettings();
        androidSettings.name = "Android";
        androidSettings.format = TextureImporterFormat.ASTC_6x6; // Android 也用 ASTC
        atlas.SetPlatformSettings(androidSettings);

        AssetDatabase.CreateAsset(atlas, "Assets/Atlases/ui_atlas.spriteatlas");
        AssetDatabase.SaveAssets();
    }
}
```

### 总结

- 图集通过合并纹理减少 Draw Call，是 2D 与 UI 性能优化的基础。
- POT 尺寸 + Padding + 合适压缩格式是图集制作的三大要点。
- 移动端优先 ASTC，PC 端可用 BC7，Web 端注意兼容性。
- 常见误区：把所有精灵塞进一张超大图集（4096+），导致内存占用过高。应按功能模块分图集。
- 实践建议：动态加载的精灵与常驻精灵分开打包，避免内存峰值。

## 第 6 讲 UI 美术与九宫格切图

### 概念

**九宫格切图（9-Slice / 9-Slicing）** 是 UI 美术中最重要的技术之一，指将一张 UI 图（如按钮背景、面板边框）切分成 9 个区域，四个角保持固定大小，四条边单向拉伸，中心区域双向拉伸。这样一张小图就能适配任意尺寸的 UI 元素，而不产生拉伸变形。这在多分辨率适配（手机/平板/PC）中是刚需。

UI 美术管线的特殊性在于：UI 资产数量大、迭代频繁、需要适配多种分辨率与比例。因此 UI 管线特别强调"可复用性"与"自动化适配"。

### 原理

九宫格的原理基于**区域分类拉伸**：

```
┌───┬─────────┬───┐
│ 1 │    2    │ 3 │   ← 1,3 角：固定不缩放
├───┼─────────┼───┤      2 上边：仅水平拉伸
│ 4 │    5    │ 6 │      4,6 边：仅垂直拉伸
├───┼─────────┼───┤      5 中心：双向拉伸
│ 7 │    8    │ 9 │      7,9 角：固定不缩放
└───┴─────────┴───┘      8 下边：仅水平拉伸
```

当 UI 元素尺寸变化时：
- 宽度变化：区域 2、5、8 水平拉伸，其余不变
- 高度变化：区域 4、5、6 垂直拉伸，其余不变
- 四个角（1、3、7、9）始终保持原始像素，保证圆角、装饰不被拉变形

这种技术的价值在于：一张 64×64 的按钮背景图，可以无损适配从 80×32 到 400×200 的任意尺寸，极大减少美术工作量与纹理内存。

**多分辨率适配**的原理则是"锚点（Anchor）+ 相对缩放"。UI 元素根据屏幕边缘的相对位置（如"距右下角 20px"）定位，而非绝对坐标。配合 Canvas Scaler（Unity）或 Safe Area（iOS），让 UI 在不同屏幕上自动调整。

### 例子

Unity 中设置九宫格的两种方式：

**方式一：Sprite Editor 手动设置**

```csharp
// 通过代码设置 Sprite 的 border（九宫格边距）
using UnityEngine;
using UnityEditor;

public class NineSliceSetup
{
    [MenuItem("Tools/Setup 9-Slice Borders")]
    static void SetupBorders()
    {
        string path = "Assets/UI/button_bg.png";
        var importer = AssetImporter.GetAtPath(path) as TextureImporter;
        if (importer == null) return;

        importer.spriteImportMode = SpriteImportMode.Single;

        // 设置九宫格边框：左10 上10 右10 下10
        // 意味着四个角各 10x10 像素保持固定
        var sheet = new SpriteSheetMetaData();
        sheet.border = new Vector4(10, 10, 10, 10);
        importer.spritesheet = new SpriteSheetMetaData[] { sheet };

        importer.SaveAndReimport();
    }
}
```

**方式二：在 UI Image 组件上启用**

```csharp
// 运行时创建九宫格 UI 元素
using UnityEngine;
using UnityEngine.UI;

public class CreateSlicedUI : MonoBehaviour
{
    void Start()
    {
        // 创建 Canvas
        var canvas = new GameObject("Canvas").AddComponent<Canvas>();
        canvas.renderMode = RenderMode.ScreenSpaceOverlay;
        canvas.gameObject.AddComponent<CanvasScaler>();
        canvas.gameObject.AddComponent<GraphicRaycaster>();

        // 创建按钮背景
        var bgObj = new GameObject("ButtonBG");
        bgObj.transform.SetParent(canvas.transform, false);

        var image = bgObj.AddComponent<Image>();
        image.sprite = Resources.Load<Sprite>("button_bg");
        image.type = Image.Type.Sliced;  // 关键：启用九宫格

        // 设置任意尺寸，九宫格保证不变形
        var rect = bgObj.GetComponent<RectTransform>();
        rect.sizeDelta = new Vector2(300, 80);  // 原图 64x64，拉伸到 300x80
        rect.anchorMin = new Vector2(0.5f, 0.5f);
        rect.anchorMax = new Vector2(0.5f, 0.5f);
        rect.anchoredPosition = Vector2.zero;
    }
}
```

```

├── button_normal.png      # 64x64，含 10px 九宫格边框
```

### 总结

- 九宫格让一张小图适配任意尺寸，是 UI 多分辨率适配的核心技术。
- 四角固定、四边单向拉伸、中心双向拉伸，记住这个规则。
- UI 资产应按"状态"（normal/pressed/disabled）成套交付。
- 常见误区：九宫格边框设得太小，导致圆角在拉伸时变形。边框应 ≥ 圆角半径。
- 实践建议：建立 UI 切图模板（PSD/FIG 模板），统一尺寸与命名，减少沟通成本。

## 第 7 讲 3D 建模基础与低模制作

### 概念

**3D 建模（3D Modeling）** 是用多边形（Polygon）构造三维物体形状的过程。在游戏美术中，我们最终交付给引擎的是**低模（Low-Poly Model）**——三角面数受控的模型，因为实时渲染对性能敏感。与之相对的是**高模（High-Poly Model）**，面数可达百万级，用于烘焙法线贴图传递细节，但不直接进引擎。

低模制作是 3D 管线的基石。一个优秀的低模师需要同时具备造型能力（形状好看）与工程意识（面数合理、布线规范、UV 友好）。低模做得好不好，直接影响后续绑定、动画、性能所有环节。

### 原理

低模制作的核心原理是**面数预算**与**布线经济性**：

1. **面数预算（Triangle Budget）**：不同平台、不同资产类型有不同的三角面预算。这背后是 GPU 渲染管线的限制——顶点处理（Vertex Shader）是瓶颈之一，面数越高，顶点变换开销越大。典型预算参考：

   | 资产类型 | 移动端 | PC/主机 | 3A 主角 |
   |---------|--------|---------|---------|
   | 主角 | 5k-15k | 30k-80k | 100k+ |
   | NPC | 2k-5k | 10k-20k | 30k-50k |
   | 道具/武器 | 0.3k-2k | 2k-8k | 5k-15k |
   | 环境（单件） | 0.1k-1k | 0.5k-3k | 1k-5k |

2. **布线经济性**：每一根线都应该"有理由存在"。布线原则包括：
   - **四边形优先**：四边形在细分、变形、平滑时行为可预测；三角形和 n-gon（多边形）可能导致不可预期结果。
   - **均匀密度**：避免一处面数密集、另一处稀疏，除非细节需要。
   - **循环边（Edge Loop）**：围绕特征的连续边线，如眼眶、嘴部的循环边，对变形至关重要。
   - **极点（Pole）控制**：超过 4 条边汇聚的点叫极点，应放在变形少的区域（如头顶、背部）。

### 例子

Blender 中用 Python 脚本创建一个简单低模木箱并检查面数：

```python
import bpy

# 清空场景
bpy.ops.object.select_all(action='SELECT')
bpy.ops.object.delete()

# 创建立方体
bpy.ops.mesh.primitive_cube_add(size=1.0, location=(0, 0, 0))
box = bpy.context.active_object
box.name = "crate_low"

# 进入编辑模式，做简单倒角
bpy.ops.object.mode_set(mode='EDIT')
bpy.ops.mesh.select_all(action='SELECT')
bpy.ops.mesh.bevel(offset=0.05, segments=2)  # 倒角 2 段

# 添加细分以做圆角效果（但保持低面数）
bpy.ops.object.mode_set(mode='OBJECT')

# 检查三角面数
mesh = box.data
mesh.calc_loop_triangles()
tri_count = len(mesh.loop_triangles)
print(f"三角面数: {tri_count}")  # 输出: 三角面数: 48

# 导出 FBX
bpy.ops.object.select_all(action='DESELECT')
box.select_set(True)
bpy.ops.export_scene.fbx(
    filepath="/home/z/my-project/download/crate_low.fbx",
    use_selection=True,
    apply_unit_scale=True,
    axis_forward='-Z', axis_up='Y'
)
print("导出完成")
```

```
【好的布线 - 关节处】        【坏的布线 - 关节处】
     ┌──┐──┌──┐                ┌──┐──┐──┐
     │  │  │  │                │  │  │  │
  ┌──┼──┼──┼──┼──┐          ┌──┼──┼──┼──┼──┐
  │  │  │  │  │  │          │  │  │  │  │  │
  └──┼──┼──┼──┼──┘          └──┼──┼──┼──┼──┘
     │  │  │  │                │  │  │  │
     └──┘──└──┘                └──┘──└──┘
  循环边清晰，弯曲时变形均匀     极点散乱，弯曲时可能撕裂
```

### 总结

- 低模是进引擎的最终模型，面数必须受控。
- 面数预算根据平台与资产类型设定，提前规划而非事后删面。
- 四边形优先、循环边保护关节、极点避开变形区。
- 常见误区：盲目追求"面数越少越好"，导致轮廓锯齿、变形失败。该有的细节不能省。
- 实践建议：建模时定期用引擎预览效果，不要只在 DCC 软件里看。

## 第 8 讲 高模雕刻技术

### 概念

**高模雕刻（High-Poly Sculpting）** 是用数百万甚至上千万多边形进行"数字雕塑"的技术，代表工具是 ZBrush。高模的目的不是直接进引擎，而是捕捉低模无法承载的细节（毛孔、划痕、铆钉、衣纹褶皱），然后通过**烘焙（Baking）** 将这些细节转移到法线贴图上，让低模在渲染时"看起来"有高模的细节。

高模雕刻让美术师摆脱了拓扑的束缚——你可以像捏泥人一样自由塑形，不用管布线是否合理。这种自由度极大提升了细节表现力，是现代 3A 美术的标配流程。

### 原理

高模雕刻的核心原理是**细分曲面**与**细节层级管理**：

1. **细分曲面（Subdivision Surface）**：通过递归细分每个四边形为 4 个小四边形，并平滑顶点位置，实现面数指数级增长。每细分一次，面数 ×4。一个 1000 面的基础模型，细分 6 次后达到 400 万面。ZBrush 的 DynaMesh 技术更进一步——动态重拓扑，让你可以随意拉伸、添加几何体而不担心面拉伸。

2. **细节层级管理**：高模制作通常分层进行，每层关注不同尺度的细节：
   - **SDiv 1-2（低细分）**：调整大形与比例
   - **SDiv 3-4（中细分）**：塑造次要形体（肌肉块、衣纹大走向）
   - **SDiv 5-6（高细分）**：添加表面细节（疤痕、毛孔、布料纹理）
   - **SDiv 7+（超高细分）**：微细节（纳米级划痕，可选）

   这种分层让你可以在低细分层调整大形而不破坏高细分层的细节——ZBrush 的 Subtool 与细分层级机制支持这种非破坏式工作流。

### 例子

ZBrush 中通过 ZScript 自动化雕刻流程的伪代码：

```
// ZScript 伪代码：高模制作流程
[VarDef, boxSize, 1.0]
[VarDef, subDivLevel, 6]

// 1. 导入低模作为基础
[IButton, "Start Sculpt", "开始雕刻流程",
    [FileLoad, "crate_low.obj"]
    [IPress, Tool:Polymesh3D:Make PolyMesh3D]

    // 2. DynaMesh 开启，动态重拓扑
    [IPress, Tool:Geometry:DynaMesh]
    [ISlider, Tool:Geometry:DynaMesh:Resolution, 128]

    // 3. 细分到高级别
    [Loop, subDivLevel,
        [IPress, Tool:Geometry:Divide]
    ]

    // 4. 添加细节（用 Alpha 笔刷）
    [IPress, Brush:Standard]
    [ISlider, Brush:Alpha, 28]  // 选择铆钉 alpha
    [ISlider, Brush:DrawSize, 15]

    // 5. 导出高模用于烘焙
    [IPress, Tool:Export]
    [FileNameSet, "crate_high.obj"]
]
```

高模与低模的细节差异示意：

```
低模（48 三角面）          高模（500,000+ 三角面）
┌─────────────┐           ┌─────────────┐
│ ┌─────────┐ │           │ ╔═════════╗ │ ← 铆钉凸起
│ │         │ │           │ ║▣▣▣▣▣▣▣▣▣║ │ ← 木纹凹凸
│ │         │ │    →      │ ║         ║ │
│ │         │ │           │ ║         ║ │
│ └─────────┘ │           │ ╚═════════╝ │
└─────────────┘           └─────────────┘
  只有基本轮廓              满是细节，但太重不能进引擎
                                     ↓ 烘焙法线贴图
                          低模 + 法线贴图 = 看起来像高模
```

### 总结

- 高模用于捕捉细节，不直接进引擎，通过烘焙传递给低模。
- 细分曲面是面数增长的核心机制，Dynamesh 让雕刻不受拓扑束缚。
- 分层管理细节（大形→次要形→表面细节），低层级调大形不破坏高层级细节。
- 常见误区：一上来就拉高细分，大形没定好就抠细节，导致返工。
- 实践建议：高模完成后，从多个角度截图与概念图对比，确认造型准确再进入烘焙。

## 第 9 讲 拓扑重建与布线规范

### 概念

**拓扑重建（Retopology / Retopo）** 是指在完成高模雕刻后，重新构建一个低面数、布线合理的网格包裹在高模表面的过程。高模虽然细节丰富，但布线混乱（Dynamesh 产生的三角面杂乱无章），无法直接用于动画或引擎。拓扑重建产出的是"干净的低模"——面数受控、四边形为主、循环边合理，既能在引擎中高效渲染，又能支持骨骼绑定与变形。

拓扑是 3D 美术中技术含量最高的环节之一。好的拓扑让模型"活"起来（动画自然），坏的拓扑让模型"死"（变形撕裂、穿模）。对于角色、生物等需要动画的资产，拓扑质量直接决定动画质量上限。

### 原理

拓扑的核心原理是**变形友好性**与**细节保留平衡**：

1. **变形友好性**：模型在动画中会发生变形（弯曲、扭转），拓扑必须支持这种变形而不产生瑕疵。关键规则：
   - **关节处循环边**：肘、膝、肩、髋等关节至少需要 3 圈循环边，保证弯曲时有足够的过渡区域。圈数太少会导致"折纸"效果——突然锐角弯折。
   - **眼眶/嘴部循环边**：面部表情动画依赖这些区域的环形布线，通常需要 3-5 圈。
   - **极点放置**：极点（valence ≠ 4 的顶点）在变形时会扭曲，应放在变形小的区域（如头顶中心、背部中线）。
   - **均匀四边形**：尽量保持四边形大小均匀，避免一处密集一处稀疏。

2. **细节保留平衡**：拓扑要在"面数少"与"保留高模轮廓"之间平衡。策略是**密度梯度**——细节多的区域（脸、手）面数密集，细节少的区域（躯干、大腿内侧）面数稀疏。这就像地图的等高线——陡峭处密集，平缓处稀疏。

### 例子

Blender 中使用 Python 脚本辅助拓扑检查：

```python

import bmesh

def check_topology(obj_name):
    # 检查模型拓扑质量
    obj = bpy.data.objects.get(obj_name)
    if not obj or obj.type != 'MESH':
        print("对象不存在或不是网格")
        return

    mesh = obj.data
    bm = bmesh.new()
    bm.from_mesh(mesh)

    # 统计
    verts = len(bm.verts)
    edges = len(bm.edges)
    faces = len(bm.faces)

    # 统计四边形/三角形/n-gon
    quads = sum(1 for f in bm.faces if len(f.verts) == 4)
    tris = sum(1 for f in bm.faces if len(f.verts) == 3)
    ngons = sum(1 for f in bm.faces if len(f.verts) > 4)

    # 统计极点（valence != 4 的顶点）
    poles = sum(1 for v in bm.verts if len(v.link_edges) != 4)

    # 三角面数（用于引擎）
    bm.faces.ensure_lookup_table()
    tri_count = sum(max(0, len(f.verts) - 2) for f in bm.faces)

    print(f"=== 拓扑报告: {obj_name} ===")
    print(f"顶点数: {verts}")
    print(f"边数: {edges}")
    print(f"面数: {faces} (四边形: {quads}, 三角形: {tris}, n-gon: {ngons})")
    print(f"引擎三角面数: {tri_count}")
    print(f"极点数: {poles} (理想: < 总顶点数的 10%)")
    print(f"四边形占比: {quads/len(bm.faces)*100:.1f}% (理想: > 95%)")

    bm.free()

# 执行检查
```

## 第 10 讲 UV 展开与排布

### 概念

**UV 展开（UV Unwrapping）** 是将 3D 模型的表面"剥皮"并平铺到 2D 平面上的过程，目的是让 2D 贴图能正确映射到 3D 表面。UV 是两个坐标轴（U 水平、V 垂直），每个顶点除了 3D 空间坐标（x,y,z）外，还有 UV 坐标（u,v），决定它在贴图上的采样位置。

UV 展开是贴图制作的前置工序——没有 UV，就无法绘制贴图。而 UV 展开的质量直接影响贴图绘制效率与最终效果：接缝位置不当会破坏纹理连续性，打包率低会浪费纹理分辨率，重叠 UV 会导致烘焙失败。

### 原理

UV 展开的核心原理是**面积保持**与**接缝最小化**：

1. **面积保持（Area Preservation）**：理想情况下，3D 表面上每个三角形的面积，与 UV 空间中对应三角形的面积成固定比例。如果比例不一致，贴图在某些区域会被拉伸（采样密度低）或压缩（采样密度高）。实际中完全等面积不可能（球面无法完美展开到平面），但应尽量减少拉伸。工具通常提供"拉伸可视化"（绿=好，红=差）。

2. **接缝最小化（Seam Minimization）**：UV 展开必然产生接缝（Seam）——3D 表面上被"剪开"的边。接缝处的贴图需要手工对齐，且在 Mipmap 缩小时可能产生渗色。因此接缝应：
   - 放在不显眼的位置（如头顶内侧、腋下、裤腿内侧）
   - 数量尽量少（但太少会导致拉伸严重，需平衡）
   - 避免穿过细节密集区（如脸部）

3. **打包率（Packing Efficiency）**：UV 岛在 0-1 UV 空间内的填充率。好的打包能让 70-85% 的纹理空间被有效利用。低打包率意味着纹理分辨率浪费——同样 1024 贴图，打包率 50% 的实际有效分辨率只有 512。

### 例子

Blender 中用 Python 脚本自动展开 UV 并检查打包率：

```python
import bpy
import bmesh
import mathutils

def auto_unwrap_and_check(obj_name):
    obj = bpy.data.objects.get(obj_name)
    if not obj:
        return

    # 确保有 UV 层
    if not obj.data.uv_layers:
        obj.data.uv_layers.new(name="UVMap")

    bpy.context.view_layer.objects.active = obj
    bpy.ops.object.mode_set(mode='EDIT')

    bm = bmesh.from_edit_mesh(obj.data)
    bm.faces.ensure_lookup_table()

    # 全选
    for f in bm.faces:
        f.select = True

    # 标记接缝（简化版：按锐边自动标记）
    bpy.ops.mesh.select_all(action='SELECT')
    bpy.ops.mesh.mark_seam(clear=True)

    # 基于角度自动标记接缝
    sharp_angle = mathutils.Vector((0, 0, 1))
    for edge in bm.edges:
        if edge.select:
            # 计算两面的夹角
            faces = edge.link_faces
            if len(faces) == 2:
                angle = faces[0].normal.angle(faces[1].normal)
                if angle > 0.5:  # 约 30 度
                    edge.seam = True

    # 展开
    bpy.ops.uv.unwrap(method='ANGLE_BASED', margin=0.02)

    # 排布（打包）
    bpy.ops.uv.select_all(action='SELECT')
    bpy.ops.uv.pack_islands(margin=0.02, rotate=True)

    bpy.ops.object.mode_set(mode='OBJECT')

    # 计算打包率
    uv_layer = obj.data.uv_layers.active
    total_area = 0
    for face in obj.data.polygons:
        uv_verts = [uv_layer.data[li].uv for li in face.loop_indices]
        if len(uv_verts) >= 3:
            # 计算三角形面积
            v0 = uv_verts[0]
            v1 = uv_verts[1]
            v2 = uv_verts[2]
            area = abs((v1.x - v0.x) * (v2.y - v0.y) -
                       (v2.x - v0.x) * (v1.y - v0.y)) / 2
            total_area += area

    # UV 空间总面积 = 1.0 (0-1 范围)
    packing_eff = total_area  # 简化计算
    print(f"UV 打包率估算: {packing_eff*100:.1f}%")

auto_unwrap_and_check("character_low")
```

### 总结

- UV 是 3D 到 2D 贴图的映射桥梁，没有 UV 就没有贴图。
- 接缝放隐蔽处、数量适中、避免穿过细节区。
- 打包率目标 70%+，低打包率浪费纹理分辨率。
- 常见误区：UV 拉伸严重却不处理，导致贴图变形。务必用拉伸可视化检查。
- 实践建议：复杂模型分多个 UV 岛，按材质/部位分组，便于多人协作绘制贴图。

## 第 11 讲 PBR 材质理论基础

### 概念

**PBR（Physically Based Rendering，基于物理的渲染）** 是当今游戏与影视行业的标准材质与光照模型。它通过模拟真实世界中光线与物质相互作用的物理规律，让材质在不同光照环境下都能呈现正确的外观——同一个材质在正午阳光下和黄昏暖光中都能"看起来对"。PBR 之前的老式材质模型（如 Phong、Blinn-Phong）依赖美术"调"参数，换一个场景就可能不对；PBR 则让材质"物理正确"，跨场景一致性大幅提升。

PBR 的核心是两套贴图工作流：**金属度-粗糙度流（Metallic-Roughness）** 和 **高光-平滑度流（Specular-Smoothness）**。前者是 Unity、Unreal、Substance 的默认方案，后者是旧版 Unity 的方案。本讲以金属度-粗糙度流为主。

### 原理

PBR 的物理基础是 **BRDF（Bidirectional Reflectance Distribution Function，双向反射分布函数）**，它描述光线从某个方向射入表面后，向各个方向反射的能量分布。游戏实时渲染中常用的 BRDF 模型是 **Cook-Torrance 模型**，它将反射分为两部分：

1. **漫反射（Diffuse / Lambert）**：光线进入物体内部，经过多次散射后均匀向各方向射出。非金属的反射以漫反射为主。颜色由 Base Color（反照率）决定。

2. **镜面反射（Specular / Cook-Torrance）**：光线在物体表面直接反射，遵循反射定律。金属的反射以镜面反射为主。镜面反射的强度与角度依赖 **Fresnel 效应**——掠射角（ grazing angle）时反射增强。

PBR 的关键参数：

| 参数 | 含义 | 非金属范围 | 金属范围 |
|------|------|-----------|---------|
| Base Color (Albedo) | 漫反射颜色 | 30-240 sRGB | 180-255 sRGB（反射色） |
| Metallic | 是否金属 | 0（纯黑） | 1（纯白） |
| Roughness | 表面粗糙度 | 0-1 | 0-1 |
| Normal | 表面微细节 | 切线空间法线 | 切线空间法线 |
| AO | 环境光遮蔽 | 0-1 灰度 | 0-1 灰度 |

**金属与非金属的本质区别**：金属没有漫反射（自由电子吸收进入内部的光），所有反射都是镜面反射，反射率高达 70-100%。非金属的镜面反射率很低（2-5%），大部分能量以漫反射形式发出。这就是为什么 Metallic 贴图通常是二值化的（0 或 1）——半金属在物理上很少见（除非是氧化过渡态或特殊材质）。

## 第 12 讲 贴图烘焙技术

### 概念

**贴图烘焙（Texture Baking）** 是将高模的细节信息"投影"到低模的 UV 贴图上的过程。烘焙产出多种贴图：法线贴图（Normal Map）、环境光遮蔽（AO）、曲率（Curvature）、位置（Position）等。其中法线贴图最重要——它让低模在渲染时"看起来"拥有高模的表面细节，是实时渲染中性价比最高的细节增强手段。

烘焙是连接高模与低模的关键环节。烘焙质量取决于三个因素：低模与高模的对齐、UV 的质量、烘焙参数（Cage、偏移、抗锯齿）的设置。

### 原理

烘焙的核心原理是**射线投影（Ray Casting）**：

1. **射线投影过程**：对低模 UV 空间中的每个像素，引擎从低模表面对应位置发射一条射线（通常沿法线方向），射线击中高模表面后，记录高模在该点的信息（如法线方向、颜色、高度），写入贴图像素。这样，高模的细节就被"转移"到了低模的贴图上。

2. **Cage（烘焙笼）**：直接沿低模法线发射射线可能出问题——如果高模有凸起超出低模法线范围，射线会射偏。Cage 是一个包裹低模的"壳"，射线从 Cage 表面发射而非低模表面，能更准确地命中高模。Cage 的膨胀距离需要调整——太小则漏掉高模凸起，太大则采样到错误区域。

3. **法线贴图的空间**：法线贴图存储的是**切线空间（Tangent Space）** 法线，而非世界空间。切线空间以每个顶点的法线为 Z 轴，这样法线贴图可以随模型旋转而正确表现（世界空间法线贴图则不能旋转）。切线空间法线贴图呈蓝紫色调（因为 Z 轴朝外，B 通道值大）。

4. **常见烘焙问题**：
   - **接缝（Seams）**：UV 接缝处法线不连续，产生可见接缝。需确保切线计算一致。
   - **锯齿（Aliasing）**：高模细节频率高于贴图分辨率时产生。需提高贴图分辨率或加抗锯齿。
   - **投影错误（Projection Errors）**：射线射到错误的高模区域。需调整 Cage 或偏移距离。

### 例子

使用 Substance Painter 的 Python API 进行批量烘焙（伪代码）：

```python
# Substance Painter Python API 伪代码

def bake_maps(low_mesh_path, high_mesh_path, output_size=2048):
    # 烘焙法线、AO、曲率贴图

    # 配置烘焙参数
    bake_config = {
        "mesh": low_mesh_path,
        "high_poly_meshes": [high_mesh_path],
        "output_size": output_size,  # 2048x2048
        "antialiasing": True,
        "ao_multiplier": 1.0,
        "ignore_backface": True,
        "use_cage": True,

    print("曲率烘焙完成")

    print("位置贴图烘焙完成")
```

## 第 13 讲 Substance 工作流实践

### 概念

**Substance 工作流** 是以 Adobe Substance 3D Painter（材质绘制）和 Substance 3D Designer（程序化材质）为核心的现代贴图制作流程。它的核心理念是**非破坏式（Non-Destructive）** 与**程序化（Procedural）**——通过图层、遮罩、智能材质、生成器等组合，让贴图可随时修改、可复用、可参数化。

传统贴图制作（如 Photoshop 手绘）是"破坏式"的——画上去的笔触难以修改，换一个模型就要重画。Substance 工作流则像"配方"——调整参数就能改变结果，同一套智能材质可应用到不同模型上，极大提升效率与一致性。

### 原理

Substance 工作流的核心原理是**图层栈与节点图**：

1. **Painter 的图层栈**：类似 Photoshop，但每个图层可以是填充、笔刷、生成器、滤镜。图层通过遮罩控制作用区域，遮罩可以基于烘焙的 AO/Curvature/Position 自动生成（如"只在边缘添加磨损"）。图层混合模式遵循 PBR 物理逻辑（如 Add 模式增加高度，Multiply 模式降低粗糙度）。

2. **Designer 的节点图**：完全程序化的材质构建方式。每个节点是一个操作（噪声、模糊、混合、变形），节点之间连接形成数据流。最终输出贴图。节点图的优势是可参数化——暴露几个参数（如"磨损程度""锈迹密度"），在引擎中实时调整。

3. **智能材质（Smart Materials）**：Painter 中的预设材质组，由多个图层按特定逻辑组合而成。应用时自动根据模型的 AO/Curvature/Position 调整效果。例如"生锈金属"智能材质会自动在凹陷处堆积锈迹、在边缘添加磨损。这让同一套材质在不同模型上都能正确表现。

4. **智能遮罩（Smart Masks）**：基于烘焙贴图自动生成的遮罩。常见类型：
   - **Ambient Occlusion**：凹陷处遮罩（用于污垢堆积）
   - **Curvature**：边缘遮罩（用于磨损、掉漆）
   - **Position**：上下位置遮罩（用于水渍、积雪）
   - **Thickness**：厚度遮罩（用于次表面散射）

### 例子

Substance Painter 中用 Python API 创建智能材质层（伪代码）：


### 总结

- Substance 工作流以非破坏式、程序化为核心，提升效率与一致性。
- 智能材质 + 智能遮罩让同一套材质自动适配不同模型。

- 常见误区：把 Substance Painter 当 Photoshop 用，全是手绘层，失去程序化优势。
- 实践建议：建立项目"智能材质库"，团队共享，保证风格统一。

## 第 14 讲 骨骼绑定与蒙皮权重

### 概念

**骨骼绑定（Rigging）** 是为 3D 模型创建一套可控制的"骨架"系统，让静态模型能够动起来。绑定包含三个核心部分：**骨骼（Skeleton/Joint）**——模拟真实骨骼结构的层级关节；**控制器（Controller）**——动画师操作的 UI 控件（如圆圈、箭头）；**蒙皮权重（Skinning Weights）**——定义每个顶点受哪些骨骼影响及影响程度。

绑定是建模与动画之间的桥梁。建模师交付的是静态模型，动画师需要的是"能动"的模型——绑定师的工作就是把静态模型变成可操控的"提线木偶"。绑定质量直接决定动画师的工作效率与最终动画质量。

### 原理

骨骼绑定的核心原理是**层级变换传递**与**权重平滑变形**：

1. **层级变换传递（Forward Kinematics, FK）**：骨骼以树状层级组织，父骨骼的变换（移动、旋转、缩放）会传递给所有子骨骼。例如，旋转肩关节会带动肘、腕、手指全部跟随。这种层级让动画师只需控制少数"根骨骼"，末端骨骼自动跟随。

2. **蒙皮权重（Linear Blend Skinning, LBS）**：每个顶点的最终位置 = 所有影响它的骨骼变换的加权平均。公式为：

   ```
   V' = Σ(Wi × Mi × V)  /  ΣWi
   ```

   其中 Wi 是第 i 块骨骼的权重，Mi 是该骨骼的变换矩阵，V 是顶点原始位置。通常每个顶点受 2-4 块骨骼影响（引擎限制通常为 4 块）。权重之和应为 1.0。权重分配决定了变形质量——关节处需要平滑过渡（如肘部皮肤同时受上臂和前臂影响），非关节处可以单骨骼完全控制。

3. **约束（Constraints）**：高级绑定使用约束实现自动化行为：
   - **IK（Inverse Kinematics）**：反向运动学，给定末端位置，自动解算中间关节角度。如"手放在桌上"时，肘部自动弯曲到合适角度。
   - **Aim Constraint**：让对象始终朝向目标（如眼睛看鼠标）
   - **Parent Constraint**：一个对象跟随另一个对象移动（如武器跟随手）
   - **Pole Vector**：IK 解算时的方向参考，防止关节翻转

### 例子

Blender 中用 Python 脚本创建简单骨架并绑定：

```python
import bpy

def create_simple_rig(mesh_name):
    # 为网格创建简单的人形骨架并绑定

    # 1. 创建骨架
    bpy.ops.object.armature_add(enter_editmode=True)
    armature = bpy.context.active_object
    armature.name = "character_rig"

    # 删除默认骨骼，从头创建
    bpy.ops.armature.select_all(action='SELECT')
    bpy.ops.armature.delete()

    # 2. 创建骨骼层级
    # 髋部（根骨骼）
    bpy.ops.armature.bone_primitive_add(name="hip")
    hip = armature.data.edit_bones["hip"]
    hip.head = (0, 0, 0.9)
    hip.tail = (0, 0, 1.0)

    # 脊椎
    bpy.ops.armature.bone_primitive_add(name="spine")
    spine = armature.data.edit_bones["spine"]
    spine.head = (0, 0, 1.0)
    spine.tail = (0, 0, 1.4)
    spine.parent = hip

    # 头部
    bpy.ops.armature.bone_primitive_add(name="head")
    head = armature.data.edit_bones["head"]
    head.head = (0, 0, 1.4)
    head.tail = (0, 0, 1.7)
    head.parent = spine

    # 左腿
    bpy.ops.armature.bone_primitive_add(name="leg_L")
    leg_l = armature.data.edit_bones["leg_L"]
    leg_l.head = (0.1, 0, 0.9)
    leg_l.tail = (0.1, 0, 0.5)
    leg_l.parent = hip

    bpy.ops.armature.bone_primitive_add(name="knee_L")
    knee_l = armature.data.edit_bones["knee_L"]
    knee_l.head = (0.1, 0, 0.5)
    knee_l.tail = (0.1, 0, 0.05)
    knee_l.parent = leg_l

    # 退出编辑模式
    bpy.ops.object.mode_set(mode='OBJECT')

    # 3. 绑定（蒙皮）
    mesh = bpy.data.objects.get(mesh_name)
    if mesh:
        mesh.select_set(True)
        armature.select_set(True)
        bpy.context.view_layer.objects.active = armature
        bpy.ops.object.parent_set(type='ARMATURE_AUTO')

        # 自动权重分配
        print("自动蒙皮权重完成")

    # 4. 添加 IK 约束（左腿）
    bpy.ops.object.mode_set(mode='POSE')
    knee_pose = armature.pose.bones["knee_L"]
    ik_constraint = knee_pose.constraints.new(type='IK')
    ik_constraint.target = armature
    ik_constraint.subtarget = "knee_L"  # 简化示例
    ik_constraint.chain_count = 2  # 影响 2 块骨骼

    print("骨架绑定完成")

create_simple_rig("character_low")
```

蒙皮权重的可视化示意：

```
顶点 V 在肘关节处：
  上臂骨骼权重: 0.4  ─┐
  前臂骨骼权重: 0.6  ─┤── 总和 = 1.0
                       │
  V' = 0.4 × (上臂变换 × V) + 0.6 × (前臂变换 × V)
  
  弯曲前臂时，V 平滑跟随，不会撕裂

【好的权重】              【坏的权重】
  上臂 0.5 | 前臂 0.5      上臂 1.0 | 前臂 0.0
  平滑过渡                 硬切，弯曲时撕裂
```

### 总结

- 绑定 = 骨骼 + 控制器 + 蒙皮权重，让静态模型可动。
- 层级变换传递（FK）让少数根骨骼控制全身，IK 反向解算提升效率。
- 蒙皮权重决定变形质量，关节处需平滑过渡（2-4 骨骼影响）。
- 常见误区：自动权重不检查直接用，导致关节穿模或撕裂。必须手动修权重。
- 实践建议：建立项目"绑定模板"（标准人形骨架），新角色套用模板，保证动画可复用。

## 第 15 讲 关键帧动画与状态机

### 概念

**关键帧动画（Keyframe Animation）** 是通过在时间轴上标记关键姿势（Key Pose），由系统自动插值生成中间帧的技术。动画师不需要画每一帧，只需定义"起点"和"终点"，软件计算过渡。**动画状态机（Animation State Machine / Animator）** 是在引擎中管理多个动画片段之间切换逻辑的系统——如"待机→走→跑→跳"的切换条件与过渡规则。

关键帧动画是游戏动画的基础（过场动画、角色动作），状态机则是实时交互动画的核心（玩家操控的角色）。两者结合，才能让角色既"动得好看"又"响应操作"。

### 原理

关键帧动画与状态机的核心原理是**插值**与**状态转换**：

1. **插值（Interpolation）**：两个关键帧之间，系统根据插值算法生成中间帧。常见插值类型：
   - **线性插值（Linear）**：匀速变化，机械感强，适合旋转的齿轮等。
   - **贝塞尔插值（Bezier/Ease-In-Out）**：先慢后快再慢，自然感强，适合角色动作。
   - **阶跃（Step/Constant）**：不插值，直接跳变，适合像素动画或离散状态。
   
   对骨骼动画，插值在骨骼的变换矩阵上进行，需注意旋转用四元数插值（SLERP）避免万向锁。

2. **动画曲线（Animation Curve）**：关键帧之间的速度变化由曲线控制。横轴是时间，纵轴是属性值。曲线的切线（Tangent）决定加速度——陡峭切线=快速变化，平缓切线=慢速变化。好的动画师通过调整曲线让动作有"节奏感"（如攻击动作的"蓄力-爆发-收招"三段节奏）。

3. **状态机（State Machine）**：引擎中的动画管理器，包含：
   - **状态（State）**：每个状态对应一个动画片段（如 Idle、Walk、Run）
   - **转换（Transition）**：状态之间的切换，由条件触发（如速度 > 0.5 时 Idle→Walk）
   - **参数（Parameter）**：触发转换的变量（如 Speed、IsGrounded、AttackTrigger）
   - **混合树（Blend Tree）**：根据参数在多个动画间平滑混合（如根据速度混合走/跑）

4. **过渡（Transition）**：状态切换时的平滑过渡，避免"跳变"。过渡有持续时间（如 0.2 秒），在过渡期间两个动画按权重混合。过渡条件可以是"立即""等动画结束""等退出时间"。

### 例子

Unity 中用脚本配置 Animator Controller：

```csharp
using UnityEngine;
using UnityEditor;
using UnityEditor.Animations;

public class AnimatorSetup
{
    [MenuItem("Tools/Setup Animator")]
    static void SetupAnimator()
    {
        // 创建 Animator Controller
        var controller = AnimatorController.CreateAnimatorControllerAtPath(
            "Assets/Animation/player_controller.controller");

        // 添加参数
        controller.AddParameter("Speed", AnimatorControllerParameterType.Float);
        controller.AddParameter("IsGrounded", AnimatorControllerParameterType.Bool);
        controller.AddParameter("Jump", AnimatorControllerParameterType.Trigger);

        // 获取根状态机
        var rootSM = controller.layers[0].stateMachine;

        // 创建状态
        var idleState = rootSM.AddState("Idle");
        var walkState = rootSM.AddState("Walk");
        var runState = rootSM.AddState("Run");
        var jumpState = rootSM.AddState("Jump");

        // 加载动画片段
        var idleClip = AssetDatabase.LoadAssetAtPath<AnimationClip>(
            "Assets/Animations/idle.anim");
        var walkClip = AssetDatabase.LoadAssetAtPath<AnimationClip>(
            "Assets/Animations/walk.anim");
        var runClip = AssetDatabase.LoadAssetAtPath<AnimationClip>(
            "Assets/Animations/run.anim");
        var jumpClip = AssetDatabase.LoadAssetAtPath<AnimationClip>(
            "Assets/Animations/jump.anim");

        idleState.motion = idleClip;
        walkState.motion = walkClip;
        runState.motion = runClip;
        jumpState.motion = jumpClip;

        // 设置默认状态
        rootSM.defaultState = idleState;

        // 创建转换：Idle → Walk（Speed > 0.1）
        var idleToWalk = idleState.AddTransition(walkState);
        idleToWalk.AddCondition(AnimatorConditionMode.Greater, 0.1f, "Speed");
        idleToWalk.duration = 0.2f;
        idleToWalk.hasExitTime = false;

        // Walk → Run（Speed > 5.0）
        var walkToRun = walkState.AddTransition(runState);
        walkToRun.AddCondition(AnimatorConditionMode.Greater, 5.0f, "Speed");
        walkToRun.duration = 0.15f;

        // Run → Walk（Speed < 5.0）
        var runToWalk = runState.AddTransition(walkState);
        runToWalk.AddCondition(AnimatorConditionMode.Less, 5.0f, "Speed");
        runToWalk.duration = 0.15f;

        // Walk → Idle（Speed < 0.1）
        var walkToIdle = walkState.AddTransition(idleState);
        walkToIdle.AddCondition(AnimatorConditionMode.Less, 0.1f, "Speed");
        walkToIdle.duration = 0.2f;

        // 任意状态 → Jump（Jump Trigger）
        var anyToJump = rootSM.AddAnyStateTransition(jumpState);
        anyToJump.AddCondition(AnimatorConditionMode.If, 0, "Jump");
        anyToJump.duration = 0.05f;  // 跳跃需要快速响应
        anyToJump.hasExitTime = false;

        // Jump → Idle（动画结束后）
        var jumpToIdle = jumpState.AddTransition(idleState);
        jumpToIdle.hasExitTime = true;
        jumpToJump.exitTime = 0.9f;  // 90% 时切换
        jumpToIdle.duration = 0.2f;

        AssetDatabase.SaveAssets();
        Debug.Log("Animator 配置完成");
    }
}
```

```
                    ┌──────────┐
          Speed>0.1 │  Idle    │ Speed<0.1
        ┌─────────→│ (待机)    │←─────────┐
        │           └──────────┘          │
        │              │                  │
        │          Speed>0.1              │ Speed<0.1
        │              ↓                  │
        │           ┌──────────┐          │
        │           │  Walk    │──────────┘
        │           │ (走)     │
        │           └──────────┘
        │              │
        │          Speed>5.0
```

### 总结

- 关键帧动画通过插值生成中间帧，动画曲线控制节奏感。
- 状态机管理动画片段切换，转换由参数触发，过渡保证平滑。
- 混合树根据参数在多个动画间平滑混合（如走跑混合）。
- 常见误区：转换条件设得太复杂，状态机难以维护。应保持简洁，复杂逻辑用子状态机。
- 实践建议：动画片段首尾帧对齐（循环动画），避免循环时跳变。

## 第 16 讲 动画混合与 IK 系统

### 概念

**动画混合（Animation Blending）** 是在多个动画片段之间按权重平滑过渡的技术，让角色动作更自然。例如角色在移动时同时播放"走"和"持枪瞄准"两个动画，上半身瞄准、下半身行走——这就是混合。**IK（Inverse Kinematics，反向运动学）** 是给定末端位置（如脚的位置），自动计算中间关节（膝盖）角度的技术，让角色能"踩准地面"或"手握物体"。

混合与 IK 是让游戏动画"活"起来的关键技术。没有它们，角色只能播放预设动画，无法适应动态场景（如斜坡行走、手扶栏杆、脚踩楼梯）。

### 原理

动画混合与 IK 的核心原理是**权重叠加**与**逆向解算**：

1. **动画混合（Blend Tree）**：引擎在每帧对多个动画的骨骼变换按权重叠加。例如：
   - 走路动画权重 0.7 + 跑步动画权重 0.3 = 快走效果
   - 上半身瞄准动画权重 0.5 + 下半身走路动画权重 1.0 = 边走边瞄准
   
   混合方式有：
   - **1D Blend**：根据一个参数混合（如速度混合走/跑）
   - **2D Blend**：根据两个参数混合（如速度+方向混合走/跑/左移/右移）
   - **Additive Blend**：叠加动画（如在基础走路上叠加"受伤倾斜"）

2. **IK 解算**：给定末端效应器（End Effector，如脚、手）的目标位置，反向计算骨骼链上各关节的旋转。常用算法：
   - **CCD（Cyclic Coordinate Descent）**：迭代调整每个关节，逐步逼近目标。简单但收敛慢。
   - **FABRIK（Forward And Backward Reaching Inverse Kinematics）**：前后迭代，更自然，收敛快。
   - **解析 IK（Analytic IK）**：对两段骨骼链有精确公式解，速度快，常用于手脚 IK。

3. **IK 在游戏中的应用**：
   - **足部 IK**：脚始终贴地，适应斜坡与楼梯
   - **手部 IK**：手握武器、扶栏杆、开门
   - **注视 IK（Look-At IK）**：头/眼朝向目标（如看向玩家）
   - **身体 IK**：全身姿势调整（如靠墙时身体倾斜）

4. **IK 与 FK 的混合**：通常骨骼链用 FK（动画师预设），末端用 IK（动态适应）。引擎支持"IK 权重"——0 时纯 FK，1 时纯 IK，中间值混合。

### 例子

Unity 中配置足部 IK 的脚本：

```csharp
using UnityEngine;

[RequireComponent(typeof(Animator))]
public class FootIK : MonoBehaviour
{
    private Animator animator;
    public LayerMask groundLayer = 1 << 0;  // 默认层
    public float footOffset = 0.1f;          // 脚底到射线原点的偏移
    public float footRadius = 0.15f;         // 射线检测半径
    public float ikWeight = 1.0f;            // IK 权重

    void Start()
    {
        animator = GetComponent<Animator>();
    }

    void OnAnimatorIK(int layerIndex)
    {
        if (!animator) return;

        // 左脚 IK
        SetFootIK(AvatarIKGoal.LeftFoot, animator.leftFootHeightWeight);

        // 右脚 IK
        SetFootIK(AvatarIKGoal.RightFoot, animator.rightFootHeightWeight);
    }

    void SetFootIK(AvatarIKGoal foot, float weight)
    {
        // 获取脚的当前位置
        Vector3 footPos = animator.GetIKPosition(foot);
        Quaternion footRot = animator.GetIKRotation(foot);

        // 从脚上方发射射线
        Vector3 rayOrigin = footPos + Vector3.up * (footOffset + footRadius);
        RaycastHit hit;

        if (Physics.SphereCast(rayOrigin, footRadius, Vector3.down,
            out hit, footOffset + footRadius * 2, groundLayer))
        {
            // 设置 IK 位置到地面
            Vector3 targetPos = hit.point;
            targetPos.y += footOffset;
            animator.SetIKPosition(foot, targetPos);

            // 设置 IK 旋转（对齐地面法线）
            Quaternion targetRot = Quaternion.FromToRotation(Vector3.up, hit.normal)
                                 * footRot;
            animator.SetIKRotation(foot, targetRot);

            // 设置权重
            animator.SetIKPositionWeight(foot, ikWeight);
            animator.SetIKRotationWeight(foot, ikWeight);
        }
        else
        {
            // 没检测到地面，降低 IK 权重
            animator.SetIKPositionWeight(foot, 0);
            animator.SetIKRotationWeight(foot, 0);
        }
    }
}
```

### 总结

- 动画混合让多个动画按权重叠加，适应复杂动作需求。
- IK 反向解算关节角度，让角色适应动态环境（踩地、握物）。
- 足部 IK 是最常见的应用，让角色在斜坡/楼梯上不"穿地"。
- 常见误区：IK 权重设为 1.0 导致动画僵硬，应适当混合 FK。
- 实践建议：IK 目标位置用射线检测动态获取，避免硬编码位置。

## 第 17 讲 Shader 与材质图基础

### 概念

**Shader（着色器）** 是运行在 GPU 上的小程序，决定每个像素的最终颜色。它是美术与程序的交叉领域——技术美术（TA）通过编写或连接 Shader，实现各种视觉效果：水流、火焰、全息投影、卡通渲染、溶解特效等。现代引擎提供**材质图（Material Graph / Shader Graph）**，让美术无需写代码就能通过连接节点构建 Shader，大幅降低了门槛。

Shader 是美术管线的"最后一公里"——模型、贴图、动画都准备好后，Shader 决定它们如何被"看见"。一个会写 Shader 的 TA 能让同样的资产呈现完全不同的风格（写实 vs 卡通 vs 像素），是美术团队中价值最高的角色之一。

### 原理

Shader 的核心原理是**渲染管线阶段编程**：

1. **渲染管线（Rendering Pipeline）**：GPU 将 3D 场景转换为 2D 图像的流程，主要阶段：
   - **顶点着色器（Vertex Shader）**：对每个顶点执行，计算其最终屏幕位置。可在此做顶点动画（如风吹草动、波浪）。
   - **曲面细分（Tessellation）**（可选）：动态增加几何体细节。
   - **几何着色器（Geometry Shader）**（可选）：增删图元（如粒子生成）。
   - **片元着色器（Fragment/Pixel Shader）**：对每个像素执行，计算最终颜色。这是美术最常打交道的阶段——采样贴图、计算光照、混合效果。

2. **Shader 数据流**：
   - **顶点输入**：位置、法线、UV、切线等属性
   - **Uniform 变量**：全局参数（如时间、灯光位置、贴图）
   - **Varying 变量**：顶点着色器传给片元着色器的插值数据
   - **输出**：片元颜色（RGBA）

3. **常见 Shader 技术**：
   - **PBR Lit**：标准 PBR 渲染（前几讲已介绍）
   - **Unlit**：不受光照影响，纯贴图颜色（如 UI、特效）
   - **Cartoon/Cel**：卡通渲染，用阶梯化光照模拟动画风格
   - **Dissolve**：溶解特效，用噪声贴图控制透明度
   - **Parallax**：视差贴图，用高度图模拟立体感
   - **Water**：水流，用 UV 动画 + 顶点波动

4. **材质图（Shader Graph）**：节点式可视化编程。每个节点是一个操作（采样、数学运算、混合），节点连接形成数据流。优点：直观、所见即所得、无需记忆语法。缺点：复杂逻辑比代码冗长，性能优化不如手写。

### 例子

Unity Shader Graph 中实现溶解特效的节点连接（伪描述）：

```
节点图结构：

[Time] ──→ [Sine] ──→ [Multiply (0.1)] ──→ [Add to UV] ──→ [Sample Noise Texture]
                                                                    ↓
                                                              [Multiply (Dissolve Amount)]
                                                                    ↓
[Alpha Clip Threshold] ←── [Subtract] ←── [Noise Value]
                                    ↑
                              [Dissolve Slider (0-1)]

[Base Color Texture] ──→ [Sample] ──→ [Albedo Output]
[Edge Glow Color] ──────────────────→ [Emission Output] (只在溶解边缘发光)
```

对应的 HLSL 代码（手写版）：

```hlsl
// Dissolve.shader - 溶解特效
Shader "Custom/Dissolve"
{
    Properties
    {
        _MainTex ("Base Texture", 2D) = "white" {}
        _NoiseTex ("Noise Texture", 2D) = "white" {}
        _DissolveAmount ("Dissolve Amount", Range(0, 1)) = 0.5
        _EdgeWidth ("Edge Width", Range(0, 0.1)) = 0.02
        _EdgeColor ("Edge Color", Color) = (1, 0.5, 0, 1)
        _ScrollSpeed ("Scroll Speed", Float) = 0.5
    }

    SubShader
    {
        Tags { "RenderType"="Transparent" "Queue"="Transparent" }
        Blend SrcAlpha OneMinusSrcAlpha

        Pass
        {
            HLSLPROGRAM
            #pragma vertex vert
            #pragma fragment frag

            #include "UnityCG.cginc"

            struct appdata
            {
                float4 vertex : POSITION;
                float2 uv : TEXCOORD0;
            };

            struct v2f
            {
                float4 pos : SV_POSITION;
                float2 uv : TEXCOORD0;
            };

            sampler2D _MainTex;
            sampler2D _NoiseTex;
            float _DissolveAmount;
            float _EdgeWidth;
            float4 _EdgeColor;
            float _ScrollSpeed;

            v2f vert(appdata v)
            {
                v2f o;
                o.pos = UnityObjectToClipPos(v.vertex);
                o.uv = v.uv;
                return o;
            }

            fixed4 frag(v2f i) : SV_Target
            {
                // 滚动噪声 UV
                float2 noiseUV = i.uv + float2(_Time.y * _ScrollSpeed, 0);
                
                // 采样噪声
                float noise = tex2D(_NoiseTex, noiseUV).r;
                
                // 计算溶解阈值
                float threshold = _DissolveAmount;
                
                // 丢弃低于阈值的像素
                clip(noise - threshold);
                
                // 采样基础颜色
                fixed4 col = tex2D(_MainTex, i.uv);
                
                // 边缘发光：在阈值附近一定范围内
                float edge = smoothstep(threshold, threshold + _EdgeWidth, noise);
                col.rgb = lerp(_EdgeColor.rgb, col.rgb, edge);
                col.rgb += _EdgeColor.rgb * (1 - edge) * 2;  // 边缘加强发光
                
                return col;
            }
            ENDHLSL
        }
    }
}
```

### 总结

- Shader 是 GPU 程序，决定每个像素的最终颜色，是美术管线的"最后一公里"。
- 顶点着色器处理位置，片元着色器处理颜色，材质图让美术无需写代码。
- 常见技术：PBR、卡通、溶解、水流、视差等。
- 常见误区：Shader 过于复杂导致性能问题（如过多分支、过多采样）。需做性能分析。
- 实践建议：简单效果用材质图，复杂或性能敏感的用手写 HLSL。

## 第 18 讲 引擎资产导入与配置

### 概念

**引擎资产导入（Asset Import）** 是将 DCC 软件（Maya/Blender/ZBrush/Substance）产出的美术资产（模型、贴图、动画）导入游戏引擎（Unity/Unreal）并配置参数的过程。导入不是简单的"拖进去"——每个资产都需要设置正确的导入参数（缩放、轴向、压缩、LOD 等），否则会出现"在 Blender 里好好的，进引擎就变形"的问题。

导入配置是美术管线的"质检关卡"。好的导入流程能自动检查资产规范、批量设置参数、生成预制体，大幅减少手工错误。大型项目通常由 TA 编写导入工具脚本，实现"一键导入 + 自动配置"。

### 原理

引擎资产导入的核心原理是**格式转换**与**参数映射**：

1. **格式转换**：DCC 软件使用各自的格式（.blend、.ma、.zpr），引擎需要通用格式。常用中间格式：
   - **FBX**：Autodesk 的通用 3D 交换格式，支持网格、骨骼、动画、材质。最常用。
   - **OBJ**：简单网格格式，不支持动画与骨骼。
   - **glTF/GLB**：Khronos 的现代 3D 格式，支持 PBR，逐渐流行。
   - **USD**：Pixar 的通用场景描述，Unreal 原生支持，未来趋势。

2. **坐标轴与缩放**：不同软件的坐标系不同：
   - **Maya**：Y-up，右手坐标系，1 unit = 1 cm
   - **Blender**：Z-up，右手坐标系，1 unit = 1 m
   - **Unity**：Y-up，左手坐标系，1 unit = 1 m
   - **Unreal**：Z-up，左手坐标系，1 unit = 1 cm
   
   导入时需转换轴向与缩放，否则模型会侧躺或大小不对。

3. **贴图压缩**：引擎对贴图做平台特定的压缩，减小内存占用：
   - **BC1 (DXT1)**：不透明贴图，4:1 压缩
   - **BC3 (DXT5)**：带透明度，4:1 压缩
   - **BC5**：法线贴图专用，双通道高精度
   - **BC7**：高质量通用，现代 GPU 支持
   - **ASTC**：移动端主流，可调压缩率
   - **ETC2**：移动端备选

4. **LOD（Level of Detail）**：自动或手动生成多个细节级别，远处用低面数版本。导入时可配置 LOD 生成参数（面数比例、屏幕大小切换阈值）。

### 例子

Unity 中用脚本自动导入并配置资产：

```csharp
using UnityEngine;
using UnityEditor;

public class AssetImportPipeline : AssetPostprocessor
{
    // 模型导入时调用
    void OnPostprocessModel(GameObject go)
    {
        // 检查命名规范
        if (!assetPath.Contains("_low") && !assetPath.Contains("_mid"))
        {
            Debug.LogWarning($"模型命名不规范: {assetPath}，应包含 _low 或 _mid");
        }

        // 配置模型导入参数
        var importer = assetImporter as ModelImporter;
        if (importer != null)
        {
            importer.globalScale = 1.0f;           // 缩放
            importer.useFileUnits = true;
            importer.meshCompression = ModelImporterMeshCompression.Medium;
            importer.isReadable = false;            // 不可读（性能优化）
            importer.optimizeMeshData = true;       // 优化网格数据
            importer.animationType = ModelImporterAnimationType.Generic;

            // 材质导入设置
            importer.importMaterials = false;       // 不导入材质，用引擎材质
            importer.materialName = ModelImporterMaterialName.BasedOnMaterialName;

            // 法线计算
            importer.importNormals = ModelImporterNormals.Calculate;
            importer.normalCalculationMode = ModelImporterNormalCalculationMode.AngleWeighted;
            importer.normalSmoothingAngle = 60.0f;

            // 切线
            importer.importTangents = ModelImporterTangents.CalculateMikk;

            // LOD 配置（如果文件名包含 _lod）
            if (assetPath.Contains("_lod"))
            {
                ConfigureLOD(go);
            }
        }

        // 自动添加组件
        AddComponentsRecursively(go);
    }

    void ConfigureLOD(GameObject go)
    {
        var lodGroup = go.GetComponent<LODGroup>();
        if (lodGroup == null)
            lodGroup = go.AddComponent<LODGroup>();

        var lods = new LOD[3];
        // LOD0: 60% 面数，屏幕占比 > 60%
        lods[0] = new LOD(0.6f, new Renderer[] { GetRenderer(go) });
        // LOD1: 30% 面数，屏幕占比 > 30%
        lods[1] = new LOD(0.3f, new Renderer[] { GetRenderer(go) });
        // LOD2: 10% 面数，屏幕占比 > 10%
        lods[2] = new LOD(0.1f, new Renderer[] { GetRenderer(go) });

        lodGroup.SetLODs(lods);
        lodGroup.RecalculateBounds();
    }

    Renderer GetRenderer(GameObject go)
    {
        return go.GetComponentInChildren<Renderer>();
    }

    void AddComponentsRecursively(GameObject go)
    {
        // 如果是角色，添加 Animator
        if (go.name.ToLower().Contains("character"))
        {
            if (go.GetComponent<Animator>() == null)
                go.AddComponent<Animator>();
        }

        // 如果是道具，添加碰撞体
        if (go.name.ToLower().Contains("prop"))
        {
            if (go.GetComponent<MeshCollider>() == null)
            {
                var col = go.AddComponent<MeshCollider>();
                col.convex = true;
            }
        }
    }

    // 贴图导入时调用
    void OnPostprocessTexture(Texture2D texture)
    {
        var importer = assetImporter as TextureImporter;

        // 根据路径自动设置贴图类型
        if (assetPath.Contains("_normal"))
        {
            importer.textureType = TextureImporterType.NormalMap;
            importer.textureCompression = TextureImporterCompression.Compressed;
            importer.crunchedCompression = true;
            importer.compressionQuality = 80;
        }
        else if (assetPath.Contains("_metallic") || assetPath.Contains("_roughness"))
        {
            importer.textureType = TextureImporterType.SingleChannel;
            importer.textureCompression = TextureImporterCompression.Compressed;
        }
        else if (assetPath.Contains("_ui"))
        {
            importer.textureType = TextureImporterType.Sprite;
            importer.mipmapEnabled = false;  // UI 不需要 mipmap
        }
        else
        {
            importer.textureType = TextureImporterType.Default;
            importer.textureCompression = TextureImporterCompression.Compressed;
            importer.crunchedCompression = true;
            importer.compressionQuality = 80;
        }

        // 设置 sRGB
        bool isLinear = assetPath.Contains("_normal") ||
                        assetPath.Contains("_metallic") ||
                        assetPath.Contains("_roughness") ||
                        assetPath.Contains("_ao");
        importer.sRGBTexture = !isLinear;

        // 最大尺寸
        importer.maxTextureSize = 2048;
    }
}
```

### 总结

- 导入是 DCC 到引擎的格式转换与参数配置，不是简单拖拽。
- 注意坐标轴、缩放、贴图压缩、LOD 等参数。
- 用 AssetPostprocessor 实现自动化导入，减少手工错误。
- 常见误区：法线贴图没设为 NormalMap 类型，导致渲染错误。
- 实践建议：建立导入检查清单，TA 编写脚本自动验证资产规范。

## 第 19 讲 LOD 与性能优化

### 概念

**LOD（Level of Detail，细节级别）** 是根据物体与摄像机的距离切换不同精度版本的技术——近处用高精度模型，远处用低精度模型，在不影响视觉的前提下大幅降低渲染开销。**性能优化（Performance Optimization）** 是让游戏在目标帧率（如 60fps）下流畅运行的一系列技术，包括 Draw Call 优化、内存优化、GPU 优化等。

LOD 与性能优化是美术管线的"收尾工程"。前面所有环节（建模、贴图、动画）产出的资产如果性能不达标，游戏就无法流畅运行。技术美术需要掌握各种优化手段，在"视觉质量"与"运行性能"之间找到平衡点。

### 原理

LOD 与性能优化的核心原理是**资源分级**与**瓶颈定位**：

1. **LOD 工作原理**：每个物体有多个精度版本（LOD0、LOD1、LOD2...），引擎根据屏幕占比（Screen Size）自动切换：
   - **LOD0**：最高精度，屏幕占比 > 60% 时使用
   - **LOD1**：中等精度，屏幕占比 30%-60%
   - **LOD2**：低精度，屏幕占比 10%-30%
   - **Culled**：屏幕占比 < 10% 时剔除（不渲染）
   
   LOD 生成方式：
   - **手动**：美术制作多个版本，质量最高但成本高
   - **自动（ProOptimizer/Decimation）**：算法减面，快速但可能丢细节
   - **程序化（Simplygon/Houdini）**：专业工具，质量与效率平衡

2. **Draw Call 优化**：Draw Call 是 CPU 向 GPU 发出的渲染命令，每次调用有开销。优化手段：
   - **静态合批（Static Batching）**：将不动的物体合并为一个大网格
   - **动态合批（Dynamic Batching）**：小物体实时合并（有限制）
   - **GPU Instancing**：相同网格与材质的物体用一次 Draw Call 渲染多个实例
   - **SRP Batcher**：Unity 的渲染管线优化，减少材质切换开销

3. **内存优化**：
   - **贴图压缩**：用 BC/ASTC 格式，减少显存占用
   - **贴图图集**：多张小贴图合并为一张大贴图
   - **Mipmap**：远处用低分辨率版本，减少采样带宽
   - **资源卸载**：不用的资源及时卸载（Addressables）

4. **GPU 优化**：
   - **Overdraw 优化**：避免半透明物体叠加过多层
   - **Shader 复杂度**：减少分支、采样次数
   - **顶点数控制**：LOD + 遮挡剔除

```csharp
using UnityEngine;
using UnityEditor;

public class LODOptimizer
{
    [MenuItem("Tools/Optimize LOD")]
    static void OptimizeLOD()
    {
        var selected = Selection.activeGameObject;
        if (selected == null) return;

        var lodGroup = selected.GetComponent<LODGroup>();
        if (lodGroup == null)
            lodGroup = selected.AddComponent<LODGroup>();

        var meshFilter = selected.GetComponentInChildren<MeshFilter>();
        if (meshFilter == null) return;

        var originalMesh = meshFilter.sharedMesh;
        int originalVertCount = originalMesh.vertexCount;

        // 生成 LOD 级别
        LOD[] lods = new LOD[3];

        // LOD0: 原始精度，60% 屏幕占比
        lods[0] = new LOD(0.6f, new Renderer[] { meshFilter.GetComponent<Renderer>() });

        // LOD1: 50% 顶点，30% 屏幕占比
        var lod1Mesh = GenerateSimplifiedMesh(originalMesh, 0.5f);
        lods[1] = new LOD(0.3f, CreateLODRenderer(selected, lod1Mesh, "LOD1"));

        // LOD2: 20% 顶点，10% 屏幕占比
        var lod2Mesh = GenerateSimplifiedMesh(originalMesh, 0.2f);
        lods[2] = new LOD(0.1f, CreateLODRenderer(selected, lod2Mesh, "LOD2"));

        lodGroup.SetLODs(lods);
        lodGroup.RecalculateBounds();

        // 性能统计
        Debug.Log($"LOD 优化完成:");
        Debug.Log($"  LOD0: {originalVertCount} 顶点");
        Debug.Log($"  LOD1: {lod1Mesh.vertexCount} 顶点 ({lod1Mesh.vertexCount * 100 / originalVertCount}%)");
        Debug.Log($"  LOD2: {lod2Mesh.vertexCount} 顶点 ({lod2Mesh.vertexCount * 100 / originalVertCount}%)");
    }

    static Mesh GenerateSimplifiedMesh(Mesh source, float quality)
    {
        // 使用 Unity 的 Mesh Simplifier（需要包）
        // 这里用简化算法示意
        var simplified = new Mesh();
        simplified.name = source.name + $"_LOD_{quality}";

        // 实际项目中用 Simplygon 或 Unity Mesh Simplifier 包
        // simplified = MeshSimplifier.Simplify(source, quality);

        // 简化版：直接复制（实际应调用减面算法）
        simplified.vertices = source.vertices;
        simplified.triangles = source.triangles;
        simplified.uv = source.uv;
        simplified.normals = source.normals;
        simplified.RecalculateBounds();

        return simplified;
    }

    static Renderer[] CreateLODRenderer(GameObject parent, Mesh mesh, string name)
    {
        var lodObj = new GameObject(name);
        lodObj.transform.SetParent(parent.transform, false);

        var mf = lodObj.AddComponent<MeshFilter>();
        mf.sharedMesh = mesh;

        var mr = lodObj.AddComponent<MeshRenderer>();
        // 复制原材质
        var origRenderer = parent.GetComponentInChildren<MeshRenderer>();
        if (origRenderer != null)
            mr.sharedMaterials = origRenderer.sharedMaterials;

        return new Renderer[] { mr };
    }
}
```

### 总结

- LOD 根据距离切换精度版本，是性价比最高的优化手段。
- Draw Call 优化靠合批与 Instancing，内存优化靠压缩与图集。
- 性能优化先定位瓶颈（CPU/GPU/内存），再针对性优化。
- 常见误区：过度优化早期阶段，应先做正确再做快。
- 实践建议：用 Profiler 持续监控，建立性能预算并定期检查。

## 第 20 讲 自动化工具与脚本

### 概念

**自动化工具（Automation Tools）** 是用脚本（Python/C#）自动完成重复性美术工作的程序。在美术管线中，大量工作是重复的——批量导出、批量压缩、命名检查、LOD 生成、贴图格式转换等。手动完成这些工作既慢又容易出错，自动化工具能将"小时级"工作缩短为"秒级"，并保证一致性。

自动化是美术管线的"终极形态"。一个成熟的美术管线，应该让美术师专注于"创作"（设计、雕刻、绘制），而把"技术性重复工作"交给脚本。技术美术（TA）的核心职责之一就是开发和维护这些自动化工具。

### 原理

自动化工具的核心原理是**流程标准化**与**脚本化**：

1. **流程标准化**：自动化前提是流程标准化——如果每个美术师的工作方式不同，无法自动化。标准化包括：
   - **命名规范**：统一的文件命名（如 `char_hero_body_low_v01.fbx`）
   - **目录结构**：统一的文件夹组织（如 `Assets/Models/Characters/`）
   - **资产模板**：统一的起始文件（如 Blender 模板、Substance 模板）
   - **导出预设**：统一的导出参数（FBX 版本、轴向、缩放）

2. **脚本化（Scripting）**：用脚本调用 DCC 软件与引擎的 API：
   - **Blender Python（bpy）**：Blender 的 Python API，可控制几乎所有功能
   - **Maya Python（PyMEL/cmds）**：Maya 的脚本接口
   - **Unity Editor Scripting（C#）**：Unity 编辑器扩展
   - **Unreal Python & C++**：Unreal 的脚本接口
   - **Substance Python API**：Substance Painter/Designer 的脚本

3. **工具类型**：
   - **批量处理工具**：一次处理多个文件（如批量导出 FBX）
   - **检查工具**：验证资产是否符合规范（如命名检查、面数检查）
   - **生成工具**：自动生成资产（如 LOD 生成、图集打包）
   - **流程工具**：串联多个步骤（如"一键从 Blender 到引擎"）

4. **CI/CD 集成**：大型项目将自动化工具集成到持续集成系统（如 Jenkins），实现：
   - 提交资产时自动检查
   - 自动构建与测试
   - 自动部署到测试环境

### 例子

Blender 中批量导出工具的 Python 脚本：

```python
import bpy
import os
import json

class BatchExporter:
    # 批量导出工具：将场景中的所有对象导出为 FBX

    def __init__(self, output_dir, export_config=None):
        self.output_dir = output_dir
        self.config = export_config or self.get_default_config()
        self.report = []

        os.makedirs(output_dir, exist_ok=True)

    def get_default_config(self):
        return {
            "format": "FBX",
            "axis_forward": "-Z",
            "axis_up": "Y",
            "apply_unit_scale": True,
            "unit_scale": 1.0,
            "apply_transform": True,
            "bake_animation": False,
            "mesh_smooth_type": "FACE",
            "use_metadata": True,
        }

    def validate_naming(self, obj_name):
        # 验证命名规范：type_name_part_version.ext
        parts = obj_name.split("_")
        if len(parts) < 3:
            return False, f"命名部分不足: {obj_name} (应至少 type_name_part)"

        valid_types = ["char", "prop", "env", "veh", "fx"]
        if parts[0].lower() not in valid_types:
            return False, f"类型前缀无效: {parts[0]} (应为 {valid_types})"

        return True, "OK"

    def export_object(self, obj):
        # 导出单个对象
        # 验证命名
        valid, msg = self.validate_naming(obj.name)
        if not valid:
            self.report.append({"object": obj.name, "status": "FAIL", "reason": msg})
            return False

        # 只导出网格对象
        if obj.type != 'MESH':
            self.report.append({"object": obj.name, "status": "SKIP", "reason": f"非网格: {obj.type}"})
            return False

        # 检查三角面数
        mesh = obj.data
        mesh.calc_loop_triangles()
        tri_count = len(mesh.loop_triangles)
        if tri_count > 100000:
            self.report.append({
                "object": obj.name,
                "status": "WARN",
                "reason": f"面数过高: {tri_count}"
            })

        # 导出文件名
        filename = f"{obj.name}.fbx"
        filepath = os.path.join(self.output_dir, filename)

        # 取消全选，只选当前对象
        bpy.ops.object.select_all(action='DESELECT')
        obj.select_set(True)
        bpy.context.view_layer.objects.active = obj

        # 导出 FBX
        try:
            bpy.ops.export_scene.fbx(
                filepath=filepath,
                use_selection=True,
                axis_forward=self.config["axis_forward"],
                axis_up=self.config["axis_up"],
                apply_unit_scale=self.config["apply_unit_scale"],
                apply_scale_options='LOCAL',
                bake_anim=self.config["bake_animation"],
                mesh_smooth_type=self.config["mesh_smooth_type"],
                use_metadata=self.config["use_metadata"],
            )

            # 验证导出
            if os.path.exists(filepath):
                size = os.path.getsize(filepath)
                self.report.append({
                    "object": obj.name,
                    "status": "OK",
                    "file": filename,
                    "size_kb": size // 1024,
                    "tris": tri_count
                })
                return True
            else:
                self.report.append({
                    "object": obj.name,
                    "status": "FAIL",
                    "reason": "导出文件不存在"
                })
                return False

        except Exception as e:
            self.report.append({
                "object": obj.name,
                "status": "ERROR",
                "reason": str(e)
            })
            return False

    def export_all(self):
        # 导出场景中所有对象
        print(f"开始批量导出，输出目录: {self.output_dir}")

        objects = [obj for obj in bpy.data.objects if obj.type == 'MESH']
        print(f"找到 {len(objects)} 个网格对象")

        success = 0
        for obj in objects:
            if self.export_object(obj):
                success += 1

        # 生成报告
        self.generate_report()

        print(f"导出完成: {success}/{len(objects)} 成功")
        return self.report

    def generate_report(self):
        # 生成导出报告
        report_path = os.path.join(self.output_dir, "export_report.json")
        with open(report_path, 'w', encoding='utf-8') as f:
            json.dump({
                "total": len(self.report),
                "success": sum(1 for r in self.report if r["status"] == "OK"),
                "warnings": sum(1 for r in self.report if r["status"] == "WARN"),
                "failures": sum(1 for r in self.report if r["status"] in ("FAIL", "ERROR")),
                "details": self.report
            }, f, indent=2, ensure_ascii=False)

        print(f"报告已保存: {report_path}")


# 使用示例
exporter = BatchExporter(
    output_dir="/home/z/my-project/download/exported_fbx",
    export_config={
        "format": "FBX",
        "axis_forward": "-Z",
        "axis_up": "Y",
        "apply_unit_scale": True,
        "unit_scale": 1.0,
        "apply_transform": True,
        "bake_animation": False,
        "mesh_smooth_type": "FACE",
        "use_metadata": True,
    }
)
exporter.export_all()
```

Unity 中批量检查资产规范的编辑器工具：

```csharp
using UnityEngine;
using UnityEditor;
using System.IO;
using System.Text.RegularExpressions;

public class AssetValidator : EditorWindow
{
    [MenuItem("Tools/Asset Validator")]
    static void ShowWindow()
    {
        GetWindow<AssetValidator>("资产检查器");
    }

    void OnGUI()
    {
        GUILayout.Label("资产规范检查", EditorStyles.boldLabel);
        GUILayout.Space(10);

        if (GUILayout.Button("检查所有模型", GUILayout.Height(30)))
        {
            CheckAllModels();
        }

        if (GUILayout.Button("检查所有贴图", GUILayout.Height(30)))
        {
            CheckAllTextures();
        }

        if (GUILayout.Button("检查命名规范", GUILayout.Height(30)))
        {
            CheckNamingConventions();
        }

        if (GUILayout.Button("生成资产报告", GUILayout.Height(30)))
        {
            GenerateAssetReport();
        }
    }

    static void CheckAllModels()
    {
        string[] guids = AssetDatabase.FindAssets("t:Model", new[] { "Assets" });
        int issues = 0;

        foreach (string guid in guids)
        {
            string path = AssetDatabase.GUIDToAssetPath(guid);
            var importer = AssetImporter.GetAtPath(path) as ModelImporter;

            if (importer == null) continue;

            // 检查项
            if (importer.isReadable)
            {
                Debug.LogWarning($"[{path}] isReadable=true，应设为 false 以节省内存");
                issues++;
            }

            if (!importer.optimizeMeshData)
            {
                Debug.LogWarning($"[{path}] optimizeMeshData=false，应设为 true");
                issues++;
            }

            // 检查面数
            var mesh = AssetDatabase.LoadAssetAtPath<Mesh>(path);
            if (mesh != null && mesh.triangles.Length / 3 > 50000)
            {
                Debug.LogWarning($"[{path}] 三角面数 {mesh.triangles.Length/3}，超过 50000");
                issues++;
            }
        }

        Debug.Log($"模型检查完成: {guids.Length} 个模型，{issues} 个问题");
    }

    static void CheckAllTextures()
    {
        string[] guids = AssetDatabase.FindAssets("t:Texture", new[] { "Assets" });
        int issues = 0;

        foreach (string guid in guids)
        {
            string path = AssetDatabase.GUIDToAssetPath(guid);
            var importer = AssetImporter.GetAtPath(path) as TextureImporter;

            if (importer == null) continue;

            // 法线贴图检查
            if (path.ToLower().Contains("_normal") &&
                importer.textureType != TextureImporterType.NormalMap)
            {
                Debug.LogError($"[{path}] 法线贴图未设为 NormalMap 类型！");
                issues++;
            }

            // 贴图尺寸检查
            if (importer.maxTextureSize > 2048 && !path.Contains("UI"))
            {
                Debug.LogWarning($"[{path}] 贴图尺寸 > 2048，确认是否必要");
                issues++;
            }

            // UI 贴图不应有 mipmap
            if (path.Contains("UI") && importer.mipmapEnabled)
            {
                Debug.LogWarning($"[{path}] UI 贴图不应启用 mipmap");
                issues++;
            }
        }

        Debug.Log($"贴图检查完成: {guids.Length} 张贴图，{issues} 个问题");
    }

    static void CheckNamingConventions()
    {
        // 命名规范正则: type_name_part_version.ext
        string pattern = @"^(char|prop|env|veh|fx)_[a-z]+_[a-z]+(_v\d+)?$";
        Regex regex = new Regex(pattern, RegexOptions.IgnoreCase);

        string[] guids = AssetDatabase.FindAssets("t:Object", new[] { "Assets/Models" });
        int issues = 0;

        foreach (string guid in guids)
        {
            string path = AssetDatabase.GUIDToAssetPath(guid);
            string filename = Path.GetFileNameWithoutExtension(path);

            if (!regex.IsMatch(filename))
            {
                Debug.LogWarning($"[{path}] 命名不符合规范: {filename}");
                issues++;
            }
        }

        Debug.Log($"命名检查完成: {issues} 个问题");
    }

    static void GenerateAssetReport()
    {
        string reportPath = "Assets/asset_report.txt";
        using (StreamWriter writer = new StreamWriter(reportPath))
        {
            writer.WriteLine("=== 资产报告 ===");
            writer.WriteLine($"生成时间: {System.DateTime.Now}");
            writer.WriteLine();

            // 统计各类资产数量
            string[] types = { "Model", "Texture", "Material", "AnimationClip", "AudioClip" };
            foreach (string type in types)
            {
                string[] guids = AssetDatabase.FindAssets($"t:{type}", new[] { "Assets" });
                writer.WriteLine($"{type}: {guids.Length} 个");
            }

            writer.WriteLine();
            writer.WriteLine("=== 贴图内存估算 ===");

            long totalTextureMemory = 0;
            string[] texGuids = AssetDatabase.FindAssets("t:Texture", new[] { "Assets" });
            foreach (string guid in texGuids)
            {
                string path = AssetDatabase.GUIDToAssetPath(guid);
                var tex = AssetDatabase.LoadAssetAtPath<Texture2D>(path);
                if (tex != null)
                {
                    long mem = tex.width * tex.height * 4;  // 粗略估算
                    totalTextureMemory += mem;
                }
            }
            writer.WriteLine($"贴图总内存: {totalTextureMemory / 1024 / 1024} MB");
        }

        AssetDatabase.Refresh();
        Debug.Log($"资产报告已生成: {reportPath}");
    }
}
```

### 总结

- 自动化工具将重复性工作脚本化，是美术管线的终极形态。

- 常见误区：过早自动化，流程未稳定就写工具，导致工具频繁返工。
- 实践建议：先手动跑通流程，再脚本化，最后集成到 CI/CD。
