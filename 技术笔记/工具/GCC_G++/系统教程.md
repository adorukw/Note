# 第一章：基础入门

## 第 1 讲 GCC 与 G++ 简介及区别

### 概念

**GCC**（GNU Compiler Collection，GNU 编译器套件）是由自由软件基金会（FSF）开发的一套开源编译器集合，最初全称为 "GNU C Compiler"，后来因为支持了 C++、Fortran、Ada、Go、D 等多种语言，改名为 "GNU Compiler Collection"。

**G++** 是 GCC 套件中的一个前端驱动程序，专门用于编译 C++ 程序。换句话说，G++ 是 GCC 的一个"子集"或"特化版本"，它内部调用的仍然是 GCC 的核心编译器，但在默认行为上针对 C++ 做了调整。

### 原理

GCC 本质上是一个**驱动程序**（driver），它根据输入文件的扩展名（`.c`、`.cpp`、`.s`、`.o` 等）和命令行参数，决定调用哪个语言前端（cc1、cc1plus 等）进行编译，然后调用汇编器 `as` 生成目标文件，最后调用链接器 `ld` 生成可执行文件。

GCC 与 G++ 的核心区别在于**默认行为**：

| 行为 | gcc | g++ |
|------|-----|-----|
| 编译 `.c` 文件 | 当作 C 语言 | 当作 C++ |
| 编译 `.cpp` 文件 | 当作 C++（但仍需 g++ 链接 C++ 库） | 当作 C++ |
| 链接阶段 | 默认不链接 C++ 标准库（libstdc++） | 默认链接 libstdc++ |
| 预定义宏 | 不定义 `__cplusplus` | 定义 `__cplusplus` |

一个常见误区是认为 "gcc 只能编译 C，g++ 只能编译 C++"。实际上 gcc 也能编译 `.cpp` 文件，只是链接时不会自动链接 C++ 标准库，需要手动加 `-lstdc++`。

### 例子

**示例 1：用 gcc 编译 C 程序**

```c
// hello.c
#include <stdio.h>
int main() {
    printf("Hello from C!\n");
    return 0;
}
```

```bash
gcc hello.c -o hello
./hello
# 输出: Hello from C!
```

**示例 2：用 g++ 编译 C++ 程序**

```cpp
// hello.cpp
#include <iostream>
int main() {
    std::cout << "Hello from C++!" << std::endl;
    return 0;
}
```

```bash
g++ hello.cpp -o hello_cpp
./hello_cpp
# 输出: Hello from C++!
```

**示例 3：用 gcc 编译 C++ 程序（需要手动链接）**

```bash
gcc hello.cpp -o hello_gcc -lstdc++
# 如果不加 -lstdc++，会报 "undefined reference to std::cout" 等错误
```

### 总结

- GCC 是编译器套件，G++ 是其中专门处理 C++ 的前端驱动
- gcc 编译 `.cpp` 时不会自动链接 C++ 标准库，g++ 会
- 实际开发中：C 程序用 gcc，C++ 程序用 g++，这是最简单的区分方式
- 底层都调用相同的汇编器和链接器，只是默认参数不同

## 第 2 讲 环境安装与第一个程序

### 概念

在开始使用 GCC/G++ 之前，需要先在系统中安装编译器套件。不同操作系统的安装方式不同，本讲以 Linux（Ubuntu/Debian 和 CentOS/RHEL）为主，兼顾 macOS 和 Windows（WSL/MinGW）。

### 原理

Linux 系统通常通过包管理器（apt、yum、dnf、pacman 等）安装软件。GCC 套件在 Debian 系中打包为 `gcc`、`g++`、`build-essential` 等包；在 Red Hat 系中打包为 `gcc`、`gcc-c++`、`Development Tools` 组。

安装后，可以通过 `which gcc`、`gcc --version` 等命令验证安装是否成功。GCC 的版本号格式为 `主版本.次版本.补丁号`（如 11.4.0），不同版本支持的 C/C++ 标准不同。

### 例子

**安装（Ubuntu/Debian）**：

```bash
sudo apt update
sudo apt install build-essential
# build-essential 包含 gcc、g++、make 及必要头文件
```

**安装（CentOS/RHEL）**：

```bash
sudo yum groupinstall "Development Tools"
# 或
sudo dnf groupinstall "Development Tools"
```

**验证安装**：

```bash
gcc --version
# gcc (Ubuntu 11.4.0-1ubuntu1~22.04) 11.4.0

g++ --version
# g++ (Ubuntu 11.4.0-1ubuntu1~22.04) 11.4.0

make --version
# GNU Make 4.3
```

**第一个程序**：

```c
// first.c
#include <stdio.h>

int main() {
    printf("My first GCC program!\n");
    printf("Compiled with GCC.\n");
    return 0;
}
```

```bash
gcc first.c -o first
./first
# 输出:
# My first GCC program!
# Compiled with GCC.
```

**查看编译器详细信息**：

```bash
gcc -v
# 输出编译器的配置信息，包括安装路径、线程模型、目标平台等
```

### 总结

- Linux 下推荐安装 `build-essential`（Debian 系）或 `Development Tools`（Red Hat 系）
- 用 `gcc --version` 和 `g++ --version` 验证安装
- 最简编译命令：`gcc 源文件 -o 可执行文件`
- macOS 自带的 clang 可能别名化为 gcc，可用 `gcc --version` 确认实际编译器

## 第 3 讲 编译流程总览

### 概念

一个 C/C++ 源文件变成可执行程序，需要经过**四个阶段**：预处理（Preprocessing）、编译（Compilation）、汇编（Assembly）、链接（Linking）。GCC 将这四个阶段串联起来，用户通常一条命令即可完成全部流程，也可以分步执行以观察中间产物。

### 原理

四个阶段的作用如下：

```
源文件(.c/.cpp)
    │  预处理 (-E)     展开宏、包含头文件、处理条件编译
    ▼
预处理后文件(.i)
    │  编译 (-S)       语法分析、语义分析、生成汇编代码
    ▼
汇编文件(.s)
    │  汇编 (-c)       将汇编指令翻译为机器码
    ▼
目标文件(.o)
    │  链接            合并多个目标文件、解析符号引用、链接库
    ▼
可执行文件(elf/a.out)
```

| 阶段 | 工具 | 产物 | GCC 选项 |
|------|------|------|----------|
| 预处理 | cpp（C Preprocessor） | `.i` 文件 | `-E` |
| 编译 | cc1 / cc1plus | `.s` 文件 | `-S` |
| 汇编 | as | `.o` 文件 | `-c` |
| 链接 | ld | 可执行文件 | 默认（无选项） |

理解这四个阶段非常重要，因为很多编译错误和选项都对应特定阶段。例如，"未定义引用"（undefined reference）发生在链接阶段，而"未声明标识符"（undeclared identifier）发生在编译阶段。

### 例子

**完整流程演示**：

```c
// demo.c
#include <stdio.h>
#define PI 3.14159

int main() {
    double area = PI * 2 * 2;
    printf("Area = %f\n", area);
    return 0;
}
```

```bash
# 一步到位
gcc demo.c -o demo

# 分步执行
gcc -E demo.c -o demo.i    # 预处理，生成 .i 文件
gcc -S demo.i -o demo.s    # 编译，生成 .s 汇编文件
gcc -c demo.s -o demo.o    # 汇编，生成 .o 目标文件
gcc demo.o -o demo         # 链接，生成可执行文件

./demo
# 输出: Area = 12.566360
```

**观察中间文件大小**：

```bash
wc -l demo.c demo.i demo.s
# demo.c:   7 行（源代码）
# demo.i: 800+ 行（头文件展开后）
# demo.s:  30+ 行（汇编代码）
```

可以看到，预处理后的 `.i` 文件因为展开了 `stdio.h`，行数大幅增加。

### 总结

- 编译四阶段：预处理 → 编译 → 汇编 → 链接
- 对应选项：`-E`、`-S`、`-c`、无选项
- 中间产物：`.i`、`.s`、`.o`、可执行文件
- 分步编译有助于理解编译过程、定位错误、排查问题
- 后续章节会逐一深入讲解每个阶段

## 第 4 讲 GCC/G++ 命令基本语法

### 概念

GCC/G++ 命令的基本语法为：

```
gcc [选项] 源文件... [选项] [目标文件]
```

虽然语法看起来简单，但 GCC 有数百个选项，掌握其分类和组织方式是高效使用的关键。选项大致可分为：输出控制、警告、调试、优化、标准、路径、链接、预处理等几大类。

### 原理

GCC 命令行的解析规则：

1. **选项顺序敏感**：某些选项（如 `-l`、`-L`）的位置会影响链接行为，库必须放在引用它的目标文件之后
2. **选项可组合**：`-Wall -Wextra` 可写成 `-Wall -Wextra`，但 `-O2 -g` 不能合并为 `-Og2`
3. **参数传递**：有些选项带参数（如 `-o output`），有些不带（如 `-Wall`）
4. **多源文件**：可同时指定多个源文件，GCC 会分别编译后统一链接

GCC 选项的命名规律：单字母选项用 `-` 开头（如 `-c`），多字母选项用 `--` 开头（如 `--version`），但很多多字母选项也支持单 `-`（如 `-Wall`）。

### 例子

**基本用法**：

```bash
# 编译单个文件
gcc main.c -o main

# 编译多个文件
gcc main.c utils.c -o program

# 只编译不链接（生成目标文件）
gcc -c main.c              # 生成 main.o

# 指定输出文件名
gcc main.c -o myprogram
```

**常用选项组合**：

```bash
# 带警告和调试信息
gcc -Wall -g main.c -o main

# 指定 C 标准
gcc -std=c99 -Wall main.c -o main

# 包含自定义头文件目录
gcc -I./include main.c -o main

# 链接数学库
gcc math_demo.c -o math_demo -lm
```

**查看帮助**：

```bash
gcc --help              # 常用选项帮助
man gcc                 # 完整手册
gcc -v --help 2>&1 | less  # 所有选项（非常长）
```

**选项分类速查**：

| 类别 | 常用选项 | 说明 |
|------|----------|------|
| 输出控制 | `-o` `-c` `-S` `-E` | 控制输出文件类型 |
| 警告 | `-Wall` `-Wextra` `-Werror` | 控制警告级别 |
| 调试 | `-g` `-ggdb` `-pg` | 生成调试/性能信息 |
| 优化 | `-O0` `-O1` `-O2` `-O3` `-Os` | 优化级别 |
| 标准 | `-std=c99` `-std=c++17` | 语言标准 |
| 路径 | `-I` `-L` `-l` | 头文件/库路径 |
| 预处理 | `-D` `-U` `-include` | 宏定义 |

### 总结

- 基本语法：`gcc [选项] 源文件 -o 输出文件`
- 选项分多类，建议按类别记忆
- 注意 `-l` 库选项要放在源文件之后（链接顺序敏感）
- 用 `gcc --help` 和 `man gcc` 查阅完整文档
- 后续章节会详细讲解每个类别的选项

# 第二章：编译流程详解

## 第 5 讲 预处理阶段（-E）

### 概念

预处理（Preprocessing）是编译的第一个阶段，由预处理器（C Preprocessor，cpp）完成。它的主要任务是处理源代码中所有以 `#` 开头的预处理指令，包括头文件包含（`#include`）、宏展开（`#define`）、条件编译（`#ifdef` 等）、删除注释等。预处理后的输出是一个纯 C/C++ 代码文件（`.i` 或 `.ii`），不再包含任何 `#` 指令。

### 原理

预处理器按以下顺序工作：

1. **三字符替换与行连接**：处理三字符序列（如 `??=` 替换为 `#`），将行尾有 `\` 的多行连接为一行
2. **注释删除**：将 `/* */` 和 `//` 注释替换为单个空格
3. **宏展开**：展开所有 `#define` 定义的宏，包括对象式宏和函数式宏
4. **头文件包含**：将 `#include` 指定的头文件内容原样插入到当前位置
5. **条件编译**：根据 `#if`、`#ifdef`、`#ifndef` 等条件，保留或删除代码段
6. **行标记插入**：在输出中插入 `#line` 标记，便于编译器报错时定位原始位置

预处理**不做语法检查**，只做文本替换。因此，即使代码有语法错误，预处理仍能成功完成。

### 例子

**示例源文件**：

```c
// preproc.c
#include <stdio.h>
#define MAX(a, b) ((a) > (b) ? (a) : (b))
#define VERSION 2

#if VERSION >= 2
    #define FEATURE_NEW
#endif

int main() {
    int x = MAX(3, 5);  // 求最大值
    printf("max = %d\n", x);
    return 0;
}
```

**执行预处理**：

```bash
gcc -E preproc.c -o preproc.i
```

**查看预处理结果**（截取关键部分）：

```c
# 1 "preproc.c"
# 1 "<built-in>"
# 1 "<command-line>"
# 31 "/usr/include/stdio.h" 1 3 4
/* ... stdio.h 的全部内容（约 800 行） ... */
# 2 "preproc.c" 2

int main() {
    int x = ((3) > (5) ? (3) : (5));
    printf("max = %d\n", x);
    return 0;
}
```

可以看到：
- `stdio.h` 的内容被完整插入
- `MAX(3, 5)` 被展开为 `((3) > (5) ? (3) : (5))`
- 注释被删除
- `#if` 条件编译已处理

**只看预处理后的行数**：

```bash
wc -l preproc.i
# 约 850 行（大部分来自 stdio.h）
```

**直接输出到终端（不生成文件）**：

```bash
gcc -E preproc.c | tail -20
```

### 总结

- 预处理用 `-E` 选项触发，输出 `.i`（C）或 `.ii`（C++）文件
- 预处理做文本替换：展开宏、包含头文件、条件编译、删注释
- 预处理不做语法检查，只做文本处理
- 查看预处理结果有助于调试宏展开问题、头文件包含问题
- 预处理后的文件很大（因头文件展开），是理解编译过程的重要中间产物

## 第 6 讲 编译阶段（-S）

### 概念

编译阶段（Compilation）是编译器的核心环节，它将预处理后的 `.i` 文件转换为汇编代码 `.s` 文件。这一阶段进行词法分析、语法分析、语义分析、中间代码生成与优化，最终生成目标平台的汇编语言代码。这是整个编译流程中**最复杂**的阶段。

### 原理

编译阶段内部又分为多个子阶段：

1. **词法分析（Lexical Analysis）**：将源代码分解为 token（关键字、标识符、常量、运算符等）
2. **语法分析（Syntax Analysis）**：根据语法规则构建抽象语法树（AST）
3. **语义分析（Semantic Analysis）**：检查类型匹配、变量声明、作用域等
4. **中间代码生成**：将 AST 转换为中间表示（如 GIMPLE、RTL）
5. **中间代码优化**：常量折叠、死代码消除、循环优化等
6. **目标代码生成**：将优化后的中间代码转换为目标架构的汇编代码

编译阶段会进行**严格的语法和语义检查**，大部分编译错误（如 "undeclared identifier"、"expected ';' "）都发生在此阶段。

### 例子

**示例源文件**：

```c
// compile.c
int add(int a, int b) {
    return a + b;
}

int main() {
    int result = add(3, 5);
    return result;
}
```

**执行编译阶段**：

```bash
gcc -S compile.c -o compile.s
```

**查看生成的汇编代码**（x86-64）：

```asm
    .file   "compile.c"
    .text
    .globl  add
    .type   add, @function
add:
.LFB0:
    pushq   %rbp
    movq    %rsp, %rbp
    movl    %edi, -4(%rbp)
    movl    %esi, -8(%rbp)
    movl    -4(%rbp), %edx
    movl    -8(%rbp), %eax
    addl    %edx, %eax
    popq    %rbp
    ret
.LFE0:
    .size   add, .-add
    .globl  main
    .type   main, @function
main:
.LFB1:
    pushq   %rbp
    movq    %rsp, %rbp
    subq    $16, %rsp
    movl    $3, %esi
    movl    $5, %edi
    call    add
    movl    %eax, -4(%rbp)
    movl    -4(%rbp), %eax
    leave
    ret
```

**对比不同优化级别**：

```bash
gcc -S -O0 compile.c -o compile_O0.s   # 无优化
gcc -S -O2 compile.c -o compile_O2.s   # 二级优化

wc -l compile_O0.s compile_O2.s
# compile_O0.s: 约 30 行
# compile_O2.s: 约 15 行（优化后更精简）
```

**从 `.i` 文件直接编译**：

```bash
gcc -S compile.i -o compile.s   # 从预处理结果编译
```

### 总结

- 编译阶段用 `-S` 选项触发，输出 `.s` 汇编文件
- 这是编译流程中最复杂的阶段，包含词法/语法/语义分析和代码生成
- 大部分编译错误（语法错误、类型错误）发生在此阶段
- 查看汇编代码有助于理解优化效果、调试性能问题
- 不同优化级别（`-O0` vs `-O2`）会显著影响生成的汇编代码

## 第 7 讲 汇编阶段（-c）

### 概念

汇编阶段（Assembly）将汇编代码 `.s` 文件翻译为机器码，生成目标文件 `.o`（Linux 下为 ELF 格式，Windows 下为 COFF/PE 格式）。这一阶段由汇编器 `as` 完成，工作相对简单直接——基本上是汇编指令与机器码的一一对应翻译。

### 原理

汇编器的工作流程：

1. **逐行解析汇编指令**：识别指令助记符（如 `mov`、`add`、`call`）、操作数、标签
2. **符号表生成**：记录全局符号（函数名、全局变量）的名称和位置，供后续链接使用
3. **机器码生成**：将每条汇编指令编码为对应的二进制机器码
4. **重定位信息**：对于外部引用的符号（如 `printf`），记录需要在链接时修正的地址位置

目标文件（`.o`）虽然是机器码，但**还不能直接执行**，因为：
- 外部符号（如库函数 `printf`）的地址尚未确定
- 可能需要与其他目标文件合并
- 全局变量的最终地址尚未确定

ELF 目标文件包含多个段（section）：`.text`（代码）、`.data`（已初始化全局变量）、`.bss`（未初始化全局变量）、`.rodata`（只读数据）、`.symtab`（符号表）等。

### 例子

**示例源文件**：

```c
// assemble.c
int global_var = 42;
int uninit_var;

int square(int x) {
    return x * x;
}
```

**执行汇编阶段**：

```bash
gcc -c assemble.c -o assemble.o
```

**查看目标文件信息**：

```bash
# 查看文件类型
file assemble.o
# assemble.o: ELF 64-bit LSB relocatable, x86-64, ...

# 查看段信息
objdump -h assemble.o

# 查看符号表
nm assemble.o
# 输出:
# 0000000000000000 T square       (T 表示代码段的全局符号)
# 0000000000000000 D global_var   (D 表示已初始化数据段)
# 0000000000000000 B uninit_var   (B 表示未初始化数据段/BSS)

# 反汇编查看机器码
objdump -d assemble.o
```

**反汇编输出示例**：

```asm
square:
   0:   push   %rbp
   1:   mov    %rsp,%rbp
   4:   mov    %edi,-0x4(%rbp)
   7:   mov    -0x4(%rbp),%eax
   a:   imul   %eax,%eax
   d:   pop    %rbp
   e:   ret
```

**从 `.s` 文件汇编**：

```bash
gcc -c assemble.s -o assemble.o
# 或直接用汇编器
as assemble.s -o assemble.o
```

### 总结

- 汇编阶段用 `-c` 选项触发，输出 `.o` 目标文件
- 汇编是机器相关的，不同 CPU 架构生成不同的机器码
- 目标文件是 ELF 格式（Linux），包含 `.text`、`.data`、`.bss` 等段
- 目标文件还不能执行，需要链接才能运行
- 用 `nm`、`objdump`、`readelf` 等工具查看目标文件内部结构

## 第 8 讲 链接阶段

### 概念

链接（Linking）是编译流程的最后一个阶段，由链接器 `ld` 完成。它将一个或多个目标文件（`.o`）以及库文件合并为一个可执行文件，并解析所有外部符号引用。链接分为**静态链接**和**动态链接**两种方式，决定了程序如何使用库代码。

### 原理

链接器的主要工作：

1. **符号解析（Symbol Resolution）**：扫描所有目标文件的符号表，将每个符号引用与其定义关联起来。例如，`main.o` 中引用了 `printf`，链接器需要在 `libc` 中找到 `printf` 的定义。

2. **地址重定位（Relocation）**：合并所有目标文件的代码段和数据段，确定每个符号的最终内存地址，并修正代码中所有需要重定位的地址引用。

3. **库链接**：
   - **静态库（`.a`）**：链接器将库中被引用的代码直接复制到可执行文件中
   - **动态库（`.so`）**：链接器只在可执行文件中记录动态库的依赖信息，运行时由动态加载器加载

链接错误的典型表现是 "undefined reference to xxx"，表示找不到某个符号的定义。

### 例子

**多文件链接示例**：

```c
// math_ops.h
#ifndef MATH_OPS_H
#define MATH_OPS_H
int add(int a, int b);
int multiply(int a, int b);
#endif
```

```c
// math_ops.c
#include "math_ops.h"
int add(int a, int b) { return a + b; }
int multiply(int a, int b) { return a * b; }
```

```c
// main.c
#include <stdio.h>
#include "math_ops.h"
int main() {
    printf("3 + 5 = %d\n", add(3, 5));
    printf("3 * 5 = %d\n", multiply(3, 5));
    return 0;
}
```

**分步编译与链接**：

```bash
# 分别编译各源文件为目标文件
gcc -c math_ops.c -o math_ops.o
gcc -c main.c -o main.o

# 链接为目标文件
gcc main.o math_ops.o -o calculator

./calculator
# 输出:
# 3 + 5 = 8
# 3 * 5 = 15
```

**查看可执行文件的依赖库**：

```bash
ldd calculator
# 输出:
#     linux-vdso.so.1 (0x...)
#     libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x...)
#     /lib64/ld-linux-x86-64.so.2 (0x...)
```

**链接错误示例**：

```bash
# 故意不链接 math_ops.o
gcc main.o -o bad_calculator
# 报错: undefined reference to `add'
#       undefined reference to `multiply'
```

**查看可执行文件符号**：

```bash
nm calculator | grep -E "add|multiply"
# 输出:
# 0000000000001149 T add
# 0000000000001169 T multiply
```

### 总结

- 链接是编译的最后阶段，将目标文件和库合并为可执行文件
- 链接做两件事：符号解析 + 地址重定位
- 静态链接将库代码复制进可执行文件，动态链接只记录依赖
- 常见链接错误 "undefined reference" 表示找不到符号定义
- 用 `ldd` 查看动态库依赖，用 `nm` 查看符号表
- 至此，编译四阶段（预处理→编译→汇编→链接）全部讲解完毕

# 第三章：常用编译选项

## 第 9 讲 输出控制选项

### 概念

输出控制选项用于指定 GCC 的输出类型和输出文件名。这是最基础也最常用的选项类别，包括 `-o`（指定输出文件名）、`-c`（只编译不链接）、`-S`（只编译到汇编）、`-E`（只预处理）等。理解这些选项是控制编译流程的基础。

### 原理

GCC 默认会执行完整的编译流程（预处理→编译→汇编→链接），生成名为 `a.out` 的可执行文件。输出控制选项可以改变这一默认行为：

| 选项 | 作用 | 输出文件 | 默认输出名 |
|------|------|----------|------------|
| 无 | 完整编译 | 可执行文件 | `a.out` |
| `-o name` | 指定输出名 | 同上 | `name` |
| `-E` | 只预处理 | 预处理文件 | 输出到 stdout |
| `-S` | 预处理+编译 | 汇编文件 `.s` | `源文件名.s` |
| `-c` | 预处理+编译+汇编 | 目标文件 `.o` | `源文件名.o` |

这些选项可以组合使用，但 `-E`、`-S`、`-c` 互斥（只能选一个），因为它们指定了编译流程的终止点。

### 例子

**`-o` 指定输出文件名**：

```bash
gcc main.c                    # 默认输出 a.out
gcc main.c -o main            # 输出 main
gcc main.c -o /tmp/myapp      # 输出到指定路径
```

**`-c` 只生成目标文件**：

```bash
gcc -c main.c                 # 生成 main.o
gcc -c main.c utils.c         # 生成 main.o 和 utils.o
gcc -c main.c -o main.obj     # 指定输出名
```

**`-S` 只生成汇编文件**：

```bash
gcc -S main.c                 # 生成 main.s
gcc -S -fverbose-asm main.c   # 生成带注释的汇编
```

**`-E` 只预处理**：

```bash
gcc -E main.c                 # 输出到终端
gcc -E main.c -o main.i       # 输出到文件
```

**组合使用示例**：

```bash
# 多文件项目分步编译
gcc -c main.c -o main.o       # 步骤1: 编译 main.c
gcc -c utils.c -o utils.o     # 步骤2: 编译 utils.c
gcc main.o utils.o -o app     # 步骤3: 链接
```

**保存所有中间文件**：

```bash
gcc -save-temps main.c -o main
# 生成 main.i, main.s, main.o, main
```

### 总结

- `-o` 指定输出文件名，是最常用的选项
- `-c`、`-S`、`-E` 控制编译流程的终止点，互斥使用
- `-save-temps` 保留所有中间文件，便于调试
- 多文件项目通常先 `-c` 分别编译，再统一链接
- 默认输出名 `a.out` 来自历史遗留，建议始终用 `-o` 指定

## 第 10 讲 警告选项（-Wall / -Wextra / -Werror）

### 概念

警告选项控制编译器对潜在问题的提示程度。GCC 有数百个警告选项，最常用的是 `-Wall`（开启大部分常用警告）、`-Wextra`（开启额外警告）、`-Werror`（将警告视为错误）。良好的警告策略能在编译阶段发现大量潜在 bug。

### 原理

GCC 的警告以 `-W` 开头，后面跟警告名称。警告分为多个级别：

- **默认开启**：严重问题，如语法错误（这些是 error 不是 warning）
- **`-Wall` 开启**：常见但非默认的警告，如未使用变量、有符号无符号比较、缺少返回值等
- **`-Wextra` 开启**：更严格的额外警告，如空函数体、缺少参数检查等
- **单独控制**：`-Wxxx` 开启，`-Wno-xxx` 关闭

`-Werror` 将所有警告提升为错误，使编译失败。这在生产项目中很有用，可以强制开发者修复所有警告。

注意：`-Wall` 并非开启**所有**警告，只是"大部分常用"警告。要开启所有警告可用 `-Weverything`（Clang）或手动指定（GCC）。

### 例子

**示例代码（含多种潜在问题）**：

```c
// warnings.c
#include <stdio.h>

int divide(int a, int b) {
    return a / b;  // 未检查 b 是否为 0
}

int main() {
    int unused = 10;           // 未使用的变量
    int result;
    printf("Result: %d\n", result);  // 使用未初始化变量

    unsigned int u = 10;
    int s = -1;
    if (u > s) {               // 有符号无符号比较
        printf("u > s\n");
    }

    return 0;
}
```

**不加任何警告选项**：

```bash
gcc warnings.c -o warnings
# 无任何警告输出（默认不检查这些问题）
```

**加 `-Wall`**：

```bash
gcc -Wall warnings.c -o warnings
# 警告:
# warnings.c: In function 'main':
# warnings.c:10:9: warning: unused variable 'unused' [-Wunused-variable]
# warnings.c:12:5: warning: 'result' is used uninitialized [-Wuninitialized]
# warnings.c:15:8: warning: comparison between signed and unsigned [-Wsign-compare]
```

**加 `-Wall -Wextra`**：

```bash
gcc -Wall -Wextra warnings.c -o warnings
# 更多警告被开启
```

**加 `-Werror`**：

```bash
gcc -Wall -Werror warnings.c -o warnings
# 错误（编译失败）:
# warnings.c:10:9: error: unused variable 'unused' [-Werror=unused-variable]
# cc1: all warnings being treated as errors
```

**单独控制某个警告**：

```bash
# 关闭未使用变量警告
gcc -Wall -Wno-unused-variable warnings.c -o warnings

# 只开启特定警告
gcc -Wuninitialized warnings.c -o warnings
```

**推荐的警告组合**：

```bash
# 开发阶段
gcc -Wall -Wextra -g main.c -o main

# 生产阶段
gcc -Wall -Wextra -Werror -O2 main.c -o main
```

### 总结

- `-Wall` 开启常用警告，`-Wextra` 开启额外警告，建议始终使用
- `-Werror` 将警告视为错误，适合生产环境强制代码质量
- `-Wno-xxx` 可关闭特定警告，`-Wxxx` 可单独开启
- 默认不加警告选项会漏掉大量潜在问题，不推荐
- 良好的习惯：开发阶段 `-Wall -Wextra`，CI/CD 阶段 `-Werror`

## 第 11 讲 调试选项（-g / -ggdb）

### 概念

调试选项用于在编译产物中嵌入调试信息，使调试器（如 GDB）能够将机器码映射回源代码。最常用的调试选项是 `-g`，它生成操作系统原生格式的调试信息（DWARF on Linux）；`-ggdb` 生成专门为 GDB 优化的调试信息。

### 原理

默认编译的可执行文件不包含源代码信息（变量名、行号、类型等），只有机器码。调试器无法将机器码与源代码关联，调试时只能看到汇编代码。

`-g` 选项让编译器在目标文件中嵌入 **DWARF** 调试信息格式（Linux 标准），包含：
- 源文件名和行号映射
- 变量名、类型、作用域
- 函数名和参数
- 宏定义（需 `-g3`）

调试信息存储在 ELF 文件的特殊段（`.debug_info`、`.debug_line` 等）中，不影响程序运行，但会增大文件体积。

调试级别：
- `-g0`：无调试信息（默认）
- `-g1`：最小信息（函数名、外部变量）
- `-g` 或 `-g2`：标准调试信息（推荐）
- `-g3`：包含宏定义等额外信息

### 例子

**示例代码**：

```c
// debug.c
#include <stdio.h>

int factorial(int n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1);
}

int main() {
    int n = 5;
    int result = factorial(n);
    printf("%d! = %d\n", n, result);
    return 0;
}
```

**不加调试信息编译**：

```bash
gcc debug.c -o debug_no_g
ls -lh debug_no_g
# 约 16KB

# 用 gdb 调试时无法看到源码
gdb debug_no_g
(gdb) list
# No symbol table is loaded.
```

**加调试信息编译**：

```bash
gcc -g debug.c -o debug
ls -lh debug
# 约 20KB（增大了，因为包含调试信息）

# gdb 调试可以看到源码
gdb debug
(gdb) list
# 1   #include <stdio.h>
# 2
# 3   int factorial(int n) {
# 4       if (n <= 1) return 1;
# 5       return n * factorial(n - 1);
# 6   }
```

**`-ggdb` 生成 GDB 专用格式**：

```bash
gcc -ggdb debug.c -o debug_gdb
# 调试信息更丰富，但只有 GDB 能完整利用
```

**调试 + 优化**：

```bash
# 注意：优化会打乱代码顺序，调试体验差
gcc -g -O0 debug.c -o debug      # 推荐：调试时不优化
gcc -g -O2 debug.c -o debug_opt  # 可行但调试困难
```

**`-g3` 包含宏定义**：

```bash
gcc -g3 macro_test.c -o macro_test
# gdb 中可以用 info macro MACRO_NAME 查看宏定义
```

**检查调试信息**：

```bash
# 查看是否包含调试段
readelf -S debug | grep debug
# 输出:
# [27] .debug_aranges PROGBITS ...
# [28] .debug_info     PROGBITS ...
# [29] .debug_abbrev   PROGBITS ...
# [30] .debug_line     PROGBITS ...
```

**剥离调试信息（发布时减小体积）**：

```bash
cp debug debug_release
strip debug_release
ls -lh debug debug_release
# debug:          20KB
# debug_release:  16KB
```

### 总结

- `-g` 生成标准调试信息（DWARF），`-ggdb` 生成 GDB 优化格式
- 调试信息不影响运行，但增大文件体积
- 调试时建议用 `-g -O0`，避免优化干扰
- `-g3` 额外包含宏定义，适合需要调试宏的场景
- 发布时用 `strip` 剥离调试信息以减小体积
- 调试信息是 GDB 调试的前提，没有 `-g` 无法有效调试

## 第 12 讲 优化选项（-O0 ~ -O3 / -Os）

### 概念

优化选项控制编译器对代码的优化程度。GCC 提供 `-O0`（不优化）、`-O1`（基本优化）、`-O2`（标准优化）、`-O3`（激进优化）、`-Os`（优化体积）、`-Ofast`（最激进）等级别。优化可以显著提升程序性能或减小体积，但也可能改变代码行为（如消除未使用变量），影响调试。

### 原理

GCC 的优化在编译阶段进行，作用于中间表示（GIMPLE/RTL）。不同级别开启不同的优化 pass：

| 级别 | 说明 | 典型优化 |
|------|------|----------|
| `-O0` | 不优化（默认） | 无，便于调试 |
| `-O1` | 基本优化 | 死代码消除、常量折叠、跳转优化 |
| `-O2` | 标准优化（推荐） | `-O1` + 循环优化、内联、指令调度 |
| `-O3` | 激进优化 | `-O2` + 向量化、循环展开、更激进内联 |
| `-Os` | 优化体积 | `-O2` 但禁用增大体积的优化 |
| `-Ofast` | 最激进 | `-O3` + `-ffast-math` 等不严格遵循标准的优化 |

优化可能带来的副作用：
- 调试困难（变量被消除、代码顺序改变）
- 浮点精度变化（`-ffast-math`）
- 编译时间增加
- 极少数情况下改变语义（如未定义行为被优化掉）

### 例子

**示例代码**：

```c
// optimize.c
#include <stdio.h>

int sum_array(int *arr, int n) {
    int sum = 0;
    for (int i = 0; i < n; i++) {
        sum += arr[i];
    }
    return sum;
}

int main() {
    int arr[1000];
    for (int i = 0; i < 1000; i++) {
        arr[i] = i;
    }
    printf("Sum = %d\n", sum_array(arr, 1000));
    return 0;
}
```

**对比不同优化级别的汇编代码**：

```bash
gcc -S -O0 optimize.c -o opt_O0.s
gcc -S -O1 optimize.c -o opt_O1.s
gcc -S -O2 optimize.c -o opt_O2.s
gcc -S -O3 optimize.c -o opt_O3.s

wc -l opt_O*.s
# opt_O0.s: 60 行
# opt_O1.s: 35 行
# opt_O2.s: 30 行
# opt_O3.s: 45 行（循环展开后行数可能增加）
```

**对比运行性能**：

```c
// bench.c
#include <stdio.h>
#include <time.h>

#define N 100000000

int main() {
    int *arr = malloc(N * sizeof(int));
    for (int i = 0; i < N; i++) arr[i] = i;

    clock_t start = clock();
    long sum = 0;
    for (int i = 0; i < N; i++) sum += arr[i];
    clock_t end = clock();

    printf("Sum = %ld, Time = %f sec\n", sum, (double)(end-start)/CLOCKS_PER_SEC);
    return 0;
}
```

```bash
gcc -O0 bench.c -o bench_O0 && ./bench_O0
gcc -O2 bench.c -o bench_O2 && ./bench_O2
gcc -O3 bench.c -o bench_O3 && ./bench_O3

# 典型结果:
# O0: 0.35 sec
# O2: 0.08 sec
# O3: 0.05 sec（向量化加速）
```

**`-Os` 优化体积**：

```bash
gcc -Os optimize.c -o opt_os
gcc -O2 optimize.c -o opt_o2
ls -lh opt_os opt_o2
# opt_os 通常比 opt_o2 小
```

**查看具体开启了哪些优化**：

```bash
gcc -O2 -Q --help=optimizers | grep enabled
# 列出 -O2 开启的所有优化 pass
```

**针对特定函数优化**：

```c
// 使用 pragma 控制单个函数的优化级别
#pragma GCC optimize("O3")
int heavy_computation(int n) {
    // 这个函数用 O3 优化
    return n * 2;
}
#pragma GCC optimize("O0")
```

### 总结

- `-O0` 调试用，`-O2` 生产推荐，`-O3` 性能极致，`-Os` 嵌入式/体积敏感
- 优化级别越高，编译越慢，但运行越快（通常）
- `-O3` 可能增大体积（循环展开、内联），不一定总是更快
- 优化会干扰调试，调试时用 `-O0 -g`
- `-Ofast` 不严格遵循标准，慎用（可能改变浮点结果）
- 建议开发用 `-O0 -g`，测试用 `-O2`，发布用 `-O2` 或 `-O3`

## 第 13 讲 语言标准选项（-std）

### 概念

`-std` 选项指定源代码遵循的 C 或 C++ 语言标准。不同标准支持不同的语言特性（如 C99 的 `//` 注释、C++11 的 `auto`、C++17 的结构化绑定）。选择正确的标准可以启用新特性、保证可移植性、避免使用已废弃的语法。

### 原理

C 和 C++ 语言标准在不断演进：

**C 语言标准**：
| 选项 | 标准 | 年份 | 关键特性 |
|------|------|------|----------|
| `-std=c89` / `-std=c90` | ANSI C | 1989/1990 | 基础 C |
| `-std=c99` | C99 | 1999 | `//`注释、变长数组、`long long`、`stdint.h` |
| `-std=c11` | C11 | 2011 | `_Generic`、原子操作、多线程 |
| `-std=c17` / `-std=c18` | C17 | 2018 | C11 的 bug 修复版 |
| `-std=c23` | C23 | 2023 | `constexpr`、`nullptr`、属性 |

**C++ 语言标准**：
| 选项 | 标准 | 年份 | 关键特性 |
|------|------|------|----------|
| `-std=c++98` | C++98 | 1998 | 基础 C++ |
| `-std=c++03` | C++03 | 2003 | C++98 的 bug 修复 |
| `-std=c++11` | C++11 | 2011 | `auto`、lambda、智能指针、range-for |
| `-std=c++14` | C++14 | 2014 | 泛型 lambda、`make_unique` |
| `-std=c++17` | C++17 | 2017 | 结构化绑定、`optional`、`filesystem` |
| `-std=c++20` | C++20 | 2020 | concepts、coroutines、modules、ranges |
| `-std=c++23` | C++23 | 2023 | `std::expected`、`print` |

加 `gnu` 前缀（如 `-std=gnu11`）表示同时启用 GNU 扩展，这是 GCC 的默认行为。

### 例子

**C 标准示例**：

```c
// c99_features.c
#include <stdio.h>
#include <stdint.h>

int main() {
    // C99 特性：// 注释、变长数组、for 内声明变量
    int n = 5;
    int vla[n];              // 变长数组（C99）
    for (int i = 0; i < n; i++) {  // for 内声明（C99）
        vla[i] = i * 2;
    }

    int64_t big_num = 9223372036854775807LL;  // long long (C99)
    printf("big = %lld\n", big_num);

    return 0;
}
```

```bash
# C89 不支持这些特性
gcc -std=c89 c99_features.c -o c99_test
# 报错: 'for' loop initial declarations are only allowed in C99 mode

# C99 支持
gcc -std=c99 c99_features.c -o c99_test    # 成功

# 默认（gnu17，支持 GNU 扩展）
gcc c99_features.c -o c99_test              # 成功
```

**C++ 标准示例**：

```cpp
// cpp11_features.cpp
#include <iostream>
#include <vector>
#include <memory>

int main() {
    // C++11 特性：auto、lambda、range-for、智能指针
    auto nums = std::vector<int>{1, 2, 3, 4, 5};

    auto sum = 0;
    for (auto n : nums) {           // range-for (C++11)
        sum += n;
    }

    auto print = [&sum]() {         // lambda (C++11)
        std::cout << "Sum = " << sum << std::endl;
    };
    print();

    auto ptr = std::make_shared<int>(42);  // 智能指针 (C++11)
    std::cout << *ptr << std::endl;

    return 0;
}
```

```bash
# C++98 不支持
g++ -std=c++98 cpp11_features.cpp -o cpp_test
# 大量报错

# C++11 支持
g++ -std=c++11 cpp11_features.cpp -o cpp_test   # 成功

# C++17 支持
g++ -std=c++17 cpp11_features.cpp -o cpp_test   # 成功
```

**C++17 结构化绑定**：

```cpp
// cpp17.cpp
#include <iostream>
#include <map>

int main() {
    std::map<std::string, int> ages = {{"Alice", 30}, {"Bob", 25}};

    // C++17 结构化绑定
    for (const auto& [name, age] : ages) {
        std::cout << name << " is " << age << std::endl;
    }
    return 0;
}
```

```bash
g++ -std=c++17 cpp17.cpp -o cpp17_test   # 成功
g++ -std=c++14 cpp17.cpp -o cpp14_test   # 报错
```

**查看默认标准**：

```bash
gcc -dM -E -x c /dev/null | grep __STDC_VERSION__
# 输出: #define __STDC_VERSION__ 201710L  (表示默认 c17)

g++ -dM -E -x c++ /dev/null | grep __cplusplus
# 输出: #define __cplusplus 201703L  (表示默认 c++17)
```

**GNU 扩展 vs 纯标准**：

```bash
gcc -std=c11 strict.c -o strict       # 严格 C11，不支持 GNU 扩展
gcc -std=gnu11 extended.c -o extended  # C11 + GNU 扩展（默认）
```

### 总结

- `-std=c99`、`-std=c++11` 等指定语言标准
- 加 `gnu` 前缀（如 `gnu11`）启用 GNU 扩展，是 GCC 默认行为
- 不同 GCC 版本支持的最新标准不同（GCC 11 支持 C++20，GCC 13 支持 C++23）
- 用 `__STDC_VERSION__`（C）和 `__cplusplus`（C++）宏检测当前标准
- 建议显式指定标准，不要依赖默认值，保证可移植性
- 新项目推荐 C17 或 C++17，需要新特性可用 C++20/C++23

# 第四章：头文件与库管理

## 第 14 讲 头文件搜索路径（-I）

### 概念

`-I`（大写 i）选项用于指定头文件的额外搜索路径。当源代码中使用 `#include "header.h"` 或 `#include <header.h>` 时，预处理器需要知道去哪里查找这些头文件。GCC 有一套默认的搜索路径（如 `/usr/include`、`/usr/local/include`），`-I` 选项可以添加自定义路径。

### 原理

GCC 查找头文件的顺序取决于 `#include` 的形式：

**`#include <header.h>`（尖括号）**：
1. `-I` 指定的路径（按命令行顺序）
2. 系统标准路径（`/usr/local/include`、`/usr/include`、`/usr/lib/gcc/.../include`）
3. 最后才查找 `-isystem` 指定的系统路径

**`#include "header.h"`（双引号）**：
1. 当前源文件所在目录
2. `-I` 指定的路径
3. 系统标准路径

`-I` 选项可以多次使用，搜索顺序按命令行中出现的先后顺序。`-I-`（已废弃）或 `-iquote` 可区分仅对双引号 include 生成的路径。

### 例子

**项目结构**：

```
project/
├── main.c
├── include/
│   └── myheader.h
└── lib/
    └── other.h
```

**main.c**：

```c
// main.c
#include <stdio.h>
#include "myheader.h"    // 在 include/ 目录
#include "other.h"       // 在 lib/ 目录

int main() {
    printf("%d\n", MY_VALUE);
    other_func();
    return 0;
}
```

**不指定路径会报错**：

```bash
gcc main.c -o main
# 错误: myheader.h: No such file or directory
```

**用 `-I` 指定路径**：

```bash
gcc -I./include -I./lib main.c -o main
# 成功编译
```

**多个 `-I` 的搜索顺序**：

```bash
# 如果 include/ 和 lib/ 都有 myheader.h，先找 include/
gcc -I./include -I./lib main.c -o main
```

**`-I` 与系统头文件**：

```c
// 如果项目中有自定义的 stdio.h
// -I./myheaders 会优先于系统 /usr/include
gcc -I./myheaders main.c -o main
# 此时 #include <stdio.h> 会先找 ./myheaders/stdio.h
```

**查看头文件搜索路径**：

```bash
echo | gcc -E -Wp,-v -x c -
# 输出:
# ignoring nonexistent directory "/usr/local/include/x86_64-linux-gnu"
# ignoring nonexistent directory "/usr/lib/gcc/x86_64-linux-gnu/11/../../../../x86_64-linux-gnu/include"
# #include "..." search starts here:
# #include <...> search starts here:
#  /usr/lib/gcc/x86_64-linux-gnu/11/include
#  /usr/local/include
#  /usr/include/x86_64-linux-gnu
#  /usr/include
# End of search list.
```

**`-I` 路径优先级验证**：

```bash
# 创建测试头文件
mkdir -p dir1 dir2
echo '#define HELLO "from dir1"' > dir1/test.h
echo '#define HELLO "from dir2"' > dir2/test.h

# 测试程序
cat > test.c << 'EOF'
#include <stdio.h>
#include "test.h"
int main() { printf("%s\n", HELLO); return 0; }
EOF

# dir1 在前，优先使用 dir1/test.h
gcc -Idir1 -Idir2 test.c -o test && ./test
# 输出: from dir1

# dir2 在前，优先使用 dir2/test.h
gcc -Idir2 -Idir1 test.c -o test && ./test
# 输出: from dir2
```

### 总结

- `-I` 添加头文件搜索路径，可多次使用
- 双引号 include 先找当前目录，再找 `-I` 路径，最后找系统路径
- 尖括号 include 跳过当前目录，直接找 `-I` 和系统路径
- 多个 `-I` 按命令行顺序搜索，先指定的优先
- 用 `gcc -E -Wp,-v -x c -` 查看完整的头文件搜索路径
- 大型项目通常用 `-I./include` 或 `-I./src` 组织头文件

## 第 15 讲 静态库的创建与使用

### 概念

静态库（Static Library，`.a` 文件）是将多个目标文件（`.o`）打包归档形成的文件，也称为归档文件（archive）。在链接时，链接器从静态库中提取被引用的目标文件，将其代码直接复制到最终的可执行文件中。静态库的优点是部署简单（无依赖），缺点是体积大、更新需重新链接。

### 原理

静态库本质上是 `ar`（archiver）工具创建的归档文件，内部包含多个 `.o` 文件和一个符号索引。其工作流程：

1. **创建**：编译源文件为 `.o`，用 `ar rcs` 打包为 `.a`
2. **链接**：链接器扫描 `.a` 文件，只提取被引用的 `.o`（而非全部）
3. **结果**：被提取的代码成为可执行文件的一部分

`ar` 命令的参数：
- `r`：插入/替换成员文件
- `c`：创建归档（不输出警告）
- `s`：创建符号索引（相当于 `ranlib`）

静态库命名约定：`lib` 前缀 + 库名 + `.a` 后缀，如 `libmymath.a`。链接时用 `-lmymath`（去掉前缀和后缀）。

### 例子

**项目结构**：

```
mathlib/
├── mymath.h
├── add.c
├── sub.c
├── mul.c
└── main.c
```

**源文件**：

```c
// mymath.h
#ifndef MYMATH_H
#define MYMATH_H
int add(int a, int b);
int sub(int a, int b);
int mul(int a, int b);
#endif
```

```c
// add.c
#include "mymath.h"
int add(int a, int b) { return a + b; }
```

```c
// sub.c
#include "mymath.h"
int sub(int a, int b) { return a - b; }
```

```c
// mul.c
#include "mymath.h"
int mul(int a, int b) { return a * b; }
```

```c
// main.c
#include <stdio.h>
#include "mymath.h"
int main() {
    printf("add(3,5) = %d\n", add(3, 5));
    printf("sub(10,4) = %d\n", sub(10, 4));
    printf("mul(6,7) = %d\n", mul(6, 7));
    return 0;
}
```

**创建静态库**：

```bash
# 步骤1: 编译各源文件为目标文件
gcc -c add.c -o add.o
gcc -c sub.c -o sub.o
gcc -c mul.c -o mul.o

# 步骤2: 打包为静态库 libmymath.a
ar rcs libmymath.a add.o sub.o mul.o

# 查看库内容
ar -t libmymath.a
# 输出:
# add.o
# sub.o
# mul.o

# 查看库中符号
nm libmymath.a
# 输出各 .o 文件的符号表
```

**使用静态库**：

```bash
# 方式1: 用 -L 和 -l
gcc -I. main.c -L. -lmymath -o calc

# 方式2: 直接指定库文件名
gcc -I. main.c libmymath.a -o calc

./calc
# 输出:
# add(3,5) = 8
# sub(10,4) = 6
# mul(6,7) = 42
```

**验证静态链接**：

```bash
# 静态库的代码被复制进可执行文件
ldd calc
# 不包含 libmymath（因为已静态链接）

# 查看可执行文件中的符号
nm calc | grep -E "add|sub|mul"
# 0000000000001149 T add
# 0000000000001169 T mul
# 0000000000001159 T sub
```

**删除静态库后仍可运行**：

```bash
mv libmymath.a /tmp/
./calc
# 仍然正常运行（因为代码已复制进 calc）
```

### 总结

- 静态库用 `ar rcs` 创建，命名约定 `libxxx.a`
- 链接时用 `-lxxx`（去掉 `lib` 前缀和 `.a` 后缀）
- 静态库的代码被复制进可执行文件，运行时无依赖
- 优点：部署简单、运行时无库依赖
- 缺点：可执行文件体积大、库更新需重新链接
- 适合小型库、嵌入式系统、需要独立部署的场景

## 第 16 讲 动态库的创建与使用

### 概念

动态库（Dynamic Library / Shared Library，`.so` 文件）是在程序运行时才加载的库，也称共享库。与静态库不同，动态库的代码不被复制到可执行文件中，而是在运行时由动态链接器（`ld-linux.so`）加载到内存。多个程序可以共享同一份动态库，节省内存。

### 原理

动态库的创建需要两个关键选项：
- `-fPIC`：生成位置无关代码（Position Independent Code），使代码可以在内存任意位置运行
- `-shared`：创建共享库

动态库的工作机制：
1. **链接时**：链接器在可执行文件中记录对 `.so` 的依赖，不复制代码
2. **加载时**：程序启动时，动态链接器 `ld-linux.so` 查找并加载所需的 `.so`
3. **运行时**：多个进程共享同一份 `.so` 的代码段（数据段各进程独立）

动态库查找顺序：
1. `-Wl,-rpath` 指定的路径（编译时嵌入）
2. `LD_LIBRARY_PATH` 环境变量
3. `/etc/ld.so.cache` 缓存（由 `ldconfig` 生成）
4. 默认路径 `/lib`、`/usr/lib`

### 例子

**沿用第 15 讲的源文件**：

**创建动态库**：

```bash
# 步骤1: 编译为位置无关代码的目标文件
gcc -fPIC -c add.c -o add.o
gcc -fPIC -c sub.c -o sub.o
gcc -fPIC -c mul.c -o mul.o

# 步骤2: 创建动态库 libmymath.so
gcc -shared -o libmymath.so add.o sub.o mul.o

# 或一步到位
gcc -fPIC -shared -o libmymath.so add.c sub.c mul.c
```

**使用动态库**：

```bash
# 编译主程序，链接动态库
gcc -I. main.c -L. -lmymath -o calc_dyn

# 运行（可能报错）
./calc_dyn
# ./calc_dyn: error while loading shared libraries: libmymath.so:
# cannot open shared object file: No such file or directory
```

**解决运行时找不到库的问题**：

```bash
# 方法1: 设置 LD_LIBRARY_PATH
export LD_LIBRARY_PATH=.:$LD_LIBRARY_PATH
./calc_dyn
# 成功运行

# 方法2: 编译时嵌入 rpath（推荐）
gcc -I. main.c -L. -lmymath -Wl,-rpath,. -o calc_dyn
./calc_dyn
# 成功运行（无需设置环境变量）

# 方法3: 将库复制到系统目录
sudo cp libmymath.so /usr/local/lib/
sudo ldconfig
./calc_dyn
# 成功运行
```

**验证动态链接**：

```bash
ldd calc_dyn
# 输出:
#     libmymath.so => ./libmymath.so (0x...)
#     libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x...)
#     /lib64/ld-linux-x86-64.so.2 (0x...)
```

**动态库更新（无需重新编译主程序）**：

```bash
# 修改 add.c
cat > add.c << 'EOF'
#include "mymath.h"
int add(int a, int b) { return a + b + 100; }  // 加了 100
EOF

# 重新编译动态库
gcc -fPIC -shared -o libmymath.so add.c sub.c mul.o

# 直接运行（无需重新编译 calc_dyn）
./calc_dyn
# 输出: add(3,5) = 108  (3+5+100)
```

**查看动态库信息**：

```bash
# 查看动态库依赖的符号
nm -D libmymath.so

# 查看动态库的 soname
readelf -d libmymath.so | grep soname

# 设置 soname（版本管理）
gcc -fPIC -shared -Wl,-soname,libmymath.so.1 -o libmymath.so.1.0 add.c sub.c mul.c
ln -s libmymath.so.1.0 libmymath.so.1
ln -s libmymath.so.1 libmymath.so
```

### 总结

- 动态库用 `-fPIC -shared` 创建，命名约定 `libxxx.so`
- 运行时由动态链接器加载，多个进程可共享代码
- 运行时找不到库是常见问题，用 `LD_LIBRARY_PATH`、`-rpath` 或系统目录解决
- 优点：体积小、可共享、更新方便（无需重新编译主程序）
- 缺点：运行时有依赖、部署需确保库存在
- 适合大型库、频繁更新的库、多程序共享的库

## 第 17 讲 库的链接与搜索路径（-L / -l）

### 概念

`-L` 选项指定库文件的搜索路径，`-l` 选项指定要链接的库名。两者配合使用，告诉链接器去哪里找库以及找哪个库。理解 `-L` 和 `-l` 的工作机制是正确链接第三方库的关键。

### 原理

**`-l` 的命名规则**：

`-l` 后面跟的名称会自动加上 `lib` 前缀和 `.a`/`.so` 后缀。例如：
- `-lm` → 查找 `libm.so` 或 `libm.a`
- `-lpthread` → 查找 `libpthread.so` 或 `libpthread.a`
- `-lmymath` → 查找 `libmymath.so` 或 `libmymath.a`

**库类型优先级**：链接器默认优先使用动态库（`.so`），如果只有静态库（`.a`）才用静态库。可用 `-static` 强制全部静态链接。

**`-L` 搜索顺序**：
1. `-L` 指定的路径（按命令行顺序）
2. 系统库路径（`/lib`、`/usr/lib`、`/usr/local/lib` 等）

**链接顺序敏感**：`-l` 选项必须放在引用它的源文件/目标文件**之后**。因为链接器是单趟扫描，遇到 `-l` 时只提取当前已知的未定义符号。

### 例子

**链接数学库 `-lm`**：

```c
// math_demo.c
#include <stdio.h>
#include <math.h>

int main() {
    double x = 2.0;
    printf("sqrt(2) = %f\n", sqrt(x));
    printf("pow(2, 10) = %f\n", pow(2.0, 10.0));
    return 0;
}
```

```bash
# 不链接数学库会报错
gcc math_demo.c -o math_demo
# 错误: undefined reference to `sqrt'

# 正确链接
gcc math_demo.c -o math_demo -lm
./math_demo
# sqrt(2) = 1.414214
# pow(2, 10) = 1024.000000
```

**链接多线程库 `-lpthread`**：

```c
// thread_demo.c
#include <stdio.h>
#include <pthread.h>

void* thread_func(void* arg) {
    printf("Hello from thread!\n");
    return NULL;
}

int main() {
    pthread_t tid;
    pthread_create(&tid, NULL, thread_func, NULL);
    pthread_join(tid, NULL);
    return 0;
}
```

```bash
gcc thread_demo.c -o thread_demo -lpthread
# 或使用现代写法
gcc thread_demo.c -o thread_demo -pthread
```

**`-L` 指定库路径**：

```bash
# 库在自定义目录
gcc main.c -L./lib -lmymath -o main

# 多个库路径
gcc main.c -L./lib -L./third_party/lib -lmylib -l3rdlib -o main
```

**链接顺序问题**：

```bash
# 错误：-lm 放在源文件前面
gcc -lm math_demo.c -o math_demo
# 可能报错: undefined reference to `sqrt'

# 正确：-lm 放在源文件后面
gcc math_demo.c -lm -o math_demo
```

**混合链接静态库和动态库**：

```bash
# 默认优先动态库
gcc main.c -L./lib -lmymath -o main

# 强制某个库静态链接
gcc main.c -L./lib -Wl,-Bstatic -lmymath -Wl,-Bdynamic -lc -o main

# 全部静态链接
gcc -static main.c -L./lib -lmymath -o main
```

**查看链接了哪些库**：

```bash
# 查看动态库依赖
ldd main

# 查看链接过程详情
gcc main.c -L./lib -lmymath -o main -Wl,--verbose 2>&1 | grep "mymath"
```

**常见系统库**：

| 库名 | 选项 | 用途 |
|------|------|------|
| `libm` | `-lm` | 数学函数 |
| `libpthread` | `-lpthread` / `-pthread` | 多线程 |
| `libdl` | `-ldl` | 动态加载 |
| `librt` | `-lrt` | 实时扩展 |
| `libc` | 默认链接 | C 标准库 |
| `libstdc++` | g++ 自动链接 | C++ 标准库 |

### 总结

- `-l` 指定库名，自动加 `lib` 前缀和 `.so`/`.a` 后缀
- `-L` 指定库搜索路径，可多次使用
- 链接器优先用动态库，`-static` 强制静态链接
- `-l` 必须放在引用它的源文件之后（链接顺序敏感）
- 常见系统库：`-lm`（数学）、`-lpthread`（线程）、`-ldl`（动态加载）
- 用 `ldd` 查看可执行文件的动态库依赖

## 第 18 讲 动态库运行时路径配置

### 概念

动态库在运行时需要被动态链接器找到，这涉及运行时搜索路径的配置。配置方式有多种：`-Wl,-rpath`（编译时嵌入）、`LD_LIBRARY_PATH`（环境变量）、`/etc/ld.so.conf`（系统配置）、`ldconfig`（缓存更新）。理解这些机制是部署动态库应用的关键。

### 原理

程序启动时，动态链接器 `ld-linux.so` 按以下顺序查找动态库：

1. **DT_RPATH / DT_RUNPATH**（ELF 文件中嵌入的路径，由 `-Wl,-rpath` 设置）
2. **`LD_LIBRARY_PATH`** 环境变量（临时设置，不推荐长期使用）
3. **`DT_RUNPATH`**（如果存在，由 `-Wl,--enable-new-dtags -Wl,-rpath` 设置）
4. **`/etc/ld.so.cache`**（由 `ldconfig` 生成的缓存，对应 `/etc/ld.so.conf` 配置）
5. **默认路径**：`/lib`、`/usr/lib`

`-Wl,-rpath` 是最可靠的方案，因为它将路径硬编码到可执行文件中，部署后无需额外配置。`-Wl,-rpath,'$ORIGIN'` 是一个特殊用法，`$ORIGIN` 表示可执行文件所在目录，便于随程序打包库文件。

### 例子

**项目结构**：

```
app/
├── bin/
│   └── myapp
├── lib/
│   └── libmylib.so
└── src/
    └── main.c
```

**方法1：`-Wl,-rpath` 嵌入路径（推荐）**：

```bash
# 编译时指定运行时库路径
gcc src/main.c -L./lib -lmylib -Wl,-rpath,/home/z/my-project/app/lib -o bin/myapp

# 验证
readelf -d bin/myapp | grep -E "rpath|runpath"
# 输出: 0x000000000000000f (RPATH) Library rpath: [/home/z/my-project/app/lib]

./bin/myapp  # 直接运行，无需设置环境变量
```

**方法2：`$ORIGIN` 相对路径（适合打包部署）**：

```bash
# $ORIGIN 表示可执行文件所在目录
gcc src/main.c -L./lib -lmylib -Wl,-rpath,'$ORIGIN/../lib' -o bin/myapp

# 注意：$ORIGIN 必须用单引号防止 shell 展开
readelf -d bin/myapp | grep rpath
# 输出: Library rpath: [$ORIGIN/../lib]

# 移动整个 app 目录后仍可运行
mv app /tmp/app
/tmp/app/bin/myapp  # 成功运行
```

**方法3：`LD_LIBRARY_PATH` 环境变量（临时）**：

```bash
# 临时设置
export LD_LIBRARY_PATH=/home/z/my-project/app/lib:$LD_LIBRARY_PATH
./bin/myapp

# 单次设置
LD_LIBRARY_PATH=./lib ./bin/myapp
```

**方法4：系统配置（永久）**：

```bash
# 添加库路径到系统配置
echo "/home/z/my-project/app/lib" | sudo tee /etc/ld.so.conf.d/myapp.conf
sudo ldconfig  # 更新缓存

# 验证
ldconfig -p | grep mylib
# 输出: libmylib.so (libc6,x86-64) => /home/z/my-project/app/lib/libmylib.so

./bin/myapp  # 成功运行
```

**方法5：复制到系统标准目录**：

```bash
sudo cp libmylib.so /usr/local/lib/
sudo ldconfig
./bin/myapp
```

**调试库查找问题**：

```bash
# 查看动态链接器的搜索行为
LD_DEBUG=libs ./bin/myapp 2>&1 | head -30
# 输出详细的库查找过程

# 查看可执行文件的 RPATH
readelf -d bin/myapp | grep -E "rpath|runpath"

# 查看系统库缓存
ldconfig -p | grep mylib
```

**`-Wl,--enable-new-dtags` 使用 RUNPATH**：

```bash
# RPATH 和 RUNPATH 的区别：
# RPATH 优先级高于 LD_LIBRARY_PATH
# RUNPATH 优先级低于 LD_LIBRARY_PATH（更灵活）

gcc src/main.c -L./lib -lmylib \
    -Wl,--enable-new-dtags -Wl,-rpath,/home/z/my-project/app/lib \
    -o bin/myapp

readelf -d bin/myapp | grep -E "rpath|runpath"
# 输出: 0x000000000000001d (RUNPATH) Library runpath: [...]
```

### 总结

- 动态库运行时查找顺序：RPATH → LD_LIBRARY_PATH → RUNPATH → ld.so.cache → 默认路径
- `-Wl,-rpath` 是最可靠的方案，路径嵌入可执行文件
- `$ORIGIN` 实现相对路径，适合打包部署
- `LD_LIBRARY_PATH` 适合临时调试，不推荐长期使用
- `/etc/ld.so.conf.d/` + `ldconfig` 适合系统级安装
- 用 `readelf -d` 查看 RPATH/RUNPATH，用 `LD_DEBUG=libs` 调试查找过程

# 第五章：预处理与宏

## 第 19 讲 宏定义（-D）

### 概念

`-D` 选项用于在命令行定义预处理宏，等价于在源文件开头写 `#define`。这在编译时配置程序行为（如调试开关、平台选择、版本号）非常有用，无需修改源代码即可生成不同版本的可执行文件。配合 `#ifdef` 条件编译，可以实现灵活的编译时配置。

### 原理

`-D` 选项的语法：
- `-DNAME`：定义宏 `NAME` 为 `1`（即 `#define NAME 1`）
- `-DNAME=value`：定义宏 `NAME` 为 `value`（即 `#define NAME value`）
- `-DNAME="string"`：定义宏为字符串（注意 shell 引号）

预处理器在处理源文件前，先将所有 `-D` 定义的宏加入宏表，然后正常展开。`-D` 定义的宏与源文件中 `#define` 的宏完全等价，优先级相同（后定义的覆盖先定义的）。

对应的取消定义选项是 `-U`（undefine），用于取消某个宏的定义。

### 例子

**基本用法**：

```c
// config_demo.c
#include <stdio.h>

int main() {
#ifdef DEBUG
    printf("Debug mode enabled\n");
    printf("Debug level: %d\n", DEBUG_LEVEL);
#else
    printf("Release mode\n");
#endif

    printf("Version: %s\n", VERSION);

    return 0;
}
```

```bash
# 不定义任何宏（Release 模式）
gcc config_demo.c -o config_demo
./config_demo
# 输出:
# Release mode
# Version: (null)  或编译错误（VERSION 未定义）

# 定义 DEBUG 宏
gcc -DDEBUG config_demo.c -o config_demo
./config_demo
# 输出: Debug mode enabled

# 定义带值的宏
gcc -DDEBUG -DDEBUG_LEVEL=3 -DVERSION=\"1.0.0\" config_demo.c -o config_demo
./config_demo
# 输出:
# Debug mode enabled
# Debug level: 3
# Version: 1.0.0
```

**实际应用：日志级别控制**：

```c
// logger.c
#include <stdio.h>

#define LOG_ERROR 1
#define LOG_WARN  2
#define LOG_INFO  3
#define LOG_DEBUG 4

#ifndef LOG_LEVEL
#define LOG_LEVEL LOG_INFO  // 默认级别
#endif

#define LOG(level, msg) do { \
    if (level <= LOG_LEVEL) { \
        printf("[%d] %s:%d: %s\n", level, __FILE__, __LINE__, msg); \
    } \
} while(0)

int main() {
    LOG(LOG_ERROR, "This is an error");
    LOG(LOG_WARN,  "This is a warning");
    LOG(LOG_INFO,  "This is info");
    LOG(LOG_DEBUG, "This is debug");
    return 0;
}
```

```bash
# 默认日志级别（INFO）
gcc logger.c -o logger && ./logger
# 输出 ERROR, WARN, INFO（不输出 DEBUG）

# 设置为 DEBUG 级别
gcc -DLOG_LEVEL=4 logger.c -o logger && ./logger
# 输出所有级别日志

# 设置为 ERROR 级别（只输出错误）
gcc -DLOG_LEVEL=1 logger.c -o logger && ./logger
# 只输出 ERROR
```

**平台选择**：

```c
// platform.c
#include <stdio.h>

int main() {
    printf("Running on: ");
#ifdef PLATFORM_WINDOWS
    printf("Windows\n");
#elif defined(PLATFORM_LINUX)
    printf("Linux\n");
#elif defined(PLATFORM_MACOS)
    printf("macOS\n");
#else
    printf("Unknown\n");
#endif
    return 0;
}
```

```bash
gcc -DPLATFORM_LINUX platform.c -o platform && ./platform
# 输出: Running on: Linux

gcc -DPLATFORM_WINDOWS platform.c -o platform && ./platform
# 输出: Running on: Windows
```

**`-U` 取消宏定义**：

```c
// undef_demo.c
#include <stdio.h>
int main() {
#ifdef FEATURE_X
    printf("Feature X enabled\n");
#else
    printf("Feature X disabled\n");
#endif
    return 0;
}
```

```bash
# 如果源文件中默认定义了 FEATURE_X，可以用 -U 取消
gcc -UFEATURE_X undef_demo.c -o undef_demo
```

**在 Makefile 中使用 `-D`**：

```makefile
VERSION = 1.2.3
CFLAGS = -DVERSION=\"$(VERSION)\" -DDEBUG

app: main.c
        gcc $(CFLAGS) main.c -o app
```

### 总结

- `-D` 在命令行定义宏，等价于 `#define`
- `-DNAME` 定义为 1，`-DNAME=value` 定义为指定值
- 字符串值需要转义引号：`-DVERSION=\"1.0\"`
- 常用于调试开关、日志级别、平台选择、版本号配置
- `-U` 取消宏定义
- 配合 `#ifdef` 实现编译时配置，无需修改源代码

## 第 20 讲 条件编译

### 概念

条件编译是预处理器的核心功能之一，它根据条件决定哪些代码段被编译、哪些被忽略。通过 `#if`、`#ifdef`、`#ifndef`、`#elif`、`#else`、`#endif` 等指令，可以在编译时选择不同的代码路径，实现跨平台支持、调试开关、功能裁剪等需求。

### 原理

条件编译指令的工作方式：

| 指令 | 含义 |
|------|------|
| `#if 表达式` | 表达式为真（非0）则编译 |
| `#ifdef 宏` | 宏已定义则编译 |
| `#ifndef 宏` | 宏未定义则编译 |
| `#elif 表达式` | 否则如果（else if） |
| `#else` | 其他情况 |
| `#endif` | 结束条件块 |

条件编译在**预处理阶段**处理，被排除的代码不会进入编译阶段，因此不会产生任何代码体积，也不会被语法检查（被排除的代码可以有语法错误，只要不被编译）。

`#if` 支持常量表达式运算，但不能使用 `sizeof`、类型转换等。常用 `defined(宏)` 函数判断宏是否定义。

### 例子

**基本条件编译**：

```c
// conditional.c
#include <stdio.h>

#define VERSION 3

int main() {
#if VERSION >= 3
    printf("Version 3+ features\n");
#elif VERSION == 2
    printf("Version 2 features\n");
#else
    printf("Legacy version\n");
#endif
    return 0;
}
```

**头文件保护（Include Guard）**：

```c
// myheader.h - 防止重复包含
#ifndef MYHEADER_H
#define MYHEADER_H

// 头文件内容
int my_function(int x);

#endif // MYHEADER_H
```

```c
// 也可以用 #pragma once（非标准但广泛支持）
#pragma once
int my_function(int x);
```

**跨平台代码**：

```c
// cross_platform.c
#include <stdio.h>

#ifdef _WIN32
    #include <windows.h>
    #define SLEEP(ms) Sleep(ms)
    #define PLATFORM "Windows"
#elif defined(__linux__)
    #include <unistd.h>
    #define SLEEP(ms) usleep(ms * 1000)
    #define PLATFORM "Linux"
#elif defined(__APPLE__)
    #include <unistd.h>
    #define SLEEP(ms) usleep(ms * 1000)
    #define PLATFORM "macOS"
#else
    #define SLEEP(ms)
    #define PLATFORM "Unknown"
#endif

int main() {
    printf("Platform: %s\n", PLATFORM);
    printf("Sleeping 100ms...\n");
    SLEEP(100);
    printf("Done\n");
    return 0;
}
```

**调试日志开关**：

```c
// debug_log.c
#include <stdio.h>

#ifdef DEBUG
    #define LOG(msg, ...) printf("[DEBUG] %s:%d: " msg "\n", \
                                 __FILE__, __LINE__, ##__VA_ARGS__)
#else
    #define LOG(msg, ...)  // Release 模式下为空
#endif

int main() {
    LOG("Program started");
    LOG("Value of x = %d", 42);
    printf("Hello\n");
    return 0;
}
```

```bash
# Release 模式
gcc debug_log.c -o debug_log && ./debug_log
# 输出: Hello

# Debug 模式
gcc -DDEBUG debug_log.c -o debug_log && ./debug_log
# 输出:
# [DEBUG] debug_log.c:12: Program started
# [DEBUG] debug_log.c:13: Value of x = 42
# Hello
```

**功能裁剪**：

```c
// features.c
#include <stdio.h>

int main() {
    printf("Core features\n");

#ifdef FEATURE_NETWORK
    printf("Network feature\n");
#endif

#ifdef FEATURE_DATABASE
    printf("Database feature\n");
#endif

#ifdef FEATURE_GUI
    printf("GUI feature\n");
#endif

    return 0;
}
```

```bash
# 只编译核心功能
gcc features.c -o features_min

# 编译全部功能
gcc -DFEATURE_NETWORK -DFEATURE_DATABASE -DFEATURE_GUI features.c -o features_full

# 编译网络和数据库版本
gcc -DFEATURE_NETWORK -DFEATURE_DATABASE features.c -o features_net_db
```

**`defined()` 运算符**：

```c
// defined_demo.c
#include <stdio.h>

int main() {
#if defined(DEBUG) && defined(VERBOSE)
    printf("Verbose debug mode\n");
#elif defined(DEBUG)
    printf("Debug mode\n");
#else
    printf("Release mode\n");
#endif
    return 0;
}
```

**查看条件编译结果**：

```bash
# 用 -E 查看哪些代码被保留
gcc -E -DDEBUG debug_log.c | tail -10
# 可以看到 LOG 宏被展开，printf 语句被保留
```

### 总结

- 条件编译在预处理阶段决定代码是否参与编译
- `#ifdef`/`#ifndef` 判断宏是否定义，`#if` 判断常量表达式
- 头文件保护（Include Guard）是条件编译最常见的应用
- 跨平台代码用 `#ifdef _WIN32`、`#ifdef __linux__` 等平台宏
- 被排除的代码不做语法检查，可以包含未完成的代码
- 用 `gcc -E` 查看条件编译的预处理结果

## 第 21 讲 内置宏与 #pragma

### 概念

GCC 预定义了大量内置宏（如 `__FILE__`、`__LINE__`、`__DATE__`），可在代码中直接使用，用于调试、日志、版本信息等。`#pragma` 指令是编译器特定的指令，用于控制编译行为（如对齐、警告、优化），GCC 支持 `#pragma GCC` 系列指令和 `_Pragma` 运算符。

### 原理

**内置宏分类**：

1. **标准预定义宏**（C 标准要求）：
   - `__FILE__`：当前源文件名（字符串）
   - `__LINE__`：当前行号（整数）
   - `__DATE__`：编译日期（字符串，如 "Jul 11 2026"）
   - `__TIME__`：编译时间（字符串，如 "14:30:00"）
   - `__func__`：当前函数名（C99）

2. **GCC 预定义宏**：
   - `__GNUC__`：GCC 主版本号
   - `__GNUC_MINOR__`：次版本号
   - `__linux__`、`_WIN32`、`__APPLE__`：平台标识
   - `__x86_64__`、`__arm__`：CPU 架构
   - `__STDC__`、`__STDC_VERSION__`：C 标准版本

3. **`#pragma` 指令**：
   - `#pragma GCC diagnostic`：控制警告
   - `#pragma GCC push_options` / `pop_options`：保存/恢复编译选项
   - `#pragma GCC optimize`：函数级优化控制
   - `#pragma once`：头文件只包含一次
   - `#pragma pack`：结构体对齐控制

### 例子

**标准内置宏**：

```c
// builtin_macros.c
#include <stdio.h>

void log_info(const char* msg) {
    printf("[%s:%d %s] %s\n", __FILE__, __LINE__, __func__, msg);
}

int main() {
    printf("File: %s\n", __FILE__);
```

```c
struct Default {

    int b;      // 4 bytes
    char c;     // 1 byte + 3 padding

struct Packed1 {
    char a;     // 1 byte
    int b;      // 4 bytes
    char c;     // 1 byte
};  // sizeof = 6
#pragma pack(pop)

// 2 字节对齐
#pragma pack(push, 2)
struct Packed2 {
    char a;     // 1 byte + 1 padding
    int b;      // 4 bytes
    char c;     // 1 byte + 1 padding
};  // sizeof = 8
#pragma pack(pop)

int main() {
    printf("Default: %zu\n", sizeof(struct Default));   // 12
    printf("Packed1: %zu\n", sizeof(struct Packed1));   // 6
    printf("Packed2: %zu\n", sizeof(struct Packed2));   // 8
    return 0;
}
```

# 第六章：多文件与项目构建

## 第 22 讲 多文件编译

### 概念

实际项目通常由多个源文件组成，每个文件负责不同的模块。多文件编译是将多个 `.c`/`.cpp` 文件编译链接为一个可执行文件的过程。GCC 支持一次性编译所有文件，也支持分步编译（先各自编译为 `.o`，再链接）。理解多文件编译是项目构建的基础。

### 原理

多文件编译的两种方式：

**方式1：一次性编译**
```
gcc main.c utils.c io.c -o program
```
GCC 内部会分别编译每个源文件为 `.o`，然后统一链接。简单方便，但任何文件修改都需要重新编译所有文件。

**方式2：分步编译**
```
gcc -c main.c -o main.o
gcc -c utils.c -o utils.o
gcc -c io.c -o io.o
gcc main.o utils.o io.o -o program
```
先分别编译为 `.o`，再链接。修改某个文件只需重新编译该文件的 `.o`，其他 `.o` 可复用。这是大型项目的标准做法。

多文件项目的关键约定：
- 每个模块的**接口**（函数声明、类型定义）放在头文件 `.h`
- 每个模块的**实现**放在源文件 `.c`/`.cpp`
- 使用模块时 `#include` 其头文件
- 头文件使用 Include Guard 防止重复包含

### 例子

**项目结构**：

```
multi_file/
├── main.c
├── calculator.h
├── calculator.c
├── printer.h
└── printer.c
```

**calculator.h**：

```c
#ifndef CALCULATOR_H
#define CALCULATOR_H

int add(int a, int b);
int subtract(int a, int b);
int multiply(int a, int b);
double divide(int a, int b);

#endif
```

**calculator.c**：

```c
#include "calculator.h"
#include <stdio.h>

int add(int a, int b) { return a + b; }
int subtract(int a, int b) { return a - b; }
int multiply(int a, int b) { return a * b; }

double divide(int a, int b) {
    if (b == 0) {
        fprintf(stderr, "Error: division by zero\n");
        return 0;
    }
    return (double)a / b;
}
```

**printer.h**：

```c
#ifndef PRINTER_H
#define PRINTER_H

void print_result(const char* op, int a, int b, double result);

#endif
```

**printer.c**：

```c
#include "printer.h"
#include <stdio.h>

void print_result(const char* op, int a, int b, double result) {
    printf("%d %s %d = %.2f\n", a, op, b, result);
}
```

**main.c**：

```c
#include <stdio.h>
#include "calculator.h"
#include "printer.h"

int main() {
    int a = 20, b = 4;

    print_result("+", a, b, add(a, b));
    print_result("-", a, b, subtract(a, b));
    print_result("*", a, b, multiply(a, b));
    print_result("/", a, b, divide(a, b));

    return 0;
}
```

**方式1：一次性编译**：

```bash
gcc -Wall main.c calculator.c printer.c -o calc
./calc
# 输出:
# 20 + 4 = 24.00
# 20 - 4 = 16.00
# 20 * 4 = 80.00
# 20 / 4 = 5.00
```

**方式2：分步编译**：

```bash
# 分别编译各源文件
gcc -Wall -c main.c -o main.o
gcc -Wall -c calculator.c -o calculator.o
gcc -Wall -c printer.c -o printer.o

# 链接
gcc main.o calculator.o printer.o -o calc

./calc
# 输出同上
```

**增量编译的优势**：

```bash
# 假设只修改了 calculator.c
# 只需重新编译 calculator.o，其他 .o 复用
gcc -Wall -c calculator.c -o calculator.o

# 重新链接
gcc main.o calculator.o printer.o -o calc
# main.o 和 printer.o 不需要重新编译，节省时间
```

**C++ 多文件编译**：

```bash
# C++ 项目
g++ -std=c++17 -Wall -c main.cpp -o main.o
g++ -std=c++17 -Wall -c engine.cpp -o engine.o
g++ main.o engine.o -o app
```

**使用头文件目录**：

```bash
# 如果头文件在 include/ 目录
gcc -I./include -c main.c -o main.o
gcc -I./include -c calculator.c -o calculator.o
gcc main.o calculator.o -o calc
```

**查看依赖关系**：

```bash
# 查看目标文件的依赖
gcc -MM main.c
# 输出: main.o: main.c calculator.h printer.h

# 这对自动生成 Makefile 依赖很有用
```

### 总结

- 多文件编译有两种方式：一次性编译（简单）和分步编译（高效）
- 分步编译支持增量编译，修改一个文件只需重新编译该文件
- 模块化设计：接口放 `.h`，实现放 `.c`，使用时 `#include` 头文件
- 头文件必须用 Include Guard 防止重复包含
- `gcc -MM` 可自动生成文件依赖关系，用于 Makefile
- 大型项目必须用分步编译 + Makefile/CMake 管理

## 第 23 讲 Makefile 基础

### 概念

Makefile 是 `make` 工具的配置文件，用于自动化管理项目的编译过程。它定义了文件之间的依赖关系和构建规则，`make` 根据这些规则和文件时间戳决定哪些文件需要重新编译。Makefile 是 C/C++ 项目最经典的构建工具，解决了手动编译多文件项目的繁琐问题。

### 原理

Makefile 的基本结构：

```makefile
目标: 依赖
        命令
```

- **目标（Target）**：要生成的文件名（如 `main.o`、`app`）或动作名（如 `clean`）
- **依赖（Prerequisites）**：生成目标所需的文件
- **命令（Recipe）**：生成目标的 shell 命令，**必须用 Tab 缩进**（不能用空格）

`make` 的工作流程：
1. 读取 Makefile，构建依赖图
2. 检查每个依赖是否比目标新（时间戳比较）
3. 如果依赖更新或目标不存在，执行命令重新生成目标
4. 按依赖顺序递归构建

Makefile 支持变量、自动变量、模式规则、函数等高级特性，使构建规则更简洁。

### 例子

**基础 Makefile**：

```makefile
# Makefile - 基础版本
CC = gcc
CFLAGS = -Wall -g

calc: main.o calculator.o printer.o
        $(CC) $(CFLAGS) main.o calculator.o printer.o -o calc

main.o: main.c calculator.h printer.h
        $(CC) $(CFLAGS) -c main.c -o main.o

calculator.o: calculator.c calculator.h
        $(CC) $(CFLAGS) -c calculator.c -o calculator.o

printer.o: printer.c printer.h
        $(CC) $(CFLAGS) -c printer.c -o printer.o

clean:
        rm -f *.o calc
```

**使用 Makefile**：

```bash
make          # 构建第一个目标（calc）
make calc     # 显式构建 calc
make clean    # 执行清理
make -B       # 强制重新构建所有目标
make -j4      # 并行构建（4个任务）
```

**使用自动变量和模式规则（进阶）**：

```makefile
# Makefile - 进阶版本
CC = gcc
CFLAGS = -Wall -g -std=c11
TARGET = calc
SRCS = main.c calculator.c printer.c
OBJS = $(SRCS:.c=.o)

# 默认目标
all: $(TARGET)

# 链接
$(TARGET): $(OBJS)
        $(CC) $(CFLAGS) $^ -o $@

# 模式规则：所有 .o 依赖同名 .c
%.o: %.c
        $(CC) $(CFLAGS) -c $< -o $@

# 依赖关系（可用 gcc -MM 自动生成）
main.o: calculator.h printer.h
calculator.o: calculator.h
printer.o: printer.h

clean:
        rm -f $(OBJS) $(TARGET)

.PHONY: all clean
```

**自动变量说明**：

| 变量 | 含义 |
|------|------|
| `$@` | 目标文件名 |
| `$<` | 第一个依赖文件 |
| `$^` | 所有依赖文件（去重） |
| `$?` | 比目标新的依赖文件 |
| `$*` | 匹配模式规则中 `%` 的部分 |

**自动生成依赖**：

```makefile
# 使用 gcc -MM 自动生成依赖
DEPS = $(SRCS:.c=.d)

%.d: %.c
        $(CC) -MM $< -o $@

-include $(DEPS)
```

**C++ 项目的 Makefile**：

```makefile
CXX = g++
CXXFLAGS = -std=c++17 -Wall -Wextra -g
LDFLAGS = -lpthread

TARGET = app
SRCS = $(wildcard src/*.cpp)
OBJS = $(SRCS:.cpp=.o)

$(TARGET): $(OBJS)
        $(CXX) $(CXXFLAGS) $^ -o $@ $(LDFLAGS)

%.o: %.cpp
        $(CXX) $(CXXFLAGS) -c $< -o $@

clean:
        rm -f $(OBJS) $(TARGET)

.PHONY: clean
```

**调试 Makefile**：

```bash
make -n       # 只打印命令不执行（dry run）
make -d       # 显示详细调试信息
make --trace  # 显示每条规则的执行情况
make V=1      # 显示完整命令（如果 Makefile 用了 @ 静默）
```

### 总结

- Makefile 定义目标、依赖、命令，`make` 根据时间戳增量构建
- 命令行必须用 **Tab** 缩进，不能用空格
- 变量（`CC`、`CFLAGS`）和自动变量（`$@`、`$<`、`$^`）简化规则
- 模式规则 `%.o: %.c` 可匹配所有同类文件
- `.PHONY` 声明伪目标（如 `clean`），避免与同名文件冲突
- `make -n` 预览命令，`make -j4` 并行构建
- 大型项目可用 `gcc -MM` 自动生成依赖关系

## 第 24 讲 CMake 简介

### 概念

CMake 是一个跨平台的构建系统生成器，它不直接构建项目，而是根据 `CMakeLists.txt` 配置文件生成标准的构建文件（如 Makefile、Ninja、Visual Studio 工程）。CMake 解决了 Makefile 跨平台困难、语法复杂的问题，是现代 C/C++ 项目的主流构建工具。

### 原理

CMake 的工作流程：

1. **编写 `CMakeLists.txt`**：描述项目结构、源文件、依赖、编译选项
2. **配置阶段**：运行 `cmake` 生成构建系统（如 Makefile）
3. **构建阶段**：运行 `cmake --build` 或直接 `make` 编译项目

CMake 的核心概念：
- **项目（Project）**：`project()` 定义项目名称和语言
- **目标（Target）**：`add_executable()` / `add_library()` 定义构建目标
- **变量**：`set()` 设置变量，`${VAR}` 引用
- **属性**：`target_include_directories()`、`target_link_libraries()` 设置目标属性
- **生成器**：决定生成什么构建系统（Makefile、Ninja、VS 等）

CMake 采用"声明式"语法，描述"要构建什么"而非"如何构建"，比 Makefile 更高级。

### 例子

**基础 CMakeLists.txt**：

```cmake
# CMakeLists.txt - 基础版本
cmake_minimum_required(VERSION 3.10)

project(Calculator C)

set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)

# 添加可执行文件
add_executable(calc
    main.c
    calculator.c
    printer.c
)

# 编译选项
target_compile_options(calc PRIVATE -Wall -Wextra -g)

# 头文件目录
target_include_directories(calc PRIVATE ${CMAKE_CURRENT_SOURCE_DIR})
```

**构建项目**：

```bash
# 创建构建目录（推荐 out-of-source 构建）
mkdir build && cd build

# 配置（生成 Makefile）
cmake ..

# 构建
make
# 或
cmake --build .

# 运行
./calc
```

**带子目录的项目结构**：

```
project/
├── CMakeLists.txt
├── src/
│   ├── CMakeLists.txt
│   ├── main.c
│   ├── calculator.c
│   └── calculator.h
└── lib/
    ├── CMakeLists.txt
    ├── utils.c
    └── utils.h
```

**顶层 CMakeLists.txt**：

```cmake
cmake_minimum_required(VERSION 3.10)
project(MyApp C)

set(CMAKE_C_STANDARD 11)

# 添加子目录
add_subdirectory(src)
add_subdirectory(lib)
```

**src/CMakeLists.txt**：

```cmake
add_executable(app main.c)
target_link_libraries(app utils)
target_include_directories(app PRIVATE ${CMAKE_SOURCE_DIR}/lib)
```

**lib/CMakeLists.txt**：

```cmake
add_library(utils STATIC utils.c)
target_include_directories(utils PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})
```

**创建动态库**：

```cmake
# 创建动态库
add_library(mymath SHARED
    add.c
    sub.c
    mul.c
)

# 设置属性
set_target_properties(mymath PROPERTIES
    VERSION 1.0
    SOVERSION 1
    OUTPUT_NAME mymath
)
```

**链接外部库**：

```cmake
# 链接数学库
add_executable(math_demo math_demo.c)
target_link_libraries(math_demo m)

# 使用 find_package 查找第三方库
find_package(Threads REQUIRED)
add_executable(thread_demo thread_demo.c)
target_link_libraries(thread_demo Threads::Threads)
```

**条件编译**：

```cmake
option(DEBUG_MODE "Enable debug mode" OFF)

if(DEBUG_MODE)
    target_compile_definitions(app PRIVATE DEBUG=1)
    target_compile_options(app PRIVATE -g -O0)
else()
    target_compile_options(app PRIVATE -O2)
endif()

# 平台判断
if(WIN32)
    target_compile_definitions(app PRIVATE PLATFORM_WINDOWS)
elseif(UNIX)
    target_compile_definitions(app PRIVATE PLATFORM_LINUX)
endif()
```

**C++ 项目示例**：

```cmake
cmake_minimum_required(VERSION 3.15)
project(MyCppApp CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(app
    src/main.cpp
    src/engine.cpp
    src/renderer.cpp
)

target_include_directories(app PRIVATE include)
target_compile_features(app PRIVATE cxx_std_17)
target_compile_options(app PRIVATE -Wall -Wextra)

# 测试
enable_testing()
add_test(NAME app_test COMMAND app --test)
```

**常用 CMake 命令**：

```bash
# 配置（指定生成器）
cmake -G "Unix Makefiles" ..
cmake -G "Ninja" ..

# 配置（指定构建类型）
cmake -DCMAKE_BUILD_TYPE=Debug ..
cmake -DCMAKE_BUILD_TYPE=Release ..

# 配置（指定安装路径）
cmake -DCMAKE_INSTALL_PREFIX=/usr/local ..

# 构建
cmake --build . -- -j4    # 传递 -j4 给 make
cmake --build . --config Release  # 多配置生成器

# 安装
cmake --install .

# 清理
cmake --build . --target clean
```

### 总结

- CMake 是构建系统生成器，生成 Makefile/Ninja 等具体构建文件
- `CMakeLists.txt` 描述项目结构和构建规则，语法声明式
- 推荐使用 out-of-source 构建：`mkdir build && cd build && cmake ..`
- `add_executable()` / `add_library()` 定义构建目标
- `target_*` 系列命令设置目标属性（头文件、库、编译选项）
- `find_package()` 查找外部库，`option()` 定义可配置选项
- CMake 是现代 C/C++ 项目的主流选择，跨平台支持好

# 第七章：调试与性能分析

## 第 25 讲 GDB 调试配合

### 概念

GDB（GNU Debugger）是 GNU 项目调试器，用于在运行时检查程序状态、设置断点、单步执行、查看变量等。GCC 与 GDB 配合使用时，需要用 `-g` 选项编译以生成调试信息。GDB 是 C/C++ 程序员排查逻辑错误、段错误、内存问题的核心工具。

### 原理

GDB 调试的工作机制：

1. **调试信息**：GCC 用 `-g` 在 ELF 文件中嵌入 DWARF 调试信息，包含源码行号、变量名、类型等
2. **进程控制**：GDB 通过 `ptrace` 系统调用控制被调试进程，能暂停/恢复执行、读写内存
3. **信号拦截**：GDB 拦截 SIGSEGV（段错误）、SIGABRT 等信号，在崩溃点暂停程序
4. **断点机制**：GDB 在指定地址插入断点指令（如 x86 的 `INT 3`），执行到此处时暂停

GDB 调试的前提是程序用 `-g` 编译。优化（`-O`）会干扰调试（变量被优化掉、代码顺序改变），建议调试时用 `-g -O0`。

### 例子

**示例程序（含 bug）**：

```c

    if (n < 0) return -1;  // 错误处理

        sum += arr[i];
    }
    return sum;
}

int main() {
    int n = 5;
    int result = factorial(n);
    printf("%d! = %d\n", n, result);

    int arr[5] = {1, 2, 3, 4, 5};
    int total = sum_array(arr, 5);
    printf("Sum = %d\n", total);

    return 0;
}
```


## 第 26 讲 性能分析（gprof）

### 概念

gprof 是 GNU 性能分析工具，用于分析程序运行时各函数的调用次数和执行时间，帮助定位性能瓶颈。使用 gprof 需要用 `-pg` 选项编译，程序运行后会生成 `gmon.out` 数据文件，再用 `gprof` 命令分析。gprof 适合分析 CPU 密集型程序的性能热点。

### 原理

gprof 的工作流程：

1. **插桩**：`-pg` 选项让 GCC 在每个函数入口插入对 `mcount` 函数的调用，记录函数调用关系
2. **采样**：程序运行时定期采样（默认 100Hz），记录当前执行的函数
3. **数据输出**：程序正常退出时，将调用次数和采样数据写入 `gmon.out`
4. **分析报告**：`gprof` 读取 `gmon.out` 和可执行文件，生成性能报告

gprof 的局限：
- 只能分析用户态 CPU 时间，不包含 I/O 等待
- 采样有统计误差，短函数可能测不准
- 多线程支持有限（每个线程需单独处理）
- 程序必须正常退出（`exit()`），不能被信号杀死

### 例子

**示例程序**：

```c
// profile_demo.c
#include <stdio.h>
#include <stdlib.h>

long long sum_naive(int n) {
    long long sum = 0;
    for (int i = 0; i < n; i++) {
        sum += i;
    }
    return sum;
}

long long sum_formula(int n) {
    return (long long)n * (n + 1) / 2;
}

void bubble_sort(int *arr, int n) {
    for (int i = 0; i < n - 1; i++) {
        for (int j = 0; j < n - i - 1; j++) {
            if (arr[j] > arr[j + 1]) {
                int tmp = arr[j];
                arr[j] = arr[j + 1];
                arr[j + 1] = tmp;
            }
        }
    }
}

int main() {
    // 求和测试
    printf("Naive sum: %lld\n", sum_naive(100000000));
    printf("Formula sum: %lld\n", sum_formula(100000000));

    // 排序测试
    int *arr = malloc(10000 * sizeof(int));
    for (int i = 0; i < 10000; i++) {
        arr[i] = 10000 - i;  // 逆序数组
    }
    bubble_sort(arr, 10000);
    printf("Sorted: %d, %d, %d...\n", arr[0], arr[1], arr[2]);
    free(arr);

    return 0;
}
```

**编译带性能分析**：

```bash

```

**运行程序（生成 gmon.out）**：

```bash
# gmon.out
```

- 适合 CPU 密集型程序的性能优化

## 第 27 讲 内存检测（Sanitizer / Valgrind）

### 概念

内存错误是 C/C++ 程序中最常见、最难排查的问题，包括内存泄漏、越界访问、悬空指针、双重释放等。GCC 内置的 Sanitizer（`-fsanitize`）和独立的 Valgrind 工具是两大内存检测利器。Sanitizer 性能开销小、集成度高；Valgrind 功能全面、无需重新编译。

### 原理

**AddressSanitizer (ASan)**：
- GCC 用 `-fsanitize=address` 启用
- 编译时在内存访问前后插入检查代码
- 运行时用"影子内存"跟踪每字节的可用性
- 检测：堆/栈/全局变量越界、释放后使用、双重释放、内存泄漏
- 性能开销：约 2x 慢，内存占用约 3x

**UndefinedBehaviorSanitizer (UBSan)**：
- GCC 用 `-fsanitize=undefined` 启用
- 检测：整数溢出、空指针解引用、除零、类型转换违规等
- 性能开销小

**Valgrind**：
- 独立工具，无需重新编译（但 `-g` 有助于定位）
- 通过 JIT 翻译所有机器码，模拟执行
- 检测：内存泄漏、越界、未初始化读取、无效释放
- 性能开销：10-50x 慢，但检测最全面

### 例子

**含内存错误的程序**：

```c
// mem_bugs.c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

void buffer_overflow() {
    int arr[5] = {0};
    arr[10] = 42;  // 栈缓冲区溢出
    printf("arr[10] = %d\n", arr[10]);
}

void use_after_free() {
    int *p = malloc(sizeof(int));
    *p = 100;
    free(p);
    printf("After free: %d\n", *p);  // 释放后使用
}

void memory_leak() {
    int *p = malloc(100 * sizeof(int));
    p[0] = 42;
    // 忘记 free(p)，内存泄漏
}

int main() {
    buffer_overflow();
    use_after_free();
    memory_leak();
    return 0;
}
```

**使用 AddressSanitizer**：

```bash
# 编译时启用 ASan
gcc -fsanitize=address -g -O0 mem_bugs.c -o mem_bugs_asan

# 运行
./mem_bugs_asan
# 输出:
# =================================================================
# ==12345==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x...
# ...
# #0 0x... in buffer_overflow mem_bugs.c:7
# #1 0x... in main mem_bugs.c:23
# ...
```

**同时启用 ASan 和 UBSan**：

```bash
gcc -fsanitize=address,undefined -g -O0 mem_bugs.c -o mem_bugs_san
./mem_bugs_san
```

**检测内存泄漏**：

```bash
# ASan 在程序退出时报告泄漏
gcc -fsanitize=address -g mem_bugs.c -o mem_bugs_leak
ASAN_OPTIONS=detect_leaks=1 ./mem_bugs_leak
# 输出:
# =================================================================
# ==12345==ERROR: LeakSanitizer: detected memory leaks
# Direct leak of 400 byte(s) in 1 object(s) allocated from:
# #0 0x... in malloc ...
# #1 0x... in memory_leak mem_bugs.c:16
```

**使用 Valgrind**：

```bash
# 编译（只需 -g，无需特殊选项）
gcc -g -O0 mem_bugs.c -o mem_bugs_val

# 运行 Valgrind
valgrind --leak-check=full --show-leak-kinds=all ./mem_bugs_val
# 输出:
# ==12345== Invalid write of size 4
# ==12345==    at 0x10917A: buffer_overflow (mem_bugs.c:7)
# ==12345==    by 0x1091E8: main (mem_bugs.c:23)
# ...
# ==12345== HEAP SUMMARY:
# ==12345==     in use at exit: 400 bytes in 1 blocks
# ==12345==   total heap usage: 2 allocs, 1 frees, 1,424 bytes allocated
# ==12345==
# ==12345== 400 bytes in 1 blocks are definitely lost in loss record 1 of 1
# ==12345==    at 0x4848899: malloc (vg_replace_malloc.c:381)
# ==12345==    by 0x1091C2: memory_leak (mem_bugs.c:15)
```

**ASan 与 Valgrind 对比**：

| 特性 | AddressSanitizer | Valgrind |
|------|------------------|----------|
| 启用方式 | 编译时 `-fsanitize=address` | 运行时 `valgrind ./prog` |
| 性能开销 | ~2x 慢 | ~10-50x 慢 |
| 内存开销 | ~3x | 较大 |
| 栈溢出检测 | 支持 | 不支持 |
| 堆溢出检测 | 支持 | 支持 |
| 内存泄漏 | 支持 | 支持（更详细） |
| 多线程 | 支持 | 支持 |
| 无需重编译 | 否 | 是 |

**实际项目中的推荐用法**：

```bash
# 开发/测试阶段：启用 ASan + UBSan
CFLAGS = -fsanitize=address,undefined -g -O1 -fno-omit-frame-pointer

# CI/CD 阶段：定期用 Valgrind 做全面检查
valgrind --leak-check=full --error-exitcode=1 ./tests

# 生产阶段：不启用任何检测（性能优先）
CFLAGS = -O2
```

**其他 Sanitizer**：

```bash
# ThreadSanitizer：检测数据竞争（多线程）
gcc -fsanitize=thread -g -O1 thread_bugs.c -o thread_tsan

# MemorySanitizer：检测未初始化内存读取
gcc -fsanitize=memory -g -O1 uninit_bugs.c -o mem_msan

# LeakSanitizer：单独的泄漏检测（ASan 已包含）
gcc -fsanitize=leak -g leak_bugs.c -o leak_lsan
```

### 总结

- ASan（`-fsanitize=address`）检测越界、释放后使用、双重释放、泄漏，性能开销小
- UBSan（`-fsanitize=undefined`）检测未定义行为（溢出、除零等）
- Valgrind 无需重编译，检测最全面，但性能开销大
- ASan 适合开发阶段频繁使用，Valgrind 适合定期全面检查
- ASan 能检测栈溢出，Valgrind 不能
- 生产环境不启用检测，开发/测试阶段启用
- 多线程用 ThreadSanitizer（`-fsanitize=thread`）

## 第 28 讲 编译时间优化

### 概念

大型 C/C++ 项目编译时间可能长达数十分钟甚至数小时，严重影响开发效率。编译时间优化通过减少重复编译、并行构建、预编译头、分布式编译等手段加速构建。GCC 提供了多种选项和技巧来优化编译速度。

### 原理

影响编译时间的因素：

1. **头文件包含**：每个 `#include` 都会展开，重复包含同一头文件浪费大量时间
2. **模板实例化**（C++）：模板代码在每次使用时实例化，非常耗时
3. **优化级别**：`-O2`/`-O3` 比 `-O0` 慢很多
4. **单线程编译**：默认 `make` 串行编译，不利用多核
5. **全量重编译**：修改头文件导致所有依赖文件重编译

优化策略：
- **并行编译**：`make -jN` 利用多核
- **预编译头（PCH）**：将常用头文件预编译，减少重复处理
- **Unity Build**：将多个 `.cpp` 合并为一个，减少重复包含
- **ccache**：缓存编译结果，未修改的文件直接复用
- **distcc**：分布式编译，利用多台机器
- **模块（C++20）**：替代 `#include`，从根本上解决重复包含

### 例子

**1. 并行编译**：

```bash
# 使用所有 CPU 核心
make -j$(nproc)

# 指定核心数
make -j8

# CMake 并行构建
cmake --build . -j8
# 或
make -j8
```

**2. 预编译头（Precompiled Header）**：


```bash
make -j8  # 配合 time 命令

```

- `-ftime-report` 分析编译时间瓶颈
- C++20 模块是未来的方向，从根本上解决头文件重复包含
- 开发用 `-O0`，发布用 `-O2`，平衡速度和质量

## 第 29 讲 交叉编译

### 概念

交叉编译（Cross Compilation）是在一个平台上编译生成另一个平台可运行的程序的过程。例如在 x86 Linux 上编译 ARM 平台的程序。交叉编译广泛应用于嵌入式开发、Android NDK 开发、树莓派开发等场景。GCC 通过指定不同的目标三元组（target triplet）和交叉工具链来实现交叉编译。

### 原理

**目标三元组（Target Triplet）**：

格式为 `架构-厂商-操作系统`，有时还有第四部分（ABI/库）：
- `x86_64-linux-gnu`：x86_64 架构，Linux，GNU libc
- `arm-linux-gnueabihf`：ARM 架构，Linux，硬浮点 ABI
- `aarch64-linux-gnu`：ARM64 架构，Linux
- `arm-none-eabi`：ARM 架构，无操作系统（裸机），嵌入式 ABI

**交叉工具链命名**：

交叉编译器的命名遵循 `目标三元组-gcc` 的格式：
- `arm-linux-gnueabihf-gcc`：ARM Linux 交叉编译器
- `aarch64-linux-gnu-gcc`：ARM64 Linux 交叉编译器
- `arm-none-eabi-gcc`：ARM 裸机交叉编译器

**交叉编译的核心挑战**：

1. **头文件和库**：目标平台的头文件和库不在本机默认路径，需用 `--sysroot` 指定
2. **链接器**：需要目标平台的链接器，而非本机链接器
3. **运行时**：编译出的程序不能在本机运行，需在目标平台或模拟器（如 QEMU）上运行

### 例子

**1. 安装交叉工具链**：

```bash
# Ubuntu/Debian 安装 ARM 交叉编译器
sudo apt install gcc-arm-linux-gnueabihf    # ARM 32位
sudo apt install gcc-aarch64-linux-gnu      # ARM 64位

# 验证安装
arm-linux-gnueabihf-gcc --version
aarch64-linux-gnu-gcc --version
```

**2. 基本交叉编译**：

```c
// hello.c - 目标平台为 ARM Linux
#include <stdio.h>
int main() {
    printf("Hello from ARM!\n");
    printf("Size of int: %zu\n", sizeof(int));
    printf("Size of pointer: %zu\n", sizeof(void*));
    return 0;
}
```

```bash
# 本机编译（x86_64）
gcc hello.c -o hello_x86
file hello_x86
# ELF 64-bit LSB executable, x86-64

# 交叉编译（ARM 32位）
arm-linux-gnueabihf-gcc hello.c -o hello_arm
file hello_arm
# ELF 32-bit LSB executable, ARM, EABI5, hard-float

# 交叉编译（ARM 64位）
aarch64-linux-gnu-gcc hello.c -o hello_arm64
file hello_arm64
# ELF 64-bit LSB executable, ARM aarch64
```

**3. 运行交叉编译的程序**：

```bash
# 直接运行会报错
./hello_arm
# bash: ./hello_arm: cannot execute binary file: Exec format error

# 用 QEMU 模拟器运行
sudo apt install qemu-user
qemu-arm ./hello_arm
# 输出: Hello from ARM!
#       Size of int: 4
#       Size of pointer: 4
```

**4. 指定 sysroot（目标平台系统库）**：

```bash
# sysroot 包含目标平台的 /usr/lib、/usr/include 等
arm-linux-gnueabihf-gcc --sysroot=/path/to/arm-rootfs hello.c -o hello_arm

# 指定头文件和库路径
arm-linux-gnueabihf-gcc \
    -I/path/to/arm-rootfs/usr/include \
    -L/path/to/arm-rootfs/usr/lib \
    hello.c -o hello_arm
```

**5. 交叉编译静态程序**：

```bash
# 静态链接，避免目标平台缺少库
arm-linux-gnueabihf-gcc -static hello.c -o hello_arm_static
file hello_arm_static
# ELF 32-bit LSB executable, ARM, statically linked
```

**6. 树莓派交叉编译**：

```bash
# 安装树莓派工具链
git clone https://github.com/raspberrypi/tools.git ~/rpi-tools

# 设置环境变量
export PATH=$HOME/rpi-tools/arm-bcm2708/gcc-linaro-arm-linux-gnueabihf-raspbian-x64/bin:$PATH

# 交叉编译
arm-linux-gnueabihf-gcc hello.c -o hello_pi

# 复制到树莓派运行
scp hello_pi pi@raspberrypi:~/
ssh pi@raspberrypi ./hello_pi
```

**7. Android NDK 交叉编译**：

```bash
# 使用 NDK 的 clang（GCC 已弃用，但原理相同）
export NDK_ROOT=/path/to/android-ndk
export TOOLCHAIN=$NDK_ROOT/toolchains/llvm/prebuilt/linux-x86_64

# 编译 ARM64 版本
$TOOLCHAIN/bin/aarch64-linux-android24-clang hello.c -o hello_android

# 编译 ARM32 版本
$TOOLCHAIN/bin/armv7a-linux-androideabi24-clang hello.c -o hello_android_arm
```

**8. CMake 交叉编译**：

创建工具链文件 `arm-toolchain.cmake`：

```cmake
# arm-toolchain.cmake
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR arm)

set(CMAKE_C_COMPILER arm-linux-gnueabihf-gcc)
set(CMAKE_CXX_COMPILER arm-linux-gnueabihf-g++)

set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
```

```bash
# 使用工具链文件
mkdir build-arm && cd build-arm
cmake -DCMAKE_TOOLCHAIN_FILE=../arm-toolchain.cmake ..
make
```

**9. 验证交叉编译结果**：

```bash
# 查看文件架构
file hello_arm

# 查看依赖的库（需要目标平台的库）
arm-linux-gnueabihf-readelf -d hello_arm | grep NEEDED

# 查看架构信息
arm-linux-gnueabihf-readelf -h hello_arm | grep -E "Machine|Class"
```

### 总结

- 交叉编译是在一个平台生成另一个平台程序的过程
- 工具链命名：`目标三元组-gcc`（如 `arm-linux-gnueabihf-gcc`）
- 常见目标：ARM（嵌入式）、ARM64（服务器/手机）、RISC-V（新兴）
- 编译出的程序不能在本机运行，需用 QEMU 模拟或目标平台运行
- `--sysroot` 指定目标平台的系统头文件和库
- CMake 用 `CMAKE_TOOLCHAIN_FILE` 指定交叉编译工具链
- 静态链接（`-static`）可避免目标平台库依赖问题

## 第 30 讲 常见错误排查与最佳实践

### 概念

本讲总结 GCC/G++ 使用中最常见的编译/链接错误及其排查方法，并给出生产环境编译选项的最佳实践建议。掌握错误排查技巧和最佳实践，能显著提升开发效率和代码质量。

### 原理

GCC 错误分为几大类：

1. **预处理错误**：头文件找不到、宏定义问题
2. **编译错误**：语法错误、类型错误、未声明标识符
3. **链接错误**：未定义引用、重复定义、库找不到
4. **运行时错误**：段错误、内存泄漏（需配合 GDB/Sanitizer）

排查错误的关键是**仔细阅读错误信息**，GCC 的错误信息通常包含文件名、行号和具体原因。从第一个错误开始排查，因为后续错误可能是第一个错误的连锁反应。

### 例子

**1. 头文件找不到**：

```bash
gcc main.c -o main
# 错误: fatal error: myheader.h: No such file or directory

# 排查: 确认头文件位置，用 -I 指定
gcc -I./include main.c -o main
```

**2. 未声明标识符**：

```c
// forgot_declare.c
int main() {
    printf("Hello\n");  // 忘记 #include <stdio.h>
    return 0;
}
```

```bash
gcc forgot_declare.c -o test
# 警告: implicit declaration of function 'printf'
# 链接时可能成功（libc 默认链接），但应修复

# 修复: 添加 #include <stdio.h>
```

**3. 未定义引用（链接错误）**：

```bash
gcc main.c -o main
# 错误: undefined reference to `sqrt'

# 排查: sqrt 在数学库 libm 中，需要 -lm
gcc main.c -o main -lm

# 链接顺序问题: -lm 必须在 main.c 之后
gcc -lm main.c -o main  # 可能仍然报错
gcc main.c -lm -o main  # 正确
```

**4. 重复定义**：

```c
// a.c
int global_var = 10;

// b.c
int global_var = 20;  // 重复定义
```

```bash
gcc a.c b.c -o app
# 错误: multiple definition of `global_var'

# 修复方案1: 只在一个文件定义，其他文件用 extern
// a.c: int global_var = 10;
// b.c: extern int global_var;

# 修复方案2: 用头文件 + 定义分离
// global.h: extern int global_var;
// global.c: int global_var = 10;
```

**5. 找不到库文件**：

```bash
gcc main.c -L./lib -lmylib -o main
# 错误: cannot find -lmylib

# 排查: 检查库文件是否存在
ls ./lib/libmylib.so ./lib/libmylib.a

# 检查库搜索路径
gcc -print-search-dirs | grep libraries
```

**6. 运行时找不到动态库**：

```bash
./main
# 错误: error while loading shared libraries: libmylib.so:
#       cannot open shared object file: No such file or directory

# 解决方案1: 设置 LD_LIBRARY_PATH
export LD_LIBRARY_PATH=./lib:$LD_LIBRARY_PATH

# 解决方案2: 编译时用 -rpath
gcc main.c -L./lib -lmylib -Wl,-rpath,./lib -o main

# 解决方案3: 安装到系统目录
sudo cp libmylib.so /usr/local/lib/
sudo ldconfig
```

**7. C++ 链接 C 库的名称修饰问题**：

```cpp
// cpp_call_c.cpp
#include <cstdio>
extern "C" {
    #include "c_library.h"  // C 语言写的头文件
}
int main() {
    c_function();  // 调用 C 函数
    return 0;
}
```

```bash
# 如果不加 extern "C"，C++ 会修改函数名，导致链接失败
g++ cpp_call_c.cpp c_library.o -o app
# 错误: undefined reference to `c_function()'

# 修复: 在 C++ 中用 extern "C" 包裹 C 头文件
```

**8. 编译选项最佳实践**：

```bash
# ===== 开发阶段（调试友好）=====
CFLAGS_DEV = -std=c11 -Wall -Wextra -g -O0 -fno-omit-frame-pointer
CXXFLAGS_DEV = -std=c++17 -Wall -Wextra -g -O0 -fno-omit-frame-pointer

# ===== 测试阶段（启用 Sanitizer）=====
CFLAGS_TEST = -std=c11 -Wall -Wextra -g -O1 \
              -fsanitize=address,undefined -fno-omit-frame-pointer

# ===== 发布阶段（性能优先）=====
CFLAGS_RELEASE = -std=c11 -Wall -Wextra -Werror -O2 -DNDEBUG
CXXFLAGS_RELEASE = -std=c++17 -Wall -Wextra -Werror -O2 -DNDEBUG

# ===== 嵌入式/体积敏感 =====
CFLAGS_EMBEDDED = -std=c11 -Wall -Wextra -Os -ffunction-sections -fdata-sections
LDFLAGS_EMBEDDED = -Wl,--gc-sections  # 链接时删除未使用的段
```

**9. 完整的 Makefile 最佳实践**：

```makefile
# 通用 Makefile 模板
CC = gcc
CXX = g++

# 根据构建类型选择选项
BUILD_TYPE ?= debug

ifeq ($(BUILD_TYPE), debug)
    CFLAGS = -std=c11 -Wall -Wextra -g -O0 -DDEBUG
else ifeq ($(BUILD_TYPE), release)
    CFLAGS = -std=c11 -Wall -Wextra -Werror -O2 -DNDEBUG
else ifeq ($(BUILD_TYPE), test)
    CFLAGS = -std=c11 -Wall -Wextra -g -O1 -fsanitize=address,undefined
endif

CXXFLAGS = $(CFLAGS:-std=c11=-std=c++17)

TARGET = app
SRCS = $(wildcard src/*.c) $(wildcard src/*.cpp)
OBJS = $(SRCS:.c=.o)
OBJS := $(OBJS:.cpp=.o)
DEPS = $(OBJS:.o=.d)

# 默认目标
all: $(TARGET)

# 链接
$(TARGET): $(OBJS)
        $(CC) $(CFLAGS) $^ -o $@ $(LDFLAGS)

# 编译 C
%.o: %.c
        $(CC) $(CFLAGS) -c $< -o $@

# 编译 C++
%.o: %.cpp
        $(CXX) $(CXXFLAGS) -c $< -o $@

# 依赖关系
-include $(DEPS)

# 清理
clean:
        rm -f $(OBJS) $(DEPS) $(TARGET)

# 安装
install: $(TARGET)
        install -D $(TARGET) $(DESTDIR)/usr/local/bin/$(TARGET)

.PHONY: all clean install
```

**10. 常用排查工具汇总**：

```bash
# 查看文件类型和架构
file program

# 查看动态库依赖
ldd program

# 查看符号表
nm program
nm -D libxxx.so  # 动态符号

# 反汇编
objdump -d program

# 查看 ELF 信息
readelf -h program  # 头信息
readelf -d program  # 动态段
readelf -S program  # 段信息

# 查看/修改 RPATH
readelf -d program | grep rpath
patchelf --set-rpath /new/path program

# 查看预定义宏
gcc -dM -E -x c /dev/null

# 查看头文件搜索路径
gcc -E -Wp,-v -x c /dev/null

# 查看库搜索路径
gcc -print-search-dirs
```

### 总结

**常见错误排查**：
- 头文件找不到 → 用 `-I` 指定路径
- 未定义引用 → 检查库链接（`-l`）和链接顺序
- 重复定义 → 用 `extern` 或头文件分离声明与定义
- 运行时找不到库 → 用 `-rpath` 或 `LD_LIBRARY_PATH`
- C++ 调用 C 库 → 用 `extern "C"` 避免名称修饰问题

**最佳实践**：
- 开发用 `-g -O0 -Wall -Wextra`，便于调试
- 测试用 `-fsanitize=address,undefined`，检测内存问题
- 发布用 `-O2 -Werror -DNDEBUG`，保证性能和质量
- 嵌入式用 `-Os -ffunction-sections -fdata-sections` + `-Wl,--gc-sections`
- 始终显式指定 `-std` 标准，不依赖默认值
- 用 Makefile/CMake 管理不同构建类型的选项

**排查工具**：`file`、`ldd`、`nm`、`objdump`、`readelf`、`patchelf`
