## 第一章 Redis 入门基础

### 第 1 讲：Redis 简介与安装配置

#### 概念

Redis（Remote Dictionary Server）是一个开源的、基于内存的、键值对（Key-Value）型 NoSQL 数据库。它由 Salvatore Sanfilippo（网名 antirez）于 2009 年使用 ANSI C 语言开发，目前由 Redis Labs 维护。与传统关系型数据库不同，Redis 将所有数据存储在内存中，因此具有极高的读写性能，单机 QPS 可达 10 万以上。Redis 不仅仅是一个简单的缓存，它还支持多种数据结构、持久化、事务、发布订阅、Lua 脚本等丰富特性，使其既能作为缓存层，也能作为数据库、消息队列、计数器等多种角色使用。

#### 原理

Redis 之所以能够实现极高的性能，主要得益于以下几个设计决策。第一，**纯内存操作**：Redis 的所有数据都驻留在内存中，避免了磁盘 I/O 的瓶颈，内存的随机读写速度比磁盘快几个数量级。第二，**单线程模型**：Redis 的核心命令处理采用单线程（Redis 6.0 后引入多线程仅用于网络 I/O，命令执行仍是单线程），避免了多线程切换和锁竞争的开销，同时也保证了命令的原子性。第三，**I/O 多路复用**：Redis 使用 epoll/kqueue 等多路复用技术，单个线程可以同时处理数千个客户端连接，极大提升了并发能力。第四，**高效的数据结构**：Redis 内部针对不同数据类型使用了 SDS（简单动态字符串）、ziplist、quicklist、skiplist 等精心设计的数据结构，在内存占用和操作效率之间取得了良好平衡。

#### 例子

**Linux 环境下安装 Redis：**

```bash
# 方式一：源码编译安装（推荐生产环境）
wget https://download.redis.io/releases/redis-7.2.4.tar.gz
tar xzf redis-7.2.4.tar.gz
cd redis-7.2.4
make && make install PREFIX=/usr/local/redis

# 启动 Redis 服务（前台）
/usr/local/redis/bin/redis-server

# 后台启动（指定配置文件）
cp redis.conf /usr/local/redis/
/usr/local/redis/bin/redis-server /usr/local/redis/redis.conf

# 方式二：使用 Docker 快速启动（推荐学习环境）
docker run -d --name my-redis -p 6379:6379 redis:7.2

# 连接 Redis
redis-cli -h 127.0.0.1 -p 6379

# 测试连接
127.0.0.1:6379> PING
PONG

# 设置和获取键值
127.0.0.1:6379> SET name "Redis"
OK
127.0.0.1:6379> GET name
"Redis"
```

**核心配置文件 `redis.conf` 关键项：**

```conf
bind 127.0.0.1              # 绑定的 IP 地址
port 6379                   # 监听端口
requirepass yourpassword    # 设置访问密码
maxmemory 1gb               # 最大内存限制
maxmemory-policy allkeys-lru  # 内存淘汰策略
appendonly yes              # 开启 AOF 持久化
save 900 1                  # RDB 持久化策略：900秒内至少1个key变化
```

#### 总结

- Redis 是基于内存的高性能键值数据库，单机 QPS 可达 10 万+
- 高性能源于：纯内存、单线程命令处理、I/O 多路复用、高效数据结构
- 生产环境推荐源码编译安装，学习环境可用 Docker 快速启动
- **注意事项**：生产环境务必设置密码、限制内存上限、配置持久化；不要将 Redis 直接暴露在公网

### 第 2 讲：数据模型与通用命令

#### 概念

Redis 采用 **Key-Value** 数据模型，其中 Key 始终是字符串类型，而 Value 可以是字符串、列表、哈希、集合、有序集合等多种数据类型。这种设计使得 Redis 既保持了键值数据库的简洁性，又具备了丰富的数据表达能力。Redis 中的所有数据都存储在一个全局的字典（dict）中，每个数据库（默认有 16 个，编号 0-15）都是独立的字典。除了针对特定数据类型的命令外，Redis 还提供了一组**通用命令**，可以作用于任何类型的键，用于键的管理、过期设置、数据库切换等操作。

#### 原理

Redis 的键空间本质上是一个哈希表（dict 结构），所有键都存储在这个哈希表中。当执行 `SET key value` 时，Redis 会在 dict 中插入或更新一个条目，键是 SDS 字符串，值是一个 `redisObject` 结构体，该结构体记录了值的类型（type）、编码方式（encoding）、引用计数（refcount）和指向实际数据的指针（ptr）。Redis 通过 `redisObject` 实现了多态——同一个命令（如 `DEL`）可以作用于任何类型的键，因为命令处理器会先检查 `redisObject.type`，再分派到对应的实现。键的过期信息存储在另一个独立的 `expires` 字典中，键指向同一个 SDS 对象，值是过期时间戳（毫秒），这种分离设计使得过期检查不会影响主字典的性能。

#### 例子

**通用键管理命令：**

```bash
# 基本操作
127.0.0.1:6379> SET user:1 "Alice"
OK
127.0.0.1:6379> EXISTS user:1          # 判断键是否存在，返回 1 存在，0 不存在
(integer) 1
127.0.0.1:6379> TYPE user:1            # 查看键的数据类型
string
127.0.0.1:6379> KEYS user:*            # 模糊匹配键（生产环境慎用！）
1) "user:1"
127.0.0.1:6379> DEL user:1             # 删除键
(integer) 1

# 过期时间设置
127.0.0.1:6379> SET token "abc123"
OK
127.0.0.1:6379> EXPIRE token 60        # 60秒后过期
(integer) 1
127.0.0.1:6379> TTL token              # 查看剩余生存时间（秒）
(integer) 58
127.0.0.1:6379> PERSIST token          # 移除过期时间，变为永久键
(integer) 1
127.0.0.1:6379> SET session "xyz" EX 30  # 设置时直接指定过期时间
OK

# 数据库切换
127.0.0.1:6379> SELECT 1               # 切换到 1 号数据库
OK
127.0.0.1:6379[1]> DBSIZE              # 查看当前数据库键数量
(integer) 0
127.0.0.1:6379[1]> FLUSHDB             # 清空当前数据库
OK
127.0.0.1:6379> FLUSHALL               # 清空所有数据库（危险！）
OK

# 扫描键（生产环境推荐替代 KEYS）
127.0.0.1:6379> SCAN 0 MATCH user:* COUNT 10
1) "0"
2) 1) "user:1"
   2) "user:2"
```

#### 总结

- Redis 采用 Key-Value 模型，Key 为字符串，Value 支持多种数据类型
- 所有键存储在全局 dict 中，过期信息存储在独立的 expires 字典
- 通用命令包括 `EXISTS`、`TYPE`、`DEL`、`EXPIRE`、`TTL`、`KEYS`、`SCAN` 等
- **关键注意事项**：生产环境**绝对禁止使用 `KEYS *`**，它会阻塞整个 Redis；应使用 `SCAN` 命令增量遍历；`FLUSHALL` 极其危险，建议禁用或重命名

### 第 3 讲：客户端连接与基本使用

#### 概念

Redis 客户端是应用程序与 Redis 服务器交互的桥梁。Redis 采用 **RESP（Redis Serialization Protocol）** 作为通信协议，这是一种简单高效的文本协议，易于解析且可读性好。Redis 7.0 后默认支持 RESP3 协议，提供了更丰富的响应类型。在实际开发中，我们通常使用各语言的高性能客户端库，如 Java 的 Jedis/Lettuce、Python 的 redis-py、Go 的 go-redis 等。这些客户端封装了连接管理、命令构建、响应解析、连接池、哨兵/集群支持等功能，让开发者可以专注于业务逻辑。

#### 原理

Redis 客户端与服务器之间通过 TCP 长连接通信。一个完整的请求-响应周期包括：客户端将命令按 RESP 协议序列化为字节流，通过 TCP 发送给服务器；服务器解析命令、执行操作，将结果按 RESP 序列化后返回。由于 Redis 是单线程处理命令，多个客户端的命令会被串行执行，因此**单个慢命令会阻塞所有客户端**。为了提高性能，客户端通常使用**连接池**复用 TCP 连接，避免频繁建立/断开连接的开销。连接池会维护一组空闲连接，请求时借用，用完归还，并定期检测连接活性。对于 Pipeline（管道）技术，客户端可以将多个命令一次性发送，服务器依次执行后一次性返回所有结果，大幅减少网络往返时间（RTT）。

#### 例子

**Python 客户端（redis-py）基本使用：**

```python
import redis

# 创建连接池
pool = redis.ConnectionPool(
    host='127.0.0.1',
    port=6379,
    password='yourpassword',
    db=0,
    max_connections=20,
    socket_timeout=5,
    socket_connect_timeout=5,
    retry_on_timeout=True
)

# 创建客户端
r = redis.Redis(connection_pool=pool)

# 基本字符串操作
r.set('name', 'Alice', ex=60)  # ex=60 表示60秒过期
print(r.get('name'))  # b'Alice'

# 哈希操作
r.hset('user:1001', mapping={'name': 'Bob', 'age': 25, 'city': 'Beijing'})
print(r.hgetall('user:1001'))
# {b'name': b'Bob', b'age': b'25', b'city': b'Beijing'}

# 列表操作
r.lpush('queue:tasks', 'task1', 'task2', 'task3')
print(r.rpop('queue:tasks'))  # b'task1' (FIFO 队列)

# Pipeline 批量操作
pipe = r.pipeline()
for i in range(100):
    pipe.set(f'key:{i}', i)
pipe.execute()  # 一次性发送100条命令

# 事务
pipe = r.pipeline(transaction=True)
pipe.multi()
pipe.set('account:A', 100)
pipe.set('account:B', 200)
pipe.execute()
```

**Java 客户端（Lettuce）示例：**

```java
import io.lettuce.core.*;

public class RedisDemo {
    public static void main(String[] args) {
        // 创建客户端（Lettuce 是 Spring Boot 默认客户端，线程安全）
        RedisClient client = RedisClient.create("redis://password@127.0.0.1:6379/0");
        StatefulRedisConnection<String, String> connection = client.connect();
        RedisCommands<String, String> commands = connection.sync();

        // 基本操作
        commands.set("name", "Alice");
        String value = commands.get("name");
        System.out.println(value);  // Alice

        // 设置带过期时间的键
        commands.setex("token", 60, "abc123");

        connection.close();
        client.shutdown();
    }
}
```

#### 总结

- Redis 使用 RESP 协议进行客户端-服务器通信，基于 TCP 长连接
- 推荐使用连接池复用连接，避免频繁建连开销
- 各语言有成熟的客户端库：Python 的 redis-py、Java 的 Jedis/Lettuce、Go 的 go-redis
- Pipeline 可大幅减少网络往返，适合批量操作
- **注意事项**：务必设置 `socket_timeout` 防止请求卡死；生产环境必须配置密码和连接池上限；Lettuce 是线程安全的，Jedis 非线程安全需配合连接池使用

## 第二章 核心数据类型

### 第 4 讲：String 字符串类型

#### 概念

String 是 Redis 最基础、最常用的数据类型。虽然名为"字符串"，但它不仅能存储文本，还能存储整数、浮点数、二进制数据（如图片、序列化对象），单个 String 值的最大容量为 **512MB**。String 类型是二进制安全的，意味着可以存储任何二进制数据，包括包含 `\0` 的数据。在实际应用中，String 类型广泛用于缓存对象、计数器、分布式锁、限流器、Session 存储等场景，是 Redis 中使用频率最高的数据类型。

#### 原理

Redis 的 String 类型底层使用 **SDS（Simple Dynamic String，简单动态字符串）** 实现，而非 C 语言传统的以 `\0` 结尾的字符数组。SDS 相比 C 字符串有以下优势：第一，**O(1) 获取长度**——SDS 在头部记录了 `len` 字段，获取长度无需遍历；第二，**二进制安全**——SDS 使用 `len` 判断字符串结束，而非 `\0`，因此可以存储任意二进制数据；第三，**杜绝缓冲区溢出**——SDS 在修改前会检查空间是否足够，不足则自动扩容；第四，**预分配与惰性释放**——扩容时不仅分配所需空间，还会额外分配未使用空间，减少内存重分配次数。SDS 根据字符串长度分为 sdshdr5、sdshdr8、sdshdr16、sdshdr32、sdshdr64 五种子类型，使用更小的字段存储短字符串，节省内存。当存储的是整数时，Redis 会直接将 `redisObject` 的 ptr 指向该整数（embstr/raw 编码），避免 SDS 开销。

#### 例子

```bash
# 基本设置与获取
127.0.0.1:6379> SET greeting "Hello Redis"
OK
127.0.0.1:6379> GET greeting
"Hello Redis"
127.0.0.1:6379> STRLEN greeting           # 获取字符串长度
(integer) 11

# 数值操作（计数器场景）
127.0.0.1:6379> SET counter 100
OK
127.0.0.1:6379> INCR counter              # 自增1
(integer) 101
127.0.0.1:6379> INCRBY counter 10         # 自增指定值
(integer) 111
127.0.0.1:6379> DECR counter              # 自减1
(integer) 110
127.0.0.1:6379> INCRBYFLOAT price 12.5    # 浮点数自增
"12.5"

# 过期设置（原子操作）
127.0.0.1:6379> SET token "abc" EX 60 NX  # NX: 不存在时才设置
OK
127.0.0.1:6379> SET token "xyz" EX 60 XX  # XX: 存在时才设置
(nil)

# 批量操作
127.0.0.1:6379> MSET k1 v1 k2 v2 k3 v3
OK
127.0.0.1:6379> MGET k1 k2 k3
1) "v1"
2) "v2"
3) "v3"

# 追加与范围
127.0.0.1:6379> APPEND greeting " World"
(integer) 17
127.0.0.1:6379> GETRANGE greeting 0 4
"Hello"
127.0.0.1:6379> SETRANGE greeting 6 "Redis"
(integer) 17
```

**实际应用：分布式锁**

```python
import redis
import uuid
import time

r = redis.Redis()

def acquire_lock(lock_name, acquire_timeout=10, lock_timeout=30):
    """获取分布式锁"""
    identifier = str(uuid.uuid4())
    end = time.time() + acquire_timeout
    while time.time() < end:
        # SET key value NX EX seconds 原子操作
        if r.set(lock_name, identifier, nx=True, ex=lock_timeout):
            return identifier
        time.sleep(0.01)
    return None

def release_lock(lock_name, identifier):
    """释放锁（使用 Lua 脚本保证原子性）"""
    script = """
    if redis.call('get', KEYS[1]) == ARGV[1] then
        return redis.call('del', KEYS[1])
    else
        return 0
    end
    """
    return r.eval(script, 1, lock_name, identifier)

# 使用示例
lock_id = acquire_lock('order:lock:1001')
if lock_id:
    try:
        # 执行业务逻辑
        process_order()
    finally:
        release_lock('order:lock:1001', lock_id)
```

#### 总结

- String 是 Redis 最基础类型，最大 512MB，二进制安全
- 底层使用 SDS 实现，支持 O(1) 取长度、二进制安全、自动扩容
- `INCR`/`DECR` 是原子操作，非常适合实现计数器、限流器
- `SET key value NX EX` 是实现分布式锁的经典模式
- **注意事项**：避免存储过大的 String（接近 512MB），会阻塞 Redis；存储对象时优先考虑 Hash 类型而非序列化的 String，便于部分更新

### 第 5 讲：List 列表类型

#### 概念

List 是 Redis 的有序字符串列表，按照插入顺序排序，元素可以重复。一个 List 最多可存储 **2^32 - 1**（约 42 亿）个元素。List 支持在两端推入（push）和弹出（pop）元素，也支持按索引访问、范围查询、修剪等操作。由于两端操作都是 O(1) 时间复杂度，List 非常适合实现队列、栈、最新消息列表、消息流水等场景。Redis 5.0 后，List 底层由 quicklist（双向链表 + ziplist 的混合结构）实现，兼顾了内存效率和操作性能。

#### 原理

Redis List 在不同长度和元素大小下使用不同的编码方式。当列表元素较少（默认 128 个）且每个元素较小（默认 64 字节）时，使用 **ziplist（压缩列表）** 编码——这是一种紧凑的连续内存结构，所有元素紧密排列，节省了指针开销，但插入/删除需要移动数据。当超过阈值时，转换为 **quicklist** 编码——本质是一个双向链表，但每个节点是一个 ziplist，既保留了链表的快速增删特性，又通过 ziplist 减少了内存碎片。两端 push/pop 操作直接作用于链表头尾节点，时间复杂度 O(1)。`LRANGE` 需要遍历链表节点，时间复杂度 O(N)。值得注意的是，Redis List 是双向的，可以从左（头）或右（尾）操作，因此既能实现 FIFO 队列（lpush + rpop），也能实现 LIFO 栈（lpush + lpop）。

#### 例子

```bash
# 基本操作
127.0.0.1:6379> LPUSH fruits apple banana cherry   # 左侧插入（头插）
(integer) 3
127.0.0.1:6379> RPUSH fruits date                  # 右侧插入（尾插）
(integer) 4
```

```python
import redis
import json
import time

r = redis.Redis()

def producer(queue_name, message):
    """生产者：将消息推入队列"""
    r.lpush(queue_name, json.dumps(message))
    print(f"Produced: {message}")

def consumer(queue_name, processing_queue, handler):
    """消费者：从队列取出消息，处理后从处理队列删除"""
    while True:
        # 阻塞式将消息从主队列移到处理队列
        item = r.brpoplpush(queue_name, processing_queue, timeout=30)
        if item is None:
            continue
        try:
            message = json.loads(item)
            handler(message)
            # 处理成功，从处理队列删除
            r.lrem(processing_queue, 1, item)
        except Exception as e:
            print(f"Error: {e}")
            # 处理失败，消息留在处理队列，可由其他消费者重试

# 使用示例
producer('order:queue', {'order_id': 'A001', 'amount': 99.9})
```

- List 是有序字符串列表，支持两端 O(1) 的 push/pop
- 底层使用 ziplist（小列表）或 quicklist（大列表）编码
- `LPUSH + RPOP` 实现 FIFO 队列，`LPUSH + LPOP` 实现 LIFO 栈
- `BLPOP`/`BRPOP` 阻塞式弹出，可实现简单的消息队列
- **注意事项**：List 不支持中间高效插入；如需按 score 排序请用 Sorted Set；`LRANGE 0 -1` 在大列表上很慢，避免频繁全量查询

### 第 6 讲：Hash 哈希类型

#### 概念

Hash 是 Redis 的键值对集合，类似于编程语言中的 Map/Dictionary/Dict。一个 Hash 类型的键对应一个包含多个字段-值（field-value）对的哈希表，每个 Hash 最多可存储 **2^32 - 1** 个字段。Hash 非常适合存储对象——例如用户信息（name、age、email）、商品信息（title、price、stock）等。相比于将对象序列化为 String 存储，Hash 允许独立读写单个字段，避免了序列化/反序列化开销，也节省了内存（短 Hash 使用 ziplist 编码非常紧凑）。

#### 原理

Redis Hash 在不同规模下使用两种编码。当字段数量较少（默认 128 个）且每个值较小（默认 64 字节）时，使用 **ziplist** 编码——所有 field-value 对紧密存储在连续内存中，遍历查找是 O(N)，但由于 N 很小，实际性能依然很好，且内存占用极低。当超过阈值时，转换为 **hashtable** 编码——标准的哈希表实现，查找、插入、删除都是 O(1) 平均时间复杂度。Redis 的 hashtable 采用链地址法解决冲突，并在负载因子过高时自动 rehash 扩容。值得一提的是，Redis 的 rehash 是**渐进式**的——扩容时不会一次性迁移所有数据，而是将迁移分散到后续的每次操作中，避免了一次性 rehash 导致的服务阻塞。

#### 例子

```bash

127.0.0.1:6379> HGET user:1001 name
```

```python
        """移除商品"""
        r.hdel(self.key, product_id)

    def update_quantity(self, product_id, quantity):
        """更新数量"""

        else:

        """获取商品总数量"""
        items = r.hgetall(self.key)
        return sum(int(v) for v in items.values())

    def clear(self):
        """清空购物车"""
        r.delete(self.key)
```

### 第 7 讲：Set 集合类型

#### 概念

Set 是 Redis 的无序字符串集合，集合中的元素唯一不重复，最多可存储 **2^32 - 1** 个元素。Set 支持添加、删除、判断成员存在等操作，时间复杂度均为 O(1)。更重要的是，Set 支持丰富的集合运算：交集（SINTER）、并集（SUNION）、差集（SDIFF），这使得 Set 在社交关系（共同好友）、标签系统、去重统计、抽奖等场景中非常有用。Redis 7.4 后还引入了 `SINTERCARD` 命令，可以限制交集结果数量，提升性能。

#### 原理

Redis Set 根据元素类型和数量使用两种编码。当所有元素都是整数且数量不超过 512 个（默认配置）时，使用 **intset（整数集合）** 编码——这是一种紧凑的有序数组，根据最大元素自动选择 int16/int32/int64 编码，内存占用极小，查找使用二分搜索 O(log N)。当元素包含非整数或数量超过阈值时，转换为 **hashtable** 编码，此时 value 为 NULL 的哈希表，查找、插入、删除均为 O(1)。集合运算的复杂度取决于参与运算的集合大小：`SINTER` 是 O(N*M)（N 是最小集合大小，M 是集合数量），`SUNION` 和 `SDIFF` 是 O(N)（N 是所有集合元素总数）。因此在大集合上执行集合运算要谨慎，可使用 `SINTERSTORE` 将结果存入新键，或使用 `SINTERCARD` 限制结果数量。

#### 例子

```python
import redis

r = redis.Redis()

class SocialService:
    @staticmethod
    def add_friend(user_id, friend_id):
        r.sadd(f"friends:{user_id}", friend_id)

    @staticmethod
    def common_friends(user_a, user_b):
        """获取共同好友"""
        return r.sinter(f"friends:{user_a}", f"friends:{user_b}")

    @staticmethod
    def recommend_friends(user_id):
        """推荐好友：好友的好友 - 自己的好友 - 自己"""
        friends = r.smembers(f"friends:{user_id}")
        candidates = set()
        for friend in friends:
            candidates.update(r.smembers(f"friends:{friend}"))
        # 排除已经是好友和自己
        candidates -= friends
        candidates.discard(user_id.encode())
        return candidates

# 使用示例
service = SocialService()
service.add_friend("A", "B")
service.add_friend("A", "C")
service.add_friend("B", "C")
service.add_friend("B", "D")
print(service.common_friends("A", "B"))  # {b'C'}
print(service.recommend_friends("A"))    # {b'D'}（B的好友D，A还不认识）
```

- 支持交集、并集、差集运算，适合社交关系、标签、去重场景
- `SPOP`/`SRANDMEMBER` 适合抽奖、随机推荐
- **注意事项**：大集合的 `SMEMBERS` 和集合运算会阻塞 Redis，应使用 `SSCAN` 或 `SINTERCARD` 限制结果；集合运算结果很大时考虑异步执行

### 第 8 讲：Sorted Set 有序集合

#### 概念

Sorted Set（简称 ZSet）是 Redis 最强大、最独特的数据类型。它在 Set 的基础上，为每个元素关联一个 **score（分数）**，元素按 score 从小到大排序。ZSet 中的元素依然唯一，但 score 可以重复。ZSet 支持按 score 范围查询、按排名查询、排名获取等丰富操作，使其成为排行榜、延时队列、带权重的消息队列、时间序列数据等场景的首选。一个 ZSet 最多可存储 2^32 - 1 个元素。

#### 原理

ZSet 底层使用 **skiplist（跳跃表）+ hashtable** 的组合编码（当元素较多或较大时），或 **ziplist** 编码（当元素少且小时）。**跳跃表**是一种概率性平衡数据结构，通过多级索引实现 O(log N) 的查找、插入、删除，相比红黑树实现更简单且支持范围查询。Redis 的 skiplist 每个节点包含元素值、score、后退指针（backward，用于反向遍历）和多层前进指针（forward）。**hashtable** 用于 O(1) 查找元素的 score，避免在 skiplist 中查找。两者共享相同的元素对象，不会重复存储。当使用 ziplist 编码时，元素按 score 排序紧密存储，节省内存但查找是 O(N)。`ZRANGEBYSCORE` 利用 skiplist 的范围查询特性，时间复杂度 O(log N + M)（M 是结果数）；`ZRANK` 利用 skiplist 节点记录的 span（跨度）信息，O(log N) 获取排名。

#### 例子

```bash
# 基本操作
```

```python
import redis
import time

r = redis.Redis()

class Leaderboard:
    def __init__(self, name):
        self.key = f"leaderboard:{name}"

    def add_score(self, user_id, score):
        """添加或更新分数"""
        r.zadd(self.key, {user_id: score})

    def increment_score(self, user_id, delta):
        """增加分数"""
        return r.zincrby(self.key, delta, user_id)

    def get_top_n(self, n=10):
        """获取前N名（降序）"""
        return r.zrevrange(self.key, 0, n - 1, withscores=True)

    def get_user_rank(self, user_id):
        """获取用户排名（降序，从0开始）"""
        return r.zrevrank(self.key, user_id)

    def get_user_score(self, user_id):
        """获取用户分数"""
        return r.zscore(self.key, user_id)

    def get_rank_range(self, start, end):
        """获取指定排名范围"""
        return r.zrevrange(self.key, start, end, withscores=True)

    def get_around_user(self, user_id, count=2):
        """获取用户附近的排名（前后各count名）"""
        rank = r.zrevrank(self.key, user_id)
        if rank is None:
            return []
        start = max(0, rank - count)
        end = rank + count
        return r.zrevrange(self.key, start, end, withscores=True)
```

```python
import redis
import time
import json

r = redis.Redis()

def add_delay_task(task_id, payload, delay_seconds):
    """添加延时任务，score为执行时间戳"""
    execute_at = time.time() + delay_seconds
    r.zadd('delay:queue', {json.dumps({'id': task_id, 'payload': payload}): execute_at})

def consume_delay_tasks(handler):
    """消费到期的延时任务"""
    while True:
        now = time.time()
        # 获取score <= 当前时间的任务
        tasks = r.zrangebyscore('delay:queue', 0, now, start=0, num=1)
        if not tasks:
            time.sleep(0.1)
            continue
        task = tasks[0]
        # 原子性地移除并获取（使用Lua脚本更安全）
        if r.zrem('delay:queue', task):
            handler(json.loads(task))

# 使用示例：30分钟后自动取消未支付订单
add_delay_task('order_001', {'action': 'cancel_order', 'order_id': '001'}, 1800)
```

- **注意事项**：大 ZSet 的 `ZRANGE 0 -1` 会阻塞，应分页查询；`ZUNIONSTORE` 等集合运算复杂度高，避免在大集合上频繁执行

## 第三章 扩展数据结构

### 第 9 讲：Bitmaps 位图

#### 概念

Bitmaps（位图）并不是一种独立的数据类型，而是 String 类型上的一组位操作命令集合。它将 String 值视为一个比特位数组，每个比特位只能为 0 或 1，通过偏移量（offset）定位。Bitmaps 的最大优势在于**极致的内存节省**——记录 1 亿个用户的某个布尔状态（如是否登录），使用 Bitmaps 只需约 12MB 内存，而使用 Set 存储用户 ID 则需要数百 MB。Bitmaps 非常适合统计用户签到、活跃用户数、在线状态、特征标记等场景，是大数据量布尔统计的利器。

#### 原理

Bitmaps 本质上是 String 类型的位操作。Redis 的 String 底层是 SDS，最大 512MB，因此 Bitmaps 最大可表示 2^32（约 42 亿）个比特位。`SETBIT key offset value` 命令会先检查 String 是否存在，不存在则创建空字符串，然后定位到 offset 对应的字节，修改其中的比特位。如果 offset 很大但前面都是 0，Redis 会用 0 填充中间的字节，因此**稀疏 Bitmaps 会浪费内存**——例如只在 offset=1000000000 设置 1，会分配约 125MB 内存。`GETBIT` 是 O(1) 操作，直接计算字节偏移和位掩码。`BITCOUNT` 统计 1 的个数，使用高效的 popcount 算法，时间复杂度 O(N)。`BITOP` 对多个 Bitmaps 执行 AND/OR/XOR/NOT 运算，结果存入目标键。`BITFIELD` 支持更复杂的位域操作，可以在一个命令中读写多个位段，并支持溢出策略（WRAP/SAT/FAIL）。

#### 例子

```bash
# 用户签到场景：每天一个Bitmaps，offset为用户ID
127.0.0.1:6379> SETBIT sign:2024-01-15 1001 1    # 用户1001签到
(integer) 0
127.0.0.1:6379> SETBIT sign:2024-01-15 1002 1    # 用户1002签到
(integer) 0
127.0.0.1:6379> GETBIT sign:2024-01-15 1001      # 查询用户是否签到
(integer) 1
127.0.0.1:6379> BITCOUNT sign:2024-01-15         # 当天签到总人数
(integer) 2

# 统计连续签到天数
127.0.0.1:6379> SETBIT sign:2024-01-14 1001 1
127.0.0.1:6379> SETBIT sign:2024-01-13 1001 1
127.0.0.1:6379> BITCOUNT sign:2024-01-13         # 1月13日签到人数
(integer) 1

# 活跃用户统计：对多天的Bitmaps做OR运算，得到任意一天活跃的用户
127.0.0.1:6379> BITOP OR active:2024-01-13:15 sign:2024-01-13 sign:2024-01-14 sign:2024-01-15
127.0.0.1:6379> BITCOUNT active:2024-01-13:15    # 三天内活跃用户数

# BITFIELD：存储多个字段
# 假设用8位存储用户等级，1位存储是否VIP
127.0.0.1:6379> BITFIELD user:1001 SET u8 0 50 SET u1 8 1
1) (integer) 50
2) (integer) 1
127.0.0.1:6379> BITFIELD user:1001 GET u8 0 GET u1 8
1) (integer) 50
2) (integer) 1

# 查找第一个值为1的位（分页统计场景）
127.0.0.1:6379> BITPOS sign:2024-01-15 1
(integer) 1001
```

**实际应用：用户签到系统**

```python
import redis
from datetime import date, timedelta

r = redis.Redis()

class SignInService:
    @staticmethod
    def sign_in(user_id, sign_date=None):
        """用户签到"""
        if sign_date is None:
            sign_date = date.today()
        key = f"sign:{sign_date.strftime('%Y-%m-%d')}"
        r.setbit(key, user_id, 1)

    @staticmethod
    def has_signed(user_id, sign_date=None):
        """查询用户某天是否签到"""
        if sign_date is None:
            sign_date = date.today()
        key = f"sign:{sign_date.strftime('%Y-%m-%d')}"
        return bool(r.getbit(key, user_id))

    @staticmethod
    def get_sign_count(sign_date=None):
        """获取某天签到总人数"""
        if sign_date is None:
            sign_date = date.today()
        key = f"sign:{sign_date.strftime('%Y-%m-%d')}"
        return r.bitcount(key)

    @staticmethod
    def get_continuous_sign_days(user_id):
        """获取用户连续签到天数（从今天往前数）"""
        today = date.today()
        days = 0
        for i in range(365):  # 最多查一年
            check_date = today - timedelta(days=i)
            if SignInService.has_signed(user_id, check_date):
                days += 1
            else:
                break
        return days

    @staticmethod
    def get_month_active_users(year, month):
        """获取某月活跃用户数（任意一天签到即算活跃）"""
        from calendar import monthrange
        _, days_in_month = monthrange(year, month)
        keys = [f"sign:{year}-{month:02d}-{day:02d}" for day in range(1, days_in_month + 1)]
        result_key = f"active:{year}-{month:02d}"
        r.bitop('OR', result_key, *keys)
        return r.bitcount(result_key)

# 使用示例
service = SignInService()
service.sign_in(1001)
service.sign_in(1002)
print(service.get_sign_count())  # 2
```

#### 总结

- Bitmaps 是 String 的位操作，每个比特位表示一个布尔值，极致省内存
- 1 亿用户状态仅需约 12MB，适合签到、活跃统计、特征标记
- `SETBIT`/`GETBIT` O(1)，`BITCOUNT` O(N)，`BITOP` 支持集合运算
- `BITFIELD` 可在一个 String 中存储多个位段字段
- **注意事项**：稀疏 Bitmaps（offset 很大但稀疏）会浪费内存，此时应考虑用 Hash 或 Set；`BITOP` 在大 Bitmaps 上较慢，避免频繁执行

### 第 10 讲：HyperLogLog 基数统计

#### 概念

HyperLogLog（简称 HLL）是一种用于**基数统计**（cardinality counting，即统计不重复元素个数）的概率性数据结构。Redis 的 HyperLogLog 每个 key 只需固定消耗 **12KB** 内存，就能统计最多约 2^64 个不同元素的基数，标准误差约为 0.81%。相比用 Set 存储所有元素再 `SCARD` 统计，HLL 在海量数据去重统计（如 UV 统计、独立 IP 数、搜索词去重数）场景下内存占用降低了几个数量级，是大数据统计的杀手锏。

#### 原理

HyperLogLog 基于概率论中的**伯努利试验**和**抛硬币原理**。直观理解：抛硬币连续出现正面的次数 k，与抛硬币总次数 N 满足 N ≈ 2^k 的关系。HLL 对每个元素计算哈希值，将哈希值的前 p 位作为桶编号（Redis 中 p=14，共 16384 个桶），后剩余位用于计算前导零个数。每个桶记录该桶内元素的最大前导零个数。估算基数时，对所有桶的值取调和平均数，再乘以桶数和修正因子，得到基数估计值。Redis 的 HLL 实现采用稀疏编码（数据少时用字节数组节省内存）和密集编码（数据多时用固定 12KB）两种方式自动切换。`PFADD` 将元素加入 HLL，`PFCOUNT` 返回基数估计，`PFMERGE` 合并多个 HLL。需要注意的是，HLL 是**概率性**的，返回的是估计值而非精确值，且不存储元素本身，无法获取具体是哪些元素。

#### 例子

```bash
# 基本操作
127.0.0.1:6379> PFADD page:uv:index user1 user2 user3 user4 user5
(integer) 1
127.0.0.1:6379> PFCOUNT page:uv:index
(integer) 5
127.0.0.1:6379> PFADD page:uv:index user1 user2 user6   # user1 user2重复
(integer) 1
127.0.0.1:6379> PFCOUNT page:uv:index
(integer) 6

# 合并多个HLL（统计多天总UV）
127.0.0.1:6379> PFADD uv:2024-01-14 user1 user2 user3
127.0.0.1:6379> PFADD uv:2024-01-15 user2 user3 user4
127.0.0.1:6379> PFMERGE uv:total uv:2024-01-14 uv:2024-01-15
OK
127.0.0.1:6379> PFCOUNT uv:total
(integer) 4   # user1 user2 user3 user4 去重后4个
```

**实际应用：网站 UV 统计**

```python
import redis
from datetime import date, timedelta

r = redis.Redis()

class UVService:
    @staticmethod
    def record_visit(user_id, page='index', visit_date=None):
        """记录用户访问"""
        if visit_date is None:
            visit_date = date.today()
        key = f"uv:{page}:{visit_date.strftime('%Y-%m-%d')}"
        r.pfadd(key, user_id)

    @staticmethod
    def get_daily_uv(page='index', visit_date=None):
        """获取某天UV"""
        if visit_date is None:
            visit_date = date.today()
        key = f"uv:{page}:{visit_date.strftime('%Y-%m-%d')}"
        return r.pfcount(key)

    @staticmethod
    def get_range_uv(page='index', start_date=None, days=7):
        """获取一段时间内的去重UV"""
        if start_date is None:
            start_date = date.today() - timedelta(days=days-1)
        keys = []
        for i in range(days):
            d = start_date + timedelta(days=i)
            keys.append(f"uv:{page}:{d.strftime('%Y-%m-%d')}")
        merge_key = f"uv:{page}:range:{start_date.strftime('%Y%m%d')}:{days}"
        r.pfmerge(merge_key, *keys)
        return r.pfcount(merge_key)

# 使用示例
uv = UVService()
# 模拟10000个用户访问
for uid in range(10000):
    uv.record_visit(f"user_{uid}")
print("今日UV:", uv.get_daily_uv())  # 约10000（有0.81%误差）

# 模拟一周访问
for day_offset in range(7):
    visit_date = date.today() - timedelta(days=day_offset)
    for uid in range(5000, 15000):  # 部分新用户
        uv.record_visit(f"user_{uid}", visit_date=visit_date)
print("7天去重UV:", uv.get_range_uv(days=7))
```

#### 总结

- HyperLogLog 用于基数统计，固定 12KB 内存可统计 2^64 个元素的基数
- 标准误差约 0.81%，是概率性估算，不存储元素本身
- `PFADD` 添加元素，`PFCOUNT` 估算基数，`PFMERGE` 合并多个 HLL
- 经典场景：UV 统计、独立 IP 数、搜索词去重数
- **注意事项**：HLL 不存储元素，无法知道具体是哪些元素；误差约 0.81%，不适合需要精确计数的场景；如需精确去重且数据量不大，用 Set

### 第 11 讲：Geo 地理位置与 Stream 消息流

#### 概念

本讲介绍两个实用的扩展数据结构。**Geo** 是 Redis 3.2 引入的地理位置功能，基于 Sorted Set 实现，支持存储经纬度坐标并执行附近搜索、距离计算、范围查询等操作，非常适合"附近的商家"、"附近的人"等 LBS（Location Based Service）场景。**Stream** 是 Redis 5.0 引入的消息流数据结构，借鉴了 Kafka 的设计理念，支持持久化、消费者组、消息确认（ACK）等特性，是 Redis 原生的轻量级消息队列方案，比 List 实现的队列更可靠、功能更丰富。

#### 原理

**Geo 的原理**：Redis Geo 底层就是 Sorted Set，它使用 **Geohash** 算法将二维的经纬度坐标转换为一维的 score 值。Geohash 的核心思想是交替编码经度和纬度的二进制位，将地球不断二分（纬度范围 -90~90，经度范围 -180~180），每一轮二分产生一个比特位，最终将经纬度编码为一个 52 位整数作为 ZSet 的 score。Geohash 编码有一个重要特性：**编码值相近的点，地理距离也相近**（反之不一定成立），因此可以利用 ZSet 的范围查询快速找到附近的点。`GEORADIUS`/`GEOSEARCH` 命令先计算目标点周围范围的 Geohash 区间，再用 `ZRANGEBYSCORE` 查询候选点，最后精确计算距离过滤。距离计算使用 Haversine 公式，考虑了地球曲率。

**Stream 的原理**：Stream 是一个**持久化的、可消费的日志结构**，内部使用 radix tree（基数树）存储消息，每条消息有一个自动生成的 ID（格式为 `<毫秒时间戳>-<序号>`），消息按 ID 有序排列。Stream 支持消费者组（Consumer Group）模式：多个消费者可以组成一个组，组内消息会被分发（一条消息只被组内一个消费者处理），每个消费者维护自己的 pending entries list（PEL），记录已读取但未确认的消息。消费者崩溃后，其他消费者可以通过 `XPENDING`/`XCLAIM` 接管未确认的消息，实现至少一次（at-least-once）投递语义。Stream 还支持阻塞式读取（`XREAD BLOCK`）和按 ID 范围查询，功能上接近 Kafka 但更轻量。

#### 例子

**Geo 示例：**

```python
import redis

r = redis.Redis()

class StoreService:
    @staticmethod
    def add_store(store_id, lng, lat, name):
        r.geoadd('stores', (lng, lat, store_id))
        r.hset('store:info', store_id, name)

    @staticmethod
    def find_nearby(lng, lat, radius_km=5, count=20):
        """查找附近商家"""
        results = r.geosearch(
            'stores',
            longitude=lng, latitude=lat,
            radius=radius_km, unit='km',
            withdist=True, withcoord=True,
            sort='ASC', count=count
        )
        stores = []
        for item in results:
            store_id = item[0].decode()
            distance = item[1].decode()
            coord = item[2]
            name = r.hget('store:info', store_id).decode()
            stores.append({
                'store_id': store_id,
                'name': name,
                'distance_km': float(distance),
                'location': coord
            })
        return stores

# 使用示例
StoreService.add_store('s001', 116.397128, 39.916527, '王府井店')
StoreService.add_store('s002', 116.405285, 39.915728, '东单店')
nearby = StoreService.find_nearby(116.397, 39.916, radius_km=2)
for s in nearby:
    print(f"{s['name']} 距离 {s['distance_km']}km")
```

- **Geo** 基于 Sorted Set + Geohash，支持附近搜索、距离计算，适合 LBS 场景
- **Stream** 是持久化消息流，支持消费者组、ACK，是轻量级消息队列
- Geo 的 `GEOSEARCH`（替代已废弃的 `GEORADIUS`）支持丰富的过滤和排序选项
- Stream 相比 List 队列：支持持久化、消费者组、消息确认、历史回溯
- **注意事项**：Geo 的精度受 Geohash 位数影响，赤道附近精度高，两极附近精度低；Stream 不限制长度需配合 `MAXLEN` 防止内存爆炸；Stream 不适合超高吞吐场景，那应该用 Kafka

## 第四章 持久化机制

### 第 12 讲：RDB 持久化

#### 概念

RDB（Redis Database）是 Redis 的两种持久化方式之一，它将 Redis 在某个时间点上的**所有数据**以二进制快照（snapshot）的形式保存到磁盘上的 `.rdb` 文件中。RDB 文件是一个紧凑的、经过压缩的二进制文件，非常适合用于备份、灾难恢复和数据迁移。RDB 支持**手动触发**（`SAVE`/`BGSAVE`）和**自动触发**（通过配置 `save` 规则）。由于 RDB 是全量快照，恢复大数据集时速度比 AOF 快，但可能丢失最后一次快照后的所有写入。

#### 原理

RDB 持久化的核心是 **fork + COW（Copy-On-Write）** 机制。当执行 `BGSAVE` 时，Redis 主进程通过 `fork()` 系统调用创建一个子进程。`fork()` 看似复制了整个进程的内存空间，但实际上操作系统采用写时复制技术——父子进程 initially 共享相同的物理内存页，只有当某一方尝试修改某个内存页时，操作系统才会真正复制该页。子进程负责遍历所有数据并写入临时 RDB 文件，写完后用临时文件替换旧文件。由于子进程写 RDB 期间，主进程仍能正常处理命令，因此 `BGSAVE` 不会阻塞服务（fork 本身会短暂阻塞，时间与内存大小成正比）。RDB 文件格式经过精心设计：包含魔数、版本号、辅助字段、数据库选择器、键值对、CRC64 校验和。每个键值对根据类型有不同的编码，字符串使用 LZF 压缩，整数使用变长编码，整体非常紧凑。

#### 例子

**手动触发 RDB：**

```bash

OK

# BGSAVE：后台异步执行，立即返回

# 查看最近一次RDB信息

# rdb_last_save_time:1705300000
# rdb_last_bgsave_status:ok
# rdb_last_bgsave_time_sec:2
```

```python
# 触发后台保存
r.bgsave()

# 获取最近保存时间
last_save = r.lastsave()
print(f"Last save at: {last_save}")

# 定时备份脚本示例
import shutil
import time
from datetime import datetime

def backup_rdb():
    r.bgsave()
    time.sleep(2)  # 等待BGSAVE完成
    timestamp = datetime.now().strftime('%Y%m%d_%H%M%S')
    shutil.copy2('/var/lib/redis/dump.rdb', f'/backup/dump_{timestamp}.rdb')
    print(f"Backup created: dump_{timestamp}.rdb")
```

#### 总结

- RDB 是全量二进制快照，文件紧凑，恢复速度快
- 核心机制：fork 子进程 + COW（写时复制），主进程不阻塞
- 支持 `SAVE`（阻塞）、`BGSAVE`（后台）、自动触发（save 规则）
- 适合备份、灾难恢复、数据迁移场景
- **注意事项**：fork 在大内存实例上较慢（1GB 约 20ms，10GB 约 200ms），可能造成主线程短暂阻塞；RDB 是全量快照，两次快照之间的写入可能丢失；`SAVE` 命令会阻塞整个 Redis，生产环境绝对禁用

### 第 13 讲：AOF 持久化

#### 概念

AOF（Append Only File）是 Redis 的另一种持久化方式，它将所有**写命令**以追加的方式记录到 `.aof` 文件中。与 RDB 的全量快照不同，AOF 是增量记录，理论上可以做到不丢失任何写入（取决于 fsync 策略）。AOF 文件是纯文本格式，可读性好，甚至可以手动编辑修复。当 Redis 重启时，通过重放 AOF 文件中的所有命令来恢复数据。AOF 的缺点是文件比 RDB 大、恢复速度慢，且写入开销略高。Redis 7.0 后 AOF 采用多文件结构（base + incremental），提升了重写效率。

#### 原理

AOF 的工作流程分为三步：**命令追加 → 文件写入 → 文件同步（fsync）**。每当执行一个写命令，Redis 会将该命令按 RESP 协议序列化后追加到 `aof_buf` 缓冲区。`aof_buf` 的内容会在每次事件循环结束时写入操作系统文件缓冲区。但是否真正落盘由 `appendfsync` 配置决定：**always** 表示每个命令都 fsync，最安全但性能最差；**everysec**（默认）表示每秒 fsync 一次，最多丢失 1 秒数据，性能与安全平衡；**no** 表示由操作系统决定何时 fsync，性能最好但可能丢失较多数据。随着命令不断追加，AOF 文件会越来越大，因此 Redis 提供 **AOF 重写（rewrite）** 机制——fork 子进程遍历当前数据，生成最小命令集的新 AOF 文件。例如对同一个 key 执行了 100 次 `SET`，重写后只保留最后一次。重写期间新的写命令会同时写入旧 AOF 和重写缓冲区，重写完成后将缓冲区内容追加到新文件，最后原子替换。Redis 7.0 引入 **multi-part AOF**，将 AOF 拆分为 base 文件（重写时的全量快照）和 incremental 文件（重写后的增量命令），避免了重写时的复杂缓冲区逻辑。

#### 例子

**AOF 配置（redis.conf）：**

```conf
# 开启AOF
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec      # 每秒fsync一次（推荐）

# AOF重写触发条件
auto-aof-rewrite-percentage 100  # 文件大小比上次重写后增长100%
auto-aof-rewrite-min-size 64mb   # 文件至少64MB才触发重写

# AOF重写期间是否禁用fsync
no-appendfsync-on-rewrite no

# Redis 7.0+ 多文件AOF配置
aof-dirname appendonlydir
aof-timestamp-enabled no
```

**AOF 操作命令：**

```bash

# 查看AOF状态

# aof_enabled:1
# aof_rewrite_in_progress:0
# aof_last_rewrite_time_sec:3
# aof_current_size:1024
# aof_base_size:512

# 查看AOF文件内容（纯文本，可读）
# cat appendonly.aof
# *2
# $6
# SELECT
# $1
# 0
# *3
# $3
# SET
# $4
# name
# $5
# Alice
```


**三种 fsync 策略对比：**


#### 总结

- AOF 以追加方式记录所有写命令，数据安全性高于 RDB
- 三种 fsync 策略：always（最安全慢）、everysec（推荐平衡）、no（最快可能丢数据）
- AOF 重写机制通过 fork 子进程生成最小命令集，避免文件无限增长
- Redis 7.0+ 采用 multi-part AOF（base + incremental），提升重写效率
- **注意事项**：AOF 文件比 RDB 大，恢复速度慢；重写时 fork 会短暂阻塞，大内存实例需注意；`appendfsync always` 性能极差，生产环境几乎不用；AOF 文件损坏可用 `redis-check-aof --fix` 修复

### 第 14 讲：持久化方案对比与选择

#### 概念

Redis 提供了 RDB 和 AOF 两种持久化方式，以及它们的**混合持久化**模式。每种方式在数据安全性、恢复速度、性能开销、文件大小等方面各有取舍。在实际生产环境中，需要根据业务对数据丢失的容忍度、恢复时间要求、性能要求等因素综合选择。Redis 4.0 引入的混合持久化结合了 RDB 和 AOF 的优点，是目前生产环境的推荐方案。理解各种持久化方式的特性与适用场景，是 Redis 运维的基础能力。

#### 原理

**混合持久化**（Redis 4.0+）的原理是在 AOF 重写时，不再生成纯命令的 AOF 文件，而是先以 RDB 二进制格式写入当前全量数据，再将重写期间的增量命令以 AOF 格式追加。这样 AOF 文件 = RDB 全量快照 + 增量 AOF 命令。恢复时，先加载 RDB 部分（速度快），再重放 AOF 增量命令（数据全）。这种设计兼顾了 RDB 的快速恢复和 AOF 的数据完整性。混合持久化通过 `aof-use-rdb-preamble yes`（Redis 4.0-4.x）或默认开启（Redis 5.0+）启用。**性能对比**：RDB 持久化开销最小（只在 fork 时有短暂阻塞），AOF everysec 开销略高（每秒 fsync），AOF always 开销最大。**恢复速度**：RDB 最快（直接加载二进制），纯 AOF 最慢（重放所有命令），混合持久化居中偏快。**数据安全性**：RDB 可能丢失最后一次快照后的数据，AOF everysec 最多丢 1 秒，AOF always 不丢失，混合持久化取决于 AOF 部分。

#### 例子

**混合持久化配置（推荐生产方案）：**

```conf
# 同时开启RDB和AOF
save 900 1
save 300 10
save 60 10000

appendonly yes
appendfsync everysec

# 开启混合持久化（Redis 5.0+默认开启）
aof-use-rdb-preamble yes

# AOF重写触发
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

**三种方案对比表：**

| 特性 | RDB | AOF | 混合持久化 |
|------|-----|-----|-----------|
| 数据安全性 | 可能丢失数分钟数据 | 最多丢1秒（everysec） | 最多丢1秒 |
| 恢复速度 | 快 | 慢 | 较快 |
| 文件大小 | 小（压缩二进制） | 大（纯文本命令） | 中等 |
| 性能开销 | 低 | 中 | 中 |
| 可读性 | 不可读 | 可读 | 部分可读 |
| 适用场景 | 备份、容灾 | 数据安全要求高 | 生产推荐 |

**不同场景的配置建议：**

```bash
# 场景1：纯缓存，允许丢失所有数据
# 不需要持久化，性能最高

appendonly no
maxmemory-policy allkeys-lru

# 场景2：会话存储，允许丢失少量数据
# 仅用RDB
save 300 10
appendonly no

# 场景3：订单系统，不能丢数据
# 混合持久化（推荐）
save 900 1
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes

# 场景4：金融级，绝对不能丢数据
# AOF always（性能牺牲换安全）
appendonly yes
appendfsync always
# 注意：性能会显著下降，建议评估后使用
```

- RDB：全量快照，恢复快，可能丢数据，适合备份
- AOF：增量命令，数据安全，恢复慢，文件大
- 混合持久化（Redis 4.0+）：RDB + AOF 增量，生产环境推荐
- 选择依据：数据丢失容忍度、恢复时间要求、性能要求
- **注意事项**：纯缓存场景可关闭持久化提升性能；金融级场景用 `appendfsync always` 但要评估性能影响；定期备份 RDB 文件到异地；监控持久化状态，及时发现失败

## 第五章 内存管理与过期策略

### 第 15 讲：过期键删除策略

#### 概念

Redis 允许为键设置**过期时间（TTL，Time To Live）**，到期后键会被自动删除。过期键的删除并非实时进行，而是采用**惰性删除 + 定期删除**两种策略配合实现。理解过期键的删除机制，对于排查"内存没释放"、"键没及时过期"等问题至关重要。Redis 提供了 `EXPIRE`、`PEXPIRE`、`EXPIREAT`、`PEXPIREAT` 等命令设置过期时间，以及 `TTL`、`PTTL` 查看剩余时间，`PERSIST` 移除过期时间。需要注意的是，过期时间只对**键级别**生效，无法为 Hash 的字段、Set 的成员单独设置过期。

#### 原理

Redis 的过期键删除采用**双策略配合**：**惰性删除（lazy expiration）** 是指在每次访问一个键时（`GET`、`SET`、`HGET` 等任何操作），Redis 都会先检查该键是否已过期，如果过期则立即删除并返回空。这种策略保证了不会返回过期数据，但问题是如果某些过期键长期不被访问，它们会一直占用内存。**定期删除（periodic expiration）** 是指 Redis 每隔一段时间（由 `hz` 配置控制，默认每秒 10 次）随机抽取一部分设置了过期的键进行检查，删除其中已过期的。具体来说，每次定期删除会从 expires 字典中随机抽取 20 个键，删除其中过期的，如果过期键比例超过 25%，则继续抽取，直到过期键比例降低或时间用尽（每次最多执行 25ms）。这种策略在 CPU 和内存之间取得平衡。如果两种策略都没能及时删除过期键，且内存达到 `maxmemory` 限制，还会触发**内存淘汰策略**（下一讲详述）。过期键的过期信息存储在独立的 `expires` 字典中，键指向同一个 SDS 对象，值是过期时间戳（毫秒），这种分离设计使得过期检查不影响主字典性能。

#### 例子

```bash
# 设置过期时间的多种方式
127.0.0.1:6379> SET session:abc "data" EX 60        # 60秒后过期
OK
127.0.0.1:6379> SET token:xyz "data" PX 60000       # 60000毫秒后过期
OK
127.0.0.1:6379> EXPIRE cache:key 300                # 已存在的键设置300秒过期
(integer) 1
127.0.0.1:6379> PEXPIRE cache:key 300000            # 毫秒级
(integer) 1
127.0.0.1:6379> EXPIREAT cache:key 1705300000       # Unix时间戳过期
(integer) 1

# 查看剩余时间
127.0.0.1:6379> TTL session:abc                     # 剩余秒数
(integer) 58
127.0.0.1:6379> PTTL session:abc                    # 剩余毫秒数
(integer) 58000
# TTL返回值：-1表示永不过期，-2表示键不存在（已过期或被删除）

# 移除过期时间
127.0.0.1:6379> PERSIST session:abc
(integer) 1
127.0.0.1:6379> TTL session:abc
(integer) -1

# NX/XX/GT/LT 选项（Redis 7.0+）
127.0.0.1:6379> EXPIRE key 60 NX                    # 仅当键没有过期时间时设置
127.0.0.1:6379> EXPIRE key 120 XX                   # 仅当键已有过期时间时更新
127.0.0.1:6379> EXPIRE key 300 GT                   # 仅当新TTL大于当前TTL时更新
127.0.0.1:6379> EXPIRE key 30 LT                    # 仅当新TTL小于当前TTL时更新
```

**过期键在不同场景下的行为：**

```python
# - 主从复制：主节点删除后，会向从节点发送DEL命令
```

#### 总结

- Redis 过期键删除采用**惰性删除 + 定期删除**双策略
- 惰性删除：访问时检查，保证不返回过期数据
- 定期删除：每秒 `hz` 次随机抽样清理，平衡 CPU 和内存
- 过期信息存储在独立的 `expires` 字典，不影响主字典性能
- **注意事项**：过期键不会立即释放内存，可能存在延迟；`hz` 配置影响过期清理频率；RDB/AOF/主从复制对过期键有不同处理；无法为 Hash 字段、Set 成员单独设置过期

### 第 16 讲：内存淘汰策略与优化

#### 概念

当 Redis 使用的内存达到 `maxmemory` 限制时，需要通过**内存淘汰策略（eviction policy）** 决定删除哪些键以腾出空间。Redis 提供了 8 种淘汰策略，涵盖不淘汰（报错）、随机淘汰、LRU（最近最少使用）、LFU（最近最少频率使用）等不同算法，每种策略又分为"只淘汰设置了过期的键"和"淘汰所有键"两个版本。合理选择淘汰策略是缓存系统设计的关键，直接影响缓存命中率和系统稳定性。此外，Redis 4.0 引入的 LFU 算法相比 LRU 更能反映数据的真实访问热度，适合大多数缓存场景。

#### 原理

Redis 的 **LRU（Least Recently Used）** 算法并非严格的 LRU 实现，而是**近似 LRU**——它不会维护一个全局的链表（那样太耗内存和 CPU），而是为每个 `redisObject` 增加一个 24 位的 `lru` 字段，记录对象最后一次被访问的时间戳（精度秒）。当需要淘汰时，Redis 随机采样 `maxmemory-samples` 个键（默认 5 个），淘汰其中 `lru` 值最小（最久未访问）的那个。增大采样数可以提高精度但增加 CPU 开销，Redis 5.0 后引入了**增强的 LRU**——维护一个大小为 16 的待淘汰候选池，进一步提升精度。**LFU（Least Frequently Used）** 算法（Redis 4.0+）同样复用 24 位 `lru` 字段，但将其拆分为 16 位的时间戳和 8 位的访问计数器。8 位计数器最大 255，但 Redis 使用**对数计数**——访问次数越多，计数器增长越慢，避免热门键计数器很快饱和。同时，计数器会随时间**衰减**（由 `lfu-decay-time` 控制，默认 1 分钟衰减 1），保证长期不访问的键会被淘汰。8 种策略：`noeviction`（不淘汰，写入报错）、`allkeys-lru`、`volatile-lru`、`allkeys-lfu`、`volatile-lfu`、`allkeys-random`、`volatile-random`、`volatile-ttl`（优先淘汰 TTL 最短的）。

#### 例子

**8 种淘汰策略对比：**

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| noeviction | 不淘汰，内存满时写入返回错误 | 数据不能丢失，如数据库 |
| allkeys-lru | 所有键中淘汰最久未使用的 | 通用缓存（推荐） |
| volatile-lru | 设置了过期的键中淘汰最久未使用的 | 混合场景（部分数据持久） |
| allkeys-lfu | 所有键中淘汰访问频率最低的 | 访问频率差异大的缓存 |
| volatile-lfu | 设置过期的键中淘汰访问频率最低的 | 同上，但有持久数据 |
| allkeys-random | 所有键中随机淘汰 | 访问模式均匀 |
| volatile-random | 设置过期的键中随机淘汰 | 同上 |
| volatile-ttl | 优先淘汰 TTL 最短的 | 缓存数据有明确过期 |

**配置淘汰策略：**

```conf
# redis.conf
maxmemory 2gb                       # 最大内存限制
```

```python
# 不推荐：very:long:key:name:that:wastes:memory
# 推荐：u:1:name（在可读性和内存间平衡）

# 5. 使用 OBJECT ENCODING 查看编码

# 6. 使用 MEMORY USAGE 查看键占用内存

def cleanup_pattern(pattern, batch=1000):
    """批量删除匹配的键"""
    cursor = 0
    while True:
        cursor, keys = r.scan(cursor, match=pattern, count=batch)
        if keys:
            r.delete(*keys)
        if cursor == 0:
            break
```

## 第六章 事务与脚本

### 第 17 讲：事务机制（MULTI/EXEC/WATCH）

#### 概念

Redis 的事务是一种**弱事务**机制，它允许将多个命令打包成一个原子执行单元——要么全部按顺序执行，要么一个都不执行。Redis 事务通过 `MULTI`、`EXEC`、`DISCARD`、`WATCH` 四个命令实现。与关系型数据库的事务不同，Redis 事务**不支持回滚**——如果事务中的某个命令执行出错（如类型错误），后续命令仍会继续执行，已执行的命令不会回滚。Redis 事务的核心价值在于**保证命令的顺序执行，且执行期间不会被其他客户端打断**。`WATCH` 命令提供了**乐观锁**机制，可以监控一个或多个键，如果在 `EXEC` 之前这些键被修改，整个事务会自动放弃。

#### 原理

Redis 事务的实现基于**命令队列**。当客户端发送 `MULTI` 命令后，Redis 会将该客户端标记为"事务模式"，此后该客户端发送的命令不会立即执行，而是按顺序加入一个队列，并返回 `QUEUED` 表示已入队。当客户端发送 `EXEC` 命令时，Redis 会一次性按顺序执行队列中的所有命令，并将所有结果打包返回。由于 Redis 是单线程执行命令，事务执行期间不会被其他客户端的命令打断，保证了原子性。**WATCH 机制**的实现：`WATCH key` 会在 `watched_keys` 字典中记录该键被当前客户端监控。如果在 `EXEC` 之前，任何被监控的键被修改（包括过期、淘汰、被其他客户端修改），Redis 会设置 `CLIENT_DIRTY_CAS` 标志。`EXEC` 时检查该标志，如果被设置，则放弃整个事务，返回 nil。这是一种典型的 **CAS（Compare-And-Swap）乐观锁**。需要注意的是，Redis 事务的"原子性"只保证命令全部执行或全不执行，但**不保证全部成功**——命令执行错误不会回滚，这是 Redis 设计哲学的取舍（作者认为命令错误通常是编程 bug，不应在生产环境发生）。

#### 例子

**基本事务：**


**Python 实现转账（WATCH + 重试）：**

```python
import redis

r = redis.Redis()

def transfer(from_account, to_account, amount, max_retries=3):
    """使用WATCH实现安全的转账"""
    for attempt in range(max_retries):
        try:
            # 开启WATCH
            with r.pipeline() as pipe:
                pipe.watch(from_account)
                balance = int(pipe.get(from_account) or 0)

                if balance < amount:
                    pipe.unwatch()
                    return False, "余额不足"

                # 开启事务
                pipe.multi()
                pipe.decrby(from_account, amount)
                pipe.incrby(to_account, amount)
                pipe.execute()  # 如果from_account被修改，抛出WatchError
                return True, "转账成功"
        except redis.WatchError:
            print(f"第{attempt+1}次尝试失败，重试...")
            continue
    return False, "重试次数耗尽"

# 使用示例
r.set('account:A', 100)
r.set('account:B', 50)
success, msg = transfer('account:A', 'account:B', 30)
print(msg)
print(f"A: {r.get('account:A')}, B: {r.get('account:B')}")
```

#### 总结

- Redis 事务通过 `MULTI`/`EXEC`/`DISCARD` 实现，命令打包顺序执行，不被打断
- `WATCH` 提供乐观锁，监控的键被修改则事务放弃（CAS 机制）
- Redis 事务**不支持回滚**，命令执行错误不回滚，后续命令继续执行
- 适合"读取-判断-写入"的原子操作场景，如转账、库存扣减
- **注意事项**：事务中命令语法错误会放弃整个事务；执行错误不回滚，需在代码层面处理；`WATCH` 后必须在 `EXEC` 前重新 `WATCH` 才能再次监控；复杂原子操作建议用 Lua 脚本替代事务

### 第 18 讲：Lua 脚本与 Pipeline

#### 概念

**Lua 脚本**是 Redis 提供的强大特性，它允许将一段 Lua 代码发送到 Redis 服务器执行，整个脚本作为一个原子操作，执行期间不会被其他命令打断。Lua 脚本比事务更强大——它支持条件判断、循环、变量等编程逻辑，可以实现复杂的原子操作。Redis 7.0 后推荐使用 `EVALSHA` + Functions 替代 `EVAL`，提升性能。**Pipeline（管道）** 是客户端技术，它将多个命令一次性发送给服务器，服务器依次执行后一次性返回所有结果，大幅减少网络往返时间（RTT）。Pipeline 不保证原子性，但能显著提升批量操作性能。两者常配合使用：用 Pipeline 批量发送，用 Lua 保证原子性。

#### 原理

**Lua 脚本的原理**：Redis 内嵌了 Lua 5.1 解释器，`EVAL script numkeys key [key...] arg [arg...]` 命令将脚本和参数发送给服务器。服务器在 Lua 环境中执行脚本，脚本通过 `redis.call()` 或 `redis.pcall()` 调用 Redis 命令。`redis.call()` 执行出错会中断脚本并返回错误，`redis.pcall()` 会捕获错误返回错误对象。整个脚本执行期间，Redis 单线程被独占，保证原子性。为了避免每次发送完整脚本的开销，Redis 提供 `SCRIPT LOAD` 将脚本缓存并返回 SHA1 校验和，后续用 `EVALSHA sha1 ...` 执行，只需发送 40 字节的哈希值。如果服务器重启或缓存丢失，`EVALSHA` 会报 `NOSCRIPT` 错误，客户端应回退到 `EVAL`。**注意事项**：Lua 脚本不能执行耗时操作（如大循环），否则会阻塞 Redis；Redis 7.0 前脚本会被复制到从节点和写入 AOF，因此脚本必须是**纯函数**（相同输入产生相同输出），不能依赖时间、随机数等。**Pipeline 的原理**：客户端将多个命令缓存到本地缓冲区，一次性通过 TCP 发送，服务器依次执行并将所有响应缓存，最后一次性返回。Pipeline 减少了 N 次 RTT 为 1 次 RTT，但**不保证原子性**——执行期间可能插入其他客户端的命令。Pipeline 也没有事务语义，命令之间是独立的。

#### 例子

**Lua 脚本基础：**

```python
import redis

r = redis.Redis()

# 1. 分布式锁释放脚本（保证原子性）
release_lock_script = """
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
"""
release_lock = r.register_script(release_lock_script)

def acquire_lock(lock_name, timeout=10):
    import uuid
    identifier = str(uuid.uuid4())
    if r.set(lock_name, identifier, nx=True, ex=timeout):
        return identifier
    return None

def release(lock_name, identifier):
    return release_lock(keys=[lock_name], args=[identifier])

# 2. 原子限流器
rate_limit_script = """
local current = redis.call('incr', KEYS[1])
if current == 1 then
    redis.call('expire', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
    return 0
end
return 1
"""
rate_limit = r.register_script(rate_limit_script)

def is_allowed(user_id, max_requests=100, window_seconds=60):
    key = f"rate_limit:{user_id}"
    return bool(rate_limit(keys=[key], args=[window_seconds, max_requests]))

# 3. 原子扣减库存
deduct_stock_script = """
local stock = tonumber(redis.call('get', KEYS[1]))
if stock == nil then
    return -1  -- 商品不存在
end

    return 0  -- 库存不足
end

return 1  -- 扣减成功
"""
```

```python
    pipe.get(f'key:{i}')
results = pipe.execute()

pipe.multi()
pipe.set('a', 1)
pipe.set('b', 2)
pipe.incr('counter')
results = pipe.execute()

# 分批Pipeline（避免内存爆炸）
def batch_set(prefix, count, batch_size=1000):
    """分批执行Pipeline，避免单次过大"""
    for start in range(0, count, batch_size):
        pipe = r.pipeline()
        for i in range(start, min(start + batch_size, count)):
            pipe.set(f'{prefix}:{i}', i)
        pipe.execute()

batch_set('batch', 100000)
```

- Pipeline 是客户端技术，减少网络 RTT，但不保证原子性
- 两者配合：Pipeline 批量发送，Lua 保证单次原子

## 第七章 消息通信

### 第 19 讲：发布订阅模式

#### 概念

发布订阅（Pub/Sub）是 Redis 提供的一种消息通信模式，允许发送者（发布者）将消息发送到频道（channel），而不需要知道有哪些接收者（订阅者）。订阅者可以订阅一个或多个频道，接收发布到这些频道的所有消息。这种模式实现了发布者和订阅者的**解耦**——发布者不关心谁在接收，订阅者不关心谁在发送。Redis 的 Pub/Sub 是**实时**的：消息发出后，只有当前在线的订阅者能收到，**不持久化**，离线订阅者会错过消息。Pub/Sub 适合实时通知、聊天室、实时数据推送等场景，但不适合需要可靠投递的消息队列场景。

#### 原理

Redis 的 Pub/Sub 实现基于两个数据结构：`pubsub_channels` 字典和 `pubsub_patterns` 链表。`pubsub_channels` 是一个 dict，key 是频道名，value 是订阅该频道的客户端链表。当发布者执行 `PUBLISH channel message` 时，Redis 在 `pubsub_channels` 中查找该频道的客户端链表，将消息发送给所有订阅者。`pubsub_patterns` 用于模式订阅（`PSUBSCRIBE`），存储 `glob` 模式与客户端的映射，发布消息时会遍历所有模式，匹配的客户端也会收到消息。Pub/Sub 的消息传递是**同步**的——`PUBLISH` 命令会遍历所有订阅者并逐一发送，如果订阅者很多或网络慢，`PUBLISH` 会变慢。**关键限制**：消息不持久化，离线订阅者收不到历史消息；没有 ACK 机制，无法保证消息被正确处理；订阅者处理慢会导致其输出缓冲区积压，可能被强制断开。这些限制使得 Pub/Sub 不适合作为可靠消息队列，Redis 5.0 引入的 Stream 解决了这些问题。

#### 例子

```bash
# 终端1：订阅频道

Reading messages... (press Ctrl-C to quit)
1) "subscribe"
2) "news:tech"
3) (integer) 1
1) "subscribe"
2) "news:sports"
3) (integer) 2

# 终端2：发布消息
127.0.0.1:6379> PUBLISH news:tech "Redis 7.2 released"
(integer) 1   # 1个订阅者收到

# 终端1收到：
1) "message"
2) "news:tech"
3) "Redis 7.2 released"

# 模式订阅（通配符）
127.0.0.1:6379> PSUBSCRIBE news:*
# 会收到 news:tech 和 news:sports 的所有消息

# 查看订阅状态
127.0.0.1:6379> PUBSUB CHANNELS news:*       # 查看匹配的活跃频道
1) "news:tech"
2) "news:sports"
127.0.0.1:6379> PUBSUB NUMSUB news:tech      # 查看频道订阅者数量
1) "news:tech"
2) (integer) 1
127.0.0.1:6379> PUBSUB NUMPAT                # 查看模式订阅数量
(integer) 1
```

**实际应用：实时通知系统**

```python
import redis
import json

r = redis.Redis()

class NotificationService:
    @staticmethod
    def notify(user_id, event_type, data):
        """向指定用户发送实时通知"""
        channel = f"notify:user:{user_id}"
        message = json.dumps({
            'type': event_type,
            'data': data
        })
        r.publish(channel, message)

    @staticmethod
    def broadcast(event_type, data):
        """广播通知给所有用户"""
        message = json.dumps({
            'type': event_type,
            'data': data
        })
        r.publish('notify:broadcast', message)

    @staticmethod
    def listen(user_id, handler):
        """监听用户通知"""
        pubsub = r.pubsub()
        pubsub.subscribe(f"notify:user:{user_id}", 'notify:broadcast')
        for message in pubsub.listen():
            if message['type'] == 'message':
                data = json.loads(message['data'])
                handler(data)

# 触发通知
NotificationService.notify(1001, 'order_paid', {'order_id': 'A001'})
NotificationService.broadcast('system', {'msg': '系统维护通知'})
```

- Pub/Sub 实现发布者与订阅者解耦，支持频道订阅和模式订阅
- 消息**不持久化**，离线订阅者收不到历史消息
- 没有 ACK 机制，不保证可靠投递
- 适合实时通知、聊天室、数据推送，不适合可靠消息队列
- **注意事项**：订阅者多或网络慢时 `PUBLISH` 会变慢；订阅者处理慢会导致输出缓冲区积压；需要可靠投递请用 Stream；模式订阅（`PSUBSCRIBE`）匹配开销较大

### 第 20 讲：Stream 消息队列

#### 概念

Stream 是 Redis 5.0 引入的消息流数据结构，专为消息队列场景设计，弥补了 Pub/Sub 不可靠、List 队列功能简单的不足。Stream 支持**消息持久化**、**消费者组**、**消息确认（ACK）**、**历史消息回溯**等特性，功能上接近 Kafka 但更轻量。一个 Stream 可以有多个消费者组，每个组内的消息会被分发（一条消息只被组内一个消费者处理），消费者维护自己的 pending 列表，未确认的消息可以被其他消费者接管。Stream 适合订单处理、任务分发、事件溯源等需要可靠投递的场景。

#### 原理

Stream 内部使用 **radix tree（基数树）** 存储消息，每条消息有一个唯一的 ID（格式 `<毫秒时间戳>-<序号>`，如 `1705300000000-0`），消息按 ID 有序排列。radix tree 是一种压缩前缀树，对于有序的、有公共前缀的 ID 非常节省内存。**消费者组（Consumer Group）** 机制：`XGROUP CREATE` 创建组时，会记录一个 `last-delivered-id`，表示该组已消费到的位置。消费者通过 `XREADGROUP GROUP group consumer STREAMS stream >` 读取消息时，`>` 表示读取 `last-delivered-id` 之后的新消息，读取后该消息 ID 会被加入消费者的 **PEL（Pending Entries List）**，表示"已读取但未确认"。消费者处理完后执行 `XACK` 确认，消息从 PEL 移除。如果消费者崩溃，PEL 中的消息不会被确认，其他消费者可以通过 `XPENDING` 查看 PEL，用 `XCLAIM` 接管超时未确认的消息，实现**至少一次（at-least-once）** 投递。`XREAD`（非组模式）可以按 ID 范围读取历史消息，支持阻塞式读取（`BLOCK`），实现类似 Pub/Sub 的实时推送但带持久化。`XADD MAXLEN` 可以限制 Stream 长度，防止无限增长。

#### 例子

```bash
# 生产消息
127.0.0.1:6379> XADD orders * order_id 1001 amount 99.9 status created
"1705300000000-0"
127.0.0.1:6379> XADD orders * order_id 1002 amount 199.9 status created
"1705300000001-0"

# 查询消息
127.0.0.1:6379> XLEN orders                          # 消息总数
(integer) 2
127.0.0.1:6379> XRANGE orders - +                    # 所有消息
127.0.0.1:6379> XRANGE orders 1705300000000-0 1705300000000-0
127.0.0.1:6379> XREVRANGE orders + - COUNT 1         # 最新一条

# 创建消费者组
127.0.0.1:6379> XGROUP CREATE orders order_group 0 MKSTREAM  # 从头消费
OK
127.0.0.1:6379> XGROUP CREATE orders order_group $ MKSTREAM   # 只消费新消息

# 消费者读取消息
127.0.0.1:6379> XREADGROUP GROUP order_group consumer1 COUNT 1 STREAMS orders >
1) 1) "orders"
   2) 1) 1) "1705300000000-0"
         2) 1) "order_id"
            2) "1001"
            3) "amount"
            4) "99.9"

# 确认消息
127.0.0.1:6379> XACK orders order_group 1705300000000-0
(integer) 1

# 查看pending消息（已读未确认）
127.0.0.1:6379> XPENDING orders order_group
1) (integer) 0   # pending数量

# 接管超时消息（消费者崩溃后）
127.0.0.1:6379> XAUTOCLAIM orders order_group consumer2 60000 0
# 60000ms超时，从ID 0开始扫描

# 限制Stream长度
127.0.0.1:6379> XADD orders MAXLEN 10000 * order_id 1003 amount 50
# 精确限制：MAXLEN 10000
# 近似限制（更高效）：MAXLEN ~ 10000
```

**Python 实现可靠消息队列：**

```python
import redis
import json
import time
import threading

r = redis.Redis()

class StreamQueue:
    def __init__(self, stream_name, group_name):
        self.stream = stream_name
        self.group = group_name
        self._ensure_group()

    def _ensure_group(self):
        """确保消费者组存在"""
        try:
            r.xgroup_create(self.stream, self.group, id='0', mkstream=True)
        except redis.ResponseError as e:
            if 'BUSYGROUP' not in str(e):
                raise

    def produce(self, message):
        """生产消息"""
        return r.xadd(self.stream, message, maxlen=10000, approximate=True)

    def consume(self, consumer_name, handler, count=1, block=5000):
        """消费消息"""
        while True:
            # 读取新消息
            messages = r.xreadgroup(
                self.group, consumer_name,
                {self.stream: '>'},
                count=count, block=block
            )
            if not messages:
                # 没有新消息，尝试处理pending（崩溃恢复）
                self._handle_pending(consumer_name, handler)
                continue

            for stream, msg_list in messages:
                for msg_id, fields in msg_list:
                    try:
                        handler(fields)
                        r.xack(self.stream, self.group, msg_id)
                    except Exception as e:
                        print(f"处理失败: {e}, 消息留在pending")

    def _handle_pending(self, consumer_name, handler, min_idle=60000):
        """处理超时未确认的pending消息"""
        pending = r.xautoclaim(
            self.stream, self.group, consumer_name,
            min_idle_time=min_idle, start_id='0', count=10
        )
        if pending and pending[1]:
            for msg_id, fields in pending[1]:
                try:
                    handler(fields)
                    r.xack(self.stream, self.group, msg_id)
                except Exception as e:
                    print(f"重试失败: {e}")

# 使用示例：订单处理
def process_order(fields):
    order_id = fields[b'order_id'].decode()
    amount = fields[b'amount'].decode()
    print(f"处理订单: {order_id}, 金额: {amount}")
    # 模拟处理
    time.sleep(0.1)

queue = StreamQueue('orders', 'order_processors')

# 生产者
queue.produce({'order_id': 'A001', 'amount': '99.9'})
queue.produce({'order_id': 'A002', 'amount': '199.9'})

# 消费者（多消费者并行）
def worker(name):
    queue.consume(name, process_order)

for i in range(3):
    threading.Thread(target=worker, args=(f'worker-{i}',), daemon=True).start()

time.sleep(2)
```

#### 总结

- Stream 是 Redis 原生的消息队列，支持持久化、消费者组、ACK
- 消费者组实现消息分发，PEL 记录未确认消息，支持崩溃恢复
- `XAUTOCLAIM` 可接管超时未确认的消息，实现至少一次投递
- `XADD MAXLEN` 限制 Stream 长度，防止内存爆炸
- **注意事项**：Stream 不适合超高吞吐（单机万级 QPS），那应该用 Kafka；消费者处理完务必 `XACK`，否则 PEL 无限增长；`MAXLEN ~ N` 近似限制比精确限制高效；阻塞读取用 `BLOCK` 参数避免空转

## 第八章 高可用架构

### 第 21 讲：主从复制

#### 概念

主从复制（Replication）是 Redis 最基础的高可用方案，它允许一个 Redis 主节点（master）的数据实时同步到一个或多个从节点（slave/replica）。主节点负责读写操作，从节点默认只读，通过异步复制保持与主节点数据一致。主从复制实现了**读写分离**（读请求分摊到从节点）和**数据冗余**（主节点故障时从节点可提升为主），是构建高可用 Redis 的基础。Redis 4.0 后建议使用 `replicaof` 替代 `slaveof`（语义更清晰），但两者功能相同。需要注意的是，Redis 的主从复制是**异步**的，主节点写入后立即返回，不等从节点确认，因此存在数据延迟和故障时少量数据丢失的可能。

#### 原理

Redis 主从复制分为**全量同步**和**命令传播**两个阶段。**全量同步**发生在从节点首次连接主节点或断线重连后无法增量同步时：从节点发送 `PSYNC ? -1`（首次）或 `PSYNC <runid> <offset>`（重连），主节点判断是否可以增量同步，如果不能则执行全量同步——主节点执行 `BGSAVE` 生成 RDB 文件，同时将生成期间的新写命令缓存到**复制缓冲区**，RDB 生成完毕后发送给从节点，从节点加载 RDB 后，主节点再将缓冲区的命令发送给从节点。**命令传播**阶段：全量同步完成后，主节点每执行一个写命令，就异步发送给所有从节点，从节点执行后保持数据一致。每个节点维护一个**复制偏移量（offset）**，主节点记录发送的字节数，从节点记录接收的字节数，通过对比 offset 可以判断是否同步。**部分重同步（PSYNC）**（Redis 2.8+）解决了断线重连必须全量同步的问题：主节点维护一个**复制积压缓冲区（backlog）**（默认 1MB），记录最近的写命令。从节点断线重连时，如果 offset 在 backlog 范围内，主节点只发送缺失的部分，避免全量同步。`repl-backlog-size` 配置 backlog 大小，对于写入量大的场景应增大（如 256MB）。Redis 还通过 **replid**（runid）标识主节点身份，主节点变更时 replid 改变，触发全量同步。

**Python 读写分离示例：**

```python
import redis

class RedisReadWriteSplit:
    def __init__(self, master_host, slave_hosts):
        self.master = redis.Redis(host=master_host[0], port=master_host[1])
        self.slaves = [redis.Redis(host=h, port=p) for h, p in slave_hosts]
        self._slave_idx = 0

    def write(self, key, value):
        """写操作走主节点"""
        return self.master.set(key, value)

    def read(self, key):
        """读操作轮询从节点"""
        slave = self.slaves[self._slave_idx % len(self.slaves)]
        self._slave_idx += 1
        return slave.get(key)

    def write_hash(self, name, mapping):
        return self.master.hset(name, mapping=mapping)

    def read_hash(self, name, field):
        slave = self.slaves[self._slave_idx % len(self.slaves)]
        self._slave_idx += 1
        return slave.hget(name, field)

# 使用示例
rw = RedisReadWriteSplit(
    master_host=('127.0.0.1', 6379),
    slave_hosts=[('127.0.0.1', 6380), ('127.0.0.1', 6381)]
)

rw.write('user:1', 'Alice')
print(rw.read('user:1'))  # 可能从从节点读取（有延迟）
```

- 全量同步（BGSAVE + RDB 传输）+ 命令传播（异步发送写命令）

### 第 22 讲：哨兵 Sentinel

#### 概念

Sentinel（哨兵）是 Redis 官方提供的高可用方案，它在主从复制基础上增加了**自动故障转移**能力。Sentinel 是一组独立运行的进程（通常 3 个以上奇数个），负责监控主从节点的存活状态，当主节点故障时自动选举新的主节点，并通知客户端切换。Sentinel 解决了主从复制中主节点故障需要人工干预的问题，实现了 Redis 的自动高可用。一个 Sentinel 集群可以监控多个 Redis 主从集群，Sentinel 之间也会相互通信，通过**多数投票**决策故障转移，避免单点误判。

#### 原理

Sentinel 的工作机制包含四个核心任务：**监控**、**通知**、**自动故障转移**、**配置中心**。**监控**：每个 Sentinel 每秒向主节点、从节点、其他 Sentinel 发送 `PING`，如果在 `down-after-milliseconds`（默认 30 秒）内未收到有效回复，则标记该节点为**主观下线（SDOWN）**。当一个 Sentinel 认为主节点主观下线后，会询问其他 Sentinel，如果超过 `quorum` 个（配置的法定数）Sentinel 都认为下线，则标记为**客观下线（ODOWN）**。**自动故障转移**：标记客观下线后，Sentinel 集群选举一个**领导者 Sentinel**（基于 Raft 算法）负责执行故障转移。领导者从从节点中选一个提升为新主节点，选举依据：1）过滤掉断线的从节点；2）按优先级（`replica-priority`）选最高的；3）优先级相同选复制偏移量最大的（数据最新）；4）都相同选 runid 最小的。选好后，领导者对新主节点执行 `REPLICAOF NO ONE`，对其他从节点执行 `REPLICAOF <新主节点>`。**通知客户端**：Sentinel 维护一份主节点地址的权威信息，客户端连接 Sentinel 查询主节点地址，故障转移后 Sentinel 会更新这个信息，客户端通过订阅 Sentinel 的频道或定期查询来感知切换。**配置中心**：Sentinel 会将集群拓扑信息持久化，新加入的 Sentinel 可以快速获取。

#### 例子

**Sentinel 配置（sentinel.conf）：**

```conf

# 主节点密码

# 主观下线判定时间（毫秒）
sentinel down-after-milliseconds mymaster 30000

# 故障转移时同时向新主节点同步的从节点数
sentinel parallel-syncs mymaster 1

# 故障转移超时时间（毫秒）
sentinel failover-timeout mymaster 180000

# Sentinel自身端口
port 26379

# 后台运行
daemonize yes
```

#### 总结

- Sentinel 在主从复制基础上实现自动故障转移，是 Redis 官方高可用方案
- 通过主观下线（SDOWN）+ 客观下线（ODOWN）两阶段判定主节点故障
- 领导者 Sentinel 执行故障转移，按优先级、偏移量、runid 选新主节点
- 客户端通过 Sentinel 感知主节点地址，故障转移后自动切换
- **注意事项**：Sentinel 至少部署 3 个奇数个，避免脑裂；`quorum` 建议设为 Sentinel 总数的一半加一；`down-after-milliseconds` 不宜过短，避免网络抖动误判；故障转移期间会有短暂不可用（秒级）；客户端必须使用 Sentinel API 而非直连主节点

### 第 23 讲：Cluster 集群

#### 概念

Redis Cluster 是 Redis 官方的**分布式集群**方案，它通过**数据分片（sharding）** 将数据分散到多个节点，突破单机内存和性能限制，同时提供自动故障转移能力。Cluster 采用 **16384 个哈希槽（slot）** 的分片方案，每个节点负责一部分槽，key 通过 CRC16 算法计算哈希值后对 16384 取模，决定存储在哪个节点。Cluster 支持在线扩缩容（迁移槽）和多副本，是大规模 Redis 部署的首选方案。与 Sentinel 不同，Cluster 既是高可用方案也是水平扩展方案，但 Cluster **不支持跨槽的多键操作**（除非使用 Hash Tag），且客户端需要感知集群拓扑。

#### 原理

Redis Cluster 的核心设计包括**数据分片**、**节点通信**、**故障转移**三部分。**数据分片**：Cluster 有 16384 个槽，每个节点负责一部分。key 的槽位计算：`slot = CRC16(key) mod 16384`。客户端可以向任意节点发送命令，如果 key 不在该节点负责的槽位，节点返回 `MOVED <slot> <ip:port>` 重定向，客户端缓存路由后直接访问正确节点。**Hash Tag**：如果多个 key 需要在同一节点（支持多键操作），可以用 `{}` 包裹相同部分，如 `user:{1001}:name` 和 `user:{1001}:age` 都用 `1001` 计算槽位，保证在同一节点。**节点通信**：Cluster 采用 **Gossip 协议**，每个节点每秒向几个随机节点发送 PING 消息，携带自己已知的集群信息，通过这种方式集群拓扑最终一致。Gossip 消息包括 PING/PONG（心跳）、MEET（加入集群）、FAIL（标记节点下线）。**故障转移**：当节点 A 发现节点 B 疑似下线（PING 超时），标记为 PFAIL（主观下线），通过 Gossip 传播。当半数以上主节点都标记 B 为 PFAIL，则升级为 FAIL（客观下线）。B 的从节点检测到后发起选举（基于 Raft），获得多数主节点投票后成为新主节点，接管 B 的槽位。**扩缩容**：扩容时新节点加入集群，通过 `CLUSTER SETSLOT` 迁移部分槽到新节点，迁移过程中支持在线服务；缩容则反向操作。

## 第九章 缓存设计实战

### 第 24 讲：缓存三大问题（穿透、击穿、雪崩）

#### 概念

缓存穿透、缓存击穿、缓存雪崩是缓存系统设计中最经典的三大问题，它们描述了在高并发场景下缓存失效导致的数据库压力骤增现象。**缓存穿透**是指查询一个**根本不存在**的数据，由于缓存和数据库都没有，每次请求都打到数据库，可能被恶意利用（如攻击者用不存在的 ID 大量请求）。**缓存击穿**是指一个**热点 key** 突然过期（或被删除），瞬间大量请求同时打到数据库，造成压力骤增。**缓存雪崩**是指**大量 key 同时过期**或 Redis 宕机，导致大量请求同时打到数据库，可能压垮数据库。理解三者的区别和解决方案，是缓存系统设计的核心能力。

#### 原理

**缓存穿透**的根因是"查询不存在的数据"——缓存无法缓存"不存在"的结果（除非主动缓存空值），导致每次请求都查数据库。解决方案有三种：1）**缓存空值**——查询不到也缓存一个空值（如 null），设置较短 TTL（如 60 秒），避免同一请求反复查库；2）**布隆过滤器**——在缓存前加一层布隆过滤器，存储所有可能存在的 key，请求先过布隆过滤器，不存在则直接返回，不查缓存和数据库；3）**接口限流/参数校验**——对非法参数（如负数 ID）直接拦截。**缓存击穿**的根因是"热点 key 过期瞬间并发"——多个请求同时发现缓存失效，同时查库并回写缓存。解决方案：1）**互斥锁（Mutex）**——缓存失效时，只让一个请求查库并回写缓存，其他请求等待或重试；2）**热点 key 永不过期**——逻辑过期，后台异步更新；3）**提前刷新**——监控热点 key 的 TTL，快过期时主动刷新。**缓存雪崩**的根因是"大量 key 同时过期"或"Redis 宕机"。解决方案：1）**TTL 随机化**——在基础 TTL 上加随机值（如 30 分钟 ± 5 分钟），避免同时过期；2）**多级缓存**——本地缓存 + Redis 缓存，Redis 宕机时本地缓存兜底；3）**熔断降级**——数据库压力过大时熔断，返回降级数据；4）**Redis 高可用**——用 Sentinel/Cluster 避免 Redis 宕机。

#### 例子

**缓存穿透解决方案：**

**缓存击穿解决方案（互斥锁）：**

```python
import redis
import json
import time
import threading

r = redis.Redis()

def get_hot_key_with_mutex(key, db_loader, ttl=3600, lock_timeout=10):
    """使用互斥锁防止缓存击穿"""
    value = r.get(key)
    if value is not None:
        return json.loads(value)

    # 缓存未命中，尝试获取互斥锁
    lock_key = f"lock:{key}"
    lock_value = str(time.time())

    # SET NX EX 获取锁
    if r.set(lock_key, lock_value, nx=True, ex=lock_timeout):
        try:
            # 再次检查缓存（双重检查）
            value = r.get(key)
            if value is not None:
                return json.loads(value)

            # 查数据库
            data = db_loader()
            r.setex(key, ttl, json.dumps(data))
            return data
        finally:
            # 释放锁（用Lua保证原子性）
            release_script = """
            if redis.call('get', KEYS[1]) == ARGV[1] then
                return redis.call('del', KEYS[1])
            else
                return 0
            end
            """
            r.eval(release_script, 1, lock_key, lock_value)
    else:
        # 未获取到锁，短暂等待后重试
        time.sleep(0.1)
        return get_hot_key_with_mutex(key, db_loader, ttl, lock_timeout)

# 使用示例：获取热门商品详情
def get_hot_product(product_id):
    return get_hot_key_with_mutex(
        f"product:{product_id}",
        lambda: db_query_product(product_id),
        ttl=3600
    )
```

```python
import json
import random

# 方案2：多级缓存（本地缓存 + Redis）
import threading
from collections import OrderedDict

class LocalCache:
    """简单的LRU本地缓存"""
    def __init__(self, max_size=1000):
        self.cache = OrderedDict()
        self.max_size = max_size
        self.lock = threading.Lock()

    def get(self, key):
        with self.lock:
            if key in self.cache:
                self.cache.move_to_end(key)
                return self.cache[key]
            return None

    def set(self, key, value, ttl=60):
        with self.lock:
            self.cache[key] = value
            self.cache.move_to_end(key)
            if len(self.cache) > self.max_size:
                self.cache.popitem(last=False)

local_cache = LocalCache()

def get_with_multi_level(key, db_loader):
    """多级缓存：本地缓存 -> Redis -> 数据库"""
    # 1. 查本地缓存
    value = local_cache.get(key)
    if value is not None:
        return value

    # 2. 查Redis
    value = r.get(key)
    if value is not None:
        data = json.loads(value)
        local_cache.set(key, data)  # 回填本地缓存
        return data

    # 3. 查数据库
    data = db_loader()
    if data:
        cache_with_random_ttl(key, data)
        local_cache.set(key, data)
    return data

# 方案3：熔断降级
class CircuitBreaker:
    """简单的熔断器"""
    def __init__(self, failure_threshold=10, recovery_timeout=60):
        self.failure_count = 0
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.last_failure_time = 0
        self.state = 'closed'  # closed, open, half_open

    def call(self, func, *args, **kwargs):
        if self.state == 'open':
            if time.time() - self.last_failure_time > self.recovery_timeout:
                self.state = 'half_open'
            else:
                return self.fallback()

        try:
            result = func(*args, **kwargs)
            self.failure_count = 0
            self.state = 'closed'
            return result
        except Exception as e:
            self.failure_count += 1
            self.last_failure_time = time.time()
            if self.failure_count >= self.failure_threshold:
                self.state = 'open'
            return self.fallback()

    def fallback(self):
        return {"error": "服务降级", "data": None}

breaker = CircuitBreaker()

def get_product_safe(product_id):
    return breaker.call(
        lambda: get_with_multi_level(f"product:{product_id}", lambda: db_query_product(product_id))
    )
```

#### 总结

- **缓存穿透**：查询不存在的数据，方案：缓存空值、布隆过滤器、参数校验
- **缓存击穿**：热点 key 过期瞬间并发，方案：互斥锁、永不过期、提前刷新
- **缓存雪崩**：大量 key 同时过期或 Redis 宕机，方案：TTL 随机化、多级缓存、熔断降级、高可用
- 三者区别：穿透是"数据不存在"，击穿是"一个热点 key 过期"，雪崩是"大量 key 过期"
- **注意事项**：缓存空值要设短 TTL，避免占用过多内存；布隆过滤器有误判率，不能删除元素；互斥锁要设超时，避免死锁；多级缓存注意本地缓存与 Redis 的一致性

### 第 25 讲：缓存与数据库一致性

#### 概念

在缓存 + 数据库的架构中，**数据一致性**是一个核心挑战——如何保证缓存中的数据与数据库中的数据保持一致。由于缓存和数据库是两个独立的存储，更新操作无法做到原子性，必然存在短暂的不一致窗口。根据业务对一致性的要求，可以选择不同的策略：**Cache Aside（旁路缓存）** 是最常用的模式，**Read/Write Through** 和 **Write Behind** 是更高级的模式。理解各种一致性策略的原理和适用场景，是设计可靠缓存系统的关键。需要明确的是，**强一致性**在缓存架构中几乎无法实现，通常追求的是**最终一致性**。

#### 原理

**Cache Aside（旁路缓存）** 是最经典的缓存模式：读时先查缓存，命中则返回，未命中查数据库并回写缓存；写时**先更新数据库，再删除缓存**（而非更新缓存）。为什么是删除而不是更新缓存？因为更新缓存可能涉及复杂计算，且并发更新可能导致数据不一致（线程 A 先更新 DB 后更新缓存，线程 B 后更新 DB 先更新缓存，缓存就是旧数据）。删除缓存是幂等的，下次读时自然回写最新值。**先更新 DB 再删除缓存**的问题：如果删除缓存失败，缓存中是旧数据。解决方案：**延迟双删**——先删缓存，更新 DB，延迟一段时间再删缓存。**先删缓存再更新 DB**的问题：线程 A 删除缓存后、更新 DB 前，线程 B 读取缓存未命中，查 DB（旧值）并回写缓存，缓存就是旧数据。解决方案也是延迟双删。**Read/Write Through**：客户端只与缓存交互，缓存组件负责同步读写数据库，对客户端透明，但实现复杂。**Write Behind（Write Back）**：写操作只写缓存，异步批量刷入数据库，性能最高但可能丢数据，适合允许丢失的场景。**最终一致性保障**：对于强一致性要求高的场景，可以借助**消息队列**或**Binlog 订阅**（如 Canal）异步同步缓存，保证最终一致。

#### 例子

**Cache Aside 模式（推荐）：**

```python
import redis
import json

r = redis.Redis()

def cache_aside_get(key, db_loader, ttl=3600):
    """读：先缓存，未命中查DB并回写"""
    value = r.get(key)
    if value is not None:
        return json.loads(value)

    data = db_loader()
    if data is not None:
        r.setex(key, ttl, json.dumps(data))
    return data

def cache_aside_set(key, value, db_saver):
    """写：先更新DB，再删除缓存"""
    db_saver(value)          # 1. 更新数据库
    r.delete(key)            # 2. 删除缓存

# 使用示例
def get_user(user_id):
    return cache_aside_get(
        f"user:{user_id}",
        lambda: db_query_user(user_id)
    )

def update_user(user_id, data):
    cache_aside_set(
        f"user:{user_id}",
        data,
        lambda d: db_update_user(user_id, d)
    )
```

**延迟双删（解决并发不一致）：**

```python
import redis
import json
import threading
import time

r = redis.Redis()

def update_with_double_delete(key, value, db_saver, delay=1.0):
    """延迟双删：先删缓存 -> 更新DB -> 延迟再删缓存"""
    # 1. 先删除缓存
    r.delete(key)

    # 2. 更新数据库
    db_saver(value)

    # 3. 延迟再次删除（异步，不阻塞主流程）
    def delayed_delete():
        time.sleep(delay)
        r.delete(key)

    threading.Thread(target=delayed_delete, daemon=True).start()

# 使用示例
def update_product(product_id, data):
    update_with_double_delete(
        f"product:{product_id}",
        data,
        lambda d: db_update_product(product_id, d),
        delay=1.0  # 延迟1秒再删
    )
```

**基于消息队列的最终一致性：**

```python
import redis
import json
import pika  # RabbitMQ客户端

r = redis.Redis()

# 写操作：更新DB后发送消息
def update_with_mq(key, value, db_saver):
    db_saver(value)
    # 发送缓存失效消息到MQ
    connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
    channel = connection.channel()
    channel.queue_declare(queue='cache_invalidation')
    channel.basic_publish(
        exchange='',
        routing_key='cache_invalidation',
        body=json.dumps({'action': 'delete', 'key': key})
    )
    connection.close()

# 消费者：监听消息，删除缓存
def cache_invalidation_consumer():
    connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
    channel = connection.channel()
    channel.queue_declare(queue='cache_invalidation')

    def callback(ch, method, properties, body):
        msg = json.loads(body)
        if msg['action'] == 'delete':
            r.delete(msg['key'])
        ch.basic_ack(delivery_tag=method.delivery_tag)

    channel.basic_consume(queue='cache_invalidation', on_message_callback=callback)
    channel.start_consuming()
```

**一致性策略对比：**

| 策略 | 一致性 | 性能 | 复杂度 | 适用场景 |
|------|--------|------|--------|---------|
| Cache Aside（先DB后删缓存） | 最终一致 | 高 | 低 | 大多数场景（推荐） |
| 延迟双删 | 较高 | 中 | 中 | 并发较高的场景 |
| 消息队列 | 高 | 中 | 高 | 强一致性要求 |
| Binlog订阅 | 高 | 高 | 高 | 零侵入，大型系统 |
| Write Behind | 弱 | 最高 | 中 | 允许丢数据的场景 |

#### 总结

- Cache Aside 是最常用的缓存模式：读穿透，写时先更新 DB 再删除缓存
- 删除缓存优于更新缓存（幂等、避免并发不一致）
- 延迟双删解决"先删缓存再更新 DB"的并发问题
- 消息队列/Binlog 订阅实现最终一致性，适合强一致性要求
- **注意事项**：缓存架构追求最终一致性，无法做到强一致；延迟双删的延迟时间要大于一次读请求的耗时；Binlog 订阅对业务零侵入但部署复杂；Write Behind 性能最高但可能丢数据，慎用
