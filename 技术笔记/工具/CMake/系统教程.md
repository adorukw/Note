本章带你理解 CMake 在构建工具生态中的定位，亲手完成第一个 CMake 项目的构建，并掌握 CMake 脚本语言的基础语法。这是后续所有章节的地基。

## 第1讲：CMake 是什么 —— 构建系统的演进与 CMake 的定位

### 概念

CMake 是一个**跨平台的构建系统生成器（build-system generator）**。它本身并不直接编译代码，而是读取开发者编写的 `CMakeLists.txt` 配置文件，生成对应平台的原生构建系统文件（如 Linux 上的 Makefile、Windows 上的 Visual Studio 工程、macOS 上的 Xcode 工程），再由这些原生构建系统调用编译器完成实际编译。

需要特别强调的是"CMake 是生成器而非构建器"这一关键定位。CMake 把"项目该如何构建"这一抽象描述，翻译成具体平台上的具体构建指令。这种解耦使得同一份 `CMakeLists.txt` 可以在 Windows、Linux、macOS 上无修改地使用，这是 CMake 最大的价值。

### 原理

要理解 CMake 为什么存在，需要回顾 C/C++ 构建工具的演进历史：

1. **手工编译时代**：早期开发者直接在命令行敲 `gcc main.c utils.c -o app`。当源文件数量增加到几十个时，每次重新编译全部文件既慢又容易出错。

2. **Make/Makefile 时代**：Make 工具通过 Makefile 描述文件之间的依赖关系，只重新编译修改过的文件。但 Makefile 与平台、编译器强耦合，写一份能在 Linux 上用的 Makefile 到 Windows 上完全不能用。

3. **跨平台构建需求**：随着开源软件跨平台分发成为常态，开发者迫切需要一种"写一次配置，到处构建"的工具。Configure 脚本（autoconf 系）是早期方案，但语法晦涩、Windows 支持差。

4. **CMake 的诞生**：1999 年 Kitware 公司为支持可视化工具包 VTK 的跨平台开发而创建 CMake。其核心思想是：用一种平台无关的描述语言（CMakeLists.txt）定义项目结构，由 CMake 翻译为各平台的原生构建文件。

CMake 的工作流程分为两个阶段：

- **配置阶段（Configure）**：CMake 解析 `CMakeLists.txt`，执行其中的命令，探测系统环境（编译器是否存在、第三方库在哪里），最终在内存中构建出完整的项目依赖图，并生成原生构建文件。
- **生成阶段（Generate）**：将依赖图翻译为具体平台的构建文件。配置与生成通常合在一起执行。

之后由原生构建工具（make、ninja、msbuild 等）执行真正的编译链接。

### 例子

一个最简单的项目结构：

```
my_project/
├── CMakeLists.txt
└── main.cpp
```

`CMakeLists.txt` 内容：

```cmake
cmake_minimum_required(VERSION 3.15)
project(HelloApp)

add_executable(hello main.cpp)
```

构建流程（Linux + Make）：

```bash
mkdir build && cd build       # 创建并进入构建目录（out-of-source 构建）
cmake ..                      # 配置 + 生成 Makefile
make                          # 实际编译
./hello                       # 运行
```

执行 `cmake ..` 时你会看到 CMake 输出一系列检查信息：编译器检测、C++ 标准支持检测等。最后生成 `Makefile`、`CMakeCache.txt` 等文件。`make` 命令则真正调用 g++ 编译 `main.cpp` 生成可执行文件 `hello`。

### 总结

- CMake 是**构建系统生成器**，不是构建器本身，它生成原生构建文件再由原生工具完成编译。
- CMake 解决的核心问题是**跨平台构建描述**：一份 `CMakeLists.txt` 适配多平台。
- 工作流程分两步：**配置阶段**解析脚本、探测环境；**生成阶段**输出原生构建文件。
- 始终使用 **out-of-source 构建**（在独立的 build 目录中构建），避免污染源码树。
- `cmake_minimum_required` 和 `project()` 是每个 CMakeLists.txt 的必备开头。

## 第2讲：第一个 CMake 项目 —— 最小化配置与构建流程

### 概念

本讲通过一个完整的最小项目，让你亲手走通 CMake 的"编写 → 配置 → 生成 → 编译 → 运行"全流程。我们将理解 `cmake_minimum_required`、`project`、`add_executable` 这三个最基础命令的含义，并掌握命令行构建的标准操作。

### 原理

一个最小的 CMake 项目至少需要三个要素：

1. **版本声明**：`cmake_minimum_required(VERSION x.y)` 告诉 CMake 该项目需要的最低版本。CMake 在不同版本间有行为差异，声明版本可以锁定行为策略（POLICY），保证脚本在新版 CMake 上行为一致。建议设为 3.15 以上以使用现代特性。

2. **项目声明**：`project(Name VERSION x.y.z LANGUAGES CXX C)` 声明项目名称、版本、使用的编程语言。它会设置一批变量：`PROJECT_NAME`、`PROJECT_VERSION`、`CMAKE_CXX_STANDARD`（如果未单独设置）等。`LANGUAGES` 参数决定 CMake 启用哪些编译器检测，省略时默认启用 C 和 CXX。

3. **构建目标**：`add_executable(name source...)` 定义一个可执行文件目标，告诉 CMake 用哪些源文件编译出名为 `name` 的程序。目标名通常也是输出文件名（Windows 上会自动加 `.exe`）。

构建流程的命令行操作遵循"out-of-source"原则：在源码目录之外创建一个 build 目录，所有生成的中间文件、可执行文件都放在 build 目录里，保持源码目录干净。这种做法的好处是：可以随时删除 build 目录重建；可以为不同编译器/配置创建多个 build 目录并行存在；版本控制系统只需忽略 build 目录即可。

### 例子

项目结构：

```
hello/
├── CMakeLists.txt
└── main.cpp
```

`main.cpp`：

```cpp
#include <iostream>

int main() {
    std::cout << "Hello, CMake!" << std::endl;
    return 0;
}
```

`CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.15)
project(HelloApp VERSION 1.0.0 LANGUAGES CXX)

# 设置 C++ 标准
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

add_executable(hello main.cpp)
```

完整构建流程：

```bash
# 1. 进入项目目录
cd hello

# 2. 创建并进入构建目录
mkdir build
cd build

# 3. 配置 + 生成（指向上一级目录的 CMakeLists.txt）
cmake ..
# 输出示例：
# -- The CXX compiler identification is GNU 11.4.0
# -- Detecting CXX compiler features
# -- Detecting CXX compiler features - done
# -- Configuring done
# -- Generating done
# -- Build files have been written to: /path/to/build

# 4. 实际编译
cmake --build .
# 或者直接 make（Linux 上）

# 5. 运行
./hello
# 输出：Hello, CMake!
```

`CMAKE_CXX_STANDARD` 三个变量的含义：
- `CMAKE_CXX_STANDARD 17`：使用 C++17 标准。
- `CMAKE_CXX_STANDARD_REQUIRED ON`：如果编译器不支持 C++17 则报错而非降级。
- `CMAKE_CXX_EXTENSIONS OFF`：禁用编译器扩展（如 GNU 扩展），使用纯标准 C++，保证可移植性。

### 总结

- 最小 CMake 项目三件套：`cmake_minimum_required` + `project` + `add_executable`。
- 标准构建流程：`mkdir build && cd build && cmake .. && cmake --build .`。
- `cmake --build .` 是跨平台编译命令，会自动调用对应平台的原生构建工具。
- 设置 C++ 标准三件套：`CMAKE_CXX_STANDARD` + `CMAKE_CXX_STANDARD_REQUIRED` + `CMAKE_CXX_EXTENSIONS`。
- 始终在独立 build 目录构建，保持源码树干净，便于多配置共存。

## 第3讲：CMake 语法基础 —— 变量、命令与注释

### 概念

CMake 有自己的脚本语言，用来编写 `CMakeLists.txt` 和 `.cmake` 模块。其语法核心三要素是：**注释**、**命令调用**、**变量**。掌握这三者，才能读懂和编写任何 CMake 脚本。CMake 语言是大小写不敏感的（命令名），但变量名大小写敏感，这是初学者常踩的坑。

### 原理

**注释**：以 `#` 开头到行尾为单行注释。CMake 3.0+ 支持块注释，用 `#[[ ]]` 包裹。

**命令调用**：CMake 的所有操作都通过命令完成，如 `set()`、`message()`、`add_executable()`。命令名大小写不敏感（`SET` 和 `set` 等价），但社区约定全部小写。命令的参数用空格分隔，可选参数用关键字标记（如 `add_executable(hello main.cpp)` 中 `hello` 和 `main.cpp` 都是位置参数）。

**变量**：CMake 变量本质是字符串（或字符串列表，用分号分隔）。变量的取值与作用域是 CMake 最容易出错的地方：

- **普通变量**：用 `set(VAR value)` 定义，作用域是当前的目录/函数范围。子目录会继承父目录的变量副本，但子目录的修改不会回传到父目录（值传递语义）。
- **缓存变量**：用 `set(VAR value CACHE TYPE "doc")` 定义，存储在 `CMakeCache.txt` 中，跨配置保持，用户可通过 `cmake-gui` 或 `-D` 命令行修改。
- **环境变量**：通过 `$ENV{VAR}` 读写。

变量引用用 `${VAR}` 语法。未定义的变量引用结果为空字符串（不报错），这是 CMake 的"宽容"特性，但也容易隐藏 bug。

CMake 中"真值"判断：`ON`、`TRUE`、`1`、非零数字、非空非零字符串为真；`OFF`、`FALSE`、`0`、`NO`、`""`、`IGNORE`、`NOTFOUND`、以 `-NOTFOUND` 结尾的字符串为假。

### 例子

```cmake
# 这是单行注释

#[[
这是块注释
可以跨多行
CMake 3.0+ 支持
]]

# ---------- 变量操作 ----------
set(MY_NAME "CMake")           # 普通变量
set(NUMBERS 1 2 3 4 5)         # 列表变量，等价于 "1;2;3;4;5"
set(EMPTY_VAR "")              # 空字符串

message(STATUS "My name is ${MY_NAME}")
message(STATUS "Numbers: ${NUMBERS}")        # 输出：1;2;3;4;5

# 列表操作
list(APPEND NUMBERS 6 7)       # 追加元素
message(STATUS "After append: ${NUMBERS}")   # 1;2;3;4;5;6;7

list(REMOVE_AT NUMBERS 0)      # 删除第 0 个元素
message(STATUS "After remove: ${NUMBERS}")   # 2;3;4;5;6;7

list(LENGTH NUMBERS len)
message(STATUS "List length: ${len}")

# ---------- 真值判断 ----------
set(FLAG ON)
if(FLAG)
    message(STATUS "FLAG is true")
endif()

set(COUNT 0)
if(NOT COUNT)
    message(STATUS "COUNT is false (zero)")
endif()

# ---------- 缓存变量 ----------
set(BUILD_TESTS OFF CACHE BOOL "Enable unit tests")
# 用户可通过 cmake -DBUILD_TESTS=ON .. 修改

# ---------- 环境变量 ----------
message(STATUS "PATH = $ENV{PATH}")

# ---------- 命令调用 ----------
add_executable(app main.cpp)   # 位置参数
target_compile_definitions(app PRIVATE DEBUG=1)  # 关键字参数
```

运行结果（用 `cmake -P script.cmake` 可直接执行 CMake 脚本）：

```
-- My name is CMake
-- Numbers: 1;2;3;4;5
-- After append: 1;2;3;4;5;6;7
-- After remove: 2;3;4;5;6;7
-- List length: 6
-- FLAG is true
-- COUNT is false (zero)
-- PATH = /usr/bin:...
```

### 总结

- CMake 语法三要素：注释（`#` 和 `#[[ ]]`）、命令调用（小写约定）、变量（`${VAR}` 引用）。
- 命令名大小写不敏感，变量名大小写敏感——这是常见坑。
- 变量分三类：普通变量（目录/函数作用域）、缓存变量（持久化）、环境变量（`$ENV{}`）。
- 变量本质是字符串，"列表"是用分号分隔的字符串。
- 未定义变量引用返回空字符串，不报错——既灵活又危险，建议用 `if(DEFINED VAR)` 显式检查。
- 真值判断规则需牢记：`ON/TRUE/1/非零` 为真，`OFF/FALSE/0/""/NOTFOUND` 为假。

# 第二章：目标与依赖管理

CMake 的核心抽象是"目标（target）"。本章讲解如何定义可执行文件和库目标，如何通过目标属性系统管理头文件路径和链接关系，以及如何组织多文件项目。这是现代 CMake 的精髓所在。

---

## 第4讲：构建目标 —— add_executable 与 add_library

### 概念

**目标（target）**是 CMake 中代表一个构建产物的抽象。一个目标可以是一个可执行文件、一个静态库、一个动态库。CMake 通过 `add_executable()` 和 `add_library()` 命令定义目标，后续所有关于编译选项、链接关系、安装规则的配置都围绕目标展开。现代 CMake 的核心理念就是"以目标为中心"——一切配置都附加在目标上，而非全局变量。

### 原理

**可执行文件目标**：`add_executable(name source1 source2 ...)` 定义一个名为 `name` 的可执行文件，由列出的源文件编译链接而成。目标名通常与输出文件名一致（Windows 上自动加 `.exe`，Linux/macOS 上无后缀）。

**库目标**有三种主要类型：

- **静态库（STATIC）**：编译时被链接进可执行文件，产物是 `.a`（Linux/macOS）或 `.lib`（Windows）。运行时不依赖外部库文件，但体积大、升级需重新链接。
- **动态库（SHARED）**：运行时动态加载，产物是 `.so`（Linux）、`.dylib`（macOS）、`.dll`（Windows）。多个程序可共享一份内存映像，便于升级，但部署需带上库文件。
- **模块库（MODULE）**：类似动态库，但设计为运行时通过 `dlopen`/`LoadLibrary` 显式加载，不参与链接。常用于插件系统。

此外还有 **OBJECT 库**：一种特殊的"中间产物"目标，只编译为目标文件（`.o`/`.obj`）不打包成库，可被其他目标"引用"以避免重复编译。这是 CMake 3.12+ 的现代特性。

库类型的选取原则：核心通用代码用静态库便于复用；需要独立升级或被多进程共享的代码用动态库；插件机制用模块库；只想避免重复编译又不想真发布库的，用 OBJECT 库。

### 例子

项目结构：

```
math_app/
├── CMakeLists.txt
├── src/
│   ├── main.cpp
│   ├── math_lib.cpp
│   └── math_lib.h
└── plugins/
    └── sqrt_plugin.cpp
```

`CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.15)
project(MathApp LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 17)

# 1. 静态库：核心数学函数
add_library(math_static STATIC src/math_lib.cpp)
target_include_directories(math_static PUBLIC src)

# 2. 动态库：同样的代码，构建为动态库
add_library(math_shared SHARED src/math_lib.cpp)
target_include_directories(math_shared PUBLIC src)

# 3. OBJECT 库：避免重复编译
add_library(math_objects OBJECT src/math_lib.cpp)

# 4. 模块库：插件
add_library(sqrt_plugin MODULE plugins/sqrt_plugin.cpp)

# 5. 可执行文件：链接静态库
add_executable(app_static src/main.cpp)
target_link_libraries(app_static PRIVATE math_static)

# 6. 可执行文件：链接动态库
add_executable(app_shared src/main.cpp)
target_link_libraries(app_shared PRIVATE math_shared)
```

构建后产物（Linux）：

```
build/
├── libmath_static.a          # 静态库
├── libmath_shared.so         # 动态库
├── app_static                # 静态链接的可执行文件
├── app_shared                # 动态链接的可执行文件
└── sqrt_plugin.so            # 模块库（插件）
```

`src/main.cpp`：

```cpp
#include "math_lib.h"
#include <iostream>

int main() {
    std::cout << "add(2, 3) = " << add(2, 3) << std::endl;
    return 0;
}
```

### 总结

- 目标是 CMake 的核心抽象，分可执行文件、静态库、动态库、模块库、OBJECT 库五种。
- `add_executable(name sources...)` 定义可执行文件目标。
- `add_library(name STATIC|SHARED|MODULE|OBJECT sources...)` 定义库目标。
- 静态库编译进可执行文件，动态库运行时加载，模块库用于插件，OBJECT 库用于避免重复编译。
- 目标名是引用目标的唯一标识，后续所有配置通过目标名附加。
- 现代 CMake 推荐显式声明库类型（STATIC/SHARED），不依赖全局 `BUILD_SHARED_LIBS` 变量。

## 第5讲：目标属性系统 —— include 目录与链接库

### 概念

现代 CMake（3.x 之后）的核心范式是**基于目标的属性传播**。每个目标拥有一组属性（如 include 目录、链接库、编译选项），这些属性通过 `PUBLIC`、`PRIVATE`、`INTERFACE` 三种可见性关键字决定是否传播给依赖该目标的其他目标。这一机制取代了旧式全局变量（`include_directories`、`link_directories`）的做法，让依赖关系清晰、可复用、可组合。

### 原理

三个可见性关键字的语义：

- **PRIVATE**：属性只用于编译当前目标本身，不传播给依赖者。例如某个库内部使用的头文件路径。
- **INTERFACE**：属性不用于编译当前目标本身（比如纯头文件库没有自己的源文件），但传播给依赖者。
- **PUBLIC**：既用于编译当前目标，也传播给依赖者。等价于 PRIVATE + INTERFACE。

直观理解：`PUBLIC` = "我自己用，依赖我的人也用"；`PRIVATE` = "只我自己用"；`INTERFACE` = "我自己不用，但依赖我的人要用"。

关键命令：

- `target_include_directories(target VISIBILITY dirs...)`：设置头文件搜索路径。
- `target_link_libraries(target VISIBILITY libs...)`：设置链接的库（可以是其他 CMake 目标名，也可以是系统库）。
- `target_compile_definitions(target VISIBILITY defs...)`：设置预处理宏。
- `target_compile_options(target VISIBILITY opts...)`：设置编译选项。
- `target_compile_features(target VISIBILITY features...)`：设置需要的 C++ 特性。

**传播机制原理**：当目标 B 通过 `target_link_libraries(B PRIVATE A)` 链接 A 时，CMake 会把 A 的 `INTERFACE_INCLUDE_DIRECTORIES` 属性合并到 B 的 `INCLUDE_DIRECTORIES` 中。这就是"传递性"——A 的 PUBLIC include 会通过 INTERFACE 属性传给 B。这种传递可以链式发生：A→B→C，C 也能拿到 A 的 PUBLIC 头文件路径。

旧式全局命令（`include_directories`、`link_directories`、`add_definitions`）会污染整个项目，难以追踪依赖，已被现代 CMake 弃用，应避免使用。

### 例子

项目结构：

```
graphics_app/
├── CMakeLists.txt
├── math/
│   ├── CMakeLists.txt
│   ├── math.h
│   └── math.cpp
├── graphics/
│   ├── CMakeLists.txt
│   ├── renderer.h
│   └── renderer.cpp
└── app/
    └── main.cpp
```

`math/CMakeLists.txt`：

```cmake
# math 库：内部使用 Eigen（PRIVATE），对外暴露 math.h（PUBLIC）
add_library(math STATIC math.cpp)

# math.h 是公开接口，依赖者也需要这个路径
target_include_directories(math PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})

# Eigen 只在 math.cpp 内部使用，依赖者不需要
target_include_directories(math PRIVATE /opt/eigen/include)
target_link_libraries(math PRIVATE eigen)  # 假设 eigen 是另一个目标
```

`graphics/CMakeLists.txt`：

```cmake
# graphics 库依赖 math 库
add_library(graphics STATIC renderer.cpp)

# renderer.h 公开，依赖者需要
target_include_directories(graphics PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})

# graphics 内部用 math 库，且 renderer.h 里 #include "math.h"
# 所以 math 的 include 路径要传播给 graphics 的依赖者 → 用 PUBLIC
target_link_libraries(graphics PUBLIC math)
```

`app/main.cpp`：

```cpp
#include "renderer.h"   // 来自 graphics 的 PUBLIC include
#include "math.h"       // 通过 graphics → math 的传递性 PUBLIC 拿到
// 但 Eigen 的路径不会传过来（math 的 Eigen 是 PRIVATE）

int main() { /* ... */ }
```

根 `CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.15)
project(GraphicsApp LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 17)

add_subdirectory(math)
add_subdirectory(graphics)

add_executable(app app/main.cpp)
target_link_libraries(app PRIVATE graphics)
# app 自动获得 graphics 和 math 的 PUBLIC include 路径
# 但不会获得 math 的 PRIVATE Eigen 路径
```

### 总结

- 现代 CMake 核心范式：**基于目标的属性传播**，弃用全局变量式配置。
- 三个可见性关键字：`PRIVATE`（只自己用）、`INTERFACE`（只传播）、`PUBLIC`（自己用 + 传播）。
- `target_link_libraries(target PUBLIC dep)` 会让 `dep` 的 INTERFACE 属性传递给 `target` 的依赖者，形成传递链。
- 判断 PUBLIC 还是 PRIVATE 的关键问题："依赖我的目标是否也需要这个属性？"——是则 PUBLIC，否则 PRIVATE。
- 纯头文件库（header-only）用 INTERFACE 库：`add_library(mylib INTERFACE)`，所有属性都用 INTERFACE。
- 避免使用 `include_directories`、`link_directories`、`add_definitions` 等全局命令。

## 第6讲：头文件与源文件组织

### 概念

实际项目中源文件数量众多，需要合理组织目录结构和文件列表。本讲讲解如何用变量收集源文件、如何用 `file(GLOB)` 自动扫描（及其利弊）、如何组织头文件目录、如何处理多目录子项目。良好的文件组织是大型项目可维护性的基础。

### 原理

**显式列出源文件**是最推荐的做法。把源文件列表存入变量，便于复用和阅读：

```cmake
set(MATH_SOURCES
    src/add.cpp
    src/sub.cpp
    src/mul.cpp
    src/div.cpp
)
add_library(math STATIC ${MATH_SOURCES})
```

**`file(GLOB)` 自动扫描**是另一种方式，但有重要陷阱：

```cmake
file(GLOB SOURCES "src/*.cpp")
add_library(math STATIC ${SOURCES})
```

`GLOB` 在配置时扫描匹配的文件，但**当新增/删除源文件时不会自动重新配置**——CMake 不知道文件系统变了。这会导致"我加了新文件但编译没包含它"的诡异问题。解决方案是用 `CONFIGURE_DEPENDS` 选项：

```cmake
file(GLOB SOURCES CONFIGURE_DEPENDS "src/*.cpp")
```

加上 `CONFIGURE_DEPENDS` 后，CMake 会在每次构建时检查文件列表是否变化，变化则触发重新配置。但这会带来轻微的性能开销，且不是所有生成器都完美支持。

社区共识：**小项目可以用 GLOB，大型严肃项目推荐显式列出**。显式列表虽然冗长，但变更可追溯（在版本控制中可见），不会因文件名拼写错误静默失败。

**头文件目录组织**：推荐每个库一个独立的 include 目录，公开头文件放在 `include/` 下，内部头文件放在 `src/` 下。这样 PUBLIC include 只暴露 `include/`，PRIVATE include 暴露 `src/`，依赖关系清晰。

**多目录项目**：用 `add_subdirectory()` 引入子目录，每个子目录有自己的 `CMakeLists.txt`，形成树状结构。子目录的目标名建议加前缀避免冲突（如 `math::` 命名空间，通过 `add_library(math::core ALIAS math_core)` 创建别名）。

### 例子

推荐的项目结构：

```
my_lib/
├── CMakeLists.txt
├── include/              # 公开头文件（PUBLIC）
│   └── my_lib/
│       ├── core.h
│       └── utils.h
├── src/                  # 内部头文件 + 源文件（PRIVATE）
│   ├── internal.h
│ ├── core.cpp
│   └── utils.cpp
└── tests/
    └── test_core.cpp
```

`CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.15)
project(my_lib LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 17)

# 方式1：显式列出源文件（推荐用于严肃项目）
set(MY_LIB_SOURCES
    src/core.cpp
    src/utils.cpp
)

# 方式2：GLOB + CONFIGURE_DEPENDS（适合快速原型）
# file(GLOB MY_LIB_SOURCES CONFIGURE_DEPENDS "src/*.cpp")

add_library(my_lib STATIC ${MY_LIB_SOURCES})

# 公开头文件目录：PUBLIC，依赖者也能找到
target_include_directories(my_lib PUBLIC
    ${CMAKE_CURRENT_SOURCE_DIR}/include
)

# 内部头文件目录：PRIVATE，只自己用
target_include_directories(my_lib PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/src
)

# 创建带命名空间的别名，供其他目标引用
add_library(my::lib ALIAS my_lib)
```

使用别名的好处：在大型项目中，`my::lib` 比 `my_lib` 更清晰地表达"这是 my 项目下的 lib 目标"，避免与同名变量混淆。

源文件分组的辅助命令 `target_sources()`（CMake 3.1+）允许在子目录中向已存在的目标追加源文件：

```cmake
# 在 src/CMakeLists.txt 中
target_sources(my_lib PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/core.cpp
    ${CMAKE_CURRENT_SOURCE_DIR}/utils.cpp
)
```

### 总结

- 推荐显式列出源文件，便于版本控制追踪和排查问题。
- `file(GLOB)` 必须加 `CONFIGURE_DEPENDS` 才能感知文件增删，否则会"加了文件没编译"。
- 大型严肃项目用显式列表，快速原型可用 GLOB。
- 头文件目录分层：`include/` 放公开头文件（PUBLIC），`src/` 放内部头文件（PRIVATE）。
- 多目录项目用 `add_subdirectory()` 组织，每个子目录有自己的 CMakeLists.txt。
- 用 `add_library(name ALIAS real_target)` 创建带命名空间的别名，提升大型项目可读性。
- `target_sources()` 可在子目录中向已有目标追加源文件，避免巨型源文件列表。

## 第7讲：变量与缓存机制

### 概念

CMake 的变量系统是初学者最容易困惑的部分。它有三类变量：**普通变量**（normal variable）、**缓存变量**（cache variable）、**环境变量**（environment variable），三者作用域和生命周期完全不同。其中缓存变量是 CMake 独特的设计——它持久化在 `CMakeCache.txt` 文件中，跨多次配置保持值，是用户与项目交互的主要接口。理解缓存变量是掌握 CMake 配置流程的关键。

### 原理

**普通变量**：用 `set(VAR value)` 定义，存在于当前作用域（目录或函数）。CMake 的作用域是"目录式"的：进入子目录（`add_subdirectory`）或函数时，会创建新的作用域，继承父作用域的变量副本；子作用域的修改不会影响父作用域（值传递）。若要在子作用域修改父作用域变量，需用 `set(VAR value PARENT_SCOPE)`。

**缓存变量**：用 `set(VAR value CACHE TYPE "doc string" [FORCE])` 定义，存储在 `CMakeCache.txt` 中。关键特性：

1. **持久化**：跨多次 `cmake` 调用保持值，除非删除 build 目录或显式清除。
2. **首次设置生效**：默认情况下，缓存变量只在"未定义时"才被 `set` 赋值。如果用户通过 `-DVAR=value` 命令行设置了，CMakeLists.txt 中的 `set(... CACHE ...)` 不会覆盖它。要强制覆盖需加 `FORCE`。
3. **类型与文档**：`TYPE` 是 `BOOL`/`PATH`/`FILEPATH`/`STRING`/`INTERNAL`，影响 `cmake-gui` 和 `ccmake` 的展示方式。`INTERNAL` 类型对用户隐藏且总是 FORCE 设置。
4. **命令行修改**：`cmake -DVAR=value ..` 是用户覆盖缓存变量的标准方式。

**普通变量与缓存变量的优先级**：当两者同名时，`${VAR}` 引用的是普通变量（如果当前作用域有定义），否则才查缓存变量。这常导致"我改了缓存变量但脚本里读到旧值"的困惑——因为脚本里某处用 `set(VAR ...)` 创建了同名普通变量遮蔽了缓存变量。

**环境变量**：用 `set(ENV{VAR} value)` 设置，`$ENV{VAR}` 读取。环境变量在 CMake 进程及其子进程（编译器）中可见。

### 例子

```cmake
cmake_minimum_required(VERSION 3.15)
project(VarDemo)

# ---------- 普通变量 ----------
set(MY_VAR "hello")
message(STATUS "MY_VAR = ${MY_VAR}")   # hello

# ---------- 缓存变量 ----------
set(BUILD_TESTS OFF CACHE BOOL "Build unit tests")
# 第一次配置：BUILD_TESTS 被设为 OFF
# 用户运行 cmake -DBUILD_TESTS=ON .. 后：BUILD_TESTS 变为 ON
# 再次 cmake ..（不带 -D）：BUILD_TESTS 仍为 ON（缓存持久化）

message(STATUS "BUILD_TESTS = ${BUILD_TESTS}")

# ---------- 普通变量遮蔽缓存变量 ----------
set(OPTIMIZATION_LEVEL "O2" CACHE STRING "Optimization level")
set(OPTIMIZATION_LEVEL "O3")   # 创建同名普通变量，遮蔽缓存变量
message(STATUS "OPTIMIZATION_LEVEL = ${OPTIMIZATION_LEVEL}")  # O3（普通变量）
# 但缓存变量仍是 O2，可在 CMakeCache.txt 中看到

# 要读取缓存变量本身，用 $CACHE{VAR}（CMake 3.21+）
message(STATUS "Cache OPTIMIZATION_LEVEL = $CACHE{OPTIMIZATION_LEVEL}")

# ---------- 作用域演示 ----------
set(COUNTER 0)

function(increment)
    set(COUNTER 1)            # 只在函数内生效
    message(STATUS "Inside function: COUNTER = ${COUNTER}")  # 1
endfunction()

increment()
message(STATUS "After function: COUNTER = ${COUNTER}")  # 0（未被修改）

function(increment_parent)
    set(COUNTER 1 PARENT_SCOPE)  # 修改父作用域
endfunction()

increment_parent()
message(STATUS "After parent modify: COUNTER = ${COUNTER}")  # 1

# ---------- 环境变量 ----------
message(STATUS "HOME = $ENV{HOME}")
set(ENV{MY_ENV_VAR} "from_cmake")
message(STATUS "MY_ENV_VAR = $ENV{MY_ENV_VAR}")
```

命令行使用：

```bash
# 用户通过 -D 修改缓存变量
cmake -DBUILD_TESTS=ON ..

# 查看所有缓存变量
cmake -L ..

# 用 ccmake 交互式修改
ccmake ..

# 删除某个缓存变量（强制重新询问）
cmake -U BUILD_TESTS ..
```

### 总结

- 三类变量：普通变量（作用域内）、缓存变量（持久化）、环境变量（进程级）。
- 缓存变量默认只在未定义时赋值，要强制覆盖加 `FORCE`。
- `cmake -DVAR=value` 是用户配置缓存变量的标准方式。
- 普通变量会遮蔽同名缓存变量，导致"改了不生效"的困惑——避免同名。
- CMake 3.21+ 用 `$CACHE{VAR}` 显式读取缓存变量本身。
- 函数内修改父作用域变量用 `set(VAR value PARENT_SCOPE)`。
- `INTERNAL` 类型缓存变量适合存储"用户不应修改的内部状态"，总是 FORCE 设置。

## 第8讲：条件判断与流程控制

### 概念

CMake 提供完整的流程控制结构：`if/elseif/else/endif` 条件判断、`foreach/endforeach` 循环、`while/endwhile` 循环、`break/continue` 控制流。其中 `if` 命令的求值规则非常特殊——它根据参数形式自动判断是变量名还是字面值，这是 CMake 最容易出错也最强大的特性之一。掌握 `if` 的求值规则，是写出正确条件分支的前提。

### 原理

**`if` 命令的求值规则**（关键且易错）：

当 `if` 的参数是一个"裸字符串"时，CMake 按以下顺序判断：

1. 如果是已定义的变量名，替换为变量的值。
2. 然后对替换后的值判断真值（`ON/TRUE/1/非零数字` 为真，`OFF/FALSE/0/""/NOTFOUND` 为假）。

这意味着 `if(MY_VAR)` 当 `MY_VAR` 的值是 `OFF` 时为假，当 `MY_VAR` 未定义时也为假（未定义变量求值为空字符串）。

**常量判断**（不经变量替换）：
- `if(TRUE)`、`if(ON)`、`if(1)`、`if(YES)`、`if(Y)`：真
- `if(FALSE)`、`if(OFF)`、`if(0)`、`if(NO)`、`if(N)`、`if(IGNORE)`、`if(NOTFOUND)`、`if("")`：假

**比较操作符**：
- `if(VAR STREQUAL "hello")`：字符串相等
- `if(VAR EQUAL 42)`：数值相等
- `if(VAR MATCHES "regex")`：正则匹配
- `if(VAR LESS/GREATER/LESS_EQUAL/GREATER_EQUAL N)`：数值比较
- `if(VAR VERSION_LESS/VERSION_GREATER "1.2.3")`：版本号比较

**逻辑操作符**：`NOT`、`AND`、`OR`，优先级：`NOT > AND > OR`。

**文件/路径测试**：
- `if(EXISTS path)`：路径存在
- `if(IS_DIRECTORY path)`：是目录
- `if(FILE_EXISTS path)`（CMake 3.24+）：文件存在

**平台/特性测试**：
- `if(WIN32)`、`if(UNIX)`、`if(APPLE)`、`if(MSVC)`、`if(CMAKE_SYSTEM_NAME STREQUAL "Linux")`

**重要陷阱**：`if(VAR STREQUAL "foo")` 中如果 `VAR` 的值恰好是字符串 `"VAR"`，会与字面值 `"VAR"` 比较而非变量值。为避免歧义，CMake 3.1+ 引入策略 `CMP0054`，启用后 `if` 中的引号字符串不再被当作变量名解释。建议在 `cmake_minimum_required(VERSION 3.1+)` 下自动启用。

**`foreach` 循环**：
- `foreach(item IN LISTS list1 list2)`：遍历列表变量
- `foreach(item IN ITEMS a b c)`：遍历字面值
- `foreach(i RANGE 0 10 2)`：数值范围（0 到 10，步长 2）
- `foreach(i RANGE 5)`：0 到 5

### 例子

```cmake
cmake_minimum_required(VERSION 3.15)
project(ControlFlowDemo)

# ---------- if 条件判断 ----------
set(PLATFORM "linux")
set(DEBUG_MODE ON)
set(VERSION "1.2.3")

if(PLATFORM STREQUAL "windows")
    message(STATUS "Building for Windows")
elseif(PLATFORM STREQUAL "linux")
    message(STATUS "Building for Linux")
elseif(PLATFORM STREQUAL "macos")
    message(STATUS "Building for macOS")
else()
    message(STATUS "Unknown platform: ${PLATFORM}")
endif()

# 平台检测的内置变量
if(WIN32)
    message(STATUS "WIN32 is true (includes 64-bit Windows)")
endif()
if(UNIX AND NOT APPLE)
    message(STATUS "This is Linux/Unix")
endif()

# 逻辑组合
if(DEBUG_MODE AND (PLATFORM STREQUAL "linux" OR PLATFORM STREQUAL "macos"))
    message(STATUS "Debug build on Unix-like system")
endif()

# 版本比较
if(VERSION VERSION_LESS "2.0.0")
    message(STATUS "Version 1.x branch")
elseif(VERSION VERSION_GREATER_EQUAL "2.0.0")
    message(STATUS "Version 2.x+ branch")
endif()

# 正则匹配
set(FILENAME "report_2023.csv")
if(FILENAME MATCHES "report_([0-9]+)\\.csv")
    message(STATUS "Year captured: ${CMAKE_MATCH_1}")  # 2023
endif()

# ---------- foreach 循环 ----------
set(SOURCES main.cpp utils.cpp io.cpp)

# 遍历列表
foreach(src IN LISTS SOURCES)
    message(STATUS "Source file: ${src}")
endforeach()

# 遍历字面值
foreach(lang IN ITEMS C CXX Fortran)
    message(STATUS "Language: ${lang}")
endforeach()

# 数值范围
foreach(i RANGE 1 5)
    message(STATUS "Iteration ${i}")
endforeach()

# 同时遍历多个列表
set(NAMES alice bob charlie)
set(AGES 30 25 35)
foreach(name IN ZIP_LISTS NAMES AGES)
    message(STATUS "${name_0} is ${name_1} years old")  # CMake 3.17+
endforeach()

# ---------- while 循环 ----------
set(COUNT 0)
while(COUNT LESS 5)
    message(STATUS "Count = ${COUNT}")
    math(EXPR COUNT "${COUNT} + 1")
endwhile()

# ---------- break/continue ----------
foreach(i RANGE 1 10)
    if(i EQUAL 5)
        continue()   # 跳过 5
    endif()
    if(i EQUAL 8)
        break()      # 在 8 时退出
    endif()
    message(STATUS "i = ${i}")
endforeach()
# 输出：1, 2, 3, 4, 6, 7
```

### 总结

- `if` 的求值规则：裸字符串先当变量名替换，再判断真值——这是 CMake 最易错的特性。
- 字符串比较用 `STREQUAL`，数值比较用 `EQUAL`，版本比较用 `VERSION_LESS/GREATER`。
- 平台检测优先用内置变量：`WIN32`、`UNIX`、`APPLE`、`MSVC`、`CMAKE_SYSTEM_NAME`。
- 正则匹配用 `MATCHES`，捕获组在 `CMAKE_MATCH_1`、`CMAKE_MATCH_2`... 中。
- `foreach(IN LISTS ...)` 遍历列表变量，`foreach(IN ITEMS ...)` 遍历字面值。
- `foreach(IN ZIP_LISTS list1 list2)`（CMake 3.17+）可并行遍历多个列表。
- 启用策略 `CMP0054`（3.1+ 自动启用）避免引号字符串被当变量名解释的歧义。

## 第9讲：构建类型与多配置

### 概念

CMake 项目通常需要支持多种构建类型（Build Type）：Debug（带调试信息、无优化）、Release（最大优化、无调试信息）、RelWithDebInfo（优化 + 调试信息）、MinSizeRel（最小体积优化）。不同构建类型决定了编译器的优化级别、调试符号、断言开关等。CMake 通过 `CMAKE_BUILD_TYPE` 变量（单配置生成器）或 `--config` 参数（多配置生成器）管理构建类型。

### 原理

**单配置生成器**（如 Makefile、Ninja）：整个 build 目录对应一种构建类型，由 `CMAKE_BUILD_TYPE` 变量决定。切换构建类型需要重新配置或创建新的 build 目录。这是 Linux/macOS 命令行开发的常见模式。

**多配置生成器**（如 Visual Studio、Xcode、Ninja Multi-Config）：一个 build 目录同时支持多种构建类型，构建时通过 `--config Debug` 或 `--config Release` 选择。这是 IDE 开发的常见模式。

**构建类型如何影响编译**：CMake 为每种构建类型预设了编译/链接选项变量：

| 构建类型 | `CMAKE_<LANG>_FLAGS_<TYPE>` 默认值（GCC） |
|---------|------------------------------------------|
| Debug | `-g` |
| Release | `-O3 -DNDEBUG` |
| RelWithDebInfo | `-O2 -g -DNDEBUG` |
| MinSizeRel | `-Os -DNDEBUG` |

`NDEBUG` 宏会禁用 `assert()`，这是 Release 模式下断言不生效的原因。

**设置构建类型**：

```cmake
# 在 CMakeLists.txt 中设置默认值（如果用户未指定）
if(NOT CMAKE_BUILD_TYPE)
    set(CMAKE_BUILD_TYPE Release CACHE STRING "Build type" FORCE)
endif()

# 限制可选值（便于 ccmake 选择）
set_property(CACHE CMAKE_BUILD_TYPE PROPERTY STRINGS
    Debug Release RelWithDebInfo MinSizeRel)
```

**自定义构建类型**：可以定义自己的构建类型，例如 `Profile`（带性能分析）：

```cmake
set(CMAKE_CXX_FLAGS_PROFILE "-pg -O2" CACHE STRING "")
mark_as_advanced(CMAKE_CXX_FLAGS_PROFILE)
```

**多配置生成器的特殊处理**：多配置生成器中，`CMAKE_BUILD_TYPE` 在配置时为空，构建类型在构建时才确定。因此不能用 `if(CMAKE_BUILD_TYPE STREQUAL "Debug")` 在配置时分支，而要用生成器表达式 `$<CONFIG:Debug>`（见第13讲）。

### 例子

单配置生成器（Makefile）的标准用法：

```cmake
cmake_minimum_required(VERSION 3.15)
project(BuildTypeDemo LANGUAGES CXX)

# 设置默认构建类型
if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
    set(CMAKE_BUILD_TYPE Release CACHE STRING "Build type" FORCE)
    message(STATUS "Setting default build type: Release")
endif()

# 提供可选值
set_property(CACHE CMAKE_BUILD_TYPE PROPERTY STRINGS
    Debug Release RelWithDebInfo MinSizeRel)

# 根据构建类型添加额外选项
if(CMAKE_BUILD_TYPE STREQUAL "Debug")
    message(STATUS "Debug mode: assertions enabled, no optimization")
    add_compile_definitions(DEBUG_BUILD=1)
elseif(CMAKE_BUILD_TYPE STREQUAL "Release")
    message(STATUS "Release mode: full optimization, no debug info")
endif()

add_executable(app main.cpp)
```

命令行使用：

```bash
# 单配置生成器：在配置时指定
cmake -DCMAKE_BUILD_TYPE=Debug ..
cmake --build .

# 多配置生成器（如 Visual Studio）：在构建时指定
cmake -G "Visual Studio 17 2022" ..
cmake --build . --config Release

# Ninja Multi-Config（CMake 3.17+）
cmake -G "Ninja Multi-Config" -DCMAKE_CONFIGURATION_TYPES="Debug;Release" ..
cmake --build . --config Debug
```

为不同构建类型输出到不同目录（避免冲突）：

```cmake
# 让不同构建类型的产物分开存放
set(CMAKE_RUNTIME_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/bin)
set(CMAKE_ARCHIVE_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/lib)
set(CMAKE_LIBRARY_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/lib)

# 多配置生成器中，自动在 bin/ 下创建 Debug/ Release/ 子目录
```

`main.cpp` 测试 NDEBUG 效果：

```cpp
#include <cassert>
#include <iostream>

int main() {
    int x = 10;
    assert(x == 10);  // Release 模式下被移除
    std::cout << "x = " << x << std::endl;

#ifdef NDEBUG
    std::cout << "NDEBUG defined (Release/RelWithDebInfo)" << std::endl;
#else
    std::cout << "NDEBUG not defined (Debug)" << std::endl;
#endif
    return 0;
}
```

### 总结

- 四种标准构建类型：Debug、Release、RelWithDebInfo、MinSizeRel，各有预设的编译选项。
- 单配置生成器（Makefile/Ninja）用 `CMAKE_BUILD_TYPE` 在配置时指定。
- 多配置生成器（VS/Xcode/Ninja Multi-Config）用 `--config` 在构建时指定。
- `NDEBUG` 宏在非 Debug 模式下定义，会禁用 `assert()`——这是 Release 模式断言失效的原因。
- 多配置生成器中不能用 `if(CMAKE_BUILD_TYPE STREQUAL ...)` 配置时分支，要用生成器表达式 `$<CONFIG:...>`。
- 建议在 CMakeLists.txt 中设置默认构建类型，避免空构建类型导致的未定义行为。
- 用 `set_property(CACHE ... PROPERTY STRINGS ...)` 为 `ccmake` 提供可选值列表。

## 第10讲：自定义命令 —— function 与 macro

### 概念

CMake 提供两种自定义命令的机制：**函数（function）**和**宏（macro）**。两者语法相似，但语义有关键差异：函数有独立的作用域（局部变量不影响外部），宏则在调用处展开（无独立作用域）。理解这一差异是正确选择和编写自定义命令的前提。此外，函数支持通过 `set(... PARENT_SCOPE)` 修改调用者变量，宏则直接在调用者作用域执行。

### 原理

**函数（function）**：

```cmake
function(name arg1 arg2 ...)
    # 函数体
    # ${arg1}、${arg2} 是参数
    # ${ARGC} 参数总数
    # ${ARGV0}、${ARGV1}... 按位置访问
    # ${ARGN} 多余参数（超出声明的）
endfunction()
```

函数创建新的作用域。函数内 `set(VAR value)` 只影响函数内，不影响调用者。要修改调用者变量用 `set(VAR value PARENT_SCOPE)`。函数参数区分大小写，按值传递（CMake 中"值"就是字符串）。

**宏（macro）**：

```cmake
macro(name arg1 arg2 ...)
    # 宏体
endmacro()
```

宏不创建新作用域，类似 C 语言的文本替换。宏内 `set(VAR value)` 直接修改调用者作用域的变量。宏的参数不是真正的变量，而是字符串替换——`${arg1}` 在宏体内被替换为调用时传入的文本。

**关键差异**：

| 特性 | function | macro |
|------|----------|-------|
| 作用域 | 独立新作用域 | 无新作用域 |
| 参数 | 真实变量 | 文本替换 |
| `set(VAR ...)` | 影响函数内 | 影响调用者 |
| `return()` | 退出函数 | 退出当前作用域（小心！） |
| 性能 | 略慢（创建作用域） | 略快 |

**选择原则**：
- 大多数情况用 `function`，作用域隔离更安全。
- 需要修改调用者多个变量、或需要"内联展开"语义时用 `macro`。
- 宏的 `return()` 行为反直觉（会退出包含它的函数或目录），避免在宏中用 `return()`。

**参数解析**：CMake 提供 `cmake_parse_arguments()` 命令解析复杂参数（关键字参数、可选参数、多值参数），是编写健壮自定义命令的关键工具。

### 例子

```cmake
cmake_minimum_required(VERSION 3.15)
project(FunctionMacroDemo)

# ---------- 基础函数 ----------
function(greet name)
    message(STATUS "Hello, ${name}!")
    set(GREET_COUNT 1)   # 只在函数内
endfunction()

greet("CMake")
message(STATUS "GREET_COUNT after greet: ${GREET_COUNT}")  # 空（未定义）

# ---------- 修改调用者变量 ----------
function(set_version major minor)
    set(PROJECT_VERSION_MAJOR ${major} PARENT_SCOPE)
    set(PROJECT_VERSION_MINOR ${minor} PARENT_SCOPE)
endfunction()

set_version(2 5)
message(STATUS "Version: ${PROJECT_VERSION_MAJOR}.${PROJECT_VERSION_MINOR}")  # 2.5

# ---------- 可变参数 ----------
function(sum_numbers)
    math(EXPR total 0)
    foreach(num IN LISTS ARGN)
        math(EXPR total "${total} + ${num}")
    endforeach()
    set(SUM_RESULT ${total} PARENT_SCOPE)
endfunction()

sum_numbers(1 2 3 4 5)
message(STATUS "Sum = ${SUM_RESULT}")  # 15

# ---------- 宏的对比 ----------
macro(macro_set var value)
    set(${var} ${value})
    message(STATUS "Inside macro: ${var} = ${value}")
endmacro()

macro_set(MY_VAR 42)
message(STATUS "After macro: MY_VAR = ${MY_VAR}")  # 42（宏直接修改调用者）

# ---------- cmake_parse_arguments：现代参数解析 ----------
function(add_test_executable)
    set(options VERBOSE)
    set(oneValueArgs NAME)
    set(multiValueArgs SOURCES LIBRARIES)
    cmake_parse_arguments(
        TEST
        "${options}"
        "${oneValueArgs}"
        "${multiValueArgs}"
        ${ARGN}
    )

    if(TEST_VERBOSE)
        message(STATUS "Adding test '${TEST_NAME}' in verbose mode")
    else()
        message(STATUS "Adding test '${TEST_NAME}'")
    endif()

    add_executable(${TEST_NAME} ${TEST_SOURCES})
    if(TEST_LIBRARIES)
        target_link_libraries(${TEST_NAME} PRIVATE ${TEST_LIBRARIES})
    endif()
endfunction()

# 使用
add_test_executable(
    NAME my_test
    SOURCES test_main.cpp test_utils.cpp
    LIBRARIES gtest gtest_main
    VERBOSE
)
# TEST_NAME = my_test
# TEST_SOURCES = test_main.cpp;test_utils.cpp
# TEST_LIBRARIES = gtest;gtest_main
# TEST_VERBOSE = TRUE
```

### 总结

- `function` 创建独立作用域，`macro` 不创建——这是核心差异。
- 函数内修改调用者变量用 `set(VAR value PARENT_SCOPE)`。
- 函数参数：`${ARGC}` 总数、`${ARGV0}` 按位置、`${ARGN}` 多余参数。
- 宏的参数是文本替换，不是真实变量；避免在宏中用 `return()`。
- 默认用 `function`，需要内联展开或修改多个调用者变量时才用 `macro`。
- `cmake_parse_arguments()` 是编写健壮自定义命令的标准工具，支持 options/oneValueArgs/multiValueArgs 三类参数。
- 现代 CMake 推荐用 `cmake_parse_arguments(PREFIX "options" "oneValue" "multiValue" ${ARGN})` 解析复杂参数。

## 第11讲：模块化组织 —— include 与子目录

### 概念

大型项目的 CMake 配置需要模块化：把通用函数抽取到 `.cmake` 文件中复用，把子项目组织到子目录中独立管理。CMake 提供两种模块化机制：`include()` 引入 `.cmake` 脚本文件（在当前作用域执行），`add_subdirectory()` 引入子目录（创建新作用域）。理解两者的差异和适用场景，是组织大型项目的基础。

### 原理

**`include()` 命令**：

```cmake
include(path/to/file.cmake [OPTIONAL] [RESULT_VARIABLE var] [NO_POLICY_SCOPE])
```

`include` 在当前作用域执行指定 `.cmake` 文件的内容，类似于 C 语言的 `#include`。被包含文件中定义的变量、函数在 include 之后在当前作用域可见。`include` 不创建新作用域，所有 `set()` 直接影响当前作用域。

`include()` 的路径搜索顺序：
1. 如果是绝对路径或相对路径，直接使用。
2. 否则在 `CMAKE_MODULE_PATH` 列表中搜索。
3. 最后在 CMake 内置模块目录搜索（`<CMake>/share/cmake/Modules/`）。

**`add_subdirectory()` 命令**：

```cmake
add_subdirectory(source_dir [binary_dir] [EXCLUDE_FROM_ALL])
```

`add_subdirectory` 引入一个子目录，该子目录必须有自己的 `CMakeLists.txt`。它创建新的作用域（变量隔离），子目录中定义的目标在父目录可见，但变量修改不回传。`binary_dir` 指定中间文件存放位置（默认在 build 目录下镜像 source_dir 结构）。

**两者对比**：

| 特性 | `include()` | `add_subdirectory()` |
|------|-------------|---------------------|
| 文件类型 | `.cmake` 脚本 | `CMakeLists.txt` |
| 作用域 | 当前作用域 | 新建子作用域 |
| 变量隔离 | 否（共享） | 是（隔离） |
| 典型用途 | 复用函数、宏、通用配置 | 组织子项目、子模块 |
| 目标定义 | 可以但不推荐 | 推荐 |

**模块化最佳实践**：
- 通用函数、宏放在 `cmake/` 目录下的 `.cmake` 文件中，用 `include()` 引入。
- 子项目（库、可执行文件）放在独立子目录，用 `add_subdirectory()` 引入。
- 用 `CMAKE_MODULE_PATH` 让 `include()` 能找到自定义模块。
- 把项目级通用配置（编译选项、警告级别）放在根 `CMakeLists.txt` 或 `cmake/Common.cmake` 中。

### 例子

项目结构：

```
my_project/
├── CMakeLists.txt
├── cmake/                    # 自定义 CMake 模块
│   ├── Common.cmake          # 通用配置
│   ├── CompilerWarnings.cmake
│   └── Utilities.cmake       # 通用函数
├── libs/
│   ├── math/
│   │   ├── CMakeLists.txt
│   │   └── ...
│   └── network/
│       ├── CMakeLists.txt
│       └── ...
└── apps/
    ├── CMakeLists.txt
    └── main.cpp
```

根 `CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.15)
project(MyProject LANGUAGES CXX)

# 把 cmake/ 目录加入模块搜索路径
list(APPEND CMAKE_MODULE_PATH ${CMAKE_CURRENT_SOURCE_DIR}/cmake)

# 引入通用配置（在当前作用域执行）
include(Common)            # 引入 cmake/Common.cmake
include(CompilerWarnings)  # 引入 cmake/CompilerWarnings.cmake
include(Utilities)         # 引入 cmake/Utilities.cmake

# 应用通用配置
apply_common_settings()    # Common.cmake 中定义的函数

# 引入子目录（每个子目录有独立 CMakeLists.txt）
add_subdirectory(libs/math)
add_subdirectory(libs/network)
add_subdirectory(apps)
```

`cmake/Common.cmake`：

```cmake
# 通用项目配置
function(apply_common_settings)
    set(CMAKE_CXX_STANDARD 17 PARENT_SCOPE)
    set(CMAKE_CXX_STANDARD_REQUIRED ON PARENT_SCOPE)
    set(CMAKE_CXX_EXTENSIONS OFF PARENT_SCOPE)
    set(CMAKE_EXPORT_COMPILE_COMMANDS ON PARENT_SCOPE)
endfunction()

# 输出目录标准化
function(set_standard_output_dirs target)
    set_target_properties(${target} PROPERTIES
        RUNTIME_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/bin
        LIBRARY_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/lib
        ARCHIVE_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/lib
    )
endfunction()
```

`cmake/CompilerWarnings.cmake`：

```cmake
# 为目标添加警告选项
function(enable_warnings target)
    if(MSVC)
        target_compile_options(${target} PRIVATE /W4 /WX)
    else()
        target_compile_options(${target} PRIVATE
            -Wall -Wextra -Wpedantic -Werror
            -Wno-unused-parameter
        )
    endif()
endfunction()
```

`libs/math/CMakeLists.txt`：

```cmake
# 子目录有独立作用域，但 CMAKE_MODULE_PATH 会继承
add_library(math STATIC math.cpp)
target_include_directories(math PUBLIC ${CMAKE_CURRENT_SOURCE_DIR}/include)
enable_warnings(math)        # 使用 Utilities.cmake 中的函数
set_standard_output_dirs(math)
```

`apps/CMakeLists.txt`：

```cmake
add_executable(myapp main.cpp)
target_link_libraries(myapp PRIVATE math network)
enable_warnings(myapp)
set_standard_output_dirs(myapp)
```

### 总结

- `include()` 在当前作用域执行 `.cmake` 文件，不创建新作用域——适合复用函数和通用配置。
- `add_subdirectory()` 创建新作用域，变量隔离——适合组织子项目。
- 用 `CMAKE_MODULE_PATH` 让 `include()` 能找到自定义 `.cmake` 模块。
- 推荐结构：`cmake/` 放通用模块，子项目放独立子目录。
- 通用配置（C++ 标准、警告级别、输出目录）封装为函数，在子目录中调用。
- `include()` 的 `OPTIONAL` 选项在文件不存在时不报错，`RESULT_VARIABLE` 可获取实际路径。
- 子目录的目标在父目录可见，但变量修改不回传——这是 `add_subdirectory` 的隔离特性。

## 第12讲：第三方库发现 —— find_package

### 概念

`find_package()` 是 CMake 集成第三方库的标准命令。它搜索系统中的库文件和头文件，设置一系列变量（如 `XXX_FOUND`、`XXX_INCLUDE_DIRS`、`XXX_LIBRARIES`）供后续使用。现代 CMake（3.x+）中，`find_package` 还会导入"导入目标（imported target）"，让依赖管理更清晰。掌握 `find_package` 是使用任何第三方库（如 Boost、OpenSSL、Qt）的前提。

### 原理

**`find_package` 的两种模式**：

1. **模块模式（Module mode）**：搜索 `FindXXX.cmake` 文件（CMake 自带或项目提供）。这种文件由 CMake 社区或项目作者编写，封装了查找逻辑。例如 `find_package(OpenSSL)` 会找 `FindOpenSSL.cmake`。

2. **配置模式（Config mode）**：搜索 `XXXConfig.cmake` 或 `xxx-config.cmake` 文件。这种文件由第三方库自己的 CMake 安装时生成，是最准确的方式。例如安装了 Boost 后，`find_package(Boost CONFIG)` 会找 `BoostConfig.cmake`。

CMake 默认先尝试模块模式，失败后尝试配置模式。可以用 `MODULE` 或 `CONFIG` 关键字强制指定。

**查找结果**：

模块模式通常设置以下变量（具体看模块文档）：
- `XXX_FOUND`：是否找到
- `XXX_INCLUDE_DIRS`：头文件目录
- `XXX_LIBRARIES`：库文件
- `XXX_VERSION`：版本号

配置模式通常提供**导入目标**（imported target），如 `Boost::boost`、`OpenSSL::SSL`。导入目标携带完整的依赖信息（include 路径、链接库、编译选项），用 `target_link_libraries` 链接即可，无需手动处理变量。

**版本要求**：

```cmake
find_package(Boost 1.70 REQUIRED COMPONENTS filesystem system)
```

- `1.70`：最低版本要求
- `REQUIRED`：找不到则报错退出（不加则只设 `XXX_FOUND=FALSE`）
- `COMPONENTS`：指定需要的子组件

**最佳实践**：优先使用导入目标而非变量。导入目标携带传递性依赖，更健壮。

### 例子

**例1：使用 OpenSSL（CMake 自带 Find 模块）**

```cmake
cmake_minimum_required(VERSION 3.15)
project(OpenSSLDemo LANGUAGES CXX)

find_package(OpenSSL 1.1 REQUIRED)

add_executable(ssl_client main.cpp)

# 现代方式：使用导入目标
target_link_libraries(ssl_client PRIVATE OpenSSL::SSL OpenSSL::Crypto)

# 旧式方式（不推荐）：
# target_include_directories(ssl_client PRIVATE ${OPENSSL_INCLUDE_DIR})
# target_link_libraries(ssl_client PRIVATE ${OPENSSL_LIBRARIES})

message(STATUS "OpenSSL version: ${OPENSSL_VERSION}")
```

**例2：使用 Boost（配置模式）**

```cmake
find_package(Boost 1.70 REQUIRED COMPONENTS filesystem system regex)

add_executable(boost_app main.cpp)
target_link_libraries(boost_app PRIVATE
    Boost::filesystem
    Boost::system
    Boost::regex
    # Boost::boost 是纯头文件库
)
```

**例3：可选依赖**

```cmake
# 不加 REQUIRED，找不到不报错
find_package(ZLIB)

if(ZLIB_FOUND)
    add_compile_definitions(HAVE_ZLIB=1)
    add_executable(compressor main.cpp)
    target_link_libraries(compressor PRIVATE ZLIB::ZLIB)
else()
    message(STATUS "ZLIB not found, building without compression support")
    add_executable(compressor main.cpp)
endif()
```

**例4：自定义 Find 模块**

当第三方库没有提供 Config 文件，CMake 也没有自带 Find 模块时，可以自己写 `cmake/FindMyLib.cmake`：

```cmake
# cmake/FindMyLib.cmake
find_path(MYLIB_INCLUDE_DIR mylib/mylib.h
    PATHS /usr/include /usr/local/include /opt/mylib/include
)

find_library(MYLIB_LIBRARY NAMES mylib
    PATHS /usr/lib /usr/local/lib /opt/mylib/lib
)

include(FindPackageHandleStandardArgs)
find_package_handle_standard_args(MyLib
    REQUIRED_VARS MYLIB_LIBRARY MYLIB_INCLUDE_DIR
)

if(MyLib_FOUND)
    # 创建导入目标，方便使用
    add_library(MyLib::MyLib UNKNOWN IMPORTED)
    set_target_properties(MyLib::MyLib PROPERTIES
        IMPORTED_LOCATION "${MYLIB_LIBRARY}"
        INTERFACE_INCLUDE_DIRECTORIES "${MYLIB_INCLUDE_DIR}"
    )
endif()

mark_as_advanced(MYLIB_INCLUDE_DIR MYLIB_LIBRARY)
```

使用：

```cmake
list(APPEND CMAKE_MODULE_PATH ${CMAKE_SOURCE_DIR}/cmake)
find_package(MyLib REQUIRED)
add_executable(app main.cpp)
target_link_libraries(app PRIVATE MyLib::MyLib)
```

### 总结

- `find_package` 有两种模式：模块模式（`FindXXX.cmake`）和配置模式（`XXXConfig.cmake`）。
- 优先使用**导入目标**（如 `OpenSSL::SSL`、`Boost::filesystem`）而非变量（`${OPENSSL_LIBRARIES}`）。
- `REQUIRED` 找不到则报错，不加则设 `XXX_FOUND=FALSE`。
- `COMPONENTS` 指定子组件，`1.70` 指定最低版本。
- 用 `if(XXX_FOUND)` 处理可选依赖。
- 第三方库无 Config 文件时，可自己写 `FindXXX.cmake`，用 `find_package_handle_standard_args` 标准化结果。
- 创建导入目标（`add_library(... IMPORTED)`）让自定义 Find 模块也支持现代用法。
- `CMAKE_PREFIX_PATH` 变量可指定第三方库安装根目录，帮助 `find_package` 找到非标准位置的库。

## 第13讲：生成器表达式

### 概念

**生成器表达式（Generator Expression）**是 CMake 中一种特殊的语法，形如 `$<...>`，它在**构建时（而非配置时）**求值。这是 CMake 区分配置时（configure time，执行 CMakeLists.txt）和构建时（build time，执行 make/ninja）的关键机制。许多信息（如当前构建类型、目标文件路径、平台特性）只在构建时才确定，生成器表达式让这些信息能被正确使用。

### 原理

**为什么需要生成器表达式**：配置时 `if(CMAKE_BUILD_TYPE STREQUAL "Debug")` 在多配置生成器（如 Visual Studio）中无效——因为多配置生成器在配置时 `CMAKE_BUILD_TYPE` 为空，构建类型在构建时才通过 `--config` 指定。生成器表达式 `$<CONFIG:Debug>` 在构建时求值，能正确处理这种情况。

**生成器表达式的语法**：`$<expression:argument>`，可以嵌套。常见类型：

**逻辑表达式**：
- `$<CONFIG:cfg>`：当前构建类型是 `cfg` 时为 1，否则为 0
- `$<PLATFORM_ID:platform>`：当前平台是 `platform` 时为 1
- `$<BOOL:value>`：value 的真值
- `$<AND:expr1,expr2,...>`：逻辑与
- `$<OR:expr1,expr2,...>`：逻辑或
- `$<NOT:expr>`：逻辑非
- `$<STREQUAL:a,b>`：字符串相等
- `$<TARGET_EXISTS:name>`：目标是否存在

**信息表达式**：
- `$<CONFIG>`：当前构建类型名
- `$<PLATFORM_ID>`：当前平台名
- `$<TARGET_FILE:name>`：目标文件的完整路径
- `$<TARGET_FILE_NAME:name>`：目标文件名
- `$<TARGET_FILE_DIR:name>`：目标文件所在目录
- `$<TARGET_PROPERTY:name,prop>`：目标的属性值
- `$<COMPILE_LANGUAGE>`：当前编译的语言
- `$<COMPILE_LANG_AND_ID:lang,compiler_id>`：语言和编译器 ID

**条件表达式**：
- `$<condition:true_value>`：condition 为真时展开为 `true_value`，否则为空
- `$<condition:true_value:false_value>`：三元表达式

**输出表达式**：
- `$<TARGET_OBJECTS:name>`：OBJECT 库的目标文件列表
- `$<JOIN:list,delimiter>`：用分隔符连接列表

**使用场景**：生成器表达式主要用于 `target_*` 命令的参数中，如 `target_compile_definitions`、`target_compile_options`、`target_link_libraries`、`target_sources` 等。

### 例子

```cmake
cmake_minimum_required(VERSION 3.15)
project(GeneratorExprDemo LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 17)

add_executable(app main.cpp)

# ---------- 按构建类型定义宏 ----------
target_compile_definitions(app PRIVATE
    $<$<CONFIG:Debug>:DEBUG_MODE=1>           # Debug 时定义 DEBUG_MODE=1
    $<$<CONFIG:Release>:NDEBUG=1>             # Release 时定义 NDEBUG=1
    $<$<CONFIG:Debug,RelWithDebInfo>:LOGGING_ENABLED=1>  # 多类型
)

# ---------- 按编译器选择选项 ----------
if(MSVC)
    target_compile_options(app PRIVATE /W4)
else()
    target_compile_options(app PRIVATE
        -Wall
        -Wextra
        $<$<CONFIG:Debug>:-O0 -g>             # Debug 时加 -O0 -g
        $<$<CONFIG:Release>:-O3>              # Release 时加 -O3
    )
endif()

# ---------- 按语言选择选项（多语言项目） ----------
target_compile_options(app PRIVATE
    $<$<COMPILE_LANGUAGE:CXX>:-fconcepts>     # 仅 C++ 文件加此选项
    $<$<COMPILE_LANG_AND_ID:CXX,GNU,Clang>:-Wall>  # GCC/Clang 编译 C++ 时
)

# ---------- 条件链接库 ----------
# Debug 时链接调试库，Release 时链接优化库
find_package(OpenSSL REQUIRED)
target_link_libraries(app PRIVATE
    OpenSSL::SSL
    $<$<CONFIG:Debug>:my_debug_lib>
    $<$<CONFIG:Release>:my_release_lib>
)

# ---------- 三元表达式 ----------
target_compile_definitions(app PRIVATE
    # 多配置生成器中，根据配置选择默认日志级别
    LOG_LEVEL=$<IF:$<CONFIG:Debug>,DEBUG,INFO>
)

# ---------- 获取目标文件路径（用于自定义命令） ----------
add_custom_command(TARGET app POST_BUILD
    COMMAND ${CMAKE_COMMAND} -E copy
        $<TARGET_FILE:app>                    # app 的完整路径
        ${CMAKE_BINARY_DIR}/final_app
    COMMENT "Copying app to final location"
)

# ---------- 按平台条件编译 ----------
target_compile_definitions(app PRIVATE
    $<$<PLATFORM_ID:Windows>:PLATFORM_WINDOWS=1>
    $<$<PLATFORM_ID:Linux>:PLATFORM_LINUX=1>
    $<$<PLATFORM_ID:Darwin>:PLATFORM_MACOS=1>
)

# ---------- JOIN 表达式 ----------
set(LIBS lib1 lib2 lib3)
message(STATUS "Libraries: $<JOIN:${LIBS}, >")  # lib1, lib2, lib3
```

`main.cpp` 测试：

```cpp
#include <iostream>

int main() {
#ifdef DEBUG_MODE
    std::cout << "Debug mode" << std::endl;
#endif
#ifdef LOGGING_ENABLED
    std::cout << "Logging enabled" << std::endl;
#endif
    std::cout << "Log level: " << LOG_LEVEL << std::endl;
    return 0;
}
```

### 总结

- 生成器表达式 `$<...>` 在**构建时**求值，解决多配置生成器中配置时信息不足的问题。
- 逻辑表达式：`$<CONFIG:cfg>`、`$<PLATFORM_ID:p>`、`$<BOOL:v>`、`$<AND:...>`、`$<OR:...>`。
- 信息表达式：`$<TARGET_FILE:name>`、`$<CONFIG>`、`$<TARGET_PROPERTY:name,prop>`。
- 条件表达式：`$<cond:true>`（假时为空）、`$<IF:cond:true:false>`（三元）。
- 主要用于 `target_*` 命令的参数中，实现按构建类型、平台、编译器的条件配置。
- 多配置生成器（VS/Xcode）必须用生成器表达式处理构建类型差异，不能用配置时 `if`。
- 生成器表达式可嵌套，如 `$<$<CONFIG:Debug>:-O0>` 中 `$<CONFIG:Debug>` 嵌入外层条件。

## 第14讲：自定义命令与自定义目标

### 概念

CMake 的 `add_custom_command()` 和 `add_custom_target()` 让你能在构建过程中执行任意命令——生成代码、下载文件、运行测试、复制资源等。`add_custom_command` 定义"如何生成某个文件"或"在某目标构建前后执行什么"，`add_custom_target` 定义"一个不产生文件的目标，只执行命令"。两者结合可以实现复杂的构建流程自动化。

### 原理

**`add_custom_command` 的两种形式**：

**形式1：生成文件**

```cmake
add_custom_command(
    OUTPUT output1 output2
    COMMAND cmd1 args...
    COMMAND cmd2 args...
    [MAIN_DEPENDENCY file]
    [DEPENDS files...]
    [WORKING_DIRECTORY dir]
    [COMMENT "text"]
    [VERBATIM]
)
```

定义一个规则：当 `output` 文件不存在或 `DEPENDS` 中的依赖更新时，执行 `COMMAND` 生成 `output`。生成的文件可作为其他目标的源文件。

**形式2：目标构建前后钩子**

```cmake
add_custom_command(
    TARGET target
    PRE_BUILD | PRE_LINK | POST_BUILD
    COMMAND cmd1 args...
    [WORKING_DIRECTORY dir]
    [COMMENT "text"]
)
```

在指定目标的构建前（PRE_BUILD）、链接前（PRE_LINK）、构建后（POST_BUILD）执行命令。

**`add_custom_target`**：

```cmake
add_custom_target(
    name
    [ALL] [command1 args...]
    [DEPENDS targets...]
    [WORKING_DIRECTORY dir]
    [COMMENT "text"]
    [SOURCES src1 src2...]
)
```

定义一个总是被构建的目标（除非不加 `ALL`），不产生文件。常用于封装一组命令，让用户能通过 `make my_target` 触发。

**关键区别**：
- `add_custom_command(OUTPUT ...)` 定义"如何生成文件"，需要被某个目标引用才会执行。
- `add_custom_command(TARGET ...)` 把命令附加到已有目标的生命周期。
- `add_custom_target` 定义新目标，本身不产生文件，常作为命令的容器。

**`CMAKE_COMMAND -E`**：CMake 自带一组跨平台命令（`-E` 模式），如 `copy`、`copy_directory`、`remove`、`make_directory`、`echo` 等。用 `${CMAKE_COMMAND} -E cmd` 可避免平台差异（如 `cp` vs `copy`）。

### 例子

**例1：生成代码文件**

```cmake
# 用工具从 schema 生成 C++ 代码
add_custom_command(
    OUTPUT ${CMAKE_CURRENT_BINARY_DIR}/generated.cpp
    COMMAND codegen --schema ${CMAKE_CURRENT_SOURCE_DIR}/schema.json
                   --output ${CMAKE_CURRENT_BINARY_DIR}/generated.cpp
    DEPENDS ${CMAKE_CURRENT_SOURCE_DIR}/schema.json
    COMMENT "Generating C++ code from schema"
    VERBATIM
)

# 把生成的文件加入目标
add_executable(app main.cpp ${CMAKE_CURRENT_BINARY_DIR}/generated.cpp)
```

**例2：构建后复制资源**

```cmake
add_executable(app main.cpp)

# 构建后复制配置文件到可执行文件目录
add_custom_command(TARGET app POST_BUILD
    COMMAND ${CMAKE_COMMAND} -E copy
        ${CMAKE_SOURCE_DIR}/config/app.conf
        $<TARGET_FILE_DIR:app>/app.conf
    COMMAND ${CMAKE_COMMAND} -E copy_directory
        ${CMAKE_SOURCE_DIR}/assets
        $<TARGET_FILE_DIR:app>/assets
    COMMENT "Copying resources to output directory"
)
```

**例3：自定义目标封装测试命令**

```cmake
# 定义一个 "test" 目标，运行所有测试
add_custom_target(run_tests
    COMMAND ctest --output-on-failure
    WORKING_DIRECTORY ${CMAKE_BINARY_DIR}
    COMMENT "Running all tests"
)

# 定义一个 "docs" 目标，生成文档
add_custom_target(docs
    COMMAND doxygen Doxyfile
    WORKING_DIRECTORY ${CMAKE_SOURCE_DIR}/docs
    COMMENT "Generating documentation"
    SOURCES Doxyfile
)
```

用户可运行 `make run_tests` 或 `make docs` 触发。

**例4：依赖链**

```cmake
# 第一步：下载数据
add_custom_command(
    OUTPUT ${CMAKE_BINARY_DIR}/data.zip
    COMMAND ${CMAKE_COMMAND} -E download
        https://example.com/data.zip ${CMAKE_BINARY_DIR}/data.zip
    COMMENT "Downloading data"
)

# 第二步：解压（依赖第一步的输出）
add_custom_command(
    OUTPUT ${CMAKE_BINARY_DIR}/data/processed.dat
    COMMAND ${CMAKE_COMMAND} -E tar xzf ${CMAKE_BINARY_DIR}/data.zip
    COMMAND process_data --input ${CMAKE_BINARY_DIR}/data/raw.dat
                        --output ${CMAKE_BINARY_DIR}/data/processed.dat
    DEPENDS ${CMAKE_BINARY_DIR}/data.zip
    COMMENT "Extracting and processing data"
)

# 第三步：把处理后的数据嵌入可执行文件
add_executable(app main.cpp ${CMAKE_BINARY_DIR}/data/processed.dat)
```

### 总结

- `add_custom_command(OUTPUT ...)` 定义文件生成规则，需被目标引用才执行。
- `add_custom_command(TARGET ... PRE_BUILD/PRE_LINK/POST_BUILD)` 在目标生命周期钩子执行命令。
- `add_custom_target` 定义不产生文件的目标，常封装命令供 `make xxx` 触发。
- 用 `${CMAKE_COMMAND} -E cmd` 执行跨平台命令，避免 `cp`/`copy` 等平台差异。
- `DEPENDS` 指定依赖文件，`COMMENT` 设置构建时显示的提示信息。
- `VERBATIM` 选项让命令参数被原样传递，避免平台 shell 转义问题——推荐总是加。
- 生成器表达式（如 `$<TARGET_FILE:app>`）常用于自定义命令中引用目标路径。

## 第15讲：属性与特性系统

### 概念

CMake 的**属性（property）**系统是细粒度配置的基础。属性可以附加在目标、源文件、目录、全局等不同层级上，控制编译选项、链接选项、输出位置、安装规则等。`set_property()` 和 `set_target_properties()` 是设置属性的主要命令。理解属性系统，才能精确控制每个目标、每个文件的行为。

### 原理

**属性的层级**：

- **全局属性**：`set_property(GLOBAL ...)`，如 `GLOBAL_DEPENDS_NO_CYCLES`。
- **目录属性**：`set_property(DIRECTORY ...)`，如 `include_directories`、`compile_definitions`。
- **目标属性**：`set_property(TARGET ...)`，最常用，如 `CXX_STANDARD`、`OUTPUT_NAME`、`POSITION_INDEPENDENT_CODE`。
- **源文件属性**：`set_property(SOURCE ...)`，如 `COMPILE_OPTIONS`、`GENERATED`、`LANGUAGE`。
- **缓存变量属性**：`set_property(CACHE ...)`，如 `STRINGS`、`HELPSTRING`。

**设置属性的两种命令**：

```cmake
# 方式1：set_property（通用，可一次设置多个目标/文件）
set_property(TARGET target1 target2
    PROPERTY CXX_STANDARD 17
)

# 方式2：set_target_properties（仅目标，语法更紧凑）
set_target_properties(target1 target2 PROPERTIES
    CXX_STANDARD 17
    CXX_STANDARD_REQUIRED ON
    CXX_EXTENSIONS OFF
)
```

**常用目标属性**：

| 属性 | 作用 |
|------|------|
| `CXX_STANDARD` | C++ 标准版本（98/11/14/17/20/23） |
| `CXX_STANDARD_REQUIRED` | 标准版本是否必须（否则降级） |
| `CXX_EXTENSIONS` | 是否允许编译器扩展（OFF 用纯标准 C++） |
| `POSITION_INDEPENDENT_CODE` | 生成位置无关代码（PIC），动态库需要 |
| `OUTPUT_NAME` | 输出文件名（默认与目标名相同） |
| `DEBUG_POSTFIX` | Debug 构建时输出文件后缀（如 `d`） |
| `VERSION` / `SOVERSION` | 动态库版本号 |
| `RUNTIME_OUTPUT_DIRECTORY` | 可执行文件输出目录 |
| `ARCHIVE_OUTPUT_DIRECTORY` | 静态库输出目录 |
| `LIBRARY_OUTPUT_DIRECTORY` | 动态库输出目录 |
| `COMPILE_FLAGS` | 编译选项（旧式，推荐用 `target_compile_options`） |
| `LINK_FLAGS` | 链接选项（旧式，推荐用 `target_link_options`） |
| `INTERFACE_*` | 接口属性，传播给依赖者 |
| `FOLDER` | 在 IDE 中分组显示 |

**源文件属性**：可以为单个源文件设置特殊属性，如：

```cmake
# 某个文件用 C 编译（即使项目是 C++）
set_source_files_properties(legacy.c PROPERTIES LANGUAGE C)

# 某个文件禁用特定警告
set_source_files_properties(noisy.cpp PROPERTIES
    COMPILE_OPTIONS -Wno-unused-variable
)

# 标记文件为"已生成"（不由 CMake 检查存在性）
set_source_files_properties(generated.cpp PROPERTIES GENERATED TRUE)
```

### 例子

```cmake
cmake_minimum_required(VERSION 3.15)
project(PropertyDemo LANGUAGES CXX)

# ---------- 目标属性综合示例 ----------
add_library(mylib STATIC mylib.cpp)

set_target_properties(mylib PROPERTIES
    CXX_STANDARD 17
    CXX_STANDARD_REQUIRED ON
    CXX_EXTENSIONS OFF
    POSITION_INDEPENDENT_CODE ON      # 生成 PIC 代码
    OUTPUT_NAME "mylib"               # 输出文件名
    DEBUG_POSTFIX "d"                 # Debug 时叫 mylibd.a
    ARCHIVE_OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/lib
    FOLDER "Libraries"                # VS 中分组
)

# ---------- 动态库版本号 ----------
add_library(mylib_shared SHARED mylib.cpp)
set_target_properties(mylib_shared PROPERTIES
    OUTPUT_NAME "mylib"
    VERSION 1.2.3                     # libmylib.so.1.2.3
    SOVERSION 1                       # libmylib.so.1 符号链接
)

# ---------- 源文件属性 ----------
add_executable(app main.cpp legacy.c generated.cpp)

# legacy.c 用 C 编译
set_source_files_properties(legacy.c PROPERTIES LANGUAGE C)

# generated.cpp 是生成的，不检查存在性
set_source_files_properties(generated.cpp PROPERTIES GENERATED TRUE)

# main.cpp 启用特定警告
set_source_files_properties(main.cpp PROPERTIES
    COMPILE_OPTIONS -Wextra -Wpedantic
)

# ---------- 读取属性 ----------
get_target_property(MYLIB_CXX_STD mylib CXX_STANDARD)
message(STATUS "mylib CXX_STANDARD = ${MYLIB_CXX_STD}")

get_target_property(MYLIB_OUTPUT mylib OUTPUT_NAME)
message(STATUS "mylib OUTPUT_NAME = ${MYLIB_OUTPUT}")

# ---------- 目录属性 ----------
set_property(DIRECTORY ${CMAKE_CURRENT_SOURCE_DIR} PROPERTY
    INCLUDE_DIRECTORIES ${CMAKE_SOURCE_DIR}/include
)

# ---------- 全局属性 ----------
set_property(GLOBAL PROPERTY USE_FOLDERS ON)  # 启用 IDE 文件夹分组

# ---------- 缓存变量属性 ----------
set(MY_OPTION "default" CACHE STRING "An option")
set_property(CACHE MY_OPTION PROPERTY STRINGS "default" "option1" "option2")
# ccmake 中会显示为下拉选择
```

### 总结

- 属性系统是 CMake 细粒度配置的基础，分全局、目录、目标、源文件、缓存变量五层。
- `set_target_properties` 是设置目标属性的主要命令，`set_property` 更通用。
- 关键目标属性：`CXX_STANDARD`、`POSITION_INDEPENDENT_CODE`、`OUTPUT_NAME`、`*_OUTPUT_DIRECTORY`、`VERSION`/`SOVERSION`。
- `CXX_STANDARD_REQUIRED ON` + `CXX_EXTENSIONS OFF` 确保使用纯标准 C++，不降级、不用编译器扩展。
- 动态库用 `VERSION` 和 `SOVERSION` 管理版本号，生成 `libxxx.so → libxxx.so.1 → libxxx.so.1.2.3` 符号链接。
- 源文件属性可单独控制文件的语言、警告级别、是否生成等。
- `get_target_property(VAR target PROPERTY)` 读取属性值。
- `set_property(GLOBAL PROPERTY USE_FOLDERS ON)` 启用 IDE 文件夹分组，配合 `FOLDER` 属性组织目标。

## 第16讲：跨平台编译与条件编译

### 概念

CMake 的核心价值之一是跨平台。同一份 `CMakeLists.txt` 应能在 Windows、Linux、macOS 上无修改地构建。这需要正确使用平台检测变量、编译器检测变量、特性检测（`try_compile`、`CheckCXXSourceCompiles`），以及条件编译机制。本讲讲解如何写出真正可移植的 CMake 配置。

### 原理

**平台检测变量**（配置时可用）：

| 变量 | 含义 |
|------|------|
| `WIN32` | Windows 系统（包括 64 位） |
| `UNIX` | Unix-like 系统（Linux、macOS、Cygwin） |
| `APPLE` | macOS/iOS |
| `MSVC` | Microsoft Visual C++ 编译器 |
| `MINGW` | MinGW（Windows 上的 GCC） |
| `CYGWIN` | Cygwin 环境 |
| `CMAKE_SYSTEM_NAME` | 系统名（`Windows`/`Linux`/`Darwin`） |
| `CMAKE_SYSTEM_PROCESSOR` | 处理器架构（`x86_64`/`arm64`/`aarch64`） |

**编译器检测变量**：

| 变量 | 含义 |
|------|------|
| `CMAKE_CXX_COMPILER_ID` | 编译器 ID（`GNU`/`Clang`/`MSVC`/`AppleClang`） |
| `CMAKE_CXX_COMPILER_VERSION` | 编译器版本 |
| `CMAKE_CXX_COMPILER` | 编译器可执行文件路径 |

**架构检测**：

```cmake
if(CMAKE_SYSTEM_PROCESSOR MATCHES "(x86_|amd)64")
    # 64 位 x86
elseif(CMAKE_SYSTEM_PROCESSOR MATCHES "aarch64|arm64")
    # ARM 64
elseif(CMAKE_SYSTEM_PROCESSOR MATCHES "i386|i686")
    # 32 位 x86
endif()
```

**特性检测**：当需要检测某个编译器特性（如某关键字、某库函数）是否存在时，用 `try_compile` 或预置的 Check 模块：

```cmake
include(CheckCXXSourceCompiles)
check_cxx_source_compiles("
    #include <atomic>
    int main() { std::atomic<int> a; return a.load(); }
" HAVE_ATOMIC)

if(HAVE_ATOMIC)
    target_compile_definitions(mylib PRIVATE HAVE_STD_ATOMIC=1)
endif()
```

**条件编译**：在 C++ 代码中通过宏控制平台相关代码：

```cpp
#ifdef _WIN32
    // Windows 代码
#elif defined(__linux__)
    // Linux 代码
#elif defined(__APPLE__)
    // macOS 代码
#endif
```

CMake 通过 `target_compile_definitions` 注入平台宏，让 C++ 代码无需自己检测平台。

### 例子

完整的跨平台项目配置：

```cmake
cmake_minimum_required(VERSION 3.15)
project(CrossPlatformApp LANGUAGES CXX)
set(CMAKE_CXX_STANDARD 17)

# ---------- 平台检测 ----------
message(STATUS "System: ${CMAKE_SYSTEM_NAME} ${CMAKE_SYSTEM_PROCESSOR}")
message(STATUS "Compiler: ${CMAKE_CXX_COMPILER_ID} ${CMAKE_CXX_COMPILER_VERSION}")

# ---------- 平台相关变量 ----------
if(WIN32)
    set(PLATFORM_LIBS ws2_32 shlwapi)
    set(PLATFORM_DEFINES PLATFORM_WINDOWS=1 _WIN32_WINNT=0x0A00)
elseif(APPLE)
    set(PLATFORM_LIBS "")
    set(PLATFORM_DEFINES PLATFORM_MACOS=1)
    # macOS 特有：设置最小部署版本
    set(CMAKE_OSX_DEPLOYMENT_TARGET "10.15" CACHE STRING "Min macOS version")
elseif(UNIX)
    set(PLATFORM_LIBS pthread dl)
    set(PLATFORM_DEFINES PLATFORM_LINUX=1)
endif()

# ---------- 架构相关 ----------
if(CMAKE_SYSTEM_PROCESSOR MATCHES "x86_64|amd64")
    list(APPEND PLATFORM_DEFINES ARCH_X86_64=1)
elseif(CMAKE_SYSTEM_PROCESSOR MATCHES "aarch64|arm64")
    list(APPEND PLATFORM_DEFINES ARCH_ARM64=1)
endif()

# ---------- 编译器相关选项 ----------
add_library(platform_compat STATIC platform.cpp)

if(MSVC)
    target_compile_options(platform_compat PRIVATE /W4 /utf-8)
    # MSVC 默认用 UTF-8 处理源文件
elseif(CMAKE_CXX_COMPILER_ID STREQUAL "GNU" OR CMAKE_CXX_COMPILER_ID MATCHES "Clang")
    target_compile_options(platform_compat PRIVATE
        -Wall -Wextra -Wpedantic
        -Wno-unused-parameter
    )
endif()

# ---------- 应用平台配置 ----------
target_compile_definitions(platform_compat PUBLIC ${PLATFORM_DEFINES})

add_executable(app main.cpp)
target_link_libraries(app PRIVATE platform_compat ${PLATFORM_LIBS})

# ---------- 特性检测 ----------
include(CheckCXXSourceCompiles)
include(CheckIncludeFileCXX)

check_include_file_cxx("filesystem" HAVE_FILESYSTEM)
if(HAVE_FILESYSTEM)
    target_compile_definitions(app PRIVATE HAVE_FILESYSTEM=1)
endif()

check_cxx_source_compiles("
    #include <thread>
    int main() { std::thread t([]{}); t.join(); return 0; }
" HAVE_STD_THREAD)
if(NOT HAVE_STD_THREAD)
    find_package(Threads REQUIRED)
    target_link_libraries(app PRIVATE Threads::Threads)
endif()

# ---------- 跨平台资源处理 ----------
if(WIN32)
    # Windows：嵌入图标和版本信息
    target_sources(app PRIVATE app.rc)
    set_target_properties(app PROPERTIES
        WIN32_EXECUTABLE ON  # 不弹出控制台窗口
    )
elseif(APPLE)
    # macOS：生成 .app bundle
    set_target_properties(app PROPERTIES
        MACOSX_BUNDLE ON
        MACOSX_BUNDLE_INFO_PLIST ${CMAKE_SOURCE_DIR}/Info.plist.in
    )
endif()
```

`main.cpp` 中的条件编译：

```cpp
#include <iostream>

int main() {
#if defined(PLATFORM_WINDOWS)
    std::cout << "Running on Windows" << std::endl;
#elif defined(PLATFORM_LINUX)
    std::cout << "Running on Linux" << std::endl;
#elif defined(PLATFORM_MACOS)
    std::cout << "Running on macOS" << std::endl;
#endif

#if defined(ARCH_X86_64)
    std::cout << "Architecture: x86_64" << std::endl;
#elif defined(ARCH_ARM64)
    std::cout << "Architecture: ARM64" << std::endl;
#endif

#ifdef HAVE_FILESYSTEM
    std::cout << "std::filesystem available" << std::endl;
#endif

    return 0;
}
```

### 总结

- 平台检测用 `WIN32`、`UNIX`、`APPLE`、`CMAKE_SYSTEM_NAME`、`CMAKE_SYSTEM_PROCESSOR`。
- 编译器检测用 `CMAKE_CXX_COMPILER_ID`（`GNU`/`Clang`/`MSVC`/`AppleClang`）和 `CMAKE_CXX_COMPILER_VERSION`。
- 用 `target_compile_definitions` 注入平台宏，让 C++ 代码通过 `#ifdef` 条件编译，而非自己检测平台。
- 特性检测用 `check_cxx_source_compiles`、`check_include_file_cXX` 等 Check 模块。
- Windows 特有：链接 `ws2_32` 等系统库、用 `.rc` 资源文件、`WIN32_EXECUTABLE` 控制控制台。
- macOS 特有：`MACOSX_BUNDLE` 生成 `.app`、`CMAKE_OSX_DEPLOYMENT_TARGET` 设置最小版本。
- 跨平台编译选项差异：MSVC 用 `/W4 /utf-8`，GCC/Clang 用 `-Wall -Wextra -Wpedantic`。

## 第17讲：安装与打包 —— install 与 CPack

### 概念

构建出可执行文件和库只是第一步，实际项目还需要"安装"——把产物复制到系统标准位置（如 `/usr/local/bin`、`/usr/local/lib`），并提供"打包"——生成可分发的安装包（如 `.deb`、`.rpm`、`.exe` 安装程序、`.dmg`）。CMake 的 `install()` 命令定义安装规则，`CPack` 工具基于这些规则生成各种格式的安装包。

### 原理

**`install()` 命令**：定义"构建完成后，把哪些文件安装到哪里"。安装规则在 `cmake --install` 时执行。

```cmake
install(TARGETS targets... [DESTINATION dir] [EXPORT export-name]
        [RUNTIME DESTINATION dir]    # 可执行文件
        [LIBRARY DESTINATION dir]    # 动态库
        [ARCHIVE DESTINATION dir]    # 静态库
        [INCLUDES DESTINATION dir])  # 头文件（仅记录，不实际安装）

install(FILES files... DESTINATION dir)           # 安装文件
install(DIRECTORY dirs... DESTINATION dir)        # 安装目录
install(PROGRAMS files... DESTINATION dir)        # 安装可执行脚本
install(EXPORT export-name DESTINATION dir)       # 安装导出目标（供下游 find_package）
```

**安装路径**：`DESTINATION` 可以是绝对路径（如 `/usr/local/lib`）或相对路径（相对于 `CMAKE_INSTALL_PREFIX`）。`CMAKE_INSTALL_PREFIX` 默认是 `/usr/local`（Unix）或 `C:/Program Files/ProjectName`（Windows），用户可通过 `-DCMAKE_INSTALL_PREFIX=/opt/myapp` 修改。

**GNUInstallDirs 模块**：提供标准安装目录变量，跨发行版兼容：

```cmake
include(GNUInstallDirs)
# 提供：
# CMAKE_INSTALL_BINDIR          - bin
# CMAKE_INSTALL_LIBDIR          - lib 或 lib64
# CMAKE_INSTALL_INCLUDEDIR      - include
# CMAKE_INSTALL_DATADIR         - share
# CMAKE_INSTALL_DOCDIR          - share/doc
```

**导出目标（EXPORT）**：让其他项目能通过 `find_package` 使用你安装的库。需要：

1. `install(TARGETS mylib EXPORT MyLibTargets ...)` 把目标加入导出集。
2. `install(EXPORT MyLibTargets ...)` 生成 `MyLibTargets.cmake`。
3. 用 `configure_package_config_file()` 生成 `MyLibConfig.cmake`。
4. 用 `write_basic_package_version_file()` 生成版本文件。

**CPack**：基于 `install()` 规则生成安装包。在 CMakeLists.txt 末尾配置：

```cmake
set(CPACK_PACKAGE_NAME "MyApp")
set(CPACK_PACKAGE_VERSION "1.0.0")
set(CPACK_PACKAGE_DESCRIPTION_SUMMARY "My awesome application")
set(CPACK_RESOURCE_FILE_LICENSE "${CMAKE_SOURCE_DIR}/LICENSE")
include(CPack)
```

CPack 支持多种生成器：`DEB`（Debian）、`RPM`（RedHat）、`NSIS`（Windows exe）、`DragNDrop`（macOS dmg）、`ZIP`、`TGZ` 等。

### 例子

完整的项目安装与打包配置：

```cmake
cmake_minimum_required(VERSION 3.15)
project(MyApp VERSION 1.2.0 LANGUAGES CXX)

include(GNUInstallDirs)

# ---------- 构建目标 ----------
add_library(mylib STATIC
    src/mylib.cpp
)
target_include_directories(mylib PUBLIC
    $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
    $<INSTALL_INTERFACE:${CMAKE_INSTALL_INCLUDEDIR}>
)
set_target_properties(mylib PROPERTIES
    VERSION ${PROJECT_VERSION}
    DEBUG_POSTFIX "d"
)

add_executable(myapp src/main.cpp)
target_link_libraries(myapp PRIVATE mylib)

# ---------- 安装目标 ----------
install(TARGETS mylib
    EXPORT MyAppTargets
    ARCHIVE DESTINATION ${CMAKE_INSTALL_LIBDIR}      # 静态库 → lib/
    LIBRARY DESTINATION ${CMAKE_INSTALL_LIBDIR}      # 动态库 → lib/
    INCLUDES DESTINATION ${CMAKE_INSTALL_INCLUDEDIR} # 头文件（记录用）
)

install(TARGETS myapp
    RUNTIME DESTINATION ${CMAKE_INSTALL_BINDIR}       # 可执行文件 → bin/
)

# 安装头文件
install(DIRECTORY include/ DESTINATION ${CMAKE_INSTALL_INCLUDEDIR})

# 安装配置文件
install(FILES config/myapp.conf DESTINATION ${CMAKE_INSTALL_SYSCONFDIR})

# ---------- 导出目标（供下游 find_package） ----------
install(EXPORT MyAppTargets
    FILE MyAppTargets.cmake
    NAMESPACE MyApp::
    DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/MyApp
)

# 生成 Config 文件
include(CMakePackageConfigHelpers)
write_basic_package_version_file(
    "${CMAKE_CURRENT_BINARY_DIR}/MyAppConfigVersion.cmake"
    VERSION ${PROJECT_VERSION}
    COMPATIBILITY SameMajorVersion
)

configure_package_config_file(
    "${CMAKE_CURRENT_SOURCE_DIR}/cmake/MyAppConfig.cmake.in"
    "${CMAKE_CURRENT_BINARY_DIR}/MyAppConfig.cmake"
    INSTALL_DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/MyApp
)

install(FILES
    "${CMAKE_CURRENT_BINARY_DIR}/MyAppConfig.cmake"
    "${CMAKE_CURRENT_BINARY_DIR}/MyAppConfigVersion.cmake"
    DESTINATION ${CMAKE_INSTALL_LIBDIR}/cmake/MyApp
)

# ---------- CPack 配置 ----------
set(CPACK_PACKAGE_NAME "MyApp")
set(CPACK_PACKAGE_VERSION ${PROJECT_VERSION})
set(CPACK_PACKAGE_DESCRIPTION_SUMMARY "My awesome application")
set(CPACK_PACKAGE_VENDOR "MyCompany")
set(CPACK_RESOURCE_FILE_LICENSE "${CMAKE_CURRENT_SOURCE_DIR}/LICENSE")
set(CPACK_PACKAGE_CONTACT "dev@mycompany.com")

# 按平台选择生成器
if(WIN32)
    set(CPACK_GENERATOR NSIS ZIP)
    set(CPACK_NSIS_INSTALL_ROOT "$PROGRAMFILES64")
elseif(APPLE)
    set(CPACK_GENERATOR DragNDrop ZIP)
else()
    set(CPACK_GENERATOR DEB RPM TGZ)
    set(CPACK_DEBIAN_PACKAGE_DEPENDS "libstdc++6")
    set(CPACK_RPM_PACKAGE_LICENSE "MIT")
endif()

include(CPack)
```

`cmake/MyAppConfig.cmake.in` 模板：

```cmake
@PACKAGE_INIT@

include("${CMAKE_CURRENT_LIST_DIR}/MyAppTargets.cmake")

check_required_components(MyApp)
```

使用流程：

```bash
# 配置与构建
cmake -B build -DCMAKE_INSTALL_PREFIX=/opt/myapp
cmake --build build

# 安装（执行 install 规则）
cmake --install build

# 打包（生成安装包）
cd build
cpack -G DEB      # 生成 .deb
cpack -G TGZ      # 生成 .tar.gz
cpack -G NSIS     # 生成 Windows .exe
```

下游项目使用安装的库：

```cmake
# 安装后，其他项目可以这样使用
find_package(MyApp 1.2 REQUIRED)
add_executable(client main.cpp)
target_link_libraries(client PRIVATE MyApp::mylib)
```

### 总结

- `install(TARGETS ...)` 定义安装规则，`cmake --install build` 执行安装。
- `CMAKE_INSTALL_PREFIX` 控制安装根目录，默认 `/usr/local`（Unix）。
- 用 `include(GNUInstallDirs)` 获取标准安装目录变量，跨发行版兼容。
- 导出目标三件套：`install(TARGETS ... EXPORT ...)`、`install(EXPORT ...)`、`configure_package_config_file()` + `write_basic_package_version_file()`。
- `$<BUILD_INTERFACE:...>` 和 `$<INSTALL_INTERFACE:...>` 区分构建时和安装时的 include 路径。
- CPack 基于 `install()` 规则生成安装包，支持 DEB/RPM/NSIS/DragNDrop/ZIP 等格式。
- 按平台选择 CPACK_GENERATOR，Windows 用 NSIS，macOS 用 DragNDrop，Linux 用 DEB/RPM。

## 第18讲：现代 CMake 最佳实践

### 概念

经过前 17 讲的学习，你已经掌握了 CMake 的各个核心特性。本讲作为总结，归纳现代 CMake（3.x+）的最佳实践，对比"旧式 CMake"与"现代 CMake"的差异，给出可直接套用的项目模板。掌握这些实践，能让你写出清晰、可维护、可移植的 CMake 配置。

### 原理

**现代 CMake 的核心理念**：

1. **以目标为中心**：所有配置附加在目标上，弃用全局变量式命令。
2. **属性传播**：用 `PUBLIC`/`PRIVATE`/`INTERFACE` 明确依赖关系。
3. **导入目标**：用 `find_package` 返回的导入目标，而非变量。
4. **显式优于隐式**：显式列出源文件、显式声明 C++ 标准、显式设置构建类型。
5. **配置时最小化**：能用生成器表达式解决的，不用配置时 `if`。

**旧式 vs 现代 CMake 对比**：

| 方面 | 旧式（避免） | 现代（推荐） |
|------|-------------|-------------|
| 头文件路径 | `include_directories(dir)` | `target_include_directories(t PUBLIC dir)` |
| 链接库 | `link_libraries(lib)` | `target_link_libraries(t PRIVATE lib)` |
| 编译选项 | `add_definitions(-DFOO)` | `target_compile_definitions(t PRIVATE FOO)` |
| 第三方库 | `${OPENSSL_LIBRARIES}` | `OpenSSL::SSL`（导入目标） |
| C++ 标准 | `add_definitions(-std=c++17)` | `set(CMAKE_CXX_STANDARD 17)` 或 `target_compile_features(t PRIVATE cxx_std_17)` |
| 全局编译选项 | `add_compile_options(-Wall)` | `target_compile_options(t PRIVATE -Wall)` |

**项目结构最佳实践**：

```
my_project/
├── CMakeLists.txt              # 根配置：project()、选项、add_subdirectory
├── cmake/                      # 自定义模块
│   ├── CompilerWarnings.cmake
│   ├── Sanitizers.cmake
│   └── FindMyDep.cmake
├── include/                    # 公开头文件
│   └── my_project/
│       └── public.h
├── src/                        # 源文件（内部）
│   ├── CMakeLists.txt
│   ├── internal.h
│   └── *.cpp
├── tests/                      # 测试
│   └── CMakeLists.txt
├── docs/                       # 文档
└── examples/                   # 示例
```

### 例子

**现代 CMake 项目模板**：

```cmake
# ========== 根 CMakeLists.txt ==========
cmake_minimum_required(VERSION 3.16)

# 项目声明：包含版本和语言
project(MyProject
    VERSION 1.0.0
    DESCRIPTION "A modern CMake project"
    LANGUAGES CXX
)

# ---------- 选项（缓存变量） ----------
option(BUILD_TESTS "Build unit tests" ON)
option(BUILD_DOCS "Build documentation" OFF)
option(ENABLE_SANITIZERS "Enable sanitizers" OFF)

# ---------- 通用配置 ----------
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)  # 生成 compile_commands.json

# 默认构建类型
if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
    set(CMAKE_BUILD_TYPE Release CACHE STRING "Build type" FORCE)
endif()

# ---------- 模块路径 ----------
list(APPEND CMAKE_MODULE_PATH ${CMAKE_CURRENT_SOURCE_DIR}/cmake)

# ---------- 通用函数 ----------
include(CompilerWarnings)
include(Sanitizers)

# ---------- 子目录 ----------
add_subdirectory(src)

if(BUILD_TESTS)
    enable_testing()
    add_subdirectory(tests)
endif()

if(BUILD_DOCS)
    add_subdirectory(docs)
endif()

# ---------- 安装与打包 ----------
include(GNUInstallDirs)
# ...（见第17讲）

# ---------- 打印配置摘要 ----------
message(STATUS "=== Configuration Summary ===")
message(STATUS "Project: ${PROJECT_NAME} v${PROJECT_VERSION}")
message(STATUS "Build type: ${CMAKE_BUILD_TYPE}")
message(STATUS "C++ standard: ${CMAKE_CXX_STANDARD}")
message(STATUS "Build tests: ${BUILD_TESTS}")
message(STATUS "Install prefix: ${CMAKE_INSTALL_PREFIX}")
```

`cmake/CompilerWarnings.cmake`：

```cmake
function(enable_project_warnings target)
    set(CLANG_GCC_WARNINGS
        -Wall
        -Wextra
        -Wpedantic
        -Wshadow
        -Wnon-virtual-dtor
        -Wold-style-cast
        -Wcast-align
        -Wunused
        -Woverloaded-virtual
        -Wconversion
        -Wnull-dereference
        -Wdouble-promotion
        -Wformat=2
    )

    if(MSVC)
        target_compile_options(${target} PRIVATE /W4 /permissive- /utf-8)
    else()
        target_compile_options(${target} PRIVATE ${CLANG_GCC_WARNINGS})
    endif()
endfunction()
```

`cmake/Sanitizers.cmake`：

```cmake
function(enable_sanitizers target)
    if(NOT ENABLE_SANITIZERS)
        return()
    endif()

    if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
        target_compile_options(${target} PRIVATE
            -fsanitize=address,undefined
            -fno-sanitize-recover=all
        )
        target_link_options(${target} PRIVATE
            -fsanitize=address,undefined
        )
    endif()
endfunction()
```

`src/CMakeLists.txt`：

```cmake
# 库目标
add_library(my_project_lib STATIC
    core.cpp
    utils.cpp
)

target_include_directories(my_project_lib
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_SOURCE_DIR}/include>
        $<INSTALL_INTERFACE:${CMAKE_INSTALL_INCLUDEDIR}>

        ${CMAKE_CURRENT_SOURCE_DIR}
)

target_compile_features(my_project_lib PUBLIC cxx_std_17)

enable_project_warnings(my_project_lib)
enable_sanitizers(my_project_lib)

add_library(MyProject::Lib ALIAS my_project_lib)

# 可执行文件
add_executable(my_project_app main.cpp)
target_link_libraries(my_project_app PRIVATE MyProject::Lib)
enable_project_warnings(my_project_app)
```

### 总结

**现代 CMake 核心原则**：
1. 以目标为中心：用 `target_*` 命令，弃用全局 `include_directories`/`link_libraries`/`add_definitions`。
2. 明确可见性：`PUBLIC`/`PRIVATE`/`INTERFACE` 表达依赖关系。
3. 用导入目标：`OpenSSL::SSL` 而非 `${OPENSSL_LIBRARIES}`。
4. 显式声明：C++ 标准、构建类型、源文件列表都显式设置。
5. 配置时最小化：能用生成器表达式解决的，不用配置时 `if`。

**项目组织**：
- 根 `CMakeLists.txt` 只做项目声明、选项、子目录引入。
- 通用配置封装为函数，放在 `cmake/` 目录。
- 公开头文件在 `include/`，内部头文件和源文件在 `src/`。
- 用 `add_library(NS::Name ALIAS real_target)` 创建命名空间别名。

**现代特性推荐**：
- `FetchContent`（3.11+）管理外部依赖源码。
- `target_compile_features` 声明需要的 C++ 特性。
- `CMAKE_EXPORT_COMPILE_COMMANDS` 生成 `compile_commands.json` 供 IDE/clangd 使用。
- `gtest_discover_tests` 自动注册 GoogleTest 测试到 CTest。

**避免的反模式**：
- 不要用全局 `include_directories`、`link_directories`、`add_definitions`。
- 不要用 `add_executable(name ${SOURCES})` 配合 `file(GLOB)`（除非加 `CONFIGURE_DEPENDS`）。
- 不要在 `CMAKE_CXX_FLAGS` 中硬编码编译选项。
- 不要用 `execute_process` 在配置时编译代码（用 `try_compile`）。
- 不要假设构建类型在配置时已知（多配置生成器中未知）。

掌握这些原则和实践，你就能写出专业级的 CMake 配置，管理从几十到几千个源文件的中大型 C++ 项目。
