## 第一章：基础入门

### 第1讲：什么是Ninja构建系统

#### 概念

Ninja是一个专注于**速度**的小型构建系统（build system）。它由Google工程师Evan Martin于2010年创建，最初是为了加速Chromium浏览器的编译而设计的。与Make、CMake等构建系统不同，Ninja的核心设计理念是：**只负责高效执行构建图，不负责生成构建图**。

Ninja的定位非常明确——它是构建系统的"后端"。它读取一种简单、紧凑的构建描述文件（通常命名为`build.ninja`），然后以尽可能快的速度执行其中的编译、链接等命令。至于如何从项目结构推导出这个构建文件，Ninja把它交给"前端"生成器（如CMake、GN、Meson等）来完成。

#### 原理

Ninja之所以快，源于几个关键设计决策：

第一，**极简的文件格式**。Ninja的构建文件采用行导向的纯文本格式，解析速度极快。一个包含数万条规则的`build.ninja`文件，Ninja可以在几十毫秒内完成解析并开始执行。相比之下，Makefile的解析涉及复杂的变量展开和模式匹配，开销要大得多。

第二，**依赖图预先构建**。Ninja在启动时就把所有构建规则解析成一个完整的依赖有向无环图（DAG），后续的增量构建只需检查文件时间戳即可决定哪些目标需要重新构建，无需重新解析规则。

第三，**并行执行**。Ninja默认根据CPU核心数启动并行任务，无需像Make那样手动指定`-j`参数。它还会智能调度，确保没有依赖关系的任务可以同时运行。

第四，**最小化I/O**。Ninja在执行命令前会批量检查所有文件的时间戳，而不是逐个检查，这减少了磁盘I/O次数，对大型项目尤其重要。

#### 例子

下面是一个最简单的Ninja构建文件示例，它编译一个C程序：

```ninja
# build.ninja - 编译 hello.c 为 hello 可执行文件

rule cc
  command = gcc -c $in -o $out
  description = 编译 $out

rule link
  command = gcc $in -o $out
  description = 链接 $out

build hello.o: cc hello.c
build hello: link hello.o

default hello
```

执行 `ninja` 命令后，Ninja会自动编译并链接生成 `hello` 可执行文件。如果再次执行 `ninja` 而源文件没有修改，它会立即报告"无需构建"（no work to do），这正是增量构建的体现。

与等效的Makefile相比，Ninja文件更简洁，且执行速度更快，尤其在大型项目中差异显著。

#### 总结

- Ninja是专注于速度的构建系统**后端**，不负责生成构建文件
- 核心设计：极简格式、预构建依赖图、并行执行、最小化I/O
- 通常配合CMake、GN等**前端生成器**使用
- 适合大型项目（如Chromium、LLVM等），增量构建速度极快
- 常见误区：Ninja不是Make的替代品，而是构建流水线中的执行层

### 第2讲：Ninja的安装与环境配置

#### 概念

Ninja是一个跨平台的命令行工具，支持Linux、macOS和Windows。它的安装方式非常灵活，既可以通过系统包管理器安装预编译版本，也可以从源码编译。对于大多数开发者来说，使用包管理器安装是最快捷的方式；而对于需要特定版本或自定义配置的场景，源码编译则更为合适。

#### 原理

Ninja本身是用C++编写的，但它的构建过程却不需要依赖Ninja自己——它提供了一个Python脚本`configure.py`用于生成Makefile，开发者可以用`make`来编译Ninja。这种"自举"方式确保了Ninja在没有预编译包的环境中也能轻松构建。

安装完成后，Ninja只提供一个名为`ninja`（在Windows上是`ninja.exe`）的可执行文件。这个单一文件包含了所有功能，没有额外的动态库依赖，这使得它非常适合作为项目的一部分进行分发。

Ninja的工作不依赖任何环境变量，但它会遵循标准的`PATH`变量来查找编译器、链接器等工具。因此，确保你的编译工具链（如gcc、clang、MSVC）在`PATH`中可用，是使用Ninja的前提条件。

#### 例子

**方式一：使用包管理器安装（推荐）**

```bash
# Ubuntu / Debian
sudo apt-get install ninja-build

# macOS (使用Homebrew)
brew install ninja

# Arch Linux
sudo pacman -S ninja

# Fedora
sudo dnf install ninja-build
```

**方式二：使用pip安装（跨平台）**

```bash
pip install ninja
```

这种方式安装的Ninja会放在Python的Scripts目录下，适合在CI/CD环境中快速部署。

**方式三：从源码编译**

```bash
git clone https://github.com/ninja-build/ninja.git
cd ninja
python configure.py --bootstrap
# 编译完成后，ninja可执行文件就在当前目录
sudo cp ninja /usr/local/bin/
```

**验证安装：**

```bash
$ ninja --version
1.11.1
```

如果看到版本号输出，说明安装成功。

#### 总结

- 推荐使用系统包管理器安装，简单快捷
- `pip install ninja`适合CI/CD和跨平台场景
- 源码编译使用`configure.py --bootstrap`，无需预装Ninja
- Ninja是单一可执行文件，无额外依赖，便于分发
- 安装后只需确保编译工具链在`PATH`中可用即可
- 使用`ninja --version`验证安装是否成功

### 第3讲：第一个Ninja构建文件

#### 概念

Ninja的构建文件通常命名为`build.ninja`，放在项目根目录下。当你在项目目录中执行`ninja`命令时，它会自动查找当前目录下的`build.ninja`文件并执行。这个文件是Ninja的核心输入，描述了项目中所有的构建规则、目标及其依赖关系。

一个`build.ninja`文件主要由以下几部分组成：变量声明、规则定义（rule）、构建语句（build）和默认目标（default）。理解这些组成部分的协作方式，是编写Ninja构建文件的第一步。

#### 原理

Ninja在读取`build.ninja`时，会按照从上到下的顺序解析每一行。解析过程中，它会把规则定义存储在一个规则表中，把构建语句转换成依赖图中的节点。当所有内容解析完毕后，Ninja拥有一个完整的依赖DAG（有向无环图）。

执行构建时，Ninja从默认目标（或命令行指定的目标）出发，沿着依赖图反向遍历，找出所有需要更新的文件。判断"需要更新"的依据是：目标文件不存在，或者目标文件的时间戳早于其依赖文件的时间戳。确定需要更新的任务后，Ninja根据CPU核心数并行执行对应的命令。

这种"先解析全部、再决定执行"的模式，使得Ninja能够全局优化执行顺序，避免不必要的重复构建。

#### 例子

让我们构建一个稍微完整一点的例子——编译一个包含两个源文件的C程序：

项目结构：
```
myproject/
├── build.ninja
├── main.c
└── utils.c
```

`build.ninja` 内容：

```ninja
# 定义编译器变量
cc = gcc
cflags = -Wall -O2

# 定义编译规则
rule cc
  command = $cc -MMD -MF $out.d $cflags -c $in -o $out
  description = 编译 $in
  depfile = $out.d
  deps = gcc

# 定义链接规则
rule link
  command = $cc $in -o $out
  description = 链接 $out

# 构建目标
build main.o: cc main.c
build utils.o: cc utils.c
build myapp: link main.o utils.o

# 默认目标
default myapp
```

`main.c` 内容：
```c
#include <stdio.h>
int utils_add(int a, int b);
int main() {
    printf("2 + 3 = %d\n", utils_add(2, 3));
    return 0;
}
```

`utils.c` 内容：
```c
int utils_add(int a, int b) {
    return a + b;
}
```

执行构建：
```bash
$ ninja
[2/3] 编译 main.c
[3/3] 编译 utils.c
[1/1] 链接 myapp

$ ./myapp
2 + 3 = 5
```

再次执行：
```bash
$ ninja
ninja: no work to do.
```

修改 `utils.c` 后再执行：
```bash
$ ninja
[1/3] 编译 utils.c
[1/1] 链接 myapp
```

可以看到，Ninja只重新编译了被修改的文件及其依赖的目标。

#### 总结

- `build.ninja`是Ninja的默认输入文件，放在项目根目录
- 文件由变量、规则（rule）、构建语句（build）、默认目标（default）组成
- Ninja先解析全部内容构建依赖DAG，再决定执行哪些任务
- 增量构建基于文件时间戳判断，只重建受影响的目标
- `$in`和`$out`是规则中的特殊变量，分别代表输入和输出文件
- `depfile`和`deps`用于自动追踪头文件依赖（后续章节详解）

### 第4讲：Ninja命令行基础

#### 概念

`ninja`命令行工具是用户与Ninja构建系统交互的主要接口。虽然Ninja的设计哲学是"让构建文件自己说话"，但命令行仍然提供了丰富的选项来控制构建行为、查询构建信息以及进行调试。掌握这些命令行选项，能够让你更高效地使用Ninja。

#### 原理

Ninja命令行的核心工作流程是：解析命令行参数 → 加载构建文件 → 构建依赖图 → 确定需要执行的任务 → 并行执行命令。在这个过程中，不同的命令行选项会影响各个阶段的行为。例如，`-j`选项控制并行度，`-v`选项改变命令输出的详细程度，`-t`选项则提供了一系列工具子命令用于查询和调试。

Ninja的命令行设计遵循Unix工具的传统：选项简洁、输出可预测、可通过管道与其他工具组合。这使得Ninja非常适合集成到CI/CD流水线和开发脚本中。

#### 例子

**基本用法：**

```bash
# 在当前目录查找 build.ninja 并执行默认目标
ninja

# 指定构建文件
ninja -f build_debug.ninja

# 构建特定目标
ninja myapp

# 构建多个目标
ninja main.o utils.o
```

**控制并行度：**

```bash
# 使用4个并行任务
ninja -j 4

# 不限制并行度（默认使用CPU核心数+2）
ninja -j 0
```

**输出控制：**

```bash
# 显示实际执行的命令（调试用）
ninja -v

# 安静模式，只输出错误
ninja -q

# 显示进度条（默认开启）
ninja --progress

# 不显示进度条
ninja --no-progress
```

**清理和重新构建：**

```bash
# 清理所有构建产物
ninja -t clean

# 清理特定目标
ninja -t clean myapp

# 强制重新构建（即使文件未修改）
ninja -t clean && ninja
```

**查询工具（-t 子命令）：**

```bash
# 列出所有可用的目标
ninja -t targets

# 列出所有规则
ninja -t rules

# 查看某个目标的所有依赖
ninja -t deps myapp

# 以文本形式输出依赖图
ninja -t browse myapp

# 查询某个目标的构建路径
ninja -t query myapp
```

**干运行模式：**

```bash
# 只显示将要执行的命令，不实际执行
ninja -n

# 干运行并显示详细命令
ninja -n -v
```

**实际输出示例：**

```bash
$ ninja -v
[1/3] gcc -MMD -MF main.o.d -Wall -O2 -c main.c -o main.o
[2/3] gcc -MMD -MF utils.o.d -Wall -O2 -c utils.o -o utils.o
[3/3] gcc main.o utils.o -o myapp
```

#### 总结

- `ninja`默认查找当前目录的`build.ninja`并执行默认目标
- `-j N`控制并行度，默认根据CPU核心数自动设置
- `-v`显示实际执行的命令，是调试构建问题的关键工具
- `-n`干运行模式只显示不执行，适合预览构建行为
- `-t`提供丰富的工具子命令：`targets`、`rules`、`clean`、`deps`、`browse`等
- `-f`指定构建文件，支持同一项目维护多套构建配置
- 命令行选项可以组合使用，如`ninja -v -j 8 myapp`

## 第二章：构建文件语法

### 第5讲：基本语法规则与注释

#### 概念

Ninja构建文件使用一种极简的、行导向的文本格式。每一行要么是一个声明（变量、规则、构建语句等），要么是空行或注释。Ninja的语法设计目标是让解析器尽可能简单和快速，因此它没有Makefile中复杂的模式匹配、条件判断和函数调用，只有最基本的声明式语法。

理解Ninja的语法规则是编写构建文件的基础。虽然在实际项目中，`build.ninja`通常由生成器自动产生，但掌握语法对于调试、优化和手动编写小型构建文件仍然非常重要。

#### 原理

Ninja的词法分析器按行处理输入文件。每一行的第一个非空白字符决定了这一行的类型：

- `#` 开头的行是注释，解析器会忽略整行内容
- 顶格的标识符后跟 `=` 表示变量赋值
- `rule` 关键字开头表示规则定义
- `build` 关键字开头表示构建语句
- `default` 关键字开头表示默认目标设置
- `include` 关键字开头表示包含另一个文件
- `subninja` 关键字开头表示包含子ninja文件
- 以空格或Tab开头的行是上一行的续行（属于上一条声明的属性）

Ninja对缩进有严格要求：顶层声明必须顶格（无前导空格），而属于某个声明的属性（如规则的`command`）必须缩进。通常使用两个空格作为缩进，但Ninja实际上接受任意数量的空格或Tab。

#### 例子

**注释：**

```ninja
# 这是一个整行注释
cc = gcc  # 行尾注释也是允许的

# 注释可以有多行
# 每行都需要以 # 开头
# Ninja没有块注释语法
```

**变量赋值：**

```ninja
# 顶层变量，顶格书写
cc = gcc
cflags = -Wall -O2 -std=c11

# 变量值可以包含空格，不需要引号
ldflags = -lm -lpthread
```

**规则定义（注意缩进）：**

```ninja
rule cc
  command = $cc $cflags -c $in -o $out
  description = 编译 $in
  depfile = $out.d
  deps = gcc
```

**构建语句：**

```ninja
build main.o: cc main.c
build utils.o: cc utils.c
build myapp: link main.o utils.o
```

**续行（使用 `$` 换行）：**

```ninja
# 当一行太长时，可以使用 $ 续行
cflags = -Wall -O2 -std=c11 \
         -Wextra -Wpedantic \
         -DDEBUG=1
```

**空行的作用：**

```ninja
# 空行不会影响解析，但可以提高可读性

cc = gcc

rule cc
  command = $cc -c $in -o $out

build main.o: cc main.c

# 空行在规则定义和构建语句之间是可选的
```

**常见语法错误：**

```ninja
# 错误：规则属性没有缩进
rule cc
command = gcc -c $in -o $out    # 这会被解析为顶层变量，而非规则属性

# 正确：
rule cc
  command = gcc -c $in -o $out
```

#### 总结

- Ninja语法是行导向的，每行一个声明
- `#`开头是注释，支持整行注释和行尾注释
- 顶层声明必须顶格，属性必须缩进（通常2个空格）
- 关键字包括：`rule`、`build`、`default`、`include`、`subninja`、`pool`
- 使用`$`续行处理过长的行
- 空行不影响解析，但能提高可读性
- 语法极其简单，没有条件判断和循环，复杂逻辑应交给生成器

### 第6讲：变量与变量扩展

#### 概念

变量是Ninja构建文件中实现复用和参数化的基本机制。Ninja中的变量分为两类：**顶层变量**（全局变量）和**规则内变量**（局部变量）。此外，Ninja还预定义了一批特殊变量（如`$in`、`$out`），它们在规则定义中具有特殊含义。

变量扩展是指在使用变量时，将变量名替换为其值的过程。Ninja的变量扩展规则简单但严格：所有变量引用都使用`$`前缀，多字符变量名需要用花括号`{}`或圆括号`()`包裹。

#### 原理

Ninja的变量扩展遵循以下规则：

1. **单字符变量名**：直接使用`$x`形式，如`$in`、`$out`
2. **多字符变量名**：使用`${name}`或`$(name)`形式，如`${cflags}`、`$(cc)`
3. **字面量`$`**：使用`$$`表示一个字面的美元符号
4. **扩展时机**：变量在引用处展开，而非定义时。这意味着如果变量在引用前被重新赋值，使用的是最后一次的值

Ninja预定义的特殊变量包括：
- `$in`：构建语句中的输入文件列表
- `$out`：构建语句中的输出文件
- `$depfile`：依赖文件的路径
- `$command`：规则中要执行的命令（在`build`语句中覆盖时使用）

变量扩展的顺序是：先展开构建语句中的变量，再将结果传递给规则，最后展开规则中的变量。这种"两层展开"机制使得规则可以参数化。

#### 例子

**基本变量定义和使用：**

```ninja
# 顶层变量
cc = gcc
cflags = -Wall -O2

rule cc
  # $cc 和 $cflags 在这里被展开
  command = $cc $cflags -c $in -o $out
  description = 编译 $in

build main.o: cc main.c
```

**多字符变量名：**

```ninja
compiler_flags = -Wall -O2 -std=c11

rule cc
  # 使用 ${} 或 () 包裹多字符变量名
  command = gcc ${compiler_flags} -c $in -o $out
```

**在构建语句中覆盖变量：**

```ninja
cflags = -Wall -O2

rule cc
  command = gcc $cflags -c $in -o $out

# 使用默认 cflags
build main.o: cc main.c

# 为特定目标覆盖 cflags
build debug.o: cc debug.c
  cflags = -Wall -O0 -g -DDEBUG

# 添加额外变量（不影响其他目标）
build optimized.o: cc optimized.c
  cflags = -Wall -O3 -march=native
```

**字面量`$`符号：**

```ninja
# 在Shell命令中使用 $ 需要转义
rule gen
  # $$ 展开为字面的 $
  command = echo "HOME=$$HOME" > $out
```

**变量展开顺序示例：**

```ninja
prefix = /usr
libdir = ${prefix}/lib

rule print
  command = echo $libdir > $out

build output.txt: print
```

执行后 `output.txt` 内容为 `/usr/lib`。

**使用 `$in` 和 `$out`：**

```ninja
rule cc
  command = gcc -c $in -o $out
  # $in = 输入文件, $out = 输出文件

# 这里 $in = "main.c", $out = "main.o"
build main.o: cc main.c

# 多个输入文件时，$in = "main.c utils.c"
build combined.o: cc main.c utils.c
```

#### 总结

- 变量分为顶层变量和规则内变量，还有预定义的特殊变量
- `$x`用于单字符变量名，`${name}`或`$(name)`用于多字符变量名
- `$$`表示字面的美元符号
- 变量在引用处展开，支持在`build`语句中覆盖规则使用的变量值
- `$in`和`$out`是最常用的特殊变量，分别代表输入和输出文件
- 变量展开是"两层"的：先展开build语句层，再展开rule层
- 理解变量扩展机制是参数化构建规则的关键

### 第7讲：规则定义rule

#### 概念

规则（rule）是Ninja中定义"如何构建某类文件"的核心机制。一条规则描述了一个构建步骤的命令模板，包括要执行的Shell命令、命令的描述文字、依赖文件的处理方式等。规则类似于编程语言中的函数定义——它定义了行为模板，而具体的构建语句则像函数调用，为规则提供具体的参数。

每条规则必须有一个唯一的名字，并且至少包含一个`command`属性。规则定义后，可以在任意多个构建语句中引用。

#### 原理

Ninja的规则定义使用`rule`关键字，后跟规则名，然后是缩进的属性列表。规则支持以下属性：

- **`command`**（必需）：要执行的Shell命令。这是规则的核心，Ninja通过执行这个命令来完成实际的构建工作。命令中通常使用`$in`、`$out`等变量。
- **`description`**（可选）：构建进度的描述文字，会显示在进度条中。良好的描述能帮助开发者理解当前正在做什么。
- **`depfile`**（可选）：指定依赖文件的路径。用于自动追踪头文件等隐式依赖。
- **`deps`**（可选）：指定依赖文件的格式，支持`gcc`和`msvc`两种。
- **`generator`**（可选）：设为`1`表示此规则生成其他构建文件，Ninja不会在清理时删除其输出。
- **`restat`**（可选）：设为`1`表示命令执行后重新检查输出文件的时间戳，如果未变化则不触发下游重建。
- **`rspfile`和`rspfile_content`**（可选）：用于Windows上的响应文件，处理超长命令行。

当Ninja执行一条规则时，它会将构建语句中提供的变量值代入规则的命令模板，然后通过Shell执行该命令。命令的退出码为0表示成功，非0表示失败。

#### 例子

**最基本的规则：**

```ninja
rule cc
  command = gcc -c $in -o $out
  description = 编译 $in

build main.o: cc main.c
```

**带依赖追踪的规则（推荐）：**

```ninja
rule cc
  command = gcc -MMD -MF $out.d -c $in -o $out
  description = 编译 $in
  depfile = $out.d
  deps = gcc

build main.o: cc main.c
# Ninja会自动读取 main.o.d 文件，追踪 main.c 包含的头文件
```

**使用变量参数化规则：**

```ninja
rule cc
  command = $cc $cflags -c $in -o $out
  description = 编译 $in ($cflags)

cc = gcc
cflags = -Wall -O2

build main.o: cc main.c
build debug.o: cc debug.c
  cflags = -Wall -O0 -g
```

**generator规则（生成构建文件）：**

```ninja
rule regenerate
  command = python generate_ninja.py > build.ninja
  generator = 1

build build.ninja: regenerate project.yaml
# 当 project.yaml 变化时，重新生成 build.ninja
# ninja -t clean 不会删除 build.ninja
```

**restat规则（避免不必要的重建）：**

```ninja
rule gen_header
  command = python gen_header.py $in $out
  description = 生成头文件 $out
  restat = 1

# 如果 gen_header.py 生成的头文件内容没变（时间戳可能更新但内容相同），
# restat 会让 Ninja 检查时间戳是否真的变化，避免下游级联重建
build generated.h: gen_header template.h
```

**Windows响应文件规则：**

```ninja
rule link
  command = link @$out.rsp
  description = 链接 $out
  rspfile = $out.rsp
  rspfile_content = $in

build myapp.exe: link main.obj utils.obj
# 当输入文件列表很长时（超过Windows命令行长度限制），
# Ninja会自动将输入列表写入 .rsp 文件
```

**多输出规则：**

```ninja
rule yacc
  command = yacc -d $in -o $out
  description = 生成解析器 $out

# yacc 同时生成 .c 和 .h 文件
build parser.c parser.h: yacc parser.y
```

#### 总结

- 规则用`rule`关键字定义，必须包含`command`属性
- `description`属性提供人类可读的进度信息
- `depfile`和`deps`用于自动追踪头文件依赖，是C/C++项目的标配
- `generator = 1`标记生成构建文件的规则，清理时不会删除其输出
- `restat = 1`避免内容未变但时间戳更新导致的级联重建
- `rspfile`用于Windows超长命令行场景
- 规则可以通过变量实现参数化，不同构建语句可传入不同参数
- 一条规则可被多个构建语句复用，是Ninja实现DRY原则的关键

### 第8讲：构建语句build

#### 概念

构建语句（build statement）是Ninja构建文件中将规则与具体文件关联起来的声明。每条构建语句声明了一个或多个输出文件、所使用的规则，以及该规则需要的输入文件。如果把规则比作函数定义，那么构建语句就是函数调用——它为规则提供具体的输入输出参数。

构建语句是Ninja依赖图的基本节点。Ninja通过分析所有构建语句，构建出一个完整的依赖有向无环图（DAG），然后根据这个图决定构建顺序和并行策略。

#### 原理

构建语句的基本语法是：

```
build OUTPUTS: RULE INPUTS | IMPLICIT_INPUTS || ORDER_ONLY_INPUTS
  VARIABLE = VALUE
  ...
```

各部分含义如下：

- **OUTPUTS**：输出文件列表，空格分隔。一个构建语句可以有多个输出文件。
- **RULE**：使用的规则名称。
- **INPUTS**：显式输入文件列表，空格分隔。这些文件的变化会触发输出重建。
- **`|` IMPLICIT_INPUTS**：隐式输入文件。这些文件也是依赖，但不会出现在规则的`$in`变量中。通常用于不希望传递给命令但需要追踪的文件。
- **`||` ORDER_ONLY_INPUTS**：顺序依赖。这些文件必须先构建完成，但它们的变化不会触发输出重建。通常用于确保目录存在等场景。
- **VARIABLE = VALUE**：缩进的变量赋值，为规则提供特定参数，覆盖顶层同名变量。

构建语句的依赖关系决定了执行顺序：如果目标A依赖目标B，那么B必须先于A构建。没有依赖关系的目标可以并行构建。

#### 例子

**基本构建语句：**

```ninja
rule cc
  command = gcc -c $in -o $out

rule link
  command = gcc $in -o $out

# 单输入单输出
build main.o: cc main.c
build utils.o: cc utils.c

# 多输入单输出
build myapp: link main.o utils.o
```

**多输出构建语句：**

```ninja
rule yacc
  command = yacc -d $in -o $out

# 一次生成两个文件
build parser.c parser.h: yacc parser.y
```

**隐式依赖（`|`）：**

```ninja
rule cc
  command = gcc -c $in -o $out

# config.h 是隐式依赖：如果它变化，main.o 会重建
# 但 config.h 不会出现在 $in 中
build main.o: cc main.c | config.h
```

**顺序依赖（`||`）：**

```ninja
rule mkdir
  command = mkdir -p $out

rule cc
  command = gcc -c $in -o build/$out

# 确保 build/ 目录先创建，但目录的存在不会触发重建
build build: mkdir
build main.o: cc main.c || build
```

**为规则提供参数：**

```ninja
rule cc
  command = $cc $cflags -c $in -o $out

cc = gcc

build main.o: cc main.c
  cflags = -O2

build debug.o: cc debug.c
  cflags = -O0 -g
```

**完整的依赖链示例：**

```ninja
cc = gcc
cflags = -Wall -O2

rule cc
  command = $cc -MMD -MF $out.d $cflags -c $in -o $out
  depfile = $out.d
  deps = gcc

rule link
  command = $cc $in -o $out

# 构建依赖链
build main.o: cc main.c
build parser.o: cc parser.c
build utils.o: cc utils.c

build myapp: link main.o parser.o utils.o

default myapp
```

Ninja会自动分析出构建顺序：先编译三个`.o`文件（可并行），再链接生成`myapp`。

**使用变量简化重复构建语句：**

```ninja
# 虽然Ninja没有循环，但可以用生成器或手动展开
build main.o: cc main.c
build parser.o: cc parser.c
build utils.o: cc utils.c
build io.o: cc io.c
build net.o: cc net.c
```

#### 总结

- 构建语句语法：`build 输出: 规则 输入 | 隐式输入 || 顺序依赖`
- 输出和输入都支持多个文件，空格分隔
- 显式输入出现在`$in`中，隐式输入不出现在`$in`中但会触发重建
- 顺序依赖（`||`）只保证构建顺序，不触发重建
- 构建语句可覆盖规则使用的变量，实现参数化
- Ninja通过分析所有构建语句自动构建依赖DAG
- 没有依赖关系的目标会自动并行构建
- 大量重复的构建语句通常由生成器自动产生

## 第三章：依赖与规则深入

### 第9讲：依赖关系管理

#### 概念

依赖关系是构建系统的核心。Ninja通过依赖关系决定哪些目标需要重建、以什么顺序构建、哪些任务可以并行执行。Ninja支持三种依赖类型：**显式依赖**（explicit dependencies）、**隐式依赖**（implicit dependencies）和**顺序依赖**（order-only dependencies）。此外，Ninja还能通过`depfile`机制自动追踪头文件等动态依赖。

理解这些依赖类型的区别和使用场景，是编写正确、高效构建文件的关键。错误的依赖声明会导致构建结果不正确（缺少依赖）或构建效率低下（多余依赖）。

#### 原理

Ninja的依赖管理基于文件时间戳。对于每条构建语句，Ninja会比较输出文件和所有依赖文件（显式+隐式）的修改时间。如果输出文件不存在，或任何依赖文件的时间戳晚于输出文件，Ninja就会重新执行该构建语句的命令。

三种依赖类型的区别：

1. **显式依赖**：在`build`语句中`:`之后、`|`之前列出的文件。它们出现在规则的`$in`变量中，其变化会触发输出重建。
2. **隐式依赖**：在`|`之后、`||`之前列出的文件。它们不出现在`$in`中，但其变化仍会触发输出重建。适用于不需要传递给命令但需要追踪的文件（如生成的头文件）。
3. **顺序依赖**：在`||`之后列出的文件。它们只保证构建顺序（依赖文件先构建），但其变化不会触发输出重建。适用于确保目录存在等场景。

此外，`depfile`机制允许构建命令在执行时生成一个依赖文件，Ninja会在下次构建时读取这个文件，将其中的依赖添加到构建语句的依赖列表中。这对于C/C++头文件依赖特别重要——编译器可以自动输出源文件包含的所有头文件。

#### 例子

**三种依赖类型的对比：**

```ninja
rule cc
  command = gcc -c $in -o $out

# 显式依赖：main.c 出现在 $in 中
build main.o: cc main.c

# 显式 + 隐式依赖：config.h 变化会重建 main.o，但不传给命令
build main.o: cc main.c | config.h

# 显式 + 隐式 + 顺序依赖：确保 objdir 先创建
build main.o: cc main.c | config.h || objdir

rule mkdir
  command = mkdir -p $out
build objdir: mkdir
```

**使用depfile自动追踪头文件依赖：**

```ninja
rule cc
  command = gcc -MMD -MF $out.d -c $in -o $out
  description = 编译 $in
  depfile = $out.d
  deps = gcc

build main.o: cc main.c
```

当Ninja执行编译命令时，gcc的`-MMD -MF`选项会生成一个`main.o.d`文件，内容类似：

```
main.o: main.c utils.h config.h /usr/include/stdio.h
```

Ninja在下次构建时会自动读取这个文件，将`utils.h`和`config.h`添加为`main.o`的依赖。如果这些头文件被修改，`main.o`会自动重建。

**`deps`选项的两种格式：**

```ninja
# gcc格式：depfile中每行是 "目标: 依赖1 依赖2 ..."
rule cc_gcc
  command = gcc -MMD -MF $out.d -c $in -o $out
  depfile = $out.d
  deps = gcc

# msvc格式：depfile中每行只有依赖文件路径
rule cc_msvc
  command = cl /showIncludes /c $in /Fo$out
  deps = msvc
  # msvc格式不需要 depfile，Ninja从命令输出中解析依赖
```

**隐式依赖的典型场景——生成的头文件：**

```ninja
rule gen_header
  command = python gen.py $in > $out

rule cc
  command = gcc -c $in -o $out

# 生成 config.h
build config.h: gen_header config.template

# main.c 包含了 config.h
# 将 config.h 作为隐式依赖，这样它变化时 main.o 会重建
# 但 config.h 不会传给 gcc 命令（因为 $in 只有 main.c）
build main.o: cc main.c | config.h
```

**顺序依赖的典型场景——创建目录：**

```ninja
rule mkdir
  command = mkdir -p $out

rule cc
  command = gcc -c $in -o $out

# 创建输出目录
build builddir: mkdir

# 所有 .o 文件都依赖 builddir 先创建
# 但 builddir 的变化（时间戳更新）不会触发 .o 重建
build main.o: cc main.c || builddir
build utils.o: cc utils.c || builddir
```

#### 总结

- 三种依赖：显式（在`$in`中）、隐式（不在`$in`中但触发重建）、顺序（只保证顺序不触发重建）
- `depfile` + `deps`机制自动追踪头文件依赖，是C/C++项目的必备配置
- gcc格式使用`-MMD -MF`生成依赖文件，msvc格式从`/showIncludes`输出解析
- 隐式依赖适用于生成的头文件等"不传给命令但需要追踪"的场景
- 顺序依赖适用于确保目录存在等"只需先执行但不触发重建"的场景
- 正确的依赖声明是构建正确性的保证，过多依赖会降低并行度
- 使用`ninja -t deps`命令可以查看依赖信息，用于调试依赖问题

### 第10讲：默认目标与phony规则

#### 概念

默认目标（default target）是当执行`ninja`命令而不指定目标时，Ninja自动构建的目标。phony规则是一种特殊规则，用于创建不对应实际文件的"虚拟目标"，通常作为一组目标的别名。这两个机制配合使用，可以为用户提供简洁的构建入口。

在大型项目中，`build.ninja`可能包含成百上千个构建目标。默认目标和phony规则让用户无需记住所有目标名称，只需执行`ninja`就能构建整个项目，或通过有意义的别名构建特定部分。

#### 原理

**默认目标**通过`default`关键字声明。如果`build.ninja`中没有`default`声明，Ninja会将文件中第一个构建语句的输出作为默认目标（但依赖这个行为是不好的实践，建议显式声明默认目标）。可以指定多个默认目标，Ninja会构建所有指定的目标。

**phony规则**是Ninja内置的特殊规则，名称固定为`phony`。当一条构建语句使用`phony`规则时，它创建一个虚拟目标——这个目标不对应实际文件，而是作为其输入文件的别名。phony目标的"构建"实际上只是构建它的所有输入。

phony规则的一个重要特性是：即使存在同名的实际文件，phony目标也不会被当作文件来检查时间戳。这使得phony目标非常适合用作"总是需要构建"的入口点。

#### 例子

**默认目标：**

```ninja
rule cc
  command = gcc -c $in -o $out
rule link
  command = gcc $in -o $out

build main.o: cc main.c
build utils.o: cc utils.c
build myapp: link main.o utils.o

# 设置默认目标
default myapp

# 执行 ninja 时，自动构建 myapp
# 执行 ninja main.o 时，只构建 main.o
```

**phony规则作为别名：**

```ninja
rule cc
  command = gcc -c $in -o $out

build main.o: cc main.c
build utils.o: cc utils.c
build parser.o: cc parser.c
build io.o: cc io.c

# 创建别名 "all_objs" 代表所有 .o 文件
build all_objs: phony main.o utils.o parser.o io.o

default all_objs
```

**phony规则分组构建：**

```ninja
# 将目标分组，方便按需构建
build core: phony main.o utils.o
build net: phony socket.o http.o ftp.o
build ui: phony window.o button.o menu.o

build everything: phony core net ui

default everything

# ninja core    - 只构建核心模块
# ninja net     - 只构建网络模块
# ninja         - 构建所有
```

**phony规则用于"总是执行"的任务：**

```ninja
rule test
  command = ./run_tests.sh

# phony 目标 "test" 总是被视为需要构建
# 因为 phony 目标不检查时间戳
build test: phony
  # 这里没有输入，但 test 是 phony 所以每次都会执行

# 也可以让 test 依赖可执行文件
build test: phony myapp
  # 先确保 myapp 构建，然后...
  # 注意：phony 不会执行命令，只是构建依赖

# 如果需要在 phony 上执行命令，需要配合实际规则
rule run_test
  command = ./myapp --test
build check: run_test myapp
  # check 依赖 myapp，每次都会重新执行测试
```

**phony规则处理目录依赖：**

```ninja
rule mkdir
  command = mkdir -p $out

# 使用 phony 表示"目录已创建"这个状态
build builddir: mkdir
build dirs: phony builddir

rule cc
  command = gcc -c $in -o builddir/$out

build main.o: cc main.c || dirs
```

**多个默认目标：**

```ninja
build app: link main.o utils.o
build docs: sphinx source/

# 同时设置两个默认目标
default app docs
```

#### 总结

- `default`关键字声明默认目标，建议总是显式设置
- `phony`是内置规则，创建不对应实际文件的虚拟目标
- phony目标不检查时间戳，适合作为别名和"总是构建"的入口
- 使用phony将目标分组，提供有意义的构建入口（如`all`、`test`、`clean`）
- 可以指定多个默认目标，Ninja会全部构建
- phony规则不执行命令，只构建其依赖；需要执行命令应配合实际规则
- 良好的phony设计能极大提升大型项目的可用性

### 第11讲：变量作用域与优先级

#### 概念

Ninja的变量作用域规则决定了在规则定义和构建语句中，变量引用如何被解析。理解作用域和优先级对于编写正确的参数化构建文件至关重要。Ninja的变量作用域相对简单，但有几个关键细节需要注意，特别是顶层变量、规则变量和构建语句变量之间的优先级关系。

#### 原理

Ninja的变量作用域分为三个层次，优先级从低到高依次为：

1. **顶层变量**（Top-level variables）：在`build.ninja`文件顶层定义的变量，对所有规则和构建语句可见。优先级最低。
2. **规则内变量**（Rule variables）：在`rule`块内定义的变量，只在该规则内可见。优先级高于顶层变量。
3. **构建语句变量**（Build-edge variables）：在`build`语句中通过缩进赋值的变量，只在该构建语句中可见。优先级最高。

当Ninja展开规则中的变量时，解析顺序如下：
- 首先查找构建语句中是否为该变量赋值
- 如果没有，查找规则定义中是否赋值
- 如果还没有，使用顶层变量的值
- 如果都没有，变量展开为空字符串

特殊变量`$in`、`$out`、`$depfile`等由Ninja根据构建语句自动设置，优先级最高，不能被覆盖。

#### 例子

**三层变量优先级：**

```ninja
# 顶层变量
cflags = -O2

rule cc
  # 规则内变量
  cflags = -O1
  command = gcc $cflags -c $in -o $out

# 使用规则内的 cflags = -O1
build main.o: cc main.c

# 构建语句变量覆盖规则内变量
build debug.o: cc debug.c
  cflags = -O0 -g    # 这里 cflags = -O0 -g

# 没有覆盖，仍然使用规则内的 cflags = -O1
build utils.o: cc utils.c
```

**顶层变量作为默认值：**

```ninja
cc = gcc
cflags = -Wall -O2

rule cc
  command = $cc $cflags -c $in -o $out
  # 这里没有定义 cc 和 cflags，会使用顶层变量

build main.o: cc main.c
  # 没有覆盖，使用顶层 cflags = -Wall -O2

build optimized.o: cc optimized.c
  cflags = -Wall -O3 -march=native
  # 覆盖为 -O3
```

**规则内变量作为默认值：**

```ninja
rule cc
  command = $cc $cflags -c $in -o $out
  cc = gcc           # 规则内默认值
  cflags = -Wall     # 规则内默认值

# 使用规则内默认值
build main.o: cc main.c

# 覆盖规则内默认值
build clang.o: cc clang.c
  cc = clang
  cflags = -Wall -Weverything
```

**特殊变量不可覆盖：**

```ninja
rule cc
  command = gcc -c $in -o $out
  # $in 和 $out 由 Ninja 根据构建语句自动设置

build main.o: cc main.c
  # $in = "main.c", $out = "main.o"
  # 不能通过 in = xxx 来覆盖（虽然语法上允许，但语义错误）
```

**变量在构建语句中的使用：**

```ninja
rule cc
  command = $cc $cflags -c $in -o $out -D$define

cc = gcc
cflags = -Wall

build main.o: cc main.c
  define = APP_VERSION=1

build utils.o: cc utils.c
  define = APP_VERSION=1
  cflags = -Wall -O2
```

**subninja中的变量作用域：**

```ninja
# 顶层变量
cflags = -O2

# subninja 文件有自己的作用域
subninja sub/build.ninja
# sub/build.ninja 中的顶层变量不会影响主文件
# 但主文件的顶层变量在 subninja 中可见（只读继承）
```

**变量展开是即时的：**

```ninja
cflags = -O2

rule cc
  command = gcc $cflags -c $in -o $out

build a.o: cc a.c
  # 此时 cflags = -O2

cflags = -O3    # 重新赋值

build b.o: cc b.c
  # 此时 cflags = -O3（使用最后一次的值）

# 注意：a.o 已经构建完成，不受影响
# 但如果重新构建 a.o，会使用 -O3
```

#### 总结

- 变量优先级：构建语句变量 > 规则内变量 > 顶层变量
- 特殊变量`$in`、`$out`由Ninja自动设置，不可覆盖
- 顶层变量作为全局默认值，规则内变量作为规则默认值，构建语句变量用于特化
- 变量在引用处展开，使用最后一次赋值的值
- `subninja`包含的文件有自己的作用域，但能继承父文件的顶层变量
- 理解作用域对于参数化构建和避免意外覆盖至关重要
- 良好的变量命名和分层设计能提高构建文件的可维护性

## 第四章：高级特性

### 第12讲：子ninja文件包含

#### 概念

随着项目规模增长，单个`build.ninja`文件会变得非常庞大且难以维护。Ninja提供了两种文件包含机制来解决这个问题：`include`和`subninja`。这两种机制都允许将构建规则拆分到多个文件中，但它们在变量作用域和规则可见性上有重要区别。

`include`将另一个文件的内容直接插入到当前位置，就像C语言的`#include`一样——被包含文件与包含文件共享同一个作用域。`subninja`则创建一个新的作用域，被包含文件可以有自己的顶层变量，但能继承父文件的变量（只读）。

#### 原理

**include机制**：
- 语法：`include path/to/file.ninja`
- 被包含文件的内容在当前位置被解析
- 变量、规则、构建语句都进入当前作用域
- 适合共享公共配置（如变量定义、通用规则）

**subninja机制**：
- 语法：`subninja path/to/file.ninja`
- 被包含文件在新的作用域中解析
- 父文件的顶层变量在子文件中可见（作为初始值）
- 子文件中重新赋值的变量不影响父文件
- 子文件中定义的规则和构建语句全局可见
- 适合按模块或子目录组织构建逻辑

这两种机制使得大型项目可以按目录结构组织构建文件，每个子目录维护自己的`build.ninja`，然后通过`subninja`在顶层文件中汇总。

#### 例子

**使用include共享公共配置：**

`common.ninja`:
```ninja
# 公共变量
cc = gcc
cxx = g++
cflags = -Wall -O2
cxxflags = -Wall -O2 -std=c++17

# 公共规则
rule cc
  command = $cc -MMD -MF $out.d $cflags -c $in -o $out
  depfile = $out.d
  deps = gcc
  description = 编译 $in

rule cxx
  command = $cxx -MMD -MF $out.d $cxxflags -c $in -o $out
  depfile = $out.d
  deps = gcc
  description = 编译 $in

rule link
  command = $cxx $in -o $out
  description = 链接 $out
```

`build.ninja`:
```ninja
include common.ninja

build main.o: cxx main.cpp
build utils.o: cxx utils.cpp
build myapp: link main.o utils.o

default myapp
```

**使用subninja按模块组织：**

项目结构：
```
project/
├── build.ninja          # 顶层文件
├── common.ninja         # 公共配置
├── core/
│   └── build.ninja      # 核心模块构建
├── net/
│   └── build.ninja      # 网络模块构建
└── ui/
    └── build.ninja      # UI模块构建
```

顶层 `build.ninja`:
```ninja
# 公共变量
cc = gcc
cxx = g++
cflags = -Wall -O2
builddir = build

# 包含各子模块
subninja core/build.ninja
subninja net/build.ninja
subninja ui/build.ninja

# 顶层链接目标
build myapp: link $
    build/core/main.o build/core/utils.o $
    build/net/socket.o build/net/http.o $
    build/ui/window.o build/ui/button.o

default myapp
```

`core/build.ninja`:
```ninja
# 继承父文件的 cc, cxx, cflags, builddir
# 可以覆盖局部变量
cflags = -Wall -O2 -DCORE_MODULE

rule cc
  command = $cc -MMD -MF $out.d $cflags -c $in -o $out
  depfile = $out.d
  deps = gcc

build build/core/main.o: cc core/main.c
build build/core/utils.o: cc core/utils.c
```

**include vs subninja 的变量作用域对比：**

```ninja
# 顶层文件
cflags = -O2

# 使用 include：共享作用域
include config.ninja
# 如果 config.ninja 中有 cflags = -O3，则此处 cflags 变为 -O3

# 使用 subninja：独立作用域
subninja sub.ninja
# sub.ninja 中即使有 cflags = -O3，也不影响此处的 cflags（仍为 -O2 或 include 后的值）
```

**动态包含（使用变量）：**

```ninja
# 可以使用变量作为文件路径
config = debug
include config/$config.ninja

# 根据配置包含不同的规则文件
subninja rules/$config.ninja
```

**递归包含：**

```ninja
# a.ninja
include b.ninja

# b.ninja
include c.ninja

# c.ninja
rule cc
  command = gcc -c $in -o $out

# 所有规则都在同一个作用域中
```

#### 总结

- `include`将文件内容插入当前位置，共享作用域
- `subninja`创建新作用域，继承父文件变量但修改不影响父文件
- 使用`include`共享公共配置（变量、规则定义）
- 使用`subninja`按模块或子目录组织构建逻辑
- 子文件中定义的规则和构建语句全局可见（跨作用域）
- 大型项目应按目录结构拆分构建文件，用`subninja`汇总
- 文件路径可以使用变量，实现按配置动态包含

### 第13讲：构建池pool与并发控制

#### 概念

构建池（pool）是Ninja中用于控制特定规则并发执行数量的机制。默认情况下，Ninja根据CPU核心数全局并行执行所有任务。但有些任务不适合高并发——例如，链接器通常消耗大量内存，同时运行太多链接任务会导致内存不足；I/O密集型任务并行过多反而会降低性能。

通过定义构建池，可以为特定规则设置独立的并发限制，实现更精细的资源管理。这是Ninja在大型项目中保持构建稳定性和效率的重要特性。

#### 原理

Ninja的pool机制允许你定义一个命名的并发槽位池。每个pool有一个`depth`属性，表示该pool允许的最大并发任务数。当一条构建语句指定使用某个pool时，Ninja会确保该pool中同时运行的任务不超过`depth`指定的数量。

pool的定义使用`pool`关键字，语法与`rule`类似。构建语句通过`pool`变量指定使用的池。Ninja内置了一个名为`console`的特殊pool，其depth为1，用于需要交互式输入输出的任务。

pool的并发限制是独立的——即使全局`-j`参数允许64个并行任务，如果一个pool的depth为4，那么使用该pool的规则最多只能同时运行4个任务。其他不使用该pool的任务仍可使用全局并行度。

#### 例子

**定义和使用pool：**

```ninja
# 定义链接池，限制同时只运行2个链接任务
pool link_pool
  depth = 2

rule cc
  command = gcc -c $in -o $out

rule link
  command = gcc $in -o $out
  pool = link_pool    # 此规则使用 link_pool

build main.o: cc main.c
build utils.o: cc utils.c
build parser.o: cc parser.c

# 多个链接任务，但最多同时运行2个
build app1: link main.o
build app2: link utils.o
build app3: link parser.o
```

**控制内存密集型任务：**

```ninja
# 链接器消耗大量内存，限制并发
pool link_pool
  depth = 1

# LTO（链接时优化）更耗内存
pool lto_pool
  depth = 2

rule link
  command = gcc $in -o $out
  pool = link_pool

rule link_lto
  command = gcc -flto $in -o $out
  pool = lto_pool

build app: link main.o utils.o
build app_opt: link_lto main.o utils.o
```

**内置console pool：**

```ninja
# console 是内置 pool，depth = 1
# 用于需要交互式输入输出的任务
rule test_interactive
  command = ./run_tests.sh
  pool = console

build check: test_interactive myapp
# 测试任务使用 console pool，确保输出不被其他任务干扰
```

**I/O密集型任务的pool：**

```ninja
# 文件复制等I/O任务，限制并发避免磁盘争用
pool io_pool
  depth = 4

rule copy
  command = cp $in $out
  pool = io_pool

build dist/main.c: copy src/main.c
build dist/utils.c: copy src/utils.c
build dist/parser.c: copy src/parser.c
build dist/io.c: copy src/io.c
```

**在构建语句中指定pool：**

```ninja
pool heavy_pool
  depth = 2

rule cc
  command = gcc -c $in -o $out

# 默认使用全局并行度
build main.o: cc main.c

# 特定目标使用 pool
build huge_file.o: cc huge_file.c
  pool = heavy_pool
```

**全局并行度与pool的关系：**

```bash
# 全局允许16个并行任务
ninja -j 16

# 但如果 link_pool depth = 2
# 那么链接任务最多同时运行2个
# 其他14个槽位可用于编译等任务
```

**实际项目中的pool配置（Chromium风格）：**

```ninja
# 链接任务通常很重，限制并发
pool link_pool
  depth = 1

# C++编译消耗较多内存
pool cc_pool
  depth = 8

rule cxx
  command = $cxx $cxxflags -c $in -o $out
  pool = cc_pool

rule link
  command = $cxx $in -o $out
  pool = link_pool
```

#### 总结

- pool通过`pool`关键字定义，`depth`属性指定最大并发数
- 规则或构建语句通过`pool`变量指定使用的池
- pool的并发限制独立于全局`-j`参数
- 内置`console` pool（depth=1）用于交互式任务
- 适用于内存密集型任务（链接、LTO）和I/O密集型任务
- 合理的pool配置能避免资源争用，提升构建稳定性
- 大型项目通常为链接等重任务设置低并发pool

### 第14讲：响应文件response file

#### 概念

响应文件（response file）是Ninja为解决Windows命令行长度限制而引入的机制。Windows系统对命令行长度有32KB的限制（`CreateProcess`的`lpCommandLine`参数），当链接大量目标文件时，命令行可能超过这个限制导致构建失败。

响应文件机制允许Ninja将过长的参数列表写入一个临时文件，然后在命令中通过`@file.rsp`语法引用该文件。虽然这个机制主要为Windows设计，但在Linux/macOS上也可以使用，用于处理超长命令行。

#### 原理

Ninja的响应文件通过规则的两个属性配合使用：

- **`rspfile`**：指定响应文件的路径。Ninja在执行命令前会创建这个文件。
- **`rspfile_content`**：指定响应文件的内容。通常使用`$in`等变量，将输入文件列表写入文件。

当规则定义了这两个属性后，Ninja的执行流程变为：
1. 将`rspfile_content`展开后的内容写入`rspfile`指定的文件
2. 执行规则的`command`，命令中可以通过`$rspfile`引用响应文件路径（但通常直接在command中硬编码`@`引用）

响应文件在每次构建时都会重新生成，因此不会有过时的问题。Ninja会自动管理响应文件的创建和清理。

#### 例子

**基本的响应文件规则：**

```ninja
rule link
  command = link @$out.rsp
  rspfile = $out.rsp
  rspfile_content = $in
  description = 链接 $out

build myapp.exe: link main.obj utils.obj parser.obj io.obj net.obj
# Ninja 会创建 myapp.rsp，内容为：
# main.obj utils.obj parser.obj io.obj net.obj
# 然后执行：link @myapp.rsp
```

**带额外参数的响应文件：**

```ninja
rule link
  command = link /OUT:$out @$out.rsp
  rspfile = $out.rsp
  rspfile_content = $in /LIBPATH:lib additional.lib

build myapp.exe: link main.obj utils.obj
# myapp.rsp 内容：
# main.obj utils.obj /LIBPATH:lib additional.lib
```

**Linux上使用响应文件（gcc/ar）：**

```ninja
# ar 归档工具支持 @file 语法
rule ar
  command = ar rcs $out @$out.rsp
  rspfile = $out.rsp
  rspfile_content = $in

build libmylib.a: ar main.o utils.o parser.o io.o net.o
```

**gcc链接时使用响应文件：**

```ninja
rule link
  command = gcc @$out.rsp -o $out
  rspfile = $out.rsp
  rspfile_content = $in -lm -lpthread

build myapp: link main.o utils.o parser.o
```

**MSVC编译器使用响应文件：**

```ninja
rule cc
  command = cl /c @$out.rsp /Fo$out
  rspfile = $out.rsp
  rspfile_content = $in $cflags /I include

cflags = /O2 /W3 /DDEBUG=1

build main.obj: cc main.c
build utils.obj: cc utils.c
```

**条件性使用响应文件（生成器常见做法）：**

```ninja
# 生成器通常会根据输入文件数量决定是否使用响应文件
# Ninja 本身不提供条件判断，但生成器可以生成不同的规则

# 对于少量文件，直接使用命令行
rule link_short
  command = link $in /OUT:$out

# 对于大量文件，使用响应文件
rule link_long
  command = link @$out.rsp /OUT:$out
  rspfile = $out.rsp
  rspfile_content = $in
```

**响应文件与变量的配合：**

```ninja
rule link
  command = gcc @$out.rsp -o $out $ldflags
  rspfile = $out.rsp
  rspfile_content = $in $libs

ldflags = -pthread
libs = -lm -lcrypto -lssl

build myapp: link main.o utils.o net.o
# myapp.rsp 内容：
# main.o utils.o net.o -lm -lcrypto -lssl
# 实际执行：gcc @myapp.rsp -o myapp -pthread
```

#### 总结

- 响应文件解决Windows命令行长度限制（32KB）问题
- 通过`rspfile`（文件路径）和`rspfile_content`（文件内容）两个属性配置
- 命令中使用`@file.rsp`语法引用响应文件
- 每次构建时自动重新生成响应文件，不会过时
- 主要用于Windows的MSVC工具链，Linux/macOS上也可用于ar等工具
- 生成器通常会根据输入数量决定是否使用响应文件
- 是大型项目在Windows上成功构建的关键机制

### 第15讲：构建类型与参数化

#### 概念

在实际项目中，通常需要支持多种构建类型（如Debug、Release、RelWithDebInfo等），每种类型有不同的编译选项和输出目录。Ninja本身不支持条件判断和循环，但通过变量参数化和文件组织，可以灵活地支持多种构建类型。

参数化构建的核心思想是：将可变部分提取为变量，通过不同的变量值生成不同的构建配置。这通常配合生成器（如CMake）实现，但理解手动实现参数化构建有助于深入理解Ninja的工作机制。

#### 原理

Ninja实现多构建类型的主要策略有三种：

1. **多文件策略**：为每种构建类型生成独立的`build.ninja`文件（如`build/debug.ninja`和`build/release.ninja`），通过`ninja -f`选择。
2. **变量驱动策略**：在单个文件中通过变量区分不同配置，使用phony目标分组。
3. **生成器策略**：由CMake等生成器在配置阶段确定构建类型，生成对应的`build.ninja`。

第一种策略最清晰，也是CMake等工具采用的方式。每种构建类型有独立的输出目录，互不干扰。第二种策略适合手动维护的小型项目。第三种策略是实际项目中最常见的方式。

#### 例子

**策略一：多文件策略（推荐）**

`build/debug.ninja`:
```ninja
builddir = build/debug
cflags = -O0 -g -DDEBUG
cc = gcc

rule cc
  command = $cc -MMD -MF $out.d $cflags -c $in -o $out
  depfile = $out.d
  deps = gcc

rule link
  command = $cc $in -o $out

build $builddir/main.o: cc main.c
build $builddir/utils.o: cc utils.c
build $builddir/myapp: link $builddir/main.o $builddir/utils.o

default $builddir/myapp
```

`build/release.ninja`:
```ninja
builddir = build/release
cflags = -O3 -DNDEBUG
cc = gcc

rule cc
  command = $cc -MMD -MF $out.d $cflags -c $in -o $out
  depfile = $out.d
  deps = gcc

rule link
  command = $cc $in -o $out

build $builddir/main.o: cc main.c
build $builddir/utils.o: cc utils.c
build $builddir/myapp: link $builddir/main.o $builddir/utils.o

default $builddir/myapp
```

使用方式：
```bash
ninja -f build/debug.ninja     # 构建Debug版本
ninja -f build/release.ninja   # 构建Release版本
```

**策略二：变量驱动策略**

```ninja
# 通过不同的 phony 目标区分构建类型
cc = gcc

rule cc_debug
  command = $cc -O0 -g -DDEBUG -c $in -o $out

rule cc_release
  command = $cc -O3 -DNDEBUG -c $in -o $out

rule link
  command = $cc $in -o $out

build debug/main.o: cc_debug main.c
build debug/utils.o: cc_debug utils.c
build debug/myapp: link debug/main.o debug/utils.o

build release/main.o: cc_release main.c
build release/utils.o: cc_release utils.c
build release/myapp: link release/main.o release/utils.o

build debug: phony debug/myapp
build release: phony release/myapp

# 不设默认目标，强制用户指定
# ninja debug    或    ninja release
```

**策略三：使用include共享公共部分**

`common.ninja`:
```ninja
cc = gcc

rule cc
  command = $cc -MMD -MF $out.d $cflags -c $in -o $out
  depfile = $out.d
  deps = gcc

rule link
  command = $cc $in -o $out
```

`build/debug.ninja`:
```ninja
include ../common.ninja
cflags = -O0 -g -DDEBUG
builddir = build/debug

build $builddir/main.o: cc main.c
build $builddir/utils.o: cc utils.c
build $builddir/myapp: link $builddir/main.o $builddir/utils.o
default $builddir/myapp
```

**参数化规则示例：**

```ninja
# 使用变量参数化规则，适应不同编译器
cc = gcc
cxx = g++

rule cc
  command = $cc $cflags -c $in -o $out

rule cxx
  command = $cxx $cxxflags -c $in -o $out

# 通过覆盖变量支持不同配置
build main.o: cc main.c
  cflags = -O2

build main_debug.o: cc main.c
  cflags = -O0 -g

build main_clang.o: cc main.c
  cflags = -O2
  cc = clang
```

**跨平台参数化：**

```ninja

# 以下是生成器输出的结果示例

  command = $cc $cflags -c $in -o $out

# Linux 配置
if_linux_cc = gcc
if_linux_cflags = -Wall -O2 -DPLATFORM_LINUX

# Windows 配置
if_win_cc = cl

# 实际使用（生成器会选择正确的变量）

cflags = $if_linux_cflags

build main.o: cc main.c
```

#### 总结

- Ninja不支持条件判断和循环，参数化通过变量和文件组织实现
- 多构建类型推荐使用多文件策略，每种类型独立文件和输出目录
- `ninja -f`选择不同的构建文件，实现配置切换
- 使用`include`共享公共规则和变量，减少重复
- 变量驱动策略适合小型项目，通过phony目标分组
- 实际项目中，构建类型通常由CMake等生成器在配置阶段确定
- 跨平台支持由生成器处理，Ninja文件中只包含特定平台的配置

## 第五章：生成器集成

### 第16讲：CMake生成Ninja

#### 概念

CMake是最流行的C/C++项目构建系统生成器之一。它本身不直接构建代码，而是根据`CMakeLists.txt`配置文件生成具体的构建文件（如Makefile或`build.ninja`）。当使用Ninja作为后端时，CMake会生成`build.ninja`文件，然后由Ninja执行实际的编译和链接。

CMake与Ninja的组合（通常称为"CNinja"）是现代C/C++项目的主流构建方案。它结合了CMake强大的项目配置能力和Ninja卓越的构建速度，被广泛用于LLVM、Chromium等大型项目。

#### 原理

CMake的工作流程分为两个阶段：**配置阶段**和**生成阶段**。在配置阶段，CMake读取`CMakeLists.txt`，检测编译器和依赖库，收集构建信息。在生成阶段，CMake将收集到的信息转换为目标构建系统的文件格式。

当指定`-G Ninja`时，CMake的Ninja生成器会遍历所有目标（targets）和源文件，为每个编译单元生成对应的`build`语句，为链接目标生成链接语句，并自动设置依赖文件追踪（depfile）。生成的`build.ninja`文件包含了完整的依赖图，Ninja可以直接执行。

CMake的Ninja生成器有两个变体：
- **Ninja**：生成单个`build.ninja`文件，适合大多数项目
- **Ninja Multi-Config**：生成支持多配置（Debug/Release等）的构建文件，无需重新配置即可切换构建类型

#### 例子

**基本用法：**

```bash
# 创建构建目录
mkdir build && cd build

# 配置项目，使用Ninja生成器
cmake -G Ninja ..

# 构建项目
ninja

# 或直接使用 cmake --build .
cmake --build .
```

**指定Ninja生成器（永久设置）：**

```bash

mkdir build && cd build
cmake ..
ninja
```

**一个简单的CMakeLists.txt示例：**

```cmake

project(MyApp C)

set(CMAKE_C_STANDARD 11)

# 添加可执行文件目标
add_executable(myapp main.c utils.c parser.c)

# 添加编译选项

```

CMake会生成类似以下的`build.ninja`（简化版）：

```ninja

  description = 链接 $out

build CMakeFiles/myapp.dir/parser.c.o: cc ../parser.c
```

```bash
# 构建Release版本
```

**指定构建类型：**


- CMake通过`-G Ninja`指定Ninja作为后端生成器
- CMake负责项目配置，Ninja负责高效执行
- Ninja生成器有两种：单配置Ninja和多配置Ninja Multi-Config
- CMake自动处理depfile、依赖关系和构建规则
- 生成的`build.ninja`包含完整的依赖图，Ninja可直接执行
- `cmake --build .`是跨生成器的构建命令，推荐使用
- CMake + Ninja是现代C/C++项目的主流构建方案

### 第17讲：GN生成Ninja

#### 概念

GN（Generate Ninja）是Google开发的元构建系统，专门为生成Ninja文件而设计。它最初为Chromium项目创建，后来也被用于Fuchsia操作系统、V8引擎、Skia图形库等项目。GN的设计目标是比GYP（Chromium之前使用的构建系统）更快速、更易理解。

GN使用自己的配置语言（`.gn`和`.BUILD`文件），语法简洁但功能强大。与CMake相比，GN更注重构建配置的模块化和可组合性，特别适合超大规模项目（如Chromium有数万个源文件）。

#### 原理

GN的工作流程是：读取`.gn`配置文件 → 分析依赖关系 → 生成`build.ninja`文件。GN的配置语言支持变量、模板、条件判断等，但故意不支持循环和复杂计算，以保持配置的声明式特性。

GN的核心概念包括：

- **target**：构建目标，类似CMake的`add_executable`/`add_library`
- **dep**：目标间的依赖关系
- **toolchain**：工具链定义，支持交叉编译
- **config**：可复用的编译配置（编译选项、定义等）
- **template**：可复用的目标模板

GN生成的`build.ninja`通常比CMake生成的更精简、更高效，因为GN专门为Ninja优化，没有历史包袱。

#### 例子

**基本用法：**

### 第18讲：自定义生成器

#### 概念

虽然CMake和GN能满足大多数需求，但有时项目需要自定义的构建文件生成器。这可能是因为项目有特殊的构建逻辑、使用非标准的工具链，或者需要从自定义的配置格式生成构建文件。

Ninja的文件格式简单且文档完善，使得编写自定义生成器非常容易。生成器可以用任何语言编写（Python、Shell、Go等），只要它能输出符合Ninja语法的文本文件即可。

#### 原理

自定义生成器的核心任务是：分析项目结构和依赖关系 → 生成符合Ninja语法的`build.ninja`文件。生成器需要处理以下内容：

1. **源文件发现**：扫描项目目录，找到所有源文件
2. **依赖分析**：确定目标之间的依赖关系
3. **规则生成**：为编译、链接等步骤生成Ninja规则
4. **构建语句生成**：为每个源文件和目标生成`build`语句
5. **变量和配置**：处理编译选项、工具链路径等变量

一个好的生成器应该支持增量更新——当项目结构变化时，只重新生成受影响的部分，而不是重新生成整个文件。此外，生成器应该支持`generator = 1`标记，这样Ninja的`-t clean`不会删除生成的构建文件。

#### 例子

**Python生成器示例：**

`gen_ninja.py`:
```python
#!/usr/bin/env python3
"""简单的Ninja文件生成器"""

import os
import glob

def find_sources(directory, extension):
    """查找目录下所有指定扩展名的文件"""
    pattern = os.path.join(directory, '**', f'*.{extension}')
    return glob.glob(pattern, recursive=True)

def generate_ninja():
    sources = find_sources('src', 'c')
    
    with open('build.ninja', 'w') as f:
        # 写入变量
        f.write('cc = gcc\n')
        f.write('cflags = -Wall -O2 -std=c11\n\n')
        
        # 写入规则
        f.write('rule cc\n')
        f.write('  command = $cc -MMD -MF $out.d $cflags -c $in -o $out\n')
        f.write('  depfile = $out.d\n')
        f.write('  deps = gcc\n')
        f.write('  description = 编译 $in\n\n')
        
        f.write('rule link\n')
        f.write('  command = $cc $in -o $out\n')
        f.write('  description = 链接 $out\n\n')
        
        # 为每个源文件生成构建语句
        objects = []
        for src in sources:
            obj = src.replace('src/', 'build/').replace('.c', '.o')
            f.write(f'build {obj}: cc {src}\n')
            objects.append(obj)
        
        f.write('\n')
        
        # 生成链接目标
        f.write(f'build myapp: link {" ".join(objects)}\n\n')
        f.write('default myapp\n')

if __name__ == '__main__':
    generate_ninja()
    print('build.ninja 已生成')
```

**带配置文件的生成器：**

`project.yaml`:
```yaml
project:
  name: myapp
  type: executable
  
sources:
  - src/main.c
  - src/utils.c
  - src/parser.c
  
include_dirs:
  - include
  - third_party/libfoo/include
  
compile_flags:
  - -Wall
  - -O2
  - -std=c11
  
libs:
  - m
  - pthread
```

`gen_ninja.py`:
```python
#!/usr/bin/env python3
import yaml

def generate():
    with open('project.yaml') as f:
        config = yaml.safe_load(f)
    
    project = config['project']
    sources = config['sources']
    include_dirs = config.get('include_dirs', [])
    compile_flags = config.get('compile_flags', [])
    libs = config.get('libs', [])
    
    with open('build.ninja', 'w') as f:
        # 变量
        f.write('cc = gcc\n')
        f.write(f'cflags = {" ".join(compile_flags)}')
        f.write(f' {" ".join("-I" + d for d in include_dirs)}\n')
        f.write(f'ldflags = {" ".join("-l" + l for l in libs)}\n\n')
        
        # 规则
        f.write('rule cc\n')
        f.write('  command = $cc -MMD -MF $out.d $cflags -c $in -o $out\n')
        f.write('  depfile = $out.d\n')
        f.write('  deps = gcc\n\n')
        
        f.write('rule link\n')
        f.write('  command = $cc $in -o $out $ldflags\n\n')
        
        # 构建语句
        objects = []
        for src in sources:
            obj = src.replace('src/', 'build/').replace('.c', '.o')
            f.write(f'build {obj}: cc {src}\n')
            objects.append(obj)
        
        f.write(f'\nbuild {project["name"]}: link {" ".join(objects)}\n\n')
        f.write(f'default {project["name"]}\n')

if __name__ == '__main__':
    generate()
```

**自更新构建文件（generator规则）：**

```ninja
  generator = 1

cflags = -Wall -O2

  command = $cc $cflags -c $in -o $out

```

**Shell脚本生成器：**

```bash
#!/bin/bash
# gen.sh - 简单的Ninja文件生成器

cat > build.ninja << 'EOF'
cc = gcc
cflags = -Wall -O2

rule cc
  command = $cc -MMD -MF $out.d $cflags -c $in -o $out
  depfile = $out.d
  deps = gcc

rule link
  command = $cc $in -o $out

# 为每个 .c 文件生成构建语句

for src in src/*.c; do
    obj="build/$(basename ${src%.c}.o)"
    echo "build $obj: cc $src" >> build.ninja
    objects="$objects $obj"
done

echo "" >> build.ninja
echo "build myapp: link$objects" >> build.ninja
echo "default myapp" >> build.ninja
```

**生成器的最佳实践：**

```python
#!/usr/bin/env python3
"""生产级Ninja生成器的最佳实践"""

import os
import json

class NinjaGenerator:
    def __init__(self):
        self.rules = []
        self.builds = []
        self.variables = {}
        self.defaults = []
    
    def set_var(self, name, value):
        self.variables[name] = value
    
    def add_rule(self, name, command, **kwargs):
        rule = {'name': name, 'command': command}
        rule.update(kwargs)
        self.rules.append(rule)
    
    def add_build(self, outputs, rule, inputs=None, implicit=None, order_only=None, variables=None):
        build = {
            'outputs': outputs,
            'rule': rule,
            'inputs': inputs or [],
            'implicit': implicit or [],
            'order_only': order_only or [],
            'variables': variables or {}
        }
        self.builds.append(build)
    
    def add_default(self, target):
        self.defaults.append(target)
    
    def generate(self, path='build.ninja'):
        with open(path, 'w') as f:
            # 变量
            for name, value in self.variables.items():
                f.write(f'{name} = {value}\n')
            f.write('\n')
            
            # 规则
            for rule in self.rules:
                f.write(f'rule {rule["name"]}\n')
                for key, value in rule.items():
                    if key != 'name':
                        f.write(f'  {key} = {value}\n')
                f.write('\n')
            
            # 构建语句
            for build in self.builds:
                outputs = ' '.join(build['outputs'])
                inputs = ' '.join(build['inputs'])
                implicit = ' '.join(build['implicit'])
                order_only = ' '.join(build['order_only'])
                
                line = f'build {outputs}: {build["rule"]} {inputs}'
                if implicit:
                    line += f' | {implicit}'
                if order_only:
                    line += f' || {order_only}'
                f.write(line + '\n')
                
                for name, value in build['variables'].items():
                    f.write(f'  {name} = {value}\n')
                f.write('\n')
            
            # 默认目标
            if self.defaults:
                f.write(f'default {" ".join(self.defaults)}\n')

# 使用示例
gen = NinjaGenerator()
gen.set_var('cc', 'gcc')
gen.set_var('cflags', '-Wall -O2')
gen.add_rule('cc', '$cc -MMD -MF $out.d $cflags -c $in -o $out',
             depfile='$out.d', deps='gcc')
gen.add_rule('link', '$cc $in -o $out')
gen.add_build(['build/main.o'], 'cc', inputs=['src/main.c'])
gen.add_build(['build/utils.o'], 'cc', inputs=['src/utils.c'])
gen.add_build(['myapp'], 'link', inputs=['build/main.o', 'build/utils.o'])
gen.add_default('myapp')
gen.generate()
```

#### 总结

- 自定义生成器用任何能输出文本的语言编写（Python最常用）
- 生成器的核心任务：发现源文件、分析依赖、生成Ninja语法
- 使用`generator = 1`标记生成器规则，避免`-t clean`删除构建文件
- 良好的生成器支持配置文件（YAML/JSON），实现配置与代码分离
- 自更新机制：当生成器或配置变化时自动重新生成`build.ninja`
- 生产级生成器应封装为类或模块，支持增量更新和错误处理
- Ninja的简单语法使得编写生成器比编写Makefile生成器更容易

### 第19讲：大型项目实战

#### 概念

在大型项目中使用Ninja，需要考虑项目结构组织、构建文件拆分、依赖管理、多平台支持等多个方面。本讲通过一个完整的多模块C++项目实例，展示如何在实际项目中应用Ninja的各项特性。

大型项目的典型特征包括：源文件数量多（数百到数万）、模块化程度高、依赖关系复杂、需要支持多平台和多构建类型。Ninja的设计天然适合这种场景——它的快速解析和增量构建能力，使得即使项目有数万个源文件，日常开发中的增量构建也能在秒级完成。

#### 原理

大型项目的Ninja构建系统通常采用分层架构：

1. **顶层构建文件**：定义全局变量、包含子模块、定义最终链接目标
2. **模块级构建文件**：每个模块（如core、net、ui）有自己的`build.ninja`，定义该模块的编译规则
3. **公共配置文件**：通过`include`共享的变量和规则定义
4. **生成器**：由CMake或自定义脚本生成所有构建文件

这种分层架构使得每个模块可以独立维护，同时通过顶层文件统一管理。模块间的依赖通过`subninja`和构建语句的输入输出关系自动建立。

#### 例子

- 使用`add_subdirectory`或`subninja`组织模块
- 模块间依赖通过`target_link_libraries`或构建语句输入输出建立
- 公共编译选项通过`add_compile_options`或顶层变量统一设置
- 测试目标用`add_custom_target`定义，可包含自定义命令
- `ninja -t targets`和`ninja -t browse`是理解大型项目构建图的有力工具

### 第20讲：性能调优

#### 概念

Ninja本身已经非常快，但在超大型项目中，仍然可以通过合理的配置和调优进一步提升构建性能。性能调优涉及多个层面：构建文件结构优化、并行度调整、I/O优化、编译器选项优化等。

理解Ninja的性能特征是调优的基础。Ninja的性能瓶颈通常不在自身，而在磁盘I/O、编译器启动时间和链接器性能上。因此，Ninja的调优更多是关于如何减少这些外部因素的耗时。

#### 原理

Ninja构建的性能受以下因素影响：

1. **构建文件解析时间**：Ninja启动时需要解析整个`build.ninja`文件。对于超大文件（数十MB），解析可能需要几百毫秒。使用`subninja`拆分文件可以略微改善，但主要优化方向是减少文件大小。

2. **依赖检查时间**：Ninja需要检查所有相关文件的时间戳。使用SSD和合理的文件数量可以控制这个时间。`depfile`机制会增加需要检查的文件数量，但这是正确性的必要代价。

3. **并行度**：并行度受CPU核心数、内存容量和磁盘I/O带宽限制。过高的并行度会导致资源争用，反而降低性能。

4. **编译器启动时间**：每次调用编译器都有固定的启动开销。使用ccache等工具可以缓存编译结果，避免重复编译。

5. **链接时间**：链接通常是单线程的，是构建的瓶颈。使用ld.gold、lld等更快的链接器，或LTO（链接时优化）可以改善。

#### 例子

**1. 调整并行度：**

```bash
# 默认使用CPU核心数+2
ninja

# 手动指定（通常不需要）
ninja -j 8

# 限制并行度以避免内存不足
ninja -j 4

# 同时限制并行任务数和负载
ninja -j 8 -l 16  # 平均负载超过16时停止启动新任务
```

**2. 使用ccache加速编译：**

```ninja
# 在Ninja规则中使用ccache
cc = ccache gcc
cxx = ccache g++

rule cc
  command = $cc -MMD -MF $out.d $cflags -c $in -o $out
  depfile = $out.d
  deps = gcc
```

CMake中启用ccache：
```cmake
set(CMAKE_C_COMPILER_LAUNCHER ccache)
set(CMAKE_CXX_COMPILER_LAUNCHER ccache)
```

**3. 使用更快的链接器：**

```bash
# 使用ld.gold（比默认ld快很多）
gcc -fuse-ld=gold ...

# 使用LLD（LLVM链接器，更快）
gcc -fuse-ld=lld ...
```

CMake中设置：
```cmake
add_link_options(-fuse-ld=gold)
```

**4. 使用pool控制资源密集型任务：**

```ninja
# 链接任务消耗大量内存，限制并发
pool link_pool
  depth = 2

rule link
  command = $cxx $in -o $out
  pool = link_pool

# LTO任务更耗资源
pool lto_pool
  depth = 1

rule link_lto
  command = $cxx -flto $in -o $out
  pool = lto_pool
```

**5. 使用distcc分布式编译：**

```ninja
cc = distcc gcc
cxx = distcc g++

rule cc
  command = $cc -MMD -MF $out.d $cflags -c $in -o $out
  depfile = $out.d
  deps = gcc
```

**6. 优化构建文件大小：**

```ninja
# 不推荐：重复定义相似规则
rule cc_o2
  command = gcc -O2 -c $in -o $out

rule cc_o0
  command = gcc -O0 -c $in -o $out

# 推荐：使用变量参数化
rule cc
  command = gcc $cflags -c $in -o $out

build main.o: cc main.c
  cflags = -O2

build debug.o: cc debug.c
  cflags = -O0 -g
```

**7. 使用restat避免不必要的重建：**

```ninja
rule gen
  command = python generator.py $in > $out
  restat = 1

# 如果生成的内容没变，restat会让Ninja认为文件未修改
# 避免下游目标不必要地重建
build generated.h: gen template.yaml
```

**8. 使用Ninja的统计信息：**

```bash
# 显示构建统计信息
ninja -t stats

# 显示构建时间分析
ninja -d stats

# 查看哪些目标耗时最长
ninja -t targets all | xargs -I{} sh -c 'time ninja {} 2>&1' | sort
```

**9. 使用Unity Build减少编译单元：**

```cmake
# CMake中启用Unity Build
set_target_properties(myapp PROPERTIES
    UNITY_BUILD ON
    UNITY_BUILD_BATCH_SIZE 8
)
```

这会将多个源文件合并为一个编译单元，减少编译器启动次数，但会降低增量构建的粒度。

**10. 性能对比基准：**

```bash
# 测量构建时间
time ninja

# 测量增量构建（无变化时）
touch src/main.cpp
time ninja

# 测量清理后完整构建

# 对比不同并行度
ninja -t clean && time ninja -j 1
ninja -t clean && time ninja -j 4
ninja -t clean && time ninja -j 8
ninja -t clean && time ninja -j 16
```

**11. 使用Ninja的依赖日志：**

```bash
# 查看依赖日志状态
ninja -t deps

# 查看特定目标的依赖
ninja -t deps myapp

# 查看依赖日志的统计信息
ninja -t deps -d
```

#### 总结

- Ninja本身已高度优化，性能瓶颈通常在外部（编译器、链接器、磁盘）
- 使用ccache缓存编译结果，避免重复编译未修改的文件
- 使用ld.gold或lld替代默认链接器，显著加速链接
- 使用pool控制资源密集型任务的并发度
- 使用distcc实现分布式编译，利用多台机器
- 使用restat避免内容未变时的级联重建
- 通过`ninja -d stats`和`time ninja`分析构建性能
- Unity Build减少编译单元数量，但牺牲增量构建粒度
- 合理的并行度取决于CPU核心数、内存和磁盘I/O

### 第21讲：调试与排错

#### 概念

即使有了完善的构建系统，构建过程中仍然会遇到各种问题：依赖缺失、规则错误、循环依赖、构建产物不正确等。Ninja提供了一系列工具和技巧来帮助调试和排查这些问题。

掌握Ninja的调试工具和排错方法，是高效使用Ninja的关键能力。本讲介绍常用的调试命令、常见问题的排查思路，以及构建正确性的验证方法。

#### 原理

Ninja的调试能力主要来自其`-t`（tools）子命令系列。这些工具可以查询构建图的各种信息，帮助理解构建行为。此外，Ninja的`-d`（debug）选项可以输出详细的调试信息，包括解析过程、依赖检查、命令执行等。

构建排错的一般思路是：首先确认构建文件语法正确 → 检查依赖关系是否完整 → 验证命令是否正确执行 → 检查输出文件是否正确生成。Ninja的工具命令在每个阶段都能提供帮助。

#### 例子

**1. 查看构建图：**

```bash
# 列出所有目标
ninja -t targets

# 列出所有规则
ninja -t rules

# 列出所有源文件（没有规则生成它们的目标）
ninja -t targets rule  # 查看规则
ninja -t targets all   # 查看所有目标

# 查看特定目标的所有依赖
ninja -t deps myapp

# 以文本浏览器查看依赖图
ninja -t browse myapp
# 这会启动一个HTTP服务器，在浏览器中显示依赖图

# 查询目标的构建路径
ninja -t query myapp
```

**2. 调试构建过程：**

```bash
# 显示实际执行的命令
ninja -v

# 显示详细调试信息
ninja -d stats

# 显示解析过程
ninja -d parse

# 显示依赖检查过程
ninja -d explain

# 干运行（只显示不执行）
ninja -n

# 干运行并显示命令
ninja -n -v
```

**3. 排查"为什么没有重新构建"：**

```bash
# 使用 -d explain 查看Ninja的决策过程

# 输出示例：
# ninja explain: output main.o older than main.c (1234567 vs 1234570)
# 这表示 main.o 的时间戳比 main.c 旧，应该重建
```

**4. 排查"为什么总是重新构建"：**

```bash

# 常见原因：
# 1. depfile中包含了不存在的文件（如系统头文件路径变化）
```

**5. 排查循环依赖：**

```ninja
# 错误示例：循环依赖
build a: cc a.c b.o
build b.o: cc b.c a
# a 依赖 b.o，b.o 依赖 a，形成循环
```

Ninja会报错：
```
ninja: error: dependency cycle: a -> b.o -> a
```

排查方法：
```bash
# 使用browse工具可视化依赖图
ninja -t browse

# 使用query工具查看依赖链
ninja -t query a
ninja -t query b.o
```

**6. 验证构建正确性：**

```bash

ninja

# 修改一个头文件，看是否触发正确的重建
touch include/common.h
ninja -d explain  # 查看哪些目标被重建

# 验证增量构建的正确性
# 1. 完整构建
ninja
# 2. 不做任何修改，再次构建（应该什么都不做）
ninja
# 输出应为：ninja: no work to do.
```

```bash
# 查看depfile内容

# depfile格式应该是：
# main.o: main.c utils.h config.h

# 如果depfile为空或格式错误，检查编译器选项
# gcc需要 -MMD -MF 选项
gcc -MMD -MF main.o.d -c main.c -o main.o

# 查看Ninja的依赖日志
ninja -t deps

# 清除依赖日志（强制重新读取depfile）
ninja -t recompact
```

```bash
# 复制命令手动执行，查看具体错误

env | grep -i path
```

**9. 常见错误及解决：**

```bash
# 错误：unknown rule 'xxx'
# 原因：规则名拼写错误或规则定义在subninja中不可见
# 解决：检查规则名和作用域

# 错误：dependency cycle
# 原因：构建语句形成循环依赖
# 解决：使用ninja -t browse查找循环

# 错误：multiple rules generate file
# 原因：两个构建语句生成同一个输出文件
# 解决：确保每个输出只有一个构建语句

# 错误：cannot open depfile
# 原因：depfile路径的目录不存在
# 解决：确保输出目录存在，或使用顺序依赖创建目录

# 错误：ninja: error: loading 'build.ninja'
# 原因：当前目录没有build.ninja
# 解决：使用 -f 指定路径，或 cd 到正确目录
```

**10. 使用Ninja的compdb工具生成编译数据库：**

```bash
# 生成compile_commands.json（用于IDE和clangd等工具）
ninja -t compdb > compile_commands.json

# 或指定规则
ninja -t compdb cc cxx > compile_commands.json
```

这个文件可以被VSCode、Vim等编辑器使用，提供代码补全、跳转等功能。

**11. 调试技巧汇总：**

```bash
# 1. 理解构建图
ninja -t targets        # 列出所有目标
ninja -t rules          # 列出所有规则
ninja -t browse         # 可视化依赖图
ninja -t query TARGET   # 查询特定目标

# 2. 理解构建决策
ninja -d explain        # 解释为什么需要重建
ninja -d stats          # 显示统计信息

# 3. 验证命令
ninja -n -v             # 干运行并显示命令
ninja -t commands TARGET # 打印构建命令

# 4. 检查依赖
ninja -t deps TARGET    # 查看依赖
ninja -t deps           # 查看所有依赖日志

# 5. 生成编译数据库
ninja -t compdb > compile_commands.json
```

#### 总结

- `ninja -t targets/rules/deps/browse/query`是理解构建图的核心工具
- `ninja -d explain`解释构建决策，是排查"为什么重建/不重建"的首选
- `ninja -v`显示实际命令，`ninja -n`干运行不执行
- 循环依赖、重复输出、缺失规则是最常见的构建错误
- depfile问题通常由编译器选项错误或目录不存在导致
- `ninja -t compdb`生成编译数据库，供IDE使用
- 增量构建正确性验证：修改源文件→检查是否触发正确重建
- 良好的调试习惯：先用`-n -v`预览，再用`-d explain`分析，最后实际执行
