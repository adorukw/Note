# 第一章 基础认知篇

> 命名是软件工程中最古老、最基础，却最容易被忽视的技能。本章带你建立对命名的正确认知，理解它为什么重要、遵循什么原则、有哪些主流风格，以及它如何影响代码可读性。

## 第 1 讲：为什么命名如此重要

### 概念

**命名（Naming）** 是为程序中的实体（项目、目录、文件、变量、函数、类等）赋予一个人类可读、可理解、可交流的标识符的过程。命名不是"贴标签"的附属工作，而是软件设计的核心活动之一——每一个名字都是一次微型的设计决策。

在软件工程中，我们花在"读代码"上的时间远多于"写代码"的时间。研究表明，程序员有大约 70% 的时间用于理解既有代码，而命名质量直接决定了这段理解时间的长短。一个好名字能让代码自解释，一个坏名字则会让后续维护者反复猜测、踩坑、甚至重写。

### 原理

命名之所以重要，背后有三层原理：

**第一层：认知负荷原理。** 人脑的工作记忆容量有限（约 7±2 个信息块）。当代码中出现 `d`、`s1`、`tmp`、`x2` 这样的名字时，读者必须额外记忆"它们分别代表什么"，这会迅速耗尽工作记忆，导致理解困难。而 `daysSinceLastLogin`、`customerEmail` 这样的名字则把语义直接编码进标识符，几乎不占用额外记忆空间。

**第二层：语义传递原理。** 名字是代码作者与读者之间唯一的"语义桥梁"。代码本身只能表达"怎么做"（how），而名字能传递"是什么"（what）和"为什么"（why）。一个叫 `validateEmail` 的函数告诉你它的意图，而一个叫 `processString` 的函数则什么也没说。

**第三层：可维护性原理。** 软件的生命周期中，原始作者往往会离开，代码会被不同的人接手、修改、扩展。好的命名是一种"自我文档化"（self-documenting），它让代码在没有额外注释的情况下也能被理解，极大降低了维护成本和沟通成本。

### 例子

对比下面两段功能完全相同的代码：

**坏命名版本：**

```javascript
function f(a, b) {
  let c = 0;
  for (let i = 0; i < a.length; i++) {
    if (a[i] === b) {
      c++;
    }
  }
  return c;
}
```

**好命名版本：**

```javascript
function countOccurrences(items, target) {
  let occurrenceCount = 0;
  for (let index = 0; index < items.length; index++) {
    if (items[index] === target) {
      occurrenceCount++;
    }
  }
  return occurrenceCount;
}
```

两段代码逻辑完全一致，但第二段几乎不需要任何注释就能让人一眼看懂：这是一个统计某个目标值在数组中出现次数的函数。而第一段代码，你必须逐行推导才能猜出它的用途。

再看一个项目层面的例子。假设你接手一个名为 `proj1` 的项目，里面有一个文件夹叫 `stuff`，文件叫 `data.js`，导出一个变量叫 `x`。你完全无法判断这是做什么的。但如果项目叫 `user-auth-service`，文件夹叫 `controllers`，文件叫 `loginController.js`，变量叫 `loginAttempts`，你立刻就能建立心智模型。

### 总结

- 命名是软件设计的核心活动，不是附属工作
- 好命名降低认知负荷、传递语义、提升可维护性
- 读代码的时间远多于写代码，命名质量直接影响团队效率
- 命名是一种"自我文档化"，是作者与读者之间的语义桥梁
- **关键要点**：永远不要为了"打字快"而牺牲命名质量，省下的几秒钟会让后来者多花几个小时

## 第 2 讲：命名的核心原则

### 概念

命名的核心原则是一组指导你做出命名决策的通用准则。它们不是死规则，而是帮助你判断"这个名字好不好"的思维框架。掌握这些原则后，无论面对项目、文件夹、文件还是变量，你都能做出一致且合理的选择。

业界公认的核心原则有六条：**准确、简洁、一致、可读、可搜索、无歧义**。这六条原则之间存在张力（比如"简洁"和"准确"有时冲突），优秀的命名往往是在这些原则之间找到平衡点。

### 原理

**准确（Accurate）**：名字必须如实反映它所代表的实体的含义和职责。如果一个函数叫 `getUser`，它就应该返回用户，而不是返回用户列表或修改用户。准确性的本质是"名字与行为的一致性"，一旦不一致，读者就会被误导，bug 就会滋生。

**简洁（Concise）**：在保证准确的前提下，名字应尽可能短。但简洁不等于简短——`d` 很短但不简洁（因为它没有传递信息），`daysSinceLastLogin` 较长但简洁（因为每个词都有意义）。简洁的本质是"信息密度高，没有冗余词"。

**一致（Consistent）**：在整个项目、整个团队中，相同的概念应该用相同的词，相同的命名风格应该贯穿始终。一致性让读者形成"模式识别"，看到 `fetchXxx` 就知道是网络请求，看到 `isXxx` 就知道是布尔值。一致性是降低认知负荷的最强武器。

**可读（Readable）**：名字应该符合自然语言的阅读习惯，能被顺畅地读出来。`getUserInfo` 比 `getusrinfo` 可读，`XMLParser` 比 `XMLHTTPParser`（连续两个大写缩写）可读。可读性还涉及大小写的选择——驼峰命名比全小写更易读，因为单词边界清晰。

**可搜索（Searchable）**：名字应该容易被全文搜索到。单字母变量（`i`、`j`）很难搜索，因为它们出现在太多地方；而 `loginAttempts` 则一搜即得。可搜索性在调试和重构时尤为关键——你需要快速定位某个概念在代码库中的所有出现位置。

**无歧义（Unambiguous）**：名字不应让读者产生多种理解。`processData` 是歧义的（什么数据？怎么处理？），而 `validateUserEmail` 则无歧义。避免使用 `data`、`info`、`temp`、`handler`、`manager` 这类"万能词"，它们看似通用，实则什么都没说。

### 例子

下面通过一组对比来展示这些原则的应用：

**准确性的例子：**

```javascript
// 坏：名字说"获取"，实际却修改了数据
function getUser(id) {
  user.lastLogin = new Date();  // 意外副作用！
  return user;
}

// 好：名字如实反映行为
function getUserById(id) {
  return user;
}
function updateLastLoginTime(userId) {
  user.lastLogin = new Date();
}
```

**简洁性的例子：**

```javascript
// 坏：冗余，"user"重复了三次
let userUserDataObject = fetchUserUserData();

// 好：每个词都有意义
let user = fetchUserData();
```

**一致性的例子：**

```javascript
// 坏：同一个概念用了三种命名
fetchUsers();
getCustomers();
retrieveClients();

// 好：统一用 fetch
fetchUsers();
fetchCustomers();
fetchClients();
```

**可搜索性的例子：**

```javascript
// 坏：单字母变量，搜索时会被淹没
for (let i = 0; i < users.length; i++) {
  let u = users[i];  // "u" 在代码库中出现上千次
}

// 好：有意义的名字，一搜即得
for (let userIndex = 0; userIndex < users.length; userIndex++) {
  let currentUser = users[userIndex];
}
```

### 总结

- 六大核心原则：准确、简洁、一致、可读、可搜索、无歧义
- 原则之间会有张力，需要在具体场景中权衡
- 一致性是降低认知负荷的最强武器，应优先保证
- 避免"万能词"：data、info、temp、handler、manager、util
- **关键要点**：命名时问自己三个问题——它准确吗？它一致吗？别人搜得到吗？

## 第 3 讲：五大命名风格总览

### 概念

**命名风格（Naming Convention）** 是指标识符中单词之间如何分隔、大小写如何组织的具体格式。主流编程世界有五种命名风格，每一种都有其适用场景和历史渊源。理解这五种风格，是制定统一命名规则的基础。

五种风格分别是：

| 风格 | 名称 | 示例 | 典型用途 |
|------|------|------|----------|
| camelCase | 小驼峰 | `userName` | JS/Java 变量、函数 |
| PascalCase | 大驼峰 | `UserName` | 类、组件、类型 |
| snake_case | 蛇形 | `user_name` | Python、Ruby、C |
| kebab-case | 烤串 | `user-name` | URL、CSS、文件名 |
| SCREAMING_SNAKE | 尖叫蛇形 | `USER_NAME` | 常量、环境变量 |

### 原理

**camelCase（小驼峰）**：第一个单词首字母小写，后续单词首字母大写，单词之间无分隔符。它的原理是利用大小写变化来标记单词边界，既保持了标识符的紧凑性（没有下划线占用字符），又保证了可读性。小驼峰起源于 Smalltalk，后被 Java、JavaScript 广泛采用。它适合变量和函数，因为这些是"动作"或"实例"，首字母小写暗示"这是一个具体的值或操作"。

**PascalCase（大驼峰）**：每个单词首字母都大写，也叫 UpperCamelCase。它的原理与小驼峰相同，但通过"全部大写首字母"来区分"类型"与"实例"——类名用 PascalCase，类的实例用 camelCase，形成天然的对照。这种"类型大写、实例小写"的约定在 Java、C#、TypeScript 中根深蒂固。

**snake_case（蛇形）**：单词之间用下划线分隔，全小写。它的原理是用显式分隔符标记单词边界，比大小写变化更清晰，尤其在某些字体下大小写区分不明显时。蛇形命名在 C 语言中就有使用，后被 Python、Ruby 发扬光大。Python 的 PEP 8 明确规定变量和函数用 snake_case，理由是"可读性优于紧凑性"。

**kebab-case（烤串）**：单词之间用连字符（hyphen）分隔，全小写。它的原理与 snake_case 类似，但连字符在 URL、CSS 选择器、HTML 属性中是合法且自然的分隔符，而下划线在这些场景中往往不合法或不推荐。此外，连字符在视觉上比下划线更明显（下划线容易被下划线遮挡），可读性略胜一筹。

**SCREAMING_SNAKE_CASE（尖叫蛇形）**：全大写 + 下划线分隔。它的原理是"视觉上的醒目"——全大写在代码中非常显眼，能立刻吸引读者注意，因此适合标记"不可变、不可修改"的常量。这种风格源于 C 语言的宏定义传统，后被几乎所有语言采纳为常量命名标准。

### 例子

下面用同一个概念"用户登录尝试次数"展示五种风格的差异：

```javascript
// camelCase —— JavaScript 变量
let maxLoginAttempts = 5;

// PascalCase —— TypeScript 类
class LoginAttempt {
  constructor(public userId: string) {}
}

// snake_case —— Python 变量
max_login_attempts = 5

// kebab-case —— CSS 类名 / URL 路径
/* CSS */
.max-login-attempts { color: red; }

<!-- URL -->
/api/max-login-attempts

// SCREAMING_SNAKE_CASE —— 常量
const MAX_LOGIN_ATTEMPTS = 5;
```

不同语言/场景的典型选择：

```
JavaScript:  变量/函数 camelCase，类 PascalCase，常量 SCREAMING_SNAKE
Python:      变量/函数 snake_case，类 PascalCase，常量 SCREAMING_SNAKE
Java:        变量/方法 camelCase，类 PascalCase，常量 SCREAMING_SNAKE
CSS:         类名 kebab-case
URL:         路径 kebab-case
文件名:       视语言而定（见第三章）
```

### 总结

- 五大风格：camelCase、PascalCase、snake_case、kebab-case、SCREAMING_SNAKE
- 每种风格有历史渊源和适用场景，不要混用
- "类型大写、实例小写"是 PascalCase 与 camelCase 配合的核心逻辑
- 连字符（kebab）在 URL/CSS 中更自然，下划线（snake）在代码中更常见
- **关键要点**：选择风格时，遵循语言/生态的惯例，而不是个人偏好

## 第 4 讲：命名与可读性的关系

### 概念

**可读性（Readability）** 是指代码被人类阅读、理解的难易程度。命名是影响可读性的最重要因素之一——甚至比注释和文档更重要，因为名字出现在代码的每一行，而注释只在特定位置。本讲深入探讨命名如何影响可读性，以及如何通过命名让代码"自解释"。

可读性不是主观感受，而是有客观衡量标准的：阅读速度、理解准确率、修改时的出错率。好的命名能显著提升这三项指标。一个可读性高的代码库，新人上手快、bug 修复快、重构风险低。

### 原理

命名影响可读性的机制有四个：

**机制一：语义激活。** 当读者看到一个名字时，大脑会自动激活与该名字相关的语义网络。看到 `invoice`，大脑立刻联想到"发票、账单、金额"等概念；看到 `data`，大脑则一片空白。好的命名能快速激活正确的语义网络，让读者"秒懂"；坏的命名则让大脑空转，需要从上下文推断。

**机制二：模式识别。** 人类大脑擅长识别模式。当命名遵循一致的规则时（比如所有布尔变量都以 `is`/`has`/`can` 开头），读者会形成"模式识别"，看到前缀就能预判变量的类型和用途。这种预判大幅降低了逐行阅读的认知成本。反之，如果命名不一致，大脑必须为每个变量重新建立认知，效率大降。

**机制三：上下文依赖。** 名字的可读性不仅取决于名字本身，还取决于它所在的上下文。在 `User` 类内部，`name` 是清晰的（显然是用户名）；但在全局函数中，`name` 就模糊了（什么的名字？）。好的命名会根据上下文调整详细程度——上下文清晰时简洁，上下文模糊时详细。

**机制四：阅读节奏。** 代码的阅读不是匀速的，而是有节奏的。读者会快速扫过"已知"的部分，慢下来读"未知"的部分。好的命名能创造流畅的阅读节奏——动词开头让人知道这是操作，名词开头让人知道这是数据。而坏命名会打断节奏，迫使读者频繁回溯。

### 例子

**上下文依赖的例子：**

```javascript
// 坏：在全局上下文中，"name" 太模糊
function process(name) {
  // name 是什么的名字？人？公司？文件？
}

// 好：在全局上下文中，需要更详细
function processUserName(fullName) {
  // 清晰：这是用户的全名
}

// 但在类内部，可以简洁
class User {
  constructor(name, email) {  // 这里 name 显然是用户名
    this.name = name;
    this.email = email;
  }
}
```

**模式识别的例子：**

```javascript
// 好的命名模式，让读者形成预判
const isLoading = true;        // is 开头 → 布尔，状态
const hasPermission = false;   // has 开头 → 布尔，拥有关系
const canEdit = true;          // can 开头 → 布尔，能力
const userCount = 42;          // 名词+Count → 数量
const userList = [];           // 名词+List → 数组
const fetchUsers = async () => {};  // fetch 开头 → 网络请求
const validateEmail = (email) => {}; // validate 开头 → 校验函数
```

**阅读节奏的例子：**

```javascript
// 坏：阅读节奏被打断，需要反复回溯
const d = new Date();
const n = d.getTime();
const s = String(n);
const r = s.slice(-6);

// 好：阅读流畅，一气呵成
const now = new Date();
const timestamp = now.getTime();
const timestampString = String(timestamp);
const lastSixDigits = timestampString.slice(-6);
```

### 总结

- 命名是影响可读性的最重要因素，比注释更重要
- 四个机制：语义激活、模式识别、上下文依赖、阅读节奏
- 好命名让代码"自解释"，减少对注释的依赖
- 根据上下文调整命名详细程度：上下文清晰时简洁，模糊时详细
- **关键要点**：写完代码后，把自己当成第一次读这段代码的人，如果需要停下来想"这是什么"，就需要改名

# 第二章 项目与文件夹命名篇

> 项目和文件夹是代码库的"骨架"，它们的命名决定了整个项目的第一印象和导航效率。本章讲解如何为项目、仓库、包、文件夹命名，以及如何通过命名实现模块化。

---

## 第 5 讲：项目命名规则

### 概念

**项目命名** 是为整个软件项目赋予一个唯一、可识别、可传播的名称的过程。项目名是代码库的最高层级标识，它会出现在仓库地址、文档标题、部署域名、包名、日志前缀等几乎所有地方。一个好的项目名应该简洁、独特、有意义、易于拼写和记忆。

项目名一旦确定并投入使用，修改成本极高（涉及域名、文档、依赖、CI/CD 等），因此在项目启动时就要慎重命名。

### 原理

项目命名需要遵循以下原理：

**原理一：独特性优先。** 项目名必须在你的组织内、甚至全球范围内（如果是开源项目）足够独特。如果公司里已经有 `user-service`，你就不能再用这个名字，否则会造成混淆。独特性还便于搜索引擎优化——搜 `user-service` 会返回无数结果，而搜 `aurora-auth` 则精准得多。

**原理二：含义与抽象并存。** 好的项目名既有字面含义（让人能猜到用途），又有一定抽象度（不至于过于局限）。`user-auth-service` 太直白且局限（万一以后扩展到权限管理呢？），`zebra`（斑马，暗示"黑白分明"的权限）则既有含义又抽象。许多知名项目采用"名词/动物/神话"命名法：Python（蟒蛇）、Kafka（作家）、ZooKeeper（动物园管理员）。

**原理三：全小写 + 连字符。** 项目名推荐使用全小写 + kebab-case，原因有三：一是 URL 不区分大小写，全小写避免歧义；二是大多数包管理器（npm、pip）要求包名小写；三是连字符在 URL、域名、文件系统中都是合法且自然的分隔符。`user-auth-service` 远比 `UserAuthService` 或 `user_auth_service` 更通用。

**原理四：长度适中。** 项目名建议在 3-20 个字符之间。太短（如 `app`）缺乏辨识度，太长（如 `enterprise-user-authentication-and-authorization-service`）难以输入和记忆。如果项目名需要多个单词，用连字符连接，控制在 2-4 个单词。

### 例子

**好的项目命名示例：**

```
# 公司内部项目：业务域 + 功能 + 类型
order-payment-service      # 订单支付服务
inventory-tracking-api     # 库存追踪 API
customer-portal-web        # 客户门户前端

# 开源项目：独特名词 + 可选后缀
react                      # 独特、简短、有含义（reactive）
vue                        # 简短、独特（view 的谐音）
tailwindcss                # 名词 + 技术栈后缀
next.js                    # 名词 + 框架后缀

# 微服务架构：服务名 + 后缀
auth-service               # 认证服务
notification-gateway       # 通知网关
data-aggregator            # 数据聚合器
```

**坏的项目命名示例：**

```
proj1                      # 无意义
my-app                     # 太通用，无法区分
TestProject                # 大写，不符合 URL 习惯
user_management_system     # 下划线，不利于 URL
super-cool-awesome-tool    # 过于随意，不专业
tmp                        # 临时名一旦上线就改不掉了
```

**项目命名的完整检查清单：**

```
□ 名字是否在组织内唯一？
□ 名字是否全小写 + 连字符？
□ 名字长度是否在 3-20 字符？
□ 名字是否容易拼写和发音？
□ 名字是否暗示了项目用途？
□ 名字是否过于局限（未来扩展会受限）？
□ 对应的域名/仓库地址是否可用？
```

### 总结

- 项目名是代码库的最高标识，修改成本极高，启动时就要慎重
- 四大原理：独特性优先、含义与抽象并存、全小写连字符、长度适中
- 公司项目推荐"业务域 + 功能 + 类型"格式
- 开源项目可用独特名词命名，增加辨识度
- **关键要点**：项目名一旦上线就不要改，所以第一天的命名决策要当成"永久决策"对待

## 第 6 讲：仓库与包命名

### 概念

**仓库命名（Repository Naming）** 是为代码版本控制仓库（如 Git 仓库）命名的规则。**包命名（Package Naming）** 是为可发布的软件包（npm 包、pip 包、Maven 包等）命名的规则。仓库名和包名通常相关但不完全相同——仓库是源码的容器，包是发布的产物。

在现代开发中，一个项目可能对应一个仓库和一个包（单体仓库），也可能对应一个仓库和多个包（monorepo），或者多个仓库和一个包（罕见）。理解仓库名与包名的关系，是工程化开发的基础。

### 原理

**仓库命名的原理：**

仓库名应该与项目名保持一致或高度相关。如果项目叫 `user-auth-service`，仓库名也应该是 `user-auth-service`（而不是 `backend` 或 `server`）。这样做的好处是：当你在 GitHub/GitLab 上看到仓库列表时，能立刻知道每个仓库对应什么项目。

在 monorepo（单仓库多包）场景下，仓库名通常是项目集合的名称，如 `company-platform`、`frontend-monorepo`，而各个子包有自己的包名。

**包命名的原理：**

包名比仓库名有更严格的约束，因为它要被发布到公共注册表（npm、PyPI、Maven Central），需要满足：

1. **唯一性**：在注册表中全局唯一。npm 上 `utils` 早已被占用，你需要用 `@your-org/utils`（scope 包）或 `your-company-utils`。
2. **小写**：几乎所有包管理器要求包名全小写。
3. **无空格、无特殊字符**：只允许字母、数字、连字符、下划线（部分管理器不允许下划线）。
4. **简短可记**：包名会被频繁输入（`npm install xxx`、`import xxx`），太长影响体验。

**scope 包的原理：**

npm 的 scope 机制（`@org/package-name`）解决了"包名冲突"问题。它通过组织前缀来保证唯一性，同时保持包名的简洁。`@angular/core`、`@babel/preset-env`、`@vue/compiler` 都是 scope 包的典范。对于公司内部包，强烈推荐使用 `@company-name/` 前缀。

### 例子

**仓库与包的命名对照：**

```
项目名:        user-auth-service
仓库地址:      github.com/company/user-auth-service
npm 包名:      @company/user-auth   （scope 包，更简洁）
Python 包名:  company-user-auth    （PyPI 不支持 scope，用前缀）
```

**monorepo 中的命名：**

```
仓库名: company-frontend-platform

packages/
  ├── @company/ui-components/      # UI 组件库
  │   └── package.json → "name": "@company/ui-components"
  ├── @company/utils/              # 工具函数库
  │   └── package.json → "name": "@company/utils"
  └── @company/hooks/              # React Hooks 库
      └── package.json → "name": "@company/hooks"
```

**package.json 中的命名规范：**

```json
{
  "name": "@company/user-auth-service",
  "version": "1.2.3",
  "description": "User authentication and authorization service",
  "main": "dist/index.js",
  "types": "dist/index.d.ts"
}
```

**Python 包命名规范：**

```python
# setup.py / pyproject.toml
# 包名用连字符（PyPI 显示），导入名用下划线（Python 语法要求）
# 包名: company-user-auth
# 导入: from company_user_auth import login

from setuptools import setup
setup(
    name="company-user-auth",
    version="1.2.3",
    packages=["company_user_auth"],
)
```

### 总结

- 仓库名应与项目名一致，便于识别和管理
- 包名有更严格的约束：唯一、小写、无特殊字符
- npm 推荐用 scope 包（`@org/name`）解决冲突
- Python 包名（连字符）与导入名（下划线）要区分
- monorepo 中，仓库名是集合名，子包各有包名
- **关键要点**：包名一旦发布就很难改（会破坏所有依赖者），发布前务必确认命名

## 第 7 讲：文件夹与目录结构命名

### 概念

**文件夹命名（Directory Naming）** 是为代码库中的目录命名的规则。文件夹是代码的组织单元，好的文件夹命名能让项目结构一目了然，开发者能凭直觉找到任何文件。文件夹命名需要兼顾"人类可读"和"工具友好"——既要语义清晰，又要避免跨平台、跨工具的兼容性问题。

文件夹命名是项目结构的"导航系统"，它直接决定了开发者的认知效率。一个混乱的文件夹结构（如 `misc`、`other`、`temp`、`old`）会让项目变成迷宫；而清晰的结构（如 `controllers`、`services`、`models`）则让项目自解释。

### 原理

**原理一：全小写 + kebab-case。** 文件夹名推荐全小写 + 连字符分隔，原因有四：一是跨平台兼容（Windows 不区分大小写，`MyFolder` 和 `myfolder` 在 Windows 上是同一个，但在 Linux 上是不同的，会导致跨平台 bug）；二是 URL 友好（文件夹名常出现在 URL 路径中）；三是 shell 友好（大写需要 Shift 键，且某些 shell 对大小写敏感）；四是与项目名、包名风格一致。

**原理二：用复数表示集合。** 文件夹通常包含多个同类文件，因此用复数名词：`controllers`（而非 `controller`）、`models`、`views`、`utils`。复数传达了"这里有一组同类东西"的语义，单数则暗示"这里只有一个"，容易误导。

**原理三：按职责而非类型分组。** 现代项目推荐按"职责/特性"分组，而非按"文件类型"分组。按类型分组（所有 controller 放一起、所有 model 放一起）会导致"修改一个功能要跳多个文件夹"；按特性分组（一个功能的 controller、model、view 放一起）则高内聚、低耦合。

**原理四：避免无意义文件夹。** `misc`、`other`、`temp`、`utils`、`helpers`、`common` 这些文件夹名是"垃圾桶"——它们没有明确语义，任何文件都可以塞进去，最终变成无法维护的杂物堆。如果发现需要一个 `utils` 文件夹，说明你的功能划分还不够清晰。

### 例子

**按类型分组（传统，不推荐）：**

```
src/
  ├── controllers/
  │   ├── userController.js
  │   ├── orderController.js
  │   └── productController.js
  ├── models/
  │   ├── userModel.js
  │   ├── orderModel.js
  │   └── productModel.js
  └── views/
      ├── userView.js
      ├── orderView.js
      └── productView.js

# 问题：修改"用户"功能要跳三个文件夹
```

**按特性分组（现代，推荐）：**

```
src/
  ├── modules/
  │   ├── user/                    # 用户模块
  │   │   ├── userController.js
  │   │   ├── userModel.js
  │   │   ├── userService.js
  │   │   └── userRoutes.js
  │   ├── order/                   # 订单模块
  │   │   ├── orderController.js
  │   │   ├── orderModel.js
  │   │   └── orderService.js
  │   └── product/                 # 商品模块
  │       ├── productController.js
  │       ├── productModel.js
  │       └── productService.js
  ├── shared/                      # 真正跨模块共享的代码
  │   ├── config/
  │   └── types/
  └── app.js
```

**标准化的文件夹命名：**

```
src/
  ├── components/        # React/Vue 组件
  ├── pages/             # 页面级组件
  ├── layouts/           # 布局组件
  ├── hooks/             # 自定义 Hooks
  ├── services/          # API 调用层
  ├── stores/            # 状态管理
  ├── utils/             # 纯函数工具（谨慎使用，避免变垃圾桶）
  ├── types/             # TypeScript 类型定义
  ├── assets/            # 静态资源
  ├── styles/            # 全局样式
  ├── config/            # 配置文件
  └── tests/             # 测试文件（或与源码同目录）
```

**跨平台兼容性注意事项：**

```
# 坏：大小写混用，跨平台会出问题
src/MyComponent/
src/mycomponent/         # Windows 上与上面是同一个，Linux 上是两个

# 坏：含空格，shell 操作麻烦
src/My Components/

# 坏：含特殊字符
src/user@auth/

# 好：全小写 + 连字符
src/user-auth/
src/my-component/
```

### 总结

- 文件夹名推荐全小写 + kebab-case，跨平台兼容
- 用复数名词表示集合：`controllers` 而非 `controller`
- 按特性/职责分组，而非按文件类型分组
- 避免 `misc`、`temp`、`utils`、`common` 等"垃圾桶"文件夹
- **关键要点**：文件夹结构是项目的"导航系统"，结构清晰则开发效率高

## 第 8 讲：模块化与命名空间

### 概念

**模块化（Modularization）** 是将系统分解为高内聚、低耦合的模块的设计方法。**命名空间（Namespace）** 是通过命名来组织代码、避免冲突的技术。文件夹命名与模块化、命名空间密切相关——好的文件夹结构本身就是一种"物理命名空间"，它让代码的组织方式与命名方式保持一致。

在现代前端和后端开发中，模块化已成为标配。理解如何通过命名来实现命名空间，是构建大型可维护系统的关键技能。

### 原理

**命名空间的原理：**

命名空间通过"前缀"或"路径"来限定标识符的作用域，避免全局冲突。例如，`User.Auth.login` 和 `Order.Payment.charge` 即使都有 `login`/`charge` 方法也不会冲突，因为它们属于不同的命名空间。命名空间的本质是"分层命名"——用层级结构来组织概念，让同名标识符在不同层级可以共存。

**文件夹即命名空间的原理：**

在现代模块系统中（ES Modules、CommonJS、Python Modules），文件夹路径天然构成命名空间。`import { login } from '@/modules/user/auth'` 中，`modules/user/auth` 就是命名空间路径。这意味着文件夹命名直接决定了命名空间的清晰度——如果文件夹叫 `misc`，命名空间就毫无意义；如果叫 `user-auth`，命名空间就自解释。

**模块命名的原理：**

模块（一个文件夹或一个文件）的命名应该反映其"领域职责"。好的模块名是"领域名词"而非"技术名词"：`user-management`（领域）优于 `crud-operations`（技术）、`payment-flow`（领域）优于 `state-machine`（技术）。领域命名让非技术人员也能理解模块用途，技术命名则只有程序员能懂。

**barrel 文件的原理：**

Barrel 文件（`index.ts`、`__init__.py`）是模块的"入口"，它重新导出模块内的公共 API。通过 barrel 文件，外部使用者只需 `import { login } from '@/modules/user'`，而不需要知道 `login` 具体在哪个文件。这实现了"接口与实现分离"——模块内部结构可以重构，外部导入路径不变。

### 例子

**文件夹作为命名空间：**

```
src/
  ├── modules/
  │   ├── user/                    # 命名空间: user
  │   │   ├── index.ts             # barrel 文件，导出公共 API
  │   │   ├── components/
  │   │   │   ├── UserProfile.tsx
  │   │   │   └── UserList.tsx
  │   │   ├── services/
  │   │   │   └── userService.ts
  │   │   ├── hooks/
  │   │   │   └── useUser.ts
  │   │   ├── types.ts
  │   │   └── userRoutes.ts
  │   ├── order/                   # 命名空间: order
  │   │   ├── index.ts
  │   │   ├── components/
  │   │   └── services/
  │   └── product/                 # 命名空间: product
  │       ├── index.ts
  │       └── components/
```

**barrel 文件的使用：**

```typescript
// src/modules/user/index.ts —— barrel 文件
export { UserProfile } from './components/UserProfile';
export { UserList } from './components/UserList';
export { useUser } from './hooks/useUser';
export type { User, UserProps } from './types';

// 外部使用：只需导入模块根，不需要知道内部结构
import { UserProfile, useUser, type User } from '@/modules/user';
// 而不是
// import { UserProfile } from '@/modules/user/components/UserProfile';
```

**命名空间冲突的避免：**

```typescript
// 坏：两个模块都有 login，直接导入会冲突
import { login } from './user/auth';
import { login } from './admin/auth';  // 冲突！

// 好：用命名空间导入
import * as userAuth from './user/auth';
import * as adminAuth from './admin/auth';

userAuth.login();
adminAuth.login();

// 或用别名
import { login as userLogin } from './user/auth';
import { login as adminLogin } from './admin/auth';
```

**Python 中的命名空间：**

```python
# company_user_auth/__init__.py
from .login import login
from .logout import logout
from .models import User

# 外部使用
from company_user_auth import login, User

# 或命名空间导入
import company_user_auth
company_user_auth.login()
```

### 总结

- 文件夹路径天然构成命名空间，文件夹命名决定命名空间清晰度
- 模块名用"领域名词"而非"技术名词"
- barrel 文件（index.ts）实现接口与实现分离
- 用命名空间导入或别名解决同名冲突
- **关键要点**：好的模块化 = 好的文件夹命名 + barrel 文件 + 清晰的公共 API

# 第三章 文件命名篇

> 文件是代码的物理载体，文件命名直接影响开发者的导航效率和工具的识别。本章讲解源代码文件、配置文件、资源文件、测试文件的命名规则。

---

## 第 9 讲：源代码文件命名

### 概念

**源代码文件命名** 是为 `.js`、`.ts`、`.py`、`.java` 等源码文件命名的规则。文件名是开发者在编辑器标签页、文件树、import 语句中最频繁看到的标识，好的文件名能让开发者快速定位、减少认知负担。

不同语言/框架对文件命名有不同的惯例：JavaScript/TypeScript 倾向 kebab-case 或 PascalCase（取决于框架），Python 强制 snake_case，Java 强制 PascalCase。理解这些差异，并在项目内保持一致，是文件命名的核心。

### 原理

**原理一：遵循语言/框架惯例。** 每种语言/框架有自己的文件命名惯例，违反惯例会让代码显得"不专业"，且可能被工具误判。例如，Java 要求公共类名与文件名一致（`User.java` 中必须是 `public class User`），Python 模块名必须是小写（`user_service.py`），React 组件文件推荐 PascalCase（`UserProfile.tsx`）。

**原理二：文件名反映内容。** 文件名应该让读者一眼知道里面是什么。`userController.js` 显然是用户相关的控制器，`utils.js` 则什么都没说（可能是任何东西）。文件名 = 内容的"摘要"，要具体而非抽象。

**原理三：避免冗余后缀。** 如果文件夹已经表达了类型，文件名就不必重复。在 `controllers/` 文件夹下，`user.js` 比 `userController.js` 更简洁——因为 `controllers/` 已经说明了这是控制器。但如果项目不按文件夹分组，则 `userController.js` 更清晰。这是"上下文依赖"原则在文件命名上的体现。

**原理四：大小写一致性。** 同一项目内，文件命名风格必须一致。不能有的用 `userProfile.js`，有的用 `UserProfile.js`，有的用 `user_profile.js`——这会让 import 语句混乱，且在大小写敏感的系统（Linux）上导致找不到文件。

### 例子

**各语言/框架的文件命名惯例：**

```
# JavaScript / TypeScript（通用）
user-service.ts              # kebab-case，模块/工具文件
UserProfile.tsx              # PascalCase，React 组件文件
useUser.ts                   # camelCase，自定义 Hook

# Next.js 特殊约定
app/
  ├── page.tsx               # 路由页面（固定文件名）
  ├── layout.tsx             # 布局（固定文件名）
  ├── loading.tsx            # 加载状态（固定文件名）
  └── error.tsx              # 错误边界（固定文件名）

# Python
user_service.py              # snake_case，模块文件
user_model.py                # snake_case，数据模型
test_user_service.py         # test_ 前缀，测试文件

# Java
User.java                    # PascalCase，与公共类名一致
UserController.java          # PascalCase
UserRepository.java          # PascalCase

# Go
user_service.go              # snake_case
user_controller.go           # snake_case
```

**文件名反映内容的示例：**

```
# 坏：文件名不反映内容
utils.js                     # 什么 utils？
helper.ts                    # 帮什么忙？
data.py                      # 什么 data？
temp.js                      # 临时文件不该进版本控制

# 好：文件名清晰反映内容
date-utils.js                # 日期工具
string-formatter.ts          # 字符串格式化
user-model.py                # 用户模型
```

**上下文依赖的文件命名：**

```
# 场景 A：按类型分组（文件夹已表达类型）
controllers/
  ├── user.js                # 简洁，因为 controllers/ 已说明类型
  ├── order.js
  └── product.js

# 场景 B：按特性分组（文件夹不表达类型）
modules/user/
  ├── userController.js      # 需要后缀，因为文件夹是 user/
  ├── userModel.js
  └── userService.js
```

**import 语句的清晰度对比：**

```javascript
// 坏：文件名风格混乱，import 看起来不专业
import { User } from './userProfile';
import { Order } from './order-controller';
import { Product } from './product_model';

// 好：风格统一
import { User } from './user-profile';
import { Order } from './order-controller';
import { Product } from './product-model';
```

### 总结

- 文件命名要遵循语言/框架的既定惯例
- 文件名应反映内容，避免 `utils`、`helper`、`data` 等无意义名
- 根据上下文决定是否加类型后缀（文件夹已表达类型时可省略）
- 同一项目内文件命名风格必须一致
- **关键要点**：在编辑器标签页中，只看文件名就应该知道里面是什么

## 第 10 讲：配置文件命名

### 概念

**配置文件命名** 是为 `.json`、`.yaml`、`.env`、`.toml` 等配置文件命名的规则。配置文件是项目运行的"参数表"，它们的命名需要兼顾"环境区分"、"工具识别"和"安全规范"。配置文件命名不当会导致环境混淆、敏感信息泄露、工具无法识别等严重问题。

配置文件通常分为三类：环境配置（dev/test/prod）、工具配置（eslint/prettier/webpack）、应用配置（app config）。每类有不同的命名规则。

### 原理

**原理一：环境配置用后缀区分。** 不同环境（开发、测试、预发布、生产）的配置不同，通过文件名后缀来区分：`.env.development`、`.env.test`、`.env.production`。这种命名让开发者一眼看出当前配置对应哪个环境，避免误用。同时，基础配置放 `.env`，环境特定配置覆盖基础配置，形成分层。

**原理二：工具配置用点号前缀。** 工具配置文件（ESLint、Prettier、Babel、Webpack）通常以点号开头（`.eslintrc`、`.prettierrc`），这是 Unix 传统——点号开头的文件在 `ls` 时默认隐藏，减少视觉干扰。现代项目也支持 `工具名.config.js` 格式（`eslint.config.js`），更易编辑和注释。

**原理三：敏感配置不入版本控制。** 含有密钥、密码的配置文件（`.env.local`、`.env.production`）绝不能提交到 Git。通过 `.gitignore` 排除，并提供 `.env.example` 作为模板。文件名约定：`.example`/`.template` 后缀表示"这是模板，可提交"；`.local` 后缀表示"本地覆盖，不提交"。

**原理四：配置文件名要自解释。** `config.json` 太模糊（什么配置？），`database-config.json` 则清晰。在配置文件较多的项目中，用业务域前缀组织：`database.config.json`、`cache.config.json`、`logging.config.json`。

### 例子

**环境配置文件命名：**

```
project/
  ├── .env                    # 基础配置，所有环境共享
  ├── .env.local              # 本地覆盖配置，不提交
  ├── .env.development        # 开发环境
  ├── .env.staging            # 预发布环境
  ├── .env.production         # 生产环境
  ├── .env.example            # 模板文件，可提交，供新人参考
  └── .gitignore              # 排除 .env.local, .env.production
```

```
# .gitignore
.env.local
.env.production
.env.staging
# 但保留 .env, .env.development, .env.example
```

**工具配置文件命名：**

```
project/
  ├── .eslintrc.js            # 或 eslint.config.js（新格式）
  ├── .prettierrc             # 或 .prettierrc.json
  ├── .babelrc                # 或 babel.config.js
  ├── .editorconfig           # 编辑器配置
  ├── .gitignore
  ├── .npmrc                  # npm 配置
  ├── tsconfig.json           # TypeScript 配置
  ├── webpack.config.js       # Webpack 配置
  ├── vite.config.ts          # Vite 配置
  ├── jest.config.js          # Jest 测试配置
  └── docker-compose.yml      # Docker Compose 配置
```

**应用配置文件命名：**

```
config/
  ├── app.config.json         # 应用主配置
  ├── database.config.json    # 数据库配置
  ├── cache.config.json       # 缓存配置
  ├── logging.config.json     # 日志配置
  ├── redis.config.json       # Redis 配置
  └── oss.config.json         # 对象存储配置
```

**配置文件内容示例：**

```json

{
  "development": {
    "host": "localhost",
    "port": 5432,
    "database": "myapp_dev"
  },
  "production": {
```

```bash

DATABASE_URL=postgresql://user:pass@localhost:5432/db

```

### 总结

- 环境配置用后缀区分：`.env.development`、`.env.production`
- 工具配置用点号前缀或 `工具名.config.js` 格式
- 敏感配置（`.env.local`、`.env.production`）不入版本控制
- 提供 `.env.example` 作为模板，供新人参考
- 应用配置用业务域前缀组织：`database.config.json`
- **关键要点**：配置文件命名的核心是"环境可区分、敏感可隔离、工具可识别"

## 第 11 讲：资源文件命名

### 概念

**资源文件命名** 是为图片、样式、字体、视频等静态资源命名的规则。资源文件与源代码文件有不同的命名考量——它们不参与编译（多数情况），但会被引用、缓存、CDN 分发，因此命名要考虑"语义清晰"、"缓存友好"、"尺寸/分辨率标识"。

资源文件命名不当会导致：找不到资源、缓存不更新、响应式图片混乱、团队协作冲突等问题。

### 原理

**原理一：语义优先，格式在后。** 资源文件名应该描述"它是什么"而非"它长什么样"。`logo.png` 是语义命名（它是 logo），`blue-square-200px.png` 是描述命名（它碰巧是蓝色方块）。语义命名让资源可替换——如果 logo 从 PNG 换成 SVG，文件名不变，引用不用改。

**原理二：尺寸/分辨率用后缀标识。** 响应式设计常需要同一图片的多个尺寸/分辨率版本，用后缀标识：`logo@2x.png`（2 倍分辨率）、`logo-200x200.png`（200x200 尺寸）、`logo-small.png`（小尺寸）。这种命名让开发者一眼看出该用哪个版本。

**原理三：状态变体用连字符。** 同一资源的不同状态（hover、active、disabled）用连字符连接：`button-hover.png`、`icon-active.svg`。状态后缀让资源与 UI 状态的对应关系一目了然。

**原理四：CSS 类名用 kebab-case。** CSS 类名必须用 kebab-case（`user-profile`、`nav-menu`），原因有二：一是 CSS 选择器中连字符是合法的单词分隔符；二是 kebab-case 在 HTML 中更自然（`class="user-profile"`）。避免 camelCase（`userProfile`）和 snake_case（`user_profile`）。

**原理五：避免特殊字符和空格。** 资源文件名不要含空格、中文、特殊字符，否则在 URL 中需要转义，且某些服务器/CDN 处理不当会导致 404。坚持全小写 + 连字符 + 字母数字。

### 例子

**图片文件命名：**

```
assets/
  ├── images/
  │   ├── logo.svg                    # 语义命名
  │   ├── logo@2x.png                 # 2 倍分辨率
  │   ├── logo@3x.png                 # 3 倍分辨率
  │   ├── hero-banner.jpg             # 主横幅
  │   ├── hero-banner-mobile.jpg      # 移动端版本
  │   ├── user-avatar-default.png     # 默认头像
  │   ├── icon-home.svg               # 首页图标
  │   ├── icon-home-active.svg        # 激活状态
  │   └── icon-home-hover.svg         # 悬停状态
  ├── icons/
  │   ├── icon-search.svg
  │   ├── icon-cart.svg
  │   └── icon-user.svg
  └── backgrounds/
      ├── bg-gradient-blue.svg
      └── bg-pattern-dots.png
```

**CSS/样式文件命名：**

```
styles/
  ├── global.css               # 全局样式
  ├── variables.css            # CSS 变量
  ├── reset.css                # 样式重置
  ├── typography.css           # 排版
  ├── layout.css               # 布局
  ├── components/
  │   ├── button.css
  │   ├── card.css
  │   └── modal.css
  └── pages/
      ├── home.css
      ├── about.css
      └── contact.css
```

```css

.nav-menu { }
.btn-primary { }
.card-header { }
.is-active { }          /* 状态类用 is-/has- 前缀 */
.has-error { }
```

**字体文件命名：**

```
fonts/
  ├── inter-regular.woff2      # 字体名-字重
  ├── inter-medium.woff2
  ├── inter-semibold.woff2
  ├── inter-bold.woff2
  ├── noto-sans-regular.woff2
  └── noto-sans-bold.woff2
```

**坏命名 vs 好命名对比：**

```

blue-button-200px.png
img1.jpg
新建项目.jpg               # 中文，URL 转义后乱码

# 好：语义命名，可替换
button-primary.png
hero-banner.jpg
project-screenshot.jpg
hero-banner.jpg
```

### 总结

- 资源文件语义优先：`logo.svg` 而非 `blue-square.png`
- 尺寸/分辨率用后缀：`@2x`、`-200x200`、`-mobile`
- 状态变体用连字符：`icon-home-active.svg`
- CSS 类名强制 kebab-case
- 避免空格、中文、特殊字符
- **关键要点**：资源文件名的核心是"语义可替换、尺寸可区分、状态可识别"

## 第 12 讲：测试文件命名

### 概念

**测试文件命名** 是为单元测试、集成测试、端到端测试文件命名的规则。测试文件命名有双重目的：一是让测试框架自动发现并运行测试，二是让开发者快速定位"某个功能的测试在哪里"。测试文件命名不当会导致测试不被运行、测试与源码对应关系混乱。

测试文件命名因框架而异：Jest 推荐 `xxx.test.js`，Python 用 `test_xxx.py`，Java 用 `xxxTest.java`。理解这些约定，并在项目内统一，是测试命名的基础。

### 原理

**原理一：测试文件与源文件同名（加测试后缀）。** 测试文件应该与被测源文件同名，加上测试后缀。`userService.ts` 的测试是 `userService.test.ts`，`user_service.py` 的测试是 `test_user_service.py`。这种"同名对应"让开发者能凭直觉找到测试——看到源文件就知道测试在哪。

**原理二：测试后缀遵循框架约定。** 不同测试框架有不同的测试文件后缀约定，必须遵循，否则框架无法自动发现测试。Jest 默认匹配 `*.test.js` 或 `*.spec.js`，Python pytest 匹配 `test_*.py`，Java JUnit 匹配 `*Test.java`。混用后缀会导致测试被遗漏。

**原理三：测试文件与源文件同目录或镜像目录。** 测试文件的放置有两种主流策略：一是与源文件同目录（`user/service.ts` + `user/service.test.ts`），二是镜像目录（`src/user/service.ts` + `tests/user/service.test.ts`）。同目录策略便于就近查看，镜像目录策略保持源码目录干净。两种都合理，关键是项目内统一。

**原理四：测试描述要表达"测什么+什么场景"。** 测试文件内的 `describe`/`it` 描述应该清晰表达"被测对象 + 场景 + 预期"。`describe('UserService', () => { it('should return user when id exists', ...) })` 比 `describe('test', () => { it('case1', ...) })` 清晰百倍。测试描述本身就是文档。

### 例子

**各框架的测试文件命名：**

```
# Jest（JavaScript/TypeScript）
userService.test.ts          # 推荐 .test.ts
userService.spec.ts          # 或 .spec.ts（Jasmine 风格）

# pytest（Python）
test_user_service.py         # test_ 前缀
test_user_model.py

# JUnit（Java）
UserServiceTest.java         # Test 后缀
UserControllerTest.java

# Go
user_service_test.go         # _test 后缀

# RSpec（Ruby）
user_service_spec.rb         # _spec 后缀
```

**测试文件放置策略：**

```
# 策略一：与源文件同目录
src/
  ├── modules/
  │   ├── user/
  │   │   ├── userService.ts
  │   │   ├── userService.test.ts    # 测试紧邻源文件
  │   │   ├── userModel.ts
  │   │   └── userModel.test.ts
  │   └── order/
  │       ├── orderService.ts
  │       └── orderService.test.ts

# 策略二：镜像目录
src/
  ├── modules/
  │   ├── user/
  │   │   └── userService.ts
  │   └── order/
  │       └── orderService.ts
tests/
  ├── modules/
  │   ├── user/
  │   │   └── userService.test.ts    # 镜像 src 结构
  │   └── order/
  │       └── orderService.test.ts
```

**测试描述的命名：**

```javascript

describe('test', () => {
  it('case1', () => { });
  it('case2', () => { });
  it('should work', () => { });
});

// 好：测试描述清晰表达意图
describe('UserService', () => {
  describe('getUserById', () => {
    it('should return user when id exists', async () => { });
    it('should return null when id does not exist', async () => { });
    it('should throw error when id is invalid', async () => { });
  });

  describe('createUser', () => {
    it('should create user with valid data', async () => { });
    it('should throw error when email is duplicate', async () => { });
    it('should hash password before saving', async () => { });
  });
});
```

**测试类型分层命名：**

```
tests/
  ├── unit/                    # 单元测试
  │   ├── services/
  │   │   └── userService.test.ts
  │   └── utils/
  │       └── dateUtils.test.ts
  ├── integration/             # 集成测试
  │   └── api/
  │       └── userApi.test.ts
  └── e2e/                     # 端到端测试
      ├── login.e2e.test.ts
      └── checkout.e2e.test.ts
```

### 总结

- 测试文件与源文件同名 + 测试后缀：`userService.test.ts`
- 测试后缀遵循框架约定：Jest 用 `.test`，pytest 用 `test_`，JUnit 用 `Test`
- 测试文件与源文件同目录或镜像目录，项目内统一
- 测试描述要表达"被测对象 + 场景 + 预期"
- 测试类型分层：unit / integration / e2e
- **关键要点**：测试文件命名的核心是"框架可发现、源码可对应、描述可理解"

# 第四章 变量与代码元素命名篇

> 变量、函数、类、常量、布尔值是代码的最小语义单元，它们的命名质量直接决定代码的可读性。本章深入讲解各类代码元素的命名规则。

---

## 第 13 讲：变量命名基础

### 概念

**变量命名** 是为程序中存储数据的标识符命名的规则。变量是代码中最频繁出现的元素，变量命名质量直接决定代码的可读性。好的变量名让代码自解释，坏的变量名则让代码变成谜题。

变量命名要回答三个问题：这个变量存什么？它的类型是什么？它的作用域是什么？一个好的名字应该让读者一眼回答这三个问题。

### 原理

**原理一：名词或名词短语。** 变量代表"数据"，因此用名词或名词短语命名：`user`、`userList`、`loginAttempts`。避免用动词命名变量（动词留给函数），除非变量本身存储一个动作（如回调函数 `onClick`）。

**原理二：类型暗示。** 变量名应暗示其类型，让读者无需查看定义就能猜到类型。复数名词暗示数组（`users`），`Map`/`Set` 后缀暗示对应数据结构（`userMap`），`count`/`total` 后缀暗示数字（`userCount`），`is`/`has`/`can` 前缀暗示布尔值（`isLoading`）。

**原理三：作用域决定长度。** 变量的作用域越大，名字应该越长越详细；作用域越小，名字可以越短。全局变量需要详细名字（`globalUserSession`），循环内的临时变量可以简短（`i`、`index`）。这是因为大作用域变量需要在远处被识别，小作用域变量在近处就能理解。

**原理四：避免缩写（除非是行业通用缩写）。** `usr` 不如 `user` 清晰，`cfg` 不如 `config` 明确。但某些缩写是行业通用的，可以使用：`URL`、`HTTP`、`API`、`ID`、`HTML`、`CSS`。判断标准：这个缩写是否在团队中所有人都认识？

**原理五：避免否定。** 变量名避免用否定形式，因为双重否定难以理解。`isNotEmpty` 不如 `isEmpty`（然后用 `!isEmpty`），`isNotValid` 不如 `isValid`。否定变量在条件判断中会造成"如果不是不空"这样的绕口令。

### 例子

**名词命名的例子：**

```javascript
// 坏：动词命名变量

// 好：名词命名变量
```

- 变量用名词或名词短语命名

- 避免缩写，除非是行业通用缩写（URL、ID、HTTP）
- 避免否定变量，用肯定形式
- **关键要点**：变量名要让人一眼回答"存什么、什么类型、什么作用域"

## 第 14 讲：函数与方法命名

### 概念

**函数命名** 是为可执行代码块命名的规则。函数是程序的"动作"，函数名应该是一个动词或动词短语，清晰表达"这个函数做什么"。好的函数名让调用处读起来像自然语言句子，无需查看实现就能理解意图。

函数命名是命名中最需要技巧的部分——变量是"是什么"，函数是"做什么"，而"做什么"的表达更依赖动词的选择和搭配。

### 原理

**原理一：动词开头。** 函数名必须以动词开头，表达动作。常用的动词前缀有约定俗成的含义：`get`/`fetch`（获取）、`set`（设置）、`create`（创建）、`update`（更新）、`delete`/`remove`（删除）、`validate`（校验）、`format`（格式化）、`parse`（解析）、`convert`（转换）、`is`/`has`/`can`（判断，返回布尔值）。

**原理二：动词与返回类型对应。** 不同的"获取"动词暗示不同的返回类型和来源：`get` 暗示从内存/本地获取（同步），`fetch` 暗示从网络/远程获取（异步），`load` 暗示从文件/存储加载，`compute`/`calculate` 暗示经过计算后返回。这种约定让调用者无需看实现就能预判函数的行为和性能特征。

**原理三：避免 `handle`/`process`/`do` 等模糊动词。** `handleClick` 说了等于没说（怎么 handle？），`processData` 同样模糊（什么数据？怎么 process？）。这些动词是"命名懒惰"的表现——它们看似通用，实则什么都没表达。应该用更具体的动词：`handleSubmit`（提交表单）、`validateUserInput`（校验用户输入）。

**原理四：纯函数 vs 有副作用函数。** 纯函数（无副作用，返回值取决于输入）用动词原形或名词形式：`calculateTotal`、`formatDate`。有副作用的函数（修改状态、发起请求、写文件）用命令式动词：`saveUser`、`sendEmail`、`updateProfile`。这种区分让调用者意识到"这个函数会改变什么"。

**原理五：方法名与类名配合。** 类的方法名不需要重复类名——`user.getName()` 比 `user.getUserName()` 简洁，因为 `user` 上下文已经明确了"是谁的名字"。但在脱离类上下文时（如独立函数），需要更详细：`getUserName()`。

### 例子

**常用动词前缀及含义：**

```javascript

// 创建/删除类
```

**避免模糊动词的例子：**


### 总结

- 函数名必须以动词开头，表达动作
- 动词前缀有约定含义：get/fetch/create/update/delete/validate/is
- 避免模糊动词：handle、process、do、manage
- 纯函数用描述性动词，副作用函数用命令式动词
- 类方法不重复类名，独立函数需要完整名称
- **关键要点**：好的函数名让调用处读起来像自然语言句子

## 第 15 讲：类与接口命名

### 概念

**类命名** 是为面向对象编程中的类命名的规则。**接口命名** 是为接口（Interface）或类型（Type）命名的规则。类和接口是"类型"层面的命名，它们定义了"概念"而非"实例"，因此命名风格与变量不同——类和接口通常用 PascalCase，且名词要足够抽象以代表一类事物。

类和接口的命名质量直接影响类型系统的清晰度。好的类名让类型关系一目了然，坏的类名则让类型系统变成谜题。

### 原理

**原理一：PascalCase + 名词。** 类和接口用 PascalCase 命名，且必须是名词或名词短语。`User`、`OrderService`、`HttpClient` 都是好的类名。PascalCase 与变量（camelCase）形成对照，让读者一眼区分"类型"和"实例"：`const user: User = new User()` 中，大写 `User` 是类型，小写 `user` 是实例。

**原理二：类名要抽象且准确。** 类名代表"一类事物"，因此要足够抽象以涵盖所有实例，又要足够准确以排除非实例。`Animal` 是好的抽象（涵盖猫狗等），`Mammal` 更具体，`Cat` 最具体。选择哪一级抽象取决于类的职责——如果类处理所有动物，用 `Animal`；如果只处理猫，用 `Cat`。

**原理三：接口命名的两种流派。** 接口命名有两种主流约定：一是不加前缀（`User`、`Repository`），二是加 `I` 前缀（`IUser`、`IRepository`）。Java/C# 传统用 `I` 前缀，TypeScript/Go 倾向不加前缀。不加前缀的理由是：接口是抽象定义，不应与实现区分（依赖倒置原则）；加前缀的理由是：一眼区分接口和类。项目内统一即可。

**原理四：抽象类/基类用 Base 后缀。** 抽象类或基类推荐用 `Base` 后缀：`BaseController`、`BaseRepository`、`BaseComponent`。这表明它是"供继承的基础类"，不应直接实例化。或者用 `Abstract` 前缀（`AbstractRepository`），但 `Base` 更简洁。

**原理五：异常类用 Exception 后缀。** 自定义异常类必须以 `Exception` 或 `Error` 结尾：`UserNotFoundException`、`InvalidEmailException`、`DatabaseConnectionError`。这是跨语言的通用约定，让读者一眼识别"这是异常类"，且便于 try-catch 时书写。

**原理六：接口表示能力用 -able 后缀。** 当接口表示"能力"（can-do）而非"是什么"（is-a）时，用 `-able` 后缀：`Comparable`、`Serializable`、`Iterable`、`Cloneable`。这种命名让接口的语义一目了然——实现 `Comparable` 表示"可比较"。

### 例子

**类命名示例：**


- 类和接口用 PascalCase + 名词命名
- 类名要抽象且准确，代表"一类事物"
- 接口命名两种流派：加 `I` 前缀或不加，项目内统一

- 能力接口用 `-able` 后缀：Comparable、Serializable
- 类型别名也用 PascalCase
- **关键要点**：类和接口命名要让人一眼区分"类型"与"实例"

## 第 16 讲：常量与枚举命名

### 概念

**常量命名** 是为程序中不可变的值命名的规则。**枚举命名** 是为一组相关的命名常量命名的规则。常量和枚举是"配置"和"状态"的载体，它们的命名需要醒目、一致、语义清晰，让读者一眼识别"这是不可变的、重要的值"。

常量和枚举的命名质量直接影响代码的可维护性——硬编码的魔法数字是 bug 之源，而好的常量命名则让代码自解释。

### 原理

**原理一：常量用 SCREAMING_SNAKE_CASE。** 全大写 + 下划线分隔是跨语言的常量命名标准。这种命名在代码中非常醒目，能立刻吸引读者注意，暗示"这是不可变的重要值"。`MAX_LOGIN_ATTEMPTS = 5` 比 `maxLoginAttempts = 5` 更醒目，让读者意识到"这是一个配置阈值，不要随意修改"。

**原理二：常量名要包含单位/上下文。** 当常量是数值时，名字应包含单位或上下文，避免歧义。`TIMEOUT = 5000` 是歧义的（5000 毫秒？秒？），`TIMEOUT_MS = 5000` 或 `CONNECTION_TIMEOUT_MS = 5000` 则清晰。包含单位让读者无需查看使用处就能理解值的含义。

**原理三：常量按用途分组。** 相关的常量应该放在一起，用对象或枚举组织，而非散落各处。`const API_ENDPOINTS = { USERS: '/api/users', ORDERS: '/api/orders' }` 比 `const USERS_API = '/api/users'; const ORDERS_API = '/api/orders'` 更有组织。分组让常量之间的关系一目了然。

**原理四：枚举用 PascalCase，枚举值用 PascalCase 或 SCREAMING_SNAKE。** 枚举名用 PascalCase（`UserStatus`、`OrderPriority`），因为它是"类型"。枚举值有两种约定：TypeScript/Java 用 PascalCase（`Active`、`Inactive`），Python/C 用 SCREAMING_SNAKE（`ACTIVE`、`INACTIVE`）。遵循语言惯例即可。

**原理五：枚举值要语义化，避免裸数字。** 枚举的意义在于"用名字代替数字"，因此枚举值必须是语义化的名字，绝不能是裸数字。`Status.Pending = 0` 比 `Status = 0` 清晰，使用时 `if (order.status === OrderStatus.Pending)` 比 `if (order.status === 0)` 可读百倍。

```typescript
  SuperAdmin = 'SUPER_ADMIN',
}

// 使用：语义清晰
function canEdit(user: User) {
  return user.role === UserRole.Admin || user.role === UserRole.SuperAdmin;
}

if (order.priority === OrderPriority.Urgent) {
  // 紧急处理
}
```

**枚举命名（Python 风格）：**

```python
from enum import Enum

# 枚举名 PascalCase，枚举值 SCREAMING_SNAKE
class UserStatus(Enum):
    ACTIVE = 'active'
    INACTIVE = 'inactive'
    BANNED = 'banned'
    PENDING = 'pending'

class OrderPriority(Enum):
    LOW = 1
    MEDIUM = 2
    HIGH = 3
    URGENT = 4

# 使用
if user.status == UserStatus.ACTIVE:
    pass
```

**避免魔法数字：**

```javascript
// 坏：魔法数字，含义不明
if (user.role === 3) { }              // 3 是什么？
if (response.status === 404) { }      // 404 还行，但不如常量
setTimeout(refresh, 1800000);         // 1800000 是多久？

// 好：用常量代替魔法数字
if (user.role === UserRole.Admin) { }
if (response.status === HTTP_STATUS.NOT_FOUND) { }
setTimeout(refresh, SESSION_TIMEOUT_MS);
```

**TypeScript const enum / union type：**

```typescript
// 联合类型替代枚举（TypeScript 推荐）
type UserStatus = 'active' | 'inactive' | 'banned' | 'pending';
type OrderPriority = 'low' | 'medium' | 'high' | 'urgent';

const user: { status: UserStatus } = { status: 'active' };
if (user.status === 'active') { }
```

### 总结

- 常量用 SCREAMING_SNAKE_CASE，醒目且暗示不可变
- 常量名包含单位/上下文：`TIMEOUT_MS` 而非 `TIMEOUT`
- 相关常量分组组织，而非散落各处
- 枚举名用 PascalCase，枚举值遵循语言惯例（TS 用 PascalCase，Python 用 SCREAMING_SNAKE）
- 枚举值必须语义化，避免裸数字
- 用常量/枚举代替魔法数字
- **关键要点**：常量和枚举让"配置"和"状态"自解释，是可维护代码的基石

## 第 17 讲：布尔变量命名

### 概念

**布尔变量命名** 是为只有 true/false 两个值的变量命名的规则。布尔变量在条件判断中频繁使用，其命名质量直接影响条件语句的可读性。好的布尔变量名让 `if` 语句读起来像自然语言，坏的布尔变量名则让条件判断变成逻辑谜题。

布尔变量命名看似简单，实则有独特的规则——它必须表达"是或否"的判断，因此命名方式与普通变量不同。

### 原理

**原理一：用 is/has/can/should 前缀。** 布尔变量必须用判断性前缀，让读者一眼识别"这是布尔值"。常用前缀有：`is`（是什么状态）、`has`（有什么属性）、`can`（能做什么操作）、`should`（应该做什么）、`will`（将要做什么）、`was`（曾经是什么）。这些前缀把变量名变成"是非问句"，与布尔值的 true/false 语义天然契合。

**原理二：用肯定形式，避免否定。** 布尔变量用肯定形式，避免否定前缀（`isNot`、`isDisabled`）。否定变量在条件判断中会造成双重否定：`if (!isNotValid)` 比 `if (isValid)` 难读得多。如果概念本身是否定的（如"禁用"），用肯定的反义词：`isEnabled` 而非 `isDisabled`，`isVisible` 而非 `isHidden`（除非概念本身就是"隐藏"）。

**原理三：布尔变量名要能回答"是/否"。** 好的布尔变量名应该能自然地回答"是"或"否"。`isLoading` 可以回答"是，正在加载"或"否，没在加载"；`data` 则无法回答。判断标准：把变量名读成问句，看是否能用 true/false 回答。

**原理四：状态布尔 vs 行为布尔。** 布尔变量分两类：状态布尔（描述当前状态，用 `is`/`has`）和行为布尔（控制是否执行某操作，用 `should`/`can`/`will`）。`isLoading` 是状态（"正在加载吗"），`shouldRefresh` 是行为（"应该刷新吗"）。区分这两类让代码意图更清晰。

**原理五：避免 `flag`/`status` 等无意义名。** `flag` 和 `status` 是布尔变量命名的两大陷阱——它们看似通用，实则什么都没说。`isDataLoaded` 比 `dataFlag` 清晰，`isUserActive` 比 `userStatus`（如果只存布尔）清晰。`status` 通常应该是枚举（有多种状态），而非布尔。

### 例子

**布尔前缀的用法：**

```javascript
// is：描述状态/性质
const isLoading = true;              // 正在加载吗
const isValid = false;               // 有效吗
const isVisible = true;              // 可见吗
const isEmpty = false;               // 为空吗
const isReady = true;                // 准备好了吗

// has：描述拥有/包含
const hasPermission = true;          // 有权限吗
const hasChildren = false;           // 有子节点吗
const hasError = false;              // 有错误吗
const hasUnsavedChanges = true;      // 有未保存的更改吗

// can：描述能力
const canEdit = true;                // 能编辑吗
const canDelete = false;             // 能删除吗
const canAccessResource = true;      // 能访问资源吗

// should：描述应该做什么
const shouldRedirect = true;         // 应该重定向吗
const shouldShowModal = false;       // 应该显示弹窗吗
const shouldRetry = true;            // 应该重试吗

// will：描述将要发生
const willUpdate = true;             // 将要更新吗
const willUnmount = false;           // 将要卸载吗

// was：描述曾经的状态
const wasSuccessful = true;          // 曾经成功吗
const wasModified = false;           // 曾经被修改吗
```

**肯定 vs 否定：**

```javascript
// 坏：否定形式，条件判断绕口
const isNotValid = false;
const isDisabled = true;
const isNotEmpty = true;
const hasNoErrors = true;

if (!isNotValid) { }          // "如果不是无效" —— 双重否定！
if (!isDisabled) { }          // "如果不是禁用" —— 绕
if (!isNotEmpty) { }          // "如果不是不空" —— 崩溃

// 好：肯定形式
const isValid = true;
const isEnabled = false;
const isEmpty = false;
const hasErrors = false;

if (isValid) { }              // "如果有效" —— 清晰
if (isEnabled) { }            // "如果启用" —— 清晰
if (isEmpty) { }              // "如果为空" —— 清晰
```

**状态布尔 vs 行为布尔：**

```javascript
// 状态布尔：描述"是什么"，用 is/has
const isLoading = true;       // 状态：正在加载
const hasData = false;        // 状态：有数据
const isVisible = true;       // 状态：可见

// 行为布尔：描述"做什么"，用 should/can/will
const shouldFetchData = true; // 行为：应该获取数据
const canSubmit = false;      // 行为：能提交
const willRedirect = true;    // 行为：将重定向

// 在条件中使用，意图清晰
if (isLoading) {              // 状态判断
  showSpinner();
}

if (shouldFetchData && canSubmit) {  // 行为判断
  fetchData();
}
```

**避免 flag/status：**

```javascript
// 坏：flag 和 status 无意义
const dataFlag = true;        // 什么 flag？
const userFlag = false;       // 什么 flag？
const status = true;          // status 应该是枚举，不是布尔

if (dataFlag) { }             // 如果 dataFlag... 然后呢？

// 好：用具体的布尔前缀
const isDataLoaded = true;
const isUserVerified = false;
const userStatus = 'active';  // 多种状态用枚举/字符串

if (isDataLoaded) { }         // 如果数据已加载 —— 清晰
```

**布尔变量在条件中的可读性：**

```javascript
// 好：条件读起来像自然语言
if (isLoading) { showSpinner(); }
if (hasPermission && canEdit) { enableEditButton(); }
if (shouldShowModal && !isVisible) { showModal(); }
if (wasSuccessful) { showSuccessMessage(); }

// 坏：条件读起来像密码
if (d) { s(); }
if (p && e) { eb(); }
if (sm && !v) { sm(); }
if (ok) { msg(); }
```

**函数返回布尔值也遵循同样规则：**

```javascript
// 布尔函数用 is/has/can 前缀
function isValidEmail(email) { }
function hasPermission(user, action) { }
function canAccess(user, resource) { }
function shouldRetry(error) { }

// 调用处读起来像问句
if (isValidEmail(email)) { }
if (hasPermission(user, 'edit')) { }
if (canAccess(user, resource)) { }
```

### 总结

- 布尔变量用 is/has/can/should/will/was 前缀
- 用肯定形式，避免否定（isNot、isDisabled）
- 布尔变量名要能回答"是/否"
- 区分状态布尔（is/has）和行为布尔（should/can/will）
- 避免 `flag`、`status` 等无意义名
- 布尔函数也用 is/has/can 前缀
- **关键要点**：好的布尔变量名让 `if` 语句读起来像自然语言句子

## 第 18 讲：跨层级统一策略

### 概念

**跨层级统一策略** 是指在项目、文件夹、文件、变量四个层级之间保持命名一致性的方法。前面几章分别讲解了每个层级的命名规则，但真正的挑战在于"跨层级一致"——同一个概念，在项目名、文件夹名、文件名、变量名中应该保持怎样的关系？

跨层级统一的核心思想是：**同一个概念，在不同层级用相同的词，但遵循各自的命名风格**。例如，"用户认证"这个概念，项目名是 `user-auth-service`，文件夹是 `user-auth/`，文件是 `authController.ts`，变量是 `userAuthData`，类是 `UserAuthService`——概念词一致（user-auth），风格各异（kebab/snake/camel/Pascal）。

### 原理

**原理一：概念词一致，风格各异。** 同一个业务概念，在所有层级用相同的"词根"，但遵循各层级的命名风格。这样开发者在不同层级看到同一个词，能立刻建立关联。`user-auth` 这个词根贯穿项目名、文件夹、文件、变量、类，让整个"用户认证"功能在代码库中高度内聚、易于追踪。

**原理二：层级映射关系。** 四个层级有自然的映射关系：项目名 → 顶级文件夹 → 模块文件夹 → 文件 → 类/函数 → 变量。每一层都是上一层的"细化"。项目 `user-auth-service` 包含 `src/modules/user-auth/` 文件夹，文件夹包含 `authController.ts` 文件，文件定义 `AuthController` 类，类有 `loginAttempts` 变量。这种层层细化的命名让代码库"自组织"。

**原理三：避免跨层级命名冲突。** 同一个名字在不同层级不要重复使用，否则造成混淆。如果项目叫 `user-service`，就不要在里面再建一个 `user-service` 文件夹——这会让 `import ... from 'user-service/user-service'` 显得荒谬。用更具体的名字：项目 `user-service`，模块文件夹 `auth/`、`profile/`、`preferences/`。

**原理四：URL 路径与文件夹路径对应。** 在 Web 项目中，URL 路径应该与文件夹/文件路径对应，且都用 kebab-case。`/api/user-auth/login` 对应 `src/modules/user-auth/controllers/login.ts`。这种对应让前后端开发者能凭直觉找到对应代码。

**原理五：数据库表名与模型类名对应。** 数据库表名用 snake_case（`user_accounts`），ORM 模型类名用 PascalCase（`UserAccount`），字段名用 snake_case（`created_at`），TypeScript 接口属性用 camelCase（`createdAt`）。这种映射关系要在项目文档中明确，并在 ORM 配置中自动化。

### 例子

**完整的跨层级命名示例：**

```

```

### 总结

- 跨层级统一的核心：概念词一致，风格各异
- 四个层级有自然映射：项目 → 文件夹 → 文件 → 变量
- 避免跨层级命名冲突（项目名不要在内部重复）
- URL 路径与文件夹路径对应，都用 kebab-case
- 数据库表名（snake_case）与模型类名（PascalCase）对应
- **关键要点**：跨层级统一让代码库"自组织"，开发者能凭直觉在层级间导航

## 第 19 讲：团队规范与工具链

### 概念

**团队规范与工具链** 是将命名规则在团队中落地并自动执行的方法。再好的命名规则，如果只停留在文档里，不配合工具强制执行，最终也会被遗忘或违反。通过 ESLint、Prettier、EditorConfig、commitlint 等工具，可以将命名规则"代码化"，让工具自动检查、自动修复、在 CI 中拦截不合规代码。

工具链是命名规范的"牙齿"——没有工具的规范只是建议，有工具的规范才是规则。

### 原理

**原理一：规范文档化。** 命名规则首先要写成文档（`NAMING_CONVENTIONS.md`），作为团队的"单一真相来源"。文档应包含：各层级的命名风格、正例反例、特殊情况处理、决策记录（为什么选这个风格）。文档放在仓库根目录，新人入职必读。

**原理二：工具自动化。** 用工具自动检查命名，避免人工 review 时遗漏。ESLint 可检查变量/函数命名风格，Prettier 可格式化代码（虽然不直接管命名，但保持一致性），EditorConfig 统一编辑器配置，commitlint 检查提交信息格式。工具配置本身也是文档——它精确描述了规则。

**原理三：CI 强制拦截。** 命名检查必须集成到 CI/CD 流程中，不合规的代码无法合并到主分支。这是"强制执行"的关键——仅靠开发者自觉是不够的，CI 拦截让规则不可绕过。GitHub Actions / GitLab CI 中配置 lint 步骤，失败则阻止合并。

**原理四：渐进式推行。** 在既有项目中推行命名规范，不能一次性重命名所有代码（风险太大）。应该渐进式推行：新代码必须遵守规范，旧代码在修改时逐步重命名。配合工具的 `--fix` 能力自动修复能修复的部分，手动处理需要思考的部分。

**原理五：规则可配置、可豁免。** 工具规则应该可配置，允许在特殊情况下豁免（用注释标记）。例如，对接第三方 API 时，字段名必须与 API 一致，无法遵循团队规范，此时用 `// eslint-disable-next-line` 豁免。但豁免要有充分理由，且在代码审查时重点检查。

### 例子

**命名规范文档（NAMING_CONVENTIONS.md）：**

```markdown
# 命名规范

## 项目命名
- 格式：kebab-case，全小写
- 示例：`user-auth-service`
- 规则：业务域-功能-类型

## 文件夹命名
- 格式：kebab-case，全小写
- 示例：`user-auth/`、`controllers/`
- 规则：复数名词表示集合

## 文件命名
- 组件文件：PascalCase（`UserProfile.tsx`）
- 普通文件：camelCase（`userService.ts`）
- 测试文件：`*.test.ts`

## 变量命名
- 变量：camelCase（`userName`）
- 常量：SCREAMING_SNAKE（`MAX_RETRY`）
- 布尔：is/has/can 前缀（`isLoading`）

## 类与接口
- 类/接口：PascalCase（`UserService`）
- 接口不加 I 前缀
- 异常类：Exception 后缀
```

## 第 20 讲：常见反模式与综合实战

### 概念

**命名反模式（Naming Anti-patterns）** 是指常见但应避免的命名习惯。识别反模式是提升命名质量的关键——知道什么是错的，才能避免犯错。本讲汇总最常见的命名反模式，并通过一个综合实战案例，将前 19 讲的知识融会贯通。

综合实战将展示一个"命名混乱"的项目如何通过应用统一命名规则，重构为清晰、可维护的代码库。这是对全课程知识的总检验。

### 原理

**反模式一：单字母变量。** `i`、`j`、`x`、`y`、`d`、`s` 等单字母变量除了循环索引外，几乎总是坏命名。它们无法传递语义，难以搜索，在大型代码库中会造成混淆。即使是循环索引，在嵌套循环或长循环中也应该用更有意义的名字（`userIndex`、`itemIndex`）。

**反模式二：匈牙利命名。** `strName`、`intCount`、`arrUsers` 这种带类型前缀的命名是历史遗留，现代语言有类型系统，不需要在名字中编码类型。匈牙利命名让代码冗长且难以维护（类型变了名字也得改）。

**反模式三：数字后缀。** `user1`、`user2`、`data2`、`temp3` 这种用数字区分变量的命名是"命名懒惰"的表现。如果需要多个同类变量，应该用更具体的名字：`primaryUser`、`secondaryUser`，或用数组/对象组织。

**反模式四：误导性命名。** 名字与实际行为不符是最严重的反模式。`getUser` 实际上修改了用户数据，`validateEmail` 实际上发送了验证邮件——这些命名会误导读者，引发 bug。命名必须与行为一致，发现不一致时立即改名或改行为。

**反模式五：过度缩写。** `usrMgr`、`authSvc`、`cfgParser` 这种过度缩写在作者脑中清晰，但在读者眼中是谜题。除非是行业通用缩写（URL、HTTP、API），否则用完整单词。打字速度不是借口——编辑器有自动补全。

**反模式六：同义词混用。** 同一个概念用不同的词：`fetch`/`get`/`retrieve`/`load` 混用，`user`/`customer`/`client`/`account` 混用。这会让读者以为它们是不同的东西。项目内建立"词汇表"，每个概念只用一个词。

### 例子

**反模式对比：**

```javascript

function f(u, p) {
  let r = db.q(u);
  if (r.p === p) {
    return t(r);
  }
}

// 正确：有意义的变量名

  const user = db.findByEmail(email);
  if (user.passwordHash === hash(password)) {
    return generateToken(user);
  }
}

// 反模式二：匈牙利命名
let strUserName = 'Alice';
let intUserCount = 42;
let arrUserList = [];
let objUserConfig = {};

// 正确：让类型系统工作
let userName = 'Alice';
let userCount = 42;
let userList = [];
let userConfig = {};

// 反模式三：数字后缀
let user1 = getAdmin();
let user2 = getMember();
let user3 = getGuest();

// 正确：语义化命名
let adminUser = getAdmin();
let memberUser = getMember();
let guestUser = getGuest();

// 反模式四：误导性命名

  const user = db.find(id);
  user.lastLogin = new Date();  // 意外副作用！
  db.save(user);                // 名字说"获取"，实际"修改+保存"
  return user;
}

// 正确：名字与行为一致
function getUserById(id) {
  return db.find(id);           // 纯获取，无副作用
}

  const user = db.find(id);
  user.lastLogin = new Date();
  db.save(user);
```

```typescript
// src/modules/user-auth/services/authService.ts
import { User } from '../models/user';
import { hashPassword, comparePassword } from '../utils/passwordUtils';
import { MAX_LOGIN_ATTEMPTS, AUTH_TOKEN_EXPIRY_MS } from '../../../shared/config';
import { InvalidCredentialsException } from '../types/authTypes';

export class AuthService {
  private loginAttempts: Map<string, number> = new Map();

  async login(email: string, password: string): Promise<User> {
    const user = await User.findByEmail(email);
    const isValidPassword = await comparePassword(password, user.passwordHash);

    if (!isValidPassword) {
      this.incrementLoginAttempts(email);
      if (this.getLoginAttempts(email) >= MAX_LOGIN_ATTEMPTS) {
        throw new InvalidCredentialsException('Too many login attempts');
      }
      throw new InvalidCredentialsException('Invalid credentials');
    }

    this.resetLoginAttempts(email);
    return user;
  }

  private getLoginAttempts(email: string): number {
    return this.loginAttempts.get(email) ?? 0;
  }

  private incrementLoginAttempts(email: string): void {
    const currentAttempts = this.getLoginAttempts(email);
    this.loginAttempts.set(email, currentAttempts + 1);
  }

  private resetLoginAttempts(email: string): void {
    this.loginAttempts.delete(email);
  }
}
```

1. 项目名从 `proj1` 改为 `user-auth-service`，语义清晰
2. 文件夹从 `stuff`/`things`/`old` 改为 `modules/user-auth`、`modules/order`，按特性分组
3. 文件从 `data.js`/`temp.js`/`file1.js` 改为 `authService.ts`/`authController.ts`，语义化命名
4. 变量从 `x`/`y`/`z`/`u`/`p` 改为 `email`/`password`/`user`/`isValidPassword`，可读命名
5. 函数从 `f`/`doStuff` 改为 `login`/`comparePassword`，动词开头，意图清晰
6. 常量用 SCREAMING_SNAKE：`MAX_LOGIN_ATTEMPTS`、`AUTH_TOKEN_EXPIRY_MS`
7. 布尔用 is 前缀：`isValidPassword`
8. 异常类用 Exception 后缀：`InvalidCredentialsException`
9. 枚举用 PascalCase：`AuthStatus.Success`
10. 配置敏感信息移到 `.env`，提供 `.env.example` 模板
11. 添加 ESLint、EditorConfig 强制命名规范
12. 添加 `NAMING_CONVENTIONS.md` 文档化规范

### 总结

- 六大反模式：单字母变量、匈牙利命名、数字后缀、误导性命名、过度缩写、同义词混用
- 识别反模式是提升命名质量的第一步
- 综合实战展示了从"命名混乱"到"统一规范"的完整重构过程
- 重构的核心：概念词贯穿所有层级，风格各异但词根一致
- **关键要点**：命名不是一次性的工作，而是持续的重构——发现坏命名就立即改，代码库会越来越清晰

## 课程总结

### 核心知识回顾

本课程从基础认知到实战应用，系统讲解了「项目 + 文件夹 + 文件 + 变量」统一命名规则：

**第一章 基础认知篇**：命名是软件设计的核心活动，遵循准确、简洁、一致、可读、可搜索、无歧义六大原则，五大命名风格各有适用场景。

**第二章 项目与文件夹命名篇**：项目名用 kebab-case 且独特可记，仓库名与项目名一致，包名遵循注册表约束，文件夹按特性分组而非类型分组。

**第三章 文件命名篇**：源代码文件遵循语言惯例，配置文件用环境后缀区分，资源文件语义优先，测试文件与源文件同名加后缀。

**第四章 变量与代码元素命名篇**：变量用名词暗示类型，函数用动词开头表达动作，类用 PascalCase 代表类型，常量用 SCREAMING_SNAKE 醒目，布尔用 is/has/can 前缀。

**第五章 统一与实战篇**：跨层级统一的核心是概念词一致风格各异，团队规范要文档化 + 工具化 + CI 强制，识别并重构六大命名反模式。

### 终极原则

如果只能记住一件事，请记住：

> **同一个概念，在所有层级用相同的词，但遵循各自的命名风格。**

这是统一命名规则的灵魂——它让代码库自组织、自解释、自维护。当你和团队都践行这一原则时，命名不再是负担，而是沟通的桥梁、设计的表达、质量的保证。
