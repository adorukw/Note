## 第1讲：LangChain 简介与环境搭建

### 概念

**LangChain** 是一个用于开发由大语言模型（LLM）驱动的应用程序的开源框架。它由 Harrison Chase 于 2022 年 10 月发布，迅速成为 LLM 应用开发领域最受欢迎的框架之一。LangChain 的核心价值在于：它将"与 LLM 交互"这件事抽象成一系列可组合、可复用的组件，让开发者能够像搭积木一样构建复杂的 AI 应用。

简单来说，如果你把 LLM 比作一个"超级大脑"，那么 LangChain 就是给这个大脑配上"眼睛（读取数据）"、"手脚（调用工具）"、"记忆（保存上下文）"和"工作流程（任务编排）"的完整身体。

### 原理

LangChain 的设计哲学可以概括为三个核心原则：

1. **组件化（Modularity）**：将 LLM 应用拆分为 Prompt、Model、Parser、Chain、Memory、Retriever、Agent 等独立组件，每个组件职责单一、可独立使用、可自由组合。

2. **可组合性（Composability）**：通过统一的接口设计，组件之间可以像管道一样串联。例如 `prompt | model | parser` 就能组成一条完整的处理链。

3. **生态集成（Ecosystem）**：LangChain 提供了数百个集成包，支持 OpenAI、Anthropic、Google、本地模型等各种 LLM，支持 Chroma、Pinecone、FAISS 等各种向量数据库，支持各种文档加载器和工具。

LangChain 的包结构在 0.2 版本后做了重要调整：
- `langchain-core`：核心抽象与基础接口
- `langchain`：主包，包含 chains、agents 等高级功能
- `langchain-community`：第三方集成
- `langchain-openai`、`langchain-anthropic` 等：特定厂商的集成包

### 例子

**环境搭建步骤：**

```bash
# 1. 创建虚拟环境（推荐）
python -m venv langchain-env
source langchain-env/bin/activate  # Windows: langchain-env\Scripts\activate

# 2. 安装核心包
pip install langchain langchain-core

# 3. 安装特定厂商的集成包（以 OpenAI 为例）
pip install langchain-openai

# 4. 安装常用辅助包
pip install python-dotenv chromadb faiss-cpu

# 5. （可选）安装 LangSmith 用于调试
pip install langsmith
```

**配置环境变量（创建 `.env` 文件）：**

```env
OPENAI_API_KEY=sk-your-api-key-here
# 如果使用 LangSmith
LANGCHAIN_TRACING_V2=true
LANGCHAIN_API_KEY=lsyour-key-here
LANGCHAIN_PROJECT=my-langchain-project
```

**第一个 LangChain 程序：**

```python
# hello_langchain.py
import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI

# 加载环境变量
load_dotenv()

# 创建一个 Chat 模型实例
llm = ChatOpenAI(
    model="gpt-3.5-turbo",
    temperature=0.7,
)

# 最简单的调用方式
response = llm.invoke("用一句话解释什么是 LangChain？")
print(response.content)
```

运行后你会看到类似这样的输出：

```
LangChain 是一个用于开发大语言模型应用的开源框架，它通过组件化的方式将 LLM 与数据源、工具、记忆等能力组合起来，帮助开发者快速构建复杂的 AI 应用。
```

### 总结

- **核心要点**：LangChain 是 LLM 应用开发框架，核心思想是组件化、可组合、生态集成。
- **包结构**：注意区分 `langchain-core`（核心抽象）、`langchain`（主包）、`langchain-xxx`（厂商集成包）。
- **环境配置**：务必使用 `.env` 文件管理 API Key，不要硬编码到代码中。
- **常见坑**：
  - 版本兼容问题：LangChain 迭代很快，建议锁定版本号（如 `langchain==0.2.x`）。
  - API Key 泄露：永远不要把 Key 提交到 Git，记得在 `.gitignore` 中加入 `.env`。
  - 网络问题：国内访问 OpenAI 需要配置代理或使用兼容 API。

## 第2讲：核心概念与架构总览

### 概念

要理解 LangChain，需要先掌握它的六大核心组件。这些组件是构建任何 LLM 应用的基石：

1. **Prompt**：提示词模板，负责将用户输入和上下文组织成 LLM 能理解的格式。
2. **Model**：模型接口，统一封装不同 LLM 的调用方式（LLM 类和 ChatModel 类）。
3. **Output Parser**：输出解析器，将 LLM 返回的文本解析成结构化数据。
4. **Chain**：链，将多个组件串联起来形成完整的处理流程。
5. **Memory**：记忆，让应用能够记住之前的对话上下文。
6. **Retriever**：检索器，从外部知识库中检索相关信息，用于 RAG。
7. **Agent**：智能体，让 LLM 自主决定调用哪些工具来完成任务。

### 原理

LangChain 的架构可以分为三层：

**第一层：核心抽象层（langchain-core）**
定义了所有组件的统一接口。例如：
- `Runnable` 接口：所有组件都实现了这个接口，提供 `invoke`、`batch`、`stream` 等方法。
- `BaseMessage`：消息的基类，有 HumanMessage、AIMessage、SystemMessage 等。
- `BaseChatModel` 和 `BaseLLM`：模型的基类。

**第二层：主包（langchain）**
提供了 Chain、Agent 等高级组合逻辑，以及一些通用实现。

**第三层：集成包（langchain-community、langchain-openai 等）**
提供与具体厂商服务的对接实现。

**关键设计：Runnable 协议**

LangChain 0.1 之后最重要的设计是 `Runnable` 协议。任何实现了 `Runnable` 接口的对象都支持：
- `invoke(input)`：单次调用
- `batch(inputs)`：批量调用
- `stream(input)`：流式输出
- `ainvoke / abatch / astream`：异步版本

这意味着 Prompt、Model、Parser、Retriever 等都可以用统一的方式调用，并且可以用 `|` 操作符串联起来。

### 例子

**理解组件关系的示意图：**

```
用户输入
   ↓
[Prompt Template] ── 组织成提示词
   ↓
[Chat Model] ── 调用 LLM
   ↓
[Output Parser] ── 解析输出
   ↓
结构化结果

如果是 Chain，则是上面流程的组合；
如果是 Agent，则 Model 会决定是否调用 Tools；
如果是 RAG，则在 Prompt 之前会有 Retriever 检索相关文档。
```

**用代码感受组件协作：**

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from langchain_core.output_parsers import StrOutputParser

# 1. Prompt 组件
prompt = ChatPromptTemplate.from_template(
    "你是一位{role}，请用{style}的风格解释{topic}。"
)

# 2. Model 组件
model = ChatOpenAI(model="gpt-3.5-turbo", temperature=0.7)

# 3. Parser 组件
parser = StrOutputParser()

# 4. 用 | 串联成 Chain（这就是 LCEL 语法）
chain = prompt | model | parser

# 5. 调用
result = chain.invoke({
    "role": "幼儿园老师",
    "style": "生动有趣",
    "topic": "什么是重力"
})
print(result)
```

输出示例：

```
小朋友们，你们有没有想过，为什么我们跳起来后总会落回地面？为什么苹果会从树上掉下来？这就是"重力"在起作用啦！重力就像地球妈妈伸出的一只看不见的大手，把所有的东西都往自己身上拉...
```

### 总结

- **核心要点**：LangChain 由 Prompt、Model、Parser、Chain、Memory、Retriever、Agent 七大组件构成，通过 Runnable 协议统一接口。
- **架构分层**：core（抽象）→ main（组合）→ community/integrations（集成）。
- **LCEL 是关键**：`|` 操作符让组件串联变得直观，这是现代 LangChain 的核心写法。
- **常见误区**：
  - 不要把 LangChain 当成"调用 OpenAI 的库"，它的核心价值在于组件化和可组合性。
  - 早期版本（0.0.x）的 `LLMChain`、`ConversationChain` 等已不推荐使用，应改用 LCEL 语法。
  - 理解 Runnable 协议是理解整个框架的钥匙。

## 第3讲：Prompt 模板（PromptTemplate）

### 概念

**Prompt 模板** 是一种预定义的提示词结构，其中包含可替换的变量占位符。它的作用是将"固定的提示逻辑"与"动态的用户输入"分离，让提示词可复用、可管理、可测试。

LangChain 提供两种主要的模板类型：
- `PromptTemplate`：用于普通 LLM（输入输出都是字符串）。
- `ChatPromptTemplate`：用于 Chat Model（输入是消息列表，包含 system、human、ai 等角色）。

### 原理

Prompt 模板的工作原理很简单：定义一个包含 `{变量名}` 占位符的字符串，调用时传入变量值，模板会自动替换占位符生成最终提示词。

**ChatPromptTemplate 的消息角色：**
- `SystemMessage`：系统消息，设定 AI 的角色、行为规范，通常放在对话最前面。
- `HumanMessage`：用户消息，代表用户的输入。
- `AIMessage`：AI 消息，代表 AI 之前的回复（用于多轮对话场景）。

**为什么需要模板而不是直接 f-string？**
1. **验证**：模板会检查是否提供了所有必需的变量。
2. **复用**：模板是对象，可以在多处复用、可以序列化保存。
3. **部分填充**：可以先用 `partial` 填充部分变量，剩余的稍后填充。
4. **与 LCEL 无缝集成**：模板天然支持 `|` 操作符。

### 例子

**基础用法 - PromptTemplate：**

```python
from langchain_core.prompts import PromptTemplate

# 方式1：from_template
prompt = PromptTemplate.from_template(
    "请将以下{text}翻译成{language}：\n{text}"
)

# 方式2：构造函数（更明确）
prompt = PromptTemplate(
    input_variables=["text", "language"],
    template="请将以下{text}翻译成{language}：\n{text}"
)

# 格式化
formatted = prompt.format(text="Hello World", language="中文")
print(formatted)
```

输出：

```
请将以下Hello World翻译成中文：
Hello World
```

**ChatPromptTemplate（更常用）：**

```python
from langchain_core.prompts import ChatPromptTemplate

# 方式1：from_messages（推荐）
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一位专业的{role}，请用简洁专业的语气回答问题。"),
    ("human", "{question}"),
])

# 调用
messages = prompt.invoke({
    "role": "法律顾问",
    "question": "租房合同需要注意什么？"
})
print(messages)
```

输出：

```
messages=[
    SystemMessage(content='你是一位专业的法律顾问，请用简洁专业的语气回答问题。'),
    HumanMessage(content='租房合同需要注意什么？')
]
```

**部分填充（partial）：**

```python
from langchain_core.prompts import ChatPromptTemplate
from datetime import datetime

prompt = ChatPromptTemplate.from_messages([
    ("system", "当前时间是 {current_time}。你是一个助手。"),
    ("human", "{question}"),
])

# 提前填充 current_time，question 稍后填充
partial_prompt = prompt.partial(current_time=datetime.now().strftime("%Y-%m-%d %H:%M"))

# 后续只需提供 question
result = partial_prompt.invoke({"question": "今天几号？"})
print(result)
```

**组合多个模板：**

```python
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.messages import HumanMessage, AIMessage

# MessagesPlaceholder 用于插入动态消息列表（如历史对话）
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个友好的助手。"),
    MessagesPlaceholder(variable_name="history"),  # 历史对话
    ("human", "{input}"),
])

result = prompt.invoke({
    "history": [
        HumanMessage(content="我叫小明"),
        AIMessage(content="你好，小明！很高兴认识你。"),
    ],
    "input": "我叫什么名字？"
})
print(result)
```

### 总结

- **核心要点**：Prompt 模板分离固定逻辑与动态输入，`ChatPromptTemplate` 是 Chat Model 场景的首选。
- **消息角色**：system 设定角色，human 是用户输入，ai 是历史回复，`MessagesPlaceholder` 用于插入动态消息列表。
- **partial 机制**：适合需要提前填充部分变量（如时间戳、用户 ID）的场景。
- **常见注意事项**：
  - 变量名要用 `{}` 包裹，且不能与 Python 的 `format` 关键字冲突。
  - 模板可以序列化为 JSON 保存到文件，方便版本管理和团队协作。
  - 复杂提示词建议拆分成多个小模板组合，而不是写成一个超长字符串。

## 第4讲：LLM 与 Chat Model 调用

### 概念

LangChain 中有两种模型接口：

- **LLM**：传统的文本输入文本输出模型（如旧版 text-davinci-003）。输入是字符串，输出也是字符串。现在已较少使用。
- **ChatModel**：对话模型（如 GPT-4、Claude），输入是消息列表（Message 列表），输出是 AIMessage 对象。这是当前主流。

在现代 LangChain 开发中，**几乎都应该使用 ChatModel**，因为所有主流 LLM 厂商都已转向对话模型。

### 原理

**ChatModel 的工作机制：**

1. 接收一个消息列表（`List[BaseMessage]`），每条消息有 `role`（system/human/ai/tool）和 `content`。
2. 将消息列表发送给 LLM API。
3. 接收响应，封装成 `AIMessage` 对象返回。

**AIMessage 的结构：**
- `content`：文本内容
- `additional_kwargs`：附加信息（如 function_call）
- `response_metadata`：响应元数据（如 token 用量、模型名）
- `tool_calls`：工具调用信息（如果模型决定调用工具）

**关键参数：**
- `temperature`：0~2，控制随机性。0 最确定，越高越随机。
- `max_tokens`：限制输出长度。
- `model`：模型名称，如 `gpt-4o`、`gpt-3.5-turbo`。
- `streaming`：是否流式输出。

**为什么 LangChain 要封装一层？**
统一接口！无论底层是 OpenAI、Anthropic 还是本地模型，上层代码完全一致。切换模型只需改一行 import 和初始化。

### 例子

**基础调用：**

```python
from langchain_openai import ChatOpenAI

# 初始化
model = ChatOpenAI(
    model="gpt-3.5-turbo",
    temperature=0.7,
    max_tokens=500,
)

from langchain_core.messages import SystemMessage, HumanMessage

# 方式1：传入消息列表
messages = [
    SystemMessage(content="你是一个 Python 专家。"),
    HumanMessage(content="解释什么是装饰器？"),
]
response = model.invoke(messages)
print(response.content)
print(f"Token 用量: {response.response_metadata['token_usage']}")
```

**切换到其他模型（只需改 import）：**

```python
# 使用 Anthropic Claude
from langchain_anthropic import ChatAnthropic
model = ChatAnthropic(model="claude-3-5-sonnet-20241022")

# 使用 Google Gemini
from langchain_google_genai import ChatGoogleGenerativeAI
model = ChatGoogleGenerativeAI(model="gemini-1.5-pro")

# 使用本地 Ollama 模型
from langchain_ollama import ChatOllama
model = ChatOllama(model="llama3")

# 上层调用代码完全一样！
response = model.invoke([HumanMessage(content="你好")])
```

**批量调用（batch）：**

```python
questions = [
    [HumanMessage(content="1+1=?")],
    [HumanMessage(content="2+2=?")],
    [HumanMessage(content="3+3=?")],
]
responses = model.batch(questions)
for r in responses:
    print(r.content)
```

**流式输出（stream）：**

```python
# 流式输出，逐 token 返回
for chunk in model.stream("写一首关于春天的诗"):
    print(chunk.content, end="", flush=True)
print()  # 换行
```

**绑定工具调用参数（bind）：**

```python
# bind 方法可以为模型附加参数，常用于 function calling
model_with_stop = model.bind(stop=["\n\n"])
response = model_with_stop.invoke("写三段话")
print(response.content)  # 只输出第一段就停止
```

**完整调用元数据：**

```python
response = model.invoke([HumanMessage(content="你好")])
print("完整响应对象：")
print(f"  content: {response.content}")
print(f"  type: {response.type}")
print(f"  metadata: {response.response_metadata}")
print(f"  id: {response.id}")
```

### 总结

- **核心要点**：现代 LangChain 优先使用 ChatModel，输入消息列表，输出 AIMessage 对象。
- **统一接口**：切换模型只需改 import 和初始化，上层代码不变，这是 LangChain 最大的价值之一。
- **三种调用方式**：`invoke`（单次）、`batch`（批量）、`stream`（流式），都有异步版本 `ainvoke/abatch/astream`。
- **常见注意事项**：
  - `temperature` 不是越低越好：事实性任务用 0，创意任务用 0.7-1.0。
  - 注意 token 限制：长输入要预留输出空间，避免被截断。
  - 不同模型的参数名可能略有差异（如 Anthropic 的 `max_tokens` 是必填的）。
  - 生产环境务必加上重试和超时机制，LLM API 不稳定是常态。

# 第二章：核心组件深入

本章深入讲解 LangChain 的核心组件：输出解析器、LCEL 表达式语言、链式调用和记忆机制。掌握这些内容后，你就能构建出真正有用的 LLM 应用，而不仅仅是简单的问答。

---

## 第5讲：Output Parsers 输出解析器

### 概念

**Output Parser（输出解析器）** 是负责将 LLM 返回的原始文本转换成结构化数据（如 Python 对象、列表、字典）的组件。LLM 的输出本质上是字符串，但实际应用中我们往往需要结构化数据来驱动后续逻辑。

LangChain 提供了多种解析器：
- `StrOutputParser`：最简单，直接返回字符串内容。
- `JsonOutputParser`：解析 JSON。
- `PydanticOutputParser`：解析成 Pydantic 模型对象（最强大）。
- `CommaSeparatedListOutputParser`：解析逗号分隔的列表。
- `XMLOutputParser`：解析 XML。

### 原理

Output Parser 的工作包含两个核心方法：

1. **`get_format_instructions()`**：生成一段提示词，告诉 LLM 应该按什么格式输出。这段提示词会被拼接到你的 Prompt 中。

2. **`parse(text)`**：将 LLM 返回的文本解析成目标数据结构。如果解析失败，可以调用 `parse_with_prompt` 利用原始 prompt 进行错误恢复。

**PydanticOutputParser 的优势：**
- 通过 Pydantic 模型定义数据结构，自带类型验证。
- 自动生成 JSON Schema 告诉 LLM 输出格式。
- 解析失败时会抛出清晰的错误信息。

**为什么需要 Parser？**
LLM 输出有不确定性，可能多一个字、少一个字、加一段解释。Parser 配合 format_instructions 能显著提升输出格式的稳定性。

### 例子

**StrOutputParser（最常用）：**

```python
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-3.5-turbo")
parser = StrOutputParser()

# StrOutputParser 把 AIMessage 的 content 提取出来
chain = model | parser
result = chain.invoke("你好")
print(type(result))  # <class 'str'>
print(result)
```

**PydanticOutputParser（推荐用于结构化输出）：**

```python
from langchain_core.output_parsers import PydanticOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI
from pydantic import BaseModel, Field
from typing import List

# 1. 定义数据结构
class BookReview(BaseModel):
    title: str = Field(description="书名")
    author: str = Field(description="作者")
    rating: float = Field(description="评分，1-5")
    summary: str = Field(description="一句话总结")
    keywords: List[str] = Field(description="3-5个关键词")

# 2. 创建解析器
parser = PydanticOutputParser(pydantic_object=BookReview)

# 3. 创建 Prompt，注入格式说明
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个书评人。请按照指定格式输出。\n{format_instructions}"),
    ("human", "请评价《{book_name}》这本书。"),
]).partial(format_instructions=parser.get_format_instructions())

# 4. 组装链
model = ChatOpenAI(model="gpt-3.5-turbo", temperature=0)
chain = prompt | model | parser

# 5. 调用
review = chain.invoke({"book_name": "三体"})
print(type(review))  # <class 'BookReview'>
print(f"书名: {review.title}")
print(f"评分: {review.rating}")
print(f"关键词: {review.keywords}")
```

输出示例：

```
<class 'BookReview'>
书名: 三体
评分: 4.8
关键词: ['科幻', '宇宙社会学', '黑暗森林', '文明', '生存']
```

**JsonOutputParser（轻量级 JSON 解析）：**

```python
from langchain_core.output_parsers import JsonOutputParser

parser = JsonOutputParser()

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个数据生成器。请输出 JSON 格式：{{name: xxx, age: xxx}}"),
    ("human", "生成一个虚构人物。"),
])

chain = prompt | model | parser
result = chain.invoke({})
print(type(result))  # <class 'dict'>
print(result)  # {'name': '李雷', 'age': 25}
```

**CommaSeparatedListOutputParser：**

```python
from langchain_core.output_parsers import CommaSeparatedListOutputParser

parser = CommaSeparatedListOutputParser()
prompt = ChatPromptTemplate.from_messages([
    ("system", "列出项目。{format_instructions}"),
    ("human", "列出5种编程语言。"),
]).partial(format_instructions=parser.get_format_instructions())

chain = prompt | model | parser
result = chain.invoke({})
print(result)  # ['Python', 'JavaScript', 'Java', 'C++', 'Go']
```

### 总结

- **核心要点**：Output Parser 将 LLM 文本输出转换为结构化数据，`PydanticOutputParser` 是最强大的选择。
- **format_instructions**：解析器会生成格式说明，必须注入到 Prompt 中，否则 LLM 不知道该按什么格式输出。
- **错误处理**：解析可能失败，生产环境要 try-except，或使用 `parse_with_prompt` 进行错误恢复。
- **常见坑**：
  - 不要忘记把 `get_format_instructions()` 加到 Prompt 里，这是新手最常犯的错误。
  - Pydantic 模型的 `Field(description=...)` 很重要，描述越清晰，LLM 输出越准确。
  - 复杂结构建议用 Pydantic 而非纯 JSON，因为 Pydantic 自带类型校验。
  - 现代 LLM（如 GPT-4o）支持原生 structured output，可以结合 `with_structured_output` 方法使用，更稳定。

## 第6讲：LCEL（LangChain 表达式语言）

### 概念

**LCEL（LangChain Expression Language）** 是 LangChain 0.1 版本引入的声明式语法，用于将组件组合成链。它的核心是 `|` 操作符，让你能像 Unix 管道一样把组件串联起来：`prompt | model | parser`。

LCEL 不是一种新语言，而是一套基于 Python 的语法约定。任何实现了 `Runnable` 接口的对象都可以用 `|` 串联。

### 原理

**Runnable 协议是 LCEL 的基础。** 每个 Runnable 对象都实现了以下方法：
- `invoke(input)`：单次同步调用
- `batch(inputs)`：批量调用
- `stream(input)`：流式输出
- `ainvoke / abatch / astream`：异步版本
- `with_structured_output`：结构化输出
- `with_retry`：自动重试

**`|` 操作符的原理：**
`a | b` 实际上创建了一个 `RunnableSequence`，它会将 `a` 的输出作为 `b` 的输入。底层等价于：

```python
from langchain_core.runnables import RunnableSequence
chain = RunnableSequence(first=a, last=b)
```

**数据传递规则：**
- 如果前一个组件输出的是 dict，后一个组件可以按 key 取值。
- 如果前一个组件输出的是 Message，后一个组件接收 Message。
- 可以用 `RunnablePassthrough` 透传原始输入。

**LCEL 的核心优势：**
1. **天然支持流式**：组合后的链自动支持流式输出。
2. **天然支持异步**：同步代码改异步只需加 `a` 前缀。
3. **天然支持批量**：`batch` 方法自动并行处理。
4. **天然支持回溯**：配合 LangSmith 可以追踪每一步。
5. **可读性强**：`prompt | model | parser` 一眼就能看懂流程。

### 例子

**基础链：**

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

prompt = ChatPromptTemplate.from_template("讲一个关于{topic}的笑话")
model = ChatOpenAI(model="gpt-3.5-turbo")
parser = StrOutputParser()

# LCEL 语法
chain = prompt | model | parser
result = chain.invoke({"topic": "程序员"})
print(result)
```

**RunnablePassthrough 透传数据：**

```python
from langchain_core.runnables import RunnablePassthrough

# RunnablePassthrough 把输入原样传递给输出
# 常用于在并行分支中保留原始输入
chain = RunnablePassthrough()
print(chain.invoke({"name": "小明"}))  # {'name': '小明'}

# 配合 parallel 使用
from langchain_core.runnables import RunnableParallel

chain = RunnableParallel(
    original=RunnablePassthrough(),  # 保留原始输入
    upper=lambda x: x["text"].upper(),  # 转大写
)
print(chain.invoke({"text": "hello"}))
# {'original': {'text': 'hello'}, 'upper': 'HELLO'}
```

**并行执行（RunnableParallel）：**

```python
from langchain_core.runnables import RunnableParallel

# 同时生成笑话和诗
joke_chain = ChatPromptTemplate.from_template("讲一个关于{topic}的笑话") | model | StrOutputParser()
poem_chain = ChatPromptTemplate.from_template("写一首关于{topic}的诗") | model | StrOutputParser()

parallel_chain = RunnableParallel(
    joke=joke_chain,
    poem=poem_chain,
)

result = parallel_chain.invoke({"topic": "秋天"})
print("笑话:", result["joke"])
print("诗:", result["poem"])
```

**使用 itemgetter 提取字段：**

```python
from operator import itemgetter

prompt = ChatPromptTemplate.from_template("将'{text}'翻译成{language}")

# itemgetter 从 dict 中提取字段
chain = (
    {
        "text": itemgetter("text"),
        "language": itemgetter("language"),
    }
    | prompt
    | model
    | StrOutputParser()
)

result = chain.invoke({"text": "Hello", "language": "中文"})
print(result)
```

**添加重试和错误处理：**

```python
# 自动重试
chain = prompt | model.with_retry(stop_after_attempt=3) | parser

# 带回退的链
from langchain_core.runnables import RunnableWithFallbacks
fallback_model = ChatOpenAI(model="gpt-3.5-turbo")
primary_model = ChatOpenAI(model="gpt-4o")
model_with_fallback = primary_model.with_fallbacks([fallback_model])

chain = prompt | model_with_fallback | parser
```

**流式输出整个链：**

```python
# 整个链都支持流式
for chunk in chain.stream({"topic": "猫"}):
    print(chunk, end="", flush=True)
print()
```

### 总结

- **核心要点**：LCEL 用 `|` 操作符组合 Runnable 组件，是现代 LangChain 的核心写法。
- **Runnable 协议**：所有组件统一支持 invoke/batch/stream/ainvoke 等方法。
- **RunnablePassthrough**：透传数据，常用于并行分支中保留原始输入。
- **RunnableParallel**：并行执行多个链，结果合并成 dict。
- **常见注意事项**：
  - 优先使用 LCEL 而非旧的 `LLMChain`、`SequentialChain` 等类。
  - `itemgetter` 比 lambda 更高效，推荐用于字段提取。
  - 复杂链可以用 `.with_config()` 添加名称、标签，方便调试。
  - LCEL 链天然支持 LangSmith 追踪，每一步都可观测。

## 第7讲：Chains 链式调用

### 概念

**Chain（链）** 是将多个组件按特定顺序组合起来完成复杂任务的抽象。在 LCEL 出现之前，LangChain 提供了 `LLMChain`、`SequentialChain`、`RouterChain` 等预定义的链类。在现代 LangChain 中，推荐使用 LCEL 来构建链，但理解这些经典模式仍然重要。

常见的链模式包括：
- **顺序链**：组件按顺序执行，前一个的输出是后一个的输入。
- **路由链**：根据输入动态选择执行哪条链。
- **Map-Reduce 链**：先分块处理（map），再汇总（reduce）。
- **分支链**：根据条件走不同分支。

### 原理

**顺序链原理：**
最简单的链模式，等价于 LCEL 的 `a | b | c`。数据从第一个组件流向最后一个组件。

**路由链原理：**
1. 先用 LLM 分析输入，判断应该走哪条分支。
2. 根据判断结果，动态选择对应的链执行。
3. 返回所选链的输出。

**Map-Reduce 链原理：**
1. **Map 阶段**：将大任务拆分成多个小任务，并行处理。
2. **Reduce 阶段**：将所有小任务的结果汇总成最终答案。

这种模式特别适合长文档摘要、批量翻译等任务。

**为什么理解链模式重要？**
虽然 LCEL 让链的构建变得简单，但"什么时候用什么链"是设计问题。理解经典模式能帮你做出正确的架构决策。

### 例子

**顺序链（用 LCEL 实现）：**

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-3.5-turbo", temperature=0)

# 第一步：生成故事大纲
outline_prompt = ChatPromptTemplate.from_template("为关于{topic}的故事生成一个简短大纲。")
outline_chain = outline_prompt | model | StrOutputParser()

# 第二步：基于大纲写故事
story_prompt = ChatPromptTemplate.from_template("基于以下大纲写一个完整故事：\n{outline}")
story_chain = story_prompt | model | StrOutputParser()

# 串联：第一步的输出作为第二步的输入
# 注意字段名要对应
full_chain = (
    {"outline": outline_chain}
    | story_chain
)

result = full_chain.invoke({"topic": "时间旅行"})
print(result)
```

**路由链（动态选择分支）：**

```python
from langchain_core.runnables import RunnableLambda
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-3.5-turbo", temperature=0)

# 定义不同学科的回答链
math_chain = ChatPromptTemplate.from_template("你是数学老师。回答：{question}") | model | StrOutputParser()
history_chain = ChatPromptTemplate.from_template("你是历史老师。回答：{question}") | model | StrOutputParser()
science_chain = ChatPromptTemplate.from_template("你是科学老师。回答：{question}") | model | StrOutputParser()

# 路由分类器
classifier_prompt = ChatPromptTemplate.from_template(
    "判断以下问题属于哪个学科，只回答 'math'、'history' 或 'science'：\n{question}"
)
classifier_chain = classifier_prompt | model | StrOutputParser()

# 路由函数
def route(info):
    subject = classifier_chain.invoke({"question": info["question"]}).strip().lower()
    if "math" in subject:
        return math_chain
    elif "history" in subject:
        return history_chain
    else:
        return science_chain

# 组装路由链
router_chain = {"question": RunnableLambda(lambda x: x["question"])} | RunnableLambda(route)

result = router_chain.invoke({"question": "秦始皇统一六国是哪一年？"})
print(result)
```

**Map-Reduce 链（长文档摘要）：**

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI
from langchain_core.runnables import RunnableLambda

model = ChatOpenAI(model="gpt-3.5-turbo", temperature=0)

# Map：对每个分块生成摘要
map_prompt = ChatPromptTemplate.from_template("总结以下文本的要点：\n{text}")
map_chain = map_prompt | model | StrOutputParser()

# Reduce：合并所有摘要
reduce_prompt = ChatPromptTemplate.from_template(
    "将这些摘要合并成一段连贯的总结：\n{summaries}"
)
reduce_chain = reduce_prompt | model | StrOutputParser()

# 假设这是长文档的分块
documents = [
    "第一段内容...",
    "第二段内容...",
    "第三段内容...",
]

# Map 阶段：并行处理每个分块
summaries = map_chain.batch([{"text": doc} for doc in documents])

# Reduce 阶段：合并
final_summary = reduce_chain.invoke({"summaries": "\n".join(summaries)})
print(final_summary)
```

**分支链（RunnableBranch）：**

```python
from langchain_core.runnables import RunnableBranch

branch = RunnableBranch(
    (lambda x: "技术" in x["topic"], tech_chain),
    (lambda x: "生活" in x["topic"], life_chain),
    default_chain,  # 默认分支
)
```

### 总结

- **核心要点**：链是组件的组合模式，常见有顺序链、路由链、Map-Reduce 链、分支链。
- **LCEL 优先**：现代 LangChain 推荐用 LCEL 实现所有链模式，而非旧的 `LLMChain` 等类。
- **路由链**：适合多场景分类任务，如多学科问答、多语言处理。
- **Map-Reduce**：适合长文档处理、批量任务，能突破 token 限制。
- **常见注意事项**：
  - 字段名要严格对应，前一个组件输出的 key 必须是后一个组件需要的 key。
  - 路由链的分类器要稳定，否则会走错分支，建议用低 temperature。
  - Map-Reduce 的并行度要控制，避免触发 API 限流。
  - 复杂链建议用 LangSmith 追踪每一步，便于调试。

## 第8讲：Memory 记忆机制

### 概念

**Memory（记忆）** 让 LLM 应用能够记住之前的对话上下文，从而支持多轮对话。没有 Memory，每次调用 LLM 都是独立的，它无法知道你上一句说了什么。

LangChain 的 Memory 经历了多次演进：
- **早期**：`ConversationBufferMemory`、`ConversationSummaryMemory` 等类。
- **现代**：推荐直接用 `RunnableWithMessageHistory` 或手动管理消息列表。

需要明确：**Memory 本质上就是"如何管理对话历史消息"的策略**。

### 原理

**为什么需要 Memory？**
LLM 本身是无状态的，每次调用都是独立的。要实现多轮对话，必须把历史消息作为上下文一起发给 LLM。但历史消息会越来越长，最终超出 token 限制，所以需要策略来管理。

**常见的 Memory 策略：**

1. **Buffer（缓冲）**：保留所有历史消息。简单但会无限增长。
2. **Window（窗口）**：只保留最近 N 轮对话。简单有效，最常用。
3. **Summary（摘要）**：用 LLM 把旧对话压缩成摘要。节省 token 但有信息损失。
4. **Summary + Buffer**：最近几轮保留原文，更早的压缩成摘要。平衡方案。
5. **Vector Store**：把历史对话存入向量库，按相关性检索。适合超长对话。

**消息存储位置：**
- 内存（默认）：进程重启就丢失。
- Redis、数据库：持久化存储。
- LangGraph 的 checkpointer：状态持久化（高级方案）。

### 例子

**方式1：手动管理消息列表（最直观）：**

```python
from langchain_openai import ChatOpenAI
from langchain_core.messages import SystemMessage, HumanMessage, AIMessage

model = ChatOpenAI(model="gpt-3.5-turbo")

# 手动维护消息列表
messages = [
    SystemMessage(content="你是一个友好的助手。"),
]

# 第一轮
messages.append(HumanMessage(content="我叫小明，今年25岁。"))
response = model.invoke(messages)
messages.append(response)  # 把 AI 回复加入历史
print(f"AI: {response.content}")

# 第二轮（AI 能记住第一轮的信息）
messages.append(HumanMessage(content="我叫什么名字？"))
response = model.invoke(messages)
messages.append(response)
print(f"AI: {response.content}")
```

**方式2：RunnableWithMessageHistory（推荐）：**

```python
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_openai import ChatOpenAI
from langchain_community.chat_message_histories import ChatMessageHistory
from langchain_core.chat_history import BaseChatMessageHistory

model = ChatOpenAI(model="gpt-3.5-turbo", temperature=0)

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个友好的助手。"),
    MessagesPlaceholder(variable_name="history"),  # 历史消息插入位置
    ("human", "{input}"),
])

chain = prompt | model

# 存储每个 session 的历史
store = {}

def get_session_history(session_id: str) -> BaseChatMessageHistory:
    if session_id not in store:
        store[session_id] = ChatMessageHistory()
    return store[session_id]

# 包装链，自动管理历史
chain_with_history = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="input",
    history_messages_key="history",
)

# 调用时指定 session_id
config = {"configurable": {"session_id": "user123"}}

# 第一轮
response1 = chain_with_history.invoke(
    {"input": "我叫小明，今年25岁。"},
    config=config
)
print(f"AI: {response1.content}")

# 第二轮（同一个 session_id，能记住上一轮）
response2 = chain_with_history.invoke(
    {"input": "我叫什么名字？今年几岁？"},
    config=config
)
print(f"AI: {response2.content}")
```

**方式3：窗口记忆（只保留最近 N 轮）：**

```python
from langchain_core.runnables import RunnableLambda
from langchain_core.messages import SystemMessage

def trim_messages(messages, max_messages=6):
    """只保留最近 max_messages 条消息（加上 system 消息）"""
    system_msgs = [m for m in messages if isinstance(m, SystemMessage)]
    other_msgs = [m for m in messages if not isinstance(m, SystemMessage)]
    # 保留最近的 N 条
    return system_msgs + other_msgs[-max_messages:]

# 在链中加入裁剪步骤
chain = (
    RunnableLambda(lambda x: trim_messages(x["messages"], 6))
    | model
)
```

**方式4：持久化到 Redis：**

```python
from langchain_community.chat_message_histories import RedisChatMessageHistory

def get_session_history(session_id: str) -> BaseChatMessageHistory:
    return RedisChatMessageHistory(
        session_id=session_id,
        url="redis://localhost:6379",
        ttl=3600,  # 1小时过期
    )

chain_with_history = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="input",
    history_messages_key="history",
)
```

### 总结

- **核心要点**：Memory 本质是"如何管理对话历史消息"的策略，现代 LangChain 推荐 `RunnableWithMessageHistory`。
- **策略选择**：短对话用 Buffer，长对话用 Window 或 Summary，超长对话用 Vector Store。
- **session_id**：是区分不同用户/会话的关键，务必正确设置。
- **常见坑**：
  - 不要把所有历史都塞给 LLM，会超出 token 限制且成本高昂。
  - `history_messages_key` 必须与 Prompt 中的 `MessagesPlaceholder` 变量名一致。
  - 生产环境务必持久化（Redis/数据库），否则服务重启历史就丢了。
  - 多用户场景要确保 session_id 唯一，否则会串话。
  - LangGraph 提供了更强大的状态管理（checkpointer），适合复杂场景。

## 第9讲：Document Loaders 文档加载

### 概念

**Document Loader（文档加载器）** 负责将各种格式的数据源加载成 LangChain 统一的 `Document` 对象。无论数据来自 PDF、Word、网页、数据库还是 Notion，Loader 都能把它转换成统一格式，供后续处理。

`Document` 对象有两个核心属性：
- `page_content`：文档的文本内容
- `metadata`：元数据（如来源、页码、作者等）

LangChain 提供了 100+ 种 Loader，覆盖几乎所有常见数据源。

### 原理

**Loader 的工作流程：**
1. 读取数据源（文件、URL、API 等）。
2. 提取文本内容（可能涉及 OCR、HTML 解析等）。
3. 封装成 `Document` 对象列表返回。

**为什么需要统一的 Document 格式？**
因为后续的 Text Splitter、Embedding、Vector Store 都是基于 `Document` 操作的。统一格式让数据源与处理逻辑解耦，你可以随时更换数据源而不影响后续流程。

**Loader 的分类：**
- **文件类**：PDF、Word、Excel、CSV、Markdown、HTML
- **网页类**：WebBaseLoader、SitemapLoader
- **云服务类**：Notion、Google Drive、S3、Azure Blob
- **数据库类**：SQL、MongoDB、Elasticsearch
- **代码类**：GitHub、GitLab

### 例子

**加载文本文件：**

```python
from langchain_community.document_loaders import TextLoader

loader = TextLoader("./example.txt", encoding="utf-8")
documents = loader.load()
print(f"加载了 {len(documents)} 个文档")
print(f"内容前100字: {documents[0].page_content[:100]}")
print(f"元数据: {documents[0].metadata}")
```

**加载 PDF（最常用）：**



**自定义 Loader：**

```python
from langchain_core.documents import Document

    def __init__(self, source: str):
        self.source = source
    
    def lazy_load(self):
        # 实现自己的加载逻辑
```

### 总结

- **核心要点**：Document Loader 将各种数据源统一转换成 `Document` 对象，是 RAG 流程的入口。
- **Document 结构**：`page_content`（文本）+ `metadata`（元数据），元数据对后续检索很重要。
- **Loader 选择**：PDF 用 PyPDFLoader，网页用 WebBaseLoader，批量用 DirectoryLoader。
- **常见注意事项**：
  - PDF 加载质量参差不齐，扫描件需要 OCR（如 unstructured 库）。
  - 网页加载要处理编码问题，建议指定 encoding。
  - 大文件用 `lazy_load` 而非 `load`，避免内存爆炸。
  - 元数据要尽量保留完整（来源、页码、时间），对溯源和过滤很有用。
  - 不同 Loader 对同一文档的解析结果可能不同，要根据场景选择。

## 第10讲：Text Splitters 文本分割

### 概念

**Text Splitter（文本分割器）** 负责将长文档切分成较小的文本块（chunks）。这是 RAG 的关键步骤，因为：
1. LLM 有 token 限制，无法一次处理整本书。
2. 向量检索时，小块文本的语义更聚焦，检索更精准。
3. 小块文本作为上下文，能减少噪音、降低成本。

LangChain 提供多种分割策略，最常用的是 `RecursiveCharacterTextSplitter`。

### 原理

**为什么不能简单按字数切？**
如果硬切，会把一句话从中间切断，破坏语义。比如"中华人民共和国成立于1949年"被切成"中华人民共和国成立"和"于1949年"，两个块都失去了完整含义。

**RecursiveCharacterTextSplitter 的原理：**
按优先级依次尝试这些分隔符：`["\n\n", "\n", " ", ""]`
1. 先尝试用段落分隔符 `\n\n` 切。
2. 如果块还是太大，再用换行符 `\n` 切。
3. 还太大，用空格切。
4. 最后才用字符切。

这样能尽量保持语义完整性——优先在段落边界切，其次在句子边界切。

**关键参数：**
- `chunk_size`：每个块的最大字符数（如 1000）。
- `chunk_overlap`：相邻块的重叠字符数（如 200），用于避免切断上下文。
- `separators`：分隔符优先级列表。
- `length_function`：计算长度的函数（默认 len）。

**chunk_overlap 的作用：**
假设 chunk_size=100，overlap=20。第一个块是字符 0-100，第二个块是字符 80-180（与第一个块重叠 80-100 这 20 个字符）。这样即使一个关键信息正好在切分边界，也能在两个块中都出现，不会丢失。

**其他分割器：**
- `CharacterTextSplitter`：按单一字符切。
- `TokenTextSplitter`：按 token 数切（更精确控制 LLM 输入）。
- `MarkdownHeaderTextSplitter`：按 Markdown 标题切（保留文档结构）。
- `HTMLHeaderTextSplitter`：按 HTML 标签切。

### 例子

**RecursiveCharacterTextSplitter（最常用）：**

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50,
    separators=["\n\n", "\n", "。", "！", "？", "，", " ", ""],
    # 中文场景建议加入中文标点
)

text = """这是一段很长的文本...

第一段内容。这里有很多话。

第二段内容。这里也有很多话。

第三段内容。"""

chunks = splitter.split_text(text)
print(f"切分成 {len(chunks)} 块")
for i, chunk in enumerate(chunks):
    print(f"--- 块 {i} (长度 {len(chunk)}) ---")
    print(chunk)
```

**分割 Document 对象：**

```python
from langchain_community.document_loaders import TextLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter

# 加载文档
loader = TextLoader("./article.txt", encoding="utf-8")
docs = loader.load()

# 分割

    chunk_size=1000,
    chunk_overlap=200,
)

# split_documents 会保留每个块的 metadata，并添加来源信息
print(f"原文档 {len(docs)} 个，切分后 {len(chunks)} 个块")
print(f"第1块元数据: {chunks[0].metadata}")
```

**MarkdownHeaderTextSplitter（按标题切）：**

```python
from langchain_text_splitters import MarkdownHeaderTextSplitter

md_text = """
# 第一章

这是第一章的内容。

## 1.1 小节

这是 1.1 小节的内容。

## 1.2 小节

这是 1.2 小节的内容。

# 第二章

这是第二章的内容。
"""

splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[
        ("#", "Header 1"),
        ("##", "Header 2"),
        ("###", "Header 3"),
    ]
)

chunks = splitter.split_text(md_text)
for chunk in chunks:
    print(f"元数据: {chunk.metadata}")
    print(f"内容: {chunk.page_content}")
    print("---")
# 每个块的 metadata 会包含它所属的标题层级
```

**TokenTextSplitter（按 token 切）：**

```python
from langchain_text_splitters import TokenTextSplitter

splitter = TokenTextSplitter(
    chunk_size=500,  # 每块最多 500 token
    chunk_overlap=50,
)
chunks = splitter.split_text(text)
```

**代码分割器（按语言语法切）：**

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter, Language

# Python 代码分割
python_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON,
    chunk_size=500,
    chunk_overlap=50,
)

code = """
def hello():
    print("hello")

class Foo:
    def bar(self):
        pass
"""

chunks = python_splitter.split_text(code)
# 会按函数、类边界切分，保持代码完整性
```

### 总结

- **核心要点**：Text Splitter 将长文档切成小块，是 RAG 的关键预处理步骤。
- **首选 RecursiveCharacterTextSplitter**：它能智能地按语义边界切分，支持自定义分隔符。
- **chunk_size 和 overlap**：典型值是 500-1000 字符，overlap 设为 chunk_size 的 10-20%。
- **常见注意事项**：
  - 中文场景要加入中文标点（`。！？，`）到 separators。
  - chunk_size 不是越小越好：太小会丢失上下文，太大会引入噪音且超出 token 限制。
  - overlap 是为了防止关键信息被切断，但会增加存储成本。
  - 不同文档类型用不同分割器：Markdown 用 HeaderSplitter，代码用 from_language。
  - 分割质量直接影响 RAG 效果，值得花时间调参。

## 第11讲：Embeddings 与 Vector Stores

### 概念

**Embeddings（嵌入）** 是将文本转换成数值向量（通常是几百到几千维的浮点数数组）的技术。语义相近的文本，其向量也相近。这是实现"语义搜索"的基础——不再依赖关键词匹配，而是理解文本的含义。

**Vector Store（向量数据库）** 是专门存储和检索向量的数据库。它能在海量向量中快速找到与查询向量最相似的 Top-K 个向量，这是 RAG 的核心检索能力。

常见的向量数据库：
- **本地开发**：Chroma、FAISS
- **生产级**：Pinecone、Weaviate、Milvus、Qdrant、pgvector

### 原理

**Embedding 原理：**
Embedding 模型（如 OpenAI 的 text-embedding-3-small）经过训练，能将语义信息编码到向量空间中。训练目标是：语义相似的文本对，向量距离小；语义不相关的文本对，向量距离大。

**相似度计算：**
- **余弦相似度（Cosine Similarity）**：最常用，衡量向量方向的一致性。
- **欧氏距离（L2）**：衡量向量的绝对距离。
- **点积（Dot Product）**：归一化后等价于余弦相似度。

**Vector Store 的工作原理：**
1. **写入**：将文本通过 Embedding 模型转成向量，连同原文和元数据一起存入。
2. **检索**：将查询文本转成向量，在数据库中找最相似的 Top-K 个向量，返回对应的文本。

**近似最近邻（ANN）算法：**
向量数据库不会逐一比较所有向量（太慢），而是用 HNSW、IVF 等 ANN 算法，在毫秒级返回近似结果。牺牲一点点精度换取巨大速度提升。

**为什么不用传统数据库？**
传统数据库基于 B-Tree 索引，擅长精确匹配和范围查询，但无法高效处理"语义相似"这种高维向量检索。

### 例子

**使用 OpenAI Embeddings：**

```python

    model="text-embedding-3-small",  # 或 text-embedding-3-large

print(f"向量维度: {len(vector)}")  # 1536

```

- **模型选择**：OpenAI 的 text-embedding-3 系列效果好但要付费；本地用 BGE、M3E 等开源模型免费且中文效果好。
- **向量库选择**：开发用 Chroma/FAISS，生产用 Pinecone/Milvus/Qdrant/pgvector。
- **常见注意事项**：
  - Embedding 模型和 LLM 是独立的，可以自由组合。
  - 维度越高通常效果越好，但存储和检索成本也越高。

## 第12讲：Retrievers 检索器与 RAG 基础

### 概念

**Retriever（检索器）** 是 LangChain 中负责"根据查询返回相关文档"的统一接口。Vector Store 是 Retriever 的一种实现，但 Retriever 不限于向量检索——也可以是关键词检索、混合检索、甚至多查询检索。

**RAG（Retrieval-Augmented Generation，检索增强生成）** 是一种将外部知识注入 LLM 的技术模式：
1. 用户提问 → 检索相关文档 → 将文档作为上下文 → LLM 基于上下文回答。

RAG 解决了 LLM 的三大痛点：知识过时、容易幻觉、无法访问私有数据。

### 原理

**RAG 的完整流程：**

```
用户问题
   ↓
[Retriever] 检索相关文档（从向量库）
   ↓
[Prompt] 组装：问题 + 检索到的文档
   ↓
[LLM] 基于上下文生成回答
   ↓
答案
```

**为什么 RAG 比微调更适合知识注入？**
1. **成本低**：不需要训练，只需更新知识库。
2. **实时性**：知识库更新后立即生效，无需重新训练。
3. **可溯源**：可以告诉用户答案来自哪个文档。
4. **可控性**：可以随时删除/修改知识，不会"遗忘"。

**Retriever 的类型：**
- **Vector Retriever**：最基础，向量相似度检索。
- **MMR（Max Marginal Relevance）**：在相似度和多样性之间平衡，避免返回重复内容。
- **Multi-Query Retriever**：用 LLM 生成多个查询变体，分别检索后合并，提升召回率。
- **Contextual Compression Retriever**：检索后用 LLM 压缩，只保留与问题相关的部分。
- **Ensemble Retriever**：混合多个检索器（如向量 + 关键词）。

**Retriever 接口：**
所有 Retriever 都实现 `get_relevant_documents(query)` 方法，返回 `List[Document]`。在 LCEL 中可以用 `invoke` 调用。

### 例子

**基础 RAG 流程：**

```python
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

# 1. 准备向量库（假设已建好）
embeddings = OpenAIEmbeddings()
vectorstore = Chroma(
    persist_directory="./chroma_db",
    embedding_function=embeddings,
    collection_name="knowledge_base",
)

# 2. 创建检索器
retriever = vectorstore.as_retriever(
    search_type="similarity",  # 或 "mmr"
    search_kwargs={"k": 4},  # 返回 top 4
)

# 3. 定义 Prompt
prompt = ChatPromptTemplate.from_template("""
基于以下上下文回答问题。如果上下文中没有答案，请说"我不知道"。

上下文：
{context}

问题：{question}

回答：
""")

# 4. 创建 LLM
model = ChatOpenAI(model="gpt-3.5-turbo", temperature=0)

# 5. 组装 RAG 链
def format_docs(docs):
    return "\n\n".join(doc.page_content for doc in docs)

rag_chain = (
    {
        "context": retriever | format_docs,  # 检索并格式化
        "question": RunnablePassthrough(),    # 透传问题
    }
    | prompt
    | model
    | StrOutputParser()
)

# 6. 调用
answer = rag_chain.invoke("什么是 LangChain？")
print(answer)
```

**使用 MMR 提升多样性：**

```python
retriever = vectorstore.as_retriever(
    search_type="mmr",
    search_kwargs={
        "k": 4,
        "fetch_k": 20,  # 先检索 20 个
        "lambda_mult": 0.5,  # 0=最大多样性，1=最大相关性
    },
)
```

**Multi-Query Retriever（提升召回率）：**

```python
from langchain.retrievers.multi_query import MultiQueryRetriever
import logging

# 用 LLM 生成多个查询变体
retriever = MultiQueryRetriever.from_llm(
    retriever=vectorstore.as_retriever(),
    llm=model,
)

# 开启日志查看生成的查询
logging.basicConfig()
logging.getLogger("langchain.retrievers.multi_query").setLevel(logging.INFO)

docs = retriever.invoke("如何学习机器学习？")
# 会看到 LLM 生成了多个变体查询，如：
# 1. 机器学习入门方法
# 2. 机器学习学习路径
# 3. 零基础学机器学习
```

**带来源引用的 RAG：**

```python
from langchain_core.runnables import RunnableParallel

def format_docs_with_source(docs):
    formatted = []
    for i, doc in enumerate(docs):
        source = doc.metadata.get("source", "未知")
        formatted.append(f"[{i+1}] (来源: {source})\n{doc.page_content}")
    return "\n\n".join(formatted)

rag_chain = RunnableParallel(
    answer=(
        {
            "context": retriever | format_docs_with_source,
            "question": RunnablePassthrough(),
        }
        | prompt
        | model
        | StrOutputParser()
    ),
    sources=retriever,  # 同时返回检索到的文档
)

result = rag_chain.invoke("什么是 LangChain？")
print("回答:", result["answer"])
print("\n来源文档:")
for doc in result["sources"]:
    print(f"- {doc.metadata.get('source')}: {doc.page_content[:50]}...")
```

**流式输出 RAG：**

```python
# RAG 链天然支持流式
for chunk in rag_chain.stream("什么是 LangChain？"):
    print(chunk, end="", flush=True)
print()
```

### 总结

- **核心要点**：Retriever 是检索接口的抽象，RAG = 检索 + 生成，是注入外部知识的主流方案。
- **检索器选择**：基础用 similarity，要多样性用 mmr，要高召回用 multi-query。
- **Prompt 设计**：要明确告诉 LLM "基于上下文回答"、"不知道就说不知道"，减少幻觉。
- **常见注意事项**：
  - `k` 值不是越大越好：太多会引入噪音，太少可能漏掉关键信息，通常 3-5。
  - 检索质量决定 RAG 效果，检索不准的话 LLM 再强也没用。
  - 一定要做溯源，让用户知道答案依据，增强可信度。
  - 长文档检索建议先用 summary 检索，再定位到具体段落（parent-document retriever）。
  - 评估 RAG 效果可以用 Ragas 等工具，从 faithfulness、relevancy 等维度量化。

# 第四章：Agents 与工具

本章进入 LangChain 最激动人心的部分——智能体（Agent）。Agent 让 LLM 从"只会说话"变成"能做事"——它能调用搜索引擎、执行代码、操作数据库、发送邮件。你将学习如何定义工具、如何让 LLM 自主决策调用工具，以及 ReAct 等经典 Agent 模式。

---

## 第13讲：Tools 工具定义与使用

### 概念

**Tool（工具）** 是 Agent 可以调用的外部能力。它本质上是一个"有名称、有描述、有输入参数 schema 的函数"。LLM 通过阅读工具的名称和描述，判断什么时候该用哪个工具，并生成对应的调用参数。

常见的工具类型：
- **搜索工具**：Google Search、Wikipedia、Tavily
- **计算工具**：计算器、Python REPL、单位换算
- **数据工具**：SQL 查询、API 调用、数据库读取
- **文件工具**：读写文件、PDF 解析
- **自定义工具**：任何你能用 Python 实现的功能

### 原理

**工具的三要素：**
1. **name**：工具名称，LLM 用它来引用工具。
2. **description**：工具描述，告诉 LLM 这个工具能做什么、什么时候用。这是 LLM 决策的依据，写得好不好直接影响 Agent 效果。
3. **args_schema**：参数的 JSON Schema，告诉 LLM 该工具接受什么参数。

**工具的工作流程：**
1. LangChain 把所有工具的 name + description + args_schema 注入到 Prompt 中。
2. LLM 分析用户问题，决定是否需要调用工具，调用哪个工具，传什么参数。
3. LangChain 执行对应的 Python 函数，把结果返回给 LLM。
4. LLM 基于工具返回的结果，继续推理或生成最终答案。

**为什么 description 如此重要？**
LLM 只能通过 description 来理解工具的用途。如果描述模糊（如"搜索工具"），LLM 可能误用。好的描述应该说明：这个工具做什么、什么时候该用、什么时候不该用、输入是什么格式。

**工具的两种定义方式：**
1. **`@tool` 装饰器**：最简单，自动从函数签名和 docstring 生成 schema。
2. **`StructuredTool.from_function`**：更灵活，可以自定义 schema。
3. **继承 `BaseTool`**：最强大，可以实现复杂逻辑。

### 例子

**用 @tool 装饰器定义工具（最简单）：**

```python
from langchain_core.tools import tool

@tool
def search_weather(city: str) -> str:
    """查询指定城市的天气。
    
    Args:
        city: 城市名称，如"北京"、"上海"
    
    Returns:
        天气信息字符串
    """
    # 实际应用中这里会调用天气 API
    weather_data = {"北京": "晴天 25°C", "上海": "多云 28°C"}
    return weather_data.get(city, f"未找到 {city} 的天气信息")

@tool
def calculate(expression: str) -> str:
    """计算数学表达式。
    
    当需要精确计算时使用此工具，不要自己心算。
    
    Args:
        expression: 数学表达式，如 "2 + 3 * 4"
    
    Returns:
        计算结果
    """
    try:
        result = eval(expression)  # 注意：生产环境不要用 eval
        return str(result)
    except Exception as e:
        return f"计算错误: {e}"

# 查看工具信息
print(f"工具名: {search_weather.name}")
print(f"工具描述: {search_weather.description}")
print(f"参数 schema: {search_weather.args_schema.model_json_schema()}")

# 直接调用工具
print(search_weather.invoke({"city": "北京"}))  # 晴天 25°C
```

**用 Pydantic 定义复杂参数：**

```python
from langchain_core.tools import tool
from pydantic import BaseModel, Field

class SearchInput(BaseModel):
    query: str = Field(description="搜索关键词")
    max_results: int = Field(default=5, description="最大返回结果数")
    language: str = Field(default="zh", description="搜索语言")

@tool(args_schema=SearchInput)
def web_search(query: str, max_results: int = 5, language: str = "zh") -> str:
    """在网络上搜索信息。
    
    当需要查找最新信息或知识库中没有的内容时使用。
    
    Args:
        query: 搜索关键词
        max_results: 最大返回结果数
        language: 搜索语言
    """
    # 模拟搜索
    return f"搜索 '{query}'，返回 {max_results} 条结果（语言: {language}）"

result = web_search.invoke({"query": "LangChain", "max_results": 3})
print(result)
```

**继承 BaseTool（最灵活）：**

```python
from langchain_core.tools import BaseTool
from pydantic import BaseModel, Field
from typing import Type

class CalculatorInput(BaseModel):
    expression: str = Field(description="数学表达式")

class CalculatorTool(BaseTool):
    name: str = "calculator"
    description: str = "计算数学表达式。当需要精确计算时使用。"
    args_schema: Type[BaseModel] = CalculatorInput
    
    def _run(self, expression: str) -> str:
        """同步执行"""
        try:
            return str(eval(expression))
        except Exception as e:
            return f"错误: {e}"
    
    async def _arun(self, expression: str) -> str:
        """异步执行"""
        # 异步版本，如果不支持异步可以抛出异常
        raise NotImplementedError("Calculator does not support async")

calc = CalculatorTool()
print(calc.invoke({"expression": "100 * 25"}))  # 2500
```

```python
# pip install langchain-community
from langchain_community.tools import DuckDuckGoSearchRun

search = DuckDuckGoSearchRun()
result = search.invoke("LangChain 是什么")
```

**将工具转换为 Runnable：**

```python
# 工具本身就是 Runnable，可以用在 LCEL 链中
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-3.5-turbo")

# 工具可以作为链的一环
chain = (
    ChatPromptTemplate.from_template("提取这个句子中的数学表达式：{text}")
    | model
    | (lambda x: x.content)
    | calculate  # 把 LLM 输出传给计算工具
)

print(result)
```

### 总结

- **核心要点**：Tool 是 Agent 的"手脚"，由 name、description、args_schema 三要素定义。
- **@tool 装饰器**：最简单的定义方式，从函数签名和 docstring 自动生成 schema。
- **description 是灵魂**：写清楚工具做什么、何时用、输入格式，LLM 才能正确决策。
- **常见注意事项**：
  - 工具描述要具体，避免歧义，比如"搜索"不如"在网络上搜索最新新闻"。
  - 参数要有清晰的 description，LLM 才知道传什么值。
  - 工具函数要有错误处理，返回字符串而不是抛异常（Agent 才能继续推理）。
  - 异步场景要实现 `_arun` 方法。
  - 工具数量不宜过多（一般 5-10 个），太多会让 LLM 选择困难。

## 第14讲：Agents 智能体基础

### 概念

**Agent（智能体）** 是一种让 LLM 自主决策"做什么、怎么做"的机制。与 Chain（固定流程）不同，Agent 的执行流程是动态的——LLM 根据当前情况决定下一步动作，可能是调用工具，也可能是直接回答，还可能是继续思考。

**Agent vs Chain 的区别：**
- **Chain**：流程固定，`A → B → C`，每次都一样。
- **Agent**：流程动态，LLM 自主决定下一步，可能 `A → B → C`，也可能 `A → C → B → A → D`。

**Agent 的核心组件：**
1. **LLM**：决策大脑。
2. **Tools**：可调用的工具集。
3. **Agent Executor**：执行循环，负责"思考-行动-观察"的迭代。

### 原理

**Agent 的基本循环（Thought-Action-Observation）：**

```
1. Thought: 我需要先搜索信息
2. Action: 调用 search 工具，参数 "LangChain"
3. Observation: 搜索结果...
4. Thought: 现在我有信息了，可以回答
5. Action: 调用 final_answer 工具
6. 结束
```

这个循环会一直进行，直到 LLM 认为可以给出最终答案，或者达到最大迭代次数。

**为什么需要 Agent？**
有些任务无法预先规划好固定流程。比如"帮我查一下北京明天的天气，如果下雨就提醒我带伞"——这需要根据天气结果动态决策。Chain 做不到，Agent 可以。

**Agent 的关键能力：**
1. **工具选择**：从多个工具中选择合适的。
2. **参数生成**：为工具生成正确的调用参数。
3. **结果理解**：理解工具返回的结果，决定下一步。
4. **终止判断**：知道什么时候该停止并给出最终答案。
5. **错误恢复**：工具调用失败时能调整策略。

**现代 Agent 的演进：**
- **早期**：基于 ReAct 论文的文本解析 Agent，用正则提取 Action。
- **现代**：基于 LLM 原生 function calling 的 Agent，更稳定可靠。
- **最新**：LangGraph 提供的图结构 Agent，支持复杂状态管理。

### 例子

**使用 create_tool_calling_agent（推荐，支持原生 function calling）：**

```python
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain.agents import create_tool_calling_agent, AgentExecutor
from langchain_core.tools import tool

# 1. 定义工具
@tool
def search_weather(city: str) -> str:
    """查询指定城市的天气。"""
    weather_data = {"北京": "晴天 25°C", "上海": "多云 28°C", "广州": "雨天 30°C"}
    return weather_data.get(city, f"未找到 {city} 的天气")

@tool
def calculate(expression: str) -> str:
    """计算数学表达式。"""
    try:
        return str(eval(expression))
    except:
        return "计算错误"

tools = [search_weather, calculate]

# 2. 创建 LLM
model = ChatOpenAI(model="gpt-3.5-turbo", temperature=0)

# 3. 创建 Prompt
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一个有用的助手。可以使用提供的工具来回答问题。"),
    ("human", "{input}"),
    MessagesPlaceholder(variable_name="agent_scratchpad"),  # Agent 思考过程
])

# 4. 创建 Agent
agent = create_tool_calling_agent(model, tools, prompt)

# 5. 创建 AgentExecutor
agent_executor = AgentExecutor(
    agent=agent,
    tools=tools,
    verbose=True,  # 打印思考过程
    max_iterations=5,  # 最大迭代次数
    handle_parsing_errors=True,  # 处理解析错误
)

# 6. 调用
result = agent_executor.invoke({"input": "北京和上海哪个温度高？"})
print(result["output"])
```

执行过程会打印类似：

```
> Entering new AgentExecutor chain...

Invoking: `search_weather` with `{'city': '北京'}`
晴天 25°C
Invoking: `search_weather` with `{'city': '上海'}`
多云 28°C
上海的温度（28°C）比北京（25°C）高。

> Finished chain.
```

**使用 create_structured_chat_agent（支持复杂参数）：**

```python

```

**手动控制 Agent 的中间步骤：**

```python
# 可以逐步执行，观察每一步

    if step["intermediate_steps"]:
        for action, observation in step["intermediate_steps"]:
            print(f"动作: {action.tool}, 参数: {action.tool_input}")
            print(f"结果: {observation}")
    else:
        print("最终输出:", step.get("output", "进行中..."))
```

**返回中间步骤：**

```python

    return_intermediate_steps=True,

for action, observation in result["intermediate_steps"]:
    print(f"工具: {action.tool}")
    print(f"参数: {action.tool_input}")
    print(f"结果: {observation}")
    print("---")
```

### 总结

- **核心要点**：Agent 让 LLM 自主决策调用工具，适合流程不确定的复杂任务。
- **核心循环**：Thought（思考）→ Action（行动）→ Observation（观察）→ 重复。
- **推荐方式**：用 `create_tool_calling_agent` + `AgentExecutor`，支持原生 function calling。
- **常见注意事项**：
  - `max_iterations` 要设置，避免 Agent 陷入死循环。
  - `verbose=True` 便于调试，生产环境关闭。
  - `handle_parsing_errors=True` 能提升稳定性。
  - 工具描述要清晰，否则 Agent 会选错工具或传错参数。
  - Agent 比 Chain 慢且贵（多次 LLM 调用），简单任务不要用 Agent。
  - 现代 LangChain 推荐用 LangGraph 构建更复杂的 Agent（第18讲）。

## 第15讲：Agent Types 与 ReAct 模式

### 概念

**Agent Type（智能体类型）** 指的是 Agent 的不同推理和决策模式。不同类型的 Agent 适用于不同场景，理解它们的差异能帮你选择合适的方案。

**ReAct（Reasoning + Acting）** 是最经典的 Agent 模式，由 Yao et al. 2022 提出。它让 LLM 交替进行"推理（Reasoning）"和"行动（Acting）"，通过自然语言把思考过程显式化。

LangChain 支持的 Agent 类型：
- **ReAct**：经典文本推理模式，通用性强。
- **Tool Calling**：基于 LLM 原生 function calling，最稳定。
- **Structured Chat**：支持多参数工具。
- **OpenAI Functions**：OpenAI 专用，已逐渐被 Tool Calling 取代。
- **Self-Ask**：自问自答，适合知识检索。

### 原理

**ReAct 模式的工作原理：**

ReAct 让 LLM 输出特定格式的文本：

```
Thought: 我需要查询北京天气
Action: search_weather
Action Input: {"city": "北京"}
Observation: 晴天 25°C
Thought: 我得到了北京天气，现在可以回答
Final Answer: 北京今天是晴天，25度。
```

LangChain 用正则表达式解析这些文本，提取 Action 和 Action Input，调用对应工具，把结果作为 Observation 拼回去，让 LLM 继续。

**为什么 ReAct 有效？**
1. **显式推理**：把思考过程写出来，LLM 的推理更严谨（类似 chain-of-thought）。
2. **可观测**：每一步思考都可见，便于调试。
3. **可纠错**：如果 Observation 与预期不符，LLM 能调整策略。

**Tool Calling 模式 vs ReAct 模式：**

| 特性 | ReAct | Tool Calling |
|------|-------|--------------|
| 实现方式 | 文本解析 | LLM 原生 API |
| 稳定性 | 一般（依赖正则） | 高（原生支持） |
| 兼容性 | 任何 LLM | 需模型支持 |
| 思考可见性 | 高 | 低 |
| 推荐度 | 旧项目 | 新项目首选 |

**现代趋势：**
新项目优先用 Tool Calling（基于 `create_tool_calling_agent`），因为：
1. 不依赖文本解析，更稳定。
2. 支持复杂参数结构。
3. 主流模型（GPT-4、Claude、Gemini）都支持。

### 例子

**ReAct Agent（经典模式）：**

```python
from langchain.agents import create_react_agent, AgentExecutor
from langchain_core.prompts import PromptTemplate
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool

@tool
def search(query: str) -> str:
    """搜索网络信息。当需要查找最新信息时使用。"""
    return f"搜索结果：{query} 的相关信息..."

@tool
def calculate(expression: str) -> str:
    """计算数学表达式。"""
    return str(eval(expression))

tools = [search, calculate]

model = ChatOpenAI(model="gpt-3.5-turbo", temperature=0)

# ReAct 模式的 Prompt 模板（必须包含这些占位符）
template = """尽可能回答以下问题。你可以使用以下工具：

{tools}

使用以下格式：

Question: 你必须回答的输入问题
Thought: 你应该总是思考该做什么
Action: 要使用的工具，必须是 [{tool_names}] 中的一个
Action Input: 工具的输入
Observation: 工具的执行结果
... (Thought/Action/Action Input/Observation 可以重复 N 次)
Thought: 我现在知道最终答案了
Final Answer: 对原始问题的最终回答

开始！

Question: {input}
Thought:{agent_scratchpad}"""

prompt = PromptTemplate.from_template(template)

agent = create_react_agent(model, tools, prompt)
agent_executor = AgentExecutor(agent=agent, tools=tools, verbose=True)
```

## 第16讲：Tool Calling 与 Function Calling

### 概念

**Tool Calling（工具调用）** 和 **Function Calling（函数调用）** 是现代 LLM 的原生能力——模型能直接输出结构化的工具调用请求，而不是输出需要解析的文本。

OpenAI 最初称之为 "Function Calling"，后来扩展为 "Tool Calling"（支持同时调用多个工具）。现在业界普遍用 "Tool Calling" 这个术语。

**与 ReAct 的区别：**
- ReAct：LLM 输出文本，框架用正则解析。
- Tool Calling：LLM 直接输出结构化的 tool_calls，无需解析。

### 原理

**Tool Calling 的工作原理：**

1. **绑定工具**：把工具的 schema（name、description、parameters）通过 API 传给 LLM。
2. **LLM 决策**：LLM 分析用户输入，决定是否调用工具，生成 `tool_calls` 字段。
3. **执行工具**：框架根据 `tool_calls` 执行对应函数。
4. **返回结果**：把工具执行结果作为 `ToolMessage` 发回 LLM。
5. **LLM 总结**：LLM 基于工具结果生成最终回答。

**消息类型：**
- `HumanMessage`：用户消息
- `AIMessage`：AI 回复，可能包含 `tool_calls`
- `ToolMessage`：工具执行结果，包含 `tool_call_id`

**为什么 Tool Calling 比 ReAct 更好？**
1. **稳定性**：不依赖文本解析，不会因为格式错误失败。
2. **多工具调用**：LLM 可以一次性调用多个工具（并行）。
3. **类型安全**：参数有 schema 约束，减少参数错误。
4. **原生支持**：主流模型都支持，性能优化更好。

**with_structured_output 方法：**
这是 Tool Calling 的一个重要应用——让 LLM 输出符合指定 schema 的结构化数据，无需 Output Parser。

### 例子

**基础 Tool Calling：**

```python
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool
from langchain_core.messages import HumanMessage, ToolMessage

@tool
def get_weather(city: str) -> str:
    """获取城市天气。"""
    return {"北京": "晴天 25°C", "上海": "多云 28°C"}.get(city, "未知")

@tool
def get_time(timezone: str) -> str:
    """获取指定时区的当前时间。"""
    return f"{timezone} 当前时间: 14:30"

tools = [get_weather, get_time]
model = ChatOpenAI(model="gpt-3.5-turbo")

# 绑定工具
model_with_tools = model.bind_tools(tools)

# 第一次调用：LLM 决定调用工具
response = model_with_tools.invoke("北京天气怎么样？现在几点？")
print(f"AI 回复: {response.content}")
print(f"工具调用: {response.tool_calls}")
# tool_calls 示例:
# [
#   {"name": "get_weather", "args": {"city": "北京"}, "id": "call_xxx1"},
#   {"name": "get_time", "args": {"timezone": "Asia/Shanghai"}, "id": "call_xxx2"}
# ]
```

**完整的 Tool Calling 循环：**

```python
from langchain_core.messages import HumanMessage, AIMessage, ToolMessage

def run_tool_calling_loop(model, tools, user_input, max_iterations=5):
    """手动实现 Tool Calling 循环"""
    # 工具映射
    tool_map = {t.name: t for t in tools}
    model_with_tools = model.bind_tools(tools)
    
    messages = [HumanMessage(content=user_input)]
    
    for i in range(max_iterations):
        # 1. LLM 决策
        response = model_with_tools.invoke(messages)
        messages.append(response)
        
        # 2. 如果没有工具调用，返回最终答案
        if not response.tool_calls:
            return response.content
        
        # 3. 执行所有工具调用
        for tool_call in response.tool_calls:
            tool_name = tool_call["name"]
            tool_args = tool_call["args"]
            tool_id = tool_call["id"]
            
            print(f"调用工具: {tool_name}({tool_args})")
            result = tool_map[tool_name].invoke(tool_args)
            print(f"结果: {result}")
            
            # 4. 把结果作为 ToolMessage 加入对话
            messages.append(ToolMessage(
                content=str(result),
                tool_call_id=tool_id,
            ))
    
    return "达到最大迭代次数"

# 使用
result = run_tool_calling_loop(
    model, tools, "北京天气如何？现在几点？"
)
print("最终答案:", result)
```

  - `with_structured_output` 比 PydanticOutputParser 更稳定，优先使用。

## 第17讲：LangSmith 调试与监控

### 概念

**LangSmith** 是 LangChain 官方的 LLM 应用开发、调试、监控平台。它能追踪应用中每一步的输入输出、耗时、token 消耗，让你像调试普通程序一样调试 LLM 应用。

LLM 应用的痛点：
- **黑盒问题**：LLM 输出不确定，难以复现 bug。
- **链路复杂**：一个请求可能经过 Prompt → Model → Parser → Retriever 多个环节，出错难定位。
- **成本不透明**：不知道哪个环节消耗 token 最多。
- **评估困难**：难以量化应用质量。

LangSmith 解决这些问题的方式：把每一步的输入、输出、耗时、错误都记录下来，提供可视化界面分析。

### 原理

**LangSmith 的工作原理：**

1. **追踪（Tracing）**：通过环境变量或代码配置，LangSmith 会自动 hook 到 LangChain 的所有组件。
2. **记录（Logging）**：每次调用 LLM、Retriever、Tool 等，都会记录输入、输出、耗时、token 数。
3. **可视化（Visualization）**：在 LangSmith Web 界面查看调用链路，像看调用栈一样。
4. **评估（Evaluation）**：可以创建测试数据集，批量评估应用效果。

**追踪的层级结构：**
```
Trace (一次完整请求)
├── Run 1: ChatPromptTemplate
├── Run 2: ChatOpenAI
│   ├── 输入: messages
│   ├── 输出: AIMessage
│   ├── 耗时: 1.2s
│   └── Token: 150 (input) + 80 (output)
└── Run 3: StrOutputParser
```

**与 Callbacks 的关系：**
LangSmith 底层基于 Callbacks 机制实现。每个 Run 都会触发 `on_llm_start`、`on_llm_end` 等回调，LangSmith 在这些回调中记录数据。

**LangSmith 的核心功能：**
1. **Trace 可视化**：查看每一步的输入输出。
2. **Dataset & Evaluation**：创建测试集，批量评估。
3. **Playground**：在线调试 Prompt。
4. **Monitoring**：生产环境监控（付费功能）。

## 第18讲：LangGraph 工作流编排

### 概念

**LangGraph** 是 LangChain 团队推出的工作流编排框架，专门用于构建有状态、多步骤、可循环的 AI 应用。它解决了传统 Agent 的局限性，支持更复杂的控制流。

**为什么需要 LangGraph？**
传统 Agent（AgentExecutor）的局限：
1. **状态管理弱**：只能通过消息列表传递状态，复杂状态难管理。
2. **控制流单一**：基本是"思考-行动-观察"循环，难以实现复杂分支。
3. **无法人工干预**：中间步骤难以暂停等待人工确认。
4. **难以并行**：多 Agent 协作困难。

LangGraph 用**图（Graph）** 来组织工作流：
- **节点（Node）**：每个节点是一个函数或 Agent。
- **边（Edge）**：节点之间的连接，可以是条件边（根据状态决定下一步）。
- **状态（State）**：在节点间传递的数据，类型安全。

### 原理

**LangGraph 的核心概念：**

1. **State（状态）**：用 TypedDict 或 Pydantic 定义，在节点间共享。
2. **Node（节点）**：接收状态，返回状态更新。
3. **Edge（边）**：定义节点间的流转，可以是固定的，也可以是条件的。
4. **Graph（图）**：节点和边的集合，定义完整工作流。

**工作原理：**
1. 初始化状态。
2. 从起始节点开始执行。
3. 根据边的定义，决定下一个节点。
4. 执行下一个节点，更新状态。
5. 重复，直到到达结束节点。

**条件边的原理：**
条件边是一个函数，接收当前状态，返回下一个节点的名称。这让工作流能根据状态动态决策。

**与 AgentExecutor 的对比：**

| 特性 | AgentExecutor | LangGraph |
|------|---------------|-----------|
| 状态管理 | 消息列表 | 任意结构化状态 |
| 控制流 | 固定循环 | 图结构，灵活 |
| 人工干预 | 不支持 | 支持（中断） |
| 并行 | 有限 | 原生支持 |
| 持久化 | 无 | Checkpointer |
| 适用场景 | 简单 Agent | 复杂工作流 |

### 例子

**基础工作流：**

```python
# pip install langgraph
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

# 1. 定义状态
class State(TypedDict):
    messages: Annotated[list, add_messages]  # 消息列表会自动累加
    language: str

# 2. 定义节点
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage

model = ChatOpenAI(model="gpt-3.5-turbo")

def chatbot(state: State):
    """聊天节点"""
    response = model.invoke(state["messages"])
    return {"messages": [response]}  # 返回状态更新

# 3. 构建图
graph_builder = StateGraph(State)
graph_builder.add_node("chatbot", chatbot)
graph_builder.add_edge(START, "chatbot")
graph_builder.add_edge("chatbot", END)

# 4. 编译图
graph = graph_builder.compile()

# 5. 调用
result = graph.invoke({
    "messages": [HumanMessage(content="你好")],
    "language": "中文",
})
print(result["messages"][-1].content)
```

**带条件分支的工作流：**

```python
from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    query: str
    category: str
    response: str

# 分类节点
def classify(state: State) -> State:
    """根据查询内容分类"""
    query = state["query"]
    if "天气" in query:
        return {"category": "weather"}
    elif "新闻" in query:
        return {"category": "news"}
    else:
        return {"category": "general"}

# 天气处理节点
def handle_weather(state: State) -> State:
    return {"response": f"天气查询：{state['query']}"}

# 新闻处理节点
def handle_news(state: State) -> State:
    return {"response": f"新闻查询：{state['query']}"}

# 通用处理节点
def handle_general(state: State) -> State:
    return {"response": f"通用查询：{state['query']}"}

# 路由函数
def route(state: State) -> Literal["weather", "news", "general"]:
    return state["category"]

# 构建图
graph_builder = StateGraph(State)
graph_builder.add_node("classify", classify)
graph_builder.add_node("weather", handle_weather)
graph_builder.add_node("news", handle_news)
graph_builder.add_node("general", handle_general)

graph_builder.add_edge(START, "classify")
# 条件边：根据 route 函数的返回值决定下一个节点
graph_builder.add_conditional_edges("classify", route)
graph_builder.add_edge("weather", END)
graph_builder.add_edge("news", END)
graph_builder.add_edge("general", END)

graph = graph_builder.compile()

# 调用
result = graph.invoke({"query": "今天天气怎么样？"})
print(result["response"])  # 天气查询：今天天气怎么样？
```

**带循环的 Agent（类似 ReAct）：**

```python
from langgraph.prebuilt import ToolNode
from langgraph.graph import StateGraph, START, END
from langchain_core.tools import tool

@tool
def search(query: str) -> str:
    """搜索信息。"""
    return f"搜索结果：{query}"

@tool
def calculate(expression: str) -> str:
    """计算表达式。"""
    return str(eval(expression))

tools = [search, calculate]
model = ChatOpenAI(model="gpt-3.5-turbo").bind_tools(tools)

def agent_node(state: State):
    """Agent 决策节点"""
    response = model.invoke(state["messages"])
    return {"messages": [response]}

def should_continue(state: State) -> Literal["tools", END]:
    """判断是否继续调用工具"""
    last_message = state["messages"][-1]
    if last_message.tool_calls:
        return "tools"
    return END

# 构建带循环的图
graph_builder = StateGraph(State)
graph_builder.add_node("agent", agent_node)
graph_builder.add_node("tools", ToolNode(tools))

graph_builder.add_edge(START, "agent")
graph_builder.add_conditional_edges("agent", should_continue)
graph_builder.add_edge("tools", "agent")  # 工具执行后回到 agent

graph = graph_builder.compile()

# 调用
result = graph.invoke({
    "messages": [HumanMessage(content="计算 25 乘以 4")]
})
```

**带人工干预的工作流：**

```python
from langgraph.checkpoint.memory import MemorySaver

# 使用 checkpointer 支持中断和恢复
memory = MemorySaver()

def human_approval(state: State):
    """需要人工确认的节点"""
    # 这个节点会暂停，等待人工输入
    pass

graph_builder = StateGraph(State)
graph_builder.add_node("agent", agent_node)
graph_builder.add_node("human_approval", human_approval)
graph_builder.add_node("execute", lambda x: x)

graph_builder.add_edge(START, "agent")
graph_builder.add_edge("agent", "human_approval")
graph_builder.add_edge("human_approval", "execute")
graph_builder.add_edge("execute", END)

# 编译时指定中断点
graph = graph_builder.compile(
    checkpointer=memory,
    interrupt_before=["human_approval"],  # 在 human_approval 前暂停
)

# 第一次调用，会在 human_approval 前暂停
config = {"configurable": {"thread_id": "1"}}
result = graph.invoke({"messages": [...]}, config)
# 此时状态已保存

# 人工确认后，继续执行
result = graph.invoke(None, config)  # 传 None 表示继续
```

### 总结

- **核心要点**：LangGraph 用图结构编排工作流，支持状态管理、条件分支、循环、人工干预。
- **核心概念**：State（状态）、Node（节点）、Edge（边）、Graph（图）。
- **适用场景**：复杂 Agent、多 Agent 协作、需要人工干预的工作流、有状态的长流程。
- **常见注意事项**：
  - 简单 Agent 用 AgentExecutor 就够，不要过度设计。
  - State 的字段设计要谨慎，影响整个工作流。
  - 条件边的路由函数要稳定，否则会走错分支。
  - 用 Checkpointer 实现持久化，支持中断恢复。
  - LangGraph 是 LangChain 的未来方向，新项目推荐使用。

## 第19讲：Callbacks 与流式输出

### 概念

**Callbacks（回调）** 是 LangChain 的事件监听机制，允许你在 LLM 应用的各个生命周期事件中执行自定义逻辑。比如：记录日志、更新 UI、发送通知、收集指标等。

**流式输出（Streaming）** 是指 LLM 生成文本时，逐 token（或逐块）返回结果，而不是等全部生成完再返回。这能显著提升用户体验——用户不用盯着空白屏幕等几秒钟，而是能看到文字逐字出现。

两者关系：流式输出底层就是通过 Callbacks 的 `on_llm_new_token` 事件实现的。

### 原理

**Callbacks 的事件类型：**

LLM 相关：
- `on_llm_start`：LLM 开始调用
- `on_llm_new_token`：LLM 生成新 token（流式）
- `on_llm_end`：LLM 调用结束
- `on_llm_error`：LLM 调用出错

Chain 相关：
- `on_chain_start`：链开始
- `on_chain_end`：链结束
- `on_chain_error`：链出错

Tool 相关：
- `on_tool_start`：工具开始
- `on_tool_end`：工具结束

Retriever 相关：
- `on_retriever_start`：检索开始
- `on_retriever_end`：检索结束

**Callback Handler 的工作原理：**
1. 你创建一个 CallbackHandler，实现感兴趣的回调方法。
2. 把 handler 传给 LLM 或 Chain。
3. 在对应事件发生时，LangChain 自动调用你的方法。

**流式输出的原理：**
1. LLM API 支持 SSE（Server-Sent Events），逐 token 返回。
2. LangChain 的 `stream()` 方法把每个 token 包装成 chunk。
3. 通过 `on_llm_new_token` 回调或迭代器，把 chunk 传给应用。
4. 应用可以实时渲染每个 chunk。

**为什么流式重要？**
1. **用户体验**：减少等待焦虑，文字逐字出现更自然。
2. **感知速度**：首 token 延迟远小于完整响应延迟。
3. **可中断**：用户可以在生成中途停止。
4. **实时交互**：聊天场景必须流式。

### 例子

**基础流式输出：**


### 总结

- **核心要点**：Callbacks 是事件监听机制，流式输出通过 `stream()` 方法或 `on_llm_new_token` 回调实现。
- **流式价值**：提升用户体验、减少感知延迟、支持实时交互。
- **Callback 应用**：日志记录、token 计数、UI 更新、错误处理、指标收集。
- **常见注意事项**：
  - 流式输出需要模型支持，大部分现代 LLM 都支持。
  - `stream()` 是同步流式，`astream()` 是异步流式，Web 应用用异步。
  - Callback Handler 不要做耗时操作，会阻塞流式。
  - 生产环境务必做错误处理，流式中断要能恢复。
  - 流式输出的 chunk 可能不完整，前端要正确拼接。

## 第20讲：实战项目：构建完整 RAG 应用

### 概念

本讲把前面所有知识串联起来，构建一个完整的、生产级的 RAG（检索增强生成）应用。这个应用能：
1. 加载多种格式的文档（PDF、Markdown、TXT）
2. 智能切分并入库
3. 支持多轮对话
4. 返回带来源引用的答案
5. 支持流式输出
6. 有完整的错误处理和日志

这是一个"知识库问答"应用，是 RAG 最典型的落地场景。

### 原理

**完整 RAG 应用的架构：**

```
用户提问
   ↓
[1. 问题改写]（可选）用 LLM 把口语化问题改写成适合检索的查询
   ↓
[2. 检索] 从向量库检索 Top-K 相关文档
   ↓
[3. 重排]（可选）用 Cross-Encoder 重排，提升精度
   ↓
[4. 上下文组装] 把检索结果 + 对话历史 + 问题组装成 Prompt
   ↓
[5. 生成] LLM 基于上下文生成答案
   ↓
[6. 后处理] 添加来源引用、格式化输出
   ↓
答案
```

**关键设计决策：**

1. **是否做问题改写？**
   - 多轮对话中，用户可能说"那它呢？"，"它"指代不明。
   - 用 LLM 结合历史把问题改写成独立、完整的查询。
   - 代价：多一次 LLM 调用，增加延迟和成本。

2. **检索策略选择？**
   - 基础：similarity_search
   - 进阶：MMR（多样性）、Multi-Query（召回率）
   - 高级：Hybrid（向量 + 关键词）

3. **上下文长度控制？**
   - 检索太多文档会超出 token 限制。
   - 方案：限制 K 值、压缩文档、只取相关段落。

4. **如何减少幻觉？**
   - Prompt 明确要求"基于上下文回答"。
   - 设置"不知道就说不知道"的规则。
   - 让 LLM 标注引用来源。

### 例子

**完整的 RAG 应用代码：**

```python
"""
完整的 RAG 知识库问答应用
依赖：pip install langchain langchain-openai langchain-chroma langchain-community
"""

import os
from typing import List, Dict, Any, Optional
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_chroma import Chroma
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough, RunnableParallel
from langchain_core.documents import Document
from langchain_core.messages import HumanMessage, AIMessage
from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_community.chat_message_histories import ChatMessageHistory
from langchain_community.document_loaders import (
    TextLoader, PyPDFLoader, DirectoryLoader
)
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_core.chat_history import BaseChatMessageHistory


# ============================================
# 1. 配置
# ============================================

class Config:
    LLM_MODEL = "gpt-3.5-turbo"
    EMBEDDING_MODEL = "text-embedding-3-small"
    CHUNK_SIZE = 500
    CHUNK_OVERLAP = 50
    SEARCH_K = 4
    PERSIST_DIR = "./chroma_db"
    COLLECTION_NAME = "knowledge_base"


# ============================================
# 2. 文档处理模块
# ============================================

class DocumentProcessor:
    """文档加载、切分、入库"""
    
    def __init__(self, config: Config):
        self.config = config
        self.embeddings = OpenAIEmbeddings(model=config.EMBEDDING_MODEL)
        self.splitter = RecursiveCharacterTextSplitter(
            chunk_size=config.CHUNK_SIZE,
            chunk_overlap=config.CHUNK_OVERLAP,
            separators=["\n\n", "\n", "。", "！", "？", "，", " ", ""],
        )
    
    def load_directory(self, dir_path: str) -> List[Document]:
        """加载目录下所有支持的文档"""
        documents = []
        
        # 加载 TXT
        txt_loader = DirectoryLoader(
            dir_path, glob="**/*.txt",
            loader_cls=TextLoader,
            loader_kwargs={"encoding": "utf-8"},
            show_progress=True,
        )
        documents.extend(txt_loader.load())
        
        # 加载 PDF
        pdf_loader = DirectoryLoader(
            dir_path, glob="**/*.pdf",
            loader_cls=PyPDFLoader,
            show_progress=True,
        )
        documents.extend(pdf_loader.load())
        
        print(f"共加载 {len(documents)} 个文档")
        return documents
    
    def split_documents(self, documents: List[Document]) -> List[Document]:
        """切分文档"""
        chunks = self.splitter.split_documents(documents)
        print(f"切分成 {len(chunks)} 个块")
        return chunks
    
    def create_vectorstore(self, chunks: List[Document]) -> Chroma:
        """创建向量库"""
        vectorstore = Chroma.from_documents(
            documents=chunks,
            embedding=self.embeddings,
            persist_directory=self.config.PERSIST_DIR,
            collection_name=self.config.COLLECTION_NAME,
        )
        print(f"向量库已创建，共 {len(chunks)} 个向量")
        return vectorstore
    
    def load_vectorstore(self) -> Chroma:
        """加载已有向量库"""
        return Chroma(
            persist_directory=self.config.PERSIST_DIR,
            embedding_function=self.embeddings,
            collection_name=self.config.COLLECTION_NAME,
        )


# ============================================
# 3. RAG 链模块
# ============================================

class RAGChain:
    """RAG 问答链"""
    
    def __init__(self, config: Config, vectorstore: Chroma):
        self.config = config
        self.vectorstore = vectorstore
        self.retriever = vectorstore.as_retriever(
            search_type="mmr",  # 用 MMR 提升多样性
            search_kwargs={"k": config.SEARCH_K},
        )
        self.model = ChatOpenAI(
            model=config.LLM_MODEL,
            temperature=0,  # 事实性问答用低温度
            streaming=True,
        )
        self._build_chain()
    
    def _build_chain(self):
        """构建 RAG 链"""
        
        # Prompt 模板
        self.prompt = ChatPromptTemplate.from_messages([
            ("system", """你是一个知识库问答助手。请基于以下上下文回答问题。

规则：
1. 只基于上下文回答，不要编造信息。
2. 如果上下文中没有答案，明确说"根据知识库，我无法回答这个问题"。
3. 回答时标注来源，格式：[来源: 文件名]
4. 保持回答简洁、准确。

上下文：
{context}"""),
            MessagesPlaceholder(variable_name="history"),
            ("human", "{question}"),
        ])
        
        # 格式化文档
        def format_docs(docs: List[Document]) -> str:
            formatted = []
            for i, doc in enumerate(docs):
                source = doc.metadata.get("source", "未知")
                formatted.append(f"[来源: {source}]\n{doc.page_content}")
            return "\n\n---\n\n".join(formatted)
        
        # RAG 链
        self.chain = (
            {
                "context": self.retriever | format_docs,
                "history": RunnablePassthrough() | (lambda x: x.get("history", [])),
                "question": RunnablePassthrough() | (lambda x: x["question"]),
            }
            | self.prompt
            | self.model
            | StrOutputParser()
        )
    
    def ask(self, question: str, history: List = None) -> str:
        """同步问答"""
        return self.chain.invoke({
            "question": question,
            "history": history or [],
        })
    
    def ask_stream(self, question: str, history: List = None):
        """流式问答"""
        for chunk in self.chain.stream({
            "question": question,
            "history": history or [],
        }):
            yield chunk
    
    def ask_with_sources(self, question: str) -> Dict[str, Any]:
        """带来源的问答"""
        # 先检索
        docs = self.retriever.invoke(question)
        
        # 再生成
        answer = self.chain.invoke({
            "question": question,
            "history": [],
            "context": "\n\n".join(d.page_content for d in docs),
        })
        
        return {
            "answer": answer,
            "sources": [
                {
                    "content": d.page_content[:100] + "...",
                    "metadata": d.metadata,
                }
                for d in docs
            ],
        }


# ============================================
# 4. 对话管理模块
# ============================================

class ConversationManager:
    """多轮对话管理"""
    
    def __init__(self):
        self.store: Dict[str, ChatMessageHistory] = {}
    
    def get_history(self, session_id: str) -> BaseChatMessageHistory:
        if session_id not in self.store:
            self.store[session_id] = ChatMessageHistory()
        return self.store[session_id]
    
    def chat(self, rag_chain: RAGChain, session_id: str, question: str) -> str:
        """多轮对话"""
        history = self.get_history(session_id)
        history_messages = history.messages
        
        # 调用 RAG
        answer = rag_chain.ask(question, history_messages)
        
        # 保存到历史
        history.add_user_message(question)
        history.add_ai_message(answer)
        
        return answer


# ============================================
# 5. 主程序
# ============================================

def main():
    """主程序入口"""
    config = Config()
    
    # 步骤1：处理文档（首次运行）
    processor = DocumentProcessor(config)
    
    # 检查向量库是否已存在
    if not os.path.exists(config.PERSIST_DIR):
        print("首次运行，正在构建知识库...")
        documents = processor.load_directory("./knowledge")  # 你的文档目录
        chunks = processor.split_documents(documents)
        vectorstore = processor.create_vectorstore(chunks)
    else:
        print("加载已有知识库...")
        vectorstore = processor.load_vectorstore()
    
    # 步骤2：创建 RAG 链
    rag = RAGChain(config, vectorstore)
    
    # 步骤3：创建对话管理器
    conversation = ConversationManager()
    
    # 步骤4：交互式问答
    session_id = "user_001"
    print("\n知识库问答系统已启动（输入 'quit' 退出）\n")
    
    while True:
        question = input("你: ").strip()
        if question.lower() in ["quit", "exit", "q"]:
            break
        if not question:
            continue
        
        print("助手: ", end="", flush=True)
        
        # 流式输出
        for chunk in rag.ask_stream(question):
            print(chunk, end="", flush=True)
        print("\n")
        
        # 保存到对话历史
        full_answer = rag.ask(question)  # 实际应用中应该复用流式结果
        conversation.get_history(session_id).add_user_message(question)
        conversation.get_history(session_id).add_ai_message(full_answer)


if __name__ == "__main__":
    main()
```

```python
from langchain_community.retrievers import BM25Retriever

def create_hybrid_retriever(docs, embeddings):

    )
```

### 总结

- **核心要点**：完整 RAG 应用 = 文档处理 + 检索 + 生成 + 对话管理，每个环节都有优化空间。
- **架构设计**：模块化（DocumentProcessor、RAGChain、ConversationManager），便于维护和扩展。
- **关键优化**：问题改写、混合检索、重排序、流式输出、来源引用。
- **常见注意事项**：
  - 向量库要持久化，避免每次重建（费钱费时）。
  - 多轮对话要管理好历史，避免 token 爆炸。
  - Prompt 要明确规则，减少幻觉。
  - 生产环境要加错误处理、重试、限流。
  - 用 LangSmith 监控每一步，便于排查问题。
  - 评估很重要：用 Ragas 等工具量化 RAG 效果，持续优化。
  - 文档质量决定 RAG 上限：垃圾进，垃圾出。
