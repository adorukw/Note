# 第一章：Git 基础认知

## 第 1 讲：什么是版本控制系统 —— Git 的诞生与价值

### 概念

**版本控制系统（Version Control System, VCS）** 是一种记录文件内容变化、以便将来查阅特定版本修订情况的系统。它的核心职责是：在时间维度上为你的文件每一次修改保留一个可追溯的快照，并支持随时回退、对比、分支与合并。

**Git** 是当前最流行的**分布式版本控制系统（DVCS）**，由 Linus Torvalds 于 2005 年为管理 Linux 内核源码而开发。与传统的集中式版本控制系统（如 SVN、CVS）不同，Git 中每一个克隆仓库都拥有完整的历史记录与版本数据库，离线也能完成绝大多数操作。

### 原理

理解 Git 的价值，需要先理解它要解决的问题。在没有版本控制的时代，开发者常用「复制文件夹 + 改名」的方式备份版本，于是出现了 `report.doc`、`report_v2.doc`、`report_final.doc`、`report_final_really.doc` 这样的混乱局面。这种方式的痛点包括：无法追溯具体改了什么、无法多人协同、无法并行开发多条线索、无法安全回退。

Git 的设计哲学有几个关键点：

1. **快照而非差异**：每次提交保存的是项目在那一刻的完整快照，而非相对于上一版本的差异。对于未变化的文件，Git 只存储指向上一次版本的链接，既高效又完整。
2. **近乎所有的操作都是本地的**：因为每个克隆都是完整仓库，`git log`、`git diff`、`git commit` 等操作无需联网，速度极快。
3. **数据完整性保障**：Git 使用 SHA-1 哈希（正在向 SHA-256 迁移）为每一个对象（提交、树、文件块）计算校验和，任何篡改都会被立即发现。
4. **三种状态**：文件在 Git 中有三种状态——已提交（committed）、已修改（modified）、已暂存（staged），对应工作区、暂存区、版本库三个区域。

### 例子

一个典型的版本控制场景：你正在写一个 Python 项目，今天新增了登录功能，明天修复了登录的 bug，后天又加上了注册功能。使用 Git 后，你的提交历史可能是这样的：

```bash
$ git log --oneline
a1b2c3d (HEAD -> main) feat: 新增用户注册功能
e4f5g6h fix: 修复登录时密码校验的空指针问题
i7j8k9l feat: 新增用户登录功能
m0n1o2p init: 项目初始化
```

每一行就是一个版本快照，你可以随时回到任意一个状态。如果某天发现注册功能引入了 bug，可以快速定位到 `a1b2c3d` 这次提交，对比改动内容，甚至一键回退。

### 总结

- 版本控制系统的核心价值是**可追溯、可回退、可协同、可并行**。
- Git 是**分布式**版本控制系统，每个克隆都是完整仓库。
- Git 以**快照**方式存储数据，以**哈希校验**保障完整性。
- Git 的三种文件状态（已修改、已暂存、已提交）贯穿所有操作，务必牢记。
- 学习 Git 不仅是学命令，更是建立一种「版本化思维」：每一次有意义的改动都应成为一个提交。

## 第 2 讲：Git 的安装与初始配置

### 概念

在开始使用 Git 之前，需要完成两件事：**安装 Git 客户端**和**配置用户身份信息**。Git 是一个命令行优先的工具，虽然也有图形化客户端（如 Sourcetree、GitKraken、IDE 内置 Git），但掌握命令行是深入理解 Git 的前提。用户身份配置（用户名和邮箱）是必须的，因为 Git 的每一次提交都会记录是谁做的修改，这是协作中追溯责任的基础。

### 原理

Git 的安装方式因操作系统而异，但安装后的配置逻辑是统一的。Git 使用三层配置文件来管理设置：

1. **系统级**（`/etc/gitconfig`）：对系统所有用户生效，用 `git config --system` 读写。
2. **全局级**（`~/.gitconfig` 或 `~/.config/git/config`）：对当前用户的所有仓库生效，用 `git config --global` 读写。这是最常用的层级。
3. **仓库级**（`.git/config`）：仅对当前仓库生效，用 `git config`（不带 `--global`）读写。

三层配置遵循「就近原则」：仓库级覆盖全局级，全局级覆盖系统级。这种设计让你既能设置统一的默认偏好，又能为特定项目做个性化调整。

提交身份（`user.name` 和 `user.email`）之所以重要，是因为 Git 不依赖中心化账号系统，而是通过你声明的邮箱来标识作者。GitHub、GitLab 等平台也是通过提交中的邮箱来匹配用户主页的。

### 例子

**安装 Git**：

```bash
# Debian / Ubuntu
sudo apt-get update && sudo apt-get install git

# macOS（推荐使用 Homebrew）
brew install git

# Windows：从官网下载安装包 https://git-scm.com/download/win
# 安装后会附带 Git Bash 终端
```

**验证安装**：

```bash
$ git --version
git version 2.43.0
```

**初始配置**：

```bash
# 配置全局用户名和邮箱（提交时会写入历史）
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

# 配置默认分支名为 main（Git 2.28+ 支持，替代旧的 master）
git config --global init.defaultBranch main

# 配置默认编辑器（用于写提交信息）
git config --global core.editor "code --wait"   # VS Code
# 或 vim / nano / subl 等

# 启用彩色输出
git config --global color.ui auto

# 查看所有配置
git config --list
```

**配置 SSH 密钥**（用于免密推送 GitHub）：

```bash
# 生成密钥对
ssh-keygen -t ed25519 -C "you@example.com"

# 将公钥 ~/.ssh/id_ed25519.pub 的内容添加到 GitHub 账户
# 测试连接
ssh -T git@github.com
```

### 总结

- 安装后第一件事是配置 `user.name` 和 `user.email`，否则无法提交。
- 配置分三层：系统级、全局级、仓库级，遵循就近覆盖原则。
- 推荐设置 `init.defaultBranch main`，与社区主流约定一致。
- 配置 SSH 密钥可以避免每次推送都输入密码，是远程协作的标配。
- 用 `git config --list` 检查配置，用 `git config --global --unset <key>` 删除某项配置。
- 初学者常犯的错误是用了错误的邮箱，导致提交无法关联到 GitHub 账户，配置时务必核对。

## 第 3 讲：Git 的核心概念与三大区域

### 概念

Git 的核心在于三个区域和三种状态的对应关系：

- **工作区（Working Directory）**：你在文件管理器里能看到的项目目录，是你直接编辑文件的地方。
- **暂存区（Staging Area / Index）**：一个介于工作区和版本库之间的「准备区」，用于收集即将一起提交的改动。它对应 `.git/index` 文件。
- **版本库（Repository）**：Git 真正存储提交历史的地方，对应项目根目录下的 `.git` 隐藏文件夹。

文件在这三个区域之间流转，对应三种状态：**已修改（Modified）**、**已暂存（Staged）**、**已提交（Committed）**。

### 原理

为什么 Git 要设计一个看似多余的「暂存区」？这是 Git 与其他 VCS 最显著的差异，也是它最强大的特性之一。

在 SVN 等系统中，工作区的改动会直接进入下一次提交，你无法精细控制「哪些改动一起提交」。而 Git 的暂存区让你能够**把相关的改动打包成一个语义清晰的提交**。例如，你同时修改了登录功能和注册功能，又顺手改了一个无关的拼写错误，你可以分三次 `git add` 把它们分别暂存，然后分三次 `git commit`，得到三个语义清晰的提交，而不是一个混杂的大提交。

底层实现上，暂存区是一个二进制索引文件，记录了「下一次提交应该包含哪些文件的哪个版本」。`git add` 把工作区的文件快照写入暂存区，`git commit` 把暂存区的快照永久写入版本库，生成一个新的提交对象。

提交对象（commit object）包含四样东西：
1. 一个指向项目根目录树（tree）的指针
2. 指向父提交的指针（首次提交没有父提交，合并提交有多个父提交）
3. 作者信息（姓名 + 邮箱 + 时间戳）
4. 提交信息

每个提交对象用其内容的 SHA-1 哈希作为唯一标识，这就是你在 `git log` 里看到的那串字符。

### 例子

一个完整的「三区流转」演示：

```bash
# 初始化一个新仓库
$ mkdir demo && cd demo
$ git init
Initialized empty Git repository in /Users/you/demo/.git/

# 创建一个文件（文件在工作区）
$ echo "hello" > a.txt

# 查看状态：a.txt 是「未跟踪」状态
$ git status
Untracked files:
  a.txt

# 把 a.txt 加入暂存区
$ git add a.txt

# 再次查看状态：a.txt 已暂存
$ git status
Changes to be committed:
  new file:   a.txt

# 提交到版本库
$ git commit -m "first commit"
[main (root-commit) a1b2c3d] first commit
 1 file changed, 1 insertion(+)

# 修改文件（工作区变化，暂存区不变）
$ echo "world" >> a.txt
$ git status
Changes not staged for commit:
  modified:   a.txt
```

整个流转过程可以用一张图概括：

```
工作区  ──git add──▶  暂存区  ──git commit──▶  版本库
  ▲                   │                        │
  │                   │                        │
  └───── git checkout ─┴──── git reset ─────────┘
```

### 总结

- Git 的三大区域：**工作区、暂存区、版本库**，对应三种状态。
- 暂存区是 Git 的核心创新，让你能精细控制每次提交的内容。
- 提交对象包含树指针、父提交指针、作者信息、提交信息，用 SHA-1 哈希标识。
- `git status` 是你最常打的命令，它告诉你当前各区域的状态。
- 理解三区模型后，所有 Git 命令都可以归类为「在区域之间搬运数据」，这是后续学习的基础。
- 常见误区：以为 `git add` 就是「保存」，其实它只是把改动放进暂存区，真正保存到历史的是 `git commit`。

# 第二章：基础工作流

## 第 4 讲：仓库的创建与克隆

### 概念

**仓库（Repository）** 是 Git 管理项目的基本单位，是一个被 `.git` 目录跟踪的项目文件夹。获取一个仓库有两种主要方式：

1. **初始化新仓库**：在本地一个尚未纳入版本控制的目录中，用 `git init` 把它变成 Git 仓库。
2. **克隆远程仓库**：用 `git clone` 从远程服务器完整复制一个已存在的仓库到本地，包括所有历史记录。

这两种方式分别对应「从零开始一个新项目」和「加入一个已有项目」两种场景。

### 原理

`git init` 做的事情非常轻量：它只是在当前目录下创建一个 `.git` 隐藏文件夹，里面包含 Git 仓库所需的最小骨架（objects、refs、HEAD、config 等）。此时没有任何文件被跟踪，工作区保持原样。这种「先建仓库再慢慢加文件」的方式适合全新项目。

`git clone` 则是「完整复制」：它不仅下载当前版本的文件，还下载整个版本库的所有提交、所有分支、所有标签。这意味着克隆完成后，你在本地拥有了一个功能完整的仓库，可以离线查看历史、切换分支、创建新提交。这与 SVN 的「检出（checkout）」概念截然不同——SVN 检出只拿到当前版本，历史仍在中央服务器。

克隆时 Git 默认会把远程仓库命名为 `origin`，并设置本地 `main` 分支跟踪远程的 `main` 分支。这种「跟踪关系」让后续的 `git pull` 和 `git push` 无需指定参数就能工作。

### 例子

**初始化新仓库**：

```bash
# 方式一：在已有目录中初始化
$ cd my-project
$ git init
Initialized empty Git repository in /Users/you/my-project/.git/

# 方式二：初始化时指定初始分支名
$ git init -b main my-new-project
Initialized empty Git repository in /Users/you/my-new-project/.git/

# 方式三：把项目推送到 GitHub
$ git remote add origin git@github.com:you/my-project.git
$ git push -u origin main
```

**克隆远程仓库**：

```bash
# 基本克隆（默认使用 HTTPS 或 SSH 协议）
$ git clone https://github.com/libgit2/libgit2.git
Cloning into 'libgit2'...

# 克隆到指定目录
$ git clone https://github.com/libgit2/libgit2.git my-libgit2

# 只克隆最近一次提交（节省时间和空间，适合 CI）
$ git clone --depth 1 https://github.com/libgit2/libgit2.git

# 克隆指定分支
$ git clone -b develop https://github.com/libgit2/libgit2.git
```

**查看仓库状态**：

```bash
$ git status
On branch main
No commits yet
nothing to commit (create/copy files and use "git add" to track)
```

### 总结

- 获取仓库的两条路径：`git init`（新建）和 `git clone`（克隆）。
- `git init` 只创建 `.git` 目录，不跟踪任何文件。
- `git clone` 是完整复制，包括全部历史，克隆后即可离线工作。
- 克隆大仓库时用 `--depth 1` 做浅克隆，可大幅节省时间和磁盘。
- 远程仓库默认命名为 `origin`，本地分支默认跟踪同名远程分支。
- 注意：`git init` 后第一件事通常是配置 `.gitignore` 和做首次提交，避免把无关文件纳入版本控制。

## 第 5 讲：跟踪与提交 —— add 与 commit

### 概念

`git add` 和 `git commit` 是 Git 中最高频的两个命令，构成了「保存改动」的核心循环：

- **`git add`**：把工作区的改动放入暂存区，告诉 Git「这些改动我准备提交」。它既能跟踪新文件，也能暂存已修改文件。
- **`git commit`**：把暂存区的快照永久写入版本库，生成一个新的提交对象。每次提交都需要附带一条提交信息（commit message）。

这两个命令的配合体现了 Git「精细控制每次提交」的设计哲学。

### 原理

`git add` 的工作机制值得深入理解。当你执行 `git add file.txt` 时，Git 会做两件事：

1. 计算文件内容的哈希，把文件内容作为一个「blob 对象」存入 `.git/objects/`。
2. 更新 `.git/index` 文件，记录「file.txt 的下一个提交版本应该指向这个 blob」。

注意：`git add` 暂存的是**执行命令那一刻的文件快照**，而非文件本身。如果你 `git add` 之后又修改了文件，需要再次 `git add` 才能把新改动纳入暂存区。这是初学者常踩的坑。

`git commit` 则把暂存区的当前状态打包成一个提交对象。提交对象包含：一个指向根目录树的指针、父提交指针、作者信息、提交信息。提交后，HEAD 和当前分支指针都会前移到这个新提交。

提交信息是协作中的「沟通语言」。一条好的提交信息应该说明「为什么做这次改动」，而不是「改了什么」（diff 已经说明了 what）。社区普遍遵循 Conventional Commits 规范：`type(scope): subject`，例如 `feat(auth): add JWT login`。

### 例子

**基本提交流程**：

```bash
# 创建并跟踪新文件
$ echo "# My Project" > README.md
$ git add README.md
$ git commit -m "docs: add README"
[main b1c2d3e] docs: add README
 1 file changed, 1 insertion(+)

# 修改已跟踪文件
$ echo "Some content" >> README.md
$ git add README.md
$ git commit -m "docs: expand README with content"
```

**高效暂存技巧**：

```bash
# 暂存所有改动（新增、修改、删除）
$ git add .

# 暂存指定文件
$ git add file1.txt file2.txt

# 暂存某个目录下所有改动
$ git add src/

# 交互式暂存（按 hunk 选择，非常强大）
$ git add -p
# Git 会逐块展示改动，让你选择 y/n/s/e 等

# 暂存被删除的文件
$ git add -A
```

**高效提交技巧**：

```bash
# 跳过 add，直接提交所有已跟踪文件的改动（不包括新文件）
$ git commit -am "fix: typo in README"

# 修改上一次提交（追加文件或改提交信息）
$ git add forgotten.txt
$ git commit --amend --no-edit

# 用多行提交信息
$ git commit -m "feat: add user login" -m "This implements JWT-based authentication
with refresh token support."
```

**Conventional Commits 类型前缀**：

| 类型 | 含义 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `docs` | 文档变更 |
| `style` | 代码格式（不影响功能） |
| `refactor` | 重构（既不是新功能也不是修 bug） |
| `test` | 测试相关 |
| `chore` | 构建、依赖、辅助工具变更 |

### 总结

- `git add` 暂存的是文件快照，再次修改后需重新 `add`。
- `git commit` 生成不可变的提交对象，是版本历史的原子单位。
- 用 `git add -p` 做交互式暂存，可以把一个文件的改动拆成多个语义清晰的提交。
- 提交信息要写「为什么」，遵循 Conventional Commits 规范。
- `git commit --amend` 是修改最近一次提交的利器，但已推送的提交慎用。
- 常见错误：`git commit -am` 不会提交未跟踪的新文件，需要先 `git add` 一次。

## 第 6 讲：查看历史与状态 —— log、status、diff

### 概念

Git 提供了一组「观察」命令，让你随时了解仓库的状态和历史：

- **`git status`**：查看工作区和暂存区的当前状态，告诉你哪些文件被修改、哪些已暂存、哪些未跟踪。
- **`git log`**：查看提交历史，按时间倒序列出所有提交。
- **`git diff`**：查看差异，可以对比工作区与暂存区、暂存区与最新提交、任意两个提交之间。

这三个命令是「只读」的，不会改变任何东西，是日常开发中最高频的诊断工具。

### 原理

`git status` 的工作原理是比较三个区域：它先读取 HEAD 指向的提交快照，再读取暂存区索引，最后扫描工作区文件，三者两两比较后输出差异。这就是为什么 `git status` 能精确告诉你「这个文件已暂存但又有新的未暂存改动」。

`git log` 实际上是遍历提交图。Git 的提交历史不是线性的链表，而是一张有向无环图（DAG），因为合并提交有多个父提交。`git log` 默认从 HEAD 出发，沿着父指针反向遍历，按时间戳排序输出。理解这一点很重要，因为它解释了为什么 `git log` 在合并历史复杂时会显示「分叉与汇合」的结构。

`git diff` 的比较逻辑遵循一个清晰的模式：

- `git diff`：工作区 vs 暂存区（未暂存的改动）
- `git diff --staged`（或 `--cached`）：暂存区 vs HEAD（已暂存的改动）
- `git diff HEAD`：工作区 vs HEAD（所有未提交的改动）
- `git diff <commit1> <commit2>`：两个提交之间的差异

### 例子

**`git status` 详解**：

```bash
$ git status
On branch main
Changes to be committed:          # 已暂存，将进入下次提交
  modified:   src/main.py

Changes not staged for commit:    # 已修改但未暂存
  modified:   README.md

Untracked files:                  # 未跟踪
  notes.txt
```

**`git log` 常用形态**：

```bash
# 简洁单行视图（最常用）
$ git log --oneline
a1b2c3d (HEAD -> main, origin/main) feat: add login
e4f5g6h fix: typo
i7j8k9l init

# 带分支图的历史（可视化合并）
$ git log --oneline --graph --all
* a1b2c3d (HEAD -> main) feat: add login
| * b2c3d4e (feature) wip: new api
|/
* e4f5g6h fix: typo
* i7j8k9l init

# 显示每次提交的改动统计
$ git log --stat

# 显示每次提交的完整 diff
$ git log -p

# 查看最近 5 次提交
$ git log -5

# 查看某作者的提交
$ git log --author="Alice"

# 查看某段时间的提交
$ git log --since="2 weeks ago" --until="yesterday"

# 查看修改了某文件的提交
$ git log -- src/main.py
```

**`git diff` 详解**：

```bash
# 查看未暂存的改动
$ git diff

# 查看已暂存的改动
$ git diff --staged

# 查看所有未提交的改动（暂存 + 未暂存）
$ git diff HEAD

# 比较两个分支
$ git diff main feature

# 比较两个提交
$ git diff a1b2c3d e4f5g6h

# 只看哪些文件变了，不看具体内容
$ git diff --stat

# 只看某文件的改动
$ git diff -- src/main.py
```

**diff 输出解读**：

```diff
diff --git a/src/main.py b/src/main.py
index 1a2b3c4..5d6e7f8 100644
--- a/src/main.py       # 旧版本（-）
+++ b/src/main.py       # 新版本（+）
@@ -10,5 +10,6 @@ def main():
     print("hello")
     print("world")
-    print("old line")   # 删除的行
+    print("new line")   # 新增的行
     return 0
```

`@@ -10,5 +10,6 @@` 表示：旧文件从第 10 行起 5 行，新文件从第 10 行起 6 行。

### 总结

- `git status`、`git log`、`git diff` 是只读的诊断三件套，频繁使用是好习惯。
- `git log --oneline --graph --all` 是查看复杂历史最直观的方式。
- `git diff` 的三种形态（vs 暂存区、vs HEAD、vs 任意提交）要分清。
- diff 输出中 `-` 表示删除、`+` 表示新增，`@@` 行标注上下文位置。
- 提交前务必 `git diff --staged` 检查即将提交的内容，避免误提交调试代码。
- 善用 `git log -- <file>` 追溯某个文件的演变历史，是排查问题的利器。

## 第 7 讲：忽略文件 —— .gitignore 配置

### 概念

**`.gitignore`** 是一个文本文件，放在仓库根目录，用于告诉 Git 哪些文件或目录不应该被跟踪。被忽略的文件不会出现在 `git status` 中，也无法被 `git add` 误加入。它是保持仓库整洁、避免提交敏感信息或无关构建产物的关键配置。

### 原理

`.gitignore` 的每一行是一条「忽略规则」，遵循 glob 通配符语法：

- `*` 匹配任意字符（除 `/`）
- `?` 匹配单个字符
- `**` 匹配多级目录
- `/` 开头表示相对于 `.gitignore` 所在目录的根
- `/` 结尾表示只匹配目录
- `!` 开头表示取反（重新包含已被忽略的文件）

规则的作用范围是从 `.gitignore` 所在目录开始，向下递归到所有子目录。你可以在子目录中放置额外的 `.gitignore`，规则会叠加生效。

需要特别注意的是：**`.gitignore` 只能忽略未被跟踪的文件**。如果一个文件已经被 `git add` 跟踪了，之后再把它加入 `.gitignore` 是无效的，Git 仍会继续跟踪它的改动。要停止跟踪一个已被纳入版本控制的文件，需要用 `git rm --cached` 把它从索引中移除（但保留工作区文件）。

GitHub 维护了一个 [github/gitignore](https://github.com/github/gitignore) 仓库，收录了各种语言和框架的推荐 `.gitignore` 模板，可以直接复用。

### 例子

**典型项目的 `.gitignore`**：

```gitignore
# ===== Python =====
__pycache__/
*.py[cod]
*$py.class
*.so
.Python
venv/
env/
.env
*.egg-info/
dist/
build/

# ===== Node.js =====
node_modules/
npm-debug.log*
yarn-debug.log*
yarn-error.log*
.npm

# ===== Java =====
*.class
target/
*.jar
*.war

# ===== IDE / 编辑器 =====
.idea/
.vscode/
*.swp
*.swo
.DS_Store
Thumbs.db

# ===== 敏感信息（务必忽略）=====
config/local.json
*.pem
*.key
secrets/

# ===== 日志与临时文件 =====
*.log
*.tmp
*.bak
```

**规则语法示例**：

```gitignore
# 忽略所有 .log 文件
*.log

# 但不忽略 important.log（取反）
!important.log

# 只忽略根目录的 build，不忽略子目录的 build
/build/

# 忽略所有目录下的 node_modules
node_modules/

# 忽略 docs 目录下所有 .pdf
docs/**/*.pdf
```

**停止跟踪已被纳入版本控制的文件**：

```bash
# 假设 config/local.json 已经被提交过，现在想忽略它
$ echo "config/local.json" >> .gitignore
$ git rm --cached config/local.json      # 从索引移除，保留本地文件
$ git commit -m "chore: stop tracking local config"
```

**全局 `.gitignore`**（忽略所有项目中的系统文件）：

```bash
$ git config --global core.excludesfile ~/.gitignore_global
$ echo ".DS_Store" >> ~/.gitignore_global
$ echo "Thumbs.db" >> ~/.gitignore_global
```

### 总结

- `.gitignore` 用 glob 语法声明忽略规则，规则向下递归生效。
- 关键原则：**已被跟踪的文件无法被 `.gitignore` 忽略**，需先 `git rm --cached`。
- 务必忽略：构建产物、依赖目录、IDE 配置、系统文件、敏感信息、日志。
- 用 `!` 取反可以重新包含被通配符忽略的特定文件。
- 配置全局 `.gitignore` 处理系统级垃圾文件（如 `.DS_Store`），项目级 `.gitignore` 处理项目特定文件。
- 提交前检查 `git status`，确保没有意外把 `.env`、密钥等敏感文件纳入跟踪——这是生产事故的常见源头。

# 第三章：分支管理

## 第 8 讲：分支的本质与基本操作

### 概念

**分支（Branch）** 是 Git 中最核心的概念之一，它是指向某个提交对象的可移动指针。分支让你能够从主线开发中分出一条独立的开发线，在不影响主线的情况下进行实验、开发新功能或修复 bug，完成后再合并回去。

Git 的分支模型被称为它的「必杀特性」，因为它使得分支操作极其轻量——创建、切换、删除分支都是秒级操作，这与 SVN 等系统形成鲜明对比。

### 原理

要理解 Git 分支的轻量性，需要先理解 Git 的内部数据模型。在 Git 内部，分支并不是一个独立的「副本」或「容器」，它仅仅是一个包含 41 个字符的文件（40 字符的 SHA-1 哈希 + 换行符），存放在 `.git/refs/heads/` 目录下。例如，`.git/refs/heads/main` 文件的内容就是 main 分支当前指向的提交哈希。

与之配套的是 **HEAD 指针**，它是一个特殊引用，指向「当前所在的分支」。当你执行 `git commit` 时，Git 实际做的是：创建一个新提交对象，其父提交是当前分支指向的提交，然后把当前分支指针前移到新提交。HEAD 始终跟随当前分支。

这种设计意味着：
- **创建分支** = 写一个 41 字节的文件，几乎零成本。
- **切换分支** = 改 HEAD 指向 + 更新工作区文件，只动变化的部分。
- **删除分支** = 删除一个文件，提交历史本身不受影响。

对比 SVN，它的分支是复制整个目录，成本高昂，所以开发者尽量避免用分支。而 Git 鼓励频繁使用分支，这是工作流现代化的基础。

### 例子

**分支基本操作**：

```bash
# 查看所有本地分支（* 标记当前分支）
$ git branch
* main
  develop
  feature/login

# 查看所有分支（包括远程）
$ git branch -a

# 创建新分支（但不切换）
$ git branch feature/register

# 创建并切换到新分支（最常用）
$ git switch -c feature/register
# 旧写法（仍然有效）：git checkout -b feature/register

# 切换分支
$ git switch main
# 旧写法：git checkout main

# 删除分支（安全删除，未合并会拒绝）
$ git branch -d feature/register

# 强制删除分支（即使未合并）
$ git branch -D feature/register

# 重命名当前分支
$ git branch -m new-name
```

**典型分支工作流**：

```bash
# 在 main 上创建功能分支
$ git switch -c feature/payment
Switched to a new branch 'feature/payment'

# 在功能分支上开发并提交
$ echo "payment logic" > payment.py
$ git add payment.py
$ git commit -m "feat: add payment module"

# 切回 main，准备合并
$ git switch main
$ git merge feature/payment
Updating a1b2c3d..e4f5g6h
Fast-forward
 payment.py | 1 +

# 合并后删除功能分支
$ git branch -d feature/payment
```

**查看分支图**：

```bash
$ git log --oneline --graph --all
* e4f5g6h (HEAD -> main, feature/payment) feat: add payment module
* a1b2c3d init
```

### 总结

- 分支本质上是指向提交的可移动指针，创建成本极低。
- HEAD 是指向当前分支的特殊指针，跟随分支移动。
- 推荐用 `git switch` / `git restore`（Git 2.23+）替代 `git checkout` 的部分功能，语义更清晰。
- 频繁使用分支是 Git 工作流的核心，每个功能、每个修复都应有独立分支。
- 删除分支不会删除提交（只要提交已被合并或被其他分支引用）。
- 常见错误：在错误的分支上提交了改动。切换分支前用 `git status` 确认当前所在分支。

## 第 9 讲：合并分支 —— merge 详解

### 概念

**`git merge`** 用于把一个分支的改动整合到当前分支。合并是分支工作流的「汇合点」——你在功能分支上完成开发后，需要把改动合并回主线。

Git 的合并有两种主要模式：
1. **快进合并（Fast-forward）**：当目标分支是当前分支的直接祖先时，Git 只需把当前分支指针「快进」到目标分支，不产生新的提交。
2. **三方合并（Three-way merge）**：当两个分支都有各自的新提交时，Git 会找到它们的共同祖先，做一次三方比较，生成一个新的「合并提交（merge commit）」，它有两个父提交。

### 原理

理解合并的关键是「三方合并」这个概念。假设你从 main 分支切出 feature 分支后，main 和 feature 都各自前进了若干提交。此时合并 feature 到 main，Git 需要决定如何整合两边的改动。

Git 的做法是找到两个分支的**最近共同祖先（merge base）**，然后对三个快照进行比较：
- 共同祖先快照（基准）
- main 分支当前快照（ ours ）
- feature 分支当前快照（ theirs ）

对于每个文件，Git 检查三方各自的版本：
- 如果只有一方相对基准有改动，采用那一方。
- 如果两方都改动了同一处且改动不同，产生**冲突（conflict）**，需要人工解决。
- 如果两方都改动了但改动相同，自动采用。

如果两个分支是线性关系（一方是另一方的祖先），则无需三方合并，直接快进即可。快进合并不会产生合并提交，历史是线性的。许多团队偏好线性历史，会用 `--no-ff` 强制生成合并提交，以保留「这里发生过一次分支合并」的信息。

### 例子

**快进合并**：

```bash
# main: A → B
# feature: A → B → C → D
$ git switch main
$ git merge feature
Updating b1c2d3e..d4e5f6g
Fast-forward
 src/payment.py | 20 ++++++++++++
 1 file changed, 20 insertions(+)
```

**三方合并**：

```bash
# main: A → B → E
# feature: A → B → C → D
$ git switch main
$ git merge feature
Merge made by the 'ort' strategy.
 src/payment.py | 20 ++++++++++++
 1 file changed, 20 insertions(+)
```

**强制生成合并提交**（保留分支历史）：

```bash
$ git merge --no-ff feature -m "merge: integrate feature/payment"
```

**解决冲突**：

```bash
$ git merge feature
Auto-merging src/config.py
CONFLICT (content): Merge conflict in src/config.py
Automatic merge failed; fix conflicts and then commit the result.

# 查看冲突文件
$ git status
Unmerged paths:
  both modified:   src/config.py

# 打开冲突文件，会看到：
<<<<<<< HEAD
DEBUG = True       # 当前分支（main）的内容
=======
DEBUG = False      # 被合并分支（feature）的内容
>>>>>>> feature

# 手动编辑，保留正确内容，删除冲突标记
DEBUG = False

# 标记冲突已解决
$ git add src/config.py

# 完成合并
$ git commit -m "merge: resolve config conflict"
```

**中止合并**：

```bash
# 冲突太复杂，想放弃这次合并
$ git merge --abort
```

### 总结

- 合并分两种：快进合并（线性）和三方合并（产生合并提交）。
- 三方合并基于「共同祖先」做比较，能自动整合大部分改动。
- 冲突发生在「同一处被两方不同地修改」时，需手动解决。
- 解决冲突的流程：编辑文件 → `git add` → `git commit`。
- 用 `--no-ff` 保留分支历史，用 `--abort` 放弃合并回到合并前状态。
- 经验：合并前先 `git fetch` 拉取最新代码，减少冲突概率；冲突解决后务必测试，避免引入逻辑错误。

## 第 10 讲：变基 —— rebase 的艺术

### 概念

**`git rebase`** 是另一种整合分支改动的方式，字面意思是「变基」——把一系列提交「重新播放」到一个新的基底之上。与 merge 不同，rebase 不产生合并提交，而是通过改写提交历史，让分支看起来像是从一个更新的起点线性发展出来的。

rebase 的核心价值是**保持线性、整洁的历史**，但它会改写提交历史，因此需要谨慎使用，尤其是已推送的提交。

### 原理

假设有这样的历史：

```
      A---B---C feature
     /
D---E---F---G main
```

如果你在 feature 上执行 `git rebase main`，Git 会做以下事情：

1. 找到 feature 和 main 的共同祖先 E。
2. 把 feature 上 E 之后的提交（A、B、C）「临时保存」起来。
3. 把 feature 分支指针移到 main 的最新提交 G。
4. 依次「重放」A、B、C 到 G 之上，生成新的提交 A'、B'、C'（哈希变了，因为是新提交）。

结果：

```
              A'---B'---C' feature
             /
D---E---F---G main
```

历史变成线性的，没有合并提交。这就是 rebase 的「魔法」。

rebase 的风险在于：它**重写了提交历史**。重放后的提交是全新的提交（哈希不同），原始提交 A、B、C 在 rebase 后会变成「悬空提交」，最终被垃圾回收。如果这些提交已经被推送到远程并有人基于它们工作，rebase 会导致历史分叉，引发混乱。因此有一条铁律：**不要 rebase 已推送的公共分支**。

### 例子

**基本 rebase**：

```bash
# 当前在 feature 分支，把它的提交变基到 main 最新
$ git switch feature
$ git rebase main
Successfully rebased and updated refs/heads/feature.
```

**交互式 rebase**（最强大的历史编辑工具）：

```bash
# 修改最近 5 次提交
$ git rebase -i HEAD~5
```

这会打开编辑器，显示：

```
pick a1b2c3d feat: add login
pick e4f5g6h fix: typo in login
pick i7j8k9l feat: add register
pick m0n1o2p chore: update deps
pick q3r4s5t docs: update README

# 命令：
# pick = 保留
# reword = 保留但修改提交信息
# edit = 保留但暂停以修改内容
# squash = 合并到上一个提交
# fixup = 合并到上一个提交，丢弃提交信息
# drop = 删除
```

例如把 fix 和 feat 合并：

```
pick a1b2c3d feat: add login
fixup e4f5g6h fix: typo in login
pick i7j8k9l feat: add register
pick m0n1o2p chore: update deps
pick q3r4s5t docs: update README
```

**rebase 冲突处理**：

```bash
$ git rebase main
# 冲突！
$ git status
interactive rebase in progress

# 解决冲突
$ vim src/config.py
$ git add src/config.py

# 继续 rebase（不要用 git commit）
$ git rebase --continue

# 跳过当前提交
$ git rebase --skip

# 放弃 rebase，回到原状
$ git rebase --abort
```

**rebase 后推送**（需要强制推送）：

```bash
$ git push --force-with-lease origin feature
# --force-with-lease 比 --force 更安全，会检查远程是否有他人新提交
```

### 总结

- rebase 通过重放提交到新基底，保持线性历史。
- 交互式 rebase（`-i`）是整理提交历史的瑞士军刀：合并、改写、删除、重排。
- **铁律：永远不要 rebase 已推送的公共分支**，否则会破坏他人工作。
- rebase 冲突解决后用 `git rebase --continue`，不是 `git commit`。
- 强制推送用 `--force-with-lease` 而非 `--force`，避免覆盖他人提交。
- 经验法则：本地整理用 rebase，公共分支整合用 merge；或者团队统一约定一种策略。

## 第 11 讲：分支策略与工作流模型

### 概念

分支策略是团队协作的「交通规则」——约定如何用分支组织开发、如何命名、如何合并、谁负责整合。好的分支策略能让团队协作井然有序，差的策略则会导致合并地狱和发布混乱。

业界有几种成熟的分支模型，最知名的是 **Git Flow**、**GitHub Flow** 和 **GitLab Flow**，它们分别适合不同规模和发布节奏的项目。

### 原理

**Git Flow**（Vincent Driessen, 2010）是最经典的模型，适合有计划发布周期的项目（如桌面软件、企业应用）。它定义了五类分支：

- `main`：生产环境代码，每次合并都打 tag。
- `develop`：日常开发集成分支。
- `feature/*`：功能分支，从 develop 切出，合并回 develop。
- `release/*`：发布准备分支，从 develop 切出，合并回 main 和 develop。
- `hotfix/*`：紧急修复分支，从 main 切出，合并回 main 和 develop。

它的优点是结构清晰、适合多版本并行维护；缺点是分支多、流程重，对持续部署的项目过于繁琐。

**GitHub Flow**（GitHub, 2011）极简，只有 `main` + `feature/*` 两类分支。任何改动都从 main 切出 feature 分支，通过 Pull Request 合并回 main，main 始终可部署。适合 Web 应用、SaaS 等持续部署场景。

**GitLab Flow** 在 GitHub Flow 基础上增加了环境分支（`staging`、`production`），通过「上游→下游」的合并方向管理部署，兼顾了简洁与环境隔离。

选择哪种模型取决于：发布频率、是否多版本并行、是否有多个部署环境、团队规模。

### 例子

**Git Flow 示例**：

```bash
# 开始新功能
$ git switch develop
$ git switch -c feature/payment
# ...开发...
$ git switch develop
$ git merge --no-ff feature/payment
$ git branch -d feature/payment

# 准备发布
$ git switch -c release/1.2.0 develop
# ...修复发布前的 bug、更新版本号...
$ git switch main
$ git merge --no-ff release/1.2.0
$ git tag -a v1.2.0 -m "Release 1.2.0"
$ git switch develop
$ git merge --no-ff release/1.2.0
$ git branch -d release/1.2.0

# 紧急修复
$ git switch -c hotfix/1.2.1 main
# ...修复...
$ git switch main
$ git merge --no-ff hotfix/1.2.1
$ git tag -a v1.2.1
$ git switch develop
$ git merge --no-ff hotfix/1.2.1
$ git branch -d hotfix/1.2.1
```

**GitHub Flow 示例**：

```bash
# 任何改动都从 main 切出
$ git switch main
$ git pull
$ git switch -c feature/dark-mode
# ...开发、提交...
$ git push -u origin feature/dark-mode
# 在 GitHub 上发起 Pull Request
# 代码评审通过后合并到 main，自动部署
$ git switch main
$ git pull
$ git branch -d feature/dark-mode
```

**分支命名约定**：

```
feature/user-authentication     # 新功能
bugfix/login-redirect-loop      # bug 修复
hotfix/security-patch           # 紧急修复
release/2.0.0                   # 发布准备
chore/upgrade-dependencies      # 杂项
```

**Trunk-Based Development**（主干开发，Google、Facebook 等大厂采用）：

```
所有开发者频繁向 main 提交（每天多次）
功能用 feature flag 控制开关
短期 feature 分支（不超过 1-2 天）
适合 CI/CD 成熟、测试覆盖高的团队
```

### 总结

- 分支策略是团队协作的契约，选择取决于发布节奏和团队规模。
- Git Flow 适合有计划发布周期的传统项目，结构完整但流程重。
- GitHub Flow 极简，适合持续部署的 Web 应用。
- GitLab Flow 兼顾简洁与环境隔离，适合多环境部署。
- Trunk-Based 适合 CI/CD 成熟的大团队，强调频繁集成。
- 分支命名要统一约定，便于识别和自动化处理。
- 没有银弹：从简单模型起步，随团队成长逐步演进，避免过度设计。

# 第四章：远程协作

## 第 12 讲：远程仓库基础 —— remote、fetch

### 概念

**远程仓库（Remote Repository）** 是托管在网络服务器上的仓库，是团队协作的「中转站」。本地仓库通过远程引用（remote）与一个或多个远程仓库建立关联，从而实现代码共享。

`git remote` 用于管理远程仓库的关联，`git fetch` 用于从远程仓库下载数据到本地（但不合并到工作区）。理解这两个命令是掌握远程协作的基础。

### 原理

Git 的远程管理是去中心化的——一个本地仓库可以关联多个远程仓库，每个远程仓库有一个简短的名字（如 `origin`、`upstream`）。远程仓库的信息存储在 `.git/config` 文件中，包括名称、URL 和 fetch/push 的引用映射。

`git fetch` 的本质是「同步引用」。它从远程仓库下载以下内容：
1. 远程分支上新的提交对象。
2. 远程的标签等其他引用。

下载后，这些内容被存储在本地的「远程跟踪分支」中，形如 `origin/main`、`origin/develop`。**关键点**：`git fetch` 不会修改你的本地分支，也不会改动工作区。它只是更新远程跟踪分支，让你「看到」远程的最新状态。要真正整合这些改动，你还需要手动 `git merge` 或 `git rebase`。

这种「下载」与「整合」分离的设计，让你可以先观察远程的变化，再决定如何整合，避免了 `git pull`（fetch + merge）可能带来的意外合并。

远程跟踪分支（如 `origin/main`）是只读的本地引用，它们在 `git fetch` 时被自动更新。你不能直接在远程跟踪分支上提交，但可以基于它创建本地分支来工作。

### 例子

**查看与管理远程**：

```bash
# 查看已配置的远程仓库
$ git remote
origin

# 查看远程仓库的 URL
$ git remote -v
origin  git@github.com:you/repo.git (fetch)
origin  git@github.com:you/repo.git (push)

# 查看某个远程的详细信息
$ git remote show origin
* remote origin
  Fetch URL: git@github.com:you/repo.git
  Push  URL: git@github.com:you/repo.git
  HEAD branch: main
  Remote branches:
    main    tracked
    develop tracked
  Local branches configured for 'git pull':
    main    merges with remote main
  Local refs configured for 'git push':
    main    pushes to main    (up to date)
```

**添加与移除远程**：

```bash
# 添加远程仓库
$ git remote add origin git@github.com:you/repo.git

# 添加上游仓库（fork 场景常用）
$ git remote add upstream git@github.com:original/repo.git

# 修改远程 URL
$ git remote set-url origin git@github.com:you/new-repo.git

# 重命名远程
$ git remote rename origin upstream

# 移除远程
$ git remote remove origin
```

**fetch 操作**：

```bash
# 拉取默认远程（origin）的所有分支
$ git fetch

# 拉取指定远程
$ git fetch origin

# 拉取指定分支
$ git fetch origin main

# 拉取所有远程
$ git fetch --all

# 拉取并清理已删除的远程分支
$ git fetch --prune
```

**fetch 后查看与整合**：

```bash
$ git fetch origin
From github.com:you/repo
 * [new branch]      develop    -> origin/develop
   a1b2c3d..e4f5g6h  main       -> origin/main

# 查看本地 main 与远程 main 的差异
$ git log main..origin/main --oneline
e4f5g6h feat: add search

# 整合到本地（merge 或 rebase）
$ git switch main
$ git merge origin/main
```

### 总结

- 远程仓库是协作的中转站，一个本地仓库可关联多个远程。
- `git fetch` 只下载不整合，是安全的「观察」操作。
- 远程跟踪分支（`origin/main`）是只读的本地引用，反映远程状态。
- 推荐用 `git fetch` + 手动 merge/rebase 替代 `git pull`，获得更多控制权。
- Fork 工作流中常用 `upstream` 远程跟踪原始仓库，定期同步上游更新。
- 用 `git fetch --prune` 清理本地缓存的已删除远程分支，保持引用整洁。

## 第 13 讲：推送与拉取 —— push、pull 详解

### 概念

`git push` 和 `git pull` 是远程协作中最核心的两个命令：

- **`git push`**：把本地分支的提交上传到远程仓库，更新远程分支。
- **`git pull`**：从远程仓库下载提交并立即整合到当前分支，等价于 `git fetch` + `git merge`。

这两个命令实现了代码在本地与远程之间的双向流动，是团队协作的命脉。

### 原理

`git push` 的工作机制是：Git 把本地分支独有的提交对象发送给远程仓库，远程仓库验证后更新对应的远程分支指针。推送时可能遇到「非快进（non-fast-forward）」错误——当远程分支有你本地没有的提交时，直接推送会覆盖他人工作，Git 会拒绝。此时需要先 `git pull` 整合远程改动，再推送。

首次推送一个本地分支时，需要用 `-u`（`--set-upstream`）建立跟踪关系，这样后续 `git push` / `git pull` 无需指定参数即可工作。跟踪关系记录在 `.git/config` 中。

`git pull` 是 `git fetch` + `git merge` 的组合快捷方式。它先下载远程改动，然后立即把远程跟踪分支合并到当前分支。这种「下载即合并」的行为可能产生意外的合并提交，因此更推荐显式地 `git fetch` + `git rebase`。可以用 `git pull --rebase` 让 pull 改用 rebase 整合，保持线性历史。

推送的权限模型：远程仓库可以配置为「只允许快进推送」或「允许强制推送」。强制推送（`--force`）会覆盖远程历史，极其危险，应优先使用 `--force-with-lease`，它会在远程有他人新提交时拒绝推送。

### 例子

**push 详解**：

```bash
# 首次推送本地分支并建立跟踪
$ git push -u origin feature/login
# 后续推送只需
$ git push

# 推送当前分支到同名远程分支
$ git push origin HEAD

# 推送所有本地分支
$ git push origin --all

# 推送标签
$ git push origin v1.0.0
$ git push origin --tags

# 删除远程分支
$ git push origin --delete feature/login

# 强制推送（慎用！优先用 --force-with-lease）
$ git push --force-with-lease origin feature/login
```

**pull 详解**：

```bash
# 拉取并合并（默认行为）
$ git pull
# 等价于：
$ git fetch origin
$ git merge origin/当前分支

# 拉取并变基（保持线性历史，推荐）
$ git pull --rebase
# 等价于：
$ git fetch origin
$ git rebase origin/当前分支

# 设置当前分支默认用 rebase 拉取
$ git config pull.rebase true

# 全局设置 pull 默认用 rebase
$ git config --global pull.rebase true
```

**典型协作循环**：

```bash
# 早上开始工作：先同步远程
$ git switch main
$ git pull --rebase

# 创建功能分支开发
$ git switch -c feature/payment
# ...开发、提交...
$ git commit -m "feat: add payment"

# 推送到远程
$ git push -u origin feature/payment

# 同事在 main 上合并了其他 PR，远程 main 前进了
# 我的功能分支需要同步最新 main
$ git fetch origin
$ git rebase origin/main
# 解决可能的冲突后
$ git push --force-with-lease origin feature/payment

# PR 合并后删除本地和远程分支
$ git switch main
$ git pull --rebase
$ git branch -d feature/payment
$ git push origin --delete feature/payment
```

**处理非快进错误**：

```bash
$ git push
! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs

# 原因：远程有你没有的提交
# 解决：先拉取整合
$ git pull --rebase
$ git push
```

### 总结

- `git push` 上传本地提交，`git pull` 下载并整合远程提交。
- 首次推送用 `-u` 建立跟踪关系，后续推送/拉取无需参数。
- 推荐配置 `pull.rebase true`，让 pull 保持线性历史。
- 遇到非快进错误先 `pull` 整合，再 `push`，绝不盲目 `--force`。
- 强制推送用 `--force-with-lease`，它比 `--force` 安全得多。
- 协作循环：pull → 分支 → 开发 → push → PR → 合并 → 清理分支，养成习惯。

## 第 14 讲：Pull Request 协作流程

### 概念

**Pull Request（PR，GitLab 中称 Merge Request / MR）** 是一种基于 Git 的协作机制：开发者在自己的分支上完成改动后，发起一个「请求」，邀请项目维护者审查代码并合并到目标分支。PR 不仅是合并的工具，更是**代码评审（Code Review）** 的载体，是现代团队协作的核心环节。

PR 工作流通常包括：创建分支 → 提交改动 → 推送 → 发起 PR → 评审讨论 → 修改 → 合并 → 清理。

### 原理

PR 的本质是一个「提议」：它声明「我希望把 feature 分支的改动合并到 main 分支」。平台（GitHub、GitLab、Bitbucket）会自动计算两个分支的差异，展示改动内容，并提供评审界面。

PR 之所以重要，是因为它把「合并」从一个个人操作变成了一个**团队流程**：

1. **透明性**：所有改动在合并前都可见、可讨论、可追溯。
2. **质量保障**：通过代码评审发现 bug、改进设计、统一风格。
3. **知识共享**：评审过程让团队成员互相了解彼此的改动。
4. **自动化集成**：PR 可触发 CI/CD 流水线，自动运行测试、构建，只有通过的 PR 才能合并。
5. **权限控制**：保护分支规则可要求「必须 N 人评审通过」「CI 必须通过」才能合并。

Fork-based PR 是开源项目的标准模式：贡献者 fork 原仓库到自己的账户，在自己的 fork 上开发，然后向原仓库发起 PR。这种模式无需原仓库的写权限，降低了协作门槛。

### 例子

**内部团队 PR 流程**：

```bash
# 1. 同步主干
$ git switch main
$ git pull --rebase

# 2. 创建功能分支
$ git switch -c feature/user-profile

# 3. 开发并提交（多个小提交）
$ git add src/profile.py
$ git commit -m "feat: add profile model"
$ git add src/profile_api.py
$ git commit -m "feat: add profile API"
$ git add tests/test_profile.py
$ git commit -m "test: add profile tests"

# 4. 推送到远程
$ git push -u origin feature/user-profile

# 5. 在 GitHub 上发起 PR：feature/user-profile → main
#    填写标题、描述、关联 issue、指定评审人

# 6. 评审反馈后继续修改
$ git add src/profile.py
$ git commit -m "fix: address review comments"
$ git push
# PR 会自动更新

# 7. 合并后清理
$ git switch main
$ git pull --rebase
$ git branch -d feature/user-profile
$ git push origin --delete feature/user-profile
```

**Fork-based 开源贡献流程**：

```bash
# 1. 在 GitHub 上 fork 原仓库到 your/repo

# 2. 克隆自己的 fork
$ git clone git@github.com:you/repo.git
$ cd repo

# 3. 添加上游远程
$ git remote add upstream git@github.com:original/repo.git

# 4. 同步上游最新
$ git fetch upstream
$ git switch main
$ git rebase upstream/main

# 5. 创建功能分支
$ git switch -c fix/typo-in-readme

# 6. 开发、提交、推送到自己的 fork
$ git commit -m "docs: fix typo in README"
$ git push -u origin fix/typo-in-readme

# 7. 在 GitHub 上向 original/repo 发起 PR
```

**PR 描述模板**（推荐配置 `.github/PULL_REQUEST_TEMPLATE.md`）：

```markdown
## 改动说明
<!-- 这个 PR 做了什么？为什么？ -->

## 关联 Issue
Closes #123

## 改动类型
- [ ] 新功能
- [ ] Bug 修复
- [ ] 重构
- [ ] 文档

## 检查清单
- [ ] 代码通过本地测试
- [ ] 添加了必要的测试
- [ ] 更新了相关文档
- [ ] 提交信息符合规范
```

**保护分支规则建议**（在 GitHub 仓库设置中配置）：

- 要求 PR 合并前至少 1 人评审
- 要求 CI 状态检查通过
- 要求分支保持最新（合并前 rebase）
- 禁止直接 push 到 main
- 禁止强制推送

### 总结

- PR 是代码评审与合并的标准化流程，是团队协作的核心。
- PR 流程：分支 → 开发 → 推送 → 发起 PR → 评审 → 合并 → 清理。
- Fork-based PR 是开源贡献的标准模式，无需原仓库写权限。
- PR 描述要清晰说明「做什么、为什么、怎么做」，关联相关 issue。
- 配置保护分支规则，强制评审和 CI，保护主干质量。
- 评审文化：对事不对人，提建议而非批评，小 PR 优于大 PR。

# 第五章：进阶技巧

## 第 15 讲：暂存妙用 —— stash

### 概念

**`git stash`** 用于把当前工作区中未提交的改动「暂存」起来，让工作区恢复到干净状态（与 HEAD 一致）。暂存的改动可以在稍后随时恢复。stash 是处理「我正在 feature 分支上写到一半，突然需要切到 main 修个紧急 bug」这类场景的利器。

stash 与 commit 的区别在于：commit 是永久写入历史，stash 是临时存放在一个栈结构中，不进入分支历史。

### 原理

`git stash` 的工作机制是：它把工作区和暂存区的改动打包成一个「 stash 提交对象」（实际上是两个提交：一个对应暂存区状态，一个对应工作区状态），存放在 `.git/refs/stash` 引用中。stash 是一个**栈**结构，可以多次 stash，按 LIFO（后进先出）顺序恢复。

默认情况下，`git stash` 只暂存已跟踪文件的改动，不会处理未跟踪的新文件（因为 Git 不知道你是否想保留它们）。要同时暂存未跟踪文件，需用 `git stash -u`（`--include-untracked`）。

stash 的内容是独立的，不属于任何分支，因此你可以在任何分支上恢复它。但要注意：恢复 stash 时如果与当前工作区冲突，需要手动解决。

### 例子

**基本 stash 流程**：

```bash
# 正在 feature 分支开发，工作区有未提交改动
$ git status
On branch feature/payment
Changes not staged for commit:
  modified:   src/payment.py

# 突然要切到 main 修 bug
$ git stash
Saved working directory and index state WIP on feature/payment: a1b2c3d

# 工作区现在干净了
$ git status
nothing to commit, working tree clean

# 切到 main 修 bug
$ git switch main
$ git switch -c hotfix/urgent-bug
# ...修复、提交、合并...

# 回到 feature 分支，恢复 stash
$ git switch feature/payment
$ git stash pop
On branch feature/payment
Changes not staged for commit:
  modified:   src/payment.py
```

**stash 栈管理**：

```bash
# 查看所有 stash
$ git stash list
stash@{0}: WIP on feature: a1b2c3d
stash@{1}: WIP on main: e4f5g6h

# 查看某个 stash 的内容
$ git stash show stash@{0}
 src/payment.py | 2 +-

# 查看详细 diff
$ git stash show -p stash@{0}

# 恢复最近的 stash 并从栈中删除（最常用）
$ git stash pop

# 恢复最近的 stash 但保留在栈中
$ git stash apply

# 恢复指定 stash
$ git stash apply stash@{1}

# 删除某个 stash
$ git stash drop stash@{0}

# 清空所有 stash
$ git stash clear
```

**高级用法**：

```bash
# 暂存未跟踪文件
$ git stash -u

# 暂存所有文件（包括被 .gitignore 忽略的）
$ git stash -a

# 带提交信息暂存
$ git stash push -m "wip: payment integration"

# 只暂存已暂存的改动（保留未暂存改动在工作区）
$ git stash --keep-index

# 暂存单个文件
$ git stash push src/payment.py

# 暂存并立即创建分支（避免恢复时冲突）
$ git stash branch feature/payment-resume stash@{0}
```

### 总结

- stash 是临时存放未提交改动的栈，不进入分支历史。
- 默认不暂存未跟踪文件，用 `-u` 包含它们。
- `pop` 恢复并删除，`apply` 恢复但保留，按需选择。
- stash 跨分支可用，但恢复时可能冲突，需手动解决。
- 用 `stash branch` 在新分支上恢复 stash，避免冲突困扰。
- 常见误区：把 stash 当长期存储。stash 是临时的，重要改动应尽早 commit，哪怕先 commit 再 reset 也比 stash 安全。

## 第 16 讲：标签管理 —— tag

### 概念

**`git tag`** 用于给某个提交打上不可移动的标签，通常用于标记**发布版本**（如 `v1.0.0`、`v2.1.3`）。与分支不同，标签是固定指针——它指向一个特定提交，不会随新提交而移动。

Git 的标签分两种：
1. **轻量标签（Lightweight Tag）**：只是一个指向提交的引用，不包含额外信息。
2. **附注标签（Annotated Tag）**：一个完整的 Git 对象，包含标签名、说明信息、打标签者、时间戳，并经过校验和验证。

### 原理

轻量标签本质上就是一个文件，存放在 `.git/refs/tags/` 下，内容是某个提交的哈希。它不创建新对象，只是一个简单的指针。

附注标签则不同：Git 会创建一个「标签对象」（tag object），它包含目标提交的指针、标签信息、打标签者信息、时间戳，并用 GPG 签名（可选）。然后 `.git/refs/tags/v1.0.0` 指向这个标签对象，而非直接指向提交。附注标签因此可以被 GPG 签名验证，适合正式发布。

**推荐实践**：发布版本用附注标签，临时标记用轻量标签。附注标签携带的元信息（谁、何时、为什么）对追溯发布历史很有价值。

语义化版本（Semantic Versioning，SemVer）是版本号的事实标准：`MAJOR.MINOR.PATCH`，例如 `2.1.3`：
- MAJOR：不兼容的 API 变更
- MINOR：向后兼容的新功能
- PATCH：向后兼容的 bug 修复

### 例子

**创建标签**：

```bash
# 轻量标签
$ git tag v1.0.0

# 附注标签（推荐用于发布）
$ git tag -a v1.0.0 -m "Release 1.0.0: initial public release"

# 给历史提交打标签
$ git tag -a v0.9.0 -m "Beta release" a1b2c3d

# GPG 签名标签（高安全要求）
$ git tag -s v1.0.0 -m "Signed release"
```

**查看标签**：

```bash
# 列出所有标签
$ git tag
v0.9.0
v1.0.0
v1.1.0
v2.0.0

# 按模式过滤
$ git tag -l "v1.*"
v1.0.0
v1.1.0

# 查看标签详情（附注标签）
$ git show v1.0.0
tag v1.0.0
Tagger: Alice <alice@example.com>
Date:   Mon Jan 1 10:00:00 2024 +0800

Release 1.0.0: initial public release

commit a1b2c3d (tag: v1.0.0)
Author: Alice <alice@example.com>
...
```

**推送与删除标签**：

```bash
# 标签默认不随 git push 推送，需显式推送
$ git push origin v1.0.0

# 推送所有标签
$ git push origin --tags

# 删除本地标签
$ git tag -d v1.0.0

# 删除远程标签
$ git push origin --delete v1.0.0
```

**检出标签**（查看某个版本的代码）：

```bash
# 这会让 HEAD 处于「分离」状态
$ git switch v1.0.0
# 或
$ git checkout v1.0.0

# 如果想在这个版本上做修改，应创建分支
$ git switch -c bugfix/v1.0.0 v1.0.0
```

**自动化版本号**（结合 tag 与 describe）：

```bash
# git describe 生成基于最近 tag 的版本描述
$ git describe --tags
v1.2.0-3-ga1b2c3d
# 含义：距离 v1.2.0 有 3 个提交，当前提交哈希 a1b2c3d

# 常用于构建脚本中自动生成版本号
$ echo "VERSION = '$(git describe --tags --always)'" > version.py
```

### 总结

- 标签是固定指针，用于标记发布版本等关键节点。
- 发布用附注标签（`-a`），临时标记用轻量标签。
- 附注标签携带元信息，可 GPG 签名，适合正式发布。
- 遵循语义化版本（SemVer）：`MAJOR.MINOR.PATCH`。
- 标签默认不随 `git push` 推送，需显式 `git push origin --tags`。
- `git describe` 是基于 tag 自动生成版本号的利器，常用于 CI/CD。

## 第 17 讲：撤销操作 —— reset、revert、checkout

### 概念

撤销是 Git 中最容易让人困惑的部分，因为 Git 提供了多种「撤销」方式，每种作用于不同的层级。理解它们的关键是搞清楚「撤销什么」：

- **`git reset`**：移动分支指针，可同时影响暂存区和工作区。
- **`git revert`**：通过创建一个「反向提交」来撤销某次提交，不改写历史。
- **`git checkout` / `git restore`**：恢复工作区或暂存区的文件到某个状态。

### 原理

`git reset` 是最强大也最危险的撤销命令。它有一个核心参数 `--mode`，决定它影响哪些区域：

- `--soft`：只移动分支指针，暂存区和工作区不变。相当于「撤销 commit，但保留所有改动在暂存区」。
- `--mixed`（默认）：移动分支指针 + 重置暂存区，工作区不变。相当于「撤销 commit + 撤销 add，但工作区改动保留」。
- `--hard`：移动分支指针 + 重置暂存区 + 重置工作区。彻底丢弃所有改动，危险！

`git reset` 会**改写历史**——它把分支指针移到另一个提交，被跳过的提交会变成悬空提交（最终被垃圾回收）。因此 `git reset` 不能用于已推送的公共分支。

`git revert` 的思路完全不同：它不移动指针，而是创建一个**新提交**，这个新提交的内容是「指定提交的反向改动」。例如某次提交增加了 3 行，revert 会创建一个删除这 3 行的提交。因为只是新增提交，历史是线性追加的，不改写已有历史，因此**revert 是撤销已推送公共提交的安全方式**。

`git checkout <file>`（或新命令 `git restore <file>`）用于把工作区的文件恢复到暂存区的版本，丢弃工作区的改动。`git checkout HEAD <file>` 则恢复到 HEAD 的版本，同时丢弃暂存区和工作区的改动。

### 例子

**reset 的三种模式**：

```bash
# 场景：刚 commit 了，但想修改提交信息或重新组织
$ git reset --soft HEAD~1
# HEAD 回到上一个提交，但所有改动保留在暂存区

# 场景：commit 了，想撤销 commit 和 add，但保留工作区改动
$ git reset HEAD~1
# 等同于 git reset --mixed HEAD~1

# 场景：彻底丢弃最近一次提交的所有改动
$ git reset --hard HEAD~1
# 警告：这会丢失工作区中未提交的改动！

# 场景：把分支指针移到指定提交
$ git reset --hard a1b2c3d
```

**revert 撤销提交**：

```bash
# 撤销最近一次提交（创建反向提交）
$ git revert HEAD
[main 9z8y7x6] Revert "feat: add broken feature"
 1 file changed, 1 deletion(+)

# 撤销指定提交
$ git revert a1b2c3d

# 撤销一段连续提交
$ git revert a1b2c3d..e4f5g6h

# 撤销合并提交（需指定保留哪个父分支）
$ git revert -m 1 <merge-commit>

# 不自动提交，先看改动
$ git revert --no-commit HEAD
```

**恢复文件**：

```bash
# 丢弃工作区某文件的改动（恢复到暂存区版本）
$ git restore src/main.py
# 旧写法：git checkout -- src/main.py

# 丢弃工作区所有改动
$ git restore .

# 把文件恢复到 HEAD 的版本（同时丢弃暂存区和工作区改动）
$ git restore --source=HEAD --staged --worktree src/main.py
# 旧写法：git checkout HEAD -- src/main.py

# 把文件恢复到某个提交的版本
$ git restore --source=a1b2c3d src/main.py
```

**典型场景速查表**：

| 场景 | 命令 |
|------|------|
| 撤销未暂存的工作区改动 | `git restore <file>` |
| 撤销已暂存但未提交的改动 | `git restore --staged <file>` |
| 修改最近一次提交信息 | `git commit --amend` |
| 撤销最近一次提交（保留改动） | `git reset --soft HEAD~1` |
| 彻底丢弃最近一次提交 | `git reset --hard HEAD~1` |
| 撤销已推送的提交 | `git revert <commit>` |

### 总结

- `reset` 改写历史（移动分支指针），`revert` 追加反向提交（不改写历史）。
- `reset --hard` 是核武器，会永久丢弃工作区改动，慎用。
- 已推送的公共提交只能用 `revert` 撤销，绝不能用 `reset`。
- `git restore`（Git 2.23+）比 `git checkout` 语义更清晰，推荐使用。
- 撤销操作前先 `git status` 和 `git log` 确认状态，避免误操作。
- 兜底方案：即使 `reset --hard` 误删了提交，`git reflog` 也能找回（见第 18 讲）。

# 第六章：高级与实战

## 第 18 讲：历史重写 —— amend、rebase、reflog

### 概念

历史重写是 Git 的高级能力，指修改已经存在的提交历史。常用工具包括：

- **`git commit --amend`**：修改最近一次提交（内容或信息）。
- **`git rebase -i`**：交互式重写一段历史（合并、改写、删除、重排提交）。
- **`git reflog`**：记录 HEAD 的所有移动轨迹，是「撤销撤销」的救命稻草。

历史重写功能强大但需谨慎，因为它会改变提交哈希，已推送的历史重写可能影响他人。

### 原理

Git 的提交对象是不可变的——一旦创建，其内容（树、父提交、作者、信息）就固定了。所谓「重写历史」其实是**创建新的提交对象替换旧的**。例如 `git commit --amend` 实际上是：以当前暂存区为基础，创建一个新的提交对象，其父提交是原提交的父提交，然后把当前分支指针指向这个新提交。原提交变成悬空提交，但仍存在于 `.git/objects/` 中，直到被垃圾回收。

交互式 rebase 的原理类似：Git 把指定范围内的提交「摘下来」，按你的指令（pick、squash、reword 等）逐个重放到目标基底上。每个被重放的提交都会生成新的提交对象（即使内容相同，哈希也会变，因为父提交变了）。

`git reflog` 是 Git 的「黑匣子」。它记录 HEAD 和分支指针的每一次移动——包括 commit、checkout、reset、rebase、pull 等所有操作。reflog 存储在 `.git/logs/` 下，默认保留 90 天（可达提交）或 30 天（不可达提交）。这意味着即使你 `reset --hard` 误删了提交，只要在 reflog 保留期内，就能通过 reflog 找回。reflog 是本地的，不会被推送，是纯个人的「撤销历史」。

### 例子

**`git commit --amend` 修改最近提交**：

```bash
# 场景 1：忘了暂存某个文件，想加进最近一次提交
$ git add forgotten.txt
$ git commit --amend --no-edit
# --no-edit 保留原提交信息

# 场景 2：修改最近一次提交的信息
$ git commit --amend -m "feat: add login with JWT auth"

# 场景 3：修改最近一次提交的代码内容
$ vim src/login.py
$ git add src/login.py
$ git commit --amend --no-edit
```

**交互式 rebase 整理历史**：

```bash
# 修改最近 5 次提交
$ git rebase -i HEAD~5
```

编辑器打开：

```
pick a1b2c3d feat: add login
pick e4f5g6h fix: typo
pick i7j8k9l feat: add register
pick m0n1o2p docs: update
pick q3r4s5t chore: deps

# 改成：
pick a1b2c3d feat: add login
fixup e4f5g6h fix: typo          # 合并到上一个，丢弃信息
pick i7j8k9l feat: add register
reword m0n1o2p docs: update      # 保留但改信息
drop q3r4s5t chore: deps         # 删除
```

保存退出后，Git 会按指令重放提交。如果选择 `reword` 或 `edit`，会暂停让你编辑。

**rebase 中途修改提交（edit）**：

```
edit a1b2c3d feat: add login
```

```bash
# Git 暂停在 a1b2c3d
$ # 修改代码
$ git add src/login.py
$ git commit --amend --no-edit
$ git rebase --continue
```

**reflog 救命操作**：

```bash
# 查看 HEAD 的移动历史
$ git reflog
a1b2c3d HEAD@{0}: reset: moving to a1b2c3d
e4f5g6h HEAD@{1}: commit: feat: add payment
i7j8k9l HEAD@{2}: checkout: moving from main to feature

# 场景：误执行了 git reset --hard HEAD~3，丢了 3 个提交
$ git reset --hard HEAD~3

# 用 reflog 找回
$ git reflog
# 找到 reset 前的 HEAD 位置，假设是 e4f5g6h
$ git reset --hard e4f5g6h
# 提交全部回来了！
```

**reflog 的高级用法**：

```bash
# 查看某分支的 reflog
$ git reflog show feature/payment

# 查看所有引用的 reflog
$ git reflog --all

# reflog 中的相对引用
$ git reset --hard HEAD@{2}
```

**强制推送重写后的历史**：

```bash
# rebase 或 amend 后，本地历史与远程分叉，需强制推送
$ git push --force-with-lease origin feature/login
# 永远用 --force-with-lease 而非 --force
```

### 总结

- `--amend` 修改最近一次提交，本质是创建新提交替换旧提交。
- 交互式 rebase 是整理历史的瑞士军刀：squash、fixup、reword、edit、drop。
- reflog 记录 HEAD 的所有移动，是「撤销撤销」的救命稻草。
- 历史重写后需 `--force-with-lease` 推送，绝不用 `--force`。
- **铁律**：已推送的公共分支不要重写历史，否则会破坏他人工作。
- 经验：本地频繁整理历史（小提交 → squash 成语义清晰的提交），推送后视为「固化」不再重写。

## 第 19 讲：子模块与工作树 —— submodule、worktree

### 概念

随着项目复杂度增长，常会遇到两类需求：

1. **在一个仓库中引用另一个仓库**：例如项目依赖一个独立的通用库，希望以子目录形式嵌入。Git 提供 **`git submodule`** 解决此问题。
2. **同时在不同分支上工作**：例如正在 feature 分支开发，突然要修 main 上的紧急 bug，又不想 stash。Git 提供 **`git worktree`** 解决此问题。

这两个功能解决了「单仓库不够用」的场景，是高级 Git 用户的必备工具。

### 原理

**submodule** 的本质是「在父仓库的某个子目录中嵌入另一个 Git 仓库的特定提交」。父仓库并不存储子模块的文件内容，而是存储一个 `.gitmodules` 文件（记录子模块的 URL 和路径）和一个「gitlink」引用（指向子模块的某个提交哈希）。克隆父仓库时，子模块目录默认是空的，需要 `git submodule update --init` 才能拉取子模块的内容。

submodule 的优势是版本锁定——父仓库精确记录子模块用哪个版本，确保团队一致性。劣势是操作复杂，初学者常在子模块的更新、提交、推送上犯错。

**worktree** 的原理是：一个 Git 仓库可以拥有多个「工作树」，每个工作树是一个独立的工作目录，检出不同的分支。所有工作树共享同一个 `.git` 版本库（包括所有提交、分支、对象），但各自有独立的工作区和暂存区。这意味着你可以在 `~/project-main` 检出 main 分支，同时在 `~/project-feature` 检出 feature 分支，两者互不干扰，无需 stash 或 clone 多份。

worktree 相比 clone 多份的优势：节省磁盘空间（共享对象库）、分支状态全局一致（在一处创建的分支在另一处可见）、切换更快。

### 例子

**submodule 基本操作**：

```bash
# 添加子模块
$ git submodule add https://github.com/you/libutils.git libs/utils
Cloning into 'libs/utils'...
$ git status
Changes to be committed:
  new file:   .gitmodules
  new file:   libs/utils
$ git commit -m "chore: add libutils as submodule"

# 克隆含子模块的仓库
$ git clone https://github.com/you/project.git
$ cd project
$ git submodule update --init --recursive
# --recursive 处理嵌套子模块

# 一条命令克隆并初始化子模块
$ git clone --recurse-submodules https://github.com/you/project.git

# 更新子模块到远程最新
$ git submodule update --remote
$ git add libs/utils
$ git commit -m "chore: bump libutils"

# 在子模块中开发并推送
$ cd libs/utils
$ git switch -c feature/new-api
# ...开发、提交...
$ git push origin feature/new-api
```

**worktree 基本操作**：

```bash
# 创建一个新的工作树，检出 feature 分支
$ git worktree add ../project-feature feature/payment
Preparing worktree (checking out 'feature/payment')
HEAD is now at a1b2c3d feat: add payment

# 现在有两个工作目录：
# ~/project        → main 分支
# ~/project-feature → feature/payment 分支

# 列出所有工作树
$ git worktree list
/path/to/project          a1b2c3d [main]
/path/to/project-feature  e4f5g6h [feature/payment]

# 在新工作树中工作
$ cd ../project-feature
$ # 修改、提交，不影响 ~/project

# 删除工作树
$ git worktree remove ../project-feature

# 清理已删除目录但未注销的工作树
$ git worktree prune
```

**worktree 典型场景**：

```bash
# 场景：正在 feature 分支开发，突然要修紧急 bug
# 不用 stash，直接开一个 worktree
$ git worktree add ../hotfix main
$ cd ../hotfix
$ git switch -c hotfix/urgent
# ...修复、提交、合并...
$ cd ../project
$ git worktree remove ../hotfix
```

**submodule 常见陷阱**：

```bash
# 陷阱 1：忘记初始化子模块
$ git clone https://github.com/you/project.git
$ cd project
$ ls libs/utils  # 空的！
# 解决：
$ git submodule update --init

# 陷阱 2：子模块的改动在父仓库中是「脏」的
$ cd libs/utils
$ git switch main  # 切换了子模块分支
$ cd ../..
$ git status
# 显示子模块有改动
# 解决：要么提交子模块的新版本，要么 checkout 回原版本
```

### 总结

- submodule 用于在仓库中嵌入其他仓库，父仓库记录子模块的特定提交。
- submodule 操作复杂，更新需 `git submodule update --remote`，克隆需 `--recurse-submodules`。
- worktree 让一个仓库拥有多个工作目录，各自检出不同分支，共享对象库。
- worktree 适合「同时处理多个分支」场景，比 stash 或 clone 多份更优雅。
- submodule 适合「依赖独立维护的库」，worktree 适合「并行多分支工作」。
- 经验：submodule 学习成本高，若团队不熟悉，可考虑用包管理器（npm、pip、maven）替代。

## 第 20 讲：Git 最佳实践与团队协作规范

### 概念

掌握 Git 命令只是起点，真正高效地使用 Git 需要建立良好的**习惯**和**团队规范**。本讲总结贯穿全课程的实践经验，涵盖提交规范、分支策略、协作流程、性能优化、安全注意事项等方面，帮助你从「会用 Git」进阶到「用好 Git」。

### 原理

Git 最佳实践的核心原则可以归纳为五条：

1. **原子性提交**：每个提交只做一件事，像一个语义完整的逻辑单元。这使得回滚、cherry-pick、bisect 都更高效。
2. **提交信息即文档**：提交信息是未来读者（包括你自己）理解改动的重要线索，应清晰说明「为什么」。
3. **分支即上下文**：每个分支承载一个独立的开发上下文（一个功能、一个修复），生命周期短，命名清晰。
4. **历史即叙事**：整理好的历史像一篇可读的故事，而非一堆杂乱的流水账。本地频繁整理，推送后视为固化。
5. **协作即契约**：团队约定优于个人偏好，统一的规范让协作顺畅。

这些原则背后的理念是：**Git 历史是给人类读的，不只是给机器用的**。一个整洁、语义清晰的历史，是团队知识库的重要组成部分。

### 例子

**提交规范**：

```bash
# ❌ 坏的提交信息
$ git commit -m "fix"
$ git commit -m "update"
$ git commit -m "asdfasdf"
$ git commit -m "修改了登录逻辑增加了注册功能还修了一个bug"

# ✅ 好的提交信息（Conventional Commits）
$ git commit -m "feat(auth): add JWT-based login with refresh token"
$ git commit -m "fix(payment): handle null amount in refund logic"
$ git commit -m "refactor(user): extract profile validation to service"
```

**提交信息模板**（`~/.gitmessage`）：

```
# <type>(<scope>): <subject>
#
# <body: 解释为什么做这次改动，背景、动机、方案>
#
# <footer: 关联 issue、breaking change 等>
```

配置：

```bash
$ git config --global commit.template ~/.gitmessage
```

**.gitattributes 跨平台一致性**：

```gitattributes
# 统一换行符
* text=auto eol=lf
*.bat text eol=crlf
*.sh text eol=lf

# 二进制文件标记
*.png binary
*.jpg binary
*.pdf binary

# 语言特定的 diff 优化
*.py diff=python
*.md diff=markdown
```

**Git 钩子（hooks）自动化**：

```bash
# .git/hooks/pre-commit（或用 husky 管理）
#!/bin/sh
# 提交前运行 lint 和测试
npm run lint || exit 1
npm test || exit 1
```

**性能优化**：

```bash
# 启用并行垃圾回收
$ git config --global gc.auto 256
$ git config --global gc.autoPackLimit 50

# 启用文件系统监控（大仓库显著加速 status）
$ git config --global core.fsmonitor true
$ git config --global core.untrackedcache true

# 浅克隆大仓库
$ git clone --depth 1 https://github.com/torvalds/linux.git

# 部分克隆（只拉取需要的对象）
$ git clone --filter=blob:none https://github.com/torvalds/linux.git

# 定期清理
$ git gc --prune=now
$ git prune
```

**安全实践**：

```bash
# 1. 用 SSH 而非 HTTPS（更安全、免密）
$ git remote set-url origin git@github.com:you/repo.git

# 2. 签名提交（证明身份）
$ git config --global commit.gpgsign true
$ git config --global gpg.program gpg

# 3. 永远不提交敏感信息
# .gitignore 中加入：
.env
*.key
*.pem
secrets/

# 4. 误提交了敏感信息，立即处理
$ git rm --cached .env
$ echo ".env" >> .gitignore
$ git commit -m "chore: remove sensitive file"
# 注意：历史中仍有该文件，需用 git filter-repo 彻底清除
$ pip install git-filter-repo
$ git filter-repo --invert-paths --path .env
$ git push --force-with-lease
# 并立即轮换泄露的密钥！
```

**团队协作检查清单**：

```
□ 仓库有清晰的 README 和 CONTRIBUTING.md
□ 配置了 .gitignore 和 .gitattributes
□ 主分支受保护，禁止直接 push
□ PR 必须经过至少 1 人评审
□ PR 必须通过 CI 测试
□ 提交信息遵循 Conventional Commits
□ 分支命名有统一约定
□ 定期清理已合并的分支
□ 敏感信息不入库，使用环境变量或密钥管理服务
□ 重要发布打附注标签
```

**排查问题的利器**：

```bash
# git bisect：二分查找引入 bug 的提交
$ git bisect start
$ git bisect bad          # 当前版本有 bug
$ git bisect good v1.0.0  # v1.0.0 没问题
# Git 自动 checkout 中间提交，你测试后标记
$ git bisect good  # 或 git bisect bad
# 重复直到定位到引入 bug 的提交
$ git bisect reset

# git blame：查看每行代码的最后修改者
$ git blame src/main.py

# git log -S：查找引入/删除某字符串的提交
$ git log -S "deprecated_function" --oneline

# git log -G：用正则搜索 diff 内容
$ git log -G "TODO.*fixme" -i
```

### 总结

- 五大原则：原子提交、信息即文档、分支即上下文、历史即叙事、协作即契约。
- 遵循 Conventional Commits 规范，提交信息写「为什么」而非「做了什么」。
- 配置 `.gitattributes` 保证跨平台一致性，用 hooks 自动化质量检查。
- 大仓库用 fsmonitor、浅克隆、部分克隆优化性能。
- 安全实践：SSH、签名提交、敏感信息不入库、误泄露立即轮换密钥。
- `git bisect` 是定位回归 bug 的神器，`git blame` 追溯代码责任，`git log -S` 搜索改动历史。
- Git 是工具，规范是文化：工具再好，也需要团队共同遵守约定才能发挥价值。
