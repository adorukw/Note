# 第 1 章 Docker 入门基础

本章是整个课程的起点。我们将从最根本的问题出发——"为什么需要 Docker"，逐步建立对容器技术的整体认知。本章不涉及复杂的操作，而是帮助您打牢概念基础，理解 Docker 在现代软件交付链中的定位与价值。

## 第 1 讲：什么是 Docker —— 容器与虚拟机的本质区别

### 概念

**Docker** 是一个开源的容器化平台，它允许开发者将应用及其所有依赖（代码、运行时、系统库、配置文件）打包到一个标准化的、可移植的容器中，从而保证应用在任何环境中都能一致地运行。

Docker 于 2013 年由 dotCloud 公司（后更名为 Docker Inc.）开源，它基于 Linux 内核的 cgroup 和 namespace 等特性实现轻量级隔离。与传统的虚拟机不同，Docker 容器不需要额外的操作系统内核，而是直接共享宿主机的内核，因此启动速度极快、资源占用极低。

一句话定义：**Docker 是一种"打包一次，到处运行"的应用交付工具，它用容器替代了笨重的虚拟机。**

### 原理

要理解 Docker 的原理，必须先理解**容器与虚拟机的本质区别**。

**虚拟机（Virtual Machine, VM）** 通过 Hypervisor（如 VMware、VirtualBox、KVM）在物理硬件之上虚拟出完整的硬件栈，每个虚拟机都包含一个完整的客户操作系统（Guest OS）。这意味着如果你在一台物理机上运行 5 个虚拟机，就会有 5 套完整的操作系统在同时运行，每个都占用数 GB 的内存和磁盘空间。虚拟机的启动时间通常在分钟级别，因为它需要完整地引导一个操作系统。

**容器（Container）** 则完全不同。容器直接运行在宿主机的内核之上，所有容器共享同一个内核，但通过 Linux 内核提供的 **namespace**（命名空间）实现进程、网络、文件系统等的隔离，通过 **cgroup**（控制组）实现 CPU、内存等资源的限制。容器内没有独立的内核，只包含应用运行所需的最小化用户空间文件。因此容器的启动时间通常在秒级甚至毫秒级，资源开销极小。

底层关键技术包括：

1. **Namespaces**：提供隔离能力。PID namespace 让容器内进程看不到宿主机进程；NET namespace 提供独立的网络栈；MNT namespace 提供独立的文件系统视图；UTS namespace 提供独立的主机名；IPC namespace 隔离进程间通信；USER namespace 提供用户 ID 映射。
2. **Cgroups**：提供资源限制能力。可以限制容器使用的 CPU 时间片、内存上限、磁盘 I/O 带宽等。
3. **UnionFS（联合文件系统）**：实现镜像的分层存储，让多个镜像层可以叠加成一个完整的文件系统视图。

### 例子

下面通过一个直观的对比来感受虚拟机与容器的差异。

**架构对比示意图：**

```
┌─────────────────────────────────┐    ┌─────────────────────────────────┐
│         虚拟机架构               │    │         容器架构                 │
├─────────────────────────────────┤    ├─────────────────────────────────┤
│  App A  │  App B  │  App C      │    │  App A  │  App B  │  App C      │
│ Bins/Lib│ Bins/Lib│ Bins/Lib    │    │ Bins/Lib│ Bins/Lib│ Bins/Lib    │
├─────────┼─────────┼─────────────┤    ├─────────┴─────────┴─────────────┤
│ Guest OS│ Guest OS│ Guest OS    │    │          Docker Engine           │
├─────────┴─────────┴─────────────┤    ├─────────────────────────────────┤
│         Hypervisor              │    │          Host OS (Kernel)        │
├─────────────────────────────────┤    ├─────────────────────────────────┤
│         Host OS                 │    │          Infrastructure          │
├─────────────────────────────────┤    └─────────────────────────────────┤
│       Infrastructure            │
└─────────────────────────────────┘
```

**资源占用对比（运行一个 Nginx 服务）：**

| 指标 | 虚拟机 | Docker 容器 |
|------|--------|-------------|
| 启动时间 | 30-60 秒 | 0.5-2 秒 |
| 内存占用 | 512MB-2GB | 10-50MB |
| 磁盘占用 | 1-5GB | 100-200MB |
| 并发密度 | 单机 10-20 个 | 单机 100-1000 个 |

**实际命令体验：**

```bash

docker run -d -p 8080:80 nginx:alpine

# 查看容器资源占用
docker stats
```

执行 `docker stats` 后你会看到类似输出：

```
CONTAINER ID   NAME        CPU %   MEM USAGE / LIMIT   MEM %   NET I/O
a1b2c3d4e5f6   nginx-web   0.05%   5.2MiB / 8GiB       0.06%   1.2kB/0B
```

可以看到一个 Nginx 容器仅占用约 5MB 内存，而同等功能的虚拟机至少需要 512MB。

### 总结

本讲核心要点：

1. **Docker 是应用交付工具**，不是虚拟机的替代品，而是更轻量的隔离方案。
2. **虚拟机隔离强但重**，每个 VM 包含完整 Guest OS；**容器隔离轻但快**，共享宿主内核。
3. **容器三大底层技术**：Namespaces（隔离）、Cgroups（限制）、UnionFS（分层存储）。
4. **容器优势**：启动快、占用小、密度高、可移植性强。

**常见注意事项**：
- 容器共享内核意味着如果宿主内核有漏洞，所有容器都可能受影响，因此生产环境要及时更新内核。
- 容器并非"万能隔离"，对于强安全隔离场景（如多租户公有云），仍需结合虚拟机使用。
- Windows 容器与 Linux 容器不互通，跨平台时需注意镜像兼容性。

## 第 2 讲：Docker 的核心概念 —— 镜像、容器、仓库

### 概念

Docker 的整个技术体系围绕三个核心概念展开，理解它们之间的关系是掌握 Docker 的前提：

1. **镜像（Image）**：镜像是容器的只读模板，包含了应用运行所需的所有内容——代码、运行时、库、环境变量、配置文件。可以把镜像理解为"面向对象编程中的类（Class）"，它是静态的、不可变的。
2. **容器（Container）**：容器是镜像运行时的实例，相当于"面向对象编程中的对象（Object）"。同一个镜像可以同时启动多个容器实例，它们彼此独立。容器在镜像之上增加了一个可写层（Writable Layer），所有运行时的修改都发生在这个层。
3. **仓库（Registry）**：仓库是存储和分发镜像的服务。Docker Hub 是最大的公共仓库（hub.docker.com），企业也可以搭建私有仓库（如 Harbor）。仓库中每个镜像通过 `仓库名:标签` 唯一标识，例如 `nginx:1.25`。

### 原理

**镜像的分层结构**是 Docker 最精妙的设计之一。一个镜像并非一个完整的文件，而是由多个只读层（Layer）叠加而成。每一层对应 Dockerfile 中的一条指令（如 `RUN`、`COPY`、`ADD`）。这种分层设计带来三个关键好处：

1. **复用与共享**：多个镜像可以共享相同的底层。例如所有基于 `ubuntu:22.04` 的镜像都共享 Ubuntu 的基础层，本地只需存储一份。
2. **增量传输**：拉取镜像时只下载本地缺失的层，大幅减少网络传输量。
3. **构建缓存**：修改 Dockerfile 时，未变化的层会命中缓存，无需重新构建，加速迭代。

**容器与镜像的关系**：当通过 `docker run` 启动容器时，Docker 在镜像的只读层之上添加一个可写层（称为 Container Layer）。容器内所有文件修改（新建、修改、删除）都写入这个可写层，而镜像本身保持不变。容器删除后，可写层随之消失，这就是容器"用完即弃"特性的来源。这种机制称为 **Copy-on-Write（写时复制）**：只有当文件被修改时，才从镜像层复制到可写层。

**仓库的寻址机制**：镜像的完整名称格式为 `[registry地址/]仓库名[:标签]`。例如：
- `nginx:1.25` → 默认从 Docker Hub 拉取官方 nginx 仓库的 1.25 标签
- `registry.example.com/myapp:v2` → 从私有仓库 registry.example.com 拉取 myapp 仓库的 v2 标签
- 不指定标签时默认使用 `latest`，但生产环境强烈建议显式指定版本号

### 例子

**镜像、容器、仓库的关系图：**

```

│                    Docker Registry                       │
│                  (Docker Hub / Harbor)                   │
│                                                          │
│    ┌──────────┐  ┌──────────┐  ┌──────────┐             │
│    │ nginx    │  │ redis    │  │ myapp    │             │
│    │ :1.25    │  │ :7.0     │  │ :v2      │             │
│    └────┬─────┘  └──────────┘  └──────────┘             │
└─────────┼────────────────────────────────────────────────┘
          │ docker pull (拉取镜像)
          ▼
┌──────────────────────────────────────────────────────────┐
│                    本地镜像存储                           │
│                                                          │

│    │  Layer 4: CMD ["nginx"]          │ ← 只读层          │
│    │  Layer 3: COPY index.html        │ ← 只读层          │
│    │  Layer 2: RUN apt install nginx  │ ← 只读层          │
│    │  Layer 1: ubuntu:22.04 base      │ ← 只读层          │
│    └──────────────────────────────────┘                  │
└─────────┬────────────────────────────────────────────────┘

          ▼
┌──────────────────────────────────────────────────────────┐
│                    运行中的容器                           │
│                                                          │
│    ┌──────────────────────────────────┐                  │
│    │  Writable Layer (可写层)         │ ← 容器独有        │

│    └──────────────────────────────────┘                  │
└──────────────────────────────────────────────────────────┘
```

**实际操作演示：**

```bash
# 1. 从仓库拉取镜像

# 2. 查看本地镜像

# 输出：
# REPOSITORY   TAG           IMAGE ID       CREATED        SIZE
# nginx        1.25-alpine   1c9d3f2e8a5b   2 weeks ago    43.2MB

# 3. 查看镜像的分层结构
docker history nginx:1.25-alpine
# 输出：
# IMAGE          CREATED       CREATED BY                                      SIZE
# 1c9d3f2e8a5b   2 weeks ago   /bin/sh -c #(nop)  CMD ["nginx" "-g" "daemon…   0B
# 7a8b9c1d2e3f   2 weeks ago   /bin/sh -c #(nop)  STOPSIGNAL SIGQUIT           0B
# 5e6f7a8b9c1d   2 weeks ago   /bin/sh -c set -x     && addgroup -g 101 ...    2.1MB
# ...

# 4. 基于镜像启动容器

# 输出：

# 6. 基于同一镜像再启动一个容器（共享镜像层，独立可写层）
docker run -d --name my-nginx-2 nginx:1.25-alpine
```

### 总结

本讲核心要点：

1. **三大核心概念**：镜像（模板/类）、容器（实例/对象）、仓库（存储分发）。
2. **镜像是分层的**，每层对应一条 Dockerfile 指令，分层带来复用、增量传输、构建缓存三大优势。
3. **容器 = 镜像 + 可写层**，采用 Copy-on-Write 机制，容器删除后修改丢失。
4. **仓库寻址格式**：`[registry/]repository[:tag]`，生产环境务必显式指定 tag。

**常见注意事项**：
- 不要混淆"镜像"和"容器"：镜像是静态文件，容器是运行进程。
- 容器内修改不会持久化到镜像，需要持久化的数据必须通过 Volume 挂载（第 10 讲详解）。
- `latest` 标签不一定是最新版本，它只是一个普通标签名，生产环境禁用 `latest`。

## 第 3 讲：Docker 的安装与环境配置

### 概念

Docker 的安装看似简单，但生产环境的配置却有不少讲究。本讲介绍 Docker Engine 在 Linux、Windows、macOS 上的安装方法，以及安装后的关键配置项（镜像加速、存储驱动、日志配置等）。

**Docker Engine** 是 Docker 的核心运行时，包含三个组件：
- **dockerd**：守护进程，负责管理镜像、容器、网络、卷。
- **REST API**：供外部程序与 dockerd 通信的接口。
- **docker CLI**：命令行客户端，通过 REST API 操作 dockerd。

### 原理

不同平台的 Docker 架构略有差异：

**Linux 平台**：Docker 原生运行，直接使用 Linux 内核的 namespace 和 cgroup。这是性能最优、最稳定的方式，也是生产环境的首选。

**Windows / macOS 平台**：由于 Docker 依赖 Linux 内核特性，在这两个平台上 Docker Desktop 会启动一个轻量级 Linux 虚拟机（Windows 上使用 WSL2 或 Hyper-V，macOS 上使用 HyperKit），然后在虚拟机内运行 Docker Engine。这意味着 Windows/macOS 上的容器实际上是运行在 Linux 虚拟机中的，存在一层额外的性能开销。

**镜像加速原理**：默认从 Docker Hub 拉取镜像时，请求会经过国际网络，国内访问速度慢且不稳定。配置镜像加速器（Registry Mirror）后，dockerd 会优先从加速器地址拉取，加速器作为透明代理缓存并转发请求，大幅提升拉取速度。

### 例子

**1. Ubuntu 22.04 安装 Docker（生产推荐方式）：**

```bash
# 卸载旧版本
sudo apt remove docker docker-engine docker.io containerd runc

# 安装依赖
sudo apt update
sudo apt install -y ca-certificates curl gnupg lsb-release

# 添加 Docker 官方 GPG 密钥
sudo mkdir -p /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | \
  sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg

# 添加 Docker 软件源
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# 安装 Docker Engine
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# 验证安装
sudo docker run hello-world
```

**2. 配置镜像加速器（国内必备）：**

```bash
# 编辑 Docker 配置文件
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json <<EOF
{
  "registry-mirrors": [
    "https://docker.mirrors.ustc.edu.cn",
    "https://hub-mirror.c.163.com"
  ],
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "100m",
    "max-file": "3"
  },
  "default-address-pools": [
    {"base": "172.17.0.0/16", "size": 24}
  ]
}
EOF

# 重启 Docker 使配置生效
sudo systemctl daemon-reload
sudo systemctl restart docker
```

**3. 将当前用户加入 docker 组（免 sudo）：**

```bash
sudo usermod -aG docker $USER
# 需要注销重新登录后生效
newgrp docker
```

**4. 验证安装与配置：**

```bash
# 查看 Docker 版本
docker version

# 查看 Docker 系统信息（含镜像加速器配置）
docker info

# 运行测试容器
docker run hello-world
```

**5. Windows / macOS 安装**：直接下载 [Docker Desktop](https://www.docker.com/products/docker-desktop/) 安装包，双击安装即可。Windows 需启用 WSL2 功能。

### 总结

本讲核心要点：

1. **Docker Engine 三组件**：dockerd（守护进程）、REST API、docker CLI。
2. **Linux 原生运行**性能最优，Windows/macOS 通过 Linux 虚拟机运行。
3. **国内必须配置镜像加速器**，否则拉取镜像极慢。
4. **生产环境配置要点**：日志轮转（防止日志撑爆磁盘）、存储驱动选择、网络地址池规划。

**常见注意事项**：
- 切勿在生产环境使用 Docker Desktop，它仅适用于开发测试。
- `daemon.json` 配置错误会导致 dockerd 启动失败，修改后用 `sudo dockerd --validate` 检查语法。
- 日志配置 `max-size` + `max-file` 是生产必备，否则容器日志会无限增长占满磁盘。
- 将用户加入 docker 组等同于赋予 root 权限，多用户服务器需谨慎。

## 第 4 讲：第一个容器 —— Hello Docker

### 概念

本讲通过运行第一个真实容器，建立对 Docker 工作流的直观感受。我们将启动一个 Nginx Web 服务器容器，并通过浏览器访问它，体验"拉取镜像 → 启动容器 → 访问服务 → 停止删除"的完整生命周期。

**Docker 的基本工作流**可以概括为五步：
1. **拉取镜像**（`docker pull`）：从仓库下载镜像到本地。
2. **运行容器**（`docker run`）：基于镜像创建并启动容器。
3. **管理容器**（`docker ps` / `docker logs` / `docker exec`）：查看状态、日志、进入容器。
4. **停止容器**（`docker stop`）：优雅停止容器。
5. **删除容器**（`docker rm`）：清理容器资源。

### 原理

`docker run` 命令是 Docker 最核心的命令，它内部执行了一系列操作：

1. **检查本地镜像**：如果本地不存在指定镜像，则从配置的仓库拉取。
2. **创建容器**：基于镜像创建一个容器实例，分配可写层。
3. **分配网络**：为容器分配 IP 地址，并将容器的端口映射到宿主机（如果指定了 `-p`）。
4. **挂载文件系统**：将镜像的只读层与可写层联合挂载为容器的根文件系统。
5. **启动进程**：执行镜像中 `CMD` 或 `ENTRYPOINT` 指定的命令。

**端口映射原理**：容器拥有独立的网络命名空间，其 IP 地址（如 172.17.0.2）在宿主机外部无法直接访问。`-p 8080:80` 参数告诉 Docker 在宿主机的 8080 端口上监听，并将流量通过 NAT（网络地址转换）转发到容器内的 80 端口。这是通过 iptables 规则和 docker-proxy 进程共同实现的。

**后台运行原理**：`-d` 参数让容器在后台运行（detached mode），容器的标准输出会被 Docker 日志驱动收集，可通过 `docker logs` 查看。如果不加 `-d`，容器会占用当前终端，按 Ctrl+C 会发送 SIGINT 信号停止容器。

### 例子

**完整体验流程：**

```bash
# 步骤 1：拉取 Nginx Alpine 版本（体积小，约 43MB）
docker pull nginx:alpine

# 步骤 2：启动容器，命名为 web，映射端口 8080->80
docker run -d --name web -p 8080:80 nginx:alpine
# 输出容器 ID：a1b2c3d4e5f6...

# 步骤 3：查看运行中的容器
docker ps
# CONTAINER ID   IMAGE          STATUS         PORTS                  NAMES
# a1b2c3d4e5f6   nginx:alpine   Up 10 seconds  0.0.0.0:8080->80/tcp   web

# 步骤 4：测试访问
curl http://localhost:8080
# 输出 Nginx 欢迎页 HTML

# 步骤 5：查看容器日志
docker logs web
# 输出 Nginx 访问日志

# 步骤 6：实时跟踪日志（类似 tail -f）
docker logs -f web

# 步骤 7：进入容器内部查看
docker exec -it web sh
# 在容器内执行：
ls /usr/share/nginx/html    # 查看 Nginx 静态文件目录
cat /etc/nginx/nginx.conf   # 查看 Nginx 配置
exit                        # 退出容器

# 步骤 8：查看容器详细信息（IP、挂载、资源限制等）
docker inspect web

# 步骤 9：查看容器资源占用
docker stats web

# 步骤 10：停止容器
docker stop web

# 步骤 11：启动已停止的容器
docker start web

# 步骤 12：删除容器（必须先停止）
docker stop web
docker rm web

# 步骤 13：删除镜像
docker rmi nginx:alpine
```

**常用命令速查表：**

| 命令 | 作用 | 示例 |
|------|------|------|
| `docker pull` | 拉取镜像 | `docker pull nginx:alpine` |
| `docker run` | 创建并启动容器 | `docker run -d --name web -p 8080:80 nginx:alpine` |
| `docker ps` | 查看运行中容器 | `docker ps -a`（含已停止） |
| `docker logs` | 查看容器日志 | `docker logs -f --tail 100 web` |
| `docker exec` | 进入容器执行命令 | `docker exec -it web sh` |
| `docker stop` | 停止容器 | `docker stop web` |
| `docker rm` | 删除容器 | `docker rm -f web`（强制删除运行中） |
| `docker rmi` | 删除镜像 | `docker rmi nginx:alpine` |
| `docker inspect` | 查看容器详情 | `docker inspect web` |
| `docker stats` | 查看资源占用 | `docker stats` |

### 总结

本讲核心要点：

1. **Docker 工作流五步**：pull → run → manage → stop → rm。
2. **`docker run` 内部流程**：检查镜像 → 创建容器 → 分配网络 → 挂载文件系统 → 启动进程。
3. **端口映射 `-p`**：通过 NAT + docker-proxy 实现宿主机到容器的端口转发。
4. **`-d` 后台运行**：日志由 Docker 收集，用 `docker logs` 查看。

**常见注意事项**：
- `docker run` 每次都会创建新容器，重复运行同名容器会报错，需先 `docker rm`。
- 端口冲突时（`port is already allocated`），说明宿主机端口被占用，换一个端口或停掉占用进程。
- `docker exec` 与 `docker attach` 不同：exec 是新开一个进程进入容器，attach 是连接到容器主进程，Ctrl+C 会停止容器。
- 容器停止后数据仍在可写层，只有 `docker rm` 才会彻底删除。

# 第 2 章 镜像管理

镜像（Image）是 Docker 的基石——所有容器都从镜像创建。本章将系统讲解镜像的获取、查看、删除等基础操作，重点深入 Dockerfile 的编写，这是构建自定义镜像的核心技能。掌握本章后，您将能够为任何应用编写高质量的 Dockerfile，并理解镜像分层原理以优化构建过程。

## 第 5 讲：镜像的基础操作 —— 拉取、查看、删除

### 概念

本讲聚焦镜像的日常管理操作。Docker 镜像管理命令遵循 `docker image <子命令>` 的规范格式，同时也提供了简写形式（如 `docker pull` 等价于 `docker image pull`）。掌握这些命令是后续学习 Dockerfile 构建的基础。

镜像管理涉及的核心操作包括：
- **拉取（pull）**：从远程仓库下载镜像到本地。
- **查看（ls / images）**：列出本地所有镜像。
- **详情（inspect）**：查看镜像的元数据。
- **历史（history）**：查看镜像的构建层历史。
- **删除（rmi）**：删除本地镜像。
- **清理（prune）**：批量清理悬空镜像。
- **标签（tag）**：为镜像打标签。
- **保存/加载（save / load）**：将镜像导出为文件或从文件导入。

### 原理

**镜像的存储结构**：Docker 镜像在本地存储时，由两部分组成——**清单（Manifest）** 和 **层（Layers）**。清单是一个 JSON 文件，描述镜像包含哪些层、每层的摘要（digest）、配置信息等。层是实际的文件内容，以 tar 包形式存储，通过 SHA256 摘要唯一标识。

**镜像标识方式**有三种：
1. **镜像名 + 标签**：`nginx:1.25`，最常用但可能重复。
2. **镜像 ID**：`1c9d3f2e8a5b`，本地唯一，是配置 JSON 的 SHA256 前 12 位。
3. **摘要（Digest）**：`nginx@sha256:abc123...`，全局唯一且不可变，生产环境推荐使用。

**删除镜像的限制**：如果一个镜像有对应的容器存在（无论运行还是停止），直接删除会报错 `image is being used by stopped container`。必须先删除所有依赖该镜像的容器，才能删除镜像。这是为了防止误删导致容器无法重启。

**悬空镜像（Dangling Image）**：当重新构建同名同标签镜像时，旧镜像的标签会被新镜像"抢走"，旧镜像变成没有标签的悬空镜像（显示为 `<none>:<none>`）。这些镜像占用磁盘但无实际用途，应定期清理。

### 例子

**1. 拉取镜像：**

```bash
# 拉取官方镜像（默认 latest 标签，不推荐）
docker pull nginx

# 拉取指定版本（推荐）
docker pull nginx:1.25-alpine

# 拉取指定平台（如 ARM 架构）
docker pull --platform linux/arm64 nginx:1.25-alpine

# 通过摘要拉取（最精确，保证内容不变）
docker pull nginx@sha256:6af79ae5de407283dcea8b00d5c37ac42b9c6b3d7c0de7c47b2c2b5d8c2d7a1f

# 拉取私有仓库镜像
docker pull registry.example.com:5000/myapp:v2
```

**2. 查看本地镜像：**

```bash
# 列出所有本地镜像
docker images
# REPOSITORY   TAG           IMAGE ID       CREATED        SIZE
# nginx        1.25-alpine   1c9d3f2e8a5b   2 weeks ago    43.2MB
# redis        7-alpine      3a4b5c6d7e8f   3 weeks ago    29.5MB
# hello-world  latest        9c7a54b2c1d3   2 months ago   13.3KB

# 过滤显示悬空镜像
docker images -f dangling=true

# 只显示镜像 ID
docker images -q

# 按仓库名过滤
docker images nginx

# 显示完整摘要
docker images --digests
```

**3. 查看镜像详情与历史：**

```bash
# 查看镜像元数据（JSON 格式，含架构、配置、层信息）
docker inspect nginx:1.25-alpine

# 只查看特定字段
docker inspect -f '{{.Architecture}}' nginx:1.25-alpine
# 输出：amd64

# 查看镜像构建历史（每一层）
docker history nginx:1.25-alpine
# IMAGE          CREATED       CREATED BY                                      SIZE
# 1c9d3f2e8a5b   2 weeks ago   /bin/sh -c #(nop)  CMD ["nginx" "-g" "daemon…   0B
# 7a8b9c1d2e3f   2 weeks ago   /bin/sh -c #(nop)  STOPSIGNAL SIGQUIT           0B
# 5e6f7a8b9c1d   2 weeks ago   /bin/sh -c set -x && addgroup -g 101 ...        2.1MB
# ...
```

**4. 为镜像打标签：**

```bash
# 为本地镜像打新标签（常用于推送到私有仓库前）
docker tag nginx:1.25-alpine myregistry.com/nginx:1.25

# 同一镜像可以有多个标签
docker tag nginx:1.25-alpine nginx:stable
```

**5. 删除镜像：**

```bash
# 通过镜像名删除
docker rmi nginx:1.25-alpine

# 通过镜像 ID 删除
docker rmi 1c9d3f2e8a5b

# 强制删除（即使有容器依赖，慎用）
docker rmi -f nginx:1.25-alpine

# 批量删除所有镜像（危险操作）
docker rmi $(docker images -q)
```

**6. 清理悬空镜像与导出导入：**

```bash
# 清理悬空镜像（无标签的中间层镜像）
docker image prune

# 清理所有未使用的镜像（更激进）
docker image prune -a

# 导出镜像为 tar 文件（离线传输用）
docker save -o nginx.tar nginx:1.25-alpine

# 从 tar 文件加载镜像
docker load -i nginx.tar
```

### 总结

本讲核心要点：

1. **镜像三种标识**：`name:tag`（常用）、`image id`（本地唯一）、`digest`（全局唯一，生产推荐）。
2. **删除镜像前必须先删容器**，否则报错；`-f` 强制删除有风险。
3. **悬空镜像**是重新构建产生的无标签旧镜像，应定期 `prune` 清理。
4. **save/load** 用于离线传输，**pull/push** 用于在线分发。

**常见注意事项**：
- 生产环境禁用 `latest` 标签，应固定具体版本号或使用 digest。
- `docker image prune -a` 会删除所有未被容器使用的镜像，执行前确认。
- 导出镜像用 `save`（保留分层），导出容器文件系统用 `export`（扁平化），两者不可混用。
- 镜像 ID 前 12 位即可唯一标识，但完整 ID 是 64 位 SHA256。

## 第 6 讲：Dockerfile 入门 —— 构建自定义镜像

### 概念

**Dockerfile** 是一个纯文本文件，包含一系列指令（Instruction），每条指令描述如何构建镜像的一层。通过 `docker build` 命令读取 Dockerfile，Docker 会逐条执行指令，最终生成一个镜像。Dockerfile 是"基础设施即代码"（Infrastructure as Code）理念在容器领域的体现——镜像的构建过程可版本控制、可复现、可审计。

一个最简单的 Dockerfile 示例：

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY . /app
RUN pip install flask
EXPOSE 5000
CMD ["python", "app.py"]
```

这 6 行代码就构建出了一个完整的 Flask Web 应用镜像。Dockerfile 的强大之处在于：用极简的声明式语法描述了从基础环境到应用部署的全过程。

### 原理

**Dockerfile 构建过程**：执行 `docker build` 时，Docker 会做以下事情：

1. **读取 Dockerfile**，解析每条指令。
2. **逐条执行指令**，每条指令生成一个新的镜像层（Layer）。
3. **构建缓存机制**：对于每条指令，Docker 会检查是否已有相同指令的缓存层。如果指令和上下文未变化，直接复用缓存层，跳过实际执行。这是 Dockerfile 构建速度快的核心原因。
4. **生成最终镜像**：所有层叠加后，生成最终镜像并打上标签。

**构建上下文（Build Context）**：`docker build` 命令的最后一个参数是构建上下文路径（通常是 `.`）。Docker 会将该路径下的所有文件打包发送给 dockerd，Dockerfile 中的 `COPY`、`ADD` 指令只能访问上下文中的文件。这就是为什么要用 `.dockerignore` 排除不需要的文件——否则会拖慢构建并增大上下文体积。

**指令执行顺序与分层**：Dockerfile 中每条 `RUN`、`COPY`、`ADD` 指令都会创建一个新层。其他指令（如 `FROM`、`ENV`、`WORKDIR`、`EXPOSE`、`CMD`）只修改镜像的配置元数据，不产生新层（或产生空层）。因此优化 Dockerfile 的核心是减少 `RUN`、`COPY`、`ADD` 的次数。

### 例子

**实战：构建一个 Python Flask 应用镜像**

项目结构：
```
myflask/
├── app.py
├── requirements.txt
└── Dockerfile
```

`app.py`：
```python
from flask import Flask
app = Flask(__name__)

@app.route('/')
def hello():
    return 'Hello from Docker!'

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
```

`requirements.txt`：
```
flask==3.0.0
```

`Dockerfile`：
```dockerfile
# 基础镜像：使用官方 Python slim 版本（体积小）
FROM python:3.11-slim

# 设置工作目录（后续指令的相对路径都基于此）
WORKDIR /app

# 先复制依赖文件（利用缓存，代码变化时不重新安装依赖）
COPY requirements.txt .

# 安装依赖
RUN pip install --no-cache-dir -r requirements.txt

# 复制应用代码
COPY . .

# 声明容器监听端口（仅文档作用，需配合 -p 使用）
EXPOSE 5000

# 容器启动命令
CMD ["python", "app.py"]
```

`.dockerignore`（排除不需要的文件）：
```
__pycache__
*.pyc
.git
.venv
.env
```

**构建与运行：**

```bash
# 进入项目目录
cd myflask

# 构建镜像，命名为 myflask，标签 v1
docker build -t myflask:v1 .

# 查看构建出的镜像
docker images myflask

# 运行容器
docker run -d --name flask-app -p 5000:5000 myflask:v1

# 测试访问
curl http://localhost:5000
# 输出：Hello from Docker!

# 查看容器日志
docker logs flask-app
```

**构建过程输出解析：**

```bash
docker build -t myflask:v1 .
# Step 1/7 : FROM python:3.11-slim
#  ---> 9c7a54b2c1d3      # 复用已存在的基础镜像层
# Step 2/7 : WORKDIR /app
#  ---> Using cache        # 命中缓存
#  ---> a1b2c3d4e5f6
# Step 3/7 : COPY requirements.txt .
#  ---> b2c3d4e5f6a7       # 文件变化，新建层
# Step 4/7 : RUN pip install --no-cache-dir -r requirements.txt
#  ---> Running in c3d4e5f6a7b8
#  ... pip 安装过程 ...
#  ---> c3d4e5f6a7b8
# Step 5/7 : COPY . .
#  ---> d4e5f6a7b8c9
# Step 6/7 : EXPOSE 5000
#  ---> Using cache
# Step 7/7 : CMD ["python", "app.py"]
#  ---> Using cache
# Successfully built e5f6a7b8c9d0
# Successfully tagged myflask:v1
```

可以看到每一步都生成了一个层 ID，命中缓存时会显示 `Using cache`。

### 总结

本讲核心要点：

1. **Dockerfile 是镜像的源代码**，声明式描述构建过程，可版本控制。
2. **构建过程**：逐条执行指令 → 每条指令生成一层 → 叠加成最终镜像。
3. **构建缓存**：指令和上下文未变则复用缓存层，是构建加速的核心。
4. **构建上下文**：`docker build` 最后的路径参数，`COPY` 只能访问上下文内文件，用 `.dockerignore` 排除无关文件。

**常见注意事项**：
- 把变化频率低的指令放前面（如安装依赖），变化频率高的放后面（如复制代码），以最大化缓存命中。
- `requirements.txt` 单独 `COPY` 再 `RUN pip install`，比直接 `COPY . .` 后安装更高效——代码变化不会触发重新安装依赖。
- `.dockerignore` 必不可少，否则 `.git`、`node_modules` 等会被打包进上下文，拖慢构建。
- `EXPOSE` 只是声明，不会真正发布端口，必须 `docker run -p` 才能访问。

## 第 7 讲：Dockerfile 指令详解

### 概念

本讲系统讲解 Dockerfile 的所有常用指令。Dockerfile 指令不区分大小写，但约定俗成使用大写以区分参数。掌握每条指令的语义和最佳实践，是编写高质量 Dockerfile 的前提。

Dockerfile 指令可分为以下几类：

| 类别 | 指令 | 作用 |
|------|------|------|
| 基础 | `FROM` | 指定基础镜像（必须为第一条非注释指令） |
| 配置 | `LABEL`、`ENV`、`ARG`、`WORKDIR`、`USER` | 设置元数据、环境变量、工作目录、运行用户 |
| 文件 | `COPY`、`ADD` | 复制文件到镜像 |
| 执行 | `RUN` | 构建时执行命令 |
| 启动 | `CMD`、`ENTRYPOINT` | 容器启动时执行命令 |
| 声明 | `EXPOSE`、`VOLUME`、`STOPSIGNAL`、`HEALTHCHECK` | 声明端口、卷、信号、健康检查 |
| 多阶段 | `FROM ... AS`、`COPY --from` | 多阶段构建 |

### 原理

**RUN 指令的两种形式**：
- **Shell 形式**：`RUN apt install -y nginx`，实际执行 `/bin/sh -c "apt install -y nginx"`。
- **Exec 形式**：`RUN ["apt", "install", "-y", "nginx"]`，直接执行，不经过 shell。

Shell 形式支持管道、变量替换等 shell 特性，但依赖 `/bin/sh` 存在；Exec 形式更安全可控，但不支持 shell 特性。

**CMD 与 ENTRYPOINT 的区别**（Dockerfile 最易混淆的点）：

- **CMD**：容器默认启动命令，可被 `docker run` 后的参数覆盖。一个 Dockerfile 只能有一个 CMD（多个时最后一个生效）。
- **ENTRYPOINT**：容器固定启动命令，`docker run` 后的参数会作为 ENTRYPOINT 的追加参数，不会被覆盖。

两者组合使用是最佳实践：`ENTRYPOINT` 指定固定程序，`CMD` 提供默认参数。例如：

```dockerfile
ENTRYPOINT ["python", "app.py"]
CMD ["--help"]
```

`docker run myimage` 执行 `python app.py --help`；`docker run myimage --version` 执行 `python app.py --version`。

**COPY 与 ADD 的区别**：
- `COPY`：纯复制，简单可靠，推荐使用。
- `ADD`：额外支持自动解压 tar 包、从 URL 下载文件。但 URL 下载功能不推荐（不可缓存、不可复用），解压功能在需要时使用。

**多阶段构建原理**：通过多个 `FROM` 指令定义多个构建阶段，每个阶段独立。最终镜像只保留最后一个阶段的内容，但可以通过 `COPY --from=阶段名` 从前序阶段复制文件。这能大幅减小最终镜像体积——编译工具、源码、中间产物都不会进入最终镜像。

### 例子

**1. 基础指令示例：**

```dockerfile
# FROM：指定基础镜像，可用 AS 命名阶段
FROM ubuntu:22.04 AS builder

# LABEL：添加元数据（替代已废弃的 MAINTAINER）
LABEL maintainer="dev@example.com"
LABEL version="1.0"
LABEL description="My production app"

# ENV：设置环境变量（运行时也生效）
ENV APP_HOME=/usr/src/app \
    PYTHONUNBUFFERED=1

# ARG：构建时变量（仅构建期有效，运行时不存在）
ARG VERSION=1.0.0
LABEL build.version=$VERSION

# WORKDIR：设置工作目录（不存在会自动创建）
WORKDIR $APP_HOME

# USER：切换运行用户（安全最佳实践，避免用 root）
RUN groupadd -r appuser && useradd -r -g appuser appuser
USER appuser
```

**2. 文件操作指令：**

```dockerfile
# COPY：复制文件/目录到镜像（推荐）
COPY package.json ./
COPY src/ ./src/
COPY --chown=appuser:appuser . .  # 复制并设置属主

# ADD：额外支持解压和 URL（谨慎使用）
ADD https://example.com/file.tar.gz /tmp/  # 下载（不推荐，用 RUN curl 代替）
ADD file.tar.gz /opt/  # 自动解压到 /opt/
```

**3. RUN 指令优化（合并命令减少层数）：**

```dockerfile
# ❌ 不好：每条 RUN 一层，产生 3 个层
RUN apt-get update
RUN apt-get install -y nginx
RUN rm -rf /var/lib/apt/lists/*

# ✅ 好：合并为一条 RUN，用 && 连接，只产生 1 个层
RUN apt-get update \
    && apt-get install -y --no-install-recommends nginx \
    && rm -rf /var/lib/apt/lists/*
```

**4. CMD 与 ENTRYPOINT 组合：**

```dockerfile
# 场景：构建一个可配置的 nginx 镜像
FROM nginx:alpine

# 复制启动脚本
COPY docker-entrypoint.sh /usr/local/bin/
RUN chmod +x /usr/local/bin/docker-entrypoint.sh

# ENTRYPOINT 固定执行启动脚本
ENTRYPOINT ["docker-entrypoint.sh"]

# CMD 提供默认参数（启动 nginx）
CMD ["nginx", "-g", "daemon off;"]
```

`docker-entrypoint.sh`：
```bash
#!/bin/sh
# 可以在这里做启动前初始化
echo "Starting container at $(date)"
exec "$@"  # 关键：把 CMD 参数传给 exec 执行
```

**5. 多阶段构建（生产必备）：**

```dockerfile
# ===== 阶段 1：构建阶段 =====
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build  # 生成 dist/ 目录

# ===== 阶段 2：运行阶段 =====
FROM nginx:alpine
# 只复制构建产物，不包含 node_modules、源码
COPY --from=builder /app/dist /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

最终镜像只有 nginx + 静态文件，约 50MB；如果不做多阶段构建，最终镜像会包含整个 Node.js 环境和源码，可能超过 1GB。

**6. HEALTHCHECK 健康检查：**

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD curl -f http://localhost:5000/health || exit 1
```

### 总结

本讲核心要点：

1. **RUN 用 shell 形式 + `&&` 合并命令**，减少层数和镜像体积。
2. **CMD 可覆盖，ENTRYPOINT 不可覆盖**，组合使用是最佳实践。
3. **COPY 优于 ADD**，ADD 仅在需要自动解压时使用。
4. **多阶段构建**是减小镜像体积的核心手段，编译产物与运行环境分离。
5. **HEALTHCHECK** 让 Docker 自动检测容器健康状态，配合编排工具实现自动重启。

**常见注意事项**：
- `ENV` 设置的变量在构建期和运行期都生效；`ARG` 只在构建期生效。
- `WORKDIR` 优于 `RUN cd /path && ...`，更清晰且不会因 shell 退出而失效。
- 多阶段构建中，未命名的阶段用序号引用（`--from=0`），命名阶段用名称（`--from=builder`）。
- `ENTRYPOINT` 用 exec 形式 `["..."]` 而非 shell 形式，否则容器收不到 SIGTERM 信号，停止超时。

## 第 8 讲：镜像分层原理与构建优化

### 概念

本讲深入镜像分层的底层原理，并系统讲解构建优化的实战技巧。理解分层原理后，您将能写出体积更小、构建更快、缓存命中率更高的 Dockerfile，这是区分"会用 Docker"和"精通 Docker"的关键。

**镜像分层（Layer）** 是 Docker 存储模型的核心。每个镜像由若干只读层叠加而成，每层对应 Dockerfile 中的一条 `RUN`、`COPY`、`ADD` 指令。容器运行时，在镜像层之上添加一个可写层。所有层通过 **UnionFS（联合文件系统）** 叠加呈现为统一的文件系统视图。

### 原理

**UnionFS 工作机制**：以 Docker 默认的 overlay2 驱动为例，它将多层叠加：

```
┌─────────────────────────────────┐
│  Upperdir (可写层/容器层)        │  ← 容器修改写入此处
├─────────────────────────────────┤
│  Lowerdir (只读层/镜像层)        │  ← 从上到下叠加
│  Layer N: CMD ["nginx"]         │
│  Layer N-1: COPY index.html     │
│  Layer ...: RUN apt install     │
│  Layer 1: FROM ubuntu:22.04     │
├─────────────────────────────────┤
│  Merged (统一视图)               │  ← 容器看到的文件系统
└─────────────────────────────────┘
```

读取文件时，从上往下查找，第一个命中的层返回；写入文件时，通过 Copy-on-Write 将文件从只读层复制到可写层再修改。

**构建缓存失效规则**：一旦某层缓存失效，该层及之后所有层的缓存都会失效。缓存失效的触发条件：
1. 指令文本发生变化（如 `RUN apt install nginx` 改为 `RUN apt install redis`）。
2. `COPY`/`ADD` 的源文件内容发生变化（通过文件元数据校验）。
3. 基础镜像发生变化。

因此，**把变化频率低的指令放前面**是优化缓存命中的核心原则。

**镜像体积优化原理**：每条 `RUN` 指令生成一层，层是不可变的——即使后续 `RUN rm` 删除了文件，前一层中的文件依然存在，只是被"遮盖"了。这就是为什么"先安装再删除"在同一层内有效，跨层无效：

```dockerfile
# ❌ 不好：apt 缓存留在前一层，rm 无法减小体积
RUN apt-get update
RUN apt-get install -y nginx
RUN rm -rf /var/lib/apt/lists/*  # 这一层只是"遮盖"，前一层仍含缓存

# ✅ 好：在同层内清理
RUN apt-get update \
    && apt-get install -y --no-install-recommends nginx \
    && rm -rf /var/lib/apt/lists/*
```

### 例子

**1. 利用缓存优化构建顺序：**

```dockerfile
# ❌ 不好：COPY . . 在安装依赖前，任何代码变化都导致重新安装依赖
FROM node:18-alpine
WORKDIR /app
COPY . .
RUN npm install
CMD ["node", "index.js"]

# ✅ 好：先复制 package.json 安装依赖，再复制代码
FROM node:18-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --production
COPY . .
CMD ["node", "index.js"]
```

优化后，只有 `package.json` 变化时才重新 `npm install`，日常改代码构建只需几秒。

**2. 选择更小的基础镜像：**

```dockerfile
# ❌ 不好：完整 Debian 镜像，约 800MB
FROM python:3.11
# ...

# ✅ 好：slim 版本，约 150MB
FROM python:3.11-slim
# ...

# ✅✅ 更好：alpine 版本，约 50MB（但可能有兼容性问题）
FROM python:3.11-alpine
# ...
```

**3. 多阶段构建消除构建工具：**

```dockerfile
# Go 应用示例
# 阶段 1：构建（含 Go 编译器，约 800MB）
FROM golang:1.21 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o myapp -ldflags="-s -w" .

# 阶段 2：运行（仅含二进制，约 20MB）
FROM alpine:3.18
RUN apk add --no-cache ca-certificates
COPY --from=builder /app/myapp /usr/local/bin/
ENTRYPOINT ["myapp"]
```

最终镜像从 800MB 降到 20MB，体积减少 96%。

**4. 使用 .dockerignore 减少上下文：**

```
# .dockerignore
.git
.gitignore
node_modules
__pycache__
*.pyc
.venv
venv
.env
*.md
tests/
docs/
.vscode
.idea
```

**5. 使用 BuildKit 高级特性（现代 Docker 默认启用）：**

```dockerfile
# syntax 指令启用 BuildKit 扩展
# syntax=docker/dockerfile:1.6

FROM ubuntu:22.04

# --mount=type=cache：缓存目录跨构建复用，不进入镜像层
RUN --mount=type=cache,target=/var/cache/apt \
    --mount=type=cache,target=/var/lib/apt \
    apt-get update && apt-get install -y nginx

# --mount=type=secret：安全传递密钥，不留在镜像历史
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm install
```

构建命令：
```bash
DOCKER_BUILDKIT=1 docker build --secret id=npmrc,src=$HOME/.npmrc -t myapp .
```

**6. 查看镜像体积构成：**

```bash
# 使用 dive 工具分析每层体积（需安装 dive）
dive myflask:v1

# 或使用 docker history 查看每层大小
docker history --no-trunc --format "{{.Size}}\t{{.CreatedBy}}" myflask:v1
```

### 总结

本讲核心要点：

1. **镜像分层 + UnionFS**：只读层叠加 + 可写层，Copy-on-Write 实现修改。
2. **缓存失效会级联**：某层失效后所有后续层都失效，因此低频变化指令放前面。
3. **跨层删除无效**：清理操作必须与安装在同一 `RUN` 内。
4. **优化三板斧**：选小基础镜像（alpine/distroless）+ 多阶段构建 + 合并 RUN 命令。
5. **BuildKit 的 `--mount=type=cache`** 是现代构建优化利器，缓存依赖不污染镜像。

**常见注意事项**：
- alpine 镜像使用 musl libc 而非 glibc，部分 C 扩展可能编译失败，需测试验证。
- `distroless` 镜像没有 shell，无法 `docker exec` 进入调试，但安全性更高。
- 镜像体积直接影响拉取时间和攻击面，生产镜像应控制在 200MB 以内。
- 使用 `dive` 工具可视化分析镜像层，找出体积异常的层。

# 第 3 章 容器操作与管理

容器是镜像的运行实例，是应用真正运行的地方。本章深入容器的全生命周期管理，包括启动停止、数据持久化、网络通信、资源限制等核心主题。这些知识是日常运维 Docker 应用的基础，也是后续学习 Docker Compose 和 Kubernetes 的前提。掌握本章后，您将能够独立运维单机上的多容器应用。

## 第 9 讲：容器的生命周期管理

### 概念

容器具有完整的生命周期，从创建到销毁经历多个状态。理解这些状态及状态间的转换，是高效管理容器的前提。

**容器的五种核心状态**：
1. **created**：已创建但未启动（`docker create` 后的状态）。
2. **running**：运行中（`docker run` 或 `docker start` 后）。
3. **paused**：已暂停（`docker pause` 后，进程被冻结但未终止）。
4. **stopped/exited**：已停止（`docker stop` 后或容器内主进程退出）。
5. **deleted**：已删除（`docker rm` 后，容器彻底消失）。

**状态转换图**：

```
                    docker create
                         │
                         ▼
                    ┌─────────┐
        docker start│ created │
              ┌─────┴─────────┴─────┐
              │                     │
              ▼                     │
        ┌─────────┐  docker stop   │
   ┌───→│ running │──────────────┐ │
   │    └────┬────┘              ▼ │
   │         │ docker pause ┌─────────┐
   │docker   │              │ stopped │
   │unpause  ▼              └────┬────┘
   │    ┌─────────┐              │ docker rm
   │    │ paused  │              ▼
   │    └─────────┘         ┌─────────┐
   └────────────────────────│ deleted │
                            └─────────┘
```

### 原理

**docker stop 的优雅停止机制**：执行 `docker stop` 时，Docker 首先向容器主进程（PID 1）发送 `SIGTERM` 信号，请求其优雅退出。应用应捕获该信号，完成清理工作（如关闭数据库连接、刷新缓存、保存状态）。如果等待 10 秒（默认）后进程仍未退出，Docker 发送 `SIGKILL` 强制终止。可通过 `-t` 参数调整等待时间，如 `docker stop -t 30 web`。

**docker kill 的强制停止**：`docker kill` 直接发送 `SIGKILL`，进程立即终止，没有机会清理。默认信号是 `SIGKILL`，可通过 `--signal` 指定其他信号，如 `docker kill --signal=SIGUSR1 web`。

**docker pause 的冻结机制**：`docker pause` 使用 Linux 的 `cgroup freezer` 子系统，冻结容器内所有进程的 CPU 调度。进程状态被保留在内存中，但不再获得 CPU 时间片，相当于"暂停"。`docker unpause` 恢复执行。与 stop 不同，pause 不发送信号，进程不知道自己被暂停过。

**容器退出码的含义**：容器停止后，`docker ps -a` 会显示退出码（EXITED STATUS），常见含义：
- `0`：正常退出。
- `1`：应用错误（通用失败）。
- `125`：docker 本身错误。
- `126`：命令不可执行。
- `127`：命令未找到。
- `137`：被 SIGKILL 杀死（通常是 OOM 或 stop 超时）。
- `139`：段错误（SIGSEGV）。
- `143`：被 SIGTERM 终止（正常 stop）。

### 例子

**1. 完整生命周期操作：**

```bash
# 创建容器（不启动）
docker create --name web -p 8080:80 nginx:alpine
# 状态：created

# 启动容器
docker start web
# 状态：running

# 查看运行中容器
docker ps
# CONTAINER ID   IMAGE          STATUS         NAMES
# a1b2c3d4e5f6   nginx:alpine   Up 10 seconds  web

# 查看所有容器（含已停止）
docker ps -a

# 查看最后创建的容器
docker ps -l

# 暂停容器（冻结进程）
docker pause web
# 状态：paused（此时 curl 访问会超时）

# 恢复容器
docker unpause web
# 状态：running

# 重启容器（stop + start）
docker restart web

# 优雅停止（发送 SIGTERM，等待 10 秒）
docker stop web
# 状态：exited

# 强制停止（发送 SIGKILL，立即终止）
docker kill web

# 删除已停止的容器
docker rm web

# 强制删除运行中的容器（stop + rm）
docker rm -f web
```

**2. docker run 的常用参数：**

```bash
# 后台运行 + 命名 + 端口映射
docker run -d --name web -p 8080:80 nginx:alpine

# 容器停止后自动删除（适合一次性任务）
docker run --rm alpine echo "hello"

# 设置环境变量
docker run -d --name db -e MYSQL_ROOT_PASSWORD=secret -e MYSQL_DATABASE=myapp mysql:8

# 从文件读取环境变量
docker run --env-file .env -d myapp

# 设置容器主机名
docker run -d --hostname web-server nginx:alpine

# 指定重启策略（容器退出后自动重启）
docker run -d --restart=always nginx:alpine          # 总是重启
docker run -d --restart=unless-stopped nginx:alpine  # 除非手动停止，否则重启
docker run -d --restart=on-failure:5 nginx:alpine    # 非零退出码重启，最多 5 次

# 设置工作目录和用户
docker run -w /app -u appuser -it myimage sh

# 添加特权（不推荐，安全风险）
docker run --privileged -d myapp
```

**3. 容器内操作：**

```bash
# 进入运行中的容器（交互式）
docker exec -it web sh

# 在容器内执行单条命令
docker exec web ls /usr/share/nginx/html

# 以 root 进入容器（即使容器默认用户非 root）
docker exec -u 0 -it web sh

# 查看容器进程列表
docker top web

# 查看容器资源占用
docker stats web
# CONTAINER ID   NAME   CPU %   MEM USAGE / LIMIT   MEM %   NET I/O
# a1b2c3d4e5f6   web    0.05%   5.2MiB / 8GiB       0.06%   1.2kB/0B

# 查看容器端口映射
docker port web
# 80/tcp -> 0.0.0.0:8080

# 查看容器内文件变更（相对于镜像）
docker diff web
# C /etc/nginx/conf.d/default.conf  # C=Changed
# A /tmp/test.txt                    # A=Added
# D /var/log/nginx/access.log        # D=Deleted
```

**4. 批量管理容器：**

```bash
# 停止所有运行中的容器
docker stop $(docker ps -q)

# 删除所有已停止的容器
docker container prune

# 删除所有容器（强制）
docker rm -f $(docker ps -aq)

# 清理所有未使用的资源（镜像、容器、网络、缓存）
docker system prune -a --volumes
```

### 总结

本讲核心要点：

1. **容器五种状态**：created → running → paused → stopped → deleted，理解状态转换是管理基础。
2. **stop 优雅、kill 强制**：stop 发 SIGTERM 等待 10 秒，kill 直接 SIGKILL。
3. **pause 用 cgroup freezer**：冻结 CPU 调度，进程状态保留，可恢复。
4. **退出码诊断**：137=OOM/超时，143=正常 stop，139=段错误。
5. **重启策略**：生产环境用 `unless-stopped`，避免 `always` 导致故障容器无限重启。

**常见注意事项**：
- 容器主进程必须是 PID 1，且要正确处理 SIGTERM，否则 stop 超时被 SIGKILL，数据可能丢失。
- `--restart=always` 会让手动 stop 的容器在 dockerd 重启后再次启动，用 `unless-stopped` 更合理。
- `docker exec` 进入容器后，`exit` 只退出 exec 的 shell，不影响容器；但如果是主进程退出，容器会停止。
- `--privileged` 等于赋予容器近乎宿主机的权限，生产环境禁用，需用 `--cap-add` 精确授权。

## 第 10 讲：容器数据管理 —— Volume 与 Bind Mount

### 概念

容器的设计哲学是"用完即弃"——容器删除后，其可写层中的所有数据都会丢失。但许多应用（数据库、消息队列、文件存储）需要持久化数据，这就需要 Docker 的数据管理机制。

Docker 提供三种数据管理方式：

1. **Volume（数据卷）**：由 Docker 管理的持久化存储，存储在宿主机的特定目录（Linux 下为 `/var/lib/docker/volumes/`）。Volume 是 Docker 官方推荐的持久化方案，独立于容器生命周期，支持跨容器共享，可备份迁移。

2. **Bind Mount（绑定挂载）**：将宿主机的任意目录或文件直接挂载到容器中。依赖宿主机的目录结构，适合开发环境（如热重载代码），但可移植性差。

3. **tmpfs Mount**：将数据存储在宿主机的内存中，容器停止后数据消失。适合存储敏感信息（如密钥）或临时高速缓存。

### 原理

**Volume 的工作机制**：创建 Volume 时，Docker 在 `/var/lib/docker/volumes/<volume名>/_data/` 创建一个目录。容器挂载 Volume 时，Docker 将该目录挂载到容器内的指定路径。Volume 的数据存储在 Docker 管理的区域，不受容器删除影响。多个容器可同时挂载同一个 Volume，实现数据共享。

**Bind Mount 的工作机制**：Bind Mount 直接将宿主机路径挂载到容器路径，本质是 Linux 的 `mount --bind`。容器内对该路径的读写直接作用于宿主机文件。这意味着容器可以修改宿主机文件（包括 `/etc` 等敏感目录），存在安全风险。

**tmpfs 的工作机制**：tmpfs 是基于内存的文件系统，数据存储在宿主机的 RAM 或 swap 中。容器停止后数据立即消失，不会写入磁盘。适合存储不需要持久化的临时数据。

**三种方式对比**：

| 特性 | Volume | Bind Mount | tmpfs |
|------|--------|------------|-------|
| 存储位置 | Docker 管理区 | 宿主机任意路径 | 内存 |
| 持久化 | 是 | 是（依赖宿主机） | 否 |
| 可移植性 | 高 | 低 | 中 |
| 安全性 | 高 | 低（可改宿主文件） | 高 |
| 适用场景 | 生产数据持久化 | 开发环境代码挂载 | 敏感数据/临时缓存 |
| 备份迁移 | 方便 | 需手动处理 | 不需要 |

### 例子

**1. Volume 的基本操作：**

```bash
# 创建命名 Volume
docker volume create mydata

# 查看 Volume 列表
docker volume ls
# DRIVER    VOLUME NAME
# local     mydata

# 查看 Volume 详情（含宿主机实际路径）
docker volume inspect mydata
# [
#     {
#         "Name": "mydata",
#         "Mountpoint": "/var/lib/docker/volumes/mydata/_data",
#         "Driver": "local"
#     }
# ]

# 使用 Volume 启动容器
docker run -d --name db \
  -v mydata:/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=secret \
  mysql:8

# 匿名 Volume（Docker 自动生成随机名）
docker run -d -v /var/lib/mysql mysql:8

# 删除 Volume（必须无容器使用）
docker volume rm mydata

# 清理所有未使用的 Volume
docker volume prune
```

**2. Bind Mount 的使用：**

```bash
# 语法：-v 宿主机路径:容器路径[:选项]
# 选项：ro（只读）、rw（读写，默认）

# 挂载宿主机目录到容器（开发环境热重载）
docker run -d --name dev-app \
  -v /home/user/myproject:/app \
  -p 5000:5000 \
  myapp:dev

# 只读挂载（配置文件等）
docker run -d --name web \
  -v /home/user/nginx.conf:/etc/nginx/nginx.conf:ro \
  nginx:alpine

# 使用 --mount 语法（更清晰，推荐）
docker run -d --name web \
  --mount type=bind,source=/home/user/nginx.conf,target=/etc/nginx/nginx.conf,readonly \
  nginx:alpine
```

**3. 实战：MySQL 数据持久化**

```bash
# 第一次启动，数据写入 Volume
docker run -d --name mysql \
  -v mysql-data:/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=secret \
  -e MYSQL_DATABASE=myapp \
  mysql:8

# 写入一些数据
docker exec -it mysql mysql -uroot -psecret -e "USE myapp; CREATE TABLE users (id INT, name VARCHAR(50)); INSERT INTO users VALUES (1, 'Alice');"

# 删除容器（Volume 数据保留）
docker rm -f mysql

# 重新启动容器，挂载同一 Volume，数据恢复
docker run -d --name mysql-new \
  -v mysql-data:/var/lib/mysql \
  -e MYSQL_ROOT_PASSWORD=secret \
  mysql:8

docker exec -it mysql-new mysql -uroot -psecret -e "SELECT * FROM myapp.users;"
# +------+-------+
# | id   | name  |
# +------+-------+
# |    1 | Alice |
# +------+-------+
```

**4. 容器间数据共享：**

```bash
# 创建共享 Volume
docker volume create shared-data

# 容器 A 写入数据
docker run -d --name writer \
  -v shared-data:/data \
  alpine sh -c 'echo "Hello from writer" > /data/message.txt && sleep 3600'

# 容器 B 读取数据
docker run --rm -v shared-data:/data alpine cat /data/message.txt
# 输出：Hello from writer
```

**5. Volume 备份与迁移：**

```bash
# 备份：用临时容器把 Volume 内容打包到宿主机
docker run --rm -v mydata:/data -v $(pwd):/backup alpine \
  tar czf /backup/mydata-backup.tar.gz -C /data .

# 恢复：把备份解压到新 Volume
docker volume create mydata-restored
docker run --rm -v mydata-restored:/data -v $(pwd):/backup alpine \
  tar xzf /backup/mydata-backup.tar.gz -C /data
```

**6. tmpfs 的使用：**

```bash
# 使用 tmpfs 存储敏感数据（容器停止后消失）
docker run -d --name secure-app \
  --tmpfs /secrets:size=10m,mode=700 \
  myapp

# 或用 --mount 语法
docker run -d --name secure-app \
  --mount type=tmpfs,destination=/secrets,tmpfs-size=10m,tmpfs-mode=700 \
  myapp
```

### 总结

本讲核心要点：

1. **三种数据管理方式**：Volume（生产推荐）、Bind Mount（开发用）、tmpfs（临时/敏感）。
2. **Volume 由 Docker 管理**，独立于容器生命周期，可跨容器共享，备份迁移方便。
3. **Bind Mount 直接挂载宿主机路径**，开发热重载方便，但可移植性差、有安全风险。
4. **生产数据库必须用 Volume**，否则容器删除数据丢失。
5. **`-v` 简写、`--mount` 标准写法**，后者更清晰，推荐生产使用。

**常见注意事项**：
- Bind Mount 挂载的宿主机目录如果不存在，Docker 会自动创建（且属主为 root），可能导致权限问题。
- 容器内进程的 UID/GID 与宿主机不一致时，Volume 文件可能出现权限冲突，需用 `--user` 指定或调整文件权限。
- 不要用 Bind Mount 挂载 `/etc`、`/var` 等系统目录，可能破坏宿主机。
- Volume 删除前确认无容器使用，`docker volume prune` 会删除所有未使用 Volume，谨慎执行。

## 第 11 讲：容器网络基础

### 概念

容器网络是 Docker 最复杂的主题之一。每个容器都需要网络通信——既要访问外部网络（如拉取数据），也要被外部访问（如 Web 服务），还可能需要与其他容器通信（如应用连数据库）。

Docker 提供五种内置网络驱动：

1. **bridge（桥接）**：默认驱动，创建虚拟网桥 docker0，容器通过 NAT 访问外部。适合单机多容器通信。
2. **host（主机）**：容器直接使用宿主机网络栈，无隔离，性能最高但端口冲突风险大。
3. **none（无网络）**：容器只有 lo 回环接口，完全隔离，适合安全敏感场景。
4. **overlay（覆盖）**：跨多台宿主机的容器通信，用于 Docker Swarm 集群。
5. **macvlan**：为容器分配物理网络中的 MAC 地址，表现为网络中的独立设备。

### 原理

**bridge 网络的工作原理**：

Docker 在宿主机创建一个虚拟网桥 `docker0`（Linux bridge），并为每个容器创建一对虚拟网卡（veth pair）——一端在容器的网络命名空间内（eth0），另一端连接到 docker0。容器从 docker0 的子网（默认 172.17.0.0/16）获取 IP 地址。

```
┌─────────────────────────────────────────────┐
│                 宿主机                       │
│                                             │
│   ┌─────────┐    ┌─────────┐               │
│   │ 容器 A   │    │ 容器 B   │               │
│   │ 172.17  │    │ 172.17  │               │
│   │ .0.2    │    │ .0.3    │               │
│   └────┬────┘    └────┬────┘               │
│        │veth          │veth                 │
│   ┌────┴──────────────┴────┐               │
│   │      docker0 (网桥)     │ 172.17.0.1    │
│   └────────────┬───────────┘               │
│                │                            │
│   ┌────────────┴───────────┐               │
│   │     eth0 (宿主机网卡)    │               │
│   └────────────────────────┘               │
│                                             │
└─────────────────────────────────────────────┘
```

**NAT 与端口映射**：容器通过 docker0 访问外部网络时，使用 iptables 的 MASQUERADE 规则做源地址转换（SNAT），把容器 IP 172.17.0.2 转换为宿主机 IP。外部访问容器时，通过 `-p 8080:80` 映射，iptables 的 DNAT 规则把宿主机 8080 端口的流量转发到容器 80 端口。

**DNS 服务发现**：默认 bridge 网络不支持容器间通过容器名解析（只能用 IP）。但**自定义 bridge 网络**内置 DNS 服务器（127.0.0.11），容器间可通过容器名互相访问。这是自定义网络的核心优势。

**host 网络原理**：容器不创建独立的网络命名空间，直接使用宿主机的网络栈。容器内 `eth0` 就是宿主机的网卡，端口直接占用宿主机端口。性能最优（无 NAT 开销），但失去网络隔离，多个容器不能绑定同一端口。

### 例子

**1. 查看与管理网络：**

```bash
# 查看所有网络
docker network ls
# NETWORK ID     NAME      DRIVER    SCOPE
# a1b2c3d4e5f6   bridge    bridge    local
# b2c3d4e5f6a7   host      host      local
# c3d4e5f6a7b8   none      null      local

# 查看网络详情（含连接的容器）
docker network inspect bridge

# 创建自定义 bridge 网络
docker network create mynet

# 创建指定子网的网络
docker network create --subnet=192.168.100.0/24 mynet

# 删除网络
docker network rm mynet

# 清理未使用的网络
docker network prune
```

**2. 默认 bridge 网络的局限：**

```bash
# 启动两个容器在默认 bridge 网络
docker run -d --name container-a alpine sleep 3600
docker run -d --name container-b alpine sleep 3600

# 尝试用容器名通信（失败！默认 bridge 无 DNS）
docker exec container-a ping -c 2 container-b
# ping: bad address 'container-b'

# 只能用 IP 通信（不灵活，IP 会变）
docker exec container-a ping -c 2 172.17.0.3
```

**3. 自定义 bridge 网络（推荐）：**

```bash
# 创建自定义网络
docker network create appnet

# 启动容器并加入网络
docker run -d --name web --network appnet nginx:alpine
docker run -d --name db --network appnet mysql:8

# 用容器名通信（成功！自定义网络有 DNS）
docker exec web ping -c 2 db
# PING db (172.18.0.3): 56 data bytes
# 64 bytes from 172.18.0.3: seq=0 ttl=64 time=0.123 ms

# 应用直接用容器名连接数据库
docker exec web sh -c 'apt-get update && apt-get install -y mysql-client && mysql -h db -uroot -psecret -e "SELECT 1"'
```

**4. 端口映射：**

```bash
# 单端口映射
docker run -d -p 8080:80 nginx:alpine

# 指定宿主机 IP
docker run -d -p 127.0.0.1:8080:80 nginx:alpine

# 多端口映射
docker run -d -p 8080:80 -p 8443:443 nginx:alpine

# 随机端口映射（Docker 分配宿主机端口）
docker run -d -P nginx:alpine
# 查看分配的端口
docker port $(docker ps -lq)
# 80/tcp -> 0.0.0.0:32768

# UDP 端口
docker run -d -p 53:53/udp dns-server
```

**5. host 与 none 网络：**

```bash
# host 网络：直接用宿主机网络
docker run -d --network host nginx:alpine
# 此时 nginx 直接监听宿主机 80 端口，无需 -p

# none 网络：完全隔离
docker run -d --network none alpine sleep 3600
docker exec $(docker ps -lq) ip addr
# 只有 lo 接口，无 eth0
```

**6. 容器加入多个网络：**

```bash
# 创建两个网络
docker network create frontend
docker network create backend

# web 容器同时加入前后端网络
docker run -d --name web --network frontend nginx:alpine
docker network connect backend web

# db 容器只加入后端
docker run -d --name db --network backend mysql:8

# web 可访问 db（通过 backend 网络）
docker exec web ping -c 2 db

# 断开网络
docker network disconnect backend web
```

### 总结

本讲核心要点：

1. **五种网络驱动**：bridge（默认）、host（高性能）、none（隔离）、overlay（跨机）、macvlan（物理网络）。
2. **默认 bridge 无 DNS**，容器间只能用 IP 通信；**自定义 bridge 有 DNS**，可用容器名通信，生产推荐。
3. **端口映射 `-p`** 通过 iptables NAT 实现，是外部访问容器的标准方式。
4. **host 网络无隔离**，性能最优但端口冲突风险大，慎用。
5. **容器可加入多个网络**，实现网络分段（如前端网络 + 后端网络）。

**常见注意事项**：
- 生产环境务必用自定义 bridge 网络，不要用默认 bridge。
- 容器名即主机名，命名要有意义（如 `db`、`redis`、`web`）。
- 端口映射会暴露服务到公网，生产环境用 `127.0.0.1:8080:80` 限制只监听本地。
- host 网络下 `-p` 参数无效，端口直接占用宿主机。

## 第 12 讲：容器资源限制与监控

### 概念

默认情况下，容器可以无限制地使用宿主机的 CPU、内存等资源。一个失控的容器（如内存泄漏）可能耗尽宿主机资源，导致所有容器崩溃。生产环境必须对容器进行资源限制，并持续监控资源使用情况。

Docker 通过 Linux cgroup 实现资源限制，主要支持：
- **CPU 限制**：限制 CPU 核心数、CPU 份额、CPU 配额。
- **内存限制**：限制内存上限、Swap 上限。
- **Block I/O 限制**：限制磁盘读写带宽。
- **PID 限制**：限制容器内最大进程数。

### 原理

**CPU 限制的三种方式**：

1. **`--cpus`**：限制可用 CPU 核心数（浮点数）。如 `--cpus=1.5` 表示最多使用 1.5 个核心。这是最直观的方式，底层使用 cgroup 的 `cpu.cfs_quota_us` 和 `cpu.cfs_period_us`。
2. **`--cpu-shares`**：相对权重，默认 1024。当宿主机 CPU 繁忙时，按权重比例分配。如容器 A=1024，容器 B=512，则 A 获得 2/3 的 CPU，B 获得 1/3。CPU 空闲时不生效。
3. **`--cpuset-cpus`**：绑定到指定 CPU 核心。如 `--cpuset-cpus=0,1` 只使用第 0、1 号核心，适合对 CPU 缓存亲和性敏感的应用。

**内存限制**：
- **`-m / --memory`**：内存上限，如 `-m 512m`。达到上限后，内核的 OOM Killer 会杀掉容器内占用内存最多的进程。
- **`--memory-swap`**：内存 + Swap 总上限。必须大于等于 memory。设为 `-1` 表示 Swap 无限。
- **`--memory-reservation`**：软限制，内核在内存紧张时尝试回收到此值。
- **`--oom-kill-disable`**：禁用 OOM Killer（危险，可能导致系统崩溃）。

**监控原理**：Docker 通过 cgroup 的统计接口收集容器资源使用数据。`docker stats` 命令实时读取这些数据并展示。底层是 `/sys/fs/cgroup/<子系统>/docker/<容器ID>/` 下的统计文件。

### 例子

**1. CPU 限制：**

```bash
# 限制最多使用 1.5 个 CPU 核心
docker run -d --name web --cpus=1.5 nginx:alpine

# CPU 权重（相对限制）
docker run -d --name high-priority --cpu-shares=2048 nginx:alpine
docker run -d --name low-priority --cpu-shares=512 nginx:alpine

# 绑定到指定 CPU 核心
docker run -d --name db --cpuset-cpus=0,1 mysql:8
```

**2. 内存限制：**

```bash
# 限制内存 512MB，Swap 1GB
docker run -d --name app -m 512m --memory-swap=1g myapp

# 只限制内存，禁用 Swap
docker run -d --name app -m 512m --memory-swap=512m myapp

# 软限制 256MB，硬限制 512MB
docker run -d --name app -m 512m --memory-reservation=256m myapp
```

**3. 实战：测试内存限制**

```bash
# 启动一个会不断分配内存的容器，限制 100MB
docker run -d --name mem-test -m 100m polinux/stress --vm 1 --vm-bytes 150M --vm-hang 0

# 查看资源使用
docker stats mem-test
# CONTAINER   CPU %   MEM USAGE / LIMIT    MEM %
# mem-test    0.0%    99.8MiB / 100MiB     99.8%

# 查看容器状态（会被 OOM Kill）
docker ps -a
# CONTAINER ID   STATUS                       NAMES
# ...            Exited (137) 5 seconds ago   mem-test
# 退出码 137 = 128 + 9 (SIGKILL)，即被 OOM Killer 杀死
```

**4. 实时监控：**

```bash
# 监控所有运行中容器（实时刷新）
docker stats
# CONTAINER ID   NAME      CPU %   MEM USAGE / LIMIT   MEM %   NET I/O         BLOCK I/O
# a1b2c3d4e5f6   web       0.05%   5.2MiB / 8GiB       0.06%   1.2kB/0B        8.19kB/0B
# b2c3d4e5f6a7   db        2.30%   256MiB / 1GiB       25.6%   5.4kB/2.1kB     12.3MB/4.5MB

# 只监控指定容器，只输出一次
docker stats --no-stream web db

# 自定义输出格式
docker stats --format "table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}"
```

**5. 查看容器详细资源信息：**

```bash
# 查看容器的资源限制配置
docker inspect web | grep -A 20 "HostConfig"

# 查看容器的 cgroup 信息
docker inspect web --format '{{.State.Pid}}' | xargs -I{} cat /proc/{}/cgroup

# 查看容器内进程
docker top web
# UID    PID    PPID   ...   COMMAND
# root   1234   5678   ...   nginx: master process nginx
# nginx  1290   1234   ...   nginx: worker process
```

**6. 使用 cAdvisor 进行可视化监控：**

```bash
# 启动 cAdvisor 容器，监控所有容器
docker run -d --name cadvisor \
  -v /:/rootfs:ro \
  -v /var/run:/var/run:ro \
  -v /sys:/sys:ro \
  -v /var/lib/docker/:/var/lib/docker:ro \
  -p 8080:8080 \
  google/cadvisor:latest

# 访问 http://localhost:8080 查看可视化监控
```

**7. 综合资源限制示例（生产配置）：**

```bash
docker run -d \
  --name production-app \
  --cpus=2 \
  --cpu-shares=1024 \
  -m 2g \
  --memory-swap=2g \
  --memory-reservation=1g \
  --pids-limit=200 \
  --restart=unless-stopped \
  --health-cmd="curl -f http://localhost:5000/health || exit 1" \
  --health-interval=30s \
  --health-retries=3 \
  -p 5000:5000 \
  myapp:production
```

### 总结

本讲核心要点：

1. **CPU 限制三种方式**：`--cpus`（绝对核心数）、`--cpu-shares`（相对权重）、`--cpuset-cpus`（绑定核心）。
2. **内存限制**：`-m` 硬限制触发 OOM Kill，`--memory-reservation` 软限制温和回收。
3. **退出码 137 = OOM Kill**，是内存不足的典型信号。
4. **`docker stats` 实时监控**，生产环境配合 cAdvisor/Prometheus 做可视化。
5. **生产容器必须设资源限制**，否则一个失控容器可能拖垮整台宿主机。

**常见注意事项**：
- Java 应用要设置 `-Xmx` 小于容器内存限制，否则 JVM 看到的内存是宿主机内存，导致 OOM。
- `--memory-swap` 必须大于等于 `-m`，设为与 `-m` 相同等于禁用 Swap。
- `--oom-kill-disable` 极度危险，只在特殊场景（如数据库）配合严格内存限制使用。
- cAdvisor 已停止维护，生产推荐用 Prometheus + node_exporter + cAdvisor 组合监控。

# 第 4 章 Docker Compose 多容器编排

现代应用很少是单容器架构——一个 Web 应用通常包含应用服务器、数据库、缓存、消息队列等多个服务。手动用 `docker run` 管理多个容器及其依赖关系、网络、数据卷，既繁琐又易错。Docker Compose 正是为解决这一问题而生：用一份 YAML 文件定义整个多容器应用栈，一条命令完成启动、停止、重建。本章将系统讲解 Compose 的使用，并通过实战部署一个完整的 Web 应用栈。

## 第 13 讲：Docker Compose 入门

### 概念

**Docker Compose** 是一个用于定义和运行多容器 Docker 应用的工具。它使用 YAML 文件（默认 `docker-compose.yml`）描述应用的服务、网络、数据卷等配置，然后通过一条命令（`docker compose up`）创建并启动所有资源。

Compose 的核心价值：
1. **声明式配置**：用 YAML 描述"应用应该是什么样"，而非"如何搭建"。
2. **一键启停**：`docker compose up -d` 启动整个栈，`docker compose down` 一键销毁。
3. **环境一致性**：同一份 compose 文件可在开发、测试、生产环境复用。
4. **依赖管理**：自动处理服务间启动顺序（如等数据库就绪再启动应用）。
5. **版本控制**：YAML 文件可纳入 Git，实现基础设施即代码。

**Compose 的版本演进**：早期 Compose 是独立的 Python 工具（`docker-compose`，带连字符），通过 HTTP API 与 dockerd 通信。从 Docker 1.27 开始，Compose 被重写为 Go 并集成到 Docker CLI（`docker compose`，无连字符），即 **Compose V2**。V2 性能更好、与 Docker CLI 集成更紧密，是当前推荐版本。本课程统一使用 V2 语法（`docker compose`）。

### 原理

**Compose 的工作流程**：

1. **解析 YAML**：读取 `docker-compose.yml`，解析服务、网络、卷定义。
2. **创建项目**：Compose 为每个 compose 文件创建一个"项目"（project），项目名默认为所在目录名（小写）。所有资源（容器、网络、卷）都加上项目名前缀，如 `myapp-web-1`、`myapp_db-data`。
3. **创建网络和卷**：先创建 compose 文件中定义的自定义网络和数据卷。
4. **构建/拉取镜像**：对有 `build` 配置的服务构建镜像，对有 `image` 配置的服务拉取镜像。
5. **启动容器**：按依赖顺序（`depends_on`）启动各服务容器，加入对应网络，挂载卷。
6. **状态管理**：Compose 持续监控容器状态，`docker compose ps` 查看状态，`docker compose logs` 查看日志。

**资源命名规则**：Compose 创建的资源遵循 `<项目名>-<服务名>-<副本序号>` 格式。例如项目 `myapp` 中服务 `web` 的第一个容器名为 `myapp-web-1`。这保证了不同 compose 项目间的资源隔离。

**与 docker run 的关系**：Compose 本质上是 `docker run` 命令的声明式封装。compose 文件中的每个配置项都对应 `docker run` 的某个参数。例如：

```yaml
# compose 写法
services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    volumes:
      - ./html:/usr/share/nginx/html
```

等价于：

```bash
# docker run 写法
docker run -d --name myapp-web-1 -p 8080:80 -v ./html:/usr/share/nginx/html nginx:alpine
```

### 例子

**实战：用 Compose 部署一个简单的 Web + Redis 应用**

项目结构：
```
myapp/
├── docker-compose.yml
├── app.py
├── requirements.txt
└── Dockerfile
```

`app.py`（一个简单的 Flask 计数器）：
```python
from flask import Flask
import redis
import os

app = Flask(__name__)
redis_host = os.environ.get('REDIS_HOST', 'redis')
r = redis.Redis(host=redis_host, port=6379)

@app.route('/')
def hello():
    count = r.incr('hits')
    return f'Hello! This page has been viewed {count} times.'

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
```

`requirements.txt`：
```
flask==3.0.0
redis==5.0.0
```

`Dockerfile`：
```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["python", "app.py"]
```

`docker-compose.yml`：
```yaml
services:
  web:
    build: .                    # 从当前目录的 Dockerfile 构建
    ports:
      - "5000:5000"             # 宿主机 5000 -> 容器 5000
    depends_on:
      - redis                   # 等 redis 启动后再启动 web
    environment:
      - REDIS_HOST=redis        # 通过容器名访问 redis
    restart: unless-stopped

  redis:
    image: redis:7-alpine       # 直接使用官方镜像
    volumes:
      - redis-data:/data        # 数据持久化
    restart: unless-stopped

volumes:
  redis-data:                   # 声明命名卷
```

**操作命令：**

```bash
# 启动所有服务（前台运行，看日志）
docker compose up

# 后台启动
docker compose up -d

# 查看运行中的服务
docker compose ps
# NAME                IMAGE        STATUS        PORTS
# myapp-web-1         myapp-web    Up 10 seconds 0.0.0.0:5000->5000/tcp
# myapp-redis-1       redis:7...   Up 11 seconds 6379/tcp

# 查看日志（所有服务）
docker compose logs -f

# 查看指定服务日志
docker compose logs -f web

# 在运行中的服务内执行命令
docker compose exec web sh
docker compose exec redis redis-cli

# 停止并删除所有容器、网络（保留卷）
docker compose down

# 停止并删除所有资源（含卷，慎用）
docker compose down -v

# 重新构建镜像（代码变更后）
docker compose up -d --build

# 只重启某个服务
docker compose restart web

# 查看服务配置（渲染后的最终配置）
docker compose config
```

**测试应用：**

```bash
# 多次访问，计数器递增
curl http://localhost:5000
# Hello! This page has been viewed 1 times.
curl http://localhost:5000
# Hello! This page has been viewed 2 times.
curl http://localhost:5000
# Hello! This page has been viewed 3 times.

# 停止后重启，计数器继续（数据持久化在卷中）
docker compose down
docker compose up -d
curl http://localhost:5000
# Hello! This page has been viewed 4 times.
```

### 总结

本讲核心要点：

1. **Compose 用 YAML 声明多容器应用**，一条命令完成启停，是 `docker run` 的声明式封装。
2. **项目名隔离**：每个 compose 文件是一个项目，资源命名 `<项目名>-<服务名>-<序号>`。
3. **依赖管理**：`depends_on` 控制启动顺序，但不等待服务"就绪"（只等启动）。
4. **V2 语法**：`docker compose`（无连字符），性能优于 V1 的 `docker-compose`。

**常见注意事项**：
- `depends_on` 只保证启动顺序，不保证服务就绪。如需等数据库就绪，用 `healthcheck` + `depends_on: condition: service_healthy`。
- `docker compose down` 默认不删卷，加 `-v` 才删卷，数据库数据会丢失。
- 修改代码后需 `--build` 重新构建镜像，否则用的是旧镜像。
- compose 文件名默认 `docker-compose.yml`，可用 `-f` 指定其他文件。

## 第 14 讲：docker-compose.yml 详解

### 概念

本讲系统讲解 `docker-compose.yml` 的完整语法。Compose 文件遵循 YAML 规范，顶层有四个核心键：`services`（服务定义）、`networks`（网络定义）、`volumes`（卷定义）、`configs`/`secrets`（配置与密钥，Swarm 模式）。掌握这些配置项，才能编写出生产级的 compose 文件。

### 原理

**Compose 文件版本**：早期 compose 文件需在顶部声明 `version: '3.8'` 等版本号。从 Compose Specification（统一规范）开始，`version` 字段已废弃，现代 compose 文件无需声明版本。本课程遵循最新规范，不写 version 字段。

**服务配置项分类**：

| 类别 | 配置项 | 作用 |
|------|--------|------|
| 镜像 | `image`、`build`、`pull_policy` | 镜像来源 |
| 网络 | `networks`、`ports`、`expose`、`hostname` | 网络配置 |
| 存储 | `volumes`、`tmpfs` | 数据挂载 |
| 环境 | `environment`、`env_file` | 环境变量 |
| 依赖 | `depends_on` | 服务依赖 |
| 资源 | `deploy.resources` | CPU/内存限制 |
| 运行 | `restart`、`user`、`working_dir`、`entrypoint`、`command` | 运行配置 |
| 健康 | `healthcheck` | 健康检查 |
| 日志 | `logging` | 日志配置 |

### 例子

**1. 完整配置示例（生产级 Web 应用）：**

```yaml
services:
  web:
    image: myapp:${TAG:-latest}        # 用环境变量，默认 latest
    build:
      context: ./app                   # 构建上下文
      dockerfile: Dockerfile.prod      # 指定 Dockerfile
      args:                            # 构建参数
        - BUILD_ENV=production
      target: production               # 多阶段构建的目标阶段
    container_name: myapp-web          # 固定容器名（不加项目前缀）
    hostname: web-server               # 容器内主机名
    ports:
      - "80:80"
      - "443:443"
      - "127.0.0.1:8080:8080"          # 只监听本地
    expose:
      - "9000"                         # 仅对同一网络的服务暴露
    environment:
      - DB_HOST=db                     # 直接写键值对
      - DB_PORT=5432
      - DEBUG=false
      - SECRET_KEY=${SECRET_KEY}       # 从宿主机环境变量读取
    env_file:
      - .env                           # 从文件批量读取
    volumes:
      - ./app:/app                     # bind mount
      - app-logs:/var/log/app          # named volume
      - /etc/timezone:/etc/timezone:ro # 只读挂载
    networks:
      - frontend
      - backend
    depends_on:
      db:
        condition: service_healthy     # 等 db 健康检查通过
      redis:
        condition: service_started
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5000/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
    deploy:
      resources:
        limits:
          cpus: '2'
          memory: 2g
        reservations:
          memory: 1g
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
    user: "1000:1000"                  # 以非 root 运行
    working_dir: /app
    entrypoint: ["/app/entrypoint.sh"]
    command: ["python", "app.py"]      # 覆盖 CMD

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - backend
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser -d myapp"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    command: redis-server --maxmemory 256mb --maxmemory-policy allkeys-lru
    networks:
      - backend
    restart: unless-stopped

networks:
  frontend:                            # 默认 bridge
  backend:
    internal: true                     # 内部网络，不暴露到外部

volumes:
  db-data:
    driver: local
  app-logs:
```

**2. 环境变量与 .env 文件：**

```bash
# .env 文件（与 docker-compose.yml 同目录）
TAG=2.1.0
DB_PASSWORD=supersecret
SECRET_KEY=abc123xyz
```

```yaml
# docker-compose.yml 中引用
services:
  web:
    image: myapp:${TAG}                # 使用 .env 中的 TAG
    environment:
      - DB_PASSWORD=${DB_PASSWORD}     # 传递给容器
```

变量优先级：宿主机 shell 环境变量 > `.env` 文件 > compose 文件默认值。

**3. 多环境配置（override 机制）：**

```yaml
# docker-compose.yml（基础配置）
services:
  web:
    image: myapp:latest
    environment:
      - DEBUG=false
```

```yaml
# docker-compose.override.yml（开发覆盖，自动加载）
services:
  web:
    build: .                           # 开发用本地构建
    volumes:
      - ./app:/app                     # 热重载
    environment:
      - DEBUG=true
    ports:
      - "5000:5000"
```

```yaml
# docker-compose.prod.yml（生产覆盖，需 -f 指定）
services:
  web:
    image: registry.com/myapp:${TAG}
    environment:
      - DEBUG=false
    deploy:
      replicas: 3
```

```bash
# 开发环境（自动合并 base + override）
docker compose up

# 生产环境（显式指定）
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

**4. profiles（按需启动服务）：**

```yaml
services:
  web:
    image: myapp
    # 无 profiles，默认启动

  db:
    image: postgres
    profiles: ["full"]                 # 只在 full profile 启动

  debug:
    image: busybox
    profiles: ["debug"]                # 只在 debug profile 启动
```

```bash
# 只启动默认服务（web）
docker compose up

# 启动 full profile（web + db）
docker compose --profile full up

# 启动 debug profile
docker compose --profile debug up
```

### 总结

本讲核心要点：

1. **四大顶层键**：`services`、`networks`、`volumes`、`configs/secrets`。
2. **环境变量**：`${VAR}` 语法，优先级 shell > `.env` > 默认值。
3. **override 机制**：`docker-compose.override.yml` 自动合并，适合开发/生产分离。
4. **profiles**：按需启动服务，避免开发时启动不必要的服务。
5. **healthcheck + depends_on**：实现真正的服务就绪等待。

**常见注意事项**：
- `container_name` 固定容器名会导致无法水平扩展（同名冲突），生产慎用。
- `internal: true` 的网络完全隔离，外部无法访问，适合数据库等内部服务。
- `deploy` 字段在 `docker compose up` 中只有 `resources` 生效，`replicas` 等需 Swarm 模式。
- `.env` 文件不要提交到 Git，应加入 `.gitignore`，提供 `.env.example` 作为模板。

## 第 15 讲：Compose 实战 —— 部署 Web 应用栈

### 概念

本讲通过一个完整的实战案例，综合运用前两讲的知识，部署一个真实的多服务 Web 应用栈。我们将部署一个博客系统（WordPress + MySQL + Nginx 反向代理 + Redis 缓存），涵盖实际项目中的典型架构模式：反向代理、数据库、缓存、数据持久化、健康检查、网络隔离。

### 原理

**典型 Web 应用栈架构**：

```
                    ┌─────────────┐
   用户 ──────────→ │   Nginx     │ (反向代理 + SSL)
                    │   :80/:443  │
                    └──────┬──────┘
                           │
                    ┌──────┴──────┐
                    │             │
              ┌─────┴─────┐ ┌─────┴─────┐
              │ WordPress │ │  静态资源  │
              │   (PHP)   │ │  (Nginx)  │
              └─────┬─────┘ └───────────┘
                    │
         ┌──────────┼──────────┐
         │          │          │
   ┌─────┴─────┐ ┌──┴───┐ ┌────┴─────┐
   │   MySQL   │ │Redis │ │  其他    │
   │  (数据)   │ │(缓存) │ │ (服务)   │
   └───────────┘ └──────┘ └──────────┘
```

**网络分层设计**：
- **frontend 网络**：Nginx 与外部通信，暴露 80/443 端口。
- **backend 网络**：应用服务器与数据库、缓存通信，不对外暴露。
- Nginx 同时连接 frontend 和 backend，作为网关。

**数据持久化设计**：
- MySQL 数据：命名卷 `mysql-data`，独立于容器生命周期。
- WordPress 文件（上传的图片等）：命名卷 `wp-content`。
- Nginx 日志：bind mount 到宿主机，方便采集。

### 例子

**项目结构：**

```
blog-stack/
├── docker-compose.yml
├── .env
├── nginx/
│   └── nginx.conf
└── wordpress/
    └── wp-config.php
```

**`.env` 文件：**

```bash
# 数据库配置
MYSQL_ROOT_PASSWORD=rootpass123
MYSQL_DATABASE=wordpress
MYSQL_USER=wpuser
MYSQL_PASSWORD=wppass123

# WordPress 配
WORDPRESS_DB_HOST=db:3306
WORDPRESS_DB_USER=wpuser
WORDPRESS_DB_PASSWORD=wppass123
WORDPRESS_DB_NAME=wordpress

# 版本
MYSQL_VERSION=8.0
WP_VERSION=6.4-php8.2
REDIS_VERSION=7-alpine
```

**`nginx/nginx.conf`：**

```nginx
upstream wordpress {
    server wordpress:80;
}

server {
    listen 80;
    server_name localhost;

    # 静态资源直接由 Nginx 处理（如果有静态资源服务）
    location /static/ {
        proxy_pass http://static:80/;
    }

    # 其他请求转发到 WordPress
    location / {
        proxy_pass http://wordpress;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

**`docker-compose.yml`：**

```yaml
services:
  # 反向代理
  nginx:
    image: nginx:1.25-alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - nginx-logs:/var/log/nginx
    networks:
      - frontend
      - backend
    depends_on:
      - wordpress
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "wget", "--spider", "-q", "http://localhost/"]
      interval: 30s
      timeout: 5s
      retries: 3

  # WordPress 应用
  wordpress:
    image: wordpress:${WP_VERSION}
    environment:
      WORDPRESS_DB_HOST: ${WORDPRESS_DB_HOST}
      WORDPRESS_DB_USER: ${WORDPRESS_DB_USER}
      WORDPRESS_DB_PASSWORD: ${WORDPRESS_DB_PASSWORD}
      WORDPRESS_DB_NAME: ${WORDPRESS_DB_NAME}
      REDIS_HOST: redis
    volumes:
      - wp-content:/var/www/html/wp-content
    networks:
      - backend
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started
    restart: unless-stopped
    deploy:
      resources:
        limits:
          memory: 512m

  # MySQL 数据库
  db:
    image: mysql:${MYSQL_VERSION}
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
      MYSQL_DATABASE: ${MYSQL_DATABASE}
      MYSQL_USER: ${MYSQL_USER}
      MYSQL_PASSWORD: ${MYSQL_PASSWORD}
    volumes:
      - mysql-data:/var/lib/mysql
    networks:
      - backend
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h localhost -u root -p${MYSQL_ROOT_PASSWORD}"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    deploy:
      resources:
        limits:
          memory: 1g

  # Redis 缓存
  redis:
    image: redis:${REDIS_VERSION}
    command: redis-server --maxmemory 128mb --maxmemory-policy allkeys-lru
    networks:
      - backend
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 3

networks:
  frontend:
    name: blog-frontend
  backend:
    name: blog-backend
    internal: true    # 内部网络，不暴露到外部

volumes:
  mysql-data:
    name: blog-mysql-data
  wp-content:
    name: blog-wp-content
  nginx-logs:
    name: blog-nginx-logs
```

**部署与运维命令：**

```bash
# 1. 首次部署：构建并启动
cd blog-stack
docker compose up -d

# 2. 查看所有服务状态
docker compose ps
# NAME                STATUS                   PORTS
# blog-nginx-1        Up (healthy)             0.0.0.0:80->80/tcp
# blog-wordpress-1    Up (healthy)             80/tcp
# blog-db-1           Up (healthy)             3306/tcp
# blog-redis-1        Up (healthy)             6379/tcp

# 3. 查看实时日志
docker compose logs -f
docker compose logs -f nginx
docker compose logs -f wordpress db

# 4. 访问应用
curl http://localhost
# 或浏览器打开 http://localhost，进入 WordPress 安装向导

# 5. 进入容器调试
docker compose exec wordpress bash
docker compose exec db mysql -u root -p

# 6. 更新某个服务（如 WordPress 升级版本）
# 修改 .env 中 WP_VERSION=6.5-php8.2
docker compose up -d wordpress    # 只重建 wordpress

# 7. 扩展服务（启动多个 WordPress 实例）
docker compose up -d --scale wordpress=3
# 注意：需要配合负载均衡，且 wp-content 要共享存储

# 8. 备份数据库
docker compose exec db mysqldump -u root -p${MYSQL_ROOT_PASSWORD} wordpress > backup.sql

# 9. 恢复数据库
cat backup.sql | docker compose exec -T db mysql -u root -p${MYSQL_ROOT_PASSWORD} wordpress

# 10. 停止服务（保留数据）
docker compose stop

# 11. 完全销毁（保留卷）
docker compose down

# 12. 完全销毁（含数据，慎用！）
docker compose down -v

# 13. 查看资源使用
docker compose stats

# 14. 查看服务配置
docker compose config
```

### 总结

本讲核心要点：

1. **网络分层**：frontend（对外）+ backend（内部，`internal: true`），Nginx 作网关连接两层。
2. **健康检查 + depends_on**：`condition: service_healthy` 实现真正的就绪等待，避免应用启动时数据库未就绪。
3. **数据持久化**：数据库、用户上传文件用命名卷，日志用 bind mount 方便采集。
4. **环境变量管理**：`.env` 文件集中管理配置，不提交 Git。
5. **运维命令**：`up/down/logs/exec/stats/config` 是日常运维六大命令。

**常见注意事项**：
- `--scale` 水平扩展时，有状态服务（如 MySQL）不能扩展，无状态服务（如 WordPress）可以。
- 数据库备份要定期做，`docker compose down -v` 会永久删除卷数据。
- 生产环境 WordPress 应配合 Redis 缓存插件，否则 Redis 不生效。
- Nginx 配置变更后需 `docker compose restart nginx` 或 `nginx -s reload`。
- `internal: true` 网络中的容器无法访问外网，数据库等内部服务用此配置提升安全性。

## 第 16 讲：Docker 网络进阶 —— 自定义网络与服务发现

### 概念

第 11 讲介绍了网络基础，本讲深入网络进阶主题：自定义网络的高级配置、服务发现机制、跨主机通信（overlay）、容器与外部服务的网络互通。这些知识在复杂生产架构中至关重要。

**本讲核心概念**：
- **自定义网络的 DNS 服务发现**：容器间通过服务名互相访问的底层机制。
- **网络别名（Network Alias）**：为一个容器在网络中配置多个主机名。
- **overlay 网络**：跨多台宿主机的容器通信，基于 VXLAN 隧道。
- **macvlan 网络**：容器获得物理网络中的独立 MAC 地址和 IP。
- **IPv6 支持**：为容器分配 IPv6 地址。

### 原理

**DNS 服务发现的底层机制**：Docker 在每个自定义 bridge 网络中内置一个 DNS 服务器（监听 127.0.0.11）。容器启动时，其 `/etc/resolv.conf` 的 nameserver 被设置为 127.0.0.11。当容器解析主机名时，请求发往该 DNS 服务器，Docker 查询内部映射表（容器名 → IP），返回对应容器的 IP。

这个机制的关键特性：
1. **容器名即主机名**：`docker run --name db` 的容器，在网络中可通过 `db` 解析。
2. **网络别名**：可为一个容器配置多个别名，如 `docker run --network-alias database --network-alias mysql`。
3. **服务发现是动态的**：容器加入/离开网络时，DNS 记录自动更新。
4. **负载均衡**：当多个容器使用相同别名时，DNS 查询会轮询返回不同 IP（Docker 内置 DNS round-robin）。

**overlay 网络原理**：overlay 网络使用 VXLAN（Virtual eXtensible LAN）技术，在物理网络之上构建虚拟二层网络。不同宿主机上的容器，通过 VXLAN 隧道通信，仿佛在同一局域网。这需要 Docker Swarm 模式（或独立的键值存储如 Consul）来维护网络状态。

```
┌─────────────────┐          ┌─────────────────┐
│    宿主机 A      │          │    宿主机 B      │
│                 │          │                 │
│  ┌───────────┐  │  VXLAN   │  ┌───────────┐  │
│  │ 容器 A     │──┼──隧道────┼──│ 容器 B     │  │
│  │10.0.0.2   │  │          │  │10.0.0.3   │  │
│  └───────────┘  │          │  └───────────┘  │
│        │        │          │        │        │
│   ┌────┴────┐   │          │   ┌────┴────┐   │
│   │ overlay │   │          │   │ overlay │   │
│   │  网桥    │   │          │   │  网桥    │   │
│   └────┬────┘   │          │   └────┬────┘   │
│        │        │          │        │        │
│   ┌────┴────┐   │          │   ┌────┴────┐   │
│   │  eth0   │───┼──────────┼───│  eth0   │   │
│   └─────────┘   │  物理网络  │   └─────────┘   │
└─────────────────┘          └─────────────────┘
```

**macvlan 原理**：macvlan 是 Linux 内核驱动，允许为一个物理网卡分配多个 MAC 地址，每个 MAC 对应一个虚拟接口。容器直接使用这些虚拟接口，获得物理网络中的独立 IP，对网络中的其他设备而言就像独立主机。性能接近物理机，但需要网卡支持混杂模式，且会消耗 IP 地址。

### 例子

**1. 网络别名与服务发现：**

```bash
# 创建网络
docker network create appnet

# 启动数据库容器，配置多个别名
docker run -d --name db \
  --network appnet \
  --network-alias database \
  --network-alias mysql \
  mysql:8

# 启动应用，用任一别名都能访问
docker run -d --name app1 --network appnet myapp
docker exec app1 ping -c 2 db         # 用容器名
docker exec app1 ping -c 2 database   # 用别名
docker exec app1 ping -c 2 mysql      # 用另一个别名
```

**2. DNS 负载均衡（多容器同别名）：**

```bash
# 启动 3 个 web 容器，使用相同别名
docker run -d --name web1 --network appnet --network-alias web nginx:alpine
docker run -d --name web2 --network appnet --network-alias web nginx:alpine
docker run -d --name web3 --network appnet --network-alias web nginx:alpine

# 用客户端解析 web，会轮询返回不同 IP
docker run --rm --network appnet alpine sh -c 'for i in 1 2 3 4 5 6; do nslookup web | grep Address | tail -1; done'
# Address: 172.18.0.2
# Address: 172.18.0.3
# Address: 172.18.0.4
# Address: 172.18.0.2
# Address: 172.18.0.3
# Address: 172.18.0.4
```

**3. 自定义网络配置（子网、网关、IP 范围）：**

```bash
# 创建指定子网和网关的网络
docker network create \
  --subnet=192.168.100.0/24 \
  --gateway=192.168.100.1 \
  --ip-range=192.168.100.128/25 \
  custom-net

# 为容器指定静态 IP
docker run -d --name web --network custom-net --ip 192.168.100.10 nginx:alpine

# 启用 IPv6
docker network create --ipv6 --subnet=2001:db8::/64 ipv6net
```

**4. 容器访问宿主机服务：**

```bash
# 方式 1：使用 host.docker.internal（Docker Desktop 内置，Linux 需额外配置）
docker run --rm alpine ping host.docker.internal

# 方式 2：Linux 下用宿主机网关 IP
docker run --rm alpine sh -c 'ip route | grep default'  # 查看网关
# default via 172.17.0.1 dev eth0
docker run --rm alpine ping 172.17.0.1

# 方式 3：用 host 网络模式（不推荐，失去隔离）
docker run --rm --network host alpine ping localhost
```

**5. 外部服务访问容器（除端口映射外的方案）：**

```bash
# 方案：用 host 网络的 Nginx 反向代理
docker run -d --network host nginx:alpine
# Nginx 配置中直接 proxy_pass http://172.18.0.2:80
```

**6. overlay 网络（需 Swarm 模式）：**

```bash
# 初始化 Swarm
docker swarm init

# 创建 overlay 网络
docker network create --driver overlay --attachable my-overlay

# 在不同节点启动容器，加入同一 overlay 网络
# 节点 A
docker run -d --name app --network my-overlay nginx:alpine
# 节点 B
docker run -d --name db --network my-overlay mysql:8
# 两容器可跨主机通过容器名通信
```

**7. macvlan 网络（容器获得物理 IP）：**

```bash
# 创建 macvlan 网络
# eth0 是宿主机物理网卡，192.168.1.0/24 是物理网络子网
docker network create -d macvlan \
  --subnet=192.168.1.0/24 \
  --gateway=192.168.1.1 \
  -o parent=eth0 \
  macnet

# 启动容器，分配物理网络 IP
docker run -d --name web --network macnet --ip 192.168.1.100 nginx:alpine

# 此时 192.168.1.100 是物理网络中的独立设备
# 其他设备可直接访问 http://192.168.1.100
```

**注意**：macvlan 模式下，宿主机和容器默认无法通信（出于安全），需在宿主机创建 macvlan 接口才能互通。

### 总结

本讲核心要点：

1. **自定义网络内置 DNS**：容器名即主机名，是服务发现的基础。
2. **网络别名**：一个容器可有多个主机名，多容器同别名实现 DNS 负载均衡。
3. **overlay 网络**：基于 VXLAN 跨主机通信，需 Swarm 模式。
4. **macvlan 网络**：容器获物理 IP，性能最优但配置复杂。
5. **host.docker.internal**：容器访问宿主机服务的便捷方式（Linux 需 `--add-host`）。

**常见注意事项**：
- 默认 bridge 网络无 DNS，生产必须用自定义网络。
- macvlan 会消耗物理网络 IP，且宿主机与容器默认不互通，慎用。
- overlay 网络的容器跨主机通信有 VXLAN 封装开销，性能略低于 bridge。
- DNS 负载均衡是 round-robin，不感知容器健康状态，故障容器仍会被解析。

## 第 17 讲：Dockerfile 最佳实践

### 概念

第 7、8 讲讲解了 Dockerfile 的指令和优化原理，本讲从工程实践角度系统总结生产级 Dockerfile 的最佳实践。这些经验来自大量生产环境的沉淀，能帮助您写出安全、高效、可维护的 Dockerfile。

**最佳实践的六大维度**：
1. **安全性**：非 root 运行、最小权限、不泄露密钥。
2. **镜像体积**：小基础镜像、多阶段构建、清理缓存。
3. **构建速度**：缓存优化、BuildKit 特性。
4. **可维护性**：清晰的注释、合理的指令顺序。
5. **可复现性**：固定版本、不依赖外部状态。
6. **运行时友好**：优雅退出、日志输出、健康检查。

### 原理

**安全最佳实践的原理**：
- **非 root 运行**：容器内 root 虽然受 namespace 隔离，但一旦容器逃逸（如 CVE），攻击者获得宿主机 root。用非 root 用户运行，即使逃逸也只获得普通权限。
- **最小基础镜像**：镜像中的每个二进制都是潜在攻击面。distroless 镜像连 shell 都没有，攻击者即使入侵也无法执行命令。
- **密钥不进镜像**：镜像可能被推送到公共仓库，构建时的密钥若留在层中，即使后续删除也可通过 `docker history` 恢复。用 BuildKit 的 `--mount=type=secret` 安全传递。

**可复现性原理**：
- `apt-get install nginx` 不指定版本，今天和明天安装的可能不同（仓库更新）。固定版本 `apt-get install nginx=1.25.3-1` 保证复现。
- 基础镜像用 digest 而非 tag：`nginx@sha256:abc...` 比 `nginx:1.25` 更精确，tag 可能被覆盖，digest 不可变。

### 例子

**1. 生产级 Python 应用 Dockerfile：**

```dockerfile
# syntax=docker/dockerfile:1.6

# ===== 构建阶段 =====
FROM python:3.11-slim AS builder

# 安装构建依赖（编译 C 扩展用）
RUN apt-get update \
    && apt-get install -y --no-install-recommends gcc libpq-dev \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app

# 创建虚拟环境（隔离依赖）
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

# 安装依赖（利用缓存）
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# ===== 运行阶段 =====
FROM python:3.11-slim AS runtime

# 只安装运行时依赖（无 gcc 等编译工具）
RUN apt-get update \
    && apt-get install -y --no-install-recommends libpq5 curl \
    && rm -rf /var/lib/apt/lists/* \
    && groupadd -r appuser && useradd -r -g appuser appuser

# 从构建阶段复制虚拟环境
COPY --from=builder --chown=appuser:appuser /opt/venv /opt/venv

WORKDIR /app
ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

# 复制应用代码
COPY --chown=appuser:appuser . .

# 切换非 root 用户
USER appuser

# 健康检查
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
    CMD curl -f http://localhost:5000/health || exit 1

EXPOSE 5000
CMD ["gunicorn", "--bind", "0.0.0.0:5000", "--workers", "4", "app:app"]
```

**2. 生产级 Node.js 应用 Dockerfile：**

```dockerfile
# syntax=docker/dockerfile:1.6

FROM node:20-alpine AS builder
WORKDIR /app

# 利用缓存：先复制 package 文件
COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build

# ===== 运行阶段 =====
FROM node:20-alpine AS runtime

# 安装 dumb-init（正确处理信号）
RUN apk add --no-cache dumb-init curl \
    && addgroup -g 1001 nodejs \
    && adduser -S -u 1001 -G nodejs nextjs

WORKDIR /app

# 只复制构建产物和必要文件
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static
COPY --from=builder --chown=nextjs:nodejs /app/public ./public

USER nextjs

HEALTHCHECK --interval=30s CMD curl -f http://localhost:3000/ || exit 1

EXPOSE 3000
# dumb-init 作为 PID 1，正确转发信号
ENTRYPOINT ["dumb-init", "--"]
CMD ["node", "server.js"]
```

**3. 安全传递密钥（BuildKit secret）：**

```dockerfile
# syntax=docker/dockerfile:1.6
FROM node:20-alpine

# 私有 npm 包需要认证
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci
```

```bash
# 构建时传递密钥（不会留在镜像层）
docker build --secret id=npmrc,src=$HOME/.npmrc -t myapp .
```

**4. 使用 .dockerignore（必备）：**

```
# .dockerignore
# 版本控制
.git
.gitignore

# 依赖目录（容器内重新安装）
node_modules
__pycache__
*.pyc
.venv
venv

# 环境配置（含密钥）
.env
.env.local

# IDE 配置
.vscode
.idea

# 文档和测试
*.md
docs/
tests/
coverage/

# 构建产物
dist/
build/
.next/

# 系统文件
.DS_Store
Thumbs.db
```

**5. 固定版本与 digest：**

```dockerfile
# ❌ 不好：latest 标签会变
FROM nginx:latest

# ✅ 好：固定版本
FROM nginx:1.25.3-alpine

# ✅✅ 最好：digest 不可变
FROM nginx@sha256:6af79ae5de407283dcea8b00d5c37ac42b9c6b3d7c0de7c47b2c2b5d8c2d7a1f
```

**6. 合并 RUN 命令的典型模式：**

```dockerfile
# Ubuntu/Debian 模式
RUN apt-get update \
    && apt-get install -y --no-install-recommends \
        package1=1.0.0 \
        package2=2.0.0 \
    && rm -rf /var/lib/apt/lists/*

# Alpine 模式
RUN apk add --no-cache \
        package1=1.0.0-r0 \
        package2=2.0.0-r0

# CentOS/RHEL 模式
RUN yum install -y \
        package1-1.0.0 \
        package2-2.0.0 \
    && yum clean all \
    && rm -rf /var/cache/yum
```

### 总结

本讲核心要点：

1. **安全六原则**：非 root 运行、最小基础镜像、密钥用 secret、固定版本、最小权限、健康检查。
2. **多阶段构建是标配**：构建阶段含编译工具，运行阶段只含运行时。
3. **缓存优化**：依赖文件单独 COPY，代码变化不触发重新安装。
4. **`.dockerignore` 必备**：排除无关文件，加速构建、避免泄露。
5. **digest > tag > latest**：生产环境用 digest 保证不可变。

**常见注意事项**：
- `USER` 指令后的所有操作都以该用户身份执行，确保文件权限正确（用 `COPY --chown`）。
- 容器主进程必须是 PID 1，用 `dumb-init` 或 `tini` 作为 init 进程，正确处理信号和僵尸进程。
- `PYTHONUNBUFFERED=1` 让 Python 日志实时输出，不缓冲，方便 `docker logs` 查看。
- gunicorn/uwsgi 等 WSGI 服务器比 `flask run` 更适合生产，支持多 worker 和优雅重启。

## 第 18 讲：Docker 安全与镜像扫描

### 概念

容器安全是生产环境不可忽视的主题。一个含已知漏洞的镜像被部署到生产，可能成为攻击入口。本讲系统讲解 Docker 安全的各个方面：镜像漏洞扫描、容器运行时安全、镜像签名验证、权限最小化。

**Docker 安全的四个层面**：
1. **镜像安全**：基础镜像漏洞、镜像中的恶意软件、镜像来源可信。
2. **构建安全**：密钥泄露、构建工具残留、不安全的构建指令。
3. **运行时安全**：容器权限、能力（capabilities）、系统调用过滤。
4. **分发安全**：镜像签名、传输加密、访问控制。

### 原理

**镜像漏洞扫描原理**：扫描工具维护一个漏洞数据库（CVE 数据库），包含每个已知漏洞影响的软件包及版本范围。扫描时，工具解析镜像的每一层，提取已安装的软件包及其版本，与漏洞数据库比对，报告匹配的漏洞。常见工具：Trivy、Grype、Clair、Snyk。

**容器能力（Capabilities）原理**：Linux 将 root 权限拆分为约 40 种细粒度能力，如 `CAP_NET_BIND_SERVICE`（绑定 1024 以下端口）、`CAP_SYS_ADMIN`（系统管理）。Docker 默认只赋予容器 14 种能力，移除了危险能力。可通过 `--cap-add`/`--cap-drop` 精确调整。

**Seccomp 原理**：Secure Computing Mode 是 Linux 内核的安全机制，可过滤进程能调用的系统调用。Docker 默认的 seccomp profile 阻止了约 44 个危险系统调用（如 `keyctl`、`mount`），防止容器利用内核漏洞。

**镜像签名原理**：Docker Content Trust（DCT）基于 Notary 项目，使用 PKI 对镜像签名。推送镜像时用私钥签名，拉取时用公钥验证。如果镜像被篡改，签名验证失败，拒绝拉取。

### 例子

**1. 使用 Trivy 扫描镜像漏洞：**

```bash
# 安装 Trivy
curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sh

# 扫描镜像
trivy image nginx:1.25-alpine

# 只显示 HIGH 和 CRITICAL 漏洞
trivy image --severity HIGH,CRITICAL nginx:1.25-alpine

# 输出 JSON 格式（CI/CD 集成）
```

## 第 19 讲：CI/CD 中的 Docker 应用

### 概念

Docker 是现代 CI/CD 流水线的核心组件。从代码提交到生产部署，Docker 贯穿构建、测试、分发、部署全流程。本讲讲解 Docker 在 CI/CD 中的典型应用模式：镜像构建自动化、多架构构建、镜像仓库管理、滚动部署。

**CI/CD 中 Docker 的核心场景**：
1. **构建镜像**：代码提交后自动构建镜像，打上版本标签。
2. **多架构构建**：一份代码构建 amd64/arm64 多架构镜像。
3. **推送仓库**：构建后推送到私有/公共镜像仓库。
4. **部署**：在目标环境拉取新镜像，重启容器。
5. **回滚**：快速回退到上一版本镜像。

### 原理

**多架构构建原理**：传统方式需在不同架构的机器上分别构建，或用 QEMU 模拟。Docker Buildx 引入 `--platform` 参数，结合 QEMU 用户态模拟，可在单机上构建多架构镜像，并推送到仓库的 manifest list 中。拉取时，Docker 根据宿主机架构自动选择对应镜像。

**镜像标签策略**：
- `latest`：永远指向最新版本（开发环境用）。
- `git-sha`：如 `abc1234`，每次提交唯一，可追溯。
- `semver`：如 `v1.2.3`，正式发布版本。
- `branch-name`：如 `feature-login`，分支构建。

**蓝绿部署与滚动部署**：
- **蓝绿部署**：同时运行新旧两套环境，切换流量。Docker 中用两套 compose 项目，Nginx 切换 upstream。
- **滚动部署**：逐个替换容器。Docker Compose 用 `docker compose up -d --no-deps --build web` 逐个重建。

### 例子

**1. 多架构镜像构建（Buildx）：**

```bash

# 构建并推送多架构镜像（amd64 + arm64）
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t myregistry.com/myapp:v1.0.0 \
  --push \
  .

# 查看多架构 manifest
docker buildx imagetools inspect myregistry.com/myapp:v1.0.0
```

**2. 完整的 GitHub Actions CI/CD 流水线：**

```yaml
# .github/workflows/cicd.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
    tags: ['v*']
  pull_request:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # 任务 1：测试
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Run tests in Docker
        run: |
          docker build -t test-image --target test .
          docker run --rm test-image pytest
      
      - name: Security scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: test-image
          severity: CRITICAL,HIGH
          exit-code: '1'

  # 任务 2：构建并推送镜像
  build-and-push:
    needs: test
    runs-on: ubuntu-latest
    if: github.event_name != 'pull_request'
    permissions:
      contents: read
      packages: write
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3
      
      - name: Login to Registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      
      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=ref,event=branch           # 分支名
            type=ref,event=pr               # PR 编号
            type=semver,pattern={{version}} # v1.2.3 -> 1.2.3
            type=sha,prefix={{branch}}-     # 分支名-commitsha
            type=raw,value=latest,enable={{is_default_branch}}
      
      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha            # GitHub Actions 缓存
          cache-to: type=gha,mode=max

  # 任务 3：部署到生产
  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    if: startsWith(github.ref, 'refs/tags/v')
    environment: production
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Deploy to production
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.PROD_HOST }}
          username: ${{ secrets.PROD_USER }}
          key: ${{ secrets.PROD_SSH_KEY }}
          script: |
            cd /opt/myapp
            export IMAGE_TAG=${{ github.ref_name }}
            docker compose pull
            docker compose up -d --no-deps --build web
            docker image prune -f
            # 健康检查
            sleep 10
            curl -f http://localhost:5000/health || docker compose rollback
```

**4. 滚动部署脚本：**

```bash
#!/bin/bash
# deploy.sh - 滚动部署脚本

set -e

IMAGE_TAG=$1
SERVICE_NAME=${2:-web}

echo "Deploying $SERVICE_NAME with image tag $IMAGE_TAG"

# 拉取新镜像
docker compose pull $SERVICE_NAME

# 备份当前镜像标签（用于回滚）
docker inspect $SERVICE_NAME --format '{{.Config.Image}}' > /tmp/last-image.txt

# 滚动更新（--no-deps 不影响依赖服务）
docker compose up -d --no-deps $SERVICE_NAME

# 健康检查
echo "Waiting for health check..."
for i in $(seq 1 30); do
    STATUS=$(docker inspect $SERVICE_NAME --format '{{.State.Health.Status}}')
    if [ "$STATUS" = "healthy" ]; then
        echo "Deployment successful!"
        exit 0
    fi
    sleep 2
done

echo "Health check failed, rolling back..."
LAST_IMAGE=$(cat /tmp/last-image.txt)
docker tag $LAST_IMAGE $SERVICE_NAME:rollback
docker compose up -d --no-deps $SERVICE_NAME
echo "Rollback complete"
exit 1
```

3. **CI/CD 流水线**：test → build → scan → push → deploy，每步可阻断。
4. **滚动部署**：`docker compose up -d --no-deps` 逐个替换，配合健康检查自动回滚。
5. **私有仓库**：Harbor 等提供镜像管理、漏洞扫描、权限控制。

## 第 20 讲：从 Docker 到 Kubernetes

### 概念

Docker 解决了单机容器管理问题，但当应用规模扩大到多台服务器、需要高可用、自动扩缩容、滚动发布时，Docker（含 Docker Compose/Swarm）就显得力不从心。**Kubernetes（K8s）** 是容器编排的事实标准，本讲讲解 Docker 与 Kubernetes 的关系、如何从 Docker 平滑过渡到 K8s，以及两者的对比。

**Kubernetes 的核心价值**：
1. **集群管理**：管理多台节点上的容器调度。
2. **自愈能力**：容器崩溃自动重启、节点故障自动迁移。
3. **自动扩缩容**：根据负载自动增减副本数。
4. **服务发现与负载均衡**：内置服务发现，自动负载均衡。
5. **滚动更新与回滚**：零停机部署，一键回滚。
6. **声明式 API**：用 YAML 描述期望状态，K8s 持续调和到该状态。

### 原理

**Docker 与 Kubernetes 的关系**：

```
┌─────────────────────────────────────────┐
│           Kubernetes (编排层)            │
│   调度、自愈、扩缩容、服务发现、滚动更新   │
├─────────────────────────────────────────┤
│         containerd (容器运行时)          │
│   镜像管理、容器生命周期                  │
├─────────────────────────────────────────┤
│            runc (OCI 运行时)             │
│   实际创建和运行容器                      │
├─────────────────────────────────────────┤
│         Linux Kernel (namespace/cgroup)  │
└─────────────────────────────────────────┘
```

Docker 本身包含 dockerd + containerd + runc。Kubernetes 不直接用 Docker，而是通过 **CRI（Container Runtime Interface）** 标准接口调用 containerd（或其他符合 CRI 的运行时如 CRI-O）。从 K8s 1.24 开始，已移除对 Docker 的直接支持（dockershim），但用 Docker 构建的镜像仍可在 K8s 上运行（因为镜像遵循 OCI 标准）。

**Docker Compose 与 Kubernetes 的对应关系**：

| Docker Compose | Kubernetes | 说明 |
|----------------|------------|------|
| Service | Deployment + Service | 容器组 + 网络入口 |
| Container | Pod | K8s 最小调度单位，可含多容器 |
| Volume | PersistentVolume + Claim | 持久化存储 |
| Network | Service + Ingress | 服务发现与入口 |
| depends_on | initContainer / readinessProbe | 启动顺序与就绪检测 |
| docker compose up | kubectl apply | 部署 |
| docker compose down | kubectl delete | 销毁 |

**K8s 的核心概念**：
- **Pod**：最小调度单位，包含一个或多个共享网络和存储的容器。
- **Deployment**：管理 Pod 副本，支持滚动更新和回滚。
- **Service**：为一组 Pod 提供固定网络入口和负载均衡。
- **Ingress**：HTTP 层路由，将外部流量路由到 Service。
- **ConfigMap/Secret**：配置和密钥管理。
- **PersistentVolume**：持久化存储。

### 例子

**1. 从 docker-compose.yml 到 Kubernetes Manifest：**

原始 `docker-compose.yml`：
```yaml
services:
  web:
    image: myapp:v1
    ports:
      - "80:5000"
    environment:
      - DB_HOST=db
    replicas: 3
  
  db:
    image: postgres:16
    volumes:
      - db-data:/var/lib/postgresql/data

      - POSTGRES_PASSWORD=secret
```

```yaml
      app: web

      labels:
        app: web

      containers:
      - name: web
        image: myapp:v1

        - containerPort: 5000

        - name: DB_HOST
          value: db                    # 通过 Service 名访问

          limits:
            memory: "512Mi"
            cpu: "500m"

            path: /health
            port: 5000

          periodSeconds: 10

  name: web

  type: LoadBalancer                   # 对外暴露

  - port: 80
    targetPort: 5000
  selector:
    app: web
```

```bash
# web-65c8b7b7-ghi56    1/1     Running   0          1m
# db-0                   1/1     Running   0          1m

# 查看服务
kubectl get svc
# NAME         TYPE           CLUSTER-IP      EXTERNAL-IP   PORT(S)
# web          LoadBalancer   10.96.100.1     <pending>     80:30000/TCP
# db           ClusterIP      10.96.100.2     <none>        5432/TCP

# 访问服务（Minikube 特有）
minikube service web

# 查看日志
kubectl logs -f deployment/web

# 进入 Pod
kubectl exec -it web-65c8b7b7-abc12 -- sh

# 滚动更新（更新镜像）
kubectl set image deployment/web web=myapp:v2
kubectl rollout status deployment/web

# 回滚

# 扩缩容

# 清理
kubectl delete -f web.yaml -f db.yaml

```

**4. Docker 与 K8s 命令对照表：**

| 操作 | Docker | Kubernetes |
|------|--------|------------|
| 部署 | `docker compose up -d` | `kubectl apply -f manifest.yaml` |
| 查看状态 | `docker compose ps` | `kubectl get pods` |
| 查看日志 | `docker compose logs -f` | `kubectl logs -f <pod>` |
| 进入容器 | `docker compose exec web sh` | `kubectl exec -it <pod> -- sh` |
| 扩缩容 | `docker compose up --scale web=3` | `kubectl scale deployment web --replicas=3` |
| 更新镜像 | `docker compose up -d --build` | `kubectl set image deployment/web web=myapp:v2` |
| 回滚 | 手动切换镜像 | `kubectl rollout undo deployment/web` |
| 删除 | `docker compose down` | `kubectl delete -f manifest.yaml` |

### 总结

本讲核心要点：

1. **K8s 是编排层，Docker 是构建工具**：K8s 不直接用 Docker，但 Docker 构建的镜像可在 K8s 运行。
2. **概念对应**：Service→Deployment+Service，Volume→PV/PVC，Network→Service+Ingress。
3. **Kompose 工具**：自动将 docker-compose.yml 转为 K8s manifest，适合快速迁移。
4. **Minikube**：本地学习 K8s 的最佳工具，单机模拟完整集群。
5. **何时从 Docker 迁移到 K8s**：多节点、高可用、自动扩缩容、复杂发布策略时。

**常见注意事项**：
- Docker 镜像无需修改即可在 K8s 运行，但需确保容器正确处理 SIGTERM（K8s 滚动更新依赖）。
- K8s 的 Pod 可含多容器（sidecar 模式），但 Compose 的一个 service 对应一个容器，迁移时需调整。
- K8s 学习曲线陡峭，小项目用 Docker Compose 足够，不要盲目上 K8s。
- K8s 的资源限制（resources.limits/requests）对应 Docker 的 `--cpus`/`-m`，但语义更严格。
