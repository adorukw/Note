## 第一章 初识 Nginx

### 第1讲 Nginx 是什么：Web 服务器与反向代理

#### 概念

Nginx（发音为 "Engine-X"）是一款开源的高性能 HTTP 服务器、反向代理服务器及邮件（IMAP/POP3）代理服务器。它由俄罗斯工程师 Igor Sysoev 于 2002 年开发，最初是为了解决 C10K 问题（即一台服务器同时处理一万个客户端连接）而设计的。如今，Nginx 已成为全球使用最广泛的 Web 服务器之一，服务于 Netflix、GitHub、WordPress、百度、淘宝等高流量站点。

要理解 Nginx 的定位，需要区分三个核心概念：

- **Web 服务器**：直接接收 HTTP 请求，返回静态文件（HTML、图片、CSS、JS 等）或通过 FastCGI/SCGI 等协议将动态请求转发给后端程序处理。Nginx、Apache、Lighttpd 都属于此类。
- **正向代理**：客户端知道要访问的目标服务器，但通过代理服务器中转请求。代理代表的是「客户端」，典型场景是翻墙、公司内网上网管控。客户端需要显式配置代理地址。
- **反向代理**：客户端不知道真实后端服务器的存在，只与代理服务器通信。代理代表的是「服务端」，对客户端透明。典型场景是负载均衡、SSL 卸载、缓存加速。

Nginx 同时具备 Web 服务器和反向代理的能力，这是它区别于许多其他服务器的关键特征。

#### 原理

Nginx 之所以能在高并发场景下表现卓越，源于其设计哲学上的几个关键选择：

**1. 事件驱动而非进程/线程驱动**。传统的 Apache 采用「每个连接一个进程或线程」的模型（prefork 或 worker MPM），当并发连接数达到数千时，进程/线程切换的开销和内存占用会成为瓶颈。Nginx 采用事件驱动模型，少量 worker 进程通过 `epoll`（Linux）/ `kqueue`（BSD）系统调用同时管理成千上万的连接，一个 worker 可以处理数百甚至数千个并发请求。

**2. 非阻塞 I/O**。Nginx 的所有 I/O 操作（网络读写、磁盘读写）都采用非阻塞方式，当一个连接在等待数据时，worker 不会阻塞，而是转去处理其他连接的就绪事件，从而实现极高的资源利用率。

**3. 内存池与精简的数据结构**。Nginx 内部使用内存池（memory pool）管理内存分配，减少了内存碎片和 `malloc/free` 的调用次数。每个连接的内存开销可以控制在几 KB 级别，远低于线程模型。

**4. 模块化设计**。Nginx 的功能由模块组成，除了核心模块外，大部分功能（如 gzip、ssl、rewrite、proxy）都以模块形式存在。编译时可以选择启用或禁用模块，甚至可以编写自定义模块（C 语言）或通过动态模块机制在运行时加载。

与 Apache 的对比可以总结为：Apache 胜在生态成熟、`.htaccess` 灵活、动态内容处理方便；Nginx 胜在高并发性能、低资源消耗、反向代理能力。现代架构中，常见组合是「Nginx 在前端做反向代理和静态服务 + Apache/应用服务器在后端处理动态请求」。

#### 例子

**最简单的 Web 服务器配置**：

```nginx
# /etc/nginx/nginx.conf
worker_processes  1;

events {
    worker_connections  1024;
}

http {
    server {
        listen       80;
        server_name  localhost;

        location / {
            root   /usr/share/nginx/html;
            index  index.html index.htm;
        }
    }
}
```

这段配置让 Nginx 监听 80 端口，将根路径 `/` 的请求映射到 `/usr/share/nginx/html` 目录下的静态文件。

**反向代理配置示例**：

```nginx
http {
    server {
        listen 80;
        server_name api.example.com;

        location / {
            proxy_pass http://127.0.0.1:8080;
        }
    }
}
```

客户端访问 `http://api.example.com` 时，Nginx 将请求转发到本机 8080 端口的后端应用（如 Node.js、Tomcat），后端处理后将响应返回给 Nginx，Nginx 再返回给客户端。客户端完全感知不到后端的存在。

**正向代理与反向代理的对比示意**：

```
正向代理：
  客户端 → [代理服务器] → 目标服务器
  （客户端配置代理，代理代表客户端）

反向代理：
  客户端 → [代理服务器] → 后端服务器A / 后端服务器B
  （客户端不感知后端，代理代表服务端）
```

#### 总结

- Nginx 是高性能的 Web 服务器 + 反向代理服务器，核心优势是高并发、低内存、事件驱动。
- 正向代理代表客户端，反向代理代表服务端，Nginx 主要用于反向代理场景。
- Nginx 的设计哲学：事件驱动、非阻塞 I/O、模块化、内存高效。
- 现代 Web 架构中，Nginx 通常位于最前端，承担静态服务、反向代理、负载均衡、SSL 卸载、缓存等多重角色。
- **注意事项**：Nginx 本身不执行动态语言（PHP、Python、Java），动态内容需通过 `proxy_pass` 或 `fastcgi_pass` 转发给后端处理。

### 第2讲 Nginx 架构：Master-Worker 与事件驱动

#### 概念

Nginx 运行时采用经典的 **Master-Worker 多进程架构**。一个 Nginx 实例由一个 master 进程和多个 worker 进程组成（在启用缓存时还会有 cache manager 和 cache loader 进程）。理解这个架构是掌握 Nginx 性能调优和故障排查的基础。

- **Master 进程**：以 root 权限启动，负责读取和验证配置文件、管理 worker 进程的创建和销毁、绑定监听端口、处理信号（如 `nginx -s reload`、`nginx -s stop`）。Master 进程本身不处理客户端请求。
- **Worker 进程**：由 master 进程 fork 出来，以非特权用户（通常是 `nginx` 或 `nobody`）运行，负责实际处理客户端的 HTTP 请求。Worker 进程之间相互独立，一个 worker 崩溃不会影响其他 worker。
- **Cache Manager / Cache Loader**：当启用了代理缓存时，这两个辅助进程负责缓存的磁盘管理。Cache Loader 在启动时加载缓存元数据，Cache Manager 周期性地清理过期缓存。

#### 原理

**1. Master-Worker 的协作机制**

Master 进程启动后，创建监听 socket（如 `0.0.0.0:80`），然后 fork 出指定数量的 worker 进程。所有 worker 进程共享同一组监听 socket，当新连接到达时，多个 worker 竞争 `accept` 这个连接。为了避免「惊群效应」（thundering herd，即所有 worker 被唤醒争抢同一个连接），Nginx 使用 `accept_mutex` 互斥锁（默认在新版本中关闭，因为 `epoll` 的边缘触发模式已能高效处理）。

每个 worker 进程内部是一个事件循环（event loop），通过 `epoll_wait` 等待所有管理的 socket 上的事件。当一个连接有数据可读、可写或出现错误时，`epoll` 通知 worker，worker 执行对应的回调函数处理请求。由于采用非阻塞 I/O，worker 在等待某个连接的磁盘 I/O 或后端响应时，可以继续处理其他连接的事件。

**2. 事件驱动模型**

Nginx 的事件驱动核心是 `ngx_event_module`。它抽象了不同操作系统的事件通知机制：
- Linux：`epoll`（高效，支持边缘触发 ET 和水平触发 LT）
- BSD/macOS：`kqueue`
- Solaris：`event ports`
- 通用回退：`select` / `poll`（性能差，仅用于不支持前者的系统）

`epoll` 相比 `select`/`poll` 的优势在于：它不需要每次调用时传入所有关注的 fd（文件描述符）集合，而是由内核维护一个就绪列表，只返回真正有事件的 fd，时间复杂度为 O(就绪fd数) 而非 O(总fd数)。

**3. 连接处理流程**

```
客户端发起 TCP 连接
    ↓
Master 的监听 socket 收到 SYN
    ↓
某个 Worker 通过 epoll 获知新连接就绪，accept() 接受连接
    ↓
Worker 创建 ngx_connection_t 结构，注册读事件到 epoll
    ↓
客户端发送 HTTP 请求 → Worker 读事件触发 → 读取并解析请求
    ↓
Worker 处理请求（返回静态文件 / proxy_pass 到后端）
    ↓
Worker 将响应写回客户端 → 写事件触发 → 发送响应
    ↓
连接关闭或保持 keepalive
```

**4. worker 数量的选择**

`worker_processes` 指令决定 worker 进程数。一般原则：等于 CPU 核心数，或 `auto`（Nginx 自动检测）。每个 worker 是单线程的（在事件循环意义上），因此 worker 数 = CPU 核心数可以充分利用多核，同时避免过多进程竞争 CPU。配合 `worker_cpu_affinity` 可以将 worker 绑定到特定 CPU 核心，减少缓存失效。

#### 例子

**查看 Nginx 进程**：

```bash
$ ps aux | grep nginx
root      1234  0.0  0.1  46440  1016 ?        Ss   10:00   0:00 nginx: master process /usr/sbin/nginx
nginx     1235  0.0  0.3  46888  3012 ?        S    10:00   0:00 nginx: worker process
nginx     1236  0.0  0.3  46888  3012 ?        S    10:00   0:00 nginx: worker process
nginx     1237  0.0  0.3  46888  3012 ?        S    10:00   0:00 nginx: worker process
nginx     1238  0.0  0.3  46888  3012 ?        S    10:00   0:00 nginx: worker process
```

可以看到 1 个 master（root 用户）和 4 个 worker（nginx 用户）。

**配置 worker 进程**：

```nginx
# /etc/nginx/nginx.conf

worker_processes  auto;          # 自动等于 CPU 核心数
# worker_processes  4;           # 或手动指定

worker_cpu_affinity auto;        # 自动绑定 CPU 亲和性
# worker_cpu_affinity 0001 0010 0100 1000;  # 4 核手动绑定

worker_rlimit_nofile 65535;      # 每个 worker 最大文件描述符数

events {
    worker_connections  10240;   # 每个 worker 最大连接数
    use epoll;                   # 使用 epoll 事件模型（Linux）
    multi_accept on;             # 一次 accept 多个连接
}
```

**最大并发连接数计算**：

```
最大并发 = worker_processes × worker_connections

对于反向代理场景：
最大并发 = worker_processes × worker_connections / 2
（每个客户端连接会占用 2 个连接：一个对客户端，一个对后端）
```

例如 4 worker × 10240 connections = 40960 并发连接（作为 Web 服务器），或 20480 并发（作为反向代理）。

#### 总结

- Nginx 采用 Master-Worker 多进程架构：Master 管理进程，Worker 处理请求。
- Worker 内部是事件循环，基于 `epoll`/`kqueue` 实现非阻塞 I/O，单 worker 可处理数千并发连接。
- `worker_processes` 一般设为 CPU 核心数，`worker_connections` 决定单 worker 的并发能力。
- 反向代理场景下，每个客户端连接消耗 2 个连接资源（客户端 + 后端），需注意 `worker_connections` 的规划。
- **注意事项**：`worker_connections` 受系统 `ulimit -n`（文件描述符上限）限制，生产环境需同时调整 `worker_rlimit_nofile` 和系统 `fs.file-max`。

### 第3讲 安装部署与目录结构

#### 概念

Nginx 的安装方式主要有两种：**包管理器安装**（apt/yum）和**源码编译安装**。前者简单快捷，适合快速上手和标准部署；后者灵活可控，可以自定义模块和编译选项，适合需要特殊功能或追求极致性能的场景。此外，Nginx 官方还提供了 Docker 镜像，适合容器化部署。

不同安装方式产生的目录结构略有不同，但核心组成是一致的：配置文件、可执行文件、日志文件、默认站点目录。

#### 原理

**包管理器安装的原理**：发行版的包管理器（如 Ubuntu 的 apt、CentOS 的 yum/dnf）从官方仓库下载预编译好的 Nginx 二进制包。这些包通常包含官方核心模块和常用模块，但可能不包含某些第三方模块。版本可能落后于 Nginx 官方最新版。

**源码编译安装的原理**：从 nginx.org 下载源码，通过 `./configure` 脚本生成 `Makefile`，指定安装路径、启用/禁用模块、设置编译参数，然后 `make && make install`。编译时静态链接的模块会被编译进二进制文件；从 Nginx 1.9.11 开始支持动态模块（`--add-dynamic-module`），编译为 `.so` 文件，运行时通过 `load_module` 指令加载。

**Nginx 官方仓库 vs 发行版仓库**：发行版仓库（如 Ubuntu 官方源）的 Nginx 版本较旧且模块较少。建议添加 Nginx 官方仓库（`nginx.org/packages`），获取最新稳定版和完整模块。

#### 例子

**方式一：apt 安装（Ubuntu/Debian）**

```bash
# 更新包索引
sudo apt update

# 安装 Nginx
sudo apt install -y nginx

# 启动并设置开机自启
sudo systemctl start nginx
sudo systemctl enable nginx

# 验证
nginx -v          # 查看版本
curl -I http://localhost   # 测试访问
```

**方式二：源码编译安装**

```bash
# 安装编译依赖
sudo apt install -y build-essential libpcre3-dev zlib1g-dev libssl-dev

# 下载源码
cd /usr/local/src
wget http://nginx.org/download/nginx-1.25.3.tar.gz
tar -zxvf nginx-1.25.3.tar.gz
cd nginx-1.25.3

# 配置编译选项
./configure \
    --prefix=/usr/local/nginx \
    --with-http_ssl_module \
    --with-http_v2_module \
    --with-http_realip_module \
    --with-http_gzip_static_module \
    --with-http_stub_status_module \
    --with-stream \
    --with-pcre

# 编译并安装
make -j$(nproc)
sudo make install

# 创建 systemd 服务文件（可选，便于管理）
sudo tee /etc/systemd/system/nginx.service << 'EOF'
[Unit]
Description=nginx HTTP Server
After=network.target

[Service]
Type=forking
PIDFile=/usr/local/nginx/logs/nginx.pid
ExecStart=/usr/local/nginx/sbin/nginx
ExecReload=/usr/local/nginx/sbin/nginx -s reload
ExecStop=/usr/local/nginx/sbin/nginx -s stop
PrivateTmp=true

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl start nginx
sudo systemctl enable nginx
```

**目录结构对比**：

```
# apt 安装的目录结构（Ubuntu）

# 编译安装的目录结构（--prefix=/usr/local/nginx）

```

**常用管理命令**：

```bash
nginx -t              # 测试配置文件语法
nginx -T              # 测试并打印完整配置（展开 include）
nginx -s reload       # 平滑重载配置（不中断服务）
nginx -s stop         # 快速停止
nginx -s quit         # 优雅停止（等待当前请求处理完）
nginx -s reopen       # 重新打开日志文件（日志轮转用）
nginx -V              # 查看编译参数和已启用模块
```

#### 总结

- 包管理器安装简单快捷，适合标准部署；源码编译灵活可控，适合定制需求。
- 建议使用 Nginx 官方仓库而非发行版默认仓库，以获取最新版本和完整模块。
- 核心目录：配置文件（`/etc/nginx/` 或 `/usr/local/nginx/conf/`）、日志（`/var/log/nginx/`）、站点根目录。
- `nginx -t` 是修改配置后必做的检查，`nginx -s reload` 实现平滑重载。
- **注意事项**：编译安装时务必记录 `./configure` 参数（`nginx -V` 可查看），后续升级或添加模块需要使用相同参数。生产环境建议使用 systemd 管理服务，便于开机自启和日志收集。

## 第二章 配置基础

### 第4讲 配置文件结构与指令体系

#### 概念

Nginx 的配置文件采用**层级化的指令块**结构，由一系列**指令**和**上下文**组成。理解配置文件的组织方式是正确使用 Nginx 的前提。核心概念包括：

- **指令**：配置的最小单元，以分号 `;` 结尾。分为**简单指令**（如 `worker_processes 1;`）和**块指令**（以 `{ }` 包裹，内部包含子指令）。
- **上下文**：块指令创建的作用域。Nginx 有四个核心上下文层级：`events`、`http`、`server`、`location`，以及 `stream`（TCP/UDP 代理）和 `mail`（邮件代理）。
- **include 指令**：将其他文件的内容引入当前配置文件，实现模块化管理。
- **指令继承**：子上下文自动继承父上下文的指令值，除非在子上下文中重新定义。

#### 原理

**1. 上下文层级**

Nginx 配置的上下文从外到内形成树状结构：

```
main（全局上下文，即配置文件最外层，无 { } 包裹）
├── events { }          # 事件模块配置（全局唯一）
├── http { }            # HTTP 模块配置（全局唯一）
│   ├── server { }      # 虚拟主机（可有多个）
│   │   └── location { }  # URL 匹配规则（可有多个）
│   └── upstream { }    # 上游服务器组（可有多个）
├── stream { }          # TCP/UDP 代理配置（可选）
└── mail { }            # 邮件代理配置（可选）
```

- `main` 上下文：配置文件最外层，不在任何 `{ }` 内的指令。如 `worker_processes`、`user`、`error_log`、`pid`。
- `events` 上下文：全局唯一，配置连接处理相关参数。如 `worker_connections`、`use epoll`。
- `http` 上下文：全局唯一，配置 HTTP 服务器相关参数。所有 `server`、`upstream` 都在 `http` 内。
- `server` 上下文：定义一个虚拟主机，通过 `listen` 和 `server_name` 区分。
- `location` 上下文：定义 URL 匹配规则和处理方式，是请求路由的核心。

**2. 指令继承机制**

子上下文会自动继承父上下文中定义的指令值。例如，在 `http` 块中定义 `gzip on;`，则所有 `server` 和 `location` 都默认启用 gzip，除非在子上下文中显式覆盖为 `gzip off;`。

但并非所有指令都可继承——有些指令只能在特定上下文中使用（如 `listen` 只能在 `server` 中），有些指令是「数组型」的（如 `proxy_set_header`），在子上下文中定义会**追加**而非覆盖父上下文的值。

**3. 指令类型**

- **标准指令**：有明确的值，如 `root /var/www;`。
- **数组指令**：可多次出现，值会累积。如 `proxy_set_header`、`add_header`、`access_log`。注意：如果在子上下文中重新定义了数组指令，父上下文的值会被**清除**，需要重新声明所有需要的值。
- **动作指令**：改变请求处理流程，如 `rewrite`、`return`。

**4. include 机制**

`include` 指令在配置解析阶段将指定文件的内容原样插入到当前位置。支持通配符 `*`。常见用法：

```nginx
http {
    include       mime.types;          # 引入 MIME 类型映射
    include       conf.d/*.conf;       # 引入 conf.d 下所有 .conf 文件
    include       sites-enabled/*;     # 引入已启用的站点配置
}
```

#### 例子

**完整的 nginx.conf 结构示例**：

```nginx
# ===== main 上下文 =====
user  nginx;                          # worker 进程运行用户
worker_processes  auto;               # worker 进程数
error_log  /var/log/nginx/error.log warn;  # 错误日志
pid        /var/run/nginx.pid;        # PID 文件位置

# ===== events 上下文 =====
events {
    worker_connections  1024;         # 每个 worker 最大连接数
    use epoll;
}

# ===== http 上下文 =====
http {
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;

    # 日志格式定义
    log_format  main  '$remote_addr - $remote_user [$time_local] "$request" '
                      '$status $body_bytes_sent "$http_referer" '
                      '"$http_user_agent" "$http_x_forwarded_for"';

    access_log  /var/log/nginx/access.log  main;

    sendfile        on;               # 启用 sendfile 系统调用
    keepalive_timeout  65;            # keepalive 超时
    gzip  on;                         # 全局启用 gzip

    # 引入额外配置
    include /etc/nginx/conf.d/*.conf;

    # ===== server 上下文：虚拟主机1 =====
    server {
        listen       80;
        server_name  www.example.com;
        root         /var/www/example;

        location / {
            index  index.html;
        }

        location /static/ {
            # 继承了 http 块的 gzip on
            expires 30d;              # 静态资源缓存 30 天
        }
    }

    # ===== upstream 上下文：后端服务器组 =====
    upstream backend {
        server 127.0.0.1:8080;
        server 127.0.0.1:8081;
    }
}
```

**数组指令的继承陷阱**：

```nginx
http {
    # 父上下文定义了 add_header
    add_header X-Frame-Options DENY;

    server {
        listen 80;
        server_name a.com;

        location /api/ {
            # 在这里重新定义 add_header，父上下文的 X-Frame-Options 会丢失！
            add_header X-Content-Type-Options nosniff;
            # 如果需要同时保留，必须重新声明：
            # add_header X-Frame-Options DENY;
            # add_header X-Content-Type-Options nosniff;
        }
    }
}
```

这是一个极其常见的坑：在 `location` 中添加新的 `add_header` 后，`http` 或 `server` 级别的 `add_header` 不再生效。解决方案是使用 `add_header ... always`（Nginx 1.7.5+）或在每个层级重复声明。

#### 总结

- Nginx 配置由指令和上下文组成，核心上下文层级为 `main > events > http > server > location`。
- 子上下文继承父上下文的指令值，但数组型指令（`add_header`、`proxy_set_header` 等）在子上下文中重新定义时会清除父级值。
- 使用 `include` 实现配置模块化管理，将不同站点的配置拆分到独立文件。
- `nginx -t` 检查语法，`nginx -T` 查看展开后的完整配置，是排查配置问题的利器。
- **注意事项**：修改配置后务必先 `nginx -t` 测试，再 `nginx -s reload` 重载。数组指令的继承陷阱是生产环境最常见的配置错误之一。

### 第5讲 server 块与 location 匹配规则

#### 概念

`server` 块定义虚拟主机，`location` 块定义 URL 路由规则。这两个指令是 Nginx HTTP 请求处理的核心：`server` 决定「哪个虚拟主机处理请求」，`location` 决定「虚拟主机内如何处理不同 URL」。

- **虚拟主机**：一台物理服务器上运行多个网站，通过 `server_name`（域名）或 `listen`（端口/IP）区分。Nginx 支持基于域名的虚拟主机、基于 IP 的虚拟主机、基于端口的虚拟主机。
- **location 匹配**：根据请求 URI 选择不同的处理规则。Nginx 支持精确匹配、前缀匹配、正则匹配等多种方式，且有严格的优先级规则。

#### 原理

**1. server 块的匹配**

当请求到达时，Nginx 根据 `listen` 指令筛选出监听该 IP:Port 的所有 server 块，然后根据 `Host` 请求头匹配 `server_name`：

- 精确匹配：`server_name www.example.com;`
- 通配符匹配：`server_name *.example.com;`（前缀通配）或 `server_name www.example.*;`（后缀通配）
- 正则匹配：`server_name ~^www\d+\.example\.com$;`（以 `~` 开头）
- 默认服务器：`default_server` 参数标记，未匹配到任何 server_name 时使用

匹配优先级：精确 > 前缀通配 > 后缀通配 > 正则 > 默认。

**2. location 匹配规则**

location 的匹配修饰符决定了匹配方式和优先级：

| 修饰符 | 含义 | 优先级 |
|--------|------|--------|
| `=` | 精确匹配，URI 完全相等 | 最高 |
| `^~` | 前缀匹配，匹配后不再检查正则 | 次高 |
| `~` | 区分大小写的正则匹配 | 按顺序，先匹配先用 |
| `~*` | 不区分大小写的正则匹配 | 按顺序，先匹配先用 |
| `!~` / `!~*` | 正则不匹配 | — |
| 无 | 普通前缀匹配 | 最低 |

**匹配流程**：
1. Nginx 先检查所有前缀匹配（无修饰符和 `^~`），选择最长匹配的 location。
2. 如果最长匹配的 location 带有 `^~`，则直接使用它，不再检查正则。
3. 如果最长匹配是普通前缀，记住它，然后按配置顺序检查正则 location。
4. 如果有正则匹配成功，使用第一个匹配的正则 location。
5. 如果没有正则匹配，使用之前记住的最长前缀 location。
6. `=` 精确匹配如果命中，立即使用，不再进行其他匹配。

**3. root 与 alias 在 location 中的作用**

`root` 和 `alias` 决定如何将 URI 映射到文件系统路径（详见第7讲）。在 location 匹配后，Nginx 根据这些指令找到对应的文件。

#### 例子

**多虚拟主机配置**：

```nginx
http {
    # 虚拟主机1：精确域名
    server {
        listen 80;
        server_name www.example.com;
        root /var/www/example;
    }

    # 虚拟主机2：通配符域名
    server {
        listen 80;
        server_name *.example.com;    # 匹配 api.example.com, blog.example.com 等
        root /var/www/wildcard;
    }

    # 虚拟主机3：默认服务器
    server {
        listen 80 default_server;    # 未匹配到任何 server_name 时使用
        server_name _;               # 无效域名，仅占位
        return 444;                  # 直接关闭连接
    }
}
```

**location 匹配示例**：

```nginx
server {
    listen 80;
    server_name example.com;
    root /var/www/site;

    # 1. 精确匹配：访问 / 时直接返回首页，不再走后续匹配
    location = / {
        index index.html;
    }

    # 2. 前缀匹配（^~）：匹配 /static/ 开头，不再检查正则
    location ^~ /static/ {
        expires 30d;
        # /static/css/style.css → /var/www/site/static/css/style.css
    }

    # 3. 正则匹配（区分大小写）：匹配 .php 结尾
    location ~ \.php$ {
        fastcgi_pass 127.0.0.1:9000;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        include fastcgi_params;
    }

    # 4. 正则匹配（不区分大小写）：匹配图片文件
    location ~* \.(jpg|jpeg|png|gif|ico|css|js)$ {
        expires 7d;
    }

    # 5. 普通前缀匹配
    location /api/ {
        proxy_pass http://127.0.0.1:8080;
    }

    # 6. 默认匹配
    location / {
        try_files $uri $uri/ =404;
    }
}
```

**匹配流程演示**：

| 请求 URI | 匹配的 location | 说明 |
|----------|-----------------|------|
| `/` | `location = /` | 精确匹配优先 |
| `/static/logo.png` | `location ^~ /static/` | 前缀 `^~` 命中，跳过正则 |
| `/image/photo.jpg` | `location ~* \.(jpg...)$` | 前缀 `/` 记住后，正则命中 |
| `/api/users` | `location /api/` | 前缀匹配，无正则命中 |
| `/about.html` | `location /` | 只有默认前缀匹配 |

**location 嵌套**：

```nginx
location /api/ {
    proxy_pass http://backend;

    # location 可以嵌套（但不能嵌套在正则 location 内）
    location /api/upload/ {
        client_max_body_size 50m;    # 上传接口放宽请求体大小
        proxy_pass http://backend;
    }
}
```

#### 总结

- `server` 通过 `listen` + `server_name` 区分虚拟主机，匹配优先级为精确 > 通配符 > 正则 > 默认。
- `location` 匹配优先级：`=` 精确 > `^~` 前缀（停止正则）> 正则（按顺序）> 普通前缀（最长匹配）。
- 正则 location 按配置文件中的出现顺序匹配，第一个命中即使用。
- `^~` 的作用是「如果前缀匹配成功，就跳过正则检查」，适合静态资源等不需要正则的场景，可提升性能。
- **注意事项**：正则 location 容易产生意外匹配，建议静态资源用 `^~` 前缀匹配，动态接口用普通前缀匹配，仅在必要时使用正则。`location` 不能嵌套在正则 location 内部。

### 第6讲 变量体系与 rewrite 重写

#### 概念

Nginx 的变量系统和 `rewrite` 指令是实现动态配置、URL 重写、请求改写的关键工具。

- **变量**：Nginx 内置了大量变量（如 `$host`、`$uri`、`$args`），可以在配置文件中引用，用于日志记录、条件判断、请求转发等。也支持自定义变量。
- **rewrite 指令**：基于正则表达式修改请求 URI，实现 URL 重定向或内部重写。
- **return 指令**：直接返回状态码和响应，常用于重定向或拒绝请求。
- **if 指令**：条件判断（但使用需谨慎，有「if is evil」之说）。
- **map 指令**：根据一个变量的值映射出另一个变量的值，比 `if` 更优雅。

#### 原理

**1. 变量的生命周期与作用域**

Nginx 变量在请求处理过程中创建，请求结束时销毁。变量分为几类：

- **请求头变量**：`$http_` 前缀 + 请求头名（小写，下划线替换横线）。如 `$http_user_agent`、`$http_x_forwarded_for`。
- **响应头变量**：`$sent_http_` 前缀。如 `$sent_http_content_type`。
- **服务器变量**：`$server_addr`、`$server_port`、`$server_name`。
- **连接变量**：`$remote_addr`（客户端 IP）、`$remote_port`、`$remote_user`。
- **请求变量**：`$uri`（当前 URI，不含参数）、`$request_uri`（完整 URI，含参数）、`$args`（查询字符串）、`$host`（请求的 Host 头或 server_name）、`$request_method`、`$scheme`。
- **自定义变量**：通过 `set` 指令定义，如 `set $cache_key "$host$request_uri";`。

**2. rewrite 的工作机制**

`rewrite regex replacement [flag];`

- `regex`：匹配当前 URI（`$uri`，不含参数）的正则表达式。
- `replacement`：替换后的 URI。如果以 `http://` 或 `https://` 开头，则返回 302 重定向。
- `flag`：控制重写后的行为：
  - `last`：停止当前 `rewrite` 指令集，重新搜索 location（会重新走一遍 location 匹配流程）。
  - `break`：停止当前 `rewrite` 指令集，不再重新搜索 location（继续在当前 location 内处理）。
  - `redirect`：返回 302 临时重定向。
  - `permanent`：返回 301 永久重定向。

**rewrite 执行阶段**：rewrite 指令在 `server` 块中的在 location 匹配前执行（server-rewrite 阶段），在 `location` 块中的在 location 匹配后执行（rewrite 阶段）。

**3. if 指令的陷阱**

`if` 指令在 Nginx 中的行为与一般编程语言不同，它不是在请求处理时动态执行，而是在配置解析阶段生成特定的指令序列。`if` 在 `location` 内部只能安全地配合 `return` 和 `rewrite` 使用，用于其他指令（如 `proxy_pass`、`root`）可能产生意外行为。这就是著名的「If Is Evil」问题。

**4. map 指令**

`map` 在 `http` 上下文中定义变量映射关系，在请求处理时根据输入变量的值查找输出值。比多个 `if` 判断更高效、更清晰。

#### 例子

**常用内置变量**：

```nginx
server {
    listen 80;
    server_name example.com;

    # 自定义日志格式，记录更多请求信息
    log_format detailed '$remote_addr - $remote_user [$time_local] '
                        '"$request" $status $body_bytes_sent '
                        '"$http_referer" "$http_user_agent" '
                        'rt=$request_time uct="$upstream_connect_time" '
                        'urt="$upstream_response_time"';

    location / {
        # 添加响应头，显示请求信息
        add_header X-Request-URI $request_uri;
        add_header X-Real-IP $remote_addr;

        # 根据请求方法返回不同内容
        if ($request_method = POST) {
            return 405;  # Method Not Allowed
        }

        return 200 "Host: $host\nURI: $uri\nArgs: $args\nIP: $remote_addr\n";
    }
}
```

**URL 重写示例**：

```nginx
server {
    listen 80;
    server_name example.com;
    root /var/www/site;

    # 旧 URL 重定向到新 URL（301 永久重定向）
    # /old-page → /new-page
    rewrite ^/old-page$ /new-page permanent;

    # /article/123 → /article.php?id=123
    rewrite ^/article/(\d+)$ /article.php?id=$1 last;

    # /download/file.zip → /files/file.zip（内部重写，不改 URL）
    rewrite ^/download/(.+)$ /files/$1 break;

    # HTTP 强制跳转 HTTPS
    if ($scheme = http) {
        return 301 https://$host$request_uri;
    }

    location / {
        try_files $uri $uri/ /index.php?$args;
    }
}
```

**map 指令示例**：

```nginx
http {
    # 根据请求路径决定是否启用缓存
    map $request_uri $skip_cache {
        default         0;
        ~*/admin/      1;    # admin 路径不缓存
        ~*/api/        1;    # api 路径不缓存
    }

    # 根据 User-Agent 判断是否为移动端
    map $http_user_agent $is_mobile {
        default                    0;
        ~*mobile                   1;
        ~*android                  1;
        ~*iphone                   1;
    }

    # 根据域名决定后端
    map $host $backend {
        default       backend-default;
        api.com       backend-api;
        cdn.com       backend-cdn;
    }

    server {
        listen 80;

        location / {
            # 使用 map 定义的变量
            if ($is_mobile) {
                rewrite ^(.*)$ /mobile$1 break;
            }

            proxy_pass http://$backend;
            proxy_cache_bypass $skip_cache;  # $skip_cache=1 时跳过缓存
        }
    }
}
```

**set 自定义变量**：

```nginx
location / {
    set $cache_key "${host}${uri}";
    # 后续可以使用 $cache_key
    add_header X-Cache-Key $cache_key;
}
```

#### 总结

- Nginx 变量在请求处理时求值，常用 `$uri`、`$request_uri`、`$host`、`$args`、`$remote_addr` 等。
- `rewrite` 的 `last` 和 `break` 区别：`last` 重新搜索 location，`break` 在当前 location 内继续处理。
- `redirect`（302）和 `permanent`（301）产生客户端重定向，`last` 和 `break` 是服务器内部重写。
- `if` 指令有「If Is Evil」陷阱，在 location 内仅安全用于 `return` 和 `rewrite`，复杂条件用 `map` 替代。
- **注意事项**：`rewrite` 的正则使用 PCRE 语法，注意转义。频繁的 `rewrite` + `last` 可能导致循环（Nginx 内置 10 次循环上限，超过返回 500）。生产环境优先使用 `return` 做重定向，`map` 做条件映射。

## 第三章 静态内容服务

### 第7讲 静态文件服务：root 与 alias

#### 概念

静态文件服务是 Nginx 最基础的功能：接收 HTTP 请求，将 URL 映射到文件系统路径，返回文件内容。`root` 和 `alias` 是实现这一映射的两个核心指令，它们的行为有微妙但关键的区别。

- **root 指令**：将 URI 追加到 root 路径后形成文件路径。即 `文件路径 = root路径 + URI`。
- **alias 指令**：用 alias 路径替换 location 匹配的部分。即 `文件路径 = alias路径 + (URI - location匹配部分)`。

#### 原理

**1. root 的工作方式**

```nginx
location /static/ {
    root /var/www;
}
```

请求 `/static/css/style.css` 时：
- 文件路径 = `/var/www` + `/static/css/style.css` = `/var/www/static/css/style.css`

root 将完整的 URI（包括 location 匹配的前缀）追加到 root 路径后面。这意味着文件系统中必须存在 `/var/www/static/` 目录。

**2. alias 的工作方式**

```nginx
location /static/ {
    alias /var/www/files/;
}
```

请求 `/static/css/style.css` 时：
- location 匹配部分 = `/static/`
- 剩余部分 = `css/style.css`
- 文件路径 = `/var/www/files/` + `css/style.css` = `/var/www/files/css/style.css`

alias 用指定的路径**替换** location 匹配的部分，URI 中 location 前缀不会出现在文件路径中。

**3. 两者的选择原则**

- 当 URL 路径与文件系统目录结构一致时，用 `root`。
- 当 URL 路径与文件系统目录结构不一致时，用 `alias`。
- `root` 可以放在 `http`、`server`、`location` 上下文中；`alias` 只能放在 `location` 中。
- `alias` 后的路径如果以 `/` 结尾，location 也应以 `/` 结尾，否则可能出现路径拼接错误。

**4. try_files 指令**

`try_files` 按顺序尝试多个文件/URI，返回第一个存在的文件，都不存在则使用最后的回退项。常用于 SPA（单页应用）的前端路由和优雅的 404 处理。

#### 例子

**root 示例**：

```nginx
server {
    listen 80;
    server_name example.com;

    # 方式1：全局 root
    root /var/www/site;

    location / {
        # /var/www/site/index.html
        index index.html;
    }

    location /images/ {
        # /var/www/site/images/logo.png
        # 继承了 server 的 root
    }

    location /docs/ {
        # 覆盖 root
        root /var/www/documentation;
        # /var/www/documentation/docs/guide.html
    }
}
```

**alias 示例**：

```nginx
server {
    listen 80;
    server_name example.com;
    root /var/www/site;

    # URL /static/ 映射到 /var/www/files/
    location /static/ {
        alias /var/www/files/;
        # /static/css/style.css → /var/www/files/css/style.css
    }

    # URL /api/docs/ 映射到 /usr/share/api-docs/
    location /api/docs/ {
        alias /usr/share/api-docs/;
        # /api/docs/v1.html → /usr/share/api-docs/v1.html
    }

    # 精确匹配单个文件
    location = /favicon.ico {
        alias /var/www/icons/favicon.ico;
        # 注意：精确匹配用 alias 时不需要结尾斜杠
    }
}
```

**try_files 示例**：

```nginx
server {
    listen 80;
    root /var/www/site;

    # SPA 前端路由：所有不存在的文件都回退到 index.html
    location / {
        try_files $uri $uri/ /index.html;
        # 1. 尝试 $uri 对应的文件
        # 2. 尝试 $uri/ 对应的目录
        # 3. 都不存在，返回 /index.html 的内容（但 URL 不变）
    }

    # 优雅的 404
    location /downloads/ {
        alias /var/www/files/;
        try_files $uri =404;  # 文件不存在时返回 404
    }
}
```

**root 与 alias 对比表**：

| 配置 | 请求 URI | 文件路径 |
|------|----------|----------|
| `location /img/ { root /data; }` | `/img/a.png` | `/data/img/a.png` |
| `location /img/ { alias /data/; }` | `/img/a.png` | `/data/a.png` |
| `location /img/ { root /data/wall; }` | `/img/a.png` | `/data/wall/img/a.png` |
| `location /img/ { alias /data/wall/; }` | `/img/a.png` | `/data/wall/a.png` |

#### 总结

- `root` 将完整 URI 追加到路径后，`alias` 用路径替换 location 匹配部分。
- URL 与文件系统结构一致用 `root`，需要「重映射」用 `alias`。
- `alias` 必须在 `location` 内使用，且路径结尾斜杠要与 location 匹配。
- `try_files` 用于按顺序尝试文件，是 SPA 路由和优雅 404 的标准方案。
- **注意事项**：`alias` 使用正则 location 时需用捕获组引用，如 `location ~ ^/img/(.*)$ { alias /data/$1; }`。`root` 在 `http` 级别定义可被所有 server 继承，是设置全局站点根目录的推荐方式。

### 第8讲 索引页、错误页与目录浏览

#### 概念

当客户端请求的是一个目录（如 `/`）或请求的文件不存在时，Nginx 需要决定如何响应。这涉及三个核心指令：

- **index**：指定目录的默认索引文件。当请求以 `/` 结尾（即目录请求）时，Nginx 按顺序查找 index 指定的文件。
- **error_page**：自定义错误页面。当请求返回特定错误状态码时，返回自定义页面而非默认错误信息。
- **autoindex**：目录浏览功能。当 index 指定的文件都不存在时，如果开启 autoindex，Nginx 生成目录列表页面。

#### 原理

**1. index 的工作流程**

当请求 URI 以 `/` 结尾时（如 `/`、`/docs/`），Nginx 将其视为目录请求：
1. 按顺序检查 `index` 指令列出的文件（如 `index.html`、`index.htm`）。
2. 如果找到第一个存在的文件，内部重定向到该文件（URI 变为 `/index.html`），重新走 location 匹配。
3. 如果所有 index 文件都不存在，且 `autoindex on`，则生成目录列表。
4. 如果 `autoindex off`（默认），返回 403 Forbidden。

**2. error_page 的工作机制**

`error_page code [code...] [=response] uri;`

- `code`：要捕获的错误状态码，如 404、500、502。
- `=response`：可选，改变最终响应的状态码。如 `error_page 404 =200 /index.html` 会让 404 返回 200 状态码。
- `uri`：错误页面的 URI，可以是本地路径或外部 URL。

error_page 触发时，Nginx 内部重定向到指定的 URI，重新走 location 匹配。可以通过 `$status` 等变量在错误页中显示错误信息。

**3. autoindex 的工作方式**

当 `autoindex on` 时，Nginx 读取目录内容，生成 HTML 格式的文件列表。相关选项：
- `autoindex_exact_size on|off`：是否显示精确文件大小（on 显示字节数，off 显示 KB/MB）。
- `autoindex_localtime on|off`：是否显示本地时间（on 本地时间，off UTC 时间）。
- `autoindex_format html|xml|json|jsonp`：输出格式。

#### 例子

**index 配置**：

```nginx
server {
    listen 80;
    root /var/www/site;

    # 默认索引文件，按顺序查找
    index index.html index.htm index.php;

    location / {
        # 请求 / → 查找 /var/www/site/index.html
        # 不存在则查找 index.htm，再不存在查找 index.php
    }

    # 不同目录使用不同索引
    location /api/ {
        alias /var/www/api/;
        index api.php;    # /api/ → /var/www/api/api.php
    }
}
```

**error_page 配置**：

```nginx
server {
    listen 80;
    root /var/www/site;

    # 自定义 404 页面
    error_page 404 /404.html;

    # 自定义 500/502/503/504 页面
    error_page 500 502 503 504 /50x.html;

    # 所有 4xx 错误统一到一个页面
    error_page 403 404 405 /error.html;

    # 改变状态码：404 返回 200 + 首页内容（SPA 常用）
    error_page 404 =200 /index.html;

    # 重定向到外部 URL
    error_page 404 https://example.com/not-found;

    # 使用变量传递状态码
    error_page 500 502 503 504 /error.html;
    location = /error.html {
        internal;    # 仅允许内部重定向访问，外部直接访问返回 404
        add_header X-Error-Status $status;  # 传递原始状态码
    }

    location / {
        try_files $uri $uri/ =404;
    }
}
```

**autoindex 目录浏览**：

```nginx
server {
    listen 80;
    server_name files.example.com;
    root /var/www/files;

    location / {
        autoindex on;                    # 开启目录浏览
        autoindex_exact_size off;        # 显示友好大小（KB/MB）
        autoindex_localtime on;          # 显示本地时间
        # autoindex_format json;         # JSON 格式输出
    }
}
```

访问效果（HTML 格式）：

```html
<html>
<head><title>Index of /</title></head>
<body>
<h1>Index of /</h1>
<hr>
<a href="../">../</a>
<a href="documents/">documents/</a>                                        08-Jul-2026 10:00       -
<a href="images/">images/</a>                                              08-Jul-2026 10:00       -
<a href="report.pdf">report.pdf</a>                                        08-Jul-2026 09:30    2.5M
<a href="data.csv">data.csv</a>                                            08-Jul-2026 09:00     15K
<hr>
</body>
</html>
```

**综合示例：完整的静态站点配置**：

```nginx
server {
    listen 80;
    server_name www.example.com;
    root /var/www/example;
    index index.html;

    # 全局错误页
    error_page 404 /404.html;
    error_page 500 502 503 504 /50x.html;
    location = /404.html { internal; }
    location = /50x.html { internal; }

    # 主站点
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 静态资源缓存
    location ~* \.(css|js|jpg|png|gif|ico|woff2?)$ {
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # 文件下载区（开启目录浏览）
    location /downloads/ {
        alias /var/www/files/;
        autoindex on;
        autoindex_exact_size off;
        autoindex_localtime on;
    }
}
```

#### 总结

- `index` 指定目录默认文件，按顺序查找，找到后内部重定向。
- `error_page` 自定义错误页面，支持改变状态码、使用变量、内部重定向。
- `autoindex` 开启目录浏览，适合文件下载站，生产环境慎用（可能暴露敏感文件）。
- `internal` 指令标记 location 仅允许内部重定向访问，保护错误页等内部页面。
- **注意事项**：`error_page` 的内部重定向会重新走 location 匹配，注意不要产生循环。SPA 应用常用 `error_page 404 =200 /index.html` 让前端路由接管所有路径。

### 第9讲 限速下载与防盗链

#### 概念

当提供文件下载或静态资源服务时，可能面临两个问题：一是大文件下载占用过多带宽，影响其他用户；二是资源被其他网站直接引用（盗链），消耗你的服务器带宽。Nginx 提供了限速和防盗链机制来应对。

- **limit_rate**：限制单个连接的响应传输速率。
- **limit_rate_after**：传输一定量数据后才开始限速（允许快速开始，然后降速）。
- **valid_referers**：校验请求的 Referer 头，拒绝来自非授权站点的引用（防盗链）。
- **limit_conn / limit_req**：连接数限制和请求速率限制（在第15讲详述）。

#### 原理

**1. 限速原理**

`limit_rate` 通过控制 Nginx 向客户端发送数据的速率来实现带宽限制。底层机制是：Nginx 在每次写入数据到 socket 后，根据已发送的数据量和时间计算是否需要延迟下一次写入。限速是针对单个连接的，如果用户开多个连接下载，总速率会是 `limit_rate × 连接数`。

`limit_rate_after` 允许先以全速传输一定量的数据（如前 1MB），然后才开始限速。这改善了用户体验：小文件不受限速影响，大文件在快速开始后降速。

**2. 防盗链原理**

HTTP 请求的 `Referer` 头记录了请求来源页面的 URL。当用户在 A 网站点击链接访问 B 网站的图片时，请求的 Referer 就是 A 网站的 URL。`valid_referers` 指令校验 Referer 是否来自允许的站点列表，如果不是，将 `$invalid_referer` 变量设为 1，配合 `if` 指令拒绝请求或返回替代图片。

需要注意的是：
- Referer 可以被客户端伪造，防盗链不是绝对安全的。
- 有些客户端/浏览器会省略 Referer（如直接输入 URL、HTTPS 跳 HTTP、隐私模式），需要允许 `none`（无 Referer）和 `blocked`（Referer 被代理删除）。
- 现代防盗链更多使用签名 URL（带过期时间的 token），而非仅靠 Referer。

#### 例子

**限速下载**：

```nginx
server {
    listen 80;
    root /var/www/site;

    # 全局限速 100KB/s
    location /downloads/ {
        alias /var/www/files/;

        # 前 1MB 不限速，之后限速 100KB/s
        limit_rate_after 1m;
        limit_rate 100k;

        # 也可以根据变量动态限速
        # limit_rate $limit_speed;
    }

    # VIP 用户不限速，普通用户限速
    location /premium/ {
        alias /var/www/premium/;

        # 通过 map 根据请求参数决定限速
        # 假设 $limit_speed 已通过 map 定义
        limit_rate_after 1m;
        limit_rate $limit_speed;
    }
}
```

**动态限速（配合 map）**：

```nginx
http {
    # 根据请求参数 token 决定限速
    map $arg_token $limit_speed {
        default    100k;    # 普通用户 100KB/s
        "vip123"   0;       # VIP 用户不限速
        "svip456"  0;       # SVIP 用户不限速
    }

    server {
        listen 80;

        location /downloads/ {
            alias /var/www/files/;
            limit_rate_after 1m;
            limit_rate $limit_speed;
        }
    }
}
```

**防盗链配置**：

```nginx
server {
    listen 80;
    server_name www.example.com;
    root /var/www/site;

    # 图片防盗链
    location ~* \.(jpg|jpeg|png|gif|webp|mp4|mp3)$ {
        # 允许的 Referer 来源
        valid_referers none blocked server_names
                       *.example.com example.*
                       ~\.google\. ~\.baidu\.;

        # 如果 Referer 无效，返回 403 或替代图片
        if ($invalid_referer) {
            # return 403;
            rewrite ^(.*)$ /images/hotlink-denied.png last;
        }
    }

    # 也可以使用 return 403
    location /protected/ {
        alias /var/www/protected/;
        valid_referers none blocked server_names *.example.com;
        if ($invalid_referer) {
            return 403;
        }
    }
}
```

**valid_referers 参数说明**：

| 参数 | 含义 |
|------|------|
| `none` | 请求头中没有 Referer（如直接输入 URL） |
| `blocked` | 请求头有 Referer 但值被代理/防火墙删除（不以 `http://` 或 `https://` 开头） |
| `server_names` | Referer 中的域名匹配 server_name |
| `*.example.com` | 允许的域名通配符 |
| `~\.google\.` | 正则匹配（以 `~` 开头） |

**综合示例：文件下载站**：

```nginx
server {
    listen 80;
    server_name download.example.com;
    root /var/www/downloads;

    # 全局限速 + 防盗链
    location /files/ {
        alias /var/www/files/;

        # 限速：前 5MB 全速，之后 200KB/s
        limit_rate_after 5m;
        limit_rate 200k;

        # 防盗链
        valid_referers none blocked server_names *.example.com;
        if ($invalid_referer) {
            return 403 "Hotlinking is not allowed";
        }

        # 开启目录浏览
        autoindex on;
        autoindex_exact_size off;
        autoindex_localtime on;

        # 允许断点续传
        max_ranges 5;
    }
}
```

#### 总结

- `limit_rate` 限制单连接传输速率，`limit_rate_after` 允许前段全速传输。
- 限速是针对单连接的，多连接下载会绕过限制，需配合 `limit_conn` 限制连接数。
- `valid_referers` 校验 Referer 实现防盗链，需允许 `none` 和 `blocked` 避免误伤正常用户。
- 防盗链不是绝对安全的（Referer 可伪造），高安全场景应使用签名 URL。
- **注意事项**：限速值单位 `k`（KB/s）和 `m`（MB/s）不区分大小写。防盗链的替代图片不要也加上防盗链规则，否则会死循环。

## 第四章 反向代理与负载均衡

### 第10讲 反向代理基础：proxy_pass 与请求头转发

#### 概念

反向代理是 Nginx 最核心的应用场景之一。Nginx 接收客户端请求，将其转发给后端服务器处理，再将后端响应返回给客户端。在这个过程中，Nginx 可以实现负载均衡、SSL 卸载、缓存、安全过滤等功能。

- **proxy_pass**：核心指令，指定后端服务器地址，将请求转发过去。
- **proxy_set_header**：修改转发给后端的请求头。
- **proxy_redirect**：修改后端返回的 Location 响应头中的 URL。
- **proxy_next_upstream**：定义什么情况下将请求转发到下一个后端服务器。

#### 原理

**1. proxy_pass 的工作流程**

当 Nginx 执行到 `proxy_pass` 指令时：
1. Nginx 作为客户端，向后端发起一个新的 HTTP 请求。
2. 将原始请求的方法、URI、请求头、请求体转发给后端。
3. 等待后端响应，将响应头和响应体返回给原始客户端。

这个过程对客户端透明——客户端只与 Nginx 通信，不知道后端的存在。

**2. proxy_pass 的 URI 处理规则**

`proxy_pass` 的地址是否带 URI，会影响转发给后端的 URI：

- **不带 URI**（如 `proxy_pass http://backend;`）：将完整的原始 URI（`$request_uri`，含 location 匹配部分）转发给后端。
- **带 URI**（如 `proxy_pass http://backend/api;`）：将 location 匹配的部分替换为 proxy_pass 中的 URI。

注意：如果 `proxy_pass` 使用了变量（如 `proxy_pass http://$backend;`），则不会进行 URI 替换，需要手动处理。

**3. 请求头转发**

默认情况下，Nginx 转发请求时会做以下处理：
- 设置 `Host` 头为 `proxy_pass` 中指定的地址（而非客户端原始的 Host）。
- 设置 `Connection: close`（不与后端保持 keepalive，除非显式配置）。
- 客户端 IP 不会自动传递给后端（后端看到的是 Nginx 的 IP）。

为了让后端获取正确的客户端信息，需要手动设置请求头：
- `proxy_set_header Host $host;`：传递原始 Host。
- `proxy_set_header X-Real-IP $remote_addr;`：传递客户端真实 IP。
- `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`：传递代理链。
- `proxy_set_header X-Forwarded-Proto $scheme;`：传递原始协议（http/https）。

**4. 代理缓冲**

`proxy_buffering on`（默认）：Nginx 先将后端响应完整接收并缓冲，再发给客户端。好处是后端可以快速释放连接，坏处是大数据响应占用 Nginx 内存。

`proxy_buffering off`：Nginx 收到后端响应后立即转发给客户端（流式传输），适合大文件下载、SSE（Server-Sent Events）等场景。

#### 例子

**基础反向代理**：

```nginx
server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://127.0.0.1:8080;

        # 传递客户端信息给后端
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

**proxy_pass 的 URI 替换**：

```nginx
server {
    listen 80;

    # 情况1：不带 URI，完整转发
    location /api/ {
        proxy_pass http://backend;
        # 请求 /api/users → 后端收到 /api/users
    }

    # 情况2：带 URI，替换 location 匹配部分
    location /api/ {
        proxy_pass http://backend/v1/;
        # 请求 /api/users → 后端收到 /v1/users
    }

    # 情况3：精确前缀替换
    location /api/ {
        proxy_pass http://backend/;
        # 请求 /api/users → 后端收到 /users
    }

    # 情况4：正则 location，proxy_pass 不能带 URI
    location ~ ^/api/(.*)$ {
        proxy_pass http://backend/$1;
        # 请求 /api/users → 后端收到 /users
        # 注意：正则 location 中 proxy_pass 不能直接带 URI，
        # 需要用捕获组或 rewrite 处理
    }
}
```

**完整的反向代理配置（生产级）**：

```nginx
server {
    listen 80;
    server_name app.example.com;

    location / {
        proxy_pass http://127.0.0.1:8080;

        # ===== 请求头转发 =====
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # ===== 连接超时设置 =====
        proxy_connect_timeout 5s;     # 连接后端超时
        proxy_send_timeout 60s;       # 发送请求给后端超时
        proxy_read_timeout 60s;       # 读取后端响应超时

        # ===== 缓冲设置 =====
        proxy_buffering on;
        proxy_buffer_size 4k;         # 响应头缓冲区大小
        proxy_buffers 8 4k;           # 响应体缓冲区数量和大小
        proxy_busy_buffers_size 8k;   # 忙碌缓冲区大小

        # ===== 请求体大小限制 =====
        client_max_body_size 50m;     # 允许上传的最大文件

        # ===== WebSocket 支持 =====
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

**WebSocket 代理**：

```nginx
# WebSocket 需要特殊处理
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

server {
    listen 80;
    server_name ws.example.com;

    location /ws/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;

        # WebSocket 长连接，超时设长
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}
```

**proxy_redirect 修改重定向**：

```nginx
location /api/ {
    proxy_pass http://backend/;

    # 后端返回 Location: http://backend/login
    # 修改为 Location: http://example.com/api/login
    proxy_redirect http://backend/ http://example.com/api/;

    # 或者使用 default 自动处理
    proxy_redirect default;

    # 关闭 redirect 修改
    # proxy_redirect off;
}
```

#### 总结

- `proxy_pass` 是反向代理核心指令，带 URI 与不带 URI 的行为不同。
- 默认 Nginx 不传递客户端真实 IP，需通过 `X-Real-IP` 和 `X-Forwarded-For` 头传递。
- WebSocket 代理需要 `proxy_http_version 1.1` + `Upgrade`/`Connection` 头处理。
- `proxy_buffering on` 适合普通 API，`off` 适合流式响应（SSE、大文件）。
- **注意事项**：正则 location 中的 `proxy_pass` 不能直接带 URI，需用捕获组。`proxy_pass` 地址带 `/` 和不带 `/` 行为不同，是常见配置错误来源。生产环境务必设置合理的超时和请求体大小限制。

### 第11讲 upstream 模块与负载均衡算法

#### 概念

当后端有多个服务器时，Nginx 通过 `upstream` 模块将请求分发到不同的后端服务器，实现负载均衡。`upstream` 定义一组后端服务器，`proxy_pass` 引用这个组名，Nginx 根据负载均衡算法选择服务器。

Nginx 内置的负载均衡算法：
- **轮询**：默认算法，按顺序依次分配请求。
- **加权轮询**：根据 `weight` 参数按权重分配，权重高的服务器分配更多请求。
- **ip_hash**：根据客户端 IP 哈希分配，同一 IP 的请求总是到同一服务器（会话保持）。
- **least_conn**：将请求分配给当前连接数最少的服务器。
- **hash**：根据自定义 key 哈希分配（Nginx 1.7.2+）。
- **random**：随机分配（Nginx 1.15.1+）。

#### 原理

**1. 轮询**

默认算法，无需额外指令。假设有 3 台服务器 A、B、C，请求依次分配到 A→B→C→A→B→C...。每台服务器权重默认为 1。

**2. 加权轮询**

通过 `weight` 参数指定权重。权重越高，分配的请求比例越大。例如 A(weight=5)、B(weight=3)、C(weight=2)，则 10 个请求中 A 得 5 个、B 得 3 个、C 得 2 个。

Nginx 的加权轮询采用「平滑加权轮询」算法，不会连续将多个请求分配给高权重服务器，而是分散分配。例如权重 5:1:1，分配序列为 A-A-B-A-C-A-A（分散而非 AAAAA BC）。

**3. ip_hash**

对客户端 IP（`$remote_addr`）计算哈希值，根据哈希值和服务器数量取模，选择服务器。同一 IP 的请求总是到同一服务器，实现会话保持。

问题：如果服务器增减，哈希结果会变化，大量会话失效。且 IP 哈希可能导致负载不均（某些 IP 段流量大）。

**4. least_conn**

选择当前活跃连接数最少的服务器。如果多个服务器连接数相同，则用加权轮询选择。适合请求处理时间差异较大的场景（如某些请求耗时长）。

**5. hash（一致性哈希）**

`hash $key consistent;` 根据指定 key（如 `$uri`、`$request_uri`）计算哈希。`consistent` 参数启用一致性哈希（Ketama 算法），服务器增减时只有部分 key 重新映射，减少缓存失效。

#### 例子

**加权轮询**：

```nginx
http {
    upstream backend {
        server 192.168.1.10:8080 weight=3;   # 30% 请求
        server 192.168.1.11:8080 weight=2;   # 20% 请求
        server 192.168.1.12:8080 weight=5;   # 50% 请求
    }

    server {
        listen 80;
        location / {
            proxy_pass http://backend;
        }
    }
}
```

**ip_hash（会话保持）**：

```nginx
http {
    upstream backend {
        ip_hash;                              # 启用 IP 哈希
        server 192.168.1.10:8080;
        server 192.168.1.11:8080;
        server 192.168.1.12:8080;
    }

    server {
        listen 80;
        location / {
            proxy_pass http://backend;
        }
    }
}
```

**least_conn（最少连接）**：

```nginx
http {
    upstream backend {
        least_conn;                           # 启用最少连接算法
        server 192.168.1.10:8080 weight=3;
        server 192.168.1.11:8080 weight=2;
        server 192.168.1.12:8080 weight=5;
    }

    server {
        listen 80;
        location / {
            proxy_pass http://backend;
        }
    }
}
```

**一致性哈希（缓存场景）**：

```nginx
http {
    upstream backend {
        # 根据请求 URI 做一致性哈希
        hash $request_uri consistent;
        server 192.168.1.10:8080;
        server 192.168.1.11:8080;
        server 192.168.1.12:8080;
    }

    server {
        listen 80;
        location / {
            proxy_pass http://backend;
        }
    }
}
```

**服务器状态控制**：

```nginx
http {
    upstream backend {
        # down：标记服务器永久下线（不参与负载均衡）
        server 192.168.1.10:8080 down;

        # backup：备份服务器，仅当所有主服务器不可用时才启用
        server 192.168.1.11:8080 backup;

        # max_fails + fail_timeout：健康检查参数
        # 在 10 秒内失败 3 次，则标记为不可用 10 秒
        server 192.168.1.12:8080 max_fails=3 fail_timeout=10s;

        # max_conns：限制最大并发连接数
        server 192.168.1.13:8080 max_conns=100;

        # slow_start：慢启动，服务器恢复后逐渐增加权重（商业版功能）
        # server 192.168.1.14:8080 slow_start=30s;
    }

    server {
        listen 80;
        location / {
            proxy_pass http://backend;

            # 定义什么情况下切换到下一个服务器
            proxy_next_upstream error timeout http_500 http_502 http_503 http_504;
            proxy_next_upstream_tries 3;       # 最多尝试 3 个服务器
            proxy_next_upstream_timeout 10s;   # 重试总超时
        }
    }
}
```

**keepalive 连接复用**：

```nginx
http {
    upstream backend {
        server 192.168.1.10:8080;
        server 192.168.1.11:8080;

        # 保持到后端的长连接池
        keepalive 32;                          # 最多保持 32 个空闲连接
        keepalive_timeout 60s;                 # 空闲连接超时
    }

    server {
        listen 80;
        location / {
            proxy_pass http://backend;

            # 必须设置 HTTP/1.1 才能复用长连接
            proxy_http_version 1.1;
            proxy_set_header Connection "";    # 清除 Connection 头
        }
    }
}
```

#### 总结

- 默认轮询，`weight` 实现加权轮询，`ip_hash` 实现会话保持，`least_conn` 适合处理时间差异大的场景。
- 一致性哈希（`hash ... consistent`）适合缓存场景，服务器增减时减少缓存失效。
- `down`/`backup`/`max_fails`/`fail_timeout` 控制服务器状态和健康检查。
- `keepalive` 复用到后端的长连接，减少连接建立开销，需配合 `proxy_http_version 1.1`。
- **注意事项**：`ip_hash` 在 IPv6 环境下取前 3 段哈希。`least_conn` 需配合 `weight` 才能发挥最佳效果。`proxy_next_upstream` 在 POST 等非幂等请求上要谨慎，可能导致重复提交。

### 第12讲 健康检查与会话保持

#### 概念

在生产环境中，后端服务器可能出现故障或需要维护。Nginx 需要能自动检测后端健康状态，将请求绕过故障服务器。同时，某些应用需要会话保持（同一用户的请求始终到同一服务器），以保证会话数据的一致性。

- **被动健康检查**：Nginx 开源版内置，通过实际请求的失败次数判断服务器是否不可用。
- **主动健康检查**：Nginx Plus（商业版）或第三方模块（如 `nginx_upstream_check_module`）提供，定期主动探测后端健康状态。
- **会话保持**：`ip_hash`（基于 IP）、`hash`（基于自定义 key）、`sticky`（基于 Cookie，商业版或第三方模块）。

#### 原理

**1. 被动健康检查**

Nginx 开源版通过 `max_fails` 和 `fail_timeout` 实现被动健康检查：
- `max_fails=N`：在 `fail_timeout` 时间窗口内，允许的最大失败次数。
- `fail_timeout=T`：失败次数达到 `max_fails` 后，服务器被标记为不可用的时长。

「失败」的定义由 `proxy_next_upstream` 指令决定，默认包括 `error`（连接错误）和 `timeout`（超时）。可以扩展为包含 HTTP 错误码（如 `http_500`、`http_502`）。

当服务器被标记为不可用后，在 `fail_timeout` 期间不会有请求分配给它。超时后，Nginx 会尝试少量请求，如果成功则恢复，如果失败则继续标记不可用。

**被动检查的局限**：只能检测「请求失败」的情况，无法主动探测。如果后端服务器虽然能接受连接但返回错误，需要配置 `proxy_next_upstream` 包含对应错误码。服务器恢复后，需要等待 `fail_timeout` 过期才能重新接收请求。

**2. 主动健康检查（Nginx Plus）**

```nginx
upstream backend {
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;

    health_check interval=5s uri=/health path=/health
                 match=healthy;
}

match healthy {
    status 200;
    header Content-Type = application/json;
    body ~ '"status":"ok"';
}
```

Nginx Plus 定期（`interval`）向 `uri` 发送健康检查请求，根据 `match` 规则判断响应是否健康。开源版需要第三方模块实现类似功能。

**3. 会话保持机制**

- **ip_hash**：基于客户端 IP 哈希。简单但不够灵活（代理后 IP 集中、负载可能不均）。
- **hash**：基于任意 key 哈希（如 `$cookie_sessionid`），配合 `consistent` 实现一致性哈希。
- **sticky cookie**（商业版/第三方）：Nginx 在首次响应中设置 Cookie，后续请求根据 Cookie 路由到同一服务器。
- **sticky learn**（商业版）：Nginx 学习后端响应中的 Session ID，自动路由。

#### 例子

**被动健康检查**：

```nginx
http {
    upstream backend {
        # 10 秒内失败 3 次，标记不可用 10 秒
        server 192.168.1.10:8080 max_fails=3 fail_timeout=10s;
        server 192.168.1.11:8080 max_fails=3 fail_timeout=10s;
        server 192.168.1.12:8080 max_fails=3 fail_timeout=10s backup;
    }

    server {
        listen 80;
        location / {
            proxy_pass http://backend;

            # 定义什么情况算「失败」，触发切换
            proxy_next_upstream error timeout
                                http_500 http_502 http_503 http_504
                                http_403 http_404;

            # 重试次数和超时
            proxy_next_upstream_tries 3;
            proxy_next_upstream_timeout 15s;

            # 超时设置
            proxy_connect_timeout 3s;
            proxy_read_timeout 10s;
        }
    }
}
```

**基于 Cookie 的会话保持（第三方模块 nginx-sticky-module）**：

```nginx
http {
    upstream backend {
        sticky name=server_id expires=1h domain=.example.com path=/;

        server 192.168.1.10:8080;
        server 192.168.1.11:8080;
        server 192.168.1.12:8080;
    }

    server {
        listen 80;
        location / {
            proxy_pass http://backend;
        }
    }
}
```

工作原理：首次请求时，Nginx 选择一个后端服务器（如 192.168.1.10），在响应中设置 Cookie `server_id=server1`。后续请求携带该 Cookie，Nginx 根据 Cookie 值路由到对应服务器。

**基于一致性哈希的会话保持**：

```nginx
http {
    upstream backend {
        # 根据会话 Cookie 做一致性哈希
        hash $cookie_session_id consistent;

        server 192.168.1.10:8080;
        server 192.168.1.11:8080;
        server 192.168.1.12:8080;
    }

    server {
        listen 80;
        location / {
            proxy_pass http://backend;
        }
    }
}
```

**综合示例：生产级负载均衡配置**：

```nginx
http {
    upstream web_backend {
        # 最少连接 + 加权
        least_conn;

        server 192.168.1.10:8080 weight=3 max_fails=3 fail_timeout=15s max_conns=500;
        server 192.168.1.11:8080 weight=3 max_fails=3 fail_timeout=15s max_conns=500;
        server 192.168.1.12:8080 weight=2 max_fails=3 fail_timeout=15s max_conns=300;
        server 192.168.1.13:8080 backup;    # 备用服务器

        # 长连接复用
        keepalive 64;
    }

    server {
        listen 80;
        server_name app.example.com;

        location / {
            proxy_pass http://web_backend;

            # 请求头
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;

            # 长连接
            proxy_http_version 1.1;
            proxy_set_header Connection "";

            # 健康检查：失败时切换
            proxy_next_upstream error timeout http_502 http_503 http_504;
            proxy_next_upstream_tries 2;
            proxy_next_upstream_timeout 10s;

            # 超时
            proxy_connect_timeout 3s;
            proxy_send_timeout 30s;
            proxy_read_timeout 30s;
        }
    }
}
```

#### 总结

- 开源版 Nginx 使用被动健康检查（`max_fails` + `fail_timeout`），主动检查需 Nginx Plus 或第三方模块。
- `proxy_next_upstream` 定义失败条件，注意非幂等请求（POST/DELETE）的重试风险。
- 会话保持方案：`ip_hash`（简单）、`hash $cookie_xxx consistent`（灵活）、`sticky`（商业版/第三方）。
- `max_conns` 限制单服务器并发连接，防止过载。
- **注意事项**：被动健康检查有延迟（需等失败次数累计），不适合对可用性要求极高的场景。会话保持与负载均衡存在矛盾（绑定后无法动态调整），建议后端使用共享 Session 存储（如 Redis）从根本上解决。`backup` 服务器仅在所有主服务器不可用时启用，适合降级方案。

## 第五章 HTTPS 与安全

### 第13讲 SSL/TLS 配置与证书管理

#### 概念

HTTPS（HTTP over TLS/SSL）通过加密传输保护数据安全，是现代 Web 应用的标配。Nginx 作为反向代理，常用于 SSL 卸载——在 Nginx 层处理 HTTPS 加密/解密，与后端使用 HTTP 明文通信，减轻后端加密负担。

- **SSL/TLS**：传输层安全协议，提供加密、身份认证、数据完整性保护。SSL 已被弃用，现代使用 TLS 1.2/1.3。
- **证书**：由 CA（证书颁发机构）签名的数字证书，证明服务器身份。包含公钥和域名信息。
- **证书链**：服务器证书 → 中间证书 → 根证书。Nginx 需配置完整证书链。
- **Let's Encrypt**：免费的自动化 CA，通过 ACME 协议自动签发和续期证书。

#### 原理

**1. TLS 握手流程**

```
客户端                              服务器
  |                                   |
  | ---- Client Hello --------------→ |  (支持的TLS版本、加密套件、随机数)
  |                                   |
  | ←--- Server Hello --------------- |  (选定TLS版本、加密套件、随机数)
  | ←--- Certificate ---------------- |  (服务器证书)
  | ←--- Server Key Exchange -------- |  (DH参数，如使用)
  | ←--- Server Hello Done ---------- |
  |                                   |
  | ---- Client Key Exchange ------→ |  (预主密钥，用服务器公钥加密)
  | ---- Change Cipher Spec ------→ |
  | ---- Finished -----------------→ |  (加密验证)
  |                                   |
  | ←--- Change Cipher Spec -------- |
  | ←--- Finished ------------------- |
  |                                   |
  | ←=== 加密通信开始 ===============→ |
```

TLS 1.3 简化了握手流程（1-RTT 甚至 0-RTT），提升了性能。

**2. 证书文件格式**

- **证书**：`.crt` 或 `.pem` 格式，PEM 编码（Base64 文本）。
- **私钥**：`.key` 格式，PEM 编码。必须保密，权限设为 600。
- **证书链**：服务器证书 + 中间证书合并为一个文件，Nginx 通过 `ssl_certificate` 指定。

**3. 加密套件**

加密套件决定密钥交换、认证、加密、MAC 算法的组合。如 `ECDHE-RSA-AES256-GCM-SHA384` 表示：ECDHE 密钥交换 + RSA 认证 + AES256-GCM 加密 + SHA384 MAC。

现代推荐使用前向安全（Forward Secrecy）的 ECDHE 套件，禁用不安全的 RC4、DES、MD5。

#### 例子

**基础 HTTPS 配置**：

```nginx
server {
    listen 443 ssl;
    server_name www.example.com;

    # 证书和私钥
    ssl_certificate     /etc/nginx/ssl/example.com.crt;   # 含证书链
    ssl_certificate_key /etc/nginx/ssl/example.com.key;   # 私钥

    # TLS 版本
    ssl_protocols TLSv1.2 TLSv1.3;    # 仅启用 TLS 1.2 和 1.3
    # ssl_protocols TLSv1.3;          # 更严格：仅 TLS 1.3

    # 加密套件
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
    ssl_prefer_server_ciphers on;     # 优先使用服务器端选择的套件

    # 会话缓存（减少握手开销）
    ssl_session_cache shared:SSL:10m; # 10MB 缓存，约 4 万个会话
    ssl_session_timeout 10m;          # 会话缓存超时
    ssl_session_tickets on;           # 启用 Session Ticket

    root /var/www/site;
    index index.html;
}
```

```nginx
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;
```

**OCSP Stapling（在线证书状态协议装订）**：

```nginx

    listen 443 ssl;

    ssl_certificate_key /etc/nginx/ssl/example.com.key;

    ssl_stapling on;
    ssl_stapling_verify on;
    ssl_trusted_certificate /etc/nginx/ssl/example.com.crt;  # 含根证书
```

```nginx
    ssl_early_data on;
```

- HTTPS 配置核心：`ssl_certificate`（证书链）+ `ssl_certificate_key`（私钥）+ `ssl_protocols`（TLS 版本）+ `ssl_ciphers`（加密套件）。
- 推荐仅启用 TLS 1.2 和 1.3，禁用 TLS 1.0/1.1 和 SSL。
- `ssl_session_cache` 和 `ssl_session_tickets` 减少握手开销，提升性能。
- Let's Encrypt + certbot 是获取免费证书的标准方案，支持自动续期。
- **注意事项**：私钥文件权限必须设为 600（仅 root 可读）。证书链不完整会导致部分浏览器报错。HSTS 一旦启用，浏览器会强制 HTTPS 访问，确保 HTTPS 配置稳定后再启用 `preload`。OCSP Stapling 需要配置 `resolver` 和 `ssl_trusted_certificate`。

### 第14讲 安全响应头与 HTTP 强制跳转

#### 概念

除了 HTTPS 加密传输，Web 安全还需要通过 HTTP 响应头向浏览器传达安全策略。这些安全头可以防御 XSS、点击劫持、MIME 嗅探、协议降级等攻击。Nginx 通过 `add_header` 指令添加安全响应头。

核心安全头：
- **HSTS**：强制 HTTPS，防止协议降级攻击。
- **CSP**：内容安全策略，限制资源加载来源，防御 XSS。
- **X-Frame-Options**：防止页面被 iframe 嵌套，防御点击劫持。
- **X-Content-Type-Options**：禁止 MIME 嗅探。
- **X-XSS-Protection**：启用浏览器 XSS 过滤器（已被 CSP 取代，但仍有兼容价值）。
- **Referrer-Policy**：控制 Referer 头的发送策略。
- **Permissions-Policy**：控制浏览器功能（摄像头、麦克风、地理位置等）的访问权限。

#### 原理

**1. HSTS（Strict-Transport-Security）**

告诉浏览器在指定时间内（`max-age`）只使用 HTTPS 访问该站点。即使用户输入 HTTP URL，浏览器也会自动跳转到 HTTPS。`includeSubDomains` 扩展到子域名，`preload` 允许加入浏览器的 HSTS 预加载列表。

**2. CSP（Content-Security-Policy）**

通过白名单机制限制页面可以加载的资源来源。例如 `default-src 'self'` 只允许加载同源资源，`script-src 'self' https://cdn.example.com` 只允许同源和指定 CDN 的脚本。CSP 是防御 XSS 最有效的手段之一。

**3. X-Frame-Options**

- `DENY`：页面不允许被任何 iframe 嵌套。
- `SAMEORIGIN`：仅允许同源页面嵌套。
- `ALLOW-FROM uri`：允许指定来源嵌套（已被废弃，使用 CSP `frame-ancestors` 替代）。

**4. X-Content-Type-Options: nosniff**

禁止浏览器猜测（嗅探）响应的 MIME 类型。没有这个头，浏览器可能将 `text/plain` 的响应当作 HTML 执行，导致 XSS。

**5. add_header 的 always 参数**

`add_header` 默认只在响应状态码为 200/201/204/206/301/302/303/304/307/308 时生效。加上 `always` 参数后，所有状态码（包括 4xx/5xx）都会添加该头。安全头通常需要 `always`，确保错误页面也有安全保护。

#### 例子

**完整的安全响应头配置**：

```nginx
server {
    listen 443 ssl;
    server_name www.example.com;

    ssl_certificate     /etc/nginx/ssl/example.com.crt;
    ssl_certificate_key /etc/nginx/ssl/example.com.key;

    # ===== 安全响应头 =====

    # HSTS：强制 HTTPS，1年有效期，含子域名
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;

    # X-Frame-Options：防止点击劫持
    add_header X-Frame-Options "SAMEORIGIN" always;

    # X-Content-Type-Options：禁止 MIME 嗅探
    add_header X-Content-Type-Options "nosniff" always;

    # X-XSS-Protection：启用浏览器 XSS 过滤器（旧浏览器兼容）
    add_header X-XSS-Protection "1; mode=block" always;

    # Referrer-Policy：控制 Referer 发送
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;

    # Permissions-Policy：禁用不必要的浏览器功能
    add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;

    # CSP：内容安全策略
    add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'unsafe-inline' https://cdn.example.com; style-src 'self' 'unsafe-inline' https://cdn.example.com; img-src 'self' data: https:; font-src 'self' https://cdn.example.com; connect-src 'self' https://api.example.com; frame-ancestors 'self'; base-uri 'self'; form-action 'self'" always;

    root /var/www/site;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

**HTTP 强制跳转 HTTPS（多种方式）**：

```nginx
# 方式1：return 301（推荐，最简洁高效）
server {
    listen 80;
    server_name www.example.com;
    return 301 https://$host$request_uri;
}

# 方式2：rewrite
server {
    listen 80;
    server_name www.example.com;
    rewrite ^ https://$host$request_uri? permanent;
}

# 方式3：if 判断（不推荐，但有时需要条件跳转）
server {
    listen 80;
    server_name www.example.com;

    if ($scheme = http) {
        return 301 https://$host$request_uri;
    }
}
```

**统一的安全配置片段（可复用）**：

```nginx

# 通过 include 引入到各 server 块

add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-XSS-Protection "1; mode=block" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;
```

```nginx

    listen 443 ssl;
    server_name www.example.com;
    ssl_certificate     /etc/nginx/ssl/example.com.crt;
    ssl_certificate_key /etc/nginx/ssl/example.com.key;

    include snippets/security-headers.conf;

    # 注意：如果在 location 中使用了 add_header，
    # 上面的安全头会失效（数组指令继承陷阱），需要重新引入
    location /api/ {
        include snippets/security-headers.conf;
        add_header X-API-Version "v1";    # 额外的头
        proxy_pass http://backend;
    }
}
```

**隐藏 Nginx 版本号**：

```nginx
# nginx.conf 的 http 块中
http {
    server_tokens off;    # 隐藏响应头 Server 和错误页中的版本号
    # server_tokens build on;  # Nginx 1.11.10+ 可隐藏 build 信息
}
```

#### 总结

- 安全响应头是 Web 安全的重要防线，核心包括 HSTS、CSP、X-Frame-Options、X-Content-Type-Options。
- `add_header` 必须加 `always` 参数，确保错误页面也有安全头。
- HTTP 强制跳转 HTTPS 推荐 `return 301`，简洁高效。
- 安全头配置建议封装为 snippet，通过 `include` 复用，避免重复。
- **注意事项**：`add_header` 的数组指令继承陷阱——在 `location` 中使用 `add_header` 会清除 `server`/`http` 级别的 `add_header`，需要重新声明或引入 snippet。CSP 策略较复杂，建议先用 `Content-Security-Policy-Report-Only` 观察违规报告，再正式启用。HSTS 的 `preload` 一旦提交到预加载列表，移除困难，确保 HTTPS 配置长期稳定后再启用。

### 第15讲 访问控制、限流与防 CC

#### 概念

Nginx 可以在请求处理的不同阶段实施访问控制和流量控制，保护后端服务免受恶意访问和过载。

- **allow / deny**：基于 IP 的访问控制（黑白名单）。
- **limit_req**：请求速率限制（令牌桶算法），防 CC 攻击、防爬虫。
- **limit_conn**：并发连接数限制，防止单 IP 占用过多连接。
- **limit_req 的 burst 和 nodelay**：控制突发流量的处理方式。
- **auth_basic**：HTTP 基本认证，简单的密码保护。

#### 原理

**1. allow / deny**

按配置顺序匹配，第一个匹配的规则生效。可以放在 `http`、`server`、`location`、`limit_except` 上下文中。

```nginx
location /admin/ {
    allow 192.168.1.0/24;    # 允许内网
    allow 10.0.0.0/8;
    deny all;                # 拒绝其他
}
```

**2. limit_req（请求速率限制）**

基于**令牌桶算法**（Leaky Bucket 的变体）：
- `limit_req_zone` 定义一个共享内存区域，存储每个 key 的请求状态。
- `rate` 指定每秒/每分钟允许的请求数。
- `limit_req` 在 location 中启用限制。
- `burst` 允许的突发请求数（排队等待）。
- `nodelay` 突发请求不延迟，立即处理（超出则拒绝）。
- `delay` 突发请求中前 N 个立即处理，其余延迟。

工作流程：
1. 请求到达，Nginx 检查对应 key 的当前速率。
2. 如果未超限，请求通过，更新时间戳。
3. 如果超限但有 burst 余量，请求排队（延迟处理）或立即处理（nodelay）。
4. 如果 burst 也满了，返回 503（默认）或指定状态码。

**3. limit_conn（并发连接数限制）**

限制同一 key 的并发连接数。与 `limit_req` 不同，`limit_conn` 限制的是「同时活跃的连接数」而非「请求速率」。

**4. auth_basic（HTTP 基本认证）**

使用 `htpasswd` 生成的密码文件，浏览器弹出登录框。密码以 Base64 编码传输（非加密），必须配合 HTTPS 使用。

#### 例子

**IP 访问控制**：

```nginx
server {
    listen 80;

    # 全局：仅允许内网访问
    # allow 192.168.0.0/16;
    # allow 10.0.0.0/8;
    # deny all;

    location / {
        allow 192.168.1.0/24;
        allow 10.0.0.0/8;
        deny all;
        proxy_pass http://backend;
    }

    # 管理后台：仅允许特定 IP
    location /admin/ {
        allow 192.168.1.100;    # 管理员 IP
        allow 192.168.1.101;
        deny all;
        proxy_pass http://backend;
    }

    # 限制特定 HTTP 方法
    location /api/ {
        limit_except GET POST {
            deny all;           # 仅允许 GET 和 POST
        }
        proxy_pass http://backend;
    }
}
```

**请求速率限制（防 CC）**：

```nginx
http {
    # 定义限流区域：按客户端 IP，每秒 10 个请求
    limit_req_zone $binary_remote_addr zone=req_limit:10m rate=10r/s;

    # 定义连接数限制区域：按客户端 IP，最多 20 个并发连接
    limit_conn_zone $binary_remote_addr zone=conn_limit:10m;

    server {
        listen 80;

        # 全局连接数限制
        limit_conn conn_limit 20;

        location /api/ {
            # 请求速率限制：突发 20 个请求，不延迟
            limit_req zone=req_limit burst=20 nodelay;

            # 超限时返回 429 而非默认 503
            limit_req_status 429;
            limit_conn_status 429;

            proxy_pass http://backend;
        }

        # 更严格的限制：登录接口
        location /api/login {
            # 每秒 1 个请求，突发 5 个
            limit_req zone=login_limit burst=5 nodelay;
            proxy_pass http://backend;
        }
    }

    # 登录接口专用限流区域
    limit_req_zone $binary_remote_addr zone=login_limit:10m rate=1r/s;
}
```

**limit_req 的 burst 和 nodelay 对比**：

```nginx
# 假设 rate=10r/s

# 配置1：无 burst
# 超过 10r/s 的请求立即 503
limit_req zone=api_limit;

# 配置2：burst=20，无 nodelay
# 突发 20 个请求排队等待（按 rate 处理），超过 20 个 503
# 请求会被延迟处理
limit_req zone=api_limit burst=20;

# 配置3：burst=20 + nodelay
# 突发 20 个请求立即处理，超过 20 个 503
# 请求不会被延迟
limit_req zone=api_limit burst=20 nodelay;

# 配置4：burst=20 + delay=5
# 前 5 个突发请求立即处理，第 6-20 个延迟处理，超过 20 个 503
limit_req zone=api_limit burst=20 delay=5;
```

**HTTP 基本认证**：

```bash
# 安装 htpasswd 工具
sudo apt install apache2-utils

# 创建密码文件和用户
sudo htpasswd -c /etc/nginx/.htpasswd admin
# 输入密码

# 添加更多用户（不加 -c）
sudo htpasswd /etc/nginx/.htpasswd user2
```

```nginx
server {
    listen 80;
    server_name admin.example.com;

    # 全站需要认证
    auth_basic "Restricted Area";
    auth_basic_user_file /etc/nginx/.htpasswd;

    location / {
        proxy_pass http://backend;
    }

    # 特定路径免认证
    location /public/ {
        auth_basic off;    # 关闭认证
        proxy_pass http://backend;
    }
}
```

**综合防 CC 策略**：

```nginx
http {
    # 按 IP 限流
    limit_req_zone $binary_remote_addr zone=ip_limit:10m rate=10r/s;

    # 按 URI 限流（针对敏感接口）
    limit_req_zone $binary_remote_addr zone=api_limit:10m rate=5r/s;
    limit_req_zone $binary_remote_addr zone=login_limit:10m rate=1r/s;

    # 连接数限制
    limit_conn_zone $binary_remote_addr zone=conn_limit:10m;

    # 按 User-Agent 限流（封禁恶意爬虫）
    map $http_user_agent $limit_bots {
        default 0;
        ~*bot    1;
        ~*spider 1;
        ~*scrapy 1;
    }

    limit_req_zone $limit_bots$binary_remote_addr zone=bot_limit:10m rate=1r/s;

    server {
        listen 80;

        # 全局连接数限制
        limit_conn conn_limit 50;

        # 全局限流
        limit_req zone=ip_limit burst=20 nodelay;

        location / {
            proxy_pass http://backend;
        }

        location /api/ {
            limit_req zone=api_limit burst=10 nodelay;
            proxy_pass http://backend;
        }

        location /api/login {
            limit_req zone=login_limit burst=3 nodelay;
            proxy_pass http://backend;
        }

        # 返回自定义错误页
        error_page 429 = @rate_limited;
        location @rate_limited {
            default_type application/json;
            return 429 '{"error":"Too Many Requests","retry_after":60}';
        }
    }
}
```

#### 总结

- `allow`/`deny` 实现 IP 黑白名单，按顺序匹配，第一个命中生效。
- `limit_req` 基于令牌桶算法限制请求速率，`burst` 控制突发，`nodelay` 控制延迟。
- `limit_conn` 限制并发连接数，与 `limit_req` 配合使用。
- `auth_basic` 实现 HTTP 基本认证，必须配合 HTTPS 使用。
- **注意事项**：`limit_req_zone` 的 `zone` 大小：1MB 约可存储 1.6 万个 IP 状态（使用 `$binary_remote_addr`）。`$binary_remote_addr` 比 `$remote_addr` 节省内存（4 字节 vs 7-15 字节）。限流 key 的选择很重要：按 IP 可能误伤 NAT 后的用户，可考虑按 `$http_x_forwarded_for` 或业务 token 限流。`burst` 和 `nodelay` 的组合需要根据业务场景调整，过大起不到保护作用，过小影响正常用户。

## 第六章 性能优化

### 第16讲 缓存机制：代理缓存与 FastCGI 缓存

#### 概念

缓存是提升 Web 性能最有效的手段之一。Nginx 提供了多层缓存能力：

- **代理缓存**：缓存后端服务器的响应，后续相同请求直接从 Nginx 缓存返回，不转发给后端。
- **FastCGI 缓存**：缓存 FastCGI 后端（如 PHP-FPM）的响应。
- **浏览器缓存**：通过 `Cache-Control`、`Expires` 等响应头指导浏览器缓存。
- **代理缓存路径**：定义缓存存储位置、大小、层级。

#### 原理

**1. 代理缓存的工作流程**

```
客户端请求 → Nginx 检查缓存
                ↓
        缓存命中？ → 是 → 返回缓存内容（HIT）
                ↓ 否
        转发请求给后端 → 后端返回响应
                ↓
        Nginx 缓存响应 → 返回给客户端（MISS）
```

**2. 缓存 Key**

Nginx 通过 `proxy_cache_key` 定义缓存的唯一标识，默认为 `$scheme$proxy_host$request_uri`。可以根据需要自定义，如加入 `$http_accept` 区分不同格式响应。

**3. 缓存有效期**

- 后端通过 `Cache-Control`、`Expires` 响应头控制缓存时间。
- `proxy_cache_valid` 指令按状态码指定缓存时间。
- `proxy_cache_min_uses` 指定请求多少次后才缓存（默认 1）。
- `proxy_cache_use_stale` 在后端故障时使用过期缓存（提升可用性）。

**4. 缓存清理**

Nginx 开源版不提供主动清理单个缓存项的指令（商业版有 `proxy_cache_purge`）。常见方案：
- 第三方模块 `ngx_cache_purge`。
- 删除缓存目录下对应文件（粗暴但有效）。
- 修改 `proxy_cache_key` 中的版本号使旧缓存失效。

#### 例子

**代理缓存基础配置**：

```nginx
http {
    # 定义缓存路径
    # levels=1:2 两级目录，keys_zone 名称和大小，max_size 最大空间，inactive 不活跃删除时间
    proxy_cache_path /var/cache/nginx/proxy
                     levels=1:2
                     keys_zone=api_cache:10m     # 10MB 共享内存，存 key 索引
                     max_size=1g                 # 磁盘最大 1GB
                     inactive=60m                # 60 分钟无访问则删除
                     use_temp_path=off;          # 临时文件直接写在缓存目录

    server {
        listen 80;

        location /api/ {
            proxy_pass http://backend;

            # 启用缓存
            proxy_cache api_cache;

            # 缓存 Key
            proxy_cache_key "$scheme$request_method$host$request_uri";

            # 按状态码设置缓存时间
            proxy_cache_valid 200 302 10m;    # 200/302 缓存 10 分钟
            proxy_cache_valid 404 1m;         # 404 缓存 1 分钟
            proxy_cache_valid 500 502 503 504 0;  # 5xx 不缓存

            # 后端故障时使用过期缓存
            proxy_cache_use_stale error timeout updating
                                 http_500 http_502 http_503 http_504;

            # 缓存锁定：防止缓存失效时多个请求同时打后端（狗群效应）
            proxy_cache_lock on;
            proxy_cache_lock_timeout 5s;

            # 添加响应头显示缓存状态
            add_header X-Cache-Status $upstream_cache_status;
            # HIT: 缓存命中
            # MISS: 缓存未命中
            # EXPIRED: 缓存过期
            # STALE: 使用过期缓存
            # UPDATING: 缓存正在更新
            # REVALIDATED: 缓存重新验证有效
        }
    }
}
```

- 代理缓存通过 `proxy_cache_path` 定义存储，`proxy_cache` 启用，`proxy_cache_valid` 设置有效期。

### 第17讲 Gzip 压缩与连接优化

#### 概念

传输优化是减少带宽消耗、提升页面加载速度的关键手段。Nginx 提供了多种优化机制：

- **Gzip 压缩**：压缩响应体，减少传输数据量。
- **Brotli 压缩**：比 Gzip 压缩率更高的现代压缩算法（需第三方模块）。
- **sendfile**：零拷贝技术，减少内核空间到用户空间的数据拷贝。
- **keepalive**：复用 TCP 连接，减少连接建立开销。
- **tcp_nodelay / tcp_nopush**：优化 TCP 数据包发送策略。
- **HTTP/2**：多路复用、头部压缩，大幅提升并发性能。

#### 原理

**1. Gzip 压缩**

Nginx 通过 `gzip` 模块对响应体进行 Gzip 压缩。浏览器发送 `Accept-Encoding: gzip` 请求头表示支持压缩，Nginx 压缩后返回 `Content-Encoding: gzip` 响应头。

压缩效果：文本文件（HTML/CSS/JS）通常可压缩 60-80%，图片和视频已经是压缩格式，再压缩效果甚微且浪费 CPU。

**2. sendfile 零拷贝**

传统文件传输：磁盘 → 内核缓冲区 → 用户缓冲区 → socket 缓冲区 → 网卡。`sendfile` 系统调用直接在内核空间从文件描述符拷贝到 socket，省去用户空间中转，大幅提升静态文件传输效率。

**3. keepalive 连接复用**

HTTP/1.1 默认开启 keepalive，一个 TCP 连接可以发送多个请求。`keepalive_timeout` 控制连接保持时间，`keepalive_requests` 控制单连接最大请求数。复用连接避免了每次请求的 TCP 三次握手和 TLS 握手开销。

**4. tcp_nopush 和 tcp_nodelay**

这两个看似矛盾的选项实际上配合使用：
- `tcp_nopush on`：数据积累到一定量再发送（适合 sendfile 传输大文件，确保 HTTP 头和文件内容在一个包内发送）。
- `tcp_nodelay on`：禁用 Nagle 算法，数据立即发送（适合小数据、实时通信）。

Nginx 同时启用两者：在 sendfile 传输时用 `tcp_nopush` 积累数据，传输完成后切换到 `tcp_nodelay` 立即发送剩余数据。

**5. HTTP/2**

HTTP/2 引入多路复用（一个连接并发多个请求）、头部压缩（HPACK）、服务器推送等特性。Nginx 通过 `listen 443 ssl http2` 启用。注意 HTTP/2 要求 HTTPS。

#### 例子

**Gzip 压缩配置**：

```nginx
http {
    # 启用 Gzip
    gzip on;

    # 压缩级别（1-9，1 最快压缩率最低，9 最慢压缩率最高）
    # 推荐 4-6，平衡 CPU 和压缩率
    gzip_comp_level 5;

    # 最小压缩文件大小（小于此值不压缩，压缩开销大于收益）
    gzip_min_length 1k;

    # 压缩的 MIME 类型
    gzip_types
        text/plain
        text/css
        text/xml
        text/javascript
        application/javascript
        application/x-javascript
        application/json
        application/xml
        application/xml+rss
        application/xhtml+xml
        application/x-font-ttf
        application/x-font-opentype
        application/vnd.ms-fontobject
        image/svg+xml
        image/x-icon
        font/woff
        font/woff2;

    # 不压缩的 MIME 类型（已经是压缩格式）
    # gzip_types 默认只压缩 text/html

    # 对代理请求也压缩
    gzip_vary on;              # 添加 Vary: Accept-Encoding 响应头
    gzip_proxied any;          # 对所有代理请求压缩
    # gzip_proxied no-cache no-store private expired auth;

    # 压缩缓冲区
    gzip_buffers 16 8k;        # 16 个 8KB 缓冲区

    # 禁用对特定浏览器的压缩（IE6 有 bug）
    gzip_disable "MSIE [1-6]\.";
}
```

```nginx
            open_file_cache_min_uses 2;
            open_file_cache_errors on;
```

#### 总结

- Gzip 压缩文本资源可减少 60-80% 传输量，压缩级别 4-6 平衡 CPU 和效果。
- `sendfile on` + `tcp_nopush on` + `tcp_nodelay on` 是静态文件传输的标准优化组合。
- `keepalive_timeout` 和 `keepalive_requests` 控制客户端连接复用，减少握手开销。
- 上游 keepalive 连接池需配合 `proxy_http_version 1.1` 和 `proxy_set_header Connection ""`。
- **注意事项**：不要压缩已压缩的格式（图片、视频、zip），浪费 CPU 且无效果。`gzip_comp_level` 超过 6 收益递减。HTTP/2 要求 HTTPS。`open_file_cache` 缓存文件描述符和元数据，减少 `stat` 系统调用，对高频访问的静态文件有显著优化。Brotli 压缩率比 Gzip 高 15-25%，但需要安装 `ngx_brotli` 模块。

### 第18讲 worker 调优与内核参数

#### 概念

Nginx 的性能不仅取决于自身配置，还受操作系统内核参数的影响。生产环境部署需要同时调整 Nginx 配置和系统内核参数，才能充分发挥硬件性能。

- **worker_processes / worker_connections**：控制 Nginx 的并发处理能力。
- **worker_cpu_affinity**：CPU 亲和性绑定，减少缓存失效。
- **worker_rlimit_nofile**：文件描述符上限。
- **内核参数**：`somaxconn`、`tcp_max_syn_backlog`、`net.core.somaxconn`、`fs.file-max` 等。
- **TIME_WAIT 优化**：`tcp_tw_reuse`、`keepalive` 减少 TIME_WAIT 状态连接。

#### 原理

**1. worker 进程数选择**

`worker_processes` 应等于 CPU 核心数（或 `auto`）。每个 worker 是单线程事件循环，多 worker 利用多核。超过 CPU 核心数的 worker 会导致频繁上下文切换，反而降低性能。

**2. worker_connections 计算**

单 worker 的最大连接数。作为 Web 服务器，最大并发 = `worker_processes × worker_connections`。作为反向代理，每个客户端连接消耗 2 个连接（客户端 + 后端），最大并发 = `worker_processes × worker_connections / 2`。

**3. 文件描述符限制**

每个连接、每个打开的文件都占用一个文件描述符。Linux 默认的 `ulimit -n` 通常为 1024，远不够高并发场景。需要同时调整：
- `worker_rlimit_nofile`：Nginx worker 进程的 fd 上限。
- `/etc/security/limits.conf`：系统用户 fd 上限。
- `/proc/sys/fs/file-max`：系统全局 fd 上限。

**4. TCP backlog**

`listen 80 backlog=8192;` 设置监听队列长度。当 Nginx 来不及 accept 新连接时，连接在 backlog 队列等待。系统内核参数 `net.core.somaxconn` 和 `net.ipv4.tcp_max_syn_backlog` 限制最大值。

**5. TIME_WAIT 优化**

短连接场景下，主动关闭连接的一方会进入 TIME_WAIT 状态（持续 60 秒），大量 TIME_WAIT 会耗尽端口。优化方案：
- 启用 keepalive 复用连接。
- `net.ipv4.tcp_tw_reuse = 1` 允许复用 TIME_WAIT 连接。
- 调整 `net.ipv4.tcp_fin_timeout` 缩短 TIME_WAIT 时长。

#### 例子

**Nginx 配置优化**：

```nginx
# /etc/nginx/nginx.conf

user nginx;
# worker 进程数 = CPU 核心数
worker_processes auto;
# worker_cpu_affinity auto;  # 自动绑定 CPU 亲和性
# 或手动绑定（4核）：
# worker_cpu_affinity 0001 0010 0100 1000;

# worker 进程最大文件描述符数
worker_rlimit_nofile 65535;

# 错误日志
error_log /var/log/nginx/error.log warn;
pid /var/run/nginx.pid;

events {
    # 每个 worker 最大连接数
    worker_connections 10240;

    # 事件模型
    use epoll;

    # 允许一次 accept 多个连接
    multi_accept on;
}

http {
    # ===== 基础优化 =====
    sendfile on;
    tcp_nopush on;
    tcp_nodelay on;

    keepalive_timeout 65s;
    keepalive_requests 1000;

    # ===== 缓冲区优化 =====
    client_body_buffer_size 16k;
    client_header_buffer_size 4k;
    large_client_header_buffers 4 16k;

    # ===== 连接优化 =====
    reset_timedout_connection on;   # 超时连接立即重置

    # ===== 日志缓冲 =====
    access_log /var/log/nginx/access.log main buffer=32k flush=5s;
    # 或关闭 access_log 提升性能（生产环境可考虑）
    # access_log off;

    include /etc/nginx/conf.d/*.conf;
}
```

```bash
wrk -t4 -c1000 -d30s http://localhost/

# 使用 ab 进行压测
ab -n 100000 -c 1000 http://localhost/

# 使用 hey 进行压测
hey -n 100000 -c 1000 http://localhost/
```

#### 总结

- `worker_processes` 设为 CPU 核心数，`worker_connections` 根据并发需求设置（通常 10240+）。
- 文件描述符限制需同时调整 `worker_rlimit_nofile`、`limits.conf`、`fs.file-max`。
- 内核参数重点优化：`somaxconn`、`tcp_max_syn_backlog`、`tcp_tw_reuse`、`ip_local_port_range`。
- systemd 管理的服务需在 service 文件中设置 `LimitNOFILE`，不读 `limits.conf`。
- **注意事项**：调优前先压测基线，调优后对比效果，避免盲目调参。`tcp_tw_reuse` 在 NAT 环境下需谨慎。`worker_connections` 不是越大越好，需考虑内存（每个连接约 2KB）。生产环境建议监控连接数、fd 使用率、TIME_WAIT 数量等指标，动态调整。日志写入是性能瓶颈之一，高并发场景可考虑 `access_log off` 或使用 syslog 发送到日志服务器。

### 第19讲 日志体系与动态模块

#### 概念

日志是运维和排障的基础。Nginx 提供了灵活的日志系统，支持自定义格式、条件记录、日志缓冲。同时，Nginx 1.9.11+ 引入的动态模块机制，允许在运行时加载/卸载模块，无需重新编译 Nginx。

- **access_log**：访问日志，记录每个请求的信息。
- **error_log**：错误日志，记录 Nginx 运行时的错误和警告。
- **log_format**：自定义日志格式。
- **动态模块**：编译为 `.so` 文件，通过 `load_module` 加载。
- **日志轮转**：通过 `logrotate` 管理日志文件大小和保留。

#### 原理

**1. 日志格式**

Nginx 通过 `log_format` 指令定义日志格式，使用变量组合成日志行。默认格式为 `combined`：

```
'$remote_addr - $remote_user [$time_local] "$request" '
'$status $body_bytes_sent "$http_referer" '
'"$http_user_agent"'
```

可以定义多个命名格式，在 `access_log` 中引用。

**2. 日志缓冲**

默认情况下，每条日志立即写入磁盘，高并发下 I/O 开销大。通过 `buffer=size` 参数缓冲日志，积累一定量后批量写入。`flush=time` 设置缓冲刷新间隔。

**3. 条件日志**

通过 `if=` 参数控制是否记录日志。如 `access_log /var/log/nginx/access.log main if=$loggable;`，配合 `map` 定义哪些请求需要记录。

**4. 日志轮转**

Nginx 的日志文件会持续增长，需要 `logrotate` 定期切割。`nginx -s reopen` 重新打开日志文件（重新创建文件描述符），是日志轮转的关键命令。

**5. 动态模块**

编译时使用 `--add-dynamic-module=path` 生成 `.so` 文件，放在 `modules/` 目录。通过 `load_module` 指令在 `nginx.conf` 最外层加载。模块在 Nginx 启动时加载，不能热加载（需 restart/reload）。

#### 例子

**自定义日志格式**：

```nginx
http {
    # 默认格式
    log_format combined '$remote_addr - $remote_user [$time_local] '
                        '"$request" $status $body_bytes_sent '
                        '"$http_referer" "$http_user_agent"';

    # JSON 格式（便于日志收集系统解析）
    log_format json escape=json
        '{'
            '"time":"$time_iso8601",'
            '"remote_addr":"$remote_addr",'
            '"request_method":"$request_method",'
            '"request_uri":"$request_uri",'
            '"server_name":"$server_name",'
            '"status":$status,'
            '"body_bytes_sent":$body_bytes_sent,'
            '"request_time":$request_time,'
            '"upstream_response_time":"$upstream_response_time",'
            '"upstream_addr":"$upstream_addr",'
            '"http_referer":"$http_referer",'
            '"http_user_agent":"$http_user_agent",'
            '"http_x_forwarded_for":"$http_x_forwarded_for"'
        '}';

    # 详细格式（含性能指标）
    log_format detailed '$remote_addr - $remote_user [$time_local] '
                        '"$request" $status $body_bytes_sent '
                        '"$http_referer" "$http_user_agent" '
                        'rt=$request_time '
                        'uct="$upstream_connect_time" '
                        'uht="$upstream_header_time" '
                        'urt="$upstream_response_time" '
                        'ua="$upstream_addr"';

    # 使用 JSON 格式
    access_log /var/log/nginx/access.log json buffer=32k flush=5s;
    # access_log /var/log/nginx/access.log detailed;
}
```

**条件日志**：

```nginx
http {
    # 根据状态码决定是否记录
    map $status $loggable {
        ~^[23]  0;    # 2xx/3xx 不记录
        default 1;    # 其他记录
    }

    # 根据请求路径决定
    map $uri $loggable_uri {
        /healthcheck 0;    # 健康检查不记录
        /favicon.ico 0;
        default      1;
    }

    server {
        listen 80;

        # 仅记录非 2xx/3xx 和非健康检查的请求
        access_log /var/log/nginx/access.log main
                   if=$loggable$loggable_uri;
        # 注意：if 条件为 0 或空时不记录，非 0 时记录

        location / {
            proxy_pass http://backend;
        }
    }
}
```

**多日志输出**：

```nginx
http {
    log_format main '$remote_addr - [$time_local] "$request" '
                    '$status $body_bytes_sent';

    server {
        listen 80;

        # 同时输出到多个日志文件
        access_log /var/log/nginx/access.log main;
        access_log /var/log/nginx/api.log main if=$is_api;

        # 按域名分日志
        access_log /var/log/nginx/$host.access.log main;
    }

    map $uri $is_api {
        default 0;
        ~^/api/ 1;
    }
}
```

**日志轮转配置**：

```bash
# /etc/logrotate.d/nginx

/var/log/nginx/*.log {
    daily              # 每天轮转
    missingok          # 日志不存在不报错
    rotate 30          # 保留 30 天
    compress           # 压缩旧日志
    delaycompress      # 延迟压缩（保留最近一个未压缩）

    sharedscripts      # 多个日志匹配时脚本只执行一次

        # 重新打开日志文件
        if [ -f /var/run/nginx.pid ]; then
            kill -USR1 $(cat /var/run/nginx.pid)
        fi
    endscript
}
```

#### 总结

- `log_format` 自定义日志格式，JSON 格式便于 ELK/Loki 等日志系统解析。
- `buffer` 和 `flush` 参数减少日志 I/O 开销，`if=` 实现条件日志。
- `logrotate` + `nginx -s reopen`（或 `kill -USR1`）实现日志轮转。
- 动态模块通过 `load_module` 加载，需在 `nginx.conf` 最外层声明。
- **注意事项**：`escape=json` 参数（Nginx 1.11.8+）自动转义 JSON 特殊字符，避免日志解析错误。日志文件权限需设置合理，避免敏感信息泄露。动态模块的 `--with-compat` 参数确保模块与 Nginx 版本二进制兼容。`debug` 级别日志量极大，仅用于排障，生产环境禁用。按域名分日志（`$host.access.log`）需注意 `open_log_cache` 缓存文件描述符，避免频繁打开关闭。

### 第20讲 OpenResty 与 Lua 扩展实战

#### 概念

OpenResty 是一个基于 Nginx 与 LuaJIT 的 Web 平台，由章亦春（agentzh）发起。它将 LuaJIT 嵌入 Nginx，使得可以用 Lua 脚本扩展 Nginx 的功能，实现复杂的业务逻辑，而无需编写 C 模块。OpenResty 在 CDN、API 网关、WAF 等场景广泛应用。

- **LuaJIT**：Lua 语言的即时编译实现，性能远高于解释执行。
- **ngx_lua 模块**：OpenResty 的核心模块，提供 Nginx 各阶段的 Lua 钩子。
- **执行阶段**：Nginx 请求处理分为多个阶段，Lua 可以在各阶段注入逻辑。
- **协程**：Lua 协程实现非阻塞 I/O，一个 worker 可处理大量并发 Lua 请求。
- **共享内存**：`lua_shared_dict` 提供 worker 间共享数据。

#### 原理

**1. Nginx 请求处理阶段**

Nginx 处理一个请求会经过多个阶段（phase），OpenResty 在各阶段提供了 Lua 钩子：

| 阶段 | Lua 指令 | 典型用途 |
|------|----------|----------|
| rewrite | `rewrite_by_lua` | URL 重写、访问控制 |
| access | `access_by_lua` | 权限检查、限流 |
| content | `content_by_lua` | 生成响应内容 |
| header_filter | `header_filter_by_lua` | 修改响应头 |
| body_filter | `body_filter_by_lua` | 修改响应体 |
| log | `log_by_lua` | 日志记录、统计 |
| init | `init_by_lua` | Worker 启动时初始化 |
| timer | `ngx.timer.at` | 定时任务 |

**2. 非阻塞 I/O**

OpenResty 的 Lua 代码运行在 LuaJIT 协程中。当 Lua 代码执行网络 I/O（如 `ngx.location.capture`、`lua-resty-http`）或 `ngx.sleep` 时，当前协程挂起，worker 转去处理其他请求。I/O 完成后协程恢复。这使得 OpenResty 可以用同步代码风格实现异步 I/O。

**3. 共享内存字典**

`lua_shared_dict` 在 Nginx 共享内存中创建键值存储，所有 worker 进程共享。适合存储限流计数器、缓存数据、全局配置等。操作是原子性的，无需锁。

**4. cosocket（Cosocket）**

OpenResty 提供的协程化 socket API（`ngx.socket.tcp`、`ngx.socket.udp`），可以用同步代码风格进行非阻塞网络通信。这是 OpenResty 最强大的特性之一，可以直连 MySQL、Redis、HTTP 等。

**访问控制（access_by_lua）**：

**连接 Redis（cosocket）**：

```nginx
http {
    # 引入 lua-resty-redis 库
    lua_package_path "/usr/local/openresty/lualib/?.lua;;";

    server {
        listen 80;

        # 从 Redis 获取数据
        location /cache/ {
            content_by_lua_block {
                local redis = require "resty.redis"
                local red = redis:new()
                red:set_timeout(1000)  -- 1秒超时

                -- 连接 Redis
                local ok, err = red:connect("127.0.0.1", 6379)
                if not ok then
                    ngx.say("failed to connect: ", err)
                    return
                end

                -- 获取 key
                local key = ngx.var.arg_key
                local res, err = red:get("cache:" .. key)

                if not res or res == ngx.null then
                    -- 缓存未命中，从后端获取
                    ngx.say("cache miss")
                    -- 这里可以发起 HTTP 请求到后端
                else
                    ngx.header.content_type = 'application/json'
                    ngx.say(res)
                end

                -- 放入连接池
                red:set_keepalive(10000, 100)
            }
        }
    }
}
```

**WAF 简易实现**：

```lua
-- /etc/nginx/lua/waf.lua
local args = ngx.req.get_uri_args()
local headers = ngx.req.get_headers()

-- 检查 URL 参数
for key, val in pairs(args) do
    if type(val) == "string" then
        local lower_val = string.lower(val)
        for _, pattern in ipairs(waf_rules.sql_injection) do
            if string.find(lower_val, pattern) then
                ngx.log(ngx.WARN, "SQL injection detected: ", val)
                ngx.status = 403
                ngx.say('{"error":"Request blocked by WAF"}')
                return ngx.exit(403)
            end
        end
    end
end

-- 检查 User-Agent
local ua = headers["user-agent"] or ""
if string.find(string.lower(ua), "sqlmap") then
    ngx.status = 403
    ngx.say('{"error":"Blocked"}')
    return ngx.exit(403)
end
```

```nginx
    lua_shared_dict config_cache 10m;

    init_by_lua_block {

        local cjson = require "cjson"
```

#### 总结

- OpenResty = Nginx + LuaJIT，用 Lua 脚本扩展 Nginx，无需编写 C 模块。
- Lua 钩子分布在 Nginx 各处理阶段：`rewrite_by_lua`、`access_by_lua`、`content_by_lua` 等。
- `lua_shared_dict` 提供 worker 间共享内存，适合限流计数器、缓存。
- cosocket（`ngx.socket`）实现非阻塞网络 I/O，可直连 Redis、MySQL、HTTP。
- **注意事项**：Lua 代码中不能使用阻塞 I/O（如标准 `io.open`、`os.execute`），会阻塞整个 worker。使用 `lua-resty-*` 库替代。`init_by_lua` 在 master 进程执行，`init_worker_by_lua` 在每个 worker 启动时执行。共享内存字典有大小限制，大数据应使用外部存储（Redis）。生产环境建议将 Lua 代码放在独立文件中（`*_by_lua_file`），便于管理和版本控制。OpenResty 性能极高，但调试相对困难，建议使用 `ngx.log` 记录调试信息。常见的 OpenResty 生态库：`lua-resty-redis`、`lua-resty-mysql`、`lua-resty-http`、`lua-resty-jwt`、`lua-resty-core`。

## 学习建议

1. **动手实践**：每学一个指令，立即在本地环境配置并测试。使用 `nginx -t` 验证配置，`curl -I` 测试响应。
2. **理解原理**：不要只记配置，理解 Nginx 的事件驱动架构、请求处理阶段、location 匹配规则等原理。
3. **善用日志**：`error_log` 设为 `debug` 级别可以查看详细的请求处理过程，是排障利器。
4. **参考官方文档**：[nginx.org/en/docs](http://nginx.org/en/docs/) 是最权威的参考，每个指令都有详细说明。
5. **性能压测**：使用 `wrk`、`ab`、`hey` 等工具压测，对比调优前后的性能差异。
6. **安全意识**：生产环境务必启用 HTTPS、安全响应头、访问控制、限流等防护措施。
7. **持续学习**：Nginx 生态丰富，OpenResty、Kong、APISIX 等基于 Nginx 的项目值得关注。
