# 第一章 基础入门

## 第1讲 Alembic 是什么？为什么需要数据库迁移

### 概念

**Alembic** 是 SQLAlchemy 作者 Michael Bayer 开发的轻量级数据库迁移工具。它通过版本化的 Python 脚本管理数据库 Schema（表结构）的变更历史，让数据库的演进过程像代码版本控制一样可追溯、可回滚、可协作。

**数据库迁移（Database Migration）** 是指在应用生命周期中，对数据库结构进行受控变更的过程。每一次变更（建表、加列、改类型、加索引等）被记录为一个"迁移脚本"，按顺序执行即可将数据库从任意历史版本升级到目标版本。

### 原理

为什么需要数据库迁移工具？考虑以下场景：

你的团队开发一个电商系统，最初 `users` 表只有 `id`、`name`、`email` 三列。上线三个月后，产品要求增加 `phone` 列。如果没有迁移工具，你可能会：

1. 直接在数据库里执行 `ALTER TABLE users ADD COLUMN phone VARCHAR(20)`；
2. 同事拉取代码后，他的本地数据库没有 `phone` 列，程序报错；
3. 测试环境、预发布环境、生产环境都需要手动同步，极易遗漏。

**迁移工具的核心价值**在于将 Schema 变更"代码化"：

- **版本化**：每个变更是一个带版本号的脚本，存放在 `versions/` 目录，纳入 Git 管理。
- **顺序执行**：脚本之间通过 `down_revision` 形成链表结构，Alembic 知道执行顺序。
- **双向操作**：每个脚本包含 `upgrade()`（升级）和 `downgrade()`（降级）两个函数，支持回滚。
- **状态追踪**：数据库中有一张 `alembic_version` 表，记录当前处于哪个版本。

Alembic 的工作流程可以概括为：

```
开发者编写/生成迁移脚本 → Alembic 读取 alembic_version 表 → 
对比目标版本 → 按顺序执行 upgrade() → 更新 alembic_version 表
```

Alembic 与其他迁移工具（如 Django migrations、Flyway、Liquibase）相比，最大优势是与 SQLAlchemy 深度集成，支持 **Autogenerate**（自动对比模型与数据库差异并生成迁移脚本）。

### 例子

一个典型的 Alembic 迁移脚本长这样：

```python
"""add phone column to users table

Revision ID: a1b2c3d4e5f6
Revises: 9x8y7z6w5v4u
Create Date: 2025-01-15 10:30:00.000000
"""
from alembic import op
import sqlalchemy as sa

# revision identifiers
revision = 'a1b2c3d4e5f6'
down_revision = '9x8y7z6w5v4u'
branch_labels = None
depends_on = None

def upgrade():
    op.add_column('users', sa.Column('phone', sa.String(20), nullable=True))

def downgrade():
    op.drop_column('users', 'phone')
```

执行升级：

```bash
$ alembic upgrade head
INFO  [alembic.runtime.migration] Running upgrade 9x8y7z6w5v4u -> a1b2c3d4e5f6, add phone column to users table
```

执行回滚：

```bash
$ alembic downgrade -1
INFO  [alembic.runtime.migration] Running downgrade a1b2c3d4e5f6 -> 9x8y7z6w5v4u, add phone column to users table
```

### 总结

- Alembic 是 SQLAlchemy 生态的数据库迁移工具，将 Schema 变更代码化、版本化。
- 核心价值：可追溯、可回滚、可协作、支持自动生成。
- 每个迁移脚本是一个 Python 文件，包含 `upgrade()` 和 `downgrade()` 两个函数。
- 数据库通过 `alembic_version` 表追踪当前版本。
- **注意事项**：迁移脚本一旦提交到团队仓库并被他人执行，就不应再修改其 `revision` 或 `down_revision`，否则会破坏版本链。

## 第2讲 安装与项目初始化

### 概念

本讲介绍如何安装 Alembic 并在一个现有项目中初始化迁移环境。Alembic 的初始化过程会生成一套标准目录结构和配置文件，这套结构是后续所有迁移操作的基础。

### 原理

Alembic 是一个纯 Python 包，通过 pip 安装即可。安装后提供 `alembic` 命令行工具。初始化使用 `alembic init` 命令，它会根据模板生成：

- `alembic.ini`：主配置文件，存放数据库连接字符串等参数
- `alembic/`：迁移环境目录（名称可自定义）
  - `env.py`：运行时环境配置脚本，每次执行迁移时被加载
  - `script.py.mako`：迁移脚本模板
  - `versions/`：存放迁移脚本的目录

Alembic 提供多种初始化模板：

| 模板名 | 说明 | 适用场景 |
|--------|------|----------|
| `generic`（默认） | 单数据库，使用 SQLAlchemy 连接 | 大多数项目 |
| `multi-env` | 多数据库环境 | 同时管理多个数据库 |
| `pylons` | Pylons 框架集成 | Pylons 项目 |
| `async` | 异步 SQLAlchemy | FastAPI + async |

### 例子

**步骤1：安装 Alembic**

```bash
pip install alembic
```

如果你使用 SQLAlchemy 2.0，建议安装最新版 Alembic（1.10+）以获得完整支持：

```bash
pip install "alembic>=1.10"
```

**步骤2：创建项目目录**

```bash
mkdir myproject && cd myproject
```

**步骤3：初始化 Alembic**

```bash
alembic init alembic
```

输出：

```
Creating directory /path/to/myproject/alembic ... done
Creating directory /path/to/myproject/alembic/versions ... done
Generating /path/to/myproject/alembic.ini ... done
Generating /path/to/myproject/alembic/env.py ... done
Generating /path/to/myproject/alembic/script.py.mako ... done
Generating /path/to/myproject/alembic/README ... done
Please edit configuration/connection/logging settings in '/path/to/myproject/alembic.ini' before running.
```

**步骤4：配置数据库连接**

编辑 `alembic.ini`，找到 `sqlalchemy.url` 配置项：

```ini
# alembic.ini
sqlalchemy.url = postgresql://user:password@localhost:5432/mydb
```

对于 SQLite：

```ini
sqlalchemy.url = sqlite:///./mydb.db
```

**步骤5：验证安装**

```bash
alembic current
```

如果输出类似以下内容，说明配置成功（此时数据库还没有 `alembic_version` 表，会自动创建）：

```
INFO  [alembic.runtime.migration] Will assume transactional DDL.
```

最终项目结构：

```
myproject/
├── alembic.ini
└── alembic/
    ├── env.py
    ├── README
    ├── script.py.mako
    └── versions/
```

### 总结

- 安装：`pip install alembic`
- 初始化：`alembic init <目录名>`
- 核心配置：在 `alembic.ini` 中设置 `sqlalchemy.url`
- 默认模板 `generic` 适合大多数项目，异步项目可用 `alembic init -t async alembic`
- **注意事项**：`alembic.ini` 中的数据库密码是明文，生产环境建议通过环境变量在 `env.py` 中动态读取，避免将密码提交到代码仓库。后续第9讲会详细讲解。

## 第3讲 项目结构详解：alembic.ini、env.py、versions/

### 概念

本讲深入讲解 Alembic 初始化后生成的三个核心组件：配置文件 `alembic.ini`、运行时脚本 `env.py`、迁移脚本目录 `versions/`。理解这三者的职责划分，是灵活运用 Alembic 的前提。

### 原理

**alembic.ini 的职责**：存放静态配置，包括数据库连接字符串、日志格式、脚本位置等。它使用 Python 的 `ConfigParser` 格式，由 Alembic 启动时读取。

**env.py 的职责**：这是 Alembic 的"大脑"。每次执行 `alembic` 命令时，`env.py` 都会被加载执行。它负责：
1. 读取 `alembic.ini` 中的配置
2. 创建 SQLAlchemy 连接
3. 如果使用 Autogenerate，需要导入你的模型元数据（`target_metadata`）
4. 配置迁移上下文（`context.configure()`）
5. 执行迁移（`context.run_migrations()`）

**versions/ 的职责**：存放所有迁移脚本文件。每个文件是一个独立的 Python 模块，文件名格式为 `<revision>_<描述>.py`。Alembic 通过文件内的 `revision` 和 `down_revision` 变量构建版本链。

### 例子

**alembic.ini 关键配置项详解**：

```ini
# alembic.ini

[alembic]
# 迁移脚本目录路径
script_location = alembic

# 模板文件
# script_template = alembic:script.py.mako

# 时间戳格式（用于生成 revision id）
# file_template = %%(rev)s_%%(slug)s

# 数据库连接字符串
sqlalchemy.url = postgresql://user:pass@localhost/mydb

# 递归搜索 versions 目录（子目录中的脚本也会被加载）
# version_path_separator = os

# 递归搜索模型文件（用于 autogenerate）
# prepend_sys_path = .

# 自定义 revision id 生成器
# revision_environment = false

[loggers]
keys = root,sqlalchemy,alembic

[handlers]
keys = console

[formatters]
keys = generic

[logger_root]
level = WARN
handlers = console
qualname =

[logger_sqlalchemy]
level = WARN
handlers =
qualname = sqlalchemy.engine

[logger_alembic]
level = INFO
handlers =
qualname = alembic

[handler_console]
class = StreamHandler
args = (sys.stderr,)
level = NOTSET
formatter = generic

[formatter_generic]
format = %(levelname)-5.5s [%(name)s] %(message)s
datefmt = %H:%M:%S
```

**env.py 默认内容详解**（带注释）：

```python
# alembic/env.py
from logging.config import fileConfig
from sqlalchemy import engine_from_config, pool
from alembic import context

# 1. 读取 alembic.ini 配置
config = context.config
fileConfig(config.config_file_name)

# 2. 导入模型元数据（用于 autogenerate）
# 如果你的项目使用 SQLAlchemy 模型，需要在这里导入
# from myapp.models import Base
# target_metadata = Base.metadata
target_metadata = None  # 默认为 None，autogenerate 不可用

# 3. 获取数据库连接配置
def run_migrations_offline():
    """离线模式：只生成 SQL，不连接数据库"""
    url = config.get_main_option("sqlalchemy.url")
    context.configure(
        url=url,
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
    )
    with context.begin_transaction():
        context.run_migrations()

def run_migrations_online():
    """在线模式：连接数据库并执行迁移"""
    connectable = engine_from_config(
        config.get_section(config.config_ini_section),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    with connectable.connect() as connection:
        context.configure(
            connection=connection,
            target_metadata=target_metadata
        )
        with context.begin_transaction():
            context.run_migrations()

# 4. 根据模式选择执行方式
if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

**versions/ 目录中的脚本结构**：

```
versions/
├── 9x8y7z6w5v4u_create_users_table.py
├── a1b2c3d4e5f6_add_phone_to_users.py
└── b2c3d4e5f6g7_create_orders_table.py
```

每个脚本文件内部都包含以下关键变量：

```python
revision = 'a1b2c3d4e5f6'        # 当前版本的唯一标识
down_revision = '9x8y7z6w5v4u'   # 上一个版本的标识（构成链表）
branch_labels = None              # 分支标签（用于分支管理）
depends_on = None                 # 依赖的其他迁移
```

### 总结

- `alembic.ini`：静态配置（连接字符串、日志、路径），适合放不敏感的配置。
- `env.py`：运行时逻辑，是定制 Alembic 行为的核心入口。
- `versions/`：迁移脚本仓库，通过 `revision`/`down_revision` 构成版本链。
- **关键理解**：`env.py` 中的 `target_metadata` 默认是 `None`，要使用 Autogenerate 必须导入你的 SQLAlchemy 模型的 `Base.metadata`。
- **注意事项**：`alembic.ini` 中的 `sqlalchemy.url` 可以被 `env.py` 覆盖，这为多环境配置提供了灵活性（第9讲详解）。

## 第4讲 第一个迁移：手动创建与执行

### 概念

本讲通过一个完整的手动迁移示例，让你亲历从"创建迁移脚本"到"执行升级"再到"执行降级"的全过程。我们将创建一个 `users` 表，包含 `id`、`name`、`email` 三个字段。

### 原理

手动创建迁移使用 `alembic revision` 命令。Alembic 会根据 `script.py.mako` 模板生成一个空的迁移脚本，你需要手动编写 `upgrade()` 和 `downgrade()` 函数。

迁移脚本中使用 `op` 对象（`from alembic import op`）执行 DDL 操作。`op` 是 `Operations` 类的实例，封装了建表、改列、加索引等常用操作，底层会根据数据库方言生成对应的 SQL。

执行迁移时，Alembic 会：
1. 查询数据库的 `alembic_version` 表获取当前版本
2. 确定需要执行的迁移脚本序列
3. 按顺序调用每个脚本的 `upgrade()` 或 `downgrade()`
4. 更新 `alembic_version` 表

### 例子

**步骤1：创建迁移脚本**

```bash
alembic revision -m "create users table"
```

输出：

```
Generating /path/to/alembic/versions/c3a8e9f1d2b3_create_users_table.py ... done
```

生成的脚本内容：

```python
"""create users table

Revision ID: c3a8e9f1d2b3
Revises:
Create Date: 2025-01-15 11:00:00.000000
"""
from alembic import op
import sqlalchemy as sa

revision = 'c3a8e9f1d2b3'
down_revision = None    # 第一个迁移，没有前驱
branch_labels = None
depends_on = None

def upgrade():
    pass    # 需要手动填写

def downgrade():
    pass    # 需要手动填写
```

**步骤2：编写 upgrade() 和 downgrade()**

```python
def upgrade():
    op.create_table(
        'users',
        sa.Column('id', sa.Integer, primary_key=True),
        sa.Column('name', sa.String(50), nullable=False),
        sa.Column('email', sa.String(120), unique=True, nullable=False),
    )

def downgrade():
    op.drop_table('users')
```

**步骤3：执行升级**

```bash
alembic upgrade head
```

输出：

```
INFO  [alembic.runtime.migration] Running upgrade  -> c3a8e9f1d2b3, create users table
```

此时数据库中会创建 `users` 表和 `alembic_version` 表。

**步骤4：查看当前版本**

```bash
alembic current
```

输出：

```
c3a8e9f1d2b3 (head)
```

**步骤5：查看历史**

```bash
alembic history --verbose
```

输出：

```
Rev: c3a8e9f1d2b3 (head)
Path: /path/to/alembic/versions/c3a8e9f1d2b3_create_users_table.py

    create users table

    Revision ID: c3a8e9f1d2b3
    Revises:
    Create Date: 2025-01-15 11:00:00.000000
```

**步骤6：执行降级（回滚）**

```bash
alembic downgrade -1
```

`-1` 表示回退一个版本。输出：

```
INFO  [alembic.runtime.migration] Running downgrade c3a8e9f1d2b3 -> , create users table
```

此时 `users` 表被删除，`alembic_version` 表中的版本记录也被清除。

**步骤7：重新升级**

```bash
alembic upgrade head
```

### 总结

- 创建迁移：`alembic revision -m "描述"`
- 升级到最新：`alembic upgrade head`
- 回退一步：`alembic downgrade -1`
- 查看当前版本：`alembic current`
- 查看历史：`alembic history`
- `op` 对象是编写迁移脚本的核心 API，下一讲会详细讲解 Operations API。
- **注意事项**：`downgrade()` 必须与 `upgrade()` 严格对称，否则回滚会丢失数据。例如 `upgrade()` 加了一列，`downgrade()` 必须删除该列。
- **注意事项**：第一个迁移的 `down_revision` 为 `None`，表示它是版本链的起点。

# 第二章 核心机制

## 第5讲 Revision 系统：版本链与哈希标识

### 概念

**Revision** 是 Alembic 版本管理的核心概念。每一个迁移脚本就是一个 revision，拥有全局唯一的标识符（revision ID）。所有 revision 通过 `down_revision` 字段相互连接，形成一条有向链表（或树），这就是 Alembic 的版本链。

### 原理

**Revision ID 的生成**：默认情况下，Alembic 生成 12 位的十六进制随机字符串（如 `c3a8e9f1d2b3`）。也可以配置为使用时间戳或其他格式。在 `alembic.ini` 中：

```ini
# 使用更短的 ID
# revision_environment = false

# 自定义 revision id 生成函数（在 env.py 中）
```

**版本链的结构**：

```
(None) ← rev_a ← rev_b ← rev_c ← rev_d (head)
```

- `rev_a` 的 `down_revision = None`，是链的起点
- `rev_b` 的 `down_revision = 'rev_a'`
- `rev_d` 是当前链的末端，称为 `head`
- Alembic 通过遍历这条链确定执行顺序

**alembic_version 表**：数据库中有一张特殊的表，只存一行一列，记录当前数据库处于哪个版本：

```sql
CREATE TABLE alembic_version (
    version_num VARCHAR(32) NOT NULL,
    CONSTRAINT alembic_version_pkc PRIMARY KEY (version_num)
);
```

**多 head 的情况**：当两个开发者同时基于同一个 revision 创建新迁移时，版本链会分叉，产生两个 head。这需要通过 merge 解决（第11讲详解）。

### 例子

**查看版本链**：

```bash
alembic history
```

输出示例：

```
c3a8e9f1d2b3 (head), create users table
b2c3d4e5f6g7 -> c3a8e9f1d2b3, add phone to users
a1b2c3d4e5f6 -> b2c3d4e5f6g7, create orders table
None -> a1b2c3d4e5f6, initial schema
```

格式解读：`<down_revision> -> <revision>, <message>`

**升级到指定版本**（而非 head）：

```bash
alembic upgrade b2c3d4e5f6g7
```

这会执行从当前版本到 `b2c3d4e5f6g7` 之间的所有 upgrade()。

**降级到指定版本**：

```bash
alembic downgrade a1b2c3d4e5f6
```

**降级到初始状态**（清空所有迁移）：

```bash
alembic downgrade base
```

`base` 是一个特殊关键字，代表版本链的起点（`down_revision = None` 的那个）。

**相对升级/降级**：

```bash
alembic upgrade +2     # 向前升级 2 个版本
alembic downgrade -1   # 向后降级 1 个版本
```

**查看两个版本之间的差异**：

```bash
alembic history -v
```

**自定义 revision ID**：有时为了可读性，你想指定 revision ID：

```bash
alembic revision -m "create users" --rev-id 0001
```

生成的脚本中 `revision = '0001'`。

### 总结

- 每个 revision 有唯一 ID，通过 `down_revision` 构成链表。
- `head` 是链的末端，`base` 是链的起点。
- `alembic_version` 表记录数据库当前版本。
- 可以升级/降级到任意指定版本，不限于 `head` 或 `-1`。
- **注意事项**：revision ID 虽然是随机的，但一旦脚本提交到版本库，就绝对不能修改，否则会断链。
- **注意事项**：如果 `alembic_version` 表中的版本号在 `versions/` 目录中找不到对应脚本（比如脚本被误删），Alembic 会报错。此时需要手动修复或恢复脚本。

## 第6讲 upgrade 与 downgrade 命令详解

### 概念

`upgrade` 和 `downgrade` 是 Alembic 最核心的两个命令，分别用于将数据库版本向前推进和向后回退。本讲系统讲解这两个命令的所有用法和参数。

### 原理

**upgrade 的工作流程**：

1. 读取数据库 `alembic_version` 表，获取当前版本 `current`
2. 解析命令参数，确定目标版本 `target`
3. 从版本链中找到从 `current` 到 `target` 的路径
4. 按顺序执行路径上每个脚本的 `upgrade()` 函数
5. 每执行完一个脚本，更新 `alembic_version` 表

**downgrade 的工作流程**类似，但执行的是 `downgrade()` 函数，且方向相反。

**事务支持**：Alembic 默认在事务中执行迁移。如果迁移过程中出错，整个事务会回滚，数据库不会处于中间状态。但注意，不是所有数据库都支持 DDL 事务（如 MySQL 的 DDL 是隐式提交的）。

### 例子

**upgrade 命令的所有用法**：

```bash
# 升级到最新版本
alembic upgrade head

# 升级到指定版本
alembic upgrade a1b2c3d4e5f6

# 相对升级
alembic upgrade +2

# 升级到某个分支的 head
alembic upgrade mybranch@head

# 升级并显示 SQL（不实际执行）
alembic upgrade head --sql

# 强制执行（即使有警告）
alembic upgrade head --tag mytag
```

**downgrade 命令的所有用法**：

```bash
# 降级一个版本
alembic downgrade -1

# 降级到指定版本
alembic downgrade a1b2c3d4e5f6

# 降级到初始状态
alembic downgrade base

# 相对降级
alembic downgrade -2

# 降级并显示 SQL
alembic downgrade -1 --sql
```

**查看当前状态**：

```bash
alembic current
# 输出：c3a8e9f1d2b3 (head)

alembic current --verbose
# 输出更详细的信息，包括迁移脚本的路径
```

**查看 head**：

```bash
alembic heads
# 如果只有一个 head：
# c3a8e9f1d2b3 (head)

# 如果有多个 head（分叉）：
# c3a8e9f1d2b3 (head)
# d4e5f6g7h8i9 (head)
# WARNING: multiple heads present; specify branch with @ syntax
```

**查看所有版本**：

```bash
alembic history
# 简洁模式

alembic history --verbose
# 详细模式，显示完整路径和文档字符串

alembic history -r a1b2c3d4e5f6:head
# 只显示某个范围内的历史
```

**实际执行示例**：

```bash
$ alembic upgrade head
INFO  [alembic.runtime.migration] Will assume transactional DDL.
INFO  [alembic.runtime.migration] Running upgrade  -> a1b2c3d4e5f6, initial schema
INFO  [alembic.runtime.migration] Running upgrade a1b2c3d4e5f6 -> b2c3d4e5f6g7, add email column
INFO  [alembic.runtime.migration] Running upgrade b2c3d4e5f6g7 -> c3a8e9f1d2b3, add index
```

**stamp 命令**（不执行迁移，只更新版本标记）：

```bash
# 标记数据库为最新版本，但不执行任何迁移脚本
alembic stamp head

# 标记为指定版本
alembic stamp a1b2c3d4e5f6
```

这在以下场景有用：
- 数据库已经手动建好了表，你想让 Alembic "认为"已经迁移过了
- 修复 `alembic_version` 表与实际状态不一致的问题

### 总结

- `upgrade head`：升级到最新；`downgrade -1`：回退一步
- `stamp` 命令只更新版本标记，不执行迁移，用于"对齐"状态
- `--sql` 参数可以生成 SQL 脚本而不实际执行（第12讲详解）
- 多 head 时需要用 `@` 语法指定分支
- **注意事项**：MySQL 的 DDL 语句（ALTER TABLE 等）是隐式提交的，不支持事务回滚。如果迁移中途失败，数据库可能处于中间状态，需要手动修复。
- **注意事项**：`stamp` 命令很强大但危险——如果标记的版本与实际数据库结构不符，后续迁移会出错。只在你确切知道数据库状态时使用。

## 第7讲 Operations API：Schema 变更的瑞士军刀

### 概念

**Operations API**（`alembic.op`）是编写迁移脚本时使用的核心 API。它封装了所有常见的 DDL 操作：建表、删表、加列、改列、加索引、加约束等。`op` 对象会根据当前数据库方言自动生成对应的 SQL。

### 原理

`op` 对象实际上是 `Operations` 类的实例，在迁移脚本执行时由 Alembic 自动注入。它底层调用 SQLAlchemy 的 DDL 构造器，生成方言无关的 DDL 表达式，再由 SQLAlchemy 的 dialect 翻译为特定数据库的 SQL。

例如，`op.add_column('users', sa.Column('phone', sa.String(20)))` 在不同数据库中生成的 SQL：

- PostgreSQL: `ALTER TABLE users ADD COLUMN phone VARCHAR(20)`
- MySQL: `ALTER TABLE users ADD COLUMN phone VARCHAR(20)`
- SQLite: 早期版本不支持 ALTER TABLE ADD COLUMN，Alembic 会用"建新表+复制数据+删旧表+重命名"的方式模拟

### 例子

**1. 表操作**

```python
def upgrade():
    # 创建表
    op.create_table(
        'users',
        sa.Column('id', sa.Integer, primary_key=True),
        sa.Column('name', sa.String(50), nullable=False),
        sa.Column('email', sa.String(120), unique=True),
        sa.Column('created_at', sa.DateTime, server_default=sa.func.now()),
    )

    # 创建带外键的表
    op.create_table(
        'posts',
        sa.Column('id', sa.Integer, primary_key=True),
        sa.Column('title', sa.String(200), nullable=False),
        sa.Column('user_id', sa.Integer, sa.ForeignKey('users.id')),
    )

def downgrade():
    op.drop_table('posts')
    op.drop_table('users')  # 先删依赖表
```

**2. 列操作**

```python
def upgrade():
    # 添加列
    op.add_column('users', sa.Column('phone', sa.String(20), nullable=True))

    # 添加带默认值的列
    op.add_column('users', sa.Column('status', sa.String(20), server_default='active'))

    # 删除列
    op.drop_column('users', 'phone')

    # 修改列（改类型）
    # 注意：SQLite 不支持 ALTER COLUMN，需要批量操作（第14讲详解）
    op.alter_column('users', 'name',
                    existing_type=sa.String(50),
                    type_=sa.String(100),
                    nullable=True)

    # 修改列名
    op.alter_column('users', 'name', new_column_name='full_name',
                    existing_type=sa.String(50))

    # 修改默认值
    op.alter_column('users', 'status',
                    existing_type=sa.String(20),
                    server_default='inactive')
```

**3. 索引操作**

```python
def upgrade():
    # 创建索引
    op.create_index('ix_users_email', 'users', ['email'], unique=True)

    # 创建复合索引
    op.create_index('ix_posts_user_created', 'posts', ['user_id', 'created_at'])

    # 删除索引
    op.drop_index('ix_users_email', table_name='users')
```

**4. 约束操作**

```python
def upgrade():
    # 添加唯一约束
    op.create_unique_constraint('uq_users_phone', 'users', ['phone'])

    # 添加检查约束
    op.create_check_constraint(
        'ck_users_age_positive',
        'users',
        'age >= 0'
    )

    # 添加外键约束
    op.create_foreign_key(
        'fk_posts_user_id',     # 约束名
        'posts',                # 源表
        'users',                # 目标表
        ['user_id'],            # 源列
        ['id'],                 # 目标列
        ondelete='CASCADE'      # 可选：级联删除
    )

    # 删除约束
    op.drop_constraint('uq_users_phone', 'users', type_='unique')
    op.drop_constraint('fk_posts_user_id', 'posts', type_='foreignkey')
```

**5. 其他常用操作**

```python
def upgrade():
    # 重命名表
    op.rename_table('users', 'accounts')

    # 执行原生 SQL
    op.execute("UPDATE users SET status = 'active' WHERE status IS NULL")

    # 批量操作（主要用于 SQLite，第14讲详解）
    with op.batch_alter_table('users') as batch_op:
        batch_op.add_column(sa.Column('age', sa.Integer))
        batch_op.alter_column('name', nullable=False)
        batch_op.drop_column('old_column')
```

### 总结

- `op` 是迁移脚本的核心 API，封装了所有 DDL 操作。
- 主要方法：`create_table`/`drop_table`、`add_column`/`drop_column`/`alter_column`、`create_index`/`drop_index`、`create_*_constraint`/`drop_constraint`。
- `op.execute()` 可以执行任意 SQL，适合处理 op API 不支持的操作。
- `op.batch_alter_table()` 用于 SQLite 等不支持 ALTER 的数据库。
- **注意事项**：`alter_column` 在不同数据库行为不同，SQLite 需要 batch 模式，MySQL 改类型可能锁表。
- **注意事项**：删除列/表是不可逆的数据丢失操作，downgrade 只能恢复结构，不能恢复数据。务必在执行前备份。

## 第8讲 Autogenerate：自动生成迁移脚本

### 概念

**Autogenerate** 是 Alembic 最强大的功能之一。它能自动对比 SQLAlchemy 模型定义（`target_metadata`）与实际数据库结构的差异，生成对应的迁移脚本。这大大减少了手动编写迁移脚本的工作量。

### 原理

Autogenerate 的工作原理：

1. **读取模型元数据**：从 `env.py` 中的 `target_metadata`（通常是 `Base.metadata`）获取模型定义的表结构
2. **反射数据库**：连接数据库，使用 SQLAlchemy 的 reflection 功能获取当前数据库的实际结构
3. **对比差异**：逐表、逐列、逐索引、逐约束地对比模型与数据库
4. **生成脚本**：根据差异生成对应的 `op` 调用代码

**Autogenerate 能检测的差异**：
- 表的增删
- 列的增删
- 列类型变化
- 可空性（nullable）变化
- 索引增删
- 外键增删
- 唯一约束增删

**Autogenerate 不能检测的差异**（需要手动处理）：
- 列名修改（会被识别为"删旧列+加新列"，数据会丢失）
- 检查约束（CheckConstraint）的变化
- 触发器、存储过程的变化
- 数据本身的变更
- 某些数据库特定的配置（如存储引擎、字符集）

### 例子

**步骤1：配置 env.py 导入模型**

```python
# alembic/env.py
from myapp.models import Base
target_metadata = Base.metadata
```

**步骤2：定义 SQLAlchemy 模型**

```python
# myapp/models.py
from sqlalchemy import Column, Integer, String, DateTime, func
from sqlalchemy.orm import DeclarativeBase

class Base(DeclarativeBase):
    pass

class User(Base):
    __tablename__ = 'users'
    id = Column(Integer, primary_key=True)
    name = Column(String(50), nullable=False)
    email = Column(String(120), unique=True, nullable=False)
    created_at = Column(DateTime, server_default=func.now())
```

**步骤3：生成自动迁移**

```bash
alembic revision --autogenerate -m "create users table"
```

输出：

```
INFO  [alembic.autogenerate.compare] Detected added table 'users'
Generating /path/to/alembic/versions/e5f6g7h8i9j0_create_users_table.py ... done
```

生成的脚本：

```python
"""create users table

Revision ID: e5f6g7h8i9j0
Revises: c3a8e9f1d2b3
Create Date: 2025-01-15 12:00:00.000000
"""
from alembic import op
import sqlalchemy as sa

revision = 'e5f6g7h8i9j0'
down_revision = 'c3a8e9f1d2b3'
branch_labels = None
depends_on = None

def upgrade():
    op.create_table(
        'users',
        sa.Column('id', sa.Integer(), nullable=False),
        sa.Column('name', sa.String(length=50), nullable=False),
        sa.Column('email', sa.String(length=120), nullable=False),
        sa.Column('created_at', sa.DateTime(), server_default=sa.text('now()'), nullable=True),
        sa.PrimaryKeyConstraint('id'),
        sa.UniqueConstraint('email'),
    )

def downgrade():
    op.drop_table('users')
```

**步骤4：修改模型后再次自动生成**

在 `User` 模型中添加 `phone` 列：

```python
class User(Base):
    __tablename__ = 'users'
    id = Column(Integer, primary_key=True)
    name = Column(String(50), nullable=False)
    email = Column(String(120), unique=True, nullable=False)
    phone = Column(String(20))  # 新增
    created_at = Column(DateTime, server_default=func.now())
```

再次生成：

```bash
alembic revision --autogenerate -m "add phone to users"
```

输出：

```
INFO  [alembic.autogenerate.compare] Detected added column 'users.phone'
```

生成的脚本会包含 `op.add_column('users', sa.Column('phone', sa.String(length=20), nullable=True))`。

**步骤5：配置 Autogenerate 排除项**

有时你不希望 Alembic 管理某些表（如缓存表、日志表），可以在 `env.py` 中配置：

```python
# env.py
def run_migrations_online():
    # ...
    context.configure(
        connection=connection,
        target_metadata=target_metadata,
        include_object=include_object,
        include_schemas=False,
        compare_type=True,         # 比较列类型
        compare_server_default=True,  # 比较默认值
    )

def include_object(object, name, type_, reflected, compare_to):
    """排除不需要管理的表"""
    if type_ == "table" and name == "cache_table":
        return False
    return True
```

### 总结

- Autogenerate 通过对比模型与数据库自动生成迁移脚本，大幅提升效率。
- 使用前必须在 `env.py` 中设置 `target_metadata = Base.metadata`。
- 命令：`alembic revision --autogenerate -m "描述"`
- **必须检查生成的脚本**：Autogenerate 不完美，尤其是列重命名会被误判为"删+加"。
- **注意事项**：`compare_type=True` 建议开启，否则列类型变化不会被检测到。
- **注意事项**：Autogenerate 生成的脚本只是"草稿"，务必人工审查后再执行。特别是涉及数据迁移时，需要手动补充逻辑。

# 第三章 进阶用法

## 第9讲 自定义 env.py：多环境与多数据库配置

### 概念

`env.py` 是 Alembic 的运行时入口，默认生成的版本只适用于简单的单数据库场景。在实际项目中，我们通常需要：根据环境变量切换数据库连接、同时管理多个数据库、集成 Flask/Django 等框架的应用上下文。这些都需要自定义 `env.py`。

### 原理

`env.py` 的本质是一个在每次 `alembic` 命令执行时都会被加载运行的 Python 脚本。它通过 `alembic.context` 对象与 Alembic 核心交互。关键调用是 `context.configure()`，它接受以下重要参数：

- `connection`：SQLAlchemy 数据库连接
- `target_metadata`：模型元数据（用于 autogenerate）
- `url`：数据库 URL（离线模式使用）
- `include_object`：过滤函数，决定哪些对象被管理
- `include_schemas`：是否包含 schema（PostgreSQL 的 schema）
- `compare_type`：是否比较列类型
- `compare_server_default`：是否比较默认值

由于 `env.py` 是普通 Python 脚本，你可以在其中执行任何 Python 代码：读取环境变量、加载配置文件、初始化框架上下文等。`alembic.ini` 中的配置可以通过 `config.get_main_option()` 读取，也可以被 `env.py` 覆盖。

### 例子

**场景1：通过环境变量配置数据库连接**

```python
# alembic/env.py
import os
from logging.config import fileConfig
from sqlalchemy import engine_from_config, pool
from alembic import context

config = context.config
fileConfig(config.config_file_name)

# 从环境变量读取数据库 URL，覆盖 alembic.ini 中的配置
database_url = os.environ.get(
    'DATABASE_URL',
    config.get_main_option('sqlalchemy.url')
)
config.set_main_option('sqlalchemy.url', database_url)

from myapp.models import Base
target_metadata = Base.metadata

def run_migrations_offline():
    url = config.get_main_option("sqlalchemy.url")
    context.configure(
        url=url,
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
    )
    with context.begin_transaction():
        context.run_migrations()

def run_migrations_online():
    connectable = engine_from_config(
        config.get_section(config.config_ini_section),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    with connectable.connect() as connection:
        context.configure(
            connection=connection,
            target_metadata=target_metadata,
            compare_type=True,
        )
        with context.begin_transaction():
            context.run_migrations()

if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

使用时：

```bash
export DATABASE_URL="postgresql://user:pass@prod-db:5432/mydb"
alembic upgrade head
```

**场景2：Flask 应用集成**

```python
# alembic/env.py
import os
from logging.config import fileConfig
from alembic import context
from flask import current_app

config = context.config
fileConfig(config.config_file_name)

# 在 Flask 应用上下文中获取模型和数据库连接
def get_engine():
    # 通过 FLASK_APP 环境变量找到 Flask 应用
    app = current_app._get_current_object()
    return app.extensions['sqlalchemy'].engine

def run_migrations_online():
    # 需要 Flask 应用上下文
    from myapp import create_app
    app = create_app()
    with app.app_context():
        engine = get_engine()
        with engine.connect() as connection:
            context.configure(
                connection=connection,
                target_metadata=current_app.extensions['sqlalchemy'].db.metadata,
                compare_type=True,
            )
            with context.begin_transaction():
                context.run_migrations()

if context.is_offline_mode():
    # 离线模式也需要应用上下文
    from myapp import create_app
    app = create_app()
    with app.app_context():
        url = current_app.config['SQLALCHEMY_DATABASE_URI']
        context.configure(url=url, target_metadata=None)
        with context.begin_transaction():
            context.run_migrations()
else:
    run_migrations_online()
```

**场景3：多数据库支持**

```python
# alembic/env.py
from logging.config import fileConfig
from sqlalchemy import engine_from_config, pool
from alembic import context
from myapp.models import Base

config = context.config
fileConfig(config.config_file_name)

# 定义多个数据库的元数据
target_metadata = {
    'default': Base.metadata,
    'analytics': Base.metadata,  # 可以是不同的 metadata
}

def run_migrations_online():
    # 为每个数据库执行迁移
    for database_key in target_metadata.keys():
        engine = engine_from_config(
            config.get_section(database_key),
            prefix='sqlalchemy.',
            poolclass=pool.NullPool,
        )
        with engine.connect() as connection:
            context.configure(
                connection=connection,
                target_metadata=target_metadata[database_key],
                compare_type=True,
            )
            with context.begin_transaction():
                context.run_migrations()

if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

对应的 `alembic.ini` 配置：

```ini
[alembic]
script_location = alembic

[default]
sqlalchemy.url = postgresql://user:pass@localhost/maindb

[analytics]
sqlalchemy.url = postgresql://user:pass@localhost/analyticsdb
```

### 总结

- `env.py` 是定制 Alembic 行为的核心入口，可以读取环境变量、加载框架上下文。
- 通过 `config.set_main_option()` 可以覆盖 `alembic.ini` 中的配置。
- 多数据库场景需要为每个数据库分别调用 `context.configure()` 和 `context.run_migrations()`。
- **注意事项**：`env.py` 中导入模型时，确保 `sys.path` 包含项目根目录。可以在 `alembic.ini` 中设置 `prepend_sys_path = .`，或在 `env.py` 中手动 `sys.path.insert(0, ...)`。
- **注意事项**：生产环境的数据库密码不应硬编码在 `alembic.ini` 中，务必通过环境变量或密钥管理服务注入。

## 第10讲 数据迁移：不只是 Schema 变更

### 概念

前面的讲次主要关注 Schema 变更（DDL），但实际项目中经常需要**数据迁移**（DML）：填充新列的默认值、拆分/合并字段、清洗脏数据、创建初始管理员账号等。Alembic 完全支持在迁移脚本中执行数据操作。

### 原理

在迁移脚本中执行数据操作，核心是使用 `op.get_bind()` 获取当前的 SQLAlchemy 连接，然后使用 SQLAlchemy Core（`sa.Table`）或直接执行 SQL 来操作数据。

**为什么不用 ORM？** 迁移脚本中**不应该使用 ORM 模型**，因为模型会随代码演进。假设你在迁移脚本中用 `User` 模型查询数据，几个月后 `User` 模型被重构（比如列名改了），这个旧迁移脚本在全新环境执行时会报错。因此，数据迁移应该使用 SQLAlchemy Core 或原生 SQL，直接引用表名和列名。

**数据迁移的典型场景**：
1. 新增列后填充默认值
2. 拆分字段（如 `full_name` → `first_name` + `last_name`）
3. 合并字段
4. 数据格式转换（如时间戳格式统一）
5. 创建初始数据（如默认角色、权限）
6. 数据清洗（去重、修正错误）

### 例子

**场景1：新增列并填充默认值**

```python
"""add status column to users

Revision ID: f1e2d3c4b5a6
Revises: e5f6g7h8i9j0
"""
from alembic import op
import sqlalchemy as sa

revision = 'f1e2d3c4b5a6'
down_revision = 'e5f6g7h8i9j0'

def upgrade():
    # 1. 添加列（允许 NULL）
    op.add_column('users', sa.Column('status', sa.String(20), nullable=True))

    # 2. 填充现有数据
    users = sa.table('users',
        sa.column('id', sa.Integer),
        sa.column('status', sa.String),
    )
    op.execute(users.update().values(status='active'))

    # 3. 修改列为 NOT NULL
    op.alter_column('users', 'status',
                    existing_type=sa.String(20),
                    nullable=False,
                    server_default='active')

def downgrade():
    op.drop_column('users', 'status')
```

**场景2：拆分字段**

将 `users.full_name` 拆分为 `first_name` 和 `last_name`：

```python
def upgrade():
    # 1. 添加新列
    op.add_column('users', sa.Column('first_name', sa.String(50), nullable=True))
    op.add_column('users', sa.Column('last_name', sa.String(50), nullable=True))

    # 2. 使用 SQLAlchemy Core 拆分数据
    users = sa.table('users',
        sa.column('id', sa.Integer),
        sa.column('full_name', sa.String),
        sa.column('first_name', sa.String),
        sa.column('last_name', sa.String),
    )
    conn = op.get_bind()
    results = conn.execute(users.select()).fetchall()
    for row in results:
        parts = row.full_name.split(' ', 1) if row.full_name else ['', '']
        first = parts[0]
        last = parts[1] if len(parts) > 1 else ''
        conn.execute(
            users.update().where(users.c.id == row.id).values(
                first_name=first,
                last_name=last
            )
        )

    # 3. 设置新列为 NOT NULL
    op.alter_column('users', 'first_name', existing_type=sa.String(50), nullable=False)
    op.alter_column('users', 'last_name', existing_type=sa.String(50), nullable=False)

    # 4. 删除旧列
    op.drop_column('users', 'full_name')

def downgrade():
    # 反向操作：合并 first_name 和 last_name 为 full_name
    op.add_column('users', sa.Column('full_name', sa.String(100), nullable=True))

    users = sa.table('users',
        sa.column('id', sa.Integer),
        sa.column('full_name', sa.String),
        sa.column('first_name', sa.String),
        sa.column('last_name', sa.String),
    )
    conn = op.get_bind()
    conn.execute(
        users.update().values(
            full_name=sa.func.concat(users.c.first_name, ' ', users.c.last_name)
        )
    )

    op.alter_column('users', 'full_name', existing_type=sa.String(100), nullable=False)
    op.drop_column('users', 'first_name')
    op.drop_column('users', 'last_name')
```

**场景3：创建初始数据**

```python
def upgrade():
    # 创建默认角色
    roles = sa.table('roles',
        sa.column('id', sa.Integer),
        sa.column('name', sa.String),
        sa.column('description', sa.String),
    )
    op.bulk_insert(roles, [
        {'id': 1, 'name': 'admin', 'description': 'Administrator'},
        {'id': 2, 'name': 'user', 'description': 'Regular user'},
        {'id': 3, 'name': 'guest', 'description': 'Guest user'},
    ])

def downgrade():
    roles = sa.table('roles', sa.column('name', sa.String))
    op.execute(roles.delete().where(roles.c.name.in_(['admin', 'user', 'guest'])))
```

**场景4：使用原生 SQL 处理复杂数据**

```python
def upgrade():
    conn = op.get_bind()
    # 使用原生 SQL 执行复杂的数据转换
    conn.execute(sa.text("""
        UPDATE orders
        SET total_amount = subtotal + tax + shipping
        WHERE total_amount IS NULL
    """))

    # 使用 CASE WHEN 做条件更新
    conn.execute(sa.text("""
        UPDATE users
        SET tier = CASE
            WHEN total_orders > 100 THEN 'platinum'
            WHEN total_orders > 50 THEN 'gold'
            WHEN total_orders > 10 THEN 'silver'
            ELSE 'bronze'
        END
    """))
```

### 总结

- 数据迁移使用 `op.get_bind()` 获取连接，配合 SQLAlchemy Core 或原生 SQL 操作数据。
- 使用 `sa.table()` 定义临时表对象，避免依赖 ORM 模型。
- `op.bulk_insert()` 适合批量插入初始数据。
- **核心原则**：迁移脚本中不要使用 ORM 模型，因为模型会演进，旧迁移脚本可能因模型变更而失效。
- **注意事项**：大数据量迁移要注意性能，避免在 Python 中逐行处理。尽量用 SQL 批量操作，或分批处理。
- **注意事项**：数据迁移的 downgrade 要特别小心——如果 upgrade 删除了数据，downgrade 无法恢复。这种情况下 downgrade 应该抛出异常或只做结构回滚。

## 第11讲 分支与合并：Branching & Merging

### 概念

当多个开发者同时基于同一个 revision 创建新迁移时，版本链会分叉，形成多个 **branch（分支）**，每个分支有自己的 head。这会导致 Alembic 不知道该先执行哪个分支，需要通过 **merge（合并）** 将多个分支重新合并为一个。

### 原理

**分支是如何产生的**：

```
原始状态：
  A ← B ← C (head)

开发者1基于C创建D：
  A ← B ← C ← D (head)

开发者2也基于C创建E（此时他还没拉取D）：
  A ← B ← C ← D (head1)
           ↖ ← E (head2)

现在有两个 head，版本链分叉了。
```

**合并的作用**：创建一个 merge revision，它的 `down_revision` 是一个**列表**，包含所有被合并分支的 head：

```python
revision = 'merge001'
down_revision = ['D', 'E']  # 多个前驱
```

合并后：

```
  A ← B ← C ← D ← merge001 (head)
           ↖ ← E ↗
```

**分支标签（branch_labels）**：可以为分支打标签，方便引用。例如 `alembic upgrade mybranch@head`。

### 例子

**场景：两个开发者同时创建迁移**

开发者1创建迁移D：

```bash
# 开发者1
alembic revision -m "add phone column"
# 生成 revision D, down_revision = C
```

开发者2创建迁移E：

```bash
# 开发者2（还没拉取D）
alembic revision -m "add address table"
# 生成 revision E, down_revision = C
```

当两个开发者的代码合并后，查看 head：

```bash
$ alembic heads
d1e2f3g4h5i6 (head)
e7f8g9h0i1j2 (head)
WARNING: multiple heads present; specify branch with @ syntax
```

**创建合并迁移**：

```bash
alembic merge -m "merge branches" d1e2f3g4h5i6 e7f8g9h0i1j2
```

生成的合并脚本：

```python
"""merge branches

Revision ID: m1e2r3g4e5
Revises: d1e2f3g4h5i6, e7f8g9h0i1j2
Create Date: 2025-01-15 14:00:00.000000
"""
from alembic import op
import sqlalchemy as sa

revision = 'm1e2r3g4e5'
down_revision = ('d1e2f3g4h5i6', 'e7f8g9h0i1j2')  # 注意是元组
branch_labels = None
depends_on = None

def upgrade():
    pass    # 合并迁移通常为空

def downgrade():
    pass
```

合并后查看 head：

```bash
$ alembic heads
m1e2r3g4e5 (head)
```

现在只有一个 head 了，可以正常 `alembic upgrade head`。

**使用分支标签**：

创建带标签的分支：

```bash
alembic revision -m "feature branch" --branch-label feature_x
```

引用分支：

```bash
# 升级到 feature_x 分支的 head
alembic upgrade feature_x@head

# 查看特定分支的当前版本
alembic current --head-only feature_x@head
```

**分支的执行顺序**：当有多个分支需要执行时，Alembic 会按字母顺序排列的 revision ID 执行。如果需要指定顺序，可以使用 `depends_on`：

```python
revision = 'e7f8g9h0i1j2'
down_revision = 'c3a8e9f1d2b3'
depends_on = ['d1e2f3g4h5i6']  # E 依赖 D，确保 D 先执行
```

### 总结

- 多 head 是团队协作中的常见问题，通过 `alembic merge` 解决。
- 合并迁移的 `down_revision` 是元组，包含所有被合并的 head。
- 合并迁移的 `upgrade()` 和 `downgrade()` 通常为空。
- 分支标签（`--branch-label`）可以方便地引用特定分支。
- **注意事项**：合并迁移只是"版本链的合并"，不会执行任何实际操作。真正的 DDL/DML 已经在各分支的迁移中定义。
- **注意事项**：合并前确保所有分支的迁移都已经在本地测试通过。合并后执行 `alembic upgrade head` 会按顺序执行所有未应用的迁移。

## 第12讲 离线模式与 SQL 生成

### 概念

**离线模式（Offline Mode）** 是指 Alembic 不连接数据库，而是根据迁移脚本生成对应的 SQL 语句，输出到终端或文件。这在以下场景非常有用：生产环境不允许直接连接数据库执行迁移，需要由 DBA 审核并手动执行 SQL；或者需要将 SQL 脚本归档审计。

### 原理

离线模式的工作原理：

1. Alembic 不创建数据库连接，而是使用 `context.configure(url=..., literal_binds=True)` 配置一个"虚拟"上下文
2. 执行迁移脚本时，`op` 对象不执行 SQL，而是将生成的 SQL 收集起来
3. 通过 `context.run_migrations()` 输出所有收集到的 SQL

`literal_binds=True` 参数的作用是将 SQL 中的参数绑定转换为字面值。例如，`INSERT INTO users (name) VALUES (?)` 会变成 `INSERT INTO users (name) VALUES ('John')`，这样生成的 SQL 可以直接复制执行。

离线模式生成的 SQL 会包含版本更新语句：

```sql
UPDATE alembic_version SET version_num='新版本' WHERE version_num='旧版本';
```

### 例子

**基本用法：生成升级 SQL**

```bash
alembic upgrade head --sql
```

输出示例：

```sql
-- 假设当前数据库在版本 C，要升级到 head（版本 D）

CREATE TABLE users (
    id INTEGER NOT NULL,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(120) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE (email)
);

UPDATE alembic_version SET version_num='d1e2f3g4h5i6' WHERE version_num='c3a8e9f1d2b3';
```

**生成指定版本范围的 SQL**

```bash
# 从版本 A 升级到版本 D 的 SQL
alembic upgrade a1b2c3d4e5f6:d1e2f3g4h5i6 --sql

# 从当前版本降级一步的 SQL
alembic downgrade -1 --sql

# 从 head 降级到 base 的 SQL（全部回滚）
alembic downgrade base --sql
```

**将 SQL 输出到文件**

```bash
alembic upgrade head --sql > migration.sql
```

**模拟从全新数据库升级**

```bash
# 从 base 开始，生成所有迁移的 SQL
alembic upgrade base:head --sql > full_schema.sql
```

这会生成从空数据库到最新版本的所有 SQL，适合用于初始化新环境。

**实际生产场景：生成迁移 SQL 供 DBA 审核**

```bash
# 1. 先查看当前生产环境版本
alembic current
# 输出：c3a8e9f1d2b3 (head)

# 2. 开发环境生成新迁移后，查看生产环境需要执行的 SQL
alembic upgrade c3a8e9f1d2b3:head --sql > prod_migration_$(date +%Y%m%d).sql

# 3. DBA 审核后，在生产数据库手动执行
psql -U dbuser -d proddb -f prod_migration_20250115.sql
```

**离线模式的限制**：

离线模式无法执行数据迁移中的 Python 逻辑。例如，第10讲中"拆分 full_name"的迁移，在离线模式下只能生成 Schema 变更的 SQL，无法生成数据处理的 SQL（因为数据处理是用 Python 写的）。

对于这种情况，需要在迁移脚本中区分在线/离线模式：

```python
def upgrade():
    op.add_column('users', sa.Column('first_name', sa.String(50), nullable=True))
    op.add_column('users', sa.Column('last_name', sa.String(50), nullable=True))

    # 数据迁移只能在在线模式执行
    if not context.is_offline_mode():
        users = sa.table('users',
            sa.column('id', sa.Integer),
            sa.column('full_name', sa.String),
            sa.column('first_name', sa.String),
            sa.column('last_name', sa.String),
        )
        conn = op.get_bind()
        # ... 数据处理逻辑 ...
    else:
        # 离线模式：输出提示，需要手动处理数据
        print("WARNING: Data migration skipped in offline mode. "
              "Please manually split full_name into first_name and last_name.")

    op.alter_column('users', 'first_name', existing_type=sa.String(50), nullable=False)
    op.alter_column('users', 'last_name', existing_type=sa.String(50), nullable=False)
    op.drop_column('users', 'full_name')
```

### 总结

- 离线模式用 `--sql` 参数启用，不连接数据库，只生成 SQL。
- `literal_binds=True` 将参数绑定转为字面值，生成的 SQL 可直接执行。
- 典型用途：生产环境迁移审核、SQL 归档、新环境初始化。
- `alembic upgrade base:head --sql` 生成完整建库脚本。
- **注意事项**：离线模式无法执行 Python 数据迁移逻辑，需要特殊处理或手动补充。
- **注意事项**：生成的 SQL 包含 `UPDATE alembic_version` 语句，手动执行时不要遗漏，否则版本追踪会不一致。
- **注意事项**：不同数据库的 SQL 方言不同，离线模式生成的 SQL 只适用于对应数据库。在 PostgreSQL 上生成的 SQL 不能直接在 MySQL 上执行。

# 第四章 高级技巧

## 第13讲 自定义类型与 SQLAlchemy 模型深度集成

### 概念

当项目使用自定义的 SQLAlchemy 类型（如枚举类型、JSON 类型、自定义 TypeDecorator）时，迁移脚本需要正确处理这些类型。本讲讲解如何在迁移脚本中引用自定义类型，以及如何让 Autogenerate 正确识别它们。

### 原理

**SQLAlchemy 的类型系统**：

- **通用类型**（Generic Type）：如 `sa.String`、`sa.Integer`，跨数据库通用
- **方言类型**（Dialect-specific Type）：如 `postgresql.JSONB`、`mysql.LONGTEXT`，特定数据库
- **自定义类型**：继承 `TypeDecorator` 或 `UserDefinedType`，实现自定义逻辑

在迁移脚本中使用自定义类型时，需要确保：
1. 迁移脚本能导入这些类型定义
2. Autogenerate 能识别这些类型并正确生成代码
3. 类型在不同数据库上的行为一致

**`render_item` 配置**：当 Autogenerate 遇到不认识的类型时，默认会生成 `sa.VARCHAR()` 等通用类型。通过配置 `render_as_batch` 和自定义 `render_item` 函数，可以控制类型的渲染方式。

### 例子

**场景1：使用 PostgreSQL 的 JSONB 类型**

```python
# models.py
from sqlalchemy import Column, Integer, String
from sqlalchemy.dialects.postgresql import JSONB
from sqlalchemy.orm import DeclarativeBase

class Base(DeclarativeBase):
    pass

class Product(Base):
    __tablename__ = 'products'
    id = Column(Integer, primary_key=True)
    name = Column(String(100))
    attributes = Column(JSONB)  # 使用 JSONB 存储产品属性
```

迁移脚本中使用：

```python
"""create products table

Revision ID: g2f3e4d5c6b7
"""
from alembic import op
import sqlalchemy as sa
from sqlalchemy.dialects.postgresql import JSONB

revision = 'g2f3e4d5c6b7'
down_revision = 'f1e2d3c4b5a6'

def upgrade():
    op.create_table(
        'products',
        sa.Column('id', sa.Integer, primary_key=True),
        sa.Column('name', sa.String(100), nullable=False),
        sa.Column('attributes', JSONB, nullable=True),
    )

def downgrade():
    op.drop_table('products')
```

**场景2：自定义 TypeDecorator**

```python
# models.py
from sqlalchemy.types import TypeDecorator, String
import json

class JSONEncodedDict(TypeDecorator):
    """自定义类型：将 dict 编码为 JSON 字符串存储"""
    impl = String(500)
    cache_ok = True  # 重要：标记类型可安全缓存

    def process_bind_param(self, value, dialect):
        if value is not None:
            return json.dumps(value)
        return None

    def process_result_value(self, value, dialect):
        if value is not None:
            return json.loads(value)
        return None

class User(Base):
    __tablename__ = 'users'
    id = Column(Integer, primary_key=True)
    name = Column(String(50))
    preferences = Column(JSONEncodedDict)  # 自定义类型
```

迁移脚本中使用自定义类型：

```python
"""add preferences column

Revision ID: h3g4f5e6d7c8
"""
from alembic import op
import sqlalchemy as sa
from myapp.models import JSONEncodedDict  # 导入自定义类型

revision = 'h3g4f5e6d7c8'
down_revision = 'g2f3e4d5c6b7'

def upgrade():
    op.add_column('users',
        sa.Column('preferences', JSONEncodedDict, nullable=True))

def downgrade():
    op.drop_column('users', 'preferences')
```

**场景3：配置 env.py 让 Autogenerate 正确渲染自定义类型**

默认情况下，Autogenerate 可能无法正确渲染自定义类型。需要在 `env.py` 中配置 `render_item`：

```python
# env.py
def render_item(type_, obj, autogen_context):
    """自定义渲染逻辑"""
    if type_ == "type" and isinstance(obj, JSONEncodedDict):
        # 让 autogenerate 生成 JSONEncodedDict 而非 String
        autogen_context.imports.add("from myapp.models import JSONEncodedDict")
        return "JSONEncodedDict()"
    return False  # 使用默认渲染

def run_migrations_online():
    # ...
    context.configure(
        connection=connection,
        target_metadata=target_metadata,
        render_item=render_item,  # 注册自定义渲染器
        compare_type=True,
    )
```

**场景4：使用 Enum 类型**

```python
# models.py
import enum
from sqlalchemy import Column, Integer, Enum

class UserStatus(enum.Enum):
    active = "active"
    inactive = "inactive"
    banned = "banned"

class User(Base):
    __tablename__ = 'users'
    id = Column(Integer, primary_key=True)
    status = Column(Enum(UserStatus), default=UserStatus.active)
```

迁移脚本：

```python
from alembic import op
import sqlalchemy as sa
from myapp.models import UserStatus

def upgrade():
    # 方式1：使用 Python enum
    op.add_column('users',
        sa.Column('status', sa.Enum(UserStatus), nullable=True))

    # 方式2：使用字符串枚举（更通用）
    op.add_column('users',
        sa.Column('status',
            sa.Enum('active', 'inactive', 'banned', name='userstatus'),
            nullable=True))

def downgrade():
    op.drop_column('users', 'status')
    # 注意：某些数据库需要手动删除枚举类型
    op.execute("DROP TYPE userstatus")  # PostgreSQL
```

### 总结

- 迁移脚本中可以直接使用 SQLAlchemy 的方言类型（如 `JSONB`）和自定义类型。
- 自定义 `TypeDecorator` 必须设置 `cache_ok = True`，否则会有性能警告。
- 通过 `env.py` 的 `render_item` 配置，可以让 Autogenerate 正确渲染自定义类型。
- Enum 类型在不同数据库行为不同：PostgreSQL 会创建独立的 TYPE 对象，删除列后需要手动 DROP TYPE。
- **注意事项**：迁移脚本导入自定义类型时，要确保导入路径在 `alembic.ini` 的 `prepend_sys_path` 中可用。
- **注意事项**：自定义类型的 `impl` 类型变更（如从 `String(500)` 改为 `String(1000)`）不会触发 Autogenerate，需要手动编写迁移。

## 第14讲 事务、约束与批量操作

### 概念

本讲讲解三个高级主题：迁移执行的事务行为、约束的延迟检查（Deferrable Constraints）、以及 SQLite 的批量操作模式（Batch Operations）。理解这些内容对于编写安全、跨数据库兼容的迁移脚本至关重要。

### 原理

**事务行为**：

Alembic 默认在事务中执行迁移。`context.begin_transaction()` 会开启一个事务，所有 `op` 调用都在这个事务中执行。如果迁移成功，事务提交；如果失败，事务回滚。

但不同数据库对 DDL 事务的支持不同：

| 数据库 | DDL 事务支持 | 说明 |
|--------|-------------|------|
| PostgreSQL | 支持 | ALTER TABLE 等可回滚 |
| SQLite | 支持 | 通过 batch 模式 |
| MySQL | 不支持 | DDL 隐式提交 |
| Oracle | 支持 | 但某些 DDL 会自动提交 |

**延迟约束（Deferrable Constraints）**：

PostgreSQL 支持将约束（如外键）标记为 `DEFERRABLE`，这样约束检查可以延迟到事务提交时，而非每条语句执行时。这在数据迁移时很有用——你可以临时违反约束，只要事务提交前修复即可。

**批量操作（Batch Operations）**：

SQLite 的 ALTER TABLE 支持非常有限：只能加列、改表名，不能删列、改列类型、加约束。Alembic 的 `batch_alter_table` 通过"影子表"模式模拟这些操作：

1. 创建一个新表（结构为目标结构）
2. 从旧表复制数据到新表
3. 删除旧表
4. 将新表重命名为旧表名

这个模式也可用于其他数据库，虽然性能不如原生 ALTER，但保证了一致性。

### 例子

**场景1：理解事务行为**

```python
def upgrade():
    # 这些操作在同一个事务中
    op.add_column('users', sa.Column('email', sa.String(120)))

    # 如果这里出错，前面的 add_column 也会回滚（在支持 DDL 事务的数据库上）
    op.create_index('ix_users_email', 'users', ['email'])

    # 但在 MySQL 上，add_column 已经隐式提交，无法回滚
```

**场景2：使用 DEFERRABLE 约束（PostgreSQL）**

```python
def upgrade():
    # 创建可延迟的外键约束
    op.create_foreign_key(
        'fk_orders_user_id',
        'orders',
        'users',
        ['user_id'],
        ['id'],
        deferrable=True,          # 允许延迟检查
        initially='deferred',     # 默认延迟到事务提交
    )

def downgrade():
    op.drop_constraint('fk_orders_user_id', 'orders', type_='foreignkey')
```

**场景3：SQLite 批量操作**

```python
def upgrade():
    # SQLite 不支持 drop_column，必须用 batch 模式
    with op.batch_alter_table('users') as batch_op:
        batch_op.add_column(sa.Column('age', sa.Integer))
        batch_op.alter_column('name', existing_type=sa.String(50),
                              type_=sa.String(100), nullable=False)
        batch_op.drop_column('old_column')

def downgrade():
    with op.batch_alter_table('users') as batch_op:
        batch_op.add_column(sa.Column('old_column', sa.String(50)))
        batch_op.alter_column('name', existing_type=sa.String(100),
                              type_=sa.String(50))
        batch_op.drop_column('age')
```

**场景4：批量操作保留表属性**

在 PostgreSQL 上使用 batch 模式时，需要指定表属性以避免丢失：

```python
def upgrade():
    with op.batch_alter_table(
        'users',
        recreate='always',          # 强制重建表
        table_args=[
            # 保留表的注释、存储引擎等属性
        ],
        table_kwargs={
            'mysql_engine': 'InnoDB',  # MySQL 存储引擎
            'mysql_charset': 'utf8mb4',
        }
    ) as batch_op:
        batch_op.add_column(sa.Column('phone', sa.String(20)))
```

**场景5：批量操作中保留约束和索引**

```python
def upgrade():
    with op.batch_alter_table('users', schema='my_schema') as batch_op:
        # 在 batch 上下文中，可以重新定义约束
        batch_op.create_unique_constraint('uq_users_email', ['email'])
        batch_op.create_index('ix_users_name', ['name'])

        # 修改列
        batch_op.alter_column('name',
            existing_type=sa.String(50),
            type_=sa.String(100),
            nullable=False)
```

**场景6：跨数据库兼容的迁移脚本**

```python
from alembic import op
import sqlalchemy as sa

def upgrade():
    # 检测数据库类型
    bind = op.get_bind()
    dialect_name = bind.dialect.name

    if dialect_name == 'sqlite':
        # SQLite 需要 batch 模式
        with op.batch_alter_table('users') as batch_op:
            batch_op.alter_column('name',
                existing_type=sa.String(50),
                type_=sa.String(100))
    else:
        # PostgreSQL/MySQL 可以直接 alter
        op.alter_column('users', 'name',
            existing_type=sa.String(50),
            type_=sa.String(100),
            existing_nullable=True)

def downgrade():
    bind = op.get_bind()
    dialect_name = bind.dialect.name

    if dialect_name == 'sqlite':
        with op.batch_alter_table('users') as batch_op:
            batch_op.alter_column('name',
                existing_type=sa.String(100),
                type_=sa.String(50))
    else:
        op.alter_column('users', 'name',
            existing_type=sa.String(100),
            type_=sa.String(50),
            existing_nullable=True)
```

### 总结

- Alembic 默认在事务中执行迁移，但 MySQL 的 DDL 不支持事务回滚。
- PostgreSQL 支持 DEFERRABLE 约束，适合复杂数据迁移。
- `batch_alter_table` 是 SQLite 的必备工具，也可用于其他数据库。
- 跨数据库项目需要根据 `bind.dialect.name` 分支处理。
- **注意事项**：batch 模式会重建表，大表会锁表较长时间。生产环境使用前评估影响。
- **注意事项**：batch 模式可能丢失表的注释、触发器、存储过程等附属对象，需要显式保留。
- **注意事项**：MySQL 上迁移失败后，数据库可能处于中间状态。务必在执行前备份，并准备好手动修复方案。

## 第15讲 编程式 API：在代码中调用 Alembic

### 概念

除了命令行工具，Alembic 还提供了完整的编程式 API。你可以在 Python 代码中直接调用 Alembic 执行迁移，这在以下场景非常有用：应用启动时自动迁移、测试环境初始化数据库、构建自定义部署脚本、集成到应用框架中。

### 原理

Alembic 的编程式 API 主要通过 `alembic.command` 和 `alembic.config` 模块提供：

- `alembic.config.Config`：配置对象，对应 `alembic.ini` 的内容
- `alembic.command`：提供与命令行对应的函数，如 `command.upgrade()`、`command.downgrade()`

编程式 API 的工作流程：

1. 创建 `Config` 对象，加载 `alembic.ini`
2. 可选：覆盖配置（如数据库 URL）
3. 调用 `command.upgrade(config, 'head')` 等函数

与命令行不同，编程式 API 允许你在调用前后插入自定义逻辑，比如记录日志、发送通知、执行健康检查等。

### 例子

**场景1：基础用法——在代码中执行迁移**

```python
from alembic.config import Config
from alembic import command

# 加载配置
alembic_cfg = Config("alembic.ini")

# 执行升级
command.upgrade(alembic_cfg, "head")

# 执行降级
# command.downgrade(alembic_cfg, "-1")

# 查看当前版本
# command.current(alembic_cfg)
```

**场景2：动态配置数据库 URL**

```python
from alembic.config import Config
from alembic import command
import os

def run_migrations(database_url: str, target: str = "head"):
    """在指定数据库上执行迁移"""

    # 覆盖数据库 URL
    cfg.set_main_option("sqlalchemy.url", database_url)

    command.upgrade(cfg, target)

# 使用环境变量

run_migrations(db_url)
```

**场景3：应用启动时自动迁移**

```python
# app.py
from alembic.config import Config
from alembic import command
from alembic.runtime.migration import MigrationContext
from sqlalchemy import create_engine
import logging

logger = logging.getLogger(__name__)

def check_and_migrate(database_url: str):
    """应用启动时检查并执行迁移"""
    engine = create_engine(database_url)

    # 检查当前版本
    with engine.connect() as conn:
        mc = MigrationContext.configure(conn)
        current_rev = mc.get_current_revision()

    if current_rev is None:
        logger.info("Database not initialized, running migrations...")
    else:
        logger.info(f"Current database version: {current_rev}")

    # 执行迁移
    cfg = Config("alembic.ini")
    cfg.set_main_option("sqlalchemy.url", database_url)
    command.upgrade(cfg, "head")

    logger.info("Migrations completed.")

# 在应用启动时调用
if __name__ == "__main__":
    check_and_migrate("postgresql://user:pass@localhost/mydb")
```

from alembic import command
import argparse
import sys

def main():
    parser = argparse.ArgumentParser(description="Database migration tool")
    parser.add_argument("action", choices=["upgrade", "downgrade", "current", "history"])
    parser.add_argument("--target", default="head", help="Target revision")

    elif args.action == "downgrade":
        command.downgrade(cfg, args.target)
    elif args.action == "current":
        command.current(cfg)
    elif args.action == "history":

- 编程式 API 通过 `alembic.config.Config` 和 `alembic.command` 提供。
- 核心函数：`command.upgrade()`、`command.downgrade()`、`command.current()`、`command.stamp()`。
- 典型用途：应用启动自动迁移、测试初始化、自定义部署脚本。
- `MigrationContext` 可以直接查询当前版本，无需执行迁移。
- **注意事项**：编程式 API 调用 `command.upgrade()` 时，`env.py` 仍然会被加载执行。确保 `env.py` 中的逻辑在编程式调用时也能正常工作。
- **注意事项**：应用启动时自动迁移要考虑并发问题——多个实例同时启动可能同时执行迁移。建议使用分布式锁或只让一个实例执行迁移。

# 第五章 实战与最佳实践

## 第16讲 团队协作中的迁移管理

### 概念

在多人协作的项目中，数据库迁移脚本的管理是一个需要特别注意的问题。如果团队成员不遵循统一的规范，很容易出现版本链冲突、迁移脚本丢失、数据库状态不一致等问题。本讲讲解团队协作中 Alembic 迁移管理的最佳实践。

### 原理

**团队协作中的核心挑战**：

1. **并发创建迁移**：多个开发者同时基于同一个 revision 创建迁移，导致多 head
2. **迁移脚本冲突**：两个迁移修改同一张表，执行顺序不当会导致错误
3. **代码合并问题**：Git 合并时，迁移脚本的 `down_revision` 可能需要调整
4. **环境一致性**：不同开发者的本地数据库版本可能不同

**最佳实践原则**：

- **一个迁移只做一件事**：不要在一个迁移中混合多个不相关的变更
- **迁移脚本不可修改**：一旦提交到版本库，就不能再修改（除非还没推送）
- **及时合并多 head**：发现多 head 时立即 merge
- **提交前本地测试**：确保迁移在本地能正常 upgrade 和 downgrade
- **代码评审**：迁移脚本必须经过评审，尤其是涉及数据变更的

### 例子

**实践1：规范的迁移脚本结构**

```python
"""add phone column to users table

Revision ID: a1b2c3d4e5f6
Revises: 9z8y7x6w5v4u
Create Date: 2025-01-15 10:00:00.000000

变更说明：
- 在 users 表添加 phone 列，用于存储用户手机号
- 类型为 VARCHAR(20)，允许 NULL（现有用户没有手机号）
- 添加唯一索引防止重复

关联需求：JIRA-1234
"""
from alembic import op
import sqlalchemy as sa

revision = 'a1b2c3d4e5f6'
down_revision = '9z8y7x6w5v4u'
branch_labels = None
depends_on = None

def upgrade():
    # 1. 添加列（允许 NULL，避免现有数据报错）
    op.add_column('users',
        sa.Column('phone', sa.String(20), nullable=True))

    # 2. 添加唯一索引
    op.create_index('ix_users_phone', 'users', ['phone'], unique=True)

def downgrade():
    # 严格对称的回滚
    op.drop_index('ix_users_phone', table_name='users')
    op.drop_column('users', 'phone')
```

**实践2：处理多 head 的工作流**

```bash

```

### 总结

- 团队协作的核心是规范和沟通，迁移脚本必须遵循统一标准。
- 多 head 是正常现象，发现后及时 merge。
- CI 中加入多 head 检测，防止问题进入主分支。
- 迁移脚本一旦提交就不可修改，需要修改则创建新迁移。
- **注意事项**：不要在迁移脚本中使用 `from myapp.models import User` 这样的 ORM 导入。模型会演进，旧迁移脚本可能因此失效。
- **注意事项**：如果两个迁移修改同一张表，确保它们的操作不冲突。例如，迁移A加了列 `phone`，迁移B也加了列 `phone`，合并后执行会报错。这种情况需要手动调整其中一个迁移。

## 第17讲 生产环境部署与回滚策略

### 概念

生产环境的数据库迁移是最需要谨慎对待的操作。一个错误的迁移可能导致服务中断、数据丢失。本讲讲解生产环境迁移的部署策略、回滚方案，以及如何最小化迁移对线上服务的影响。

### 原理

**生产环境迁移的核心原则**：

1. **零停机优先**：尽量采用不锁表的迁移方式
2. **可回滚**：每个迁移必须有可靠的 downgrade
3. **分阶段发布**：复杂变更拆分为多个迁移，分批上线
4. **备份优先**：迁移前必须备份数据库
5. **低峰执行**：在业务低峰期执行迁移

**扩展性迁移模式（Expand-Contract Pattern）**：

对于破坏性的 Schema 变更（如改列类型、删列），采用分阶段策略：

- **Expand 阶段**：添加新结构，与旧结构并存
- **Migrate 阶段**：迁移数据到新结构
- **Contract 阶段**：移除旧结构

例如，将 `users.phone` 从 `VARCHAR(20)` 改为 `VARCHAR(30)`：

1. 迁移1：添加 `phone_new VARCHAR(30)`（Expand）
2. 迁移2：将 `phone` 数据复制到 `phone_new`
3. 部署代码：应用读写 `phone_new`
4. 迁移3：删除 `phone`，将 `phone_new` 重命名为 `phone`（Contract）

### 例子

**策略1：大表加列（零停机）**

```python
"""add status column to orders (10M+ rows)

注意：此迁移针对大表，采用安全策略
"""
from alembic import op
import sqlalchemy as sa

revision = 'x1y2z3'
down_revision = 'w9x8y7'

def upgrade():
    # 1. 添加带默认值的列
    # PostgreSQL 11+ 会优化为元数据操作，不重写表
    # MySQL 8.0+ 同样支持 instant ADD COLUMN
    op.add_column('orders',
        sa.Column('status', sa.String(20),
                  server_default='pending',
                  nullable=False))

def downgrade():
    op.drop_column('orders', 'status')
```

**策略2：大表加索引（在线创建）**

```python
def upgrade():
    # PostgreSQL: CONCURRENTLY 不锁表
    op.execute(
        "CREATE INDEX CONCURRENTLY ix_orders_user_id ON orders (user_id)"
    )

def downgrade():
    op.execute(
        "DROP INDEX CONCURRENTLY ix_orders_user_id"
    )
```

注意：`CONCURRENTLY` 不能在事务中执行，需要在 `env.py` 中配置 `transaction_per_migration = False` 或使用 `with op.get_context().autocommit_block():`。

**策略3：Expand-Contract 模式改列类型**

```python
# 迁移1：Expand - 添加新列
"""step 1: add phone_new column

Revision ID: e1
"""
def upgrade():
    op.add_column('users',
        sa.Column('phone_new', sa.String(30), nullable=True))

def downgrade():
    op.drop_column('users', 'phone_new')


# 迁移2：Migrate - 复制数据
"""step 2: copy phone data to phone_new

Revision ID: e2
Revises: e1
"""
def upgrade():
    conn = op.get_bind()
    conn.execute(sa.text("""
        UPDATE users SET phone_new = phone WHERE phone IS NOT NULL
    """))

def downgrade():
    conn = op.get_bind()
    conn.execute(sa.text("UPDATE users SET phone_new = NULL"))


# 迁移3：Contract - 删除旧列，重命名新列
"""step 3: drop phone, rename phone_new to phone

Revision ID: e3
Revises: e2

注意：执行此迁移前，确保应用代码已切换到使用 phone_new
"""
def upgrade():
    op.drop_column('users', 'phone')
    op.alter_column('users', 'phone_new',
                    new_column_name='phone',
                    existing_type=sa.String(30))

def downgrade():
    # 注意：回滚需要重新添加旧列，可能丢失数据
    op.alter_column('users', 'phone',
                    new_column_name='phone_new',
                    existing_type=sa.String(30))
    op.add_column('users',
        sa.Column('phone', sa.String(20), nullable=True))
```

**策略4：生产部署脚本**

```bash
#!/bin/bash
# scripts/deploy_migrations.sh
set -euo pipefail

DB_URL="${DATABASE_URL:?DATABASE_URL must be set}"
BACKUP_DIR="/backups/$(date +%Y%m%d_%H%M%S)"

echo "=== Production Migration Deploy ==="

# 1. 备份数据库
echo "[1/5] Creating backup..."
mkdir -p "$BACKUP_DIR"
pg_dump "$DB_URL" > "$BACKUP_DIR/pre_migration.sql"
echo "Backup saved to $BACKUP_DIR/pre_migration.sql"

# 2. 检查当前版本
echo "[2/5] Current database version:"
alembic current

# 3. 检查待执行的迁移
echo "[3/5] Pending migrations:"
alembic history -r $(alembic current 2>/dev/null | awk '{print $1}'):head

# 4. 执行迁移
echo "[4/5] Executing migrations..."
alembic upgrade head

# 5. 验证
echo "[5/5] Post-migration version:"
alembic current

echo "=== Migration completed successfully ==="
```

**策略5：回滚脚本**

```bash
#!/bin/bash
# scripts/rollback_migration.sh
set -euo pipefail

DB_URL="${DATABASE_URL:?DATABASE_URL must be set}"
STEPS="${1:-1}"  # 默认回退1步

echo "=== Rolling back $STEPS migration(s) ==="

# 记录回滚前的版本
BEFORE=$(alembic current 2>/dev/null | awk '{print $1}')
echo "Current version: $BEFORE"

# 执行回滚
alembic downgrade "-$STEPS"

# 记录回滚后的版本
AFTER=$(alembic current 2>/dev/null | awk '{print $1}')
echo "Rolled back to: $AFTER"

echo "=== Rollback completed ==="
echo "If needed, restore from backup: pg_restore -d \$DATABASE_URL < backup.sql"
```

### 总结

- 生产迁移遵循"备份 → 检查 → 执行 → 验证"流程。
- 大表操作使用 `CONCURRENTLY`、`instant ADD COLUMN` 等零停机技术。
- 破坏性变更采用 Expand-Contract 模式，分多个迁移逐步进行。
- 必须准备回滚脚本和数据库备份。
- **注意事项**：PostgreSQL 的 `CREATE INDEX CONCURRENTLY` 不能在事务中执行，需要特殊处理 `env.py`。
- **注意事项**：MySQL 的 `ALTER TABLE` 会锁表，大表迁移要在低峰期执行，或使用 `pt-online-schema-change` 等工具。
- **注意事项**：Expand-Contract 模式中，Contract 阶段（删旧列）必须在应用代码完全切换后才能执行，否则会导致应用报错。建议在两个版本之间留出足够的观察期。

## 第18讲 CI/CD 集成与常见陷阱

### 概念

将 Alembic 迁移集成到 CI/CD 流水线中，可以实现迁移的自动化测试和部署。同时，本讲总结 Alembic 使用中的常见陷阱和解决方案，帮助你避免踩坑。

### 原理

**CI/CD 中的迁移测试策略**：

1. **CI 阶段**：每次提交自动测试迁移能否正常执行
2. **CD 阶段**：部署时自动执行迁移或生成 SQL 供审核
3. **回滚机制**：部署失败时自动回滚迁移

**常见陷阱分类**：

- **版本链问题**：多 head、断链、revision ID 冲突
- **数据问题**：数据丢失、ORM 依赖、大数据量性能
- **数据库差异**：SQLite 与 PostgreSQL 行为不同
- **环境问题**：环境变量缺失、路径问题、权限问题

### 例子

**CI/CD 配置1：GitHub Actions 完整流水线**

```yaml
# .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [main]

jobs:
  test-migrations:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:15
        env:
          POSTGRES_PASSWORD: test
          POSTGRES_DB: testdb
        ports:
          - 5432:5432
    steps:
      - uses: actions/checkout@v3
      - uses: actions/setup-python@v4
        with:
          python-version: '3.11'

      - name: Install dependencies
        run: |
          pip install alembic sqlalchemy psycopg2-binary
          pip install -r requirements.txt

      - name: Check single head
        run: |
          HEADS=$(alembic heads | grep -c "(head)")
          [ "$HEADS" -eq 1 ] || { echo "Multiple heads!"; exit 1; }

      - name: Test fresh migration
        env:
          DATABASE_URL: postgresql://postgres:test@localhost:5432/testdb
        run: |
          # 从零开始迁移
          alembic upgrade head
          echo "Fresh migration: OK"

      - name: Test downgrade
        env:
          DATABASE_URL: postgresql://postgres:test@localhost:5432/testdb
        run: |
          # 测试回滚
          alembic downgrade base
          echo "Downgrade: OK"

      - name: Test upgrade again
        env:
          DATABASE_URL: postgresql://postgres:test@localhost:5432/testdb
        run: |
          alembic upgrade head
          echo "Re-upgrade: OK"

  deploy:
    needs: test-migrations
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v3
      - name: Deploy to production
        env:
          DATABASE_URL: ${{ secrets.PROD_DATABASE_URL }}
        run: |
          # 生成迁移 SQL 供审核
          alembic upgrade head --sql > migration.sql
          cat migration.sql

          # 执行迁移
          alembic upgrade head
```

**常见陷阱1：Autogenerate 漏检列重命名**

```python
# 问题：将 User.name 改为 User.full_name
# Autogenerate 会生成：
#   op.drop_column('users', 'name')
#   op.add_column('users', sa.Column('full_name', sa.String(50)))
# 这会导致数据丢失！

# 解决：手动编写迁移，使用 alter_column 的 new_column_name
def upgrade():
    op.alter_column('users', 'name',
                    new_column_name='full_name',
                    existing_type=sa.String(50))
```

**常见陷阱2：迁移脚本中使用 ORM**

```python
# 错误做法
from myapp.models import User

def upgrade():
    # 这会在模型变更后失效！
    users = session.query(User).all()
    for user in users:
        user.status = 'active'
    session.commit()

# 正确做法
def upgrade():
    users = sa.table('users',
        sa.column('id', sa.Integer),
        sa.column('status', sa.String),
    )
    op.execute(users.update().values(status='active'))
```

**常见陷阱3：SQLite 测试通过，PostgreSQL 生产失败**

```python
# 问题：SQLite 不强制外键约束，PostgreSQL 会
def upgrade():
    op.add_column('orders',
        sa.Column('user_id', sa.Integer, sa.ForeignKey('users.id'), nullable=False))
    # SQLite: OK（不检查现有数据）
    # PostgreSQL: 如果有 user_id 为 NULL 的行，会失败

# 解决：分两步
def upgrade():
    # 1. 添加允许 NULL 的列
    op.add_column('orders',
        sa.Column('user_id', sa.Integer, nullable=True))

    # 2. 填充数据
    op.execute("UPDATE orders SET user_id = 1 WHERE user_id IS NULL")

    # 3. 添加外键约束
    op.create_foreign_key('fk_orders_user_id', 'orders', 'users',
                          ['user_id'], ['id'])

    # 4. 修改为 NOT NULL
    op.alter_column('orders', 'user_id',
                    existing_type=sa.Integer, nullable=False)
```

**常见陷阱4：迁移卡住（锁表）**

```python
# 问题：在 PostgreSQL 上，ALTER TABLE 会获取锁
# 如果有长事务持有锁，迁移会一直等待

# 解决：设置锁超时
def upgrade():
    op.execute("SET lock_timeout = '5s'")  # 5秒获取不到锁就失败
    op.add_column('users', sa.Column('phone', sa.String(20)))
    op.execute("SET lock_timeout = '0'")   # 恢复默认
```

**常见陷阱5：忘记在 env.py 中导入所有模型**

```python
# 问题：Autogenerate 检测不到某些表
# 原因：模型定义在其他模块，但没有被导入

# 解决：在 env.py 中显式导入所有模型模块
# alembic/env.py
from myapp.models import Base
from myapp.models import user, order, product  # 显式导入所有模型模块
# 或者
import myapp.models  # 确保 __init__.py 中导入了所有模型

target_metadata = Base.metadata
```

**常见陷阱6：生产环境直接执行迁移导致服务中断**

```bash
# 错误：直接在生产执行迁移
alembic upgrade head  # 可能锁表，导致服务超时

# 正确：先生成 SQL 审核，再低峰执行
alembic upgrade head --sql > migration.sql
# 审核 SQL...
# 低峰期执行
alembic upgrade head
```

### 总结

- CI 中测试迁移的完整周期：fresh upgrade → downgrade → re-upgrade。
- Docker 部署时在 entrypoint 中先迁移再启动应用。
- Autogenerate 的列重命名陷阱：务必手动检查。
- 迁移脚本中不要使用 ORM，使用 SQLAlchemy Core。
- **注意事项**：SQLite 是开发/测试友好的数据库，但不强制外键、不支持 ALTER COLUMN，不能作为生产环境迁移的测试基准。建议 CI 中使用与生产相同的数据库（如 PostgreSQL）。
- **注意事项**：生产迁移前务必在预发布环境（staging）完整测试，staging 环境的数据应尽可能接近生产规模。
- **注意事项**：迁移失败后不要慌张，先查看错误日志，评估数据库当前状态。如果迁移部分执行了（MySQL 常见），需要手动修复后用 `alembic stamp` 对齐版本，再继续。
