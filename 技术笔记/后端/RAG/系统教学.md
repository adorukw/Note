# 第一章：RAG 基础认知

本章是整个课程的起点。在深入技术细节之前，我们必须先回答三个根本问题：RAG 究竟是什么？它为什么会出现？它整体上是如何运转的？理解了这三个问题，后续所有技术组件的学习都会有清晰的坐标。

---

## 第 1 讲：什么是 RAG——定义、起源与应用场景

### 概念

**RAG（Retrieval-Augmented Generation，检索增强生成）** 是一种将**信息检索**与**文本生成**结合起来的技术范式。其核心思想是：在让大语言模型（LLM）回答问题之前，先从一个外部知识库中检索出与问题相关的文档片段，然后将这些片段作为上下文拼接到 Prompt 中，再让 LLM 基于这些上下文生成最终答案。

用一句话概括：**RAG = 检索 + 生成**。它让模型"先查资料，再回答"，而不是仅凭自身记忆作答。

### 原理

RAG 的出现有其深刻的技术背景。传统 LLM（如 GPT、LLaMA）是基于大规模语料训练的统计模型，它们的知识被"压缩"在模型参数中。这种参数化知识存在三个根本性缺陷：

1. **知识截止**：模型的知识停留在训练数据的截止时间，无法获取最新信息。
2. **幻觉问题**：当模型对某个问题不确定时，它倾向于"编造"看似合理但实际错误的答案。
3. **私有知识缺失**：模型从未见过企业内部文档、个人笔记等私有数据，无法回答相关问题。

RAG 通过引入一个**外部非参数化知识库**来解决这些问题。检索阶段从知识库中获取事实依据，生成阶段则基于这些事实进行推理与表达。这种"参数化知识 + 非参数化知识"的双轨结构，使得模型既能保持通用的语言理解能力，又能获取精确的、可更新的、可溯源的事实知识。

RAG 的概念最早由 Lewis 等人在 2020 年的论文《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》中系统提出，最初用于问答、事实核查等知识密集型任务。随着 ChatGPT 的兴起，RAG 迅速成为让 LLM 接入私有知识的事实标准。

### 例子

下面是一个最小化的 RAG 工作流伪代码，展示"检索 + 生成"的核心逻辑：

```python
from langchain.embeddings import OpenAIEmbeddings
from langchain.vectorstores import Chroma
from langchain.llms import OpenAI
from langchain.chains import RetrievalQA

# 1. 准备知识库文档
documents = [
    "RAG 由 Lewis 等人在 2020 年提出。",
    "RAG 结合了检索与生成两个阶段。",
    "向量数据库是 RAG 系统的核心存储组件。",
    "Embedding 模型将文本映射为高维向量。"
]

# 2. 构建向量知识库（实际中这一步是离线完成的）
embeddings = OpenAIEmbeddings()
vectorstore = Chroma.from_texts(documents, embeddings)

# 3. 创建检索器
retriever = vectorstore.as_retriever(search_kwargs={"k": 2})

# 4. 创建 RAG 链：检索 + 生成
qa_chain = RetrievalQA.from_chain_type(
    llm=OpenAI(temperature=0),
    chain_type="stuff",
    retriever=retriever
)

# 5. 提问
question = "RAG 是什么时候提出的？"
answer = qa_chain.run(question)
print(answer)
# 输出：RAG 由 Lewis 等人在 2020 年提出。
```

这段代码体现了 RAG 的完整闭环：文档被向量化存入数据库 → 用户提问 → 检索器找出最相关的 2 段文档 → LLM 基于这些文档生成答案。

**典型应用场景**：

| 场景 | 说明 |
|------|------|
| 企业知识库问答 | 员工查询公司制度、产品文档、技术手册 |
| 智能客服 | 基于产品 FAQ 和历史工单回答用户问题 |
| 法律/医疗辅助 | 检索法条/文献，辅助专业人员决策 |
| 学术研究助手 | 检索论文库，回答研究相关问题 |
| 个人笔记助手 | 基于个人知识库（如 Obsidian、Notion）问答 |

### 总结

本讲的核心要点：

1. **RAG = 检索 + 生成**，本质是让 LLM "先查资料再回答"。
2. RAG 解决了 LLM 的三大缺陷：知识截止、幻觉、私有知识缺失。
3. RAG 采用"参数化知识 + 非参数化知识"双轨结构，兼顾通用能力与精确事实。
4. RAG 已成为让 LLM 接入私有知识的事实标准，应用场景广泛。

**常见注意事项**：不要把 RAG 简单等同于"搜索引擎 + LLM"。搜索引擎返回的是文档列表，而 RAG 的检索结果会被进一步加工、组装、推理后生成自然语言答案，二者在目标与流程上有本质区别。

## 第 2 讲：为什么需要 RAG——LLM 的局限性与 RAG 的价值

### 概念

要理解 RAG 的价值，必须先深刻理解 LLM 本身的局限性。本讲聚焦于"为什么"——为什么我们不能直接用 LLM 回答所有问题？为什么微调（Fine-tuning）不够？RAG 相比其他方案有哪些独特优势？

### 原理

LLM 的局限性可以从多个维度分析：

**1. 知识时效性问题**。LLM 的知识来源于训练数据，训练完成后知识就"冻结"了。例如，一个 2023 年训练的模型不知道 2024 年发生的事件。要让模型获取新知识，要么重新训练（成本极高），要么通过 RAG 动态注入。

**2. 幻觉问题（Hallucination）**。LLM 本质上是概率生成模型，它会生成"看起来合理"的文本，但不保证事实正确。当模型对某个问题缺乏确切知识时，它不会说"我不知道"，而是会编造答案。RAG 通过提供明确的事实上下文，显著降低了幻觉率。

**3. 长尾知识缺失**。LLM 对高频知识掌握良好，但对低频、专业、私有的知识覆盖很差。比如某公司内部某款产品的某个配置项，模型几乎不可能知道。

**4. 不可溯源**。LLM 直接生成的答案无法追溯来源，用户无法验证答案的可靠性。RAG 的答案可以明确指向检索到的文档，实现可溯源。

**5. 微调的局限性**。一种替代方案是用私有数据微调模型。但微调存在几个问题：成本高（需要 GPU、数据标注）、更新慢（每次更新都要重新训练）、容易遗忘（可能损害模型原有能力）、不适合频繁变化的事实性知识（微调学的是"风格"而非"事实"）。

下面这张表对比了三种方案的差异：

| 方案 | 知识更新 | 成本 | 可溯源 | 私有知识 | 适合场景 |
|------|---------|------|--------|---------|---------|
| 直接用 LLM | 不可更新 | 低 | 否 | 不支持 | 通用对话 |
| 微调 LLM | 慢、成本高 | 高 | 否 | 部分支持 | 风格/领域适配 |
| RAG | 快、低成本 | 中 | 是 | 完全支持 | 知识密集型问答 |

**RAG 的核心价值**可以归纳为四点：
- **时效性**：知识库可随时更新，模型无需重训。
- **准确性**：基于检索到的事实生成，降低幻觉。
- **可溯源性**：答案可指向具体文档来源。
- **可控性**：通过管理知识库内容，控制模型能回答什么、不能回答什么。

### 例子

下面用一个对比实验直观展示 RAG 的价值。我们问一个 LLM："我们公司 2024 年第三季度的营收是多少？"——这是一个私有知识问题。

```python
from openai import OpenAI

client = OpenAI()

question = "我们公司 2024 年第三季度的营收是多少？"

# 方案 A：直接问 LLM（无 RAG）
response_a = client.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": question}]
)
print("【无 RAG】", response_a.choices[0].message.content)
# 输出：很抱歉，我无法获取贵公司 2024 年第三季度的营收数据...
#       （或者更糟：编造一个数字）

# 方案 B：用 RAG
# 假设我们已经从内部财报中检索到相关段落
retrieved_context = """
2024 年 Q3 财报摘要：
- 总营收：3.42 亿元，同比增长 18%
- 其中云服务营收 1.8 亿元，SaaS 营收 1.2 亿元
- 净利润 4500 万元
"""

prompt = f"""请根据以下资料回答问题。如果资料中没有答案，请说"资料中未提及"。

资料：
{retrieved_context}

问题：{question}
"""

response_b = client.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": prompt}]
)
print("【有 RAG】", response_b.choices[0].message.content)
# 输出：根据财报，贵公司 2024 年第三季度总营收为 3.42 亿元，同比增长 18%。
```

这个例子清晰地展示了：没有 RAG 时，模型要么拒绝回答，要么编造；有了 RAG，模型能基于真实数据给出准确、可溯源的答案。

### 总结

本讲的核心要点：

1. LLM 存在知识时效性、幻觉、长尾缺失、不可溯源等根本局限。
2. 微调不适合解决事实性知识问题，它更适合风格与领域适配。
3. RAG 的四大价值：时效性、准确性、可溯源性、可控性。
4. RAG 不是 LLM 的替代，而是 LLM 的"外挂知识库"，二者互补。

**常见注意事项**：RAG 并非银弹。对于需要深度推理、多步计算的任务，单纯 RAG 可能不够，需要结合 Agent、思维链等技术。同时，RAG 的效果高度依赖知识库的质量——"垃圾进，垃圾出"。

## 第 3 讲：RAG 整体架构——端到端流程概览

### 概念

一个完整的 RAG 系统由两大阶段、五个核心环节构成。两大阶段是**索引阶段（Indexing）**和**查询阶段（Querying）**；五个核心环节是：文档加载、分块、Embedding、检索、生成。本讲给出 RAG 的全局架构图，为后续每一讲的深入学习建立地图。

### 原理

RAG 的端到端流程如下：

```
┌──────────────────────── 索引阶段（离线） ────────────────────────┐
│                                                                  │
│  原始文档 → 文档加载 → 文本分块 → Embedding → 存入向量数据库      │
│  (PDF/HTML/...)  (Loader)  (Splitter)  (Embedder)  (VectorStore) │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────────── 查询阶段（在线） ────────────────────────┐
│                                                                  │
│  用户问题 → Query Embedding → 向量检索 → 上下文组装 → LLM 生成     │
│             (Embedder)        (Retriever) (Prompt)    (Generator) │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

**索引阶段**（离线，一次性或定期执行）：
1. **文档加载**：从 PDF、Word、HTML、数据库等来源读取原始文档，提取纯文本。
2. **文本分块**：将长文档切分为语义连贯的小片段（chunk），通常几百字一段。
3. **Embedding**：用 Embedding 模型将每个 chunk 编码为高维向量。
4. **存储**：将向量及原始文本存入向量数据库，建立索引。

**查询阶段**（在线，每次用户提问时执行）：
1. **Query Embedding**：用同一个 Embedding 模型将用户问题编码为向量。
2. **检索**：在向量数据库中找出与问题向量最相似的 Top-K 个 chunk。
3. **上下文组装**：将检索到的 chunk 拼接成上下文，与问题一起构造 Prompt。
4. **生成**：LLM 基于 Prompt 生成最终答案。

这个架构的关键设计在于：**索引阶段和查询阶段使用同一个 Embedding 模型**，确保问题和文档被映射到同一个语义空间，从而可以通过向量相似度进行匹配。这也是为什么 Embedding 模型的选择对 RAG 效果至关重要。

### 例子

下面用 LangChain 实现一个完整的端到端 RAG 流程，覆盖所有五个环节：

```python
from langchain.document_loaders import PyPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.embeddings import OpenAIEmbeddings
from langchain.vectorstores import FAISS
from langchain.llms import OpenAI
from langchain.chains import RetrievalQA
from langchain.prompts import PromptTemplate

# ========== 索引阶段 ==========

# 1. 文档加载
loader = PyPDFLoader("company_handbook.pdf")
documents = loader.load()
print(f"加载了 {len(documents)} 页文档")

# 2. 文本分块
splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,        # 每块最大 500 字符
    chunk_overlap=50,      # 块之间重叠 50 字符
    separators=["\n\n", "\n", "。", "，", " "]  # 中文友好的分隔符
)
chunks = splitter.split_documents(documents)
print(f"分成了 {len(chunks)} 个 chunk")

# 3 & 4. Embedding + 存储到向量数据库
embeddings = OpenAIEmbeddings()
vectorstore = FAISS.from_documents(chunks, embeddings)
print("向量索引构建完成")

# ========== 查询阶段 ==========

# 创建检索器
retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

# 自定义 Prompt 模板
prompt_template = """
你是一个公司制度问答助手。请根据以下资料回答问题。
如果资料中没有相关信息，请回答"根据现有资料无法回答该问题"。

资料：
{context}

问题：{question}

回答：
"""
PROMPT = PromptTemplate(template=prompt_template, input_variables=["context", "question"])

# 创建 RAG 链
qa_chain = RetrievalQA.from_chain_type(
    llm=OpenAI(temperature=0),
    chain_type="stuff",
    retriever=retriever,
    chain_type_kwargs={"prompt": PROMPT},
    return_source_documents=True  # 返回来源文档，便于溯源
)

# 提问
result = qa_chain({"query": "公司的年假政策是怎样的？"})
print("答案：", result["result"])
print("\n来源文档：")
for i, doc in enumerate(result["source_documents"]):
    print(f"  [{i+1}] {doc.page_content[:100]}... (来源: {doc.metadata.get('source', 'unknown')})")
```

运行后，你会看到模型基于检索到的公司手册片段，准确回答了年假政策，并附上了来源页码。

### 总结

本讲的核心要点：

1. RAG 分为**索引阶段**（离线）和**查询阶段**（在线）两大阶段。
2. 五个核心环节：文档加载 → 分块 → Embedding → 检索 → 生成。
3. 索引与查询必须使用**同一个 Embedding 模型**，保证语义空间一致。
4. `return_source_documents=True` 可实现答案溯源，这是 RAG 的重要优势。

**常见注意事项**：
- 索引阶段是"一次性投入"，但知识库更新时需要重新索引（或增量索引）。
- 查询阶段的延迟主要来自检索和 LLM 生成两步，工程上需要分别优化。
- 本讲展示的是最基础的"Naive RAG"，后续章节会逐步引入更高级的技术。

# 第二章：文档处理与索引

索引阶段是 RAG 系统的地基。知识库的质量直接决定了检索的质量，而检索的质量又直接决定了最终答案的质量。本章深入讲解从原始文档到可检索向量的完整链路，涵盖文档加载、文本分块、Embedding 模型和向量数据库四个核心环节。这四个环节的每一个都存在大量工程权衡，理解它们是构建高质量 RAG 系统的前提。

---

## 第 4 讲：文档加载与解析——从原始数据到文本

### 概念

**文档加载（Document Loading）** 是 RAG 索引流程的第一步，负责将各种格式的原始文件（PDF、Word、HTML、Markdown、Excel、数据库等）转换为统一的文本结构。这一步看似简单，实则是 RAG 工程中最容易被低估、也最容易出问题的环节。一个解析错误的 PDF 可能导致整段关键信息丢失，使后续检索完全失效。

### 原理

文档加载的核心挑战在于**异构格式的统一处理**。不同格式的文档有不同的内部结构：

- **PDF**：本质是页面描述语言，文本按视觉位置排列，没有逻辑段落概念。表格、图片、多栏布局的解析尤其困难。
- **HTML**：包含大量标签噪声，需要提取正文、去除导航栏和广告。
- **Word/DOCX**：有较好的结构（段落、标题、表格），但样式信息可能干扰文本提取。
- **Markdown**：结构清晰，但需要正确处理代码块、链接、图片引用。
- **Excel/CSV**：是结构化表格，需要决定是按行还是按单元格组织文本。

一个优秀的文档加载器需要解决三个问题：
1. **文本提取**：从二进制或标记格式中提取纯文本。
2. **元数据保留**：保留页码、标题层级、来源文件等元信息，用于后续溯源。
3. **结构感知**：识别标题、段落、表格、列表等逻辑结构，避免把不相关的内容拼在一起。

对于复杂文档（尤其是包含表格、公式、扫描件的 PDF），简单的文本提取往往不够，需要借助 OCR、布局分析模型（如 LayoutLM、Unstructured.io）来获得高质量结果。

## 第 5 讲：文本分块策略——Chunking 的方法与权衡

### 概念

**文本分块（Text Chunking / Splitting）** 是将长文档切分为若干短片段的过程。这是 RAG 中影响检索质量最关键的环节之一。分块的大小、方式、重叠度，直接决定了检索能否精准命中相关内容。一个糟糕的分块策略，可能把一个完整的概念切成两半，导致检索时两半都不够相关。

### 原理

为什么需要分块？有两个根本原因：

**第一，Embedding 模型有输入长度限制**。大多数 Embedding 模型（如 text-embedding-ada-002）最大输入为 8191 个 token。超出部分会被截断，导致信息丢失。

**第二，检索精度与片段粒度强相关**。如果片段太长，一个片段可能包含多个主题，检索时虽然命中了，但大量无关内容会稀释信号，并浪费 LLM 的上下文窗口。如果片段太短，又可能丢失上下文，导致片段语义不完整。理想的片段应该"语义自足"——单独拿出来也能理解。

常见的分块策略有以下几种：

**1. 固定长度分块（Fixed-size Chunking）**：按固定字符数切分。简单粗暴，但可能切断句子和段落。

**2. 递归字符分块（Recursive Character Splitting）**：按优先级依次尝试不同的分隔符（如 `\n\n` → `\n` → `。` → 空格），尽量在自然边界处切分。这是最常用的策略。

**3. 语义分块（Semantic Chunking）**：用 Embedding 计算相邻句子的语义相似度，在语义"断点"处切分。更智能但计算成本高。

**4. 文档结构分块（Document Structure-based Chunking）**：按文档的标题层级（H1/H2/H3）切分，保留结构信息。适合 Markdown、HTML。

**5. 父子分块（Parent-Child Chunking）**：检索时用小块（精准），但返回给 LLM 时用大块（上下文完整）。这是高级策略，后续章节会详述。

分块的两个关键参数：
- **chunk_size**：每块的最大长度。常见值 300-1000 字符。
- **chunk_overlap**：相邻块之间的重叠长度。常见值 50-200 字符。重叠的作用是避免在边界处丢失上下文。

### 例子

下面对比展示不同分块策略的效果：

```python
from langchain.text_splitter import (
    RecursiveCharacterTextSplitter,
    CharacterTextSplitter,
    MarkdownHeaderTextSplitter,
    TokenTextSplitter
)

sample_text = """
# 第一章 公司概述

本公司成立于 2015 年，总部位于北京。
公司主营业务包括云计算和人工智能。

## 1.1 组织架构

公司设有技术部、产品部、市场部。
技术部下设前端组、后端组、算法组。

## 1.2 发展历程

2015 年公司成立。
2018 年完成 A 轮融资。
2021 年在科创板上市。
"""

# 策略 1：固定长度分块（不推荐，仅作对比）
fixed_splitter = CharacterTextSplitter(
    chunk_size=50,
    chunk_overlap=0,
    separator=" "
)
fixed_chunks = fixed_splitter.split_text(sample_text)
print("=== 固定长度分块 ===")
for i, c in enumerate(fixed_chunks[:3]):
    print(f"[{i}] {c}")

# 策略 2：递归字符分块（推荐，最常用）
recursive_splitter = RecursiveCharacterTextSplitter(
    chunk_size=100,
    chunk_overlap=20,
    separators=["\n\n", "\n", "。", "，", " ", ""]
)
recursive_chunks = recursive_splitter.split_text(sample_text)
print("\n=== 递归字符分块 ===")
for i, c in enumerate(recursive_chunks[:3]):
    print(f"[{i}] {c}")

# 策略 3：按 Markdown 标题结构分块（保留层级）
md_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[
        ("#", "Chapter"),
        ("##", "Section"),
    ]
)
md_chunks = md_splitter.split_text(sample_text)
print("\n=== Markdown 结构分块 ===")
for doc in md_chunks:
    print(f"[{doc.metadata}] {doc.page_content.strip()}")
```

**语义分块**（高级策略）示例：

```python

from langchain.embeddings import OpenAIEmbeddings

    OpenAIEmbeddings(),
    breakpoint_threshold_type="percentile",  # 用百分位数确定断点
    breakpoint_threshold_amount=95           # 相似度差异超过 95 分位时切分
)
semantic_chunks = semantic_splitter.split_text(sample_text)
print(f"语义分块得到 {len(semantic_chunks)} 个片段")
```

### 总结

本讲的核心要点：

1. 分块是 RAG 中影响检索质量的关键环节，目标是让每个片段"语义自足"。
2. **递归字符分块**是最常用的策略，兼顾简单与效果。
3. `chunk_size` 通常 300-1000 字符，`chunk_overlap` 通常 50-200 字符。
4. 高级策略包括语义分块、结构分块、父子分块，适用于不同场景。

**常见注意事项**：
- 分块大小需要根据具体文档和查询类型调优，没有"万能参数"。
- 中文分块要注意使用中文分隔符（`。`、`！`、`？`），否则可能在词中间切断。
- 表格、代码块不应被切断，需要特殊处理（如将整个表格作为一个 chunk）。

## 第 6 讲：词向量与 Embedding 模型——原理与选择

### 概念

**Embedding（词向量/嵌入）** 是将文本映射为固定维度的实数向量的过程。Embedding 模型是 RAG 系统的"语义引擎"——它决定了文档和查询如何被表示、如何被比较。选择合适的 Embedding 模型，是 RAG 效果的决定性因素之一。

### 原理

Embedding 的核心思想是**分布式语义假设**：语义相近的文本，其向量表示在空间中也相近。这个假设源于语言学中的"上下文相似则语义相似"原则。

Embedding 模型的发展经历了几个阶段：

**1. 词向量时代（Word2Vec / GloVe, 2013-2015）**：将每个词映射为一个固定向量，通过上下文窗口学习。缺点是无法处理一词多义，也无法表示整句语义。

**2. 上下文向量时代（BERT / Sentence-BERT, 2018-2020）**：基于 Transformer，能根据上下文生成动态向量。Sentence-BERT 专门优化了句子级别的向量表示，是早期 RAG 的主力。

**3. 指令化 Embedding 时代（BGE / E5 / GTE, 2022-至今）**：引入"指令"机制，针对不同任务（查询、文档）生成不同向量，显著提升了检索效果。例如 BGE 模型对查询会加上 "Represent this sentence for searching relevant passages:" 前缀。

Embedding 向量的相似度通常用**余弦相似度**衡量：

```
similarity(A, B) = (A · B) / (|A| × |B|)
```

值域为 [-1, 1]，越接近 1 表示越相似。

选择 Embedding 模型时需要考虑以下因素：
- **语言支持**：中文、英文或多语言。
- **维度**：常见 768、1024、1536 维。维度越高表达力越强，但存储和计算成本也越高。
- **最大输入长度**：通常 512 token，部分模型支持 8192 token。
- **性能**：参考 MTEB（Massive Text Embedding Benchmark）排行榜。
- **部署方式**：API（如 OpenAI）还是本地开源模型。

### 例子

下面展示使用不同 Embedding 模型的方法，以及如何对比它们的语义相似度：


### 总结

本讲的核心要点：

1. Embedding 将文本映射为向量，使语义相似度可计算。
2. 现代 Embedding 模型（BGE/E5）引入指令机制，针对查询和文档分别优化。
3. 选择模型需考虑语言、维度、长度、性能、部署方式。
4. 中文场景推荐 BGE 系列，通用场景推荐 OpenAI 或 BGE-M3。

**常见注意事项**：
- **索引和查询必须用同一个 Embedding 模型**，否则向量空间不一致。
- Embedding 模型升级后，整个知识库需要**重新向量化**。
- 不要盲目追求高维度，768 维在多数场景已足够，且更省存储。

## 第 7 讲：向量数据库——存储、索引与检索

### 概念

**向量数据库（Vector Database）** 是专门用于存储、索引和检索高维向量的数据库系统。它是 RAG 系统的"记忆中枢"——所有文档向量都存放在这里，每次查询都要在这里进行相似度搜索。向量数据库的性能、扩展性和功能丰富度，直接决定了 RAG 系统的响应速度和可扩展规模。

### 原理

向量数据库的核心技术是**近似最近邻搜索（Approximate Nearest Neighbor, ANN）**。对于精确的最近邻搜索，需要计算查询向量与库中所有向量的距离，复杂度为 O(N)，当 N 达到百万、亿级时完全不可行。ANN 通过建立索引结构，在精度和速度之间做权衡，实现亚秒级检索。

主流的 ANN 索引算法有三种：

**1. HNSW（Hierarchical Navigable Small World，分层可导航小世界图）**：
- 构建多层图结构，上层稀疏用于快速定位，下层密集用于精确搜索。
- 查询时从顶层开始逐层下沉，类似"跳表"。
- 优点：查询速度快、召回率高。缺点：内存占用大，构建慢。
- 代表：FAISS（HNSW 模式）、Milvus、Qdrant。

**2. IVF（Inverted File Index，倒排文件索引）**：
- 先用 K-means 将向量空间聚为 K 个簇，查询时只搜索最近的 nprobe 个簇。
- 优点：内存效率高。缺点：需要训练聚类中心，精度依赖 nprobe 参数。
- 常与 PQ（Product Quantization）压缩结合，形成 IVF-PQ 索引。

**3. LSH（Locality-Sensitive Hashing，局部敏感哈希）**：
- 通过哈希函数将相近向量映射到同一桶。
- 优点：简单。缺点：召回率较低，实际使用较少。

除了索引算法，向量数据库还需要支持：
- **元数据过滤**：在向量检索的同时，按元数据（如时间、来源、标签）过滤。
- **混合检索**：同时支持向量检索和关键词检索。
- **增删改**：动态添加、删除、更新向量。
- **持久化与分布式**：数据落盘、水平扩展。

主流向量数据库对比：

| 数据库 | 类型 | 特点 | 适合场景 |
|--------|------|------|---------|
| FAISS | 库（非服务） | 极快，单机，无持久化 | 原型、小规模 |
| Chroma | 嵌入式 | 轻量，Python 友好 | 原型、中小规模 |
| Milvus | 分布式 | 功能全，可扩展到亿级 | 生产、大规模 |
| Qdrant | 服务化 | Rust 编写，支持丰富过滤 | 生产、中等规模 |
| Pinecone | 云服务 | 全托管，免运维 | 快速上线、不想运维 |
| Weaviate | 服务化 | 内置混合检索、模块化 | 生产、需要混合检索 |
| pgvector | PostgreSQL 扩展 | 复用现有 PG 生态 | 已有 PG 基础设施 |

### 例子

下面展示使用 Chroma（轻量）和 Milvus（生产级）的完整示例：

```python
# from langchain.vectorstores import Milvus
# milvus_store = Milvus.from_documents(
#     docs, embeddings,

#     collection_name="company_kb"
# )

# ===== 增量更新 =====
new_doc = Document(page_content="2024 年新增育儿假 10 天。", 
                   metadata={"source": "update.pdf", "page": 1, "category": "hr"})
vectorstore.add_documents([new_doc])  # 增量添加

# 删除（通过 ID）
vectorstore.delete_collection()  # 删除整个集合
```

### 总结

本讲的核心要点：

1. 向量数据库使用 ANN 算法（HNSW/IVF/LSH）实现快速近似检索。
2. 主流选择：开发用 Chroma/FAISS，生产用 Milvus/Qdrant/Pinecone。
3. 元数据过滤是重要功能，可实现"在某类文档中检索"。
4. 增删改能力决定了知识库能否动态更新。

**常见注意事项**：
- FAISS 是库不是服务，没有持久化和并发管理，不适合多进程写入。
- 向量数据库的"距离"定义不同：余弦距离、L2 距离、内积，使用时要确认。
- 大规模场景下，索引参数（如 HNSW 的 `efConstruction`、`efSearch`）需要调优。

# 第三章：检索核心

检索是 RAG 的心脏。前面两章解决了"如何把知识存起来"的问题，本章解决"如何把相关知识找出来"的问题。一个 RAG 系统的上限由检索质量决定——如果检索不到正确的文档，再强的 LLM 也无法生成正确的答案。本章从基础的相似度检索讲起，逐步深入到混合检索、重排序和查询变换，这些技术共同构成了现代 RAG 系统的检索引擎。

## 第 8 讲：相似度检索——余弦、点积与欧氏距离

### 概念

**相似度检索**是 RAG 最基础的检索方式：将用户查询编码为向量，然后在向量数据库中找出与之"最相似"的 Top-K 个文档向量。这里的关键问题是：如何定义"相似"？本讲深入讲解三种主流的向量相似度度量方式，以及它们各自的适用场景。

### 原理

向量相似度的度量方式主要有三种，它们从不同角度衡量两个向量的"接近程度"：

**1. 余弦相似度（Cosine Similarity）**

衡量两个向量的方向一致性，忽略长度：

```
cos(A, B) = (A · B) / (|A| × |B|)
```

值域 [-1, 1]，1 表示方向完全一致，0 表示正交（无关），-1 表示方向相反。余弦相似度只关注向量的"方向"，不关注"长度"，因此对文本长度的差异不敏感。这是 NLP 中最常用的相似度度量，因为 Embedding 向量的长度往往没有明确的语义含义。

**2. 点积相似度（Dot Product / Inner Product）**

```
dot(A, B) = A · B = Σ(ai × bi)
```

点积同时考虑方向和长度。当所有向量都经过 L2 归一化（长度为 1）时，点积等价于余弦相似度。某些 Embedding 模型（如 OpenAI 的）输出的向量已经归一化，此时点积和余弦等价，但点积计算更快。

**3. 欧氏距离（L2 Distance / Euclidean Distance）**

```
L2(A, B) = √(Σ(ai - bi)²)
```

衡量两个向量在空间中的直线距离。值越小越相似。欧氏距离同时考虑方向和长度，对向量的绝对位置敏感。

**三者的关系与选择**：

| 度量方式 | 值域 | 是否考虑长度 | 归一化后等价于 | 典型场景 |
|---------|------|------------|--------------|---------|
| 余弦相似度 | [-1, 1] | 否 | — | 通用文本检索 |
| 点积 | (-∞, +∞) | 是 | 余弦相似度 | 已归一化向量，追求速度 |
| 欧氏距离 | [0, +∞) | 是 | √(2-2cos) | 图像、需要绝对位置 |

**关键原则**：相似度度量方式必须与 Embedding 模型的训练目标一致。例如，BGE 模型训练时用余弦相似度，检索时也应使用余弦相似度。用错度量方式会导致检索效果显著下降。

### 例子

下面用代码对比三种度量方式的效果：

```python
import numpy as np

# 三个示例向量（模拟 Embedding 输出）
query = np.array([0.8, 0.6, 0.0])        # 查询
doc1 = np.array([0.9, 0.5, 0.1])         # 相关文档
doc2 = np.array([0.1, 0.1, 0.9])         # 不相关文档
doc3 = np.array([4.0, 3.0, 0.0])         # 相关但长度很大

def cosine_similarity(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

def dot_product(a, b):
    return np.dot(a, b)

def euclidean_distance(a, b):
    return np.linalg.norm(a - b)

print("=== 三种度量方式对比 ===")
print(f"{'文档':<8} {'余弦相似度':<14} {'点积':<10} {'欧氏距离':<10}")
print("-" * 45)
for name, vec in [("doc1(相关)", doc1), ("doc2(无关)", doc2), ("doc3(相关但长)", doc3)]:
    cos = cosine_similarity(query, vec)
    dot = dot_product(query, vec)
    l2 = euclidean_distance(query, vec)
    print(f"{name:<12} {cos:<14.4f} {dot:<10.4f} {l2:<10.4f}")

# 输出分析：
# - 余弦相似度：doc1 和 doc3 都很相似（方向一致），doc2 不相似
# - 点积：doc3 分数最高（因为长度大），可能误导排序
# - 欧氏距离：doc3 距离最大（因为长度差异），也可能误导
```

在 LangChain 中使用不同度量方式：

```python
from langchain.vectorstores import FAISS
from langchain.embeddings import OpenAIEmbeddings

embeddings = OpenAIEmbeddings()

# FAISS 默认使用 L2 距离
store_l2 = FAISS.from_texts(["文档1", "文档2"], embeddings, 
                             distance_strategy="COSINE")  # 可切换

# 在实际检索中指定
results = store_l2.similarity_search_with_relevance_scores(
    "查询内容", k=3
)
# relevance_scores 使用余弦相似度，值域 [0, 1]，越大越相关
for doc, score in results:
    print(f"[{score:.4f}] {doc.page_content}")
```

### 总结

本讲的核心要点：

1. 三种主流度量：余弦相似度（看方向）、点积（看方向+长度）、欧氏距离（看绝对位置）。
2. **余弦相似度**是文本检索的默认选择，对长度不敏感。
3. 已归一化的向量，点积等价于余弦但更快。
4. 度量方式必须与 Embedding 模型训练时一致。

**常见注意事项**：
- 不同向量数据库默认的度量方式不同，迁移时要注意切换。
- "距离"和"相似度"方向相反：距离越小越相似，相似度越大越相似。
- 检索结果排序时，确认是按距离升序还是相似度降序。

## 第 9 讲：混合检索——稠密 + 稀疏检索

### 概念

**混合检索（Hybrid Retrieval）** 是将**稠密检索（Dense Retrieval，即向量检索）** 和**稀疏检索（Sparse Retrieval，即关键词检索）** 结合起来的检索策略。纯向量检索擅长语义匹配但可能遗漏关键词，纯关键词检索擅长精确匹配但不理解语义。混合检索取两者之长，是目前生产级 RAG 系统的标配。

### 原理

先理解两种检索各自的优缺点：

**稠密检索（向量检索）**：
- 原理：将查询和文档都编码为稠密向量，用向量相似度匹配。
- 优点：理解语义，能匹配"意思相近但用词不同"的内容。例如查询"如何请假"能匹配到"休假申请流程"。
- 缺点：对专有名词、型号、代码等精确字符串不敏感。例如查询"iPhone 15 Pro Max 256GB"可能匹配到"iPhone 14"。
- 适合：自然语言问答、概念性查询。

**稀疏检索（关键词检索）**：
- 原理：基于词频统计（如 TF-IDF、BM25），匹配包含查询关键词的文档。
- 优点：对精确字符串、专有名词、代码标识符高度敏感。
- 缺点：不理解语义，"请假"匹配不到"休假"。
- 适合：精确查找、专业术语查询。

**混合检索的流程**：
1. 分别用稠密检索和稀疏检索各取 Top-K 结果。
2. 对两路结果用**倒数排名融合（Reciprocal Rank Fusion, RRF）** 或加权分数融合。
3. 输出融合后的 Top-K 结果。

**RRF 融合公式**：

```
RRF_score(d) = Σ 1 / (k + rank_i(d))
```

其中 `rank_i(d)` 是文档 d 在第 i 路检索中的排名，k 通常取 60。RRF 的优点是不需要归一化两路的分数（因为向量相似度和 BM25 分数量纲不同），只依赖排名，鲁棒性强。

### 例子

下面用 LangChain 实现一个完整的混合检索系统：

```python
from langchain.retrievers import BM25Retriever, EnsembleRetriever
from langchain.vectorstores import FAISS
from langchain.embeddings import OpenAIEmbeddings
from langchain.schema import Document

# 准备文档（包含专有名词和语义内容）
docs = [
    Document(page_content="iPhone 15 Pro Max 256GB 钛原色售价 9999 元"),
    Document(page_content="苹果手机旗舰款支持 USB-C 接口和钛金属边框"),
    Document(page_content="休假申请需要在 OA 系统提交，提前 3 天审批"),
    Document(page_content="年假、病假、事假均通过人力资源系统办理"),
    Document(page_content="Python 3.12 引入了类型参数语法（PEP 695）"),
    Document(page_content="Python 新版本改进了错误提示信息"),
]

# 1. 稀疏检索：BM25
bm25_retriever = BM25Retriever.from_documents(docs)
bm25_retriever.k = 3

# 2. 稠密检索：向量
embeddings = OpenAIEmbeddings()
faiss_store = FAISS.from_documents(docs, embeddings)
faiss_retriever = faiss_store.as_retriever(search_kwargs={"k": 3})

# 3. 混合检索：集成两路
ensemble_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, faiss_retriever],
    weights=[0.5, 0.5]  # BM25 和向量各占 50%
)

# 测试不同类型的查询
print("=== 查询 1：精确型号（适合 BM25） ===")
query1 = "iPhone 15 Pro Max 256GB"
print("BM25:", [d.page_content[:30] for d in bm25_retriever.get_relevant_documents(query1)])
print("向量:", [d.page_content[:30] for d in faiss_retriever.get_relevant_documents(query1)])
print("混合:", [d.page_content[:30] for d in ensemble_retriever.get_relevant_documents(query1)])

print("\n=== 查询 2：语义查询（适合向量） ===")
query2 = "怎么请假"
print("BM25:", [d.page_content[:30] for d in bm25_retriever.get_relevant_documents(query2)])
print("向量:", [d.page_content[:30] for d in faiss_retriever.get_relevant_documents(query2)])
print("混合:", [d.page_content[:30] for d in ensemble_retriever.get_relevant_documents(query2)])
```

**使用 BGE-M3 实现原生混合检索**（BGE-M3 同时输出稠密和稀疏向量）：

```python
# BGE-M3 模型原生支持稠密 + 稀疏 + 多向量检索
from FlagEmbedding import BGEM3FlagModel

model = BGEM3FlagModel('BAAI/bge-m3', use_fp16=True)

sentences = ["如何申请年假", "休假申请流程"]
output = model.encode(sentences, return_dense=True, return_sparse=True, return_colbert_vecs=True)

# 稠密相似度
dense_sim = output['dense_vecs'][0] @ output['dense_vecs'][1]
# 稀疏匹配（BM25 风格的词权重）
sparse_scores = model.compute_lexical_matching_score(
    sentences[0], sentences[1], output['lexical_weights']
)
```

### 总结

本讲的核心要点：

1. 稠密检索擅长语义匹配，稀疏检索擅长精确匹配，二者互补。
2. 混合检索 = 稠密 + 稀疏 + 融合（通常用 RRF）。
3. 融合权重需要根据场景调优，关键词敏感场景提高 BM25 权重。
4. BGE-M3 等新模型原生支持混合检索，简化了工程实现。

**常见注意事项**：
- BM25 对中文需要先分词（如 jieba），否则效果很差。
- 两路检索的 Top-K 可以不同，通常向量路取多一些。
- 融合权重不是固定的，建议用评估集调优。

## 第 10 讲：检索优化——重排序与 Cross-Encoder

### 概念

**重排序（Re-ranking）** 是在初步检索（召回）之后，对候选文档进行二次精排的技术。初步检索（向量检索或 BM25）追求速度，从海量文档中快速召回 Top-N（如 50 个）候选；重排序追求精度，用更强大但更慢的模型对这 50 个候选重新打分，选出最相关的 Top-K（如 5 个）喂给 LLM。这种"先粗排、再精排"的两阶段架构，是现代检索系统的标准范式。

### 原理

为什么需要重排序？核心原因在于**Embedding 模型和 Cross-Encoder 模型的能力差异**。

**Bi-Encoder（双编码器，即 Embedding 模型）**：
- 查询和文档分别独立编码为向量，再用向量相似度匹配。
- 优点：文档可以预计算向量，查询时只需计算查询向量 + 向量检索，极快。
- 缺点：查询和文档没有交互，模型无法"看到"查询和文档的细节对应关系，精度有限。

**Cross-Encoder（交叉编码器）**：
- 将查询和文档拼接成一个序列 `[CLS] query [SEP] document [SEP]`，一起输入 Transformer，输出一个相关性分数。
- 优点：查询和文档在每一层都进行注意力交互，精度远高于 Bi-Encoder。
- 缺点：无法预计算，每次查询都要对每个候选文档重新计算，速度慢、成本高。

因此，工业界的标准做法是**两阶段检索**：
1. **召回阶段**：用 Bi-Encoder（向量检索）从百万文档中快速召回 Top-50。
2. **精排阶段**：用 Cross-Encoder 对这 50 个候选重新打分，选 Top-5。

这就像招聘：先用简历关键词筛出 50 份（召回），再由面试官深度评估选出 5 人（精排）。

主流的重排序模型：
- **Cohere Rerank**：商用 API，效果优秀。
- **BGE-Reranker**：开源，中英文都好。
- **Jina Reranker**：开源，支持长文档。
- **bge-reranker-v2-m3**：多语言，轻量。

### 例子

下面展示使用 BGE-Reranker 进行重排序的完整流程：

```python
from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import CrossEncoderRerankerModel
from langchain.vectorstores import FAISS
from langchain.embeddings import OpenAIEmbeddings
from langchain.cross_encoders import HuggingFaceCrossEncoder

# 1. 构建基础向量检索器（召回阶段）
embeddings = OpenAIEmbeddings()
vectorstore = FAISS.from_texts([
    "RAG 是检索增强生成技术",
    "RAG 由 Lewis 在 2020 年提出",
    "向量数据库用于存储 Embedding",
    "Transformer 是深度学习架构",
    "GPT 是生成式预训练模型",
], embeddings)

base_retriever = vectorstore.as_retriever(search_kwargs={"k": 10})  # 先召回 10 个

# 2. 加载 Cross-Encoder 重排序模型
cross_encoder = HuggingFaceCrossEncoder(model_name="BAAI/bge-reranker-base")
compressor = CrossEncoderRerankerModel(
    model=cross_encoder,
    top_n=3  # 精排后保留 3 个
)

# 3. 构建带重排序的检索器
reranking_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=base_retriever
)

# 4. 对比效果
query = "RAG 是什么时候提出的？"
print("=== 召回阶段（向量检索 Top-10） ===")
for doc in base_retriever.get_relevant_documents(query):
    print(f"  - {doc.page_content}")

print("\n=== 精排阶段（重排序 Top-3） ===")
for doc in reranking_retriever.get_relevant_documents(query):
    print(f"  - {doc.page_content}")
# 重排序后，"RAG 由 Lewis 在 2020 年提出" 应该排在最前
```

**使用 Cohere Rerank API**（商用，效果更好）：

```python
from langchain.retrievers.document_compressors import CohereRerank

compressor = CohereRerank(top_n=3, model="rerank-multilingual-v3.0")
reranking_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=base_retriever
)
```

**手动实现重排序**（更灵活的控制）：

```python
from sentence_transformers import CrossEncoder

# 加载模型
reranker = CrossEncoder('BAAI/bge-reranker-large')

def rerank_documents(query, documents, top_k=3):
    # 构造 (query, doc) 对
    pairs = [(query, doc.page_content) for doc in documents]
    # 计算相关性分数
    scores = reranker.predict(pairs)
    # 按分数排序
    ranked = sorted(zip(documents, scores), key=lambda x: x[1], reverse=True)
    return [doc for doc, score in ranked[:top_k]]

# 使用
candidates = base_retriever.get_relevant_documents(query)
top_docs = rerank_documents(query, candidates, top_k=3)
```

### 总结

本讲的核心要点：

1. 重排序采用"先粗排（Bi-Encoder 召回）、再精排（Cross-Encoder）"的两阶段架构。
2. Bi-Encoder 快但精度低，Cross-Encoder 精度高但慢，二者互补。
3. 主流重排序模型：Cohere Rerank（商用）、BGE-Reranker（开源）。
4. 典型配置：召回 Top-50，重排序选 Top-5。

**常见注意事项**：
- 重排序会增加延迟（通常 100-500ms），需要权衡延迟与精度。
- Cross-Encoder 的最大输入长度有限（通常 512 token），长文档需要截断。
- 重排序模型的语言要与文档语言匹配。

## 第 11 讲：查询变换——扩展、分解与重写

### 概念

**查询变换（Query Transformation）** 是在检索之前对用户原始查询进行改写、扩展或分解的技术。用户输入的查询往往存在表述不清、过于简短、包含多个子问题等情况，直接用于检索效果不佳。查询变换通过 LLM 对原始查询进行"预处理"，生成更适合检索的查询，从而显著提升检索质量。

### 原理

查询变换有多种策略，适用于不同场景：

**1. 查询重写（Query Rewriting）**

将用户的口语化、模糊的查询重写为更清晰、更符合检索需求的形式。例如用户问"那个东西怎么用"，重写为"产品 X 的使用说明"。LLM 可以根据对话历史推断"那个东西"指什么。

**2. 查询扩展（Query Expansion）**

为原始查询添加相关术语、同义词、上下文，扩大检索覆盖面。例如查询"Python 性能优化"扩展为"Python 性能优化 提速 加速 Cython Numba profiling"。这能召回更多相关文档。

**3. 查询分解（Query Decomposition）**

将复杂的多部分查询分解为多个子查询，分别检索后再合并。例如"比较 Python 和 Java 在 Web 开发中的优劣"分解为"Python Web 开发优势"、"Python Web 开发劣势"、"Java Web 开发优势"、"Java Web 开发劣势"四个子查询。

**4. 多查询生成（Multi-Query Generation）**

用 LLM 从不同角度生成多个查询变体，分别检索后合并去重。例如查询"如何学习机器学习"生成"机器学习入门路线"、"机器学习推荐书籍"、"机器学习在线课程"等变体。这能从多个语义角度召回文档。

**5. HyDE（Hypothetical Document Embeddings）**

让 LLM 先根据查询"假设"一个答案文档，再用这个假设文档去检索。原理是：假设答案的向量可能比简短查询的向量更接近真实答案文档的向量。例如查询"什么是 RAG"，LLM 先生成一段关于 RAG 的假设性解释，再用这段解释检索。

**6. 步退提示（Step-Back Prompting）**

让 LLM 将具体查询"退一步"抽象为更宏观的查询。例如"2024 年 Q3 营收"退步为"公司各季度财务数据"，先检索宏观背景，再结合具体问题。

### 例子

下面展示几种查询变换的实现：

```python
from langchain.retrievers import MultiQueryRetriever, SelfQueryRetriever
from langchain.chains import LLMChain
from langchain.llms import OpenAI
from langchain.prompts import PromptTemplate
from langchain.vectorstores import FAISS
from langchain.embeddings import OpenAIEmbeddings
import logging

# 准备知识库
docs = [
    "Python 是一种解释型高级编程语言",
    "Python 的 GIL 限制了多线程性能",
    "Java 是面向对象的编译型语言",
    "Java 的 JVM 实现了跨平台运行",
    "机器学习需要数学基础和编程能力",
    "深度学习是机器学习的子领域",
]
embeddings = OpenAIEmbeddings()
vectorstore = FAISS.from_texts(docs, embeddings)
llm = OpenAI(temperature=0)

# ===== 1. 多查询生成 =====
logging.basicConfig()
logging.getLogger("langchain.retrievers.multi_query").setLevel(logging.INFO)

multi_query_retriever = MultiQueryRetriever.from_llm(
    retriever=vectorstore.as_retriever(),
    llm=llm
)
# 会生成多个查询变体，分别检索后合并
results = multi_query_retriever.get_relevant_documents("Python 和 Java 的区别")
print("=== 多查询生成结果 ===")
for r in results:
    print(f"  - {r.page_content}")

# ===== 2. 查询重写 =====
rewrite_prompt = PromptTemplate.from_template("""
请将以下用户问题重写为更清晰、更适合检索的形式。只输出重写后的问题，不要解释。

原始问题：{question}
重写后的问题：
""")
rewrite_chain = LLMChain(llm=llm, prompt=rewrite_prompt)

original = "那个 Python 的多线程问题怎么解决"
rewritten = rewrite_chain.run(question=original)
print(f"\n=== 查询重写 ===")
print(f"原始: {original}")
print(f"重写: {rewritten.strip()}")

# ===== 3. 查询分解 =====
decompose_prompt = PromptTemplate.from_template("""
将以下复杂问题分解为多个简单的子问题，每行一个，不要编号。

复杂问题：{question}
子问题：
""")
decompose_chain = LLMChain(llm=llm, prompt=decompose_prompt)

complex_q = "比较 Python 和 Java 在性能和跨平台方面的差异"
sub_queries = decompose_chain.run(question=complex_q).strip().split("\n")
print(f"\n=== 查询分解 ===")
print(f"复杂问题: {complex_q}")
for i, sq in enumerate(sub_queries):
    print(f"  子问题 {i+1}: {sq.strip()}")
    # 对每个子问题分别检索
    sub_results = vectorstore.similarity_search(sq.strip(), k=2)
    for r in sub_results:
        print(f"    → {r.page_content}")

# ===== 4. HyDE =====
from langchain.retrievers import HypotheticalDocumentRetriever

hyde_retriever = HypotheticalDocumentRetriever.from_llm(
    llm=llm,
    base_retriever=vectorstore.as_retriever(),
    prompt_key="llm"
)
# HyDE 会先让 LLM 生成假设答案，再用假设答案检索
results = hyde_retriever.get_relevant_documents("什么是 GIL")
print(f"\n=== HyDE 检索 ===")
for r in results:
    print(f"  - {r.page_content}")
```

### 总结

本讲的核心要点：

1. 查询变换在检索前对用户查询进行"预处理"，提升检索质量。
2. 主要策略：重写、扩展、分解、多查询、HyDE、步退。
3. 多查询和 HyDE 是最常用的两种，效果稳定。
4. 查询分解适合复杂多部分问题，但会增加检索次数和延迟。

**常见注意事项**：
- 查询变换会增加一次 LLM 调用的延迟（通常 500ms-2s），需要权衡。
- 变换用的 LLM 可以用较小的模型（如 GPT-3.5），降低成本。
- 变换后的查询要记录日志，便于排查检索问题。

## 第 12 讲：Prompt 工程在 RAG 中的应用

### 概念

**Prompt 工程**在 RAG 中的核心任务是：设计合适的指令模板，引导 LLM 基于检索到的上下文生成准确、忠实、有用的答案。RAG 的 Prompt 与普通对话 Prompt 的最大区别在于，它必须包含检索到的上下文，并明确指示 LLM "基于上下文回答"而非"凭记忆回答"。一个设计良好的 RAG Prompt，能显著降低幻觉、提升答案准确率。

### 原理

RAG Prompt 的设计需要遵循几个核心原则：

**1. 明确角色与任务边界**

Prompt 应明确告诉 LLM 它的角色（如"知识库问答助手"）和任务边界（如"只基于提供的资料回答"）。这能减少 LLM 越界发挥、凭空编造的倾向。

**2. 上下文优先级**

将检索到的上下文放在 Prompt 的显眼位置（通常在问题之前），并明确标注"以下是参考资料"。LLM 对最近、最显眼的内容注意力更高。

**3. 忠实性约束**

明确指示 LLM："如果资料中没有相关信息，请回答'根据现有资料无法回答'"。这是防止幻觉的关键约束。没有这条指令，LLM 倾向于"编造"一个看似合理的答案。

**4. 结构化输出**

要求 LLM 以结构化方式输出（如分点、带引用），能提升答案的可读性和可溯源性。例如要求"每个观点后标注来源编号 [1][2]"。

**5. 引用与溯源**

指示 LLM 在答案中引用来源，如"根据[资料1]，年假为5天"。这不仅提升可信度，也方便用户验证。

一个标准的 RAG Prompt 模板通常包含以下部分：
```
[角色定义]
[行为约束/规则]
[参考资料]
{context}
[用户问题]
{question}
[输出格式要求]
```

### 例子

下面展示从基础到高级的 RAG Prompt 设计：

```python
from langchain.prompts import PromptTemplate, ChatPromptTemplate
from langchain.chains import RetrievalQA
from langchain.chat_models import ChatOpenAI
from langchain.vectorstores import FAISS
from langchain.embeddings import OpenAIEmbeddings

# 准备知识库
docs = [
    "公司年假政策：入职满一年享 5 天年假，满三年享 10 天，满五年享 15 天。",
    "年假申请需提前 7 天在 OA 系统提交，由直属主管审批。",
    "未休年假可在次年 Q1 末前折算为工资，按日薪的 300% 计算。",
]
vectorstore = FAISS.from_texts(docs, OpenAIEmbeddings())
retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

# ===== 1. 基础 Prompt =====
basic_prompt = PromptTemplate.from_template("""
根据以下资料回答问题。

资料：{context}

问题：{question}

回答：
""")

# ===== 2. 进阶 Prompt（加约束、防幻觉） =====
advanced_prompt = PromptTemplate.from_template("""
你是一个公司制度问答助手。请严格根据以下资料回答问题。

规则：
1. 只基于资料中的信息回答，不要编造。
2. 如果资料中没有相关信息，请回答"根据现有资料无法回答该问题"。
3. 回答时请标注信息来源，格式为[资料N]。

资料：
{context}

问题：{question}

回答：
""")

# ===== 3. 高级 Prompt（结构化输出 + 引用） =====
structured_prompt = ChatPromptTemplate.from_messages([
    ("system", """你是公司知识库问答助手。请基于提供的参考资料回答用户问题。

回答要求：
1. 忠实于资料：只使用资料中的信息，不编造。
2. 结构化输出：分点陈述，每点简明扼要。
3. 标注来源：每个事实后用 [资料N] 标注来源。
4. 诚实拒答：资料中无相关信息时，明确说明。
5. 语言简洁：避免冗余，直击要点。"""),
    ("human", """参考资料：
{context}

问题：{question}

请回答：""")
])

# 使用不同 Prompt 构建 RAG 链
llm = ChatOpenAI(temperature=0, model="gpt-4")

qa_basic = RetrievalQA.from_chain_type(
    llm=llm, chain_type="stuff",
    retriever=retriever,
    chain_type_kwargs={"prompt": basic_prompt}
)

qa_advanced = RetrievalQA.from_chain_type(
    llm=llm, chain_type="stuff",
    retriever=retriever,
    chain_type_kwargs={"prompt": advanced_prompt}
)

# 测试
question = "入职两年的员工有多少天年假？怎么申请？"
print("=== 基础 Prompt 答案 ===")
print(qa_basic.run(question))

print("\n=== 进阶 Prompt 答案 ===")
print(qa_advanced.run(question))
```

**处理"无法回答"的场景**：

```python
# 测试知识库中没有的问题
question_out = "公司食堂的菜单是什么？"
print("\n=== 测试超出知识库的问题 ===")
print(qa_advanced.run(question_out))
# 应该回答"根据现有资料无法回答该问题"
```

### 总结

本讲的核心要点：

1. RAG Prompt 的核心原则：明确角色、上下文优先、忠实约束、结构化输出、引用溯源。
2. **防幻觉指令**是 RAG Prompt 的灵魂——明确要求"无信息则拒答"。
3. 结构化输出和来源标注能提升答案的可读性和可信度。
4. System Prompt + Human Prompt 的对话格式比单条 Prompt 效果更好。

**常见注意事项**：
- `temperature=0` 让答案更确定、更忠实，适合知识问答场景。
- Prompt 不宜过长，否则会稀释关键指令的注意力。
- 不同 LLM 对同一 Prompt 的响应不同，需要针对性调优。

## 第 13 讲：上下文组装与压缩

### 概念

**上下文组装（Context Assembly）** 是将检索到的多个文档片段组织成最终输入 LLM 的上下文的过程。**上下文压缩（Context Compression）** 是在文档过多或过长时，对内容进行筛选、摘要或过滤，以适应 LLM 上下文窗口限制的技术。这两个环节决定了 LLM 能"看到"什么，直接影响生成质量。

### 原理

**上下文组装面临的核心挑战是 LLM 的上下文窗口有限**。即使是支持 128K token 的模型，过长的上下文也会导致"中间遗忘"（Lost in the Middle）现象——LLM 对上下文中间部分的信息利用率显著低于首尾部分。因此，不能简单地把所有检索结果堆砌进 Prompt。

**上下文组装的策略**：

**1. Stuff（直接拼接）**：将所有文档直接拼成一个字符串。最简单，但文档多时会超长。

**2. Map-Reduce（映射-归约）**：先对每个文档分别让 LLM 提取要点（Map），再合并所有要点生成最终答案（Reduce）。适合文档多、需要深度处理的场景。

**3. Refine（迭代精炼）**：依次处理每个文档，用前一个文档的中间答案 + 下一个文档生成更精炼的答案。适合需要逐步整合信息的场景。

**4. Map-Rerank（映射-排序）**：对每个文档分别生成答案并打分，选最高分的作为最终答案。适合多文档独立回答的场景。

**上下文压缩的策略**：

**1. 相关性过滤**：用 LLM 或 Embedding 过滤掉与查询无关的文档片段，只保留相关的。

**2. 摘要压缩**：用 LLM 对长文档生成摘要，用摘要替代原文。

**3. 抽取式压缩**：从文档中抽取与查询最相关的句子，丢弃无关部分。如 LLMLingua 等工具。

**4. 父子文档策略**：检索时用小块（精准命中），返回时用小块所属的大块（上下文完整），兼顾精度与上下文完整性。

### 例子

下面展示不同的上下文组装和压缩策略：

```python
from langchain.chains import RetrievalQA
from langchain.chains.combine_documents import (
    stuff, map_reduce, refine
)
from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import (
    LLMChainExtractor, LLMChainFilter, EmbeddingsFilter
)
from langchain.chat_models import ChatOpenAI
from langchain.vectorstores import FAISS
from langchain.embeddings import OpenAIEmbeddings
from langchain.text_splitter import RecursiveCharacterTextSplitter

# 准备较长的知识库
long_docs = [
    "公司年假政策详细说明：根据《员工手册》第三章第二节，年假天数与工龄挂钩。"
    "入职满一年享 5 天年假；满三年享 10 天年假；满五年享 15 天年假；"
    "满十年享 20 天年假。年假按自然年计算，不跨年累积。"
    "新员工入职当年按剩余月份折算年假天数。",
    
    "年假申请流程：员工需提前 7 个工作日在 OA 系统提交年假申请，"
    "填写请假起止时间、事由、工作交接安排。申请提交后由直属主管审批，"
    "主管需在 3 个工作日内审批完毕。超过 3 天的年假需部门总监二级审批。"
    "审批通过后，员工会收到系统通知和邮件确认。",
    
    "未休年假处理：当年未休完的年假可在次年 Q1 末前休完。"
    "Q1 末仍未休完的年假，公司将按日薪的 300% 折算为工资发放。"
    "但员工主动放弃的年假不享受折算补偿。离职时未休年假按日薪 100% 结算。",
]

# 分块
splitter = RecursiveCharacterTextSplitter(chunk_size=200, chunk_overlap=30)
chunks = splitter.create_documents(long_docs)
vectorstore = FAISS.from_documents(chunks, OpenAIEmbeddings())
retriever = vectorstore.as_retriever(search_kwargs={"k": 5})
llm = ChatOpenAI(temperature=0)

# ===== 1. Stuff 策略（直接拼接） =====
qa_stuff = RetrievalQA.from_chain_type(
    llm=llm, chain_type="stuff", retriever=retriever
)
print("=== Stuff 策略 ===")
print(qa_stuff.run("年假怎么折算？"))

# ===== 2. Map-Reduce 策略（适合大量文档） =====
qa_map_reduce = RetrievalQA.from_chain_type(
    llm=llm, chain_type="map_reduce", retriever=retriever
)
print("\n=== Map-Reduce 策略 ===")
print(qa_map_reduce.run("年假怎么折算？"))

# ===== 3. Refine 策略（迭代精炼） =====
qa_refine = RetrievalQA.from_chain_type(
    llm=llm, chain_type="refine", retriever=retriever
)
print("\n=== Refine 策略 ===")
print(qa_refine.run("年假怎么折算？"))

# ===== 4. 上下文压缩：LLM 提取相关部分 =====
compressor = LLMChainExtractor.from_llm(llm)
compression_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=retriever
)
print("\n=== LLM 压缩后的检索结果 ===")
query = "年假折算比例是多少？"
compressed_docs = compression_retriever.get_relevant_documents(query)
for doc in compressed_docs:
    print(f"  [压缩后] {doc.page_content}")

# ===== 5. Embedding 过滤（更快的压缩方式） =====
embeddings_filter = EmbeddingsFilter(
    embeddings=OpenAIEmbeddings(),
    similarity_threshold=0.5  # 只保留相似度 > 0.5 的文档
)
filter_retriever = ContextualCompressionRetriever(
    base_compressor=embeddings_filter,
    base_retriever=retriever
)
print("\n=== Embedding 过滤后的检索结果 ===")
filtered_docs = filter_retriever.get_relevant_documents(query)
for doc in filtered_docs:
    print(f"  [过滤后] {doc.page_content[:80]}...")

# ===== 6. 父子文档策略 =====
from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore

parent_splitter = RecursiveCharacterTextSplitter(chunk_size=1000)  # 大块
child_splitter = RecursiveCharacterTextSplitter(chunk_size=200)    # 小块
vectorstore = FAISS.from_texts([], OpenAIEmbeddings())
docstore = InMemoryStore()

parent_retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=docstore,
    child_splitter=child_splitter,
    parent_splitter=parent_splitter,
)
parent_retriever.add_documents([d for d in chunks])
# 检索时用小块匹配，返回大块（上下文完整）
print("\n=== 父子文档策略 ===")
parent_docs = parent_retriever.get_relevant_documents(query)
for doc in parent_docs:
    print(f"  [父文档] {doc.page_content[:100]}...")
```

### 总结

本讲的核心要点：

1. 上下文组装有四种策略：Stuff（直接拼）、Map-Reduce（分治）、Refine（迭代）、Map-Rerank（排序）。
2. 上下文压缩包括：LLM 提取、Embedding 过滤、摘要压缩、抽取式压缩。
3. **父子文档策略**是兼顾检索精度和上下文完整性的优秀方案。
4. 注意"中间遗忘"现象，重要信息放在上下文首尾。

**常见注意事项**：
- Stuff 策略文档多时会超长，需改用 Map-Reduce 或 Refine。
- LLM 压缩效果好但慢，Embedding 过滤快但精度低，按需选择。
- 父子文档策略需要额外的 docstore 存储父文档。

## 第 14 讲：生成质量评估与控制

### 概念

**生成质量评估**是衡量 RAG 系统输出答案准确性和可靠性的过程。**生成质量控制**是基于评估结果，通过各种技术手段降低幻觉、提升忠实度和相关性的实践。RAG 系统不是"构建完就结束"的，必须建立评估与监控机制，持续保证输出质量。没有评估的 RAG 系统就像没有仪表盘的汽车——你不知道它什么时候会出问题。

### 原理

RAG 生成质量主要从三个维度评估：

**1. 忠实度（Faithfulness / Groundedness）**

答案是否忠实于检索到的上下文？有没有编造上下文中不存在的信息？这是 RAG 最核心的质量指标。忠实度低的系统会产生"看似合理但实际错误"的幻觉答案，比直接说"不知道"更危险。

评估方法：将答案拆分为若干事实陈述，逐一检查每条事实是否能从上下文中推导出来。忠实度 = 可推导的事实数 / 总事实数。

**2. 答案相关性（Answer Relevance）**

答案是否真正回答了用户的问题？有没有答非所问、跑题？LLM 有时会被上下文带偏，回答了上下文中的内容但偏离了问题。

评估方法：让 LLM 根据答案反推可能的问题，计算反推问题与原始问题的相似度。相似度越高，说明答案越切题。

**3. 上下文相关性（Context Relevance）**

检索到的上下文是否与问题相关？有没有检索到大量无关内容？这反映的是检索质量，但会间接影响生成质量。

评估方法：让 LLM 判断每个检索片段与问题的相关性，计算相关片段占比。

**质量控制技术**：

- **置信度阈值**：检索分数低于阈值的文档不纳入上下文。
- **答案校验**：生成后用另一个 LLM 校验答案是否忠实于上下文。
- **自我反思**：让 LLM 评估自己的答案，不达标则重新生成。
- **多路生成 + 投票**：生成多个答案，选一致性最高的。

### 例子

下面展示如何用 LLM 自动评估 RAG 答案质量：


本讲的核心要点：

1. RAG 质量评估三大维度：忠实度（防幻觉）、答案相关性（防跑题）、上下文相关性（防噪声）。
2. 忠实度是 RAG 最核心的指标——答案必须忠实于检索上下文。
3. 质量控制技术：置信度阈值、答案校验、自我反思、多路投票。
4. 评估应自动化、批量化，纳入持续监控流程。

- 评估用的 LLM 应比生成用的更强（如用 GPT-4 评估 GPT-3.5 的输出）。
- 评估本身也有成本，建议对采样数据评估而非全量评估。
- 建立人工标注的"黄金集"作为评估基准，定期校准自动评估。

# 第五章：进阶架构

前面四章讲解的是"标准 RAG"——检索一次、生成一次的线性流程。但真实世界的问答场景远比这复杂：有时检索结果质量差需要修正，有时问题需要跨文档推理，有时需要多轮检索才能找到答案。本章介绍三种突破标准 RAG 局限的进阶架构：Self-RAG（自我反思与修正）、GraphRAG（知识图谱增强）、Agentic RAG（智能体化）。这些架构代表了 RAG 技术的前沿发展方向。

---

## 第 15 讲：Self-RAG 与 Corrective RAG

### 概念

**Self-RAG（Self-Reflective RAG）** 是一种引入"自我反思"机制的 RAG 架构，让 LLM 在检索和生成的各个阶段进行自我评估，判断是否需要检索、检索结果是否相关、生成答案是否忠实。**Corrective RAG（CRAG）** 则是一种"纠错"机制，当检索结果质量不佳时，自动触发修正策略（如重检索、网络搜索补充）。两者的共同思想是：RAG 不应是"一条路走到黑"的线性流程，而应具备动态调整和自我修正的能力。

### 原理

**标准 RAG 的问题**：无论检索结果好坏，都一股脑塞给 LLM 生成。如果检索结果完全不相关，LLM 要么硬编答案（幻觉），要么被无关内容干扰。

**Self-RAG 的反思机制**：

Self-RAG 通过训练特殊的"反思 token"实现自我评估，包含三种关键判断：

1. **Retrieve?（是否需要检索）**：对于简单问题（如"你好"）不需要检索，直接回答；对于知识性问题才触发检索。这避免了不必要的检索开销。

2. **IsRel?（检索结果是否相关）**：判断每个检索到的文档是否与问题相关，过滤掉无关文档。

3. **IsSup?（答案是否有支撑）**：判断生成的答案是否被检索到的文档支撑，即忠实度检查。

4. **IsUse?（答案是否有用）**：判断最终答案对用户是否有用，综合评估质量。

基于这些判断，Self-RAG 可以动态决定：跳过检索、过滤文档、重新生成、给出多个候选答案等。

**Corrective RAG（CRAG）的纠错机制**：

CRAG 引入"检索评估器"，对检索结果打分，分三档处理：

1. **Correct（正确，高分）**：检索结果相关，直接用于生成。
2. **Incorrect（错误，低分）**：检索结果不相关，丢弃检索结果，转而触发网络搜索补充信息。
3. **Ambiguous（模糊，中分）**：检索结果部分相关，对文档进行"知识精炼"（提取关键句子），再用于生成。

CRAG 的核心洞察是：当本地知识库检索失败时，不应硬撑，而应转向外部知识源（如网络搜索）兜底。

**Self-RAG vs CRAG 的区别**：
- Self-RAG 侧重"生成阶段的自我反思"，需要训练反思 token。
- CRAG 侧重"检索阶段的纠错"，用规则 + 知识精炼实现，更易工程化。

### 例子

下面用 LangGraph 实现一个 Corrective RAG 流程：

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict, List
from langchain.chat_models import ChatOpenAI
from langchain.prompts import PromptTemplate
from langchain.chains import LLMChain
from langchain.vectorstores import FAISS
from langchain.embeddings import OpenAIEmbeddings
from langchain.schema import Document

# 定义状态
class CRAGState(TypedDict):
    question: str
    documents: List[Document]
    web_documents: List[Document]
    generation: str
    retrieval_grade: str  # "yes" / "no"

# 准备知识库
docs = [
    Document(page_content="Python 是解释型语言"),
    Document(page_content="Java 是编译型语言"),
]
vectorstore = FAISS.from_documents(docs, OpenAIEmbeddings())
llm = ChatOpenAI(temperature=0)

# ===== 节点 1：检索 =====
def retrieve(state):
    question = state["question"]
    documents = vectorstore.similarity_search(question, k=3)
    return {"documents": documents, "question": question}

# ===== 节点 2：评估检索质量 =====
grade_prompt = PromptTemplate.from_template("""
你是一个检索结果评估器。请判断以下文档是否与问题相关。

问题：{question}
文档：{document}

只回答 "yes" 或 "no"。
""")
grade_chain = LLMChain(llm=llm, prompt=grade_prompt)

def grade_documents(state):
    question = state["question"]
    documents = state["documents"]
    filtered = []
    for doc in documents:
        grade = grade_chain.run(question=question, document=doc.page_content).strip().lower()
        if grade == "yes":
            filtered.append(doc)
    # 如果没有相关文档，标记为需要网络搜索
    retrieval_grade = "yes" if len(filtered) > 0 else "no"
    return {"documents": filtered, "question": question, "retrieval_grade": retrieval_grade}

# ===== 节点 3：网络搜索（兜底） =====
from langchain.tools import DuckDuckGoSearchRun
def web_search(state):
    question = state["question"]
    search = DuckDuckGoSearchRun()
    result = search.run(question)
    web_doc = Document(page_content=result, metadata={"source": "web"})
    return {"documents": [web_doc], "question": question}

# ===== 节点 4：生成答案 =====
generate_prompt = PromptTemplate.from_template("""
基于以下资料回答问题。如果资料不足，请说明。

资料：{context}
问题：{question}
答案：
""")
generate_chain = LLMChain(llm=llm, prompt=generate_prompt)

def generate(state):
    question = state["question"]
    documents = state["documents"]
    context = "\n".join([d.page_content for d in documents])
    generation = generate_chain.run(context=context, question=question)
    return {"generation": generation}

# ===== 路由函数 =====
def decide_to_generate(state):
    grade = state["retrieval_grade"]
    if grade == "yes":
        return "generate"
    else:
        return "web_search"

# ===== 构建 CRAG 工作流 =====
workflow = StateGraph(CRAGState)
workflow.add_node("retrieve", retrieve)
workflow.add_node("grade_documents", grade_documents)
workflow.add_node("web_search", web_search)
workflow.add_node("generate", generate)

workflow.set_entry_point("retrieve")
workflow.add_edge("retrieve", "grade_documents")
workflow.add_conditional_edges(
    "grade_documents",
    decide_to_generate,
    {"generate": "generate", "web_search": "web_search"}
)
workflow.add_edge("web_search", "generate")
workflow.add_edge("generate", END)

app = workflow.compile()

# 测试：知识库中有的问题
print("=== 测试 1：知识库内问题 ===")
result1 = app.invoke({"question": "Python 是什么语言？"})
print(result1["generation"])

# 测试：知识库中没有的问题（触发网络搜索）
print("\n=== 测试 2：知识库外问题（触发兜底） ===")
result2 = app.invoke({"question": "2024 年诺贝尔文学奖得主是谁？"})
print(result2["generation"])
```

### 总结

本讲的核心要点：

1. Self-RAG 通过反思 token 实现检索必要性、相关性、忠实度的自我评估。
2. CRAG 通过检索评估 + 网络搜索兜底，实现检索失败的自动纠错。
3. 两者都打破了"线性 RAG"的局限，引入了动态决策能力。
4. LangGraph 是实现这类有状态、可分支 RAG 流程的理想工具。

**常见注意事项**：
- Self-RAG 需要专门训练反思模型，工程成本高；CRAG 用规则实现，更易落地。
- 网络搜索兜底会增加延迟和不确定性，需要设置超时和结果过滤。
- 反思和纠错会增加 LLM 调用次数，成本和延迟会上升。

## 第 16 讲：GraphRAG——知识图谱增强

### 概念

**GraphRAG** 是将**知识图谱（Knowledge Graph）** 与 RAG 结合的架构。传统 RAG 基于向量检索，擅长"找相关片段"，但在处理需要跨文档推理、全局性总结、多跳关系的问题时力不从心。GraphRAG 通过构建知识图谱，显式表示实体和关系，让 RAG 具备"关系推理"和"全局视角"的能力。2024 年微软发布的 GraphRAG 论文，使这一架构成为业界热点。

### 原理

**传统 RAG 的局限**：

1. **局部视角**：向量检索只能找到与查询语义相似的片段，无法回答"全局性"问题，如"这部小说的主要主题是什么"——答案分散在全书各处，单个片段无法回答。

2. **缺乏关系推理**：向量检索不理解实体间的关系。问"A 的同事的导师是谁"，需要多跳推理，传统 RAG 难以处理。

3. **冗余与碎片化**：同一实体的信息分散在多个片段中，检索时可能只命中部分，导致答案不完整。

**GraphRAG 的解决方案**：

GraphRAG 分为两个阶段：

**索引阶段（离线）**：
1. **实体抽取**：用 LLM 从文档中抽取实体（人名、地名、组织等）和关系（"A 是 B 的导师"）。
2. **图谱构建**：将实体作为节点，关系作为边，构建知识图谱。
3. **社区检测**：用图算法（如 Leiden 算法）将图谱划分为若干"社区"（主题相关的实体簇）。
4. **社区摘要**：用 LLM 为每个社区生成摘要，形成层次化的全局索引。

**查询阶段（在线）**：

GraphRAG 支持两种查询模式：

1. **局部搜索（Local Search）**：针对具体实体的问题，从图谱中找到相关实体及其邻居，结合原始文本片段生成答案。适合"A 的背景是什么"这类问题。

2. **全局搜索（Global Search）**：针对全局性、总结性问题，遍历所有社区摘要，用 Map-Reduce 方式汇总生成答案。适合"这本书的主要主题是什么"这类问题。

**GraphRAG vs 传统 RAG**：

| 维度 | 传统 RAG | GraphRAG |
|------|---------|----------|
| 检索单元 | 文本片段 | 实体 + 关系 + 社区摘要 |
| 全局问题 | 弱 | 强 |
| 多跳推理 | 弱 | 强 |
| 索引成本 | 低 | 高（需 LLM 抽取实体） |
| 适合场景 | 事实问答 | 总结、关系推理 |

### 例子

下面展示使用微软 GraphRAG 库的基本流程，以及手动构建简易知识图谱 RAG：

```python

# 以下为配置和调用流程的示意

"""

  llm:
    api_key: ...
    type: openai_embedding

# 全局查询：
# python -m graphrag.query --root ./ragtest --method global "这部小说的主要主题是什么？"

# 局部查询：
# python -m graphrag.query --root ./ragtest --method local "张三和谁有合作关系？"
"""

# ===== 方案 2：手动构建简易 GraphRAG =====
from langchain.graphs import Neo4jGraph
from langchain.chains import GraphCypherQAChain
from langchain.chat_models import ChatOpenAI

# 假设已有一个 Neo4j 知识图谱
# graph = Neo4jGraph(url="bolt://localhost:7687", username="neo4j", password="password")

# 用 LLM 将自然语言转为 Cypher 查询
# chain = GraphCypherQAChain.from_llm(
#     llm=ChatOpenAI(temperature=0),
#     graph=graph,
#     verbose=True
# )
# result = chain.run("张三的导师是谁？")
# LLM 会生成类似 Cypher: MATCH (p:Person {name: '张三'})-[:ADVISED_BY]->(a:Person) RETURN a.name

# ===== 方案 3：用 LLM 抽取实体关系，构建简易图谱 RAG =====
from langchain.prompts import PromptTemplate
from langchain.chains import LLMChain
import networkx as nx

llm = ChatOpenAI(temperature=0, model="gpt-4")

# 实体关系抽取 Prompt
extract_prompt = PromptTemplate.from_template("""
从以下文本中抽取实体和关系，输出 JSON 格式。

文本：{text}

输出格式：
{{
  "entities": ["实体1", "实体2", ...],
  "relations": [
    {{"subject": "实体A", "relation": "关系", "object": "实体B"}},
    ...
  ]
}}
""")
extract_chain = LLMChain(llm=llm, prompt=extract_prompt)

# 构建知识图谱
texts = [
    "张三是清华大学的教授，他的导师是李四。",
    "李四是北京大学的院士，研究方向是人工智能。",
    "张三和王五合作发表了关于大模型的论文。",
]

graph = nx.Graph()
all_entities = {}

for text in texts:
    result = extract_chain.run(text=text)
    import json
    data = json.loads(result)
    
    for entity in data["entities"]:
        if entity not in graph:
            graph.add_node(entity)
            all_entities[entity] = []
        all_entities[entity].append(text)  # 记录实体出现的文本
    
    for rel in data["relations"]:
        graph.add_edge(rel["subject"], rel["object"], relation=rel["relation"])

print("=== 知识图谱节点 ===")
print(list(graph.nodes()))
print("\n=== 知识图谱边 ===")
for edge in graph.edges(data=True):
    print(f"  {edge[0]} --[{edge[2]['relation']}]--> {edge[1]}")

# 基于图谱的检索
def graph_retrieve(question, graph, all_entities, k=2):
    """从问题中识别实体，检索相关文本和邻居"""
    # 简化：用 LLM 识别问题中的实体
    entity_prompt = PromptTemplate.from_template("从问题中提取已知实体，逗号分隔。\n问题：{q}\n实体：")
    entities = LLMChain(llm=llm, prompt=entity_prompt).run(q=question).strip().split("，")
    
    relevant_texts = set()
    for entity in entities:
        entity = entity.strip()
        if entity in all_entities:
            relevant_texts.update(all_entities[entity])
        # 扩展到邻居
        if entity in graph:
            for neighbor in graph.neighbors(entity):
                relevant_texts.update(all_entities.get(neighbor, []))
    
    return list(relevant_texts)[:k]

# 测试
print("\n=== 图谱 RAG 检索 ===")
question = "张三的导师研究什么方向？"
retrieved = graph_retrieve(question, graph, all_entities)
for t in retrieved:
    print(f"  - {t}")
# 应该能检索到张三和李四相关的文本，支持多跳推理
```

### 总结

本讲的核心要点：

1. GraphRAG 通过知识图谱显式表示实体和关系，弥补向量检索的局部性缺陷。
2. 索引阶段：实体抽取 → 图谱构建 → 社区检测 → 社区摘要。
3. 查询阶段：局部搜索（实体级问题）+ 全局搜索（总结性问题）。
4. GraphRAG 适合需要跨文档推理、全局总结的场景，但索引成本高。

**常见注意事项**：
- GraphRAG 的索引成本远高于传统 RAG（需要大量 LLM 调用抽取实体）。
- 实体抽取的质量直接决定图谱质量，需要好的 Prompt 和校验。
- 知识图谱需要维护和更新，实体消歧（同名实体）是难点。

## 第 17 讲：Agentic RAG——智能体化的 RAG

### 概念

**Agentic RAG** 是将 RAG 嵌入到 **AI Agent（智能体）** 框架中的架构。传统 RAG 是"检索-生成"的固定流程，而 Agentic RAG 让 LLM 作为"大脑"，自主决定何时检索、检索什么、检索几次、是否需要其他工具（如计算器、代码执行、API 调用）。Agentic RAG 将 RAG 从"工具"升级为"能力"，使系统能处理复杂的多步推理任务。

### 原理

**Agent 的核心特征**：

1. **自主决策**：Agent 根据当前状态自主选择下一步行动，而非遵循固定流程。
2. **工具使用**：Agent 可以调用多种工具（检索、搜索、计算、代码执行等）。
3. **多轮迭代**：Agent 可以多轮思考和行动，直到完成任务。
4. **反思与修正**：Agent 可以评估自己的行动结果，决定是否调整策略。

**Agentic RAG 与传统 RAG 的区别**：

| 维度 | 传统 RAG | Agentic RAG |
|------|---------|-------------|
| 检索次数 | 固定 1 次 | 按需多次 |
| 检索策略 | 固定 | 动态选择 |
| 工具 | 仅检索 | 检索 + 搜索 + 计算 + 代码等 |
| 流程 | 线性 | 循环迭代 |
| 复杂问题 | 弱 | 强 |

**Agent 的核心循环（ReAct 模式）**：

```
Thought: 我需要思考下一步做什么
Action: 选择一个工具执行
Observation: 观察工具返回的结果
Thought: 基于观察继续思考
...（循环直到得出最终答案）
Final Answer: 给出最终答案
```

**Agentic RAG 的典型场景**：

1. **多跳问答**："A 公司的 CEO 毕业于哪所大学？" → 先检索"A 公司 CEO 是谁"，再检索"该人毕业于哪所大学"。
2. **对比分析**："比较 X 和 Y 的优劣" → 分别检索 X 和 Y 的信息，再综合对比。
3. **需要计算的问答**："公司 Q3 营收增长率？" → 检索 Q2 和 Q3 营收，调用计算器算增长率。
4. **需要实时信息**："今天股价多少？" → 检索不到时，调用网络搜索工具。

### 例子

下面用 LangChain 的 Agent 实现一个 Agentic RAG：

```python

# 测试 4：知识库外的问题（触发网络搜索）
```

**使用 LangGraph 实现更可控的 Agentic RAG**：

```python
from langgraph.graph import StateGraph, END
from langgraph.prebuilt import ToolNode
from typing import TypedDict, Annotated
import operator

class AgentState(TypedDict):
    messages: Annotated[list, operator.add]

def agent_node(state):
    """Agent 决策节点"""
    messages = state["messages"]
    response = llm.bind_tools([kb_tool, web_tool, calc_tool]).invoke(messages)
    return {"messages": [response]}

def should_continue(state):
    """判断是否继续调用工具"""
    last_message = state["messages"][-1]
    if last_message.tool_calls:
        return "tools"
    return END

# 构建工作流
workflow = StateGraph(AgentState)
workflow.add_node("agent", agent_node)
workflow.add_node("tools", ToolNode([kb_tool, web_tool, calc_tool]))

workflow.set_entry_point("agent")
workflow.add_conditional_edges("agent", should_continue, {"tools": "tools", END: END})
workflow.add_edge("tools", "agent")  # 工具执行后回到 agent

app = workflow.compile()
result = app.invoke({"messages": [("user", "公司 Q3 营收增长率是多少？")]})
```

### 总结

本讲的核心要点：

1. Agentic RAG 将 RAG 嵌入 Agent 框架，让 LLM 自主决策检索策略。
2. Agent 具备自主决策、工具使用、多轮迭代、反思修正四大特征。
3. 核心循环采用 ReAct 模式：Thought → Action → Observation。
4. 适合多跳问答、对比分析、需要计算或实时信息的复杂任务。

**常见注意事项**：
- Agent 的不确定性更高，需要设置 `max_iterations` 防止死循环。
- 多轮工具调用会增加延迟和成本，需要权衡。
- Agent 的可解释性较差，建议记录完整的思考链路便于调试。
- 简单问题不需要 Agent，传统 RAG 更快更稳定。

## 第 18 讲：RAG 评估指标——RAGAS 与 TruLens

### 概念

**RAG 评估框架**是系统化衡量 RAG 系统质量的工具集。第 14 讲介绍了评估的维度（忠实度、相关性等），本讲介绍如何用专业框架实现自动化、批量化、可对比的评估。**RAGAS** 和 **TruLens** 是目前最主流的两个 RAG 评估框架，它们提供了标准化的指标定义、自动化的评估流程和可视化的评估报告，让 RAG 系统的"效果"变得可量化、可追踪、可优化。

### 原理

**RAGAS（RAG Assessment）** 的核心思想是：用 LLM 自动评估 RAG 的各个环节，无需人工标注。RAGAS 定义了四个核心指标，覆盖 RAG 的完整链路：

**1. 上下文精确率（Context Precision）**：检索到的上下文中，与问题相关的占比。衡量检索的"精度"——有没有检索到无关内容。

**2. 上下文召回率（Context Recall）**：回答问题所需的信息，有多少被检索到了。衡量检索的"召回"——有没有漏掉关键信息。这需要有参考答案来对比。

**3. 忠实度（Faithfulness）**：答案中的事实陈述，有多少能从上下文中推导出来。衡量生成的"忠实性"——有没有幻觉。

**4. 答案相关性（Answer Relevance）**：答案是否切题，有没有答非所问。衡量生成的"相关性"。

这四个指标构成了 RAG 的"体检报告"：上下文精确率和召回率反映检索质量，忠实度和答案相关性反映生成质量。定位问题时，可以精准到环节。

**TruLens** 的思路类似，但更强调"可视化追踪"——记录每次查询的完整链路（查询→检索→上下文→生成），让开发者能看到每一步的输入输出，便于调试。TruLens 还支持"用户反馈"采集，将主观评价纳入评估。

**评估的数据需求**：
- **无参考评估**：只需要 question、contexts、answer，可评估忠实度和答案相关性。
- **有参考评估**：额外需要 ground_truth（标准答案），可评估上下文召回率和答案正确性。

## 第 19 讲：生产化部署——缓存、监控与优化

### 概念

**生产化部署**是将 RAG 从原型推向线上服务的过程。实验室里的 RAG 只需关心"能不能跑对"，生产级 RAG 还要关心"快不快、稳不稳、省不省、可不可观测"。本讲讲解 RAG 生产化的四个关键方面：缓存加速、性能优化、系统监控和成本控制。这些工程能力决定了 RAG 系统能否真正服务用户。

### 原理

**1. 缓存加速**

RAG 中有多个可缓存环节：

- **Embedding 缓存**：相同查询的 Embedding 结果可缓存，避免重复调用 Embedding API。这对查询变换（生成多个查询变体）尤其重要。
- **检索结果缓存**：相同查询的检索结果可缓存。对于高频问题（如 FAQ），命中率很高。
- **LLM 响应缓存**：相同 (query, context) 的 LLM 响应可缓存。LangChain 的 `LLMCache` 和 GPTCache 都支持。
- **语义缓存**：不仅缓存完全相同的查询，还缓存"语义相似"的查询。用 Embedding 判断相似度，命中则直接返回缓存答案。这是 RAG 最有价值的缓存策略。

**2. 性能优化**

RAG 的延迟主要来自三部分：Embedding 计算、向量检索、LLM 生成。优化策略：

- **Embedding 优化**：用本地模型替代 API（省网络延迟）；批量编码（batch）。
- **检索优化**：调整 HNSW 参数（`efSearch`）；用 ANN 替代精确检索；预热索引。
- **生成优化**：用流式输出（streaming）让用户提前看到部分答案；用更快的模型（如 GPT-4o-mini）；减少上下文长度。
- **并行化**：查询变换的多个子查询可并行检索；多路检索可并行。

**3. 系统监控**

生产级 RAG 需要监控：

- **性能指标**：P50/P95/P99 延迟、吞吐量（QPS）、错误率。
- **质量指标**：忠实度、相关性（采样评估）、用户反馈（点赞/点踩）。
- **业务指标**：查询量、缓存命中率、拒答率（"无法回答"的比例）。
- **资源指标**：向量数据库内存、GPU 利用率、API 调用量。

**4. 成本控制**

RAG 的成本主要来自 LLM API 调用和 Embedding API 调用。控制策略：

- **模型分级**：简单问题用小模型（GPT-4o-mini），复杂问题用大模型（GPT-4）。
- **缓存优先**：能命中缓存就不调用 LLM。
- **上下文裁剪**：只送最相关的 Top-K 文档，减少 token 消耗。
- **异步评估**：质量评估异步离线进行，不阻塞在线响应。

```python
import time
import functools
from collections import defaultdict

metrics = defaultdict(list)

def monitor(stage_name):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            start = time.time()
            try:
                result = func(*args, **kwargs)
                elapsed = time.time() - start
                metrics[stage_name].append(elapsed)
                return result
            except Exception as e:
                metrics[f"{stage_name}_errors"].append(str(e))
                raise
        return wrapper
    return decorator

# 应用到 RAG 各环节
```

```python
# 第一部分：索引构建
# ============================================================
class IndexBuilder:
    """知识库索引构建器"""
    
    def __init__(self, embedding_model_name="BAAI/bge-large-zh-v1.5"):
        self.embeddings = HuggingFaceBgeEmbeddings(
            model_name=embedding_model_name,
            model_kwargs={"device": "cpu"},
            query_instruction="为这个句子生成表示用于检索相关文章："
        )
        self.splitter = RecursiveCharacterTextSplitter(
            chunk_size=500,
            chunk_overlap=50,
            separators=["\n\n", "\n", "。", "！", "？", "，", " ", ""]
        )
    
    def build_index(self, documents: List[Document], index_path: str):
        """从文档构建向量索引"""
        logger.info(f"开始构建索引，共 {len(documents)} 个文档")
        
        # 1. 分块
        chunks = self.splitter.split_documents(documents)
        logger.info(f"分块完成，共 {len(chunks)} 个 chunk")
        
        # 2. 向量化并存储
        vectorstore = FAISS.from_documents(chunks, self.embeddings)
        vectorstore.save_local(index_path)
        logger.info(f"索引已保存到 {index_path}")
        
        # 3. 同时保存原始 chunks 用于 BM25
        import pickle
        with open(f"{index_path}/chunks.pkl", "wb") as f:
            pickle.dump(chunks, f)
        
        return vectorstore
    
    def load_index(self, index_path: str):
        """加载已有索引"""
        vectorstore = FAISS.load_local(index_path, self.embeddings)
        import pickle
        with open(f"{index_path}/chunks.pkl", "rb") as f:
            chunks = pickle.load(f)
        return vectorstore, chunks


# ============================================================
# 第二部分：检索引擎
# ============================================================
class RetrievalEngine:
    """混合检索 + 重排序引擎"""
    
    def __init__(self, vectorstore, chunks, top_k_recall=20, top_k_final=5):
        self.vector_retriever = vectorstore.as_retriever(
            search_kwargs={"k": top_k_recall}
        )
        self.bm25_retriever = BM25Retriever.from_documents(chunks)
        self.bm25_retriever.k = top_k_recall
        
        # 混合检索
        self.ensemble_retriever = EnsembleRetriever(
            retrievers=[self.bm25_retriever, self.vector_retriever],
            weights=[0.3, 0.7]  # 向量检索权重更高
        )
        
        # 重排序
        self.reranker = CrossEncoder('BAAI/bge-reranker-large')
        self.top_k_final = top_k_final
    
    def retrieve(self, query: str) -> List[Document]:
        """混合检索 + 重排序"""
        # 1. 混合召回
        candidates = self.ensemble_retriever.get_relevant_documents(query)
        
        # 2. Cross-Encoder 重排序
        pairs = [(query, doc.page_content) for doc in candidates]
        scores = self.reranker.predict(pairs)
        ranked = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)
        
        # 3. 取 Top-K
        top_docs = [doc for doc, _ in ranked[:self.top_k_final]]
        return top_docs

# 第三部分：生成引擎
# ============================================================
class GenerationEngine:
    """答案生成引擎"""
    
    def __init__(self, model_name="gpt-4o", temperature=0):
        self.llm = ChatOpenAI(model=model_name, temperature=temperature)
        
        self.prompt = ChatPromptTemplate.from_messages([
            ("system", """你是企业知识库问答助手。请基于提供的参考资料回答用户问题。

回答要求：
1. 忠实于资料：只使用资料中的信息，不编造。
2. 结构化输出：分点陈述，简明扼要。
3. 标注来源：每个事实后用 [资料N] 标注。
4. 诚实拒答：资料中无相关信息时，明确说明。
5. 语言专业：使用准确、专业的表述。"""),
            ("human", """参考资料：
{context}

问题：{question}

请回答：""")
        ])
        
        self.chain = LLMChain(llm=self.llm, prompt=self.prompt)
    
    def generate(self, question: str, documents: List[Document]) -> Dict:
        """基于检索文档生成答案"""
        # 组装上下文（带编号）
        context_parts = []
        for i, doc in enumerate(documents, 1):
            source = doc.metadata.get("source", "未知")
            context_parts.append(f"[资料{i}] (来源: {source})\n{doc.page_content}")
        context = "\n\n".join(context_parts)
        
        # 生成
        answer = self.chain.run(context=context, question=question)
        
        return {
            "answer": answer,
            "sources": [
                {
                    "content": doc.page_content[:100] + "...",
                    "metadata": doc.metadata
                }
                for doc in documents
            ]
        }

# ============================================================
class EnterpriseRAG:
    """企业知识库问答系统"""
    
    def __init__(self, index_path: str):
        # 初始化各组件
        self.index_builder = IndexBuilder()
        self.vectorstore, self.chunks = self.index_builder.load_index(index_path)
        self.retrieval_engine = RetrievalEngine(self.vectorstore, self.chunks)
        self.generation_engine = GenerationEngine()
        
        # 监控指标
        self.metrics = {
            "total_queries": 0,
            "total_latency": 0,
            "cache_hits": 0,
        }
    
    def query(self, question: str, use_cache: bool = True) -> Dict:
        """查询接口"""
        start_time = time.time()
        self.metrics["total_queries"] += 1
        
        try:
            # 1. 检索
            retrieve_start = time.time()
            documents = self.retrieval_engine.retrieve(question)
            retrieve_time = time.time() - retrieve_start
            
            # 2. 生成
            generate_start = time.time()
            result = self.generation_engine.generate(question, documents)
            generate_time = time.time() - generate_start
            
            total_time = time.time() - start_time
            self.metrics["total_latency"] += total_time
            
            # 3. 记录详细指标
            result["metadata"] = {
                "retrieve_time": f"{retrieve_time:.3f}s",
                "generate_time": f"{generate_time:.3f}s",
                "total_time": f"{total_time:.3f}s",
                "num_sources": len(documents),
            }
            
            logger.info(f"查询: {question[:50]}... | 耗时: {total_time:.3f}s")
            return result
            
        except Exception as e:
            logger.error(f"查询失败: {e}")
            return {
                "answer": "抱歉，系统处理查询时出现错误。",
                "sources": [],
                "error": str(e)
            }
    
    def get_stats(self) -> Dict:
        """获取系统统计信息"""
        avg_latency = (
            self.metrics["total_latency"] / self.metrics["total_queries"]
            if self.metrics["total_queries"] > 0 else 0
        )
        return {
            "total_queries": self.metrics["total_queries"],
            "avg_latency": f"{avg_latency:.3f}s",
            "cache_hit_rate": (
                self.metrics["cache_hits"] / self.metrics["total_queries"]
                if self.metrics["total_queries"] > 0 else 0
            ),
        }
```
