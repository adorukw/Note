# 第一章：动画帧基础认知

在讨论"如何重组"之前，我们必须先弄清楚"动画帧"到底是什么。这一章会从最根本的视觉原理讲起，建立后续所有讨论的共同语言。

---

## 第 1 讲：什么是动画帧

### 概念

**动画帧（Frame）** 是动画中最小的、不可再分的视觉单元。它是一张静态图像，在时间轴上占据一个极短的瞬间。当多张帧按顺序、以足够快的速度连续播放时，人眼就会因为"视觉暂留"现象而产生运动的错觉。

帧不等于"一张图片"——它是一张图片**加上它在时间轴上的位置**。换句话说，帧 = 图像 + 时间点。一张孤立的 PNG 只是图像；当你说"这是第 3 帧，播放时刻为 0.05 秒"时，它才成为帧。

### 原理

动画的本质是**对运动的采样**。现实中的运动是连续的，但显示器只能显示离散的画面。我们以固定的时间间隔对运动进行"快照"，每一张快照就是一帧。播放时再以相同（或不同）的速率把这些快照依次呈现，大脑就会把它们"插值"成连续运动。

这里有一个关键点：**帧本身不携带"它应该出现在哪里"的信息**。一张 100×200 的拳击手站立图，它只是像素的集合。它不知道自己应该贴在屏幕左边还是右边，不知道自己的脚应该在 y=500 还是 y=300。这个"位置"信息是动画系统在播放时额外赋予的。

### 例子

假设你有 5 张拳击手打拳的图：

```
帧1: 站立        100×200
帧2: 微微躬身    130×180
帧3: 继续前倾    200×150
帧4: 出拳        280×110
帧5: 收拳        150×170
```

如果你只是把这 5 张图按文件名顺序"一张接一张"地显示，每张显示 0.1 秒，你会看到什么？你会看到一个**在画面里乱跳的拳击手**——因为每张图的尺寸不同，如果你都从左上角 (0,0) 开始绘制，他的脚会忽高忽低，他的身体会忽左忽右。这就是本教程要解决的核心问题的雏形。

### 总结

- 帧是"图像 + 时间点"的组合，不是孤立的图片
- 帧记录的是"这一瞬间的样子"，不记录"这一瞬间应该出现在屏幕的哪里"
- 尺寸不同的帧如果直接按左上角对齐绘制，会产生"乱跳"的视觉效果
- 记住这一点，它是后面所有讨论的起点

## 第 2 讲：帧率与时间的关系

### 概念

**帧率（Frame Rate，FPS，Frames Per Second）** 是指每秒钟播放多少帧。常见的帧率有 12、24、30、60 FPS。帧率决定了动画的"流畅度"和"采样密度"。

与帧率对应的概念是**帧时长（Frame Duration）**，即每一帧停留多长时间。帧时长 = 1 / 帧率。例如 60 FPS 时，每帧停留约 16.67 毫秒。

### 原理

帧率背后是**时间采样定理**的一个直观应用。人眼对运动的感知有一个"融合阈值"——当画面切换速度超过约 10-12 FPS 时，大脑开始把它们感知为连续运动；达到 24 FPS 时，运动看起来比较平滑；60 FPS 时，快速运动也能保持清晰。

但帧率不仅仅是"越快越好"。在传统手绘动画中，**并不是每一帧都重新画**。迪士尼常用的做法是"一拍一"（on ones，每帧都画）和"一拍二"（on twies，一张画停留两帧）。一拍二在 24 FPS 下实际只有 12 张独立画，但观感依然流畅。这说明：**帧的时间长度可以不均匀**，动画序列里可以混合不同时长的帧。

这一点对后面的重组问题至关重要：当你拿到一堆 PNG，你不仅需要知道它们的顺序，还需要知道每帧该停留多久。如果所有帧都按相同时长播放，快速的动作会显得拖沓，慢动作会显得仓促。

### 例子

一个 0.5 秒的出拳动作，在不同帧率下需要的帧数不同：

```
12 FPS → 6 帧
24 FPS → 12 帧
60 FPS → 30 帧
```

如果这 6 帧（12 FPS 版本）每帧都停留 1/12 秒 ≈ 83ms，出拳看起来"顿挫有力"——这是很多格斗游戏的风格。如果同样 6 帧硬塞进 60 FPS 播放（每帧 16.67ms），整个动作只持续 100ms，快到看不清。

所以拿到帧序列后，**第一件事不是急着画，而是确定播放节奏**。没有节奏信息，再完美的对齐也救不了动画。

### 总结

- 帧率 = 每秒帧数；帧时长 = 1 / 帧率
- 帧时长可以不均匀，传统动画常用"一拍一""一拍二"混合
- 重组动画时，必须同时考虑"空间对齐"和"时间节奏"
- 拿到一堆 PNG 时，如果不知道帧率，需要根据动作类型合理推测（格斗动作通常 12-24 FPS）

## 第 3 讲：动画序列的本质

### 概念

**动画序列（Animation Sequence）** 是一组按时间顺序排列的帧的集合，加上每帧的时长信息，共同描述一个完整的动作。它不仅仅是"一堆图片的列表"，而是一个**带时间戳的有序结构**。

一个完整的动画序列包含三个要素：
1. **帧列表**：按播放顺序排列的图像
2. **时间信息**：每帧的停留时长（或统一的帧率）
3. **空间信息**：每帧在画布上的位置（这正是本教程的核心难点）

### 原理

动画序列可以形式化为一个三元组：

```
Sequence = { frames: [Frame], timings: [Duration], transforms: [Transform] }
```

其中 `Transform` 描述每一帧相对于"参考点"的位移、旋转、缩放。在理想情况下，原始视频里每一帧都有一个明确的画布位置（比如拳击手的脚始终在 y=400 这条线上），这个位置就是 `Transform` 的一部分。

问题在于：当你把每一帧**紧贴角色边缘裁剪**后，你丢掉了"画布位置"这个信息。你保留了 `frames` 和 `timings`（如果文件名按顺序编号的话），但 `transforms` 完全丢失了。所以重组动画的本质，就是**重建这个丢失的 transforms 信息**。

### 例子

原始视频里，拳击手 5 帧的完整信息可能是：

```
帧1: 图像=站立图, 画布位置=(350, 200), 尺寸=100×200, 时长=83ms
帧2: 图像=躬身图, 画布位置=(320, 220), 尺寸=130×180, 时长=83ms
帧3: 图像=前倾图, 画布位置=(250, 250), 尺寸=200×150, 时长=83ms
帧4: 图像=出拳图, 画布位置=(170, 290), 尺寸=280×110, 时长=83ms
帧5: 图像=收拳图, 画布位置=(300, 230), 尺寸=150×170, 时长=83ms
```

注意"画布位置"这一列——它告诉你每一帧的左上角应该贴在画布的哪里。裁剪后，你只剩下了"图像"和"尺寸"，"画布位置"这一列被擦除了。重组动画 = 想办法把这一列填回去。

### 总结

- 动画序列 = 帧列表 + 时间信息 + 空间信息
- 紧贴裁剪会擦除"空间信息"这一列
- 重组动画的本质是重建丢失的空间位置信息
- 把问题抽象成"填回画布位置"，后续所有方案都是围绕"怎么填"展开

## 第 4 讲：帧的存储形式

### 概念

帧在计算机里有两种主流存储形式：**独立文件**和**图集（Sprite Sheet）**。独立文件就是一张 PNG 对应一帧；图集是把所有帧拼在一张大图上，再用一个元数据文件记录每帧在大图中的位置和尺寸。

### 原理

独立文件的好处是简单直观，坏处是：每张 PNG 都有文件头、颜色表等开销，1000 帧就是 1000 个文件，加载时磁盘 I/O 开销大，显存占用也高（每张图都要单独上传到 GPU）。

图集把所有帧拼成一张大图，只需要一次 I/O 就能加载全部帧，GPU 也只需上传一次纹理。代价是需要额外的元数据文件来描述"第 N 帧在大图的哪个矩形区域"。

无论哪种形式，**帧的尺寸信息都是已知的**（PNG 头里就有宽高）。但"帧应该贴在画布的哪里"这个信息，两种形式都不天然包含——它必须由额外的元数据提供，或者由播放器用某种对齐策略推断出来。

这就是为什么工业级的动画工具（TexturePacker、Aseprite）在导出时一定会同时生成一个 JSON 或 XML 文件——那个文件里记录的就是每帧的"偏移量"，也就是我们一直在说的"丢失的空间信息"。

### 例子

**独立文件形式**：

```
boxer/
├── frame_001.png   (100×200)
├── frame_002.png   (130×180)
├── frame_003.png   (200×150)
├── frame_004.png   (280×110)
└── frame_005.png   (150×170)
```

**图集形式**：

```
boxer/
├── atlas.png       (一张大图，比如 600×400)
└── atlas.json      (元数据，记录每帧在大图里的位置)
```

`atlas.json` 里大概长这样：

```json
{
  "frames": [
    {"name": "frame_001", "x": 0,   "y": 0, "w": 100, "h": 200, "offsetX": 350, "offsetY": 200},
    {"name": "frame_002", "x": 100, "y": 0, "w": 130, "h": 180, "offsetX": 320, "offsetY": 220},
    ...
  ]
}
```

注意 `offsetX` 和 `offsetY`——这就是被裁剪掉的"画布位置"信息。**有它，重组就 trivial；没它，就得靠后面讲的策略去推断。**

### 总结

- 帧有两种存储形式：独立文件、图集
- 无论哪种形式，尺寸信息都在，但"画布位置"信息都不天然包含
- 工业级工具通过额外的元数据文件（JSON/XML）记录每帧的偏移量
- 你的拳击手场景 = 只有独立文件、没有元数据，所以需要"推断偏移量"

# 第二章：紧贴裁剪带来的问题

这一章我们正式进入你的拳击手案例。我们会拆解"紧贴裁剪"这个操作到底做了什么，为什么它会让重组变得困难，以及"信息丢失"具体丢失的是哪些信息。

---

## 第 5 讲：紧贴裁剪（Tight Crop）的概念

### 概念

**紧贴裁剪（Tight Crop / Trim to Bounds）** 是指把一张图像的透明边缘（或纯色背景边缘）全部裁掉，只保留包含实际内容的最小矩形区域。裁剪后，图像的边界紧贴内容的边缘，没有任何"留白"。

在动画制作中，紧贴裁剪是非常常见的优化手段。因为 PNG 的文件大小和显存占用直接取决于图像尺寸，裁掉大片透明区域能显著减少存储和内存开销。一张 800×600 但内容只占中间 100×200 的图，裁剪后变成 100×200，体积可能缩小到原来的 1/10。

### 原理

紧贴裁剪的算法很简单：扫描图像的所有像素，找到"非透明像素"（或非背景色像素）的最小外接矩形，然后把这个矩形裁剪出来。数学上就是求四个极值：

```
left   = min(所有非透明像素的 x 坐标)
right  = max(所有非透明像素的 x 坐标) + 1
top    = min(所有非透明像素的 y 坐标)
bottom = max(所有非透明像素的 y 坐标) + 1

裁剪后的图像 = 原图像[left:right, top:bottom]
```

这个操作本身是"无损"的——它没有改变任何像素的颜色，只是去掉了边缘的空白。但从**动画序列**的角度看，它是有损的，因为它丢掉了"内容在原图中的位置"这个信息。

关键洞察：**裁剪前，每一帧的尺寸都相同（比如都是 800×600），角色在画面里的位置就是它的"画布坐标"。裁剪后，每一帧的尺寸不同，"画布坐标"信息随着边缘空白一起被丢掉了。**

### 例子

假设原始视频是 800×600 的画布，拳击手站在画面中央偏左：

```
原始帧1（站立）:
┌──────────────────────────────┐
│                              │
│        ┌──┐                  │
│        │  │  ← 拳击手         │
│        │  │    100×200        │
│        │  │    位于(350,200)  │
│        └──┘                  │
│                              │
└──────────────────────────────┘
尺寸: 800×600
```

紧贴裁剪后：

```
裁剪后帧1:
┌──┐
│  │  ← 只剩拳击手本身
│  │    尺寸变成 100×200
│  │    "位于(350,200)" 这个信息没了
└──┘
尺寸: 100×200
```

你拿到了 100×200 的图，但再也看不出它原本应该贴在 800×600 画布的 (350, 200) 处。这就是问题的根源。

### 总结

- 紧贴裁剪 = 去掉边缘空白，只保留内容的最小外接矩形
- 它是存储优化手段，但对动画序列来说会丢失"画布位置"信息
- 裁剪前所有帧尺寸相同、位置明确；裁剪后尺寸各异、位置丢失
- 这是后续所有重组问题的直接原因

## 第 6 讲：拳击手案例：尺寸变化的本质

### 概念

回到你的拳击手案例。从站立到出拳，每一帧的尺寸都在变化：站立时约 100×200（窄高），出拳时约 300×100（宽矮）。这种尺寸变化不是"图片被缩放了"，而是**角色本身的姿态变化导致其外接矩形的形状变化**。

理解这一点非常重要：**尺寸变化反映的是姿态变化，不是缩放变化**。角色的实际大小（比如身高 1.8 米）没变，变的是他在画面上"摊开"的方式——站立时纵向延展，出拳时横向延展。

### 原理

我们可以把角色看作一个由关节连接的刚体集合。每个姿态下，所有关节点在画面上有一个分布，这个分布的外接矩形就是裁剪后的帧尺寸。

- **站立姿态**：身体竖直，手臂收拢，所有关节点在 x 方向集中、y 方向分散 → 外接矩形窄而高
- **出拳姿态**：身体前倾，手臂前伸，关节点在 x 方向分散、y 方向集中 → 外接矩形宽而矮

这里有一个隐含的、极其重要的事实：**虽然外接矩形的尺寸在变，但角色的某些"参考点"在画面上是相对稳定的**。比如：
- 脚底（如果脚没离地）：y 坐标基本不变
- 髋部（身体重心附近）：移动幅度比手脚小
- 头顶：在站立和微躬时变化不大

这些"相对稳定的参考点"就是后面重组动画的关键线索。如果你能找到一个在所有帧里都"应该对齐"的参考点，你就能把尺寸各异的帧重新对齐到正确的位置。

### 例子

拳击手 5 帧的尺寸变化与可能的参考点：

```
帧1 站立:  尺寸 100×200,  脚底在 y=200, 髋部在 y=120
帧2 微躬:  尺寸 130×180,  脚底在 y=180, 髋部在 y=110
帧3 前倾:  尺寸 200×150,  脚底在 y=150, 髋部在 y=95
帧4 出拳:  尺寸 280×110,  脚底在 y=110, 髋部在 y=70
帧5 收拳:  尺寸 150×170,  脚底在 y=170, 髋部在 y=105
```

注意：**脚底的 y 坐标 = 帧的高度**（因为紧贴裁剪，脚底就是图像的最下边）。这意味着，如果你假设"拳击手的脚始终贴在地面上"，那么所有帧的"底边"应该对齐到同一条水平线。这就是第 15 讲"基线对齐"方案的直觉来源。

### 总结

- 尺寸变化反映姿态变化，不是缩放
- 站立时外接矩形窄高，出拳时宽矮，这是关节分布的自然结果
- 关键洞察：虽然尺寸在变，但某些参考点（脚底、髋部）相对稳定
- 这些稳定的参考点是重组动画的"对齐线索"

## 第 7 讲：信息丢失：裁剪掉了什么

### 概念

紧贴裁剪丢失的信息可以精确地描述为：**每一帧相对于某个全局参考系的位移偏移量（offset）**。这个偏移量是一个二维向量 `(offsetX, offsetY)`，它告诉你"这一帧的左上角，应该贴在原始画布的哪个坐标"。

除了偏移量，裁剪本身不会丢失任何像素信息——角色身上的每一个像素都完整保留。所以"信息丢失"是特指"位置元数据"的丢失，不是图像内容的丢失。

### 原理

让我们用数学精确描述。设原始画布尺寸为 `W × H`（比如 800×600），第 i 帧在原始画布上的内容区域是矩形 `[x_i, y_i, x_i + w_i, y_i + h_i]`，其中 `(x_i, y_i)` 是左上角坐标，`w_i × h_i` 是裁剪后的尺寸。

紧贴裁剪后，你拿到的是尺寸为 `w_i × h_i` 的图像，但 `(x_i, y_i)` 这个坐标丢失了。重组动画时，你需要为每一帧重新确定一个 `(x_i', y_i')`，使得播放时角色"看起来在正确的地方"。

如果 `(x_i', y_i')` 等于原始的 `(x_i, y_i)`，重组就是完美的——和原视频一模一样。但因为你不知道 `(x_i, y_i)`，只能用各种策略去"猜"一个合理的 `(x_i', y_i')`。猜得越准，动画越接近原视频；猜得差，角色就会"乱跳"。

**所以"信息丢失"= 丢失了每一帧的 `(x_i, y_i)` 偏移量。重组 = 用合理策略重建 `(x_i', y_i')`。**

### 例子

原始 5 帧的完整数据（裁剪前在画布上的位置）：

```
帧1: (x=350, y=200), 尺寸 100×200   → 脚底在 y=400
帧2: (x=320, y=220), 尺寸 130×180   → 脚底在 y=400
帧3: (x=250, y=250), 尺寸 200×150   → 脚底在 y=400
帧4: (x=170, y=290), 尺寸 280×110   → 脚底在 y=400
帧5: (x=300, y=230), 尺寸 150×170   → 脚底在 y=400
```

注意一个关键规律：**所有帧的脚底（y + h）都等于 400**。这不是巧合——因为拳击手的脚始终踩在地面上，地面就是 y=400 这条线。这个规律就是"基线对齐"方案能工作的根本原因。

裁剪后你拿到的是：

```
帧1: 尺寸 100×200, 位置 ???
帧2: 尺寸 130×180, 位置 ???
帧3: 尺寸 200×150, 位置 ???
帧4: 尺寸 280×110, 位置 ???
帧5: 尺寸 150×170, 位置 ???
```

你的任务就是填上那些 `???`。

### 总结

- 裁剪丢失的是"每帧左上角在画布上的坐标 `(x_i, y_i)`"，不是像素内容
- 重组 = 为每帧重建一个合理的 `(x_i', y_i')`
- 原始数据里往往隐藏着规律（如脚底 y 坐标恒定），这些规律是对齐的线索
- 找到规律 → 填回偏移量 → 动画就重组成功了

## 第 8 讲：为什么直接拼接会出错

### 概念

"直接拼接"是指：拿到一堆尺寸不一的 PNG，按文件名顺序，每一帧都从画布的左上角 (0, 0) 开始绘制。这是没有任何对齐策略时最朴素的做法，也是初学者最容易犯的错误。

直接拼接几乎一定会产生错误的视觉效果，表现为角色在画面里"乱跳"——脚的位置忽高忽低，身体左右漂移，动作看起来不连贯。

### 原理

为什么直接拼接会出错？因为"左上角对齐"隐含了一个假设：**每一帧的内容在图像里的相对位置是相同的**。也就是说，它假设"角色的脚始终在图像的左下角""角色的头始终在图像的右上角"等等。

但紧贴裁剪恰恰打破了这个假设。站立时，角色占满整个图像高度，脚在最底部；出拳时，角色变矮，脚仍然在最底部，但"最底部"在图像里的绝对位置变了（因为图像变矮了）。如果你把两张图都从 (0,0) 开始绘制，站立帧的脚在 y=200，出拳帧的脚在 y=110——脚突然"跳"到上面去了，看起来就像角色瞬间矮了一截又长回来。

同理，站立时角色在图像里偏左（因为窄），出拳时角色横跨整个图像宽度（因为宽）。左上角对齐会让角色的左侧身体忽左忽右。

**根本原因：紧贴裁剪后，"图像左上角"这个参考点在不同帧里对应角色身体的不同部位。用它做对齐基准，等于让角色的不同部位轮流对齐到同一点，必然产生跳动。**

### 例子

用拳击手 5 帧做左上角对齐（假设画布 400×400，每帧从 (0,0) 绘制）：

```
帧1 站立:  绘制在 (0, 0), 尺寸 100×200 → 脚在 (0~100, 200)
帧2 微躬:  绘制在 (0, 0), 尺寸 130×180 → 脚在 (0~130, 180)
帧3 前倾:  绘制在 (0, 0), 尺寸 200×150 → 脚在 (0~200, 150)
帧4 出拳:  绘制在 (0, 0), 尺寸 280×110 → 脚在 (0~280, 110)
帧5 收拳:  绘制在 (0, 0), 尺寸 150×170 → 脚在 (0~150, 170)
```

播放时你会看到：拳击手的脚从 y=200 突然跳到 y=180，再跳到 y=150、y=110，又回到 y=170。整个角色像在蹦床上乱蹦，完全看不出"打拳"的动作。这就是直接拼接的灾难性后果。

### 总结

- 直接拼接 = 所有帧从画布左上角 (0,0) 绘制
- 它假设"图像左上角对应角色同一部位"，但紧贴裁剪打破了这个假设
- 结果是角色脚部忽高忽低、身体左右漂移，动作完全错乱
- 结论：必须引入一个**有意义的对齐参考点**，这就是下一章"锚点"的主题

# 第三章：锚点与对齐原理

这一章是整个教程的理论核心。我们会引入"锚点""注册点""枢轴点"这三个关键概念，它们是解决"尺寸不一的帧如何对齐"的标准武器。理解了这一章，后面的所有方案都只是这三个概念的不同应用。

---

## 第 9 讲：什么是锚点（Anchor Point）

### 概念

**锚点（Anchor Point）** 是图像中一个被指定的"参考点"，用于在绘制时确定图像的位置。锚点是一个相对坐标，通常用图像宽高的比例表示，比如 (0.5, 0.5) 表示图像中心，(0, 1) 表示左下角，(0.5, 1) 表示底边中点。

绘制时，不是把图像的左上角放在目标位置，而是把**锚点**放在目标位置。比如锚点是 (0.5, 1)（底边中点），目标位置是 (200, 400)，那么图像的底边中点会对齐到 (200, 400)，图像实际绘制在 `(200 - w/2, 400 - h)` 到 `(200 + w/2, 400)` 这个矩形里。

### 原理

锚点的本质是**把"图像位置"从"左上角对齐"泛化成"任意点对齐"**。数学上：

```
设锚点为 (ax, ay)（比例坐标，0~1），目标位置为 (px, py)，图像尺寸为 w×h

则图像左上角的绘制位置 = (px - ax * w, py - ay * h)
```

锚点的威力在于：**如果所有帧使用相同的锚点比例（比如都用底边中点 0.5, 1），并且目标位置相同（比如都贴在 (200, 400)），那么不同尺寸的帧会自动按"底边中点对齐"的方式排列**。这正是我们需要的——找到一个在所有帧里都"语义一致"的参考点。

"语义一致"是关键。锚点 (0.5, 1) 在站立帧里是脚底中点，在出拳帧里也是脚底中点——只要角色的脚始终在图像底部中央，这个锚点就语义一致。但如果某帧角色跳起来了（脚不在底部），这个锚点就失效了，需要换一个。

### 例子

拳击手 5 帧，统一用锚点 (0.5, 1)（底边中点），目标位置 (200, 400)：

```
帧1 站立 100×200: 左上角 = (200 - 50, 400 - 200) = (150, 200)
帧2 微躬 130×180: 左上角 = (200 - 65, 400 - 180) = (135, 220)
帧3 前倾 200×150: 左上角 = (200 - 100, 400 - 150) = (100, 250)
帧4 出拳 280×110: 左上角 = (200 - 140, 400 - 110) = (60, 290)
帧5 收拳 150×170: 左上角 = (200 - 75, 400 - 170) = (125, 230)
```

看，所有帧的底边都在 y=400，底边中点都在 x=200。播放时拳击手的脚稳稳踩在 y=400 这条线上，身体随着出拳动作自然前倾——这就是一个合理的动画！仅仅通过选择正确的锚点，我们就解决了"乱跳"问题。

### 总结

- 锚点是图像中指定的参考点，用比例坐标 (ax, ay) 表示
- 绘制时把锚点对齐到目标位置，而不是左上角
- 关键是选择"语义一致"的锚点：在所有帧里都对应角色的同一部位
- 拳击手案例用底边中点 (0.5, 1) 就能基本解决问题

## 第 10 讲：注册点（Registration Point）的概念

### 概念

**注册点（Registration Point）** 是锚点的一个变体说法，在 Flash、Animate 等软件里常用。它指的是"图像或元件的坐标系原点"——也就是图像内部那个被定义为 (0, 0) 的点。

注册点和锚点的区别在于"参考系"：锚点是用图像自身的比例坐标描述（如 0.5, 1），注册点是用绝对像素偏移描述（如"从左上角向右 50 像素、向下 200 像素"）。但本质上是同一个东西——都是"绘制时的对齐参考点"。

### 原理

在 Flash/Animate 里，每个元件（Symbol）都有一个注册点。当你把元件拖到舞台上时，注册点会对齐到你拖放的位置。注册点可以是 9 个预设位置之一（四角、四边中点、中心），也可以是自定义位置。

注册点的价值在于**它和元件一起存储**。也就是说，当你导出一个带注册点的元件时，注册点信息会保留在文件里，下一个打开文件的人能直接看到"这个元件的注册点在底边中点"。这比"只给一堆 PNG"要友好得多——PNG 格式本身不存储锚点信息，所以接收方无从得知。

这就是为什么"给一堆 PNG"是个难题：**PNG 不携带注册点信息**。如果原始作者在导出时把注册点信息写进文件名（如 `frame_001_pivot_50_200.png`）或单独的元数据文件，接收方就能直接用；否则只能靠猜。

### 例子

Flash 里一个拳击手元件的注册点设置：

```
元件: boxer_stand
尺寸: 100×200
注册点: (50, 200)  ← 底边中点，用绝对像素表示

当你在舞台上把元件放到 (200, 400) 时:
元件实际占据: (200-50, 400-200) 到 (200+50, 400) = (150, 200) 到 (250, 400)
```

对比锚点写法：

```
锚点写法: (0.5, 1)  ← 比例坐标
注册点写法: (50, 200)  ← 绝对像素 = (0.5*100, 1*200)
```

两者完全等价，只是表达方式不同。

### 总结

- 注册点是锚点的另一种说法，用绝对像素偏移而非比例坐标
- 注册点通常和元件一起存储，接收方能直接看到
- PNG 格式不携带注册点信息，这是"给一堆 PNG"难题的技术原因
- 解决思路：要么用元数据文件记录注册点，要么靠对齐策略推断

## 第 11 讲：枢轴点（Pivot Point）的作用

### 概念

**枢轴点（Pivot Point）** 是从 3D 和骨骼动画里借来的概念，指"物体旋转或变换时的不动点"。在 2D 动画里，枢轴点通常指角色身上的一个语义点——比如髋部、脚底、手心——它是角色运动的"逻辑中心"。

枢轴点和锚点的区别在于**语义层次**：锚点是图像层面的几何概念（"图像的哪个点对齐到目标"），枢轴点是角色层面的语义概念（"角色的哪个身体部位是运动中心"）。一个枢轴点在每一帧里对应图像上的不同像素位置，但语义上始终是"同一个身体部位"。

### 原理

考虑拳击手的出拳动作。整个动作的"逻辑中心"是髋部——身体围绕髋部前倾，手臂从髋部附近伸出。如果每一帧都把髋部对齐到同一个目标位置，整个动作会看起来非常自然，因为运动中心是稳定的。

但问题是：**紧贴裁剪后，髋部在图像里的像素位置是变化的**。站立时髋部大概在图像的 (50, 120)；出拳时身体前倾，髋部在图像里的相对位置变了，可能在 (140, 70)。如果你只用简单的锚点（如底边中点），无法精确对齐髋部——因为底边中点和髋部的相对关系在每一帧里都不同。

这时候就需要枢轴点：**为每一帧单独指定"髋部在图像里的像素位置"**，然后绘制时把每帧的枢轴点都对齐到同一个目标位置。这样无论帧尺寸怎么变，髋部始终稳定，动作就连贯了。

枢轴点信息必须**逐帧记录**，因为它在每帧里的像素位置不同。这就是为什么专业的动画格式（如 Spine、DragonBones）会为每一帧单独存储枢轴点坐标。

### 例子

拳击手 5 帧，逐帧指定髋部枢轴点（像素坐标，相对于图像左上角）：

```
帧1 站立 100×200: 髋部在 (50, 120)
帧2 微躬 130×180: 髋部在 (65, 110)
帧3 前倾 200×150: 髋部在 (100, 95)
帧4 出拳 280×110: 髋部在 (140, 70)
帧5 收拳 150×170: 髋部在 (75, 105)
```

目标位置：把髋部对齐到画布的 (200, 300)。则每帧左上角绘制位置：

```
帧1: (200 - 50, 300 - 120) = (150, 180)
帧2: (200 - 65, 300 - 110) = (135, 190)
帧3: (200 - 100, 300 - 95) = (100, 205)
帧4: (200 - 140, 300 - 70) = (60, 230)
帧5: (200 - 75, 300 - 105) = (125, 195)
```

播放时，拳击手的髋部始终在 (200, 300)，身体围绕髋部自然前倾出拳——这是最精确的对齐方式。但代价是必须逐帧标注枢轴点，工作量较大。

### 总结

- 枢轴点是角色层面的语义概念（如髋部、脚底），是运动的逻辑中心
- 枢轴点在每帧里的像素位置不同，必须逐帧记录
- 锚点是图像层面的几何概念，枢轴点是语义层面的对齐目标
- 枢轴点对齐最精确，但需要逐帧标注，适合重要角色动画

## 第 12 讲：三种基础对齐方式

### 概念

把锚点 / 枢轴点的思想具体化，有三种最常用的基础对齐方式：

1. **中心对齐（Center Alignment）**：锚点 = (0.5, 0.5)，所有帧的图像中心对齐到同一点
2. **底边对齐（Bottom Alignment）**：锚点 = (0.5, 1) 或 (0, 1)，所有帧的底边对齐到同一条水平线
3. **枢轴对齐（Pivot Alignment）**：逐帧指定语义点（如髋部），对齐到同一目标位置

这三种方式从简单到精确，适用场景各不相同。

### 原理

**中心对齐**假设"角色的几何中心在运动中稳定"。这对对称的、原地进行的动作（如待机呼吸、转身）有效，但对有位移的动作（如出拳、行走）效果差——因为出拳时角色横向延展，几何中心会前移，中心对齐会让角色"后退"。

**底边对齐**假设"角色的脚底（或着地点）在运动中稳定"。这对地面上的动作（如站立、出拳、蹲下）非常有效，因为脚始终踩在地上。但对跳跃、飞行等离地动作失效。底边对齐还可以细分为"底边中点对齐"和"底边左点对齐"——前者适合对称动作，后者适合有明确朝向的动作。

**枢轴对齐**不依赖任何几何假设，而是依赖语义标注。它最精确，但需要人工指定每帧的枢轴点位置。适合主角、Boss 等高质量动画，不适合小怪、特效等批量动画。

选择哪种方式，取决于**动作类型**和**精度要求**。没有"万能对齐方式"，关键是理解每种方式的假设，判断假设是否成立。

### 例子

三种对齐方式在拳击手案例上的效果对比：

```
【中心对齐】锚点 (0.5, 0.5), 目标 (200, 200)
帧1 100×200: 左上角 (150, 100), 中心 (200, 200) ✓
帧4 280×110: 左上角 (60, 145),  中心 (200, 200) ✓
→ 中心稳定，但脚从 y=300 跳到 y=255，角色"飘起来了" ✗

【底边中点对齐】锚点 (0.5, 1), 目标 (200, 400)
帧1 100×200: 左上角 (150, 200), 脚底中点 (200, 400) ✓
帧4 280×110: 左上角 (60, 290),  脚底中点 (200, 400) ✓
→ 脚底稳定，身体自然前倾 ✓（推荐）

【枢轴对齐】髋部对齐到 (200, 300)
帧1: 髋部 (50,120) → 左上角 (150, 180)
帧4: 髋部 (140,70) → 左上角 (60, 230)
→ 髋部稳定，最精确 ✓（最佳，但需标注）
```

### 总结

- 中心对齐：简单，适合原地对称动作，不适合有位移的动作
- 底边对齐：适合地面动作（站立、出拳、蹲下），假设脚底稳定
- 枢轴对齐：最精确，需逐帧标注，适合重要角色
- 选择依据：动作类型 + 精度要求，没有万能方案

## 第 13 讲：锚点的数学表达

### 概念

把前面几讲的概念用数学统一表达。设第 i 帧的图像尺寸为 `w_i × h_i`，锚点为 `(ax, ay)`（比例坐标，0~1），目标位置为 `(px, py)`，则该帧在画布上的左上角绘制位置为：

```
drawX_i = px - ax * w_i
drawY_i = py - ay * h_i
```

如果使用逐帧枢轴点，设第 i 帧的枢轴点像素坐标为 `(pivotX_i, pivotY_i)`，目标位置为 `(px, py)`，则：

```
drawX_i = px - pivotX_i
drawY_i = py - pivotY_i
```

这两个公式是所有对齐方案的统一数学基础。

### 原理

观察统一公式 `drawX_i = px - ax * w_i`，可以看出：**不同帧的绘制位置差异，完全来自于 `w_i` 和 `h_i` 的差异**（因为 `ax, ay, px, py` 对所有帧相同）。也就是说，锚点对齐的本质是"用帧尺寸的线性函数来补偿绘制位置"。

这揭示了一个深刻的事实：**只要你能找到一个"在所有帧里都对应角色同一部位"的图像坐标，你就能用它做对齐**。锚点对齐假设这个坐标可以表示为 `(ax * w_i, ay * h_i)`——即它和帧尺寸成比例。枢轴对齐则不假设比例关系，直接给出每帧的坐标。

介于两者之间还有一种"混合对齐"：某些帧用锚点，某些帧用枢轴点。比如拳击手前 3 帧用底边中点对齐（脚没离地），第 4 帧如果跳起来就改用髋部枢轴点。这种混合策略在实际项目里很常见。

### 例子

用统一公式重新计算拳击手案例（底边中点对齐，ax=0.5, ay=1, px=200, py=400）：

```python
frames = [
    ("frame1", 100, 200),
    ("frame2", 130, 180),
    ("frame3", 200, 150),
    ("frame4", 280, 110),
    ("frame5", 150, 170),
]
ax, ay, px, py = 0.5, 1.0, 200, 400

for name, w, h in frames:
    drawX = px - ax * w
    drawY = py - ay * h
    print(f"{name}: 绘制在 ({drawX}, {drawY}), 尺寸 {w}×{h}")
```

输出：

```
frame1: 绘制在 (150.0, 200.0), 尺寸 100×200
frame2: 绘制在 (135.0, 220.0), 尺寸 130×180
frame3: 绘制在 (100.0, 250.0), 尺寸 200×150
frame4: 绘制在 (60.0,  290.0), 尺寸 280×110
frame5: 绘制在 (125.0, 230.0), 尺寸 150×170
```

验证：每帧的底边 = drawY + h = 400 ✓，底边中点 = drawX + w/2 = 200 ✓。对齐成功。

### 总结

- 统一公式：`drawX = px - ax * w`，`drawY = py - ay * h`
- 锚点对齐 = 假设对齐点和帧尺寸成比例
- 枢轴对齐 = 直接给出每帧的对齐点像素坐标，不做比例假设
- 理解公式后，所有对齐方案都只是参数选择问题

## 第 14 讲：方案一：中心点对齐

### 概念

**中心点对齐**是最简单的方案：所有帧使用锚点 (0.5, 0.5)，把图像中心对齐到画布上的同一个目标点。绘制位置公式为 `drawX = px - w/2`，`drawY = py - h/2`。

这个方案假设"角色的几何中心在运动过程中保持稳定"，适用于对称的、原地进行的动作。

### 原理

中心点对齐的吸引力在于**零配置**——你不需要任何额外信息，只要知道每帧的尺寸（PNG 头里就有），就能直接计算绘制位置。接收方拿到 PNG 后，无需任何元数据，立刻就能播放。

但它的假设很强：角色几何中心稳定。这对以下场景不成立：
- 有明显方向性的动作（出拳、踢腿）：角色向一侧延展，中心偏移
- 有上下位移的动作（跳跃、下蹲）：中心 y 坐标变化
- 尺寸变化剧烈的动作：中心点在不同帧里对应角色不同部位

拳击手案例就不适合中心对齐——出拳时角色横向延展，中心点前移，中心对齐会让角色"向后退"，看起来像在原地扭动而不是向前出拳。

### 例子

Python 实现中心点对齐播放器：

```python
from PIL import Image
import os

def play_center_aligned(frame_dir, canvas_size, target_pos, fps=12):
    """中心点对齐播放器"""
    px, py = target_pos
    canvas_w, canvas_h = canvas_size
    
    frames = sorted(os.listdir(frame_dir))
    frame_duration = 1000 // fps  # 毫秒
    
    for frame_name in frames:
        img = Image.open(os.path.join(frame_dir, frame_name))
        w, h = img.size
        
        # 中心点对齐：计算左上角绘制位置
        draw_x = int(px - w / 2)
        draw_y = int(py - h / 2)
        
        # 创建画布并粘贴
        canvas = Image.new("RGBA", canvas_size, (255, 255, 255, 255))
        canvas.paste(img, (draw_x, draw_y), img)
        
        # 显示或保存 canvas
        canvas.show()
        # 实际项目中用 pygame.display 或 tkinter 更新

# 使用
play_center_aligned(
    frame_dir="boxer_frames",
    canvas_size=(400, 500),
    target_pos=(200, 250),  # 画布中心
    fps=12
)
```

### 总结

- 中心点对齐：锚点 (0.5, 0.5)，零配置，最简单
- 假设角色几何中心稳定，适用于对称原地动作
- 不适合有方向性或位移的动作（如出拳）
- 优点：无需元数据；缺点：适用范围窄

## 第 15 讲：方案二：基线 / 脚底对齐

### 概念

**基线对齐（Baseline Alignment）** 是指所有帧的某一条边（通常是底边）对齐到同一条水平线。最常用的是**底边中点对齐**：锚点 (0.5, 1)，把每帧的底边中点对齐到目标点。

这个方案假设"角色的着地点（脚底）在运动过程中始终在同一条水平线上"，适用于地面上的动作：站立、行走、出拳、蹲下、起身等。

### 原理

基线对齐是游戏开发里最常用的方案，因为绝大多数角色动作都发生在地面上。它的核心洞察是：**紧贴裁剪后，图像的底边就是角色的脚底**（假设角色脚始终是图像最下方的像素）。所以把所有帧的底边对齐，就等价于把所有帧的脚底对齐——而脚底稳定正是地面动作的特征。

底边对齐还可以细分为：
- **底边中点对齐** (0.5, 1)：适合对称或前后对称的动作
- **底边左点对齐** (0, 1)：适合朝右的动作，角色左脚始终在原地
- **底边右点对齐** (1, 1)：适合朝左的动作

拳击手朝右出拳，用底边中点或底边左点都可以。底边左点假设"后脚（左脚）始终不动"，更符合"弓步出拳"的力学；底边中点假设"两脚中点不动"，更符合"原地出拳"。根据实际动作选择。

### 例子

拳击手 5 帧用底边中点对齐（目标点 (200, 400)）：

```python
def play_bottom_aligned(frame_dir, canvas_size, target_x, ground_y, fps=12):
    """底边中点对齐播放器"""
    frames = sorted(os.listdir(frame_dir))
    
    for frame_name in frames:
        img = Image.open(os.path.join(frame_dir, frame_name))
        w, h = img.size
        
        # 底边中点对齐：锚点 (0.5, 1)
        draw_x = int(target_x - w / 2)
        draw_y = int(ground_y - h)  # 底边对齐到 ground_y
        
        canvas = Image.new("RGBA", canvas_size, (255, 255, 255, 255))
        canvas.paste(img, (draw_x, draw_y), img)
        canvas.show()

# 使用：脚底对齐到 y=400
play_bottom_aligned(
    frame_dir="boxer_frames",
    canvas_size=(400, 500),
    target_x=200,
    ground_y=400,
    fps=12
)
```

效果：拳击手的脚始终踩在 y=400 这条"地面线"上，身体随出拳自然前倾，动作连贯。**这是拳击手案例的推荐方案。**

### 总结

- 基线对齐：锚点 (0.5, 1) 或 (0, 1)，底边对齐到同一水平线
- 假设着地点稳定，适用于地面动作（站立、出拳、行走、蹲下）
- 是游戏开发最常用的方案，零配置或低配置
- 拳击手案例推荐用底边中点对齐

## 第 16 讲：方案三：枢轴点对齐

### 概念

**枢轴点对齐**是为每一帧单独指定一个"语义对齐点"（如髋部、脚底、手心），绘制时把每帧的枢轴点对齐到同一目标位置。这是最精确的方案，但需要逐帧标注枢轴点坐标。

### 原理

枢轴点对齐放弃了"锚点和帧尺寸成比例"的假设，转而直接给出每帧的对齐点像素坐标。它的理论基础是：**角色的运动总是围绕某些关节进行，把这些关节对齐，动作就连贯**。

比如出拳动作，运动中心是髋部——身体围绕髋部前倾，手臂从髋部附近伸出。如果每帧都把髋部对齐到同一点，整个动作会非常自然，因为运动中心稳定。

但枢轴点在每帧里的像素位置不同（因为裁剪掉了不同的边缘），所以必须逐帧标注。标注方法有两种：
1. **人工标注**：在每一帧上点击髋部位置，记录坐标
2. **算法推断**：用骨骼检测或特征点匹配自动找髋部（高级话题，第 23 讲会提）

人工标注虽然费时，但质量最高。一个 12 帧的出拳动画，人工标注髋部大概需要 2 分钟，完全可接受。

### 例子

带枢轴点元数据的播放器：

```python
import json

def play_pivot_aligned(frame_dir, metadata_file, canvas_size, target_pos, fps=12):
    """枢轴点对齐播放器"""
    with open(metadata_file) as f:
        metadata = json.load(f)
    
    px, py = target_pos
    
    for frame_info in metadata["frames"]:
        img = Image.open(os.path.join(frame_dir, frame_info["file"]))
        
        # 枢轴点对齐：每帧用各自的 pivot 坐标
        pivot_x = frame_info["pivotX"]
        pivot_y = frame_info["pivotY"]
        
        draw_x = int(px - pivot_x)
        draw_y = int(py - pivot_y)
        
        canvas = Image.new("RGBA", canvas_size, (255, 255, 255, 255))
        canvas.paste(img, (draw_x, draw_y), img)
        canvas.show()

# 元数据文件 pivot.json 内容：
# {
#   "frames": [
#     {"file": "frame_001.png", "pivotX": 50, "pivotY": 120},
#     {"file": "frame_002.png", "pivotX": 65, "pivotY": 110},
#     {"file": "frame_003.png", "pivotX": 100, "pivotY": 95},
#     {"file": "frame_004.png", "pivotX": 140, "pivotY": 70},
#     {"file": "frame_005.png", "pivotX": 75, "pivotY": 105}
#   ]
# }

play_pivot_aligned(
    frame_dir="boxer_frames",
    metadata_file="pivot.json",
    canvas_size=(400, 500),
    target_pos=(200, 300),  # 髋部对齐到 (200, 300)
    fps=12
)
```

### 总结

- 枢轴点对齐：逐帧指定语义点（髋部、脚底等），最精确
- 适用于重要角色动画（主角、Boss）
- 需要人工标注或算法推断枢轴点坐标
- 工作量较大，但质量最高

## 第 17 讲：方案四：元数据辅助

### 概念

**元数据辅助方案**是指不依赖对齐策略推断，而是直接由原始作者在导出帧时附带一个元数据文件，记录每帧的偏移量、枢轴点、时长等信息。接收方直接读取元数据，无需猜测。

这是工业级标准做法。TexturePacker、Aseprite、Spine 等工具导出时都会自动生成元数据文件（JSON、XML、plist 等）。

### 原理

元数据方案的核心思想是：**与其让接收方猜，不如让发送方说清楚**。原始作者在裁剪帧时，工具能精确知道"裁剪掉了多少边缘"——这个信息就是每帧的偏移量。把它写进元数据文件，接收方就能完美还原。

元数据文件通常包含以下字段：

```json
{
  "frames": [
    {
      "file": "frame_001.png",
      "x": 0, "y": 0,          // 在图集中的位置（如果是图集）
      "w": 100, "h": 200,       // 帧尺寸
      "offsetX": 350, "offsetY": 200,  // 在原始画布中的左上角位置
      "pivotX": 50, "pivotY": 120,     // 枢轴点（可选）
      "duration": 83            // 帧时长（毫秒，可选）
    },
    ...
  ],
  "canvas": {"w": 800, "h": 600},  // 原始画布尺寸
  "fps": 12
}
```

有了 `offsetX` 和 `offsetY`，接收方直接把每帧绘制在 `(offsetX, offsetY)` 即可，完美还原原始视频。这是最可靠的方案，前提是原始作者愿意提供元数据。

### 例子

带完整元数据的播放器：

```python
def play_with_metadata(frame_dir, metadata_file, fps=None):
    """元数据驱动播放器"""
    with open(metadata_file) as f:
        meta = json.load(f)
    
    canvas_w = meta["canvas"]["w"]
    canvas_h = meta["canvas"]["h"]
    default_fps = meta.get("fps", 12)
    if fps is None:
        fps = default_fps
    
    for frame_info in meta["frames"]:
        img = Image.open(os.path.join(frame_dir, frame_info["file"]))
        
        # 直接用元数据里的偏移量
        draw_x = frame_info["offsetX"]
        draw_y = frame_info["offsetY"]
        
        # 帧时长（如果元数据里有就用，否则用默认）
        duration = frame_info.get("duration", 1000 // fps)
        
        canvas = Image.new("RGBA", (canvas_w, canvas_h), (255, 255, 255, 255))
        canvas.paste(img, (draw_x, draw_y), img)
        canvas.show()
        # time.sleep(duration / 1000)

# 元数据 metadata.json:
# {
#   "canvas": {"w": 800, "h": 600},
#   "fps": 12,
#   "frames": [
#     {"file": "f1.png", "offsetX": 350, "offsetY": 200, "w": 100, "h": 200},
#     {"file": "f2.png", "offsetX": 320, "offsetY": 220, "w": 130, "h": 180},
#     {"file": "f3.png", "offsetX": 250, "offsetY": 250, "w": 200, "h": 150},
#     {"file": "f4.png", "offsetX": 170, "offsetY": 290, "w": 280, "h": 110},
#     {"file": "f5.png", "offsetX": 300, "offsetY": 230, "w": 150, "h": 170}
#   ]
# }

play_with_metadata("boxer_frames", "metadata.json")
```

### 总结

- 元数据辅助：原始作者导出时附带偏移量、枢轴点等信息
- 工业级标准做法，TexturePacker、Aseprite 等工具自动生成
- 接收方无需猜测，直接读取元数据即可完美还原
- 前提：原始作者愿意提供元数据文件

## 第 18 讲：方案对比与选择

### 概念

把前四讲的方案放在一起对比，根据动作类型、精度要求、是否有元数据来选择最合适的方案。

### 原理

选择方案时考虑三个维度：

1. **是否有元数据**：有 → 直接用方案四，无需其他
2. **动作类型**：地面动作 → 方案二（基线对齐）；原地对称动作 → 方案一（中心对齐）；复杂动作 → 方案三（枢轴对齐）
3. **精度要求**：背景小怪 → 方案一或二；主角、Boss → 方案三

实际项目里往往是混合策略：大部分帧用基线对齐，少数关键帧（如跳跃最高点）用枢轴点微调。

### 例子

方案对比表：

| 方案 | 配置量 | 精度 | 适用场景 | 拳击手案例 |
|------|--------|------|----------|-----------|
| 中心对齐 | 零 | 低 | 对称原地动作 | ✗ 不适合 |
| 基线对齐 | 零 | 中 | 地面动作 | ✓ 推荐 |
| 枢轴对齐 | 高（逐帧标注） | 高 | 重要角色动画 | ✓ 最佳但费时 |
| 元数据辅助 | 工具自动生成 | 完美 | 有原始工程文件 | ✓ 如有元数据则首选 |

决策流程：

```
拿到一堆 PNG
    ↓
有元数据文件吗？
    ├─ 有 → 方案四（元数据辅助）
    └─ 无 → 动作类型？
              ├─ 地面动作（站立/出拳/行走）→ 方案二（基线对齐）
              ├─ 原地对称动作（待机/转身）→ 方案一（中心对齐）
              └─ 复杂动作（跳跃/飞行）→ 方案三（枢轴对齐，需标注）
```

拳击手案例：没有元数据 + 地面动作 → **方案二（底边中点对齐）** 是最佳起点。如果效果不够好，再升级到方案三（标注髋部枢轴点）。

### 总结

- 有元数据 → 方案四，首选
- 无元数据 + 地面动作 → 方案二（基线对齐），拳击手案例推荐
- 无元数据 + 对称原地动作 → 方案一（中心对齐）
- 无元数据 + 复杂动作 → 方案三（枢轴对齐），需人工标注
- 实际项目常混合使用，关键帧用枢轴点微调

## 第 19 讲：Sprite Sheet 与图集

### 概念

**Sprite Sheet（精灵图集）** 是把多帧动画拼在一张大图上的存储形式。它解决两个问题：一是减少文件数量（1000 帧变成 1 张图），二是减少 GPU 纹理切换开销（一次加载全部帧）。

图集通常配合一个元数据文件使用，元数据记录每帧在大图中的位置和尺寸，以及每帧的对齐偏移量。

### 原理

图集的核心思想是**空间换时间**。把分散的小图拼成大图，虽然总像素数不变，但：
- 磁盘 I/O 从 1000 次变成 1 次
- GPU 纹理上传从 1000 次变成 1 次
- 文件系统元数据开销大幅降低

图集的排版有两种常见策略：
1. **网格排版**：所有帧尺寸相同，按 N×M 网格排列。简单但浪费空间（如果帧尺寸差异大）
2. **紧凑排版**：帧尺寸不同，用矩形打包算法（如 MaxRects）紧凑排列。省空间但需要元数据记录每帧位置

对于拳击手这种尺寸差异大的动画（100×200 到 280×110），紧凑排版能节省 30-50% 的图集面积。但代价是必须依赖元数据文件才能定位每帧。

图集的元数据文件里，每帧通常包含：
- 在图集中的位置 `(x, y)` 和尺寸 `(w, h)`
- 在原始画布中的偏移量 `(offsetX, offsetY)` 或枢轴点 `(pivotX, pivotY)`
- 帧时长 `duration`

有了这些信息，播放器就能从图集里裁出正确的帧，并贴到正确的位置。

### 例子

一个拳击手图集的紧凑排版示意：

```
图集 atlas.png (400×400):
┌──────────────────────────────┐
│ ┌──┐  ┌──────┐               │
│ │F1│  │  F3  │   F4          │
│ │  │  │      │ ┌──────────┐  │
│ │  │  └──────┘ │          │  │
│ │  │  ┌────┐   │          │  │
│ │  │  │ F2 │   │          │  │
│ │  │  │    │   └──────────┘  │
│ └──┘  └────┘       ┌──────┐  │
│                    │  F5  │  │
│                    │      │  │
│                    └──────┘  │
└──────────────────────────────┘

元数据 atlas.json:
{
  "image": "atlas.png",
  "size": {"w": 400, "h": 400},
  "frames": [
```

```python
def play_from_atlas(atlas_img, atlas_meta, canvas_size):
    with open(atlas_meta) as f:
        meta = json.load(f)
    
    atlas = Image.open(atlas_img)
    canvas_w, canvas_h = canvas_size
    
    for frame_info in meta["frames"]:
        # 从图集裁出帧
        crop_box = (frame_info["x"], frame_info["y"],
                    frame_info["x"] + frame_info["w"],
                    frame_info["y"] + frame_info["h"])
        frame = atlas.crop(crop_box)
        
        # 用元数据偏移量贴到画布
        canvas = Image.new("RGBA", canvas_size, (255, 255, 255, 255))
        canvas.paste(frame, (frame_info["offsetX"], frame_info["offsetY"]), frame)
        canvas.show()
```

- Sprite Sheet 把多帧拼在一张大图上，减少 I/O 和 GPU 开销
- 紧凑排版适合尺寸差异大的动画，但必须配合元数据
- 元数据记录每帧在图集中的位置 + 在画布中的偏移量
- 图集 + 元数据是游戏开发的标准资源格式

## 第 20 讲：TexturePacker 与类似工具

### 概念

**TexturePacker** 是最流行的图集打包工具，能自动把一堆 PNG 打包成图集并生成元数据文件。类似工具还有 ShoeBox、Free Texture Packer、Unity 的 Sprite Atlas 等。

这些工具的核心价值是：**自动计算每帧的偏移量**。你把原始帧（未裁剪的、尺寸相同的）喂给它，它会自动做紧贴裁剪、紧凑排版、并记录每帧的偏移量到元数据文件。

### 原理

TexturePacker 的工作流程：

1. **输入**：一堆尺寸相同的原始帧（如都是 800×600，角色在画面中央）
2. **紧贴裁剪**：自动扫描每帧的非透明区域，裁掉边缘空白，得到尺寸不同的帧
3. **记录偏移量**：裁剪时记录"裁掉了多少左边缘、多少上边缘"，这就是 `offsetX` 和 `offsetY`
4. **紧凑排版**：用矩形打包算法把所有帧拼进一张大图
5. **输出**：图集 PNG + 元数据文件（JSON/XML/plist 等格式）

关键在第 3 步——工具知道每帧裁剪前后的关系，所以能精确记录偏移量。这就是为什么"用工具导出"比"手动裁剪再给别人"要好得多：工具自动保留了偏移量信息。

TexturePacker 还支持一些高级功能：
- **Trim mode**：控制裁剪策略（trim 到非透明边缘、trim 到近似非透明等）
- **Extrude**：把边缘像素向外扩展几像素，避免采样时出现接缝
- **Pivot point**：可以为每帧或整个动画指定枢轴点

### 例子

TexturePacker 的命令行用法：

```bash
# 把 boxer_frames/ 目录下的所有 PNG 打包成图集
TexturePacker \
  --sheet atlas.png \
  --data atlas.json \
  --format json \
  --trim-mode Trim \
  --algorithm MaxRects \
  --enable-rotation \
  --extrude 1 \
  boxer_frames/
```

生成的 `atlas.json`：

```json
{
  "frames": {
    "frame_001.png": {
      "frame": {"x": 0, "y": 0, "w": 100, "h": 200},
      "rotated": false,
      "trimmed": true,
      "spriteSourceSize": {"x": 350, "y": 200, "w": 100, "h": 200},
      "sourceSize": {"w": 800, "h": 600}
    },
    ...
  }
}
```

注意 `spriteSourceSize.x` 和 `spriteSourceSize.y`——这就是裁剪前的偏移量（350, 200），完美记录了"这一帧原本在 800×600 画布的 (350, 200) 位置"。`sourceSize` 是原始画布尺寸。有了这两个信息，接收方可以完美还原。

### 总结

- TexturePacker 自动完成裁剪、排版、记录偏移量
- 关键能力：裁剪时保留偏移量信息到元数据
- 命令行可批处理，适合自动化流水线
- 如果原始作者用这类工具导出，接收方就不会有"对齐难题"

## 第 21 讲：Aseprite 与动画元数据

### 概念

**Aseprite** 是专业的像素动画制作软件，广泛用于独立游戏开发。它不仅能画帧，还能直接定义动画序列、帧时长、枢轴点，并导出带完整元数据的资源。

Aseprite 的导出格式（.aseprite 或 JSON）包含了比 TexturePacker 更丰富的动画信息：帧序列、每帧时长、标签（标记动画片段如"站立""出拳"）、枢轴点等。

### 原理

Aseprite 的工作流和 TexturePacker 不同：TexturePacker 是"事后打包"（你已经有帧了，它帮你打包），Aseprite 是"事前定义"（你在 Aseprite 里画帧的同时就定义了动画信息）。

Aseprite 的元数据结构：

```json
{
  "frames": [
    {
      "frame": {"x": 0, "y": 0, "w": 100, "h": 200},
      "duration": 80,
      "trimmed": false,
      "spriteSourceSize": {"x": 0, "y": 0, "w": 100, "h": 200},
      "sourceSize": {"w": 100, "h": 200}
    },
    ...
  ],
  "meta": {
    "frameTags": [
      {"name": "stand", "from": 0, "to": 0, "direction": "forward"},
      {"name": "punch", "from": 1, "to": 4, "direction": "forward"},
      {"name": "recover", "from": 4, "to": 5, "direction": "reverse"}
    ],
    "slices": [...]
  }
}
```

关键特性：
- **duration**：每帧时长可以不同（支持"一拍一""一拍二"混合）
- **frameTags**：把帧序列标记成多个动画片段（站立、出拳、收拳）
- **slices**：可以定义角色身上的区域（如头部、躯干），用于碰撞检测或换装

Aseprite 还支持为每帧设置枢轴点（通过 slice 或自定义插件），导出时一并写入元数据。

### 例子

Aseprite 命令行导出带元数据的图集：

```bash
aseprite -b boxer.aseprite \
  --sheet atlas.png \
  --format json-array \
  --data atlas.json \
  --trim \
  --tag punch
```

读取 Aseprite JSON 并播放：

```python
def play_aseprite(atlas_img, aseprite_json, canvas_size):
    with open(aseprite_json) as f:
        data = json.load(f)
    
    atlas = Image.open(atlas_img)
    
    # 找到 "punch" 标签对应的帧范围
    punch_tag = next(t for t in data["meta"]["frameTags"] if t["name"] == "punch")
    start, end = punch_tag["from"], punch_tag["to"]
    
    for i in range(start, end + 1):
        frame_info = data["frames"][i]
        
        # 从图集裁帧
        fx = frame_info["frame"]["x"]
        fy = frame_info["frame"]["y"]
        fw = frame_info["frame"]["w"]
        fh = frame_info["frame"]["h"]
        frame = atlas.crop((fx, fy, fx + fw, fy + fh))
        
        # 用 spriteSourceSize 获取偏移量
        offset_x = frame_info["spriteSourceSize"]["x"]
        offset_y = frame_info["spriteSourceSize"]["y"]
        
        canvas = Image.new("RGBA", canvas_size, (255, 255, 255, 255))
        canvas.paste(frame, (offset_x, offset_y), frame)
        canvas.show()
        
        # 用 duration 控制帧时长
        duration = frame_info["duration"] / 1000.0
        # time.sleep(duration)
```

### 总结

- Aseprite 是专业像素动画工具，支持帧时长、标签、枢轴点
- 导出的 JSON 包含完整动画信息，不只是图集位置
- frameTags 支持一个文件里定义多个动画片段
- 适合需要精细控制帧时长和动画片段的项目

## 第 22 讲：JSON / XML 元数据格式

### 概念

动画元数据有几种常见格式：JSON、XML、plist（Apple 专用）、自定义文本格式。其中 JSON 最通用，几乎所有引擎和库都支持。

不同工具导出的 JSON 结构略有差异，但核心字段相似。理解这些字段的语义，就能读懂任何工具的元数据。

### 原理

无论哪种格式，元数据都包含以下核心信息：

| 字段 | 含义 | 用途 |
|------|------|------|
| `frame` / `x, y, w, h` | 帧在图集中的位置和尺寸 | 从图集裁帧 |
| `sourceSize` | 原始画布尺寸 | 还原画布 |
| `spriteSourceSize` / `offsetX, offsetY` | 帧在原始画布中的偏移 | 贴到画布正确位置 |
| `duration` | 帧时长（毫秒） | 控制播放节奏 |
| `rotated` | 帧是否旋转 90° | 裁帧时是否需要旋转回来 |
| `trimmed` | 是否做过紧贴裁剪 | 判断是否有偏移量 |
| `pivotX, pivotY` | 枢轴点坐标 | 枢轴对齐 |

理解这些字段后，任何工具的元数据都能读懂。比如 TexturePacker 用 `spriteSourceSize`，Aseprite 也用 `spriteSourceSize`，Unity 的 Sprite Atlas 用 `spritePivot`——字段名不同但语义一致。

### 例子

三种常见 JSON 格式对比：

**TexturePacker Hash 格式**：

```json
{
  "frames": {
    "frame_001.png": {
      "frame": {"x": 0, "y": 0, "w": 100, "h": 200},
      "rotated": false,
      "trimmed": true,
      "spriteSourceSize": {"x": 350, "y": 200, "w": 100, "h": 200},
      "sourceSize": {"w": 800, "h": 600}
    }
  },
  "meta": {"image": "atlas.png"}
}
```

**TexturePacker Array 格式**：

```json
{
  "frames": [
    {
      "filename": "frame_001.png",
      "frame": {"x": 0, "y": 0, "w": 100, "h": 200},
      "rotated": false,
      "trimmed": true,
      "spriteSourceSize": {"x": 350, "y": 200, "w": 100, "h": 200},
      "sourceSize": {"w": 800, "h": 600}
    }
  ]
}
```

**Unity Sprite Atlas（简化）**：

```json
{
  "name": "boxer_atlas",
  "sprites": [
    {
      "name": "frame_001",
      "rect": {"x": 0, "y": 0, "width": 100, "height": 200},
      "pivot": {"x": 0.5, "y": 1.0},
      "border": {"x": 0, "y": 0, "z": 0, "w": 0}
    }
  ]
}
```

注意 Unity 用 `pivot` 的比例坐标 (0.5, 1.0) 而非像素偏移——这对应我们第 9 讲的"锚点"概念。不同工具选择不同表达方式，但底层原理一致。

### 总结

- JSON 是最通用的元数据格式
- 核心字段：frame 位置、sourceSize、spriteSourceSize/offset、duration、pivot
- 不同工具字段名不同，但语义一致
- 理解字段语义后，任何工具的元数据都能读懂

## 第 23 讲：Python 实现帧加载与对齐

### 概念

这一讲实现一个通用的动画帧播放器类 `FramePlayer`，支持四种对齐方案：中心对齐、底边对齐、枢轴对齐、元数据驱动。它接受一个帧目录（和可选的元数据文件），按指定方案播放动画。

### 原理

播放器的核心职责：
1. **加载帧**：从目录读取所有 PNG，按文件名排序
2. **计算绘制位置**：根据对齐方案，为每帧计算 `(drawX, drawY)`
3. **渲染**：创建画布，把帧粘贴到计算出的位置
4. **时间控制**：按帧率或逐帧时长切换帧

设计上把"对齐策略"抽象成可替换的组件，遵循策略模式。这样添加新的对齐方案只需新增一个策略类，播放器主逻辑不变。

### 例子

完整的 `FramePlayer` 实现：

```python
"""
动画帧播放器 - 支持四种对齐方案
用法:
    player = FramePlayer("boxer_frames", canvas_size=(400, 500))
    player.play_bottom_aligned(target_x=200, ground_y=400, fps=12)
"""
import os
import time
import json
from PIL import Image
from typing import List, Dict, Tuple, Optional


class AlignmentStrategy:
    """对齐策略基类"""
    
    def compute_draw_position(self, frame_size: Tuple[int, int],
                              frame_index: int) -> Tuple[int, int]:
        """计算帧在画布上的左上角绘制位置"""
        raise NotImplementedError


class CenterAlignment(AlignmentStrategy):
    """中心点对齐: 锚点 (0.5, 0.5)"""
    
    def __init__(self, target_x: int, target_y: int):
        self.target_x = target_x
        self.target_y = target_y
    
    def compute_draw_position(self, frame_size, frame_index):
        w, h = frame_size
        return (int(self.target_x - w / 2), int(self.target_y - h / 2))


class BottomCenterAlignment(AlignmentStrategy):
    """底边中点对齐: 锚点 (0.5, 1)"""
    
    def __init__(self, target_x: int, ground_y: int):
        self.target_x = target_x
        self.ground_y = ground_y
    
    def compute_draw_position(self, frame_size, frame_index):
        w, h = frame_size
        return (int(self.target_x - w / 2), int(self.ground_y - h))


class BottomLeftAlignment(AlignmentStrategy):
    """底边左点对齐: 锚点 (0, 1)"""
    
    def __init__(self, left_x: int, ground_y: int):
        self.left_x = left_x
        self.ground_y = ground_y
    
    def compute_draw_position(self, frame_size, frame_index):
        w, h = frame_size
        return (self.left_x, int(self.ground_y - h))


class PivotAlignment(AlignmentStrategy):
    """枢轴点对齐: 逐帧指定枢轴坐标"""
    
    def __init__(self, pivots: List[Tuple[int, int]],
                 target_x: int, target_y: int):
        self.pivots = pivots  # 每帧的枢轴点像素坐标
        self.target_x = target_x
        self.target_y = target_y
    
    def compute_draw_position(self, frame_size, frame_index):
        pivot_x, pivot_y = self.pivots[frame_index]
        return (self.target_x - pivot_x, self.target_y - pivot_y)


class MetadataAlignment(AlignmentStrategy):
    """元数据驱动对齐: 直接用每帧的 offsetX, offsetY"""
    
    def __init__(self, offsets: List[Tuple[int, int]]):
        self.offsets = offsets
    
    def compute_draw_position(self, frame_size, frame_index):
        return self.offsets[frame_index]


class FramePlayer:
    """通用动画帧播放器"""
    
    def __init__(self, frame_dir: str, canvas_size: Tuple[int, int],
                 bg_color=(255, 255, 255, 255)):
        self.frame_dir = frame_dir
        self.canvas_size = canvas_size
        self.bg_color = bg_color
        self.frames = self._load_frames()
    
    def _load_frames(self) -> List[Image.Image]:
        """加载目录下所有 PNG，按文件名排序"""
        files = sorted(f for f in os.listdir(self.frame_dir) if f.endswith('.png'))
        return [Image.open(os.path.join(self.frame_dir, f)).convert('RGBA') for f in files]
    
    def play(self, strategy: AlignmentStrategy,
             fps: int = 12, loop: int = 1):
        """按指定对齐策略播放动画"""
        frame_duration = 1.0 / fps
        
        for _ in range(loop):
            for i, frame in enumerate(self.frames):
                draw_pos = strategy.compute_draw_position(frame.size, i)
                
                canvas = Image.new('RGBA', self.canvas_size, self.bg_color)
                canvas.paste(frame, draw_pos, frame)
                
                # 实际项目用 pygame 或 tkinter 显示
                # 这里用 save 保存每一帧用于调试
                canvas.save(f"/tmp/debug_frame_{i:03d}.png")
                time.sleep(frame_duration)
    
    def render_to_gif(self, strategy: AlignmentStrategy,
                      fps: int = 12, output_path: str = "output.gif"):
        """渲染成 GIF 用于预览"""
        frame_duration = int(1000 / fps)
        canvases = []
        
        for i, frame in enumerate(self.frames):
            draw_pos = strategy.compute_draw_position(frame.size, i)
            canvas = Image.new('RGBA', self.canvas_size, self.bg_color)
            canvas.paste(frame, draw_pos, frame)
            canvases.append(canvas.convert('RGB'))
        
        canvases[0].save(
            output_path,
            save_all=True,
            append_images=canvases[1:],
            duration=frame_duration,
            loop=0
        )
        print(f"GIF 已保存到 {output_path}")


# ===== 使用示例 =====

# 场景1: 底边中点对齐（拳击手案例推荐方案）
player = FramePlayer("boxer_frames", canvas_size=(400, 500))
strategy = BottomCenterAlignment(target_x=200, ground_y=400)
player.render_to_gif(strategy, fps=12, output_path="boxer_bottom.gif")

# 场景2: 中心点对齐（对比效果）
strategy_center = CenterAlignment(target_x=200, target_y=250)
player.render_to_gif(strategy_center, fps=12, output_path="boxer_center.gif")

# 场景3: 枢轴点对齐（最精确）
pivots = [(50, 120), (65, 110), (100, 95), (140, 70), (75, 105)]
strategy_pivot = PivotAlignment(pivots, target_x=200, target_y=300)
player.render_to_gif(strategy_pivot, fps=12, output_path="boxer_pivot.gif")

# 场景4: 元数据驱动（如果有 metadata.json）
with open("metadata.json") as f:
    meta = json.load(f)
offsets = [(fr["offsetX"], fr["offsetY"]) for fr in meta["frames"]]
strategy_meta = MetadataAlignment(offsets)
player.render_to_gif(strategy_meta, fps=12, output_path="boxer_meta.gif")
```

### 总结

- 用策略模式把对齐方案抽象成可替换组件
- 四种策略：CenterAlignment、BottomCenterAlignment、PivotAlignment、MetadataAlignment
- `FramePlayer` 类负责加载、渲染、输出 GIF
- 实际项目里把 `play()` 里的 `canvas.save` 换成 `pygame.display.update()` 即可实时播放

## 第 24 讲：完整案例：拳击手动画还原

### 概念

这一讲把前面所有知识串起来，模拟你的完整场景：你拿到一堆"大小不一、无元数据"的拳击手 PNG，从零开始还原出流畅的出拳动画。我们会演示完整的决策和实现过程。

### 原理

完整的工作流：

1. **盘点资源**：查看帧目录，统计每帧尺寸，判断尺寸变化模式
2. **分析动作**：从尺寸变化推断动作类型（窄高→宽矮 = 前倾/出拳）
3. **选择方案**：根据动作类型选择对齐策略（地面动作 → 底边对齐）
4. **确定参数**：选择目标位置（脚底 y 坐标、中心 x 坐标）
5. **试播放**：渲染 GIF 预览，检查效果
6. **微调**：如果效果不理想，升级到枢轴对齐，人工标注关键点
7. **定稿**：输出最终动画

这个流程的关键是**从简单方案开始，按需升级**。不要一上来就标注枢轴点——先试底边对齐，大多数情况下已经够好。

### 例子

完整案例代码（包含资源分析和方案选择）：

```python
"""
拳击手动画还原完整案例
输入: boxer_frames/ 目录下 5 张大小不一的 PNG
输出: boxer_animation.gif 流畅的出拳动画
"""
import os
import json
from PIL import Image
from typing import List, Tuple


class BoxerAnimationRestorer:
    """拳击手动画还原器"""
    
    def __init__(self, frame_dir: str):
        self.frame_dir = frame_dir
        self.frames = []
        self.frame_sizes = []
        self._load_and_analyze()
    
    def _load_and_analyze(self):
        """加载帧并分析尺寸模式"""
        files = sorted(f for f in os.listdir(self.frame_dir) if f.endswith('.png'))
        
        print("=" * 60)
        print("步骤1: 盘点资源")
        print("=" * 60)
        print(f"找到 {len(files)} 帧:")
        
        for f in files:
            img = Image.open(os.path.join(self.frame_dir, f)).convert('RGBA')
            self.frames.append(img)
            self.frame_sizes.append(img.size)
            print(f"  {f}: {img.size[0]}×{img.size[1]}")
    
    def analyze_motion(self):
        """分析动作类型"""
        print("\n" + "=" * 60)
        print("步骤2: 分析动作")
        print("=" * 60)
        
        widths = [s[0] for s in self.frame_sizes]
        heights = [s[1] for s in self.frame_sizes]
        
        width_change = widths[-1] - widths[0]
        height_change = heights[-1] - heights[0]
        
        print(f"宽度变化: {widths[0]} → {widths[-1]} (Δ{width_change:+d})")
        print(f"高度变化: {heights[0]} → {heights[-1]} (Δ{height_change:+d})")
        
        if width_change > 50 and height_change < -50:
            motion_type = "前倾/出拳（横向延展，纵向收缩）"
            recommendation = "底边中点对齐（脚底稳定）"
        elif abs(width_change) < 20 and abs(height_change) < 20:
            motion_type = "原地动作（尺寸稳定）"
            recommendation = "中心点对齐"
        else:
            motion_type = "复杂动作"
            recommendation = "枢轴点对齐（需标注）"
        
        print(f"动作类型: {motion_type}")
        print(f"推荐方案: {recommendation}")
        return motion_type, recommendation
    
    def restore_with_bottom_align(self, canvas_size=(400, 500),
                                   target_x=200, ground_y=400, fps=12):
        """用底边中点对齐还原动画"""
        print("\n" + "=" * 60)
        print("步骤3: 底边中点对齐还原")
        print("=" * 60)
        
        canvases = []
        for i, frame in enumerate(self.frames):
            w, h = frame.size
            draw_x = int(target_x - w / 2)
            draw_y = int(ground_y - h)
            
            print(f"帧{i+1}: 绘制在 ({draw_x}, {draw_y}), 尺寸 {w}×{h}")
            
            canvas = Image.new('RGBA', canvas_size, (255, 255, 255, 255))
            canvas.paste(frame, (draw_x, draw_y), frame)
            canvases.append(canvas.convert('RGB'))
        
        output_path = "boxer_animation.gif"
        canvases[0].save(
            output_path,
            save_all=True,
            append_images=canvases[1:],
            duration=int(1000 / fps),
            loop=0
        )
        print(f"\n✓ 动画已保存到 {output_path}")
        return output_path
    
    def restore_with_pivot_align(self, pivots, canvas_size=(400, 500),
                                  target_x=200, target_y=300, fps=12):
        """用枢轴点对齐还原动画（更精确）"""
        print("\n" + "=" * 60)
        print("步骤4: 枢轴点对齐还原（精确版）")
        print("=" * 60)
        
        assert len(pivots) == len(self.frames), "枢轴点数量必须等于帧数"
        
        canvases = []
        for i, frame in enumerate(self.frames):
            pivot_x, pivot_y = pivots[i]
            draw_x = target_x - pivot_x
            draw_y = target_y - pivot_y
            
            print(f"帧{i+1}: 枢轴({pivot_x},{pivot_y}) → 绘制在 ({draw_x}, {draw_y})")
            
            canvas = Image.new('RGBA', canvas_size, (255, 255, 255, 255))
            canvas.paste(frame, (draw_x, draw_y), frame)
            canvases.append(canvas.convert('RGB'))
        
        output_path = "boxer_animation_pivot.gif"
        canvases[0].save(
            output_path,
            save_all=True,
            append_images=canvases[1:],
            duration=int(1000 / fps),
            loop=0
        )
        print(f"\n✓ 精确版动画已保存到 {output_path}")
        return output_path
    
    def export_metadata(self, output_path="boxer_metadata.json"):
        """导出元数据文件，方便下次直接使用"""
        metadata = {
            "canvas": {"w": 400, "h": 500},
            "fps": 12,
            "alignment": "bottom_center",
            "target": {"x": 200, "y": 400},
            "frames": []
        }
        
        for i, (frame, size) in enumerate(zip(self.frames, self.frame_sizes)):
            w, h = size
            draw_x = int(200 - w / 2)
            draw_y = int(400 - h)
            metadata["frames"].append({
                "file": f"frame_{i+1:03d}.png",
                "w": w, "h": h,
                "offsetX": draw_x,
                "offsetY": draw_y
            })
        
        with open(output_path, 'w') as f:
            json.dump(metadata, f, indent=2)
        print(f"\n✓ 元数据已导出到 {output_path}")
```

### 总结

完整还原流程的核心要点：

1. **先盘点再动手**：查看帧尺寸，分析动作类型，不要盲目选方案
2. **从简单方案开始**：先试底边对齐，大多数地面动作这就够了
3. **按需升级**：底边对齐效果不好再升级到枢轴对齐
4. **导出元数据**：还原成功后把偏移量写进 JSON，下次直接用方案四
5. **形成闭环**：第一次靠策略推断，之后靠元数据复用

**回到你最初的问题**：把一堆大小不一的 PNG 给一个不知道原视频的人，他应该这样做——

- **第一步**：查看所有帧的尺寸，发现从 100×200 变到 280×110，判断是"前倾/出拳"动作
- **第二步**：因为是地面动作，选择**底边中点对齐**，把所有帧的脚底对齐到同一条水平线
- **第三步**：渲染 GIF 预览，如果拳击手脚不乱跳了，说明对齐成功
- **第四步**：如果想要更精确（比如髋部稳定），用图像编辑器逐帧标注髋部坐标，改用枢轴对齐
- **第五步**：导出元数据 JSON，以后这个动画就可以直接用元数据驱动播放

这就是从"一堆无标注 PNG"到"流畅动画"的完整路径。

## 课程总结

恭喜你完成了全部 24 讲！让我们回顾整个知识体系：

**核心问题**：紧贴裁剪会丢失每帧的"画布位置"信息，导致尺寸不一的帧无法直接拼接。

**解决思路**：找到一个"在所有帧里语义一致的对齐参考点"，把每帧的这个参考点对齐到同一目标位置。

**四种方案**：
1. 中心对齐——最简单，适合对称原地动作
2. 底边对齐——最常用，适合地面动作（拳击手案例推荐）
3. 枢轴对齐——最精确，需逐帧标注，适合重要角色
4. 元数据辅助——最可靠，需原始作者配合，工业级标准

**关键概念**：
- 帧 = 图像 + 时间点
- 动画序列 = 帧列表 + 时间信息 + 空间信息
- 锚点 / 注册点 / 枢轴点 = 不同层次的对齐参考点
- 紧贴裁剪丢失的是 `(offsetX, offsetY)` 偏移量
- 重组 = 用合理策略重建偏移量

**实践建议**：
- 拿到一堆 PNG 时，先分析尺寸变化模式，再选方案
- 从简单方案开始，按需升级
- 还原成功后导出元数据，形成可复用资产
- 如果你是资源制作者，请务必用 TexturePacker / Aseprite 等工具导出元数据，别让接收方去猜

希望这个教程能帮你彻底理解动画帧对齐的本质。下次再遇到"一堆大小不一的 PNG"，你就知道该怎么把它们变成流畅的动画了。
