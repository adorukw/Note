# 第 1 章 数据库基础

数据库是现代信息系统的核心基础设施。本章将带您理解数据库的本质、发展脉络、数据模型与体系结构，为后续学习打下坚实基础。

---

## 第 1 讲：数据库概述与发展历史

### 概念

**数据库（Database, DB）** 是长期存储在计算机内、有组织的、可共享的大量数据的集合。**数据库管理系统（DBMS）** 是位于用户与操作系统之间的一层数据管理软件，负责科学有效地组织和存储数据、获取和维护数据。**数据库系统（DBS）** 则是一个完整的系统，包括数据库、DBMS、应用程序和数据库管理员（DBA）。

数据库的核心特征包括：数据结构化（数据按某种数据模型组织）、数据共享性高冗余度低（多用户共享，减少不必要重复）、数据独立性高（数据与应用程序解耦）、以及由 DBMS 统一管理和控制。这些特征使数据库区别于早期的文件系统，成为现代信息系统的基石。

### 原理

数据管理技术经历了三个主要发展阶段，每个阶段都解决了前一阶段的痛点：

1. **人工管理阶段（20 世纪 50 年代前）**：数据不保存，应用程序自己管理数据，数据不共享。这一阶段计算机主要用于科学计算，数据量小且临时。
2. **文件系统阶段（50 年代末—60 年代末）**：数据以文件形式长期保存，由操作系统统一管理。但文件之间缺乏联系，数据冗余度高，数据独立性差，并发控制困难。
3. **数据库系统阶段（60 年代末至今）**：数据由 DBMS 统一管理，采用复杂的数据模型描述数据及其联系，实现数据共享和高独立性。

数据库发展的里程碑事件包括：1968 年 IBM 推出的 IMS（层次模型）、1969 年 CODASYL 发布的 DBTG 报告（网状模型）、1970 年 E.F.Codd 发表里程碑论文提出关系模型、以及 70 年代末 System R 和 Ingres 等关系数据库原型系统的诞生。这些工作奠定了现代数据库的理论与实践基础。

### 例子

以一个简单的"学生选课"场景为例，对比文件系统与数据库系统的差异。

**文件系统方式**：需要三个独立文件 `students.txt`、`courses.txt`、`selections.txt`，应用程序需自行处理文件读写、数据一致性、并发冲突。例如，若两个程序同时修改 `students.txt`，可能造成数据损坏。

**数据库方式**（以 MySQL 为例）：

```sql
-- 创建学生表
CREATE TABLE students (
    student_id   VARCHAR(10) PRIMARY KEY,
    name         VARCHAR(50) NOT NULL,
    department   VARCHAR(50)
);

-- 创建课程表
CREATE TABLE courses (
    course_id    VARCHAR(10) PRIMARY KEY,
    course_name  VARCHAR(100) NOT NULL,
    credit       INT
);

-- 创建选课表（关联学生与课程）
CREATE TABLE selections (
    student_id   VARCHAR(10),
    course_id    VARCHAR(10),
    score        DECIMAL(5,2),
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES students(student_id),
    FOREIGN KEY (course_id)  REFERENCES courses(course_id)
);

-- 查询"张三"同学选修的所有课程
SELECT c.course_name, s.score
FROM selections s
JOIN courses c ON s.course_id = c.course_id
JOIN students st ON s.student_id = st.student_id
WHERE st.name = '张三';
```

DBMS 自动处理存储、索引、并发、事务、安全等问题，开发者只需关注业务逻辑。

### 总结

- 数据库的本质是"有组织、可共享、长期存储"的数据集合，DBMS 是管理它的软件。
- 数据管理经历了人工管理 → 文件系统 → 数据库系统三个阶段，每个阶段都解决了前一阶段的核心痛点。
- 关系模型（1970 年 Codd 提出）是现代数据库的主流理论基础。
- 数据库相比文件系统的核心优势：数据结构化、共享性高、冗余度低、独立性高、由 DBMS 统一管理。
- **常见误区**：混淆"数据库"与"数据库管理系统"。数据库是数据本身，DBMS 是管理软件，二者共同构成数据库系统。

## 第 2 讲：数据模型与数据库体系结构

### 概念

**数据模型（Data Model）** 是对现实世界数据特征的抽象，是数据库系统的核心与基础。它严格定义了一组概念的集合，用于描述数据结构、数据操作和数据约束。数据模型通常由三要素组成：**数据结构**（描述对象类型与关系）、**数据操作**（描述允许的操作类型与方式）、**数据完整性约束**（描述数据及其联系应满足的规则）。

**数据库体系结构** 是数据库的内部组织框架。最经典的是**三级模式结构**：外模式（用户视图）、模式（逻辑结构）、内模式（物理存储），以及两级映象（外模式/模式映象、模式/内模式映象），实现了逻辑独立性和物理独立性。

### 原理

数据模型按应用层次分为两类：

**1. 概念模型（信息模型）**：面向用户、按用户观点对数据建模，与具体 DBMS 无关。最常用的是实体-联系模型（E-R 模型），用实体、属性、联系描述现实世界。

**2. 逻辑模型与物理模型**：逻辑模型按计算机观点建模，包括层次模型（树形）、网状模型（图）、关系模型（二维表）、面向对象模型等。物理模型描述数据在存储介质上的组织方式。

三级模式结构的原理如下：

- **外模式（External Schema）**：也称用户模式，是数据库用户能看见的局部数据逻辑结构和特征描述，是模式的子集。一个数据库可以有多个外模式。
- **模式（Schema）**：也称逻辑模式，是数据库中全体数据的逻辑结构和特征描述，是所有用户的公共数据视图。一个数据库只有一个模式。
- **内模式（Internal Schema）**：也称存储模式，是数据物理结构和存储方式的描述，是数据在数据库内部的组织方式。一个数据库只有一个内模式。

两级映象保证数据独立性：当模式改变时，DBA 修改外模式/模式映象使外模式不变，从而应用程序不变（**逻辑独立性**）；当内模式改变时，DBA 修改模式/内模式映象使模式不变（**物理独立性**）。

### 例子

以"大学教务系统"为例说明三级模式：

```
┌─────────────────────────────────────────────┐
│  外模式（视图层）                              │
│  ┌──────────────┐  ┌──────────────┐         │
│  │ 学生视图:     │  │ 教师视图:     │         │
│  │ 学号,姓名,    │  │ 工号,姓名,    │         │
│  │ 选课,成绩     │  │ 授课,学生名单 │         │
│  └──────────────┘  └──────────────┘         │
└─────────────────────────────────────────────┘
                    ↑ 外模式/模式映象
┌─────────────────────────────────────────────┐
│  模式（逻辑层）                                │
│  students(id,name,dept)                      │
│  courses(id,name,credit)                     │
│  selections(sid,cid,score)                   │
└─────────────────────────────────────────────┘
                    ↑ 模式/内模式映象
┌─────────────────────────────────────────────┐
│  内模式（存储层）                              │
│  students 表 → B+树索引, 页大小16KB           │
│  courses 表  → Hash索引                       │
│  selections 表 → 复合索引(sid,cid)            │
└─────────────────────────────────────────────┘
```

关系模型示例（最常用的逻辑模型）：

| 学号 | 姓名 | 院系 |
|------|------|------|
| S01  | 张三 | 计算机 |
| S02  | 李四 | 数学 |

关系模型用二维表组织数据，表与表之间通过外键关联，简单直观且数学基础扎实。

### 总结

- 数据模型三要素：数据结构、数据操作、数据完整性约束。
- 数据模型分两层：概念模型（E-R）面向用户，逻辑/物理模型面向机器。
- 主流逻辑模型是关系模型，基于二维表，数学基础扎实。
- 三级模式（外模式/模式/内模式）+ 两级映象实现数据独立性。
- **关键要点**：逻辑独立性靠外模式/模式映象，物理独立性靠模式/内模式映象。
- **常见误区**：把"模式"理解为"模式匹配"中的模式。在数据库中，模式特指数据库的逻辑结构描述。

## 第 3 讲：关系数据库基本概念

### 概念

**关系数据库** 是基于关系模型建立的数据库，由 E.F.Codd 于 1970 年提出。其核心思想是用二维表（关系）来组织和表示数据。关系数据库的基本术语包括：

- **关系（Relation）**：一个关系对应一张二维表。
- **元组（Tuple）**：表中的一行即为一个元组，对应一个实体。
- **属性（Attribute）**：表中的一列即为一个属性，每个属性有唯一名称。
- **码/键（Key）**：能唯一标识元组的属性或属性组。**候选码** 是最小码，**主码（Primary Key）** 是从候选码中选定的一个，**外码（Foreign Key）** 是引用其他关系主码的属性。
- **域（Domain）**：属性的取值范围。
- **分量**：元组中的一个属性值。

### 原理

关系模型建立在严格的数学基础——集合论之上。一个关系可形式化定义为：域 D1, D2, ..., Dn 的笛卡尔积 D1×D2×...×Dn 的子集称为在这些域上的一个 n 元关系。例如，若 D1={男,女}，D2={北京,上海}，则笛卡尔积有 4 个元组，从中选取子集即得到一个关系。

关系有六条重要性质：

1. **列同质**：每一列的分量来自同一域，是同类型数据。
2. **列顺序无关**：列的次序可以任意交换，不影响关系含义。
3. **行顺序无关**：行的次序可以任意交换。
4. **元组唯一性**：任意两个元组不能完全相同（集合性质）。
5. **分量原子性**：每个分量必须是不可分的数据项（第一范式要求）。
6. **属性名唯一**：属性名在关系内唯一。

关系模式是关系的"型"，关系是关系模式的"值"。关系模式可表示为 `R(U, D, DOM, F)`，其中 U 是属性集合，D 是域集合，DOM 是属性到域的映射，F 是属性间依赖关系集合。通常简记为 `R(A1, A2, ..., An)`。

### 例子

以"学生-课程"关系为例：

**关系模式**：
- Student(Sno, Sname, Sdept, Sage)
- Course(Cno, Cname, Credit)
- SC(Sno, Cno, Grade)

**关系实例**（Student 关系）：

| Sno | Sname | Sdept | Sage |
|-----|-------|-------|------|
| S01 | 张三  | 计算机 | 20 |
| S02 | 李四  | 数学  | 21 |
| S03 | 王五  | 计算机 | 19 |

分析这个关系：
- 关系名：Student
- 属性：Sno, Sname, Sdept, Sage（4 个属性，4 元关系）
- 元组：3 个元组（3 行）
- 候选码：Sno（学号唯一），若姓名不重复则 Sname 也是候选码
- 主码：选 Sno
- 域：Sage 的域是正整数（如 15-50）

SQL 中定义关系模式：

```sql
CREATE TABLE Student (
    Sno   CHAR(5)   PRIMARY KEY,        -- 主码
    Sname VARCHAR(20) NOT NULL,
    Sdept VARCHAR(20),
    Sage  SMALLINT  CHECK (Sage > 0)
);

CREATE TABLE Course (
    Cno    CHAR(4)   PRIMARY KEY,
    Cname  VARCHAR(40) NOT NULL,
    Credit SMALLINT
);

CREATE TABLE SC (
    Sno   CHAR(5),
    Cno   CHAR(4),
    Grade DECIMAL(5,2),
    PRIMARY KEY (Sno, Cno),              -- 复合主码
    FOREIGN KEY (Sno) REFERENCES Student(Sno),  -- 外码
    FOREIGN KEY (Cno) REFERENCES Course(Cno)
);
```

### 总结

- 关系数据库基于关系模型，用二维表组织数据，数学基础扎实。
- 核心术语：关系（表）、元组（行）、属性（列）、码（键）、域（取值范围）。
- 关系有六条性质，最重要的是分量原子性（第一范式）和元组唯一性。
- 关系模式是"型"，关系是"值"，二者关系类似"类"与"对象"。
- **关键要点**：码的概念层次——超码 ⊇ 候选码 ⊇ 主码；外码用于建立关系间联系。
- **常见误区**：把"关系"理解为"联系"。在关系模型中，关系特指二维表本身，而实体间的联系也用关系（表）表示，这是关系模型的优雅之处。

# 第 2 章 关系数据库与 SQL

本章是数据库学习的核心。先从理论上的关系代数入手，再逐步掌握 SQL 的数据定义、数据操作和高级查询，最终能够熟练使用 SQL 解决实际问题。

---

## 第 4 讲：关系代数

### 概念

**关系代数** 是一种抽象的查询语言，用对关系的运算表达查询。它是关系数据库操作的理论基础，与关系演算共同构成关系数据语言的两大流派。关系代数的运算对象是关系，运算结果也是关系，因此可以嵌套使用。

关系代数运算按运算符不同分为两类：

- **传统的集合运算**：并（∪）、差（−）、交（∩）、笛卡尔积（×）。要求参与运算的关系具有相同的目（属性数）且对应属性取自同一域（除笛卡尔积外）。
- **专门的关系运算**：选择（σ）、投影（π）、连接（⋈）、除（÷）。这些运算是关系代数特有的，用于表达实际的查询需求。

### 原理

**1. 传统的集合运算**

设关系 R 和 S 具有相同的目 n，且对应属性取自同一域：

- **并（R ∪ S）**：由属于 R 或属于 S 的元组组成，结果仍为 n 目关系。用于合并两个同类关系。
- **差（R − S）**：由属于 R 但不属于 S 的元组组成。
- **交（R ∩ S）**：由既属于 R 又属于 S 的元组组成。R ∩ S = R − (R − S)。
- **笛卡尔积（R × S）**：R 为 n 目、S 为 m 目时，结果为 (n+m) 目关系，元组数为 R 的元组数 × S 的元组数。

**2. 专门的关系运算**

- **选择（σ，Selection）**：`σ_F(R)` 从关系 R 中选取满足条件 F 的元组，是行级操作。例如 `σ_Sage>20(Student)` 选出年龄大于 20 的学生。
- **投影（π，Projection）**：`π_A(R)` 从关系 R 中选取若干属性列组成新关系，是列级操作。投影后会自动去重。
- **连接（⋈，Join）**：从两个关系的笛卡尔积中选取属性间满足一定条件的元组。**等值连接** 是条件为等值的连接；**自然连接** 是特殊的等值连接，要求比较的属性同名且自动去重。
- **除（÷，Division）**：`R ÷ S` 用于"查询包含全部..."类问题。例如"选修了所有课程的学生"。

关系代数表达式可以嵌套组合，例如 `π_Sname(σ_Sdept='计算机'(Student ⋈ SC))` 表示"查询计算机系学生的姓名"。

### 例子

设有关系 R 和 S：

**R**：

| A | B |
|---|---|
| 1 | 2 |
| 3 | 4 |

**S**：

| A | B |
|---|---|
| 3 | 4 |
| 5 | 6 |

**运算示例**：

```
R ∪ S = {(1,2), (3,4), (5,6)}
R − S = {(1,2)}
R ∩ S = {(3,4)}
R × S = {(1,2,3,4), (1,2,5,6), (3,4,3,4), (3,4,5,6)}
```

**实际查询示例**：以 Student(Sno, Sname, Sdept, Sage)、Course(Cno, Cname, Credit)、SC(Sno, Cno, Grade) 为例。

查询 1：查询年龄大于 20 岁的计算机系学生姓名。

```
π_Sname( σ_Sage>20 ∧ Sdept='计算机' (Student) )
```

查询 2：查询选修了 C01 课程的学生学号与姓名。

```
π_Sno, Sname( Student ⋈ σ_Cno='C01'(SC) )
```

查询 3：查询选修了全部课程的学生学号（除运算）。

```
π_Sno, Cno(SC) ÷ π_Cno(Course)
```

对应的 SQL 实现：

```sql
-- 查询1
SELECT Sname FROM Student
WHERE Sage > 20 AND Sdept = '计算机';

-- 查询2
SELECT Student.Sno, Sname
FROM Student JOIN SC ON Student.Sno = SC.Sno
WHERE SC.Cno = 'C01';

-- 查询3（关系除法在SQL中需用双重NOT EXISTS实现）
SELECT Sno FROM Student S
WHERE NOT EXISTS (
    SELECT Cno FROM Course C
    WHERE NOT EXISTS (
        SELECT * FROM SC
        WHERE SC.Sno = S.Sno AND SC.Cno = C.Cno
    )
);
```

### 总结

- 关系代数是关系数据库的理论查询语言，运算对象和结果都是关系。
- 五种基本运算：并、差、笛卡尔积、选择、投影，其他运算可由它们导出。
- 选择是行级过滤，投影是列级筛选，连接用于组合多表数据，除运算用于"全部"类查询。
- 关系代数表达式可嵌套，是 SQL 优化的理论基础。
- **关键要点**：自然连接会自动去重同名属性，等值连接不会。
- **常见误区**：混淆"选择"和"投影"。选择 σ 是横向过滤（选行），投影 π 是纵向筛选（选列）。

## 第 5 讲：SQL 基础——DDL 数据定义

### 概念

**SQL（Structured Query Language，结构化查询语言）** 是关系数据库的标准语言，集数据定义（DDL）、数据操纵（DML）、数据控制（DCL）和事务控制（TCL）于一体。SQL 于 1974 年由 Boyce 和 Chamberlin 提出，1986 年成为 ANSI 标准，至今已发布 SQL-86、SQL-89、SQL-92、SQL:1999、SQL:2003、SQL:2008、SQL:2011、SQL:2016 等多个版本。

**DDL（Data Definition Language，数据定义语言）** 用于定义和修改数据库结构，主要包括：

- **CREATE**：创建数据库对象（数据库、表、视图、索引等）。
- **ALTER**：修改已有对象的结构。
- **DROP**：删除数据库对象。
- **TRUNCATE**：清空表数据（保留结构）。

### 原理

SQL 的设计有几个关键特点：

**1. 非过程化语言**：用户只需说明"做什么"，不需说明"怎么做"。具体的执行路径由 DBMS 的查询优化器决定。这使得 SQL 简洁易学，同时保持高效。

**2. 面向集合**：SQL 操作的对象是集合（表），而非单条记录。一条 SQL 语句可以同时处理多行数据，这与过程化语言逐条处理形成对比。

**3. 数据类型系统**：每种 DBMS 提供丰富的数据类型，常见包括：
- 数值类型：INT, SMALLINT, DECIMAL(p,s), FLOAT, DOUBLE
- 字符类型：CHAR(n) 定长, VARCHAR(n) 变长, TEXT 长文本
- 日期时间：DATE, TIME, DATETIME, TIMESTAMP
- 二进制：BLOB, BINARY
- 布尔：BOOLEAN

**4. 完整性约束**：DDL 通过约束保证数据正确性：
- `NOT NULL`：非空约束
- `UNIQUE`：唯一约束
- `PRIMARY KEY`：主键（非空且唯一）
- `FOREIGN KEY`：外键（参照完整性）
- `CHECK`：检查约束（满足条件）
- `DEFAULT`：默认值

约束可在列级或表级定义。列级约束跟在列定义后，表级约束在所有列定义之后单独定义，常用于复合主键和多列约束。

### 例子

**1. 创建数据库与表**

```sql
-- 创建数据库
CREATE DATABASE University
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;

USE University;

-- 创建学生表（含各种约束）
CREATE TABLE Student (
    Sno       CHAR(5)     PRIMARY KEY
                           COMMENT '学号，主键',
    Sname     VARCHAR(20) NOT NULL
                           COMMENT '姓名',
    Ssex      CHAR(2)     CHECK (Ssex IN ('男', '女')),
    Sage      SMALLINT    CHECK (Sage BETWEEN 15 AND 60),
    Sdept     VARCHAR(20) DEFAULT '未分配'
);

-- 创建课程表
CREATE TABLE Course (
    Cno      CHAR(4)     PRIMARY KEY,
    Cname    VARCHAR(40) NOT NULL,
    Credit   SMALLINT    CHECK (Credit > 0 AND Credit <= 10),
    Cpno     CHAR(4),    -- 先修课
    FOREIGN KEY (Cpno) REFERENCES Course(Cno)  -- 自引用外键
);

-- 创建选课表（复合主键 + 双外键）
CREATE TABLE SC (
    Sno   CHAR(5),
    Cno   CHAR(4),
    Grade DECIMAL(5,2) CHECK (Grade BETWEEN 0 AND 100),
    PRIMARY KEY (Sno, Cno),
    FOREIGN KEY (Sno) REFERENCES Student(Sno)
        ON DELETE CASCADE          -- 删学生时级联删除选课
        ON UPDATE CASCADE,
    FOREIGN KEY (Cno) REFERENCES Course(Cno)
        ON DELETE RESTRICT         -- 有选课记录时禁止删课程
);
```

**2. 修改表结构**

```sql
-- 添加列
ALTER TABLE Student ADD COLUMN Email VARCHAR(50) UNIQUE;

-- 修改列类型
ALTER TABLE Student MODIFY COLUMN Sname VARCHAR(50) NOT NULL;

-- 重命名列
ALTER TABLE Student CHANGE COLUMN Sdept Department VARCHAR(30);

-- 添加约束
ALTER TABLE Student ADD CONSTRAINT chk_age CHECK (Sage >= 15);

-- 删除列
ALTER TABLE Student DROP COLUMN Email;
```

**3. 删除与清空**

```sql
-- 清空表数据（保留结构，速度快，不可回滚）
TRUNCATE TABLE SC;

-- 删除表（结构和数据一起删除）
DROP TABLE SC;

-- 删除数据库
DROP DATABASE University;
```

**DROP、DELETE、TRUNCATE 的区别**：

| 操作 | 作用 | 速度 | 可回滚 | 触发器 |
|------|------|------|--------|--------|
| DELETE | 按条件删除行 | 慢（逐行） | 是 | 触发 |
| TRUNCATE | 清空整表 | 快（重置页） | 否 | 不触发 |
| DROP | 删除表对象 | 快 | 否 | 不触发 |

### 总结

- SQL 是关系数据库的标准语言，集 DDL/DML/DCL/TCL 于一体，是非过程化、面向集合的语言。
- DDL 用于定义结构：CREATE 创建、ALTER 修改、DROP 删除、TRUNCATE 清空。
- 数据类型选择要恰当：定长用 CHAR，变长用 VARCHAR，金额用 DECIMAL，避免用浮点存钱。
- 完整性约束是数据正确性的第一道防线：NOT NULL、UNIQUE、PRIMARY KEY、FOREIGN KEY、CHECK、DEFAULT。
- **关键要点**：外键的 ON DELETE/ON UPDATE 策略（CASCADE/RESTRICT/SET NULL/NO ACTION）需根据业务谨慎选择。
- **常见误区**：用 TRUNCATE 误删数据无法回滚；用 FLOAT/DOUBLE 存储金额导致精度丢失。

## 第 6 讲：SQL 进阶——DML 与查询

### 概念

**DML（Data Manipulation Language，数据操纵语言）** 用于操作表中的数据，主要包括：

- **INSERT**：插入数据。
- **UPDATE**：更新数据。
- **DELETE**：删除数据。

**SELECT** 语句虽然常被归为 DQL（数据查询语言），但广义上也属于 DML。SELECT 是 SQL 中最复杂、最强大的语句，本讲重点讲解单表查询。

SELECT 语句的完整语法结构：

```sql
SELECT [DISTINCT] 列名列表
FROM 表名
[WHERE 条件]
[GROUP BY 列名 [HAVING 组条件]]
[ORDER BY 列名 [ASC|DESC]]
[LIMIT 偏移量, 行数];
```

### 原理

**1. SELECT 的执行顺序**

理解执行顺序对正确编写 SQL 至关重要。SQL 的书写顺序与执行顺序不同：

```
书写顺序: SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
执行顺序: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
```

执行顺序解释了为什么 WHERE 中不能用 SELECT 中的别名（此时别名还未生成），而 ORDER BY 中可以使用。

**2. WHERE 条件谓词**

- 比较运算符：=, <>, !=, >, <, >=, <=
- 逻辑运算符：AND, OR, NOT
- 范围：BETWEEN a AND b
- 集合：IN (v1, v2, ...), NOT IN
- 模式匹配：LIKE（% 任意多字符，_ 单字符）
- 空值判断：IS NULL, IS NOT NULL
- 子查询：EXISTS, ANY, ALL

**3. 聚合函数与分组**

聚合函数对一组值进行计算返回单个值：COUNT、SUM、AVG、MAX、MIN。GROUP BY 按指定列分组，HAVING 对分组结果过滤（区别于 WHERE 对行过滤）。

**4. NULL 的特殊处理**

NULL 表示"未知"或"不存在"，参与运算时遵循三值逻辑（TRUE/FALSE/UNKNOWN）。`NULL = NULL` 的结果是 UNKNOWN（视为假），需用 `IS NULL` 判断。聚合函数（除 COUNT(*)）自动忽略 NULL。

### 例子

**1. INSERT 插入数据**

```sql
-- 插入单行（指定列）
INSERT INTO Student(Sno, Sname, Ssex, Sage, Sdept)
VALUES ('S01', '张三', '男', 20, '计算机');

-- 插入单行（全部列，顺序须一致）
INSERT INTO Student
VALUES ('S02', '李四', '女', 21, '数学');

-- 批量插入
INSERT INTO Student VALUES
('S03', '王五', '男', 19, '计算机'),
('S04', '赵六', '女', 22, '物理'),
('S05', '钱七', '男', 20, '计算机');

-- 从其他表插入（INSERT INTO ... SELECT）
INSERT INTO CS_Student(Sno, Sname)
SELECT Sno, Sname FROM Student WHERE Sdept = '计算机';
```

**2. UPDATE 更新数据**

```sql
-- 简单更新
UPDATE Student SET Sage = 21 WHERE Sno = 'S01';

-- 多列更新
UPDATE Student SET Sdept = '软件工程', Sage = Sage + 1
WHERE Sdept = '计算机';

-- 基于子查询的更新
UPDATE SC SET Grade = Grade * 1.05
WHERE Cno = (SELECT Cno FROM Course WHERE Cname = '数据库');
```

**3. DELETE 删除数据**

```sql
-- 条件删除
DELETE FROM SC WHERE Grade IS NULL;

-- 删除全部（保留结构，可回滚，逐行删除）
DELETE FROM SC;
```

**4. SELECT 单表查询**

```sql
-- 投影查询
SELECT Sno, Sname FROM Student;

-- 去重
SELECT DISTINCT Sdept FROM Student;

-- 条件查询
SELECT Sname, Sage FROM Student
WHERE Sdept = '计算机' AND Sage BETWEEN 18 AND 22;

-- 模糊查询：姓"张"且名字两个字
SELECT * FROM Student WHERE Sname LIKE '张_';

-- 排序与分页
SELECT Sno, Sname, Sage FROM Student
ORDER BY Sage DESC, Sno ASC
LIMIT 0, 10;  -- 第1页，每页10条

-- 聚合查询
SELECT Sdept, COUNT(*) AS 人数, AVG(Sage) AS 平均年龄
FROM Student
GROUP BY Sdept
HAVING COUNT(*) > 2
ORDER BY 人数 DESC;
```

**5. NULL 处理示例**

```sql
-- 查询未参加考试的学生（Grade为NULL）
SELECT Sno FROM SC WHERE Grade IS NULL;

-- 用 IFNULL/COALESCE 处理NULL
SELECT Sno, IFNULL(Grade, 0) AS 成绩 FROM SC;

-- COUNT的区别
SELECT
    COUNT(*)          AS 总行数,    -- 包含NULL行
    COUNT(Grade)      AS 非空成绩数, -- 忽略NULL
    COUNT(DISTINCT Sno) AS 不同学生数
FROM SC;
```

### 总结

- DML 操作表数据：INSERT 插入、UPDATE 更新、DELETE 删除，SELECT 查询。
- SELECT 执行顺序：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT，理解这一点能避免很多错误。
- WHERE 过滤行，HAVING 过滤组；WHERE 中不能用聚合函数和 SELECT 别名。
- NULL 遵循三值逻辑，必须用 IS NULL 判断，聚合函数自动忽略 NULL（COUNT(*) 除外）。
- **关键要点**：UPDATE/DELETE 一定要带 WHERE，否则会误操作全表；生产环境建议先用 SELECT 验证条件。
- **常见误区**：在 WHERE 中使用 SELECT 别名（执行顺序问题）；用 `= NULL` 而非 `IS NULL` 判断空值。

## 第 7 讲：SQL 高级——连接、子查询与视图

### 概念

本讲讲解 SQL 的三大高级特性：

**1. 连接查询（JOIN）**：从多个表中按一定条件组合数据，是关系数据库"关系"二字的精髓。连接类型包括内连接（INNER JOIN）、左外连接（LEFT JOIN）、右外连接（RIGHT JOIN）、全外连接（FULL JOIN）、交叉连接（CROSS JOIN）和自连接（Self Join）。

**2. 子查询（Subquery）**：嵌套在其他 SQL 语句中的查询，分为非相关子查询（独立执行）和相关子查询（依赖外层）。子查询可出现在 WHERE、FROM、SELECT 子句中，配合 IN、EXISTS、ANY、ALL 等谓词使用。

**3. 视图（View）**：基于一个或多个表的查询定义的虚拟表，本身不存储数据，只存储查询定义。视图提供逻辑数据独立性、简化查询、保护数据安全。

### 原理

**1. 连接查询的原理**

连接的本质是先计算参与表的笛卡尔积，再按连接条件筛选。优化器会采用嵌套循环、哈希连接、归并连接等算法避免实际计算庞大的笛卡尔积。

- **内连接**：只返回两表中满足连接条件的元组。
- **左外连接**：返回左表所有元组，右表不匹配的填 NULL。
- **右外连接**：返回右表所有元组，左表不匹配的填 NULL。
- **全外连接**：返回两表所有元组，不匹配的填 NULL（MySQL 不直接支持，需用 UNION 模拟）。
- **自连接**：一张表与自己连接，需用别名区分。

**2. 子查询的原理**

- **非相关子查询**：内查询独立于外查询，只执行一次，结果作为外查询的输入。
- **相关子查询**：内查询引用外查询的列，外查询每行都触发一次内查询，效率较低但表达能力强。
- **EXISTS vs IN**：EXISTS 返回布尔值，找到第一条匹配即停止；IN 需要收集所有结果。一般而言，外大内小用 IN，外小内大用 EXISTS。

**3. 视图的原理**

视图是一种"查询快捷方式"。当查询视图时，DBMS 将视图定义与用户查询合并，重写为对基表的查询后执行。因此视图本身不占用存储空间（除物化视图外）。视图的更新有限制：包含聚合、DISTINCT、GROUP BY、JOIN 的视图通常不可更新。

### 例子

**1. 连接查询**

```sql
-- 内连接：查询每个学生及其选课成绩
SELECT Student.Sno, Sname, Cname, Grade
FROM Student
INNER JOIN SC ON Student.Sno = SC.Sno
INNER JOIN Course ON SC.Cno = Course.Cno;

-- 左外连接：查询所有学生及其选课（未选课的显示NULL）
SELECT Student.Sno, Sname, Cno, Grade
FROM Student
LEFT JOIN SC ON Student.Sno = SC.Sno;

-- 自连接：查询与"张三"同系的学生
SELECT S2.Sno, S2.Sname
FROM Student S1
JOIN Student S2 ON S1.Sdept = S2.Sdept
WHERE S1.Sname = '张三' AND S2.Sname <> '张三';
```

**2. 子查询**

```sql
-- 非相关子查询（IN）：查询选修了"数据库"课程的学生
SELECT Sno, Sname FROM Student
WHERE Sno IN (
    SELECT Sno FROM SC
    WHERE Cno = (SELECT Cno FROM Course WHERE Cname = '数据库')
);

-- 相关子查询（EXISTS）：查询选修了全部课程的学生
SELECT Sno, Sname FROM Student S
WHERE NOT EXISTS (
    SELECT * FROM Course C
    WHERE NOT EXISTS (
        SELECT * FROM SC
        WHERE SC.Sno = S.Sno AND SC.Cno = C.Cno
    )
);

-- 子查询在FROM中（派生表）：查询每门课程的选课人数
SELECT Cname, 选课人数
FROM Course C
JOIN (
    SELECT Cno, COUNT(*) AS 选课人数
    FROM SC
    GROUP BY Cno
) T ON C.Cno = T.Cno;

-- 子查询在SELECT中：查询学生及其选课数
SELECT Sname,
       (SELECT COUNT(*) FROM SC WHERE SC.Sno = Student.Sno) AS 选课数
FROM Student;

-- ANY/ALL：查询比计算机系所有学生年龄都大的学生
SELECT Sname, Sage FROM Student
WHERE Sage > ALL (
    SELECT Sage FROM Student WHERE Sdept = '计算机'
);
```

**3. 视图**

```sql
-- 创建视图：计算机系学生视图
CREATE VIEW CS_Student AS
SELECT Sno, Sname, Sage FROM Student
WHERE Sdept = '计算机'
WITH CHECK OPTION;  -- 通过视图插入/更新时必须满足WHERE条件

-- 创建视图：学生成绩视图（多表连接）
CREATE VIEW Student_Grade AS
SELECT Student.Sno, Sname, Cname, Grade
FROM Student
JOIN SC ON Student.Sno = SC.Sno
JOIN Course ON SC.Cno = Course.Cno;

-- 使用视图（像普通表一样查询）
SELECT * FROM CS_Student WHERE Sage > 20;
SELECT Sname, AVG(Grade) AS 平均分
FROM Student_Grade
GROUP BY Sno, Sname
HAVING AVG(Grade) >= 80;

-- 通过可更新视图修改数据
UPDATE CS_Student SET Sage = Sage + 1 WHERE Sno = 'S01';

-- 删除视图
DROP VIEW CS_Student;
```

### 总结

- 连接查询是关系数据库的核心，掌握内连接、外连接、自连接的区别与使用场景。
- 子查询分为相关与非相关，相关子查询效率较低但表达能力强；EXISTS 适合"存在性"判断，IN 适合"集合成员"判断。
- 视图是虚拟表，提供逻辑独立性、简化查询、安全保护；可更新视图有限制条件。
- **关键要点**：左外连接保留左表全部行，是实际开发中最常用的外连接类型。
- **常见误区**：混淆 INNER JOIN 和 LEFT JOIN 导致遗漏数据；在视图上随意更新导致基表数据异常；滥用相关子查询导致性能问题。

# 第 3 章 数据库设计与规范化

数据库设计是数据库应用的核心环节。好的设计能让系统高效、易维护、少出错；差的设计会导致数据冗余、更新异常、性能低下。本章讲解从需求分析到物理设计的完整流程，重点是 ER 建模和规范化理论。

---

## 第 8 讲：ER 模型与概念设计

### 概念

**ER 模型（Entity-Relationship Model，实体-联系模型）** 由 P.P.Chen 于 1976 年提出，是概念模型的主流表示方法。它用图形化的方式描述现实世界的实体、属性及其联系，与具体的 DBMS 无关，是数据库概念设计阶段的核心工具。

ER 模型的三个基本要素：

- **实体（Entity）**：客观存在并可相互区别的事物，如学生、课程、订单。在 ER 图中用**矩形**表示。
- **属性（Attribute）**：实体所具有的某一特性，如学生的姓名、年龄。在 ER 图中用**椭圆**表示，并用无向边与实体相连。
- **联系（Relationship）**：实体之间的关联，如学生与课程的"选修"联系。在 ER 图中用**菱形**表示，用无向边与相关实体相连，边上标注联系类型。

联系有三种基数：**1:1**（一对一）、**1:N**（一对多）、**M:N**（多对多）。例如，校长与学校是 1:1，班级与学生是 1:N，学生与课程是 M:N。

### 原理

**1. ER 图的绘制规则**

ER 图用统一的符号体系表达概念模型。实体集是同类型实体的集合，用矩形表示；属性用椭圆表示，主键属性下加下划线；联系用菱形表示，联系也可以有自己的属性（多对多联系的属性尤其常见）。

**2. 联系的转换规则**

ER 模型向关系模式转换时遵循以下规则：

- **实体** → 一张表，实体的属性即表的列，实体的码即表的主键。
- **1:1 联系** → 可在任一表加入对方主键作为外键，也可独立成表。
- **1:N 联系** → 在 N 端表加入 1 端主键作为外键。
- **M:N 联系** → 必须独立成一张新表，主键由两端实体的码组合而成，联系自身的属性作为非主属性。

**3. 概念设计的步骤**

1. **需求分析**：明确用户需求，收集数据项、数据流、业务规则。
2. **抽象数据**：将需求抽象为实体、属性、联系。
3. **绘制局部 ER 图**：为每个子系统或业务模块绘制局部 ER 图。
4. **合并 ER 图**：解决冲突（属性冲突、命名冲突、结构冲突），生成全局 ER 图。
5. **优化 ER 图**：消除冗余属性和冗余联系。

### 例子

**场景**：设计一个简易教务系统的概念模型，包含学生、课程、教师、院系四个实体。

**1. 识别实体与属性**

- 学生（**学号**, 姓名, 性别, 年龄）
- 课程（**课程号**, 课程名, 学分）
- 教师（**工号**, 姓名, 职称）
- 院系（**院系号**, 院系名, 电话）

**2. 识别联系**

- 学生—选修—课程（M:N），联系有属性"成绩"
- 教师—讲授—课程（M:N），联系有属性"学期"
- 院系—拥有—学生（1:N）
- 院系—聘用—教师（1:N）

**3. ER 图（文字描述）**

```
[院系]——(拥有,1:N)——[学生]——(选修,M:N,属性:成绩)——[课程]
   |                                                    |
(聘用,1:N)                                          (讲授,M:N,属性:学期)
   |                                                    |
[教师]——————————————————————————————————————————————————
```

**4. 转换为关系模式**

```sql
-- 实体表
Department(Dno, Dname, Tel)              -- 院系
Student(Sno, Sname, Ssex, Sage, Dno)     -- 学生，Dno为外键（1:N）
Teacher(Tno, Tname, Title, Dno)          -- 教师，Dno为外键（1:N）
Course(Cno, Cname, Credit)               -- 课程

-- M:N联系转独立表
SC(Sno, Cno, Grade)                      -- 选课，主键(Sno,Cno)
TC(Tno, Cno, Term)                       -- 授课，主键(Tno,Cno,Term)
```

**5. 完整 SQL 实现**

```sql
CREATE TABLE Department (
    Dno   CHAR(4) PRIMARY KEY,
    Dname VARCHAR(30) NOT NULL,
    Tel   VARCHAR(15)
);

CREATE TABLE Student (
    Sno   CHAR(5) PRIMARY KEY,
    Sname VARCHAR(20) NOT NULL,
    Ssex  CHAR(2),
    Sage  SMALLINT,
    Dno   CHAR(4),
    FOREIGN KEY (Dno) REFERENCES Department(Dno)
);

CREATE TABLE Teacher (
    Tno   CHAR(5) PRIMARY KEY,
    Tname VARCHAR(20) NOT NULL,
    Title VARCHAR(20),
    Dno   CHAR(4),
    FOREIGN KEY (Dno) REFERENCES Department(Dno)
);

CREATE TABLE Course (
    Cno    CHAR(4) PRIMARY KEY,
    Cname  VARCHAR(40) NOT NULL,
    Credit SMALLINT
);

CREATE TABLE SC (
    Sno   CHAR(5),
    Cno   CHAR(4),
    Grade DECIMAL(5,2),
    PRIMARY KEY (Sno, Cno),
    FOREIGN KEY (Sno) REFERENCES Student(Sno),
    FOREIGN KEY (Cno) REFERENCES Course(Cno)
);

CREATE TABLE TC (
    Tno  CHAR(5),
    Cno  CHAR(4),
    Term VARCHAR(10),
    PRIMARY KEY (Tno, Cno, Term),
    FOREIGN KEY (Tno) REFERENCES Teacher(Tno),
    FOREIGN KEY (Cno) REFERENCES Course(Cno)
);
```

### 总结

- ER 模型是概念设计的核心工具，三要素：实体（矩形）、属性（椭圆）、联系（菱形）。
- 联系基数有 1:1、1:N、M:N 三种，决定了关系模式转换的方式。
- M:N 联系必须独立成表，主键由两端实体码组合而成。
- 概念设计步骤：需求分析 → 抽象数据 → 局部 ER 图 → 合并全局 ER 图 → 优化。
- **关键要点**：合并 ER 图时需解决三类冲突——属性冲突（类型不同）、命名冲突（同名异义/异名同义）、结构冲突（同一实体在不同图属性数不同）。
- **常见误区**：把 M:N 联系直接放在某一端表里（导致大量冗余）；忽略联系自身的属性（如选课的成绩）。

## 第 9 讲：函数依赖与范式

### 概念

**规范化理论** 由 E.F.Codd 提出，是数据库设计的理论基础。其核心思想是通过分解关系模式消除不合适的数据依赖，解决数据冗余和更新异常问题。

**函数依赖（Functional Dependency, FD）** 是规范化理论的核心概念。设 R(U) 是属性集 U 上的关系模式，X、Y 是 U 的子集。若对于 R 的任意关系 r，r 中不可能有两个元组在 X 上的属性值相等而在 Y 上的属性值不等，则称"X 函数确定 Y"或"Y 函数依赖于 X"，记作 X → Y。

函数依赖的分类：

- **平凡函数依赖**：X → Y 且 Y ⊆ X。如 (Sno, Cno) → Sno。
- **非平凡函数依赖**：X → Y 且 Y ⊈ X。如 Sno → Sname。
- **完全函数依赖**：X → Y 且对 X 的任何真子集 X' 都有 X' ↛ Y。记作 X →(F) Y。如 (Sno, Cno) →(F) Grade。
- **部分函数依赖**：X → Y 但不是完全函数依赖。记作 X →(P) Y。如 (Sno, Cno) →(P) Sname（Sname 只依赖 Sno）。
- **传递函数依赖**：X → Y（Y ↛ X），Y → Z，则 X →(传递) Z。如 Sno → Sdept → Dname。

**范式（Normal Form, NF）** 是符合某一级别的关系模式的集合。Codd 提出了 1NF、2NF、3NF，后来 Boyce 和 Codd 提出了 BCNF，再后来又有 4NF、5NF 等。

### 原理

**1. 第一范式（1NF）**

**定义**：关系模式 R 的所有属性都是不可分的基本数据项（即属性值是原子的）。

1NF 是关系的基本要求。违反 1NF 的典型情况是"表中有表"，如"电话"字段包含多个号码。解决方法是拆分为多行或拆分为多列。

**2. 第二范式（2NF）**

**定义**：R ∈ 1NF，且每个非主属性完全函数依赖于候选码（不存在非主属性对码的部分函数依赖）。

2NF 解决的问题是：在复合码的情况下，非主属性只依赖码的一部分，导致数据冗余和更新异常。

**3. 第三范式（3NF）**

**定义**：R ∈ 2NF，且每个非主属性都不传递函数依赖于候选码（不存在非主属性对码的传递依赖）。

3NF 解决的问题是：非主属性通过其他非主属性间接依赖码，导致冗余和更新异常。

**4. BCNF（Boyce-Codd 范式）**

**定义**：R ∈ 1NF，且对于每一个非平凡函数依赖 X → Y，X 都包含候选码（即每个决定因素都包含码）。

BCNF 是 3NF 的加强版，解决了 3NF 中主属性对码的部分和传递依赖问题。

**规范化与反规范化**：规范化消除冗余但增加连接开销；反规范化（Denormalization）为提升查询性能适度增加冗余。实际应用中常在 3NF 基础上适度反规范化。

### 例子

**反例**：设关系模式 SCD(Sno, Cno, Sname, Sdept, Dname, Grade)，其中 Sno 学号、Cno 课程号、Sname 姓名、Sdept 院系、Dname 院系主任、Grade 成绩。

函数依赖：
- (Sno, Cno) → Grade（完全依赖）
- Sno → Sname, Sdept（部分依赖，因 Sname、Sdept 只依赖 Sno）
- Sdept → Dname（传递依赖：Sno → Sdept → Dname）

**问题分析**：

| 异常类型 | 具体表现 |
|---------|---------|
| 数据冗余 | 学生的姓名、院系、院系主任在每条选课记录中重复存储 |
| 插入异常 | 学生未选课时无法插入学生信息（码不能为空） |
| 删除异常 | 删除学生所有选课记录会丢失学生基本信息 |
| 更新异常 | 修改院系主任需更新多行，遗漏会导致数据不一致 |

**规范化过程**：

**第 1 步：消除部分依赖，达到 2NF**

将 SCD 分解为：
- SC(Sno, Cno, Grade) —— 选课表
- SD(Sno, Sname, Sdept, Dname) —— 学生表

**第 2 步：消除传递依赖，达到 3NF**

将 SD 进一步分解为：
- Student(Sno, Sname, Sdept) —— 学生表
- Department(Sdept, Dname) —— 院系表

**最终结果**（3NF）：

```sql
-- 院系表
CREATE TABLE Department (
    Dno    CHAR(4) PRIMARY KEY,
    Dname  VARCHAR(30) NOT NULL,
    Dean   VARCHAR(20)
);

-- 学生表
CREATE TABLE Student (
    Sno    CHAR(5) PRIMARY KEY,
    Sname  VARCHAR(20) NOT NULL,
    Dno    CHAR(4),
    FOREIGN KEY (Dno) REFERENCES Department(Dno)
);

-- 课程表
CREATE TABLE Course (
    Cno    CHAR(4) PRIMARY KEY,
    Cname  VARCHAR(40) NOT NULL,
    Credit SMALLINT
);

-- 选课表
CREATE TABLE SC (
    Sno   CHAR(5),
    Cno   CHAR(4),
    Grade DECIMAL(5,2),
    PRIMARY KEY (Sno, Cno),
    FOREIGN KEY (Sno) REFERENCES Student(Sno),
    FOREIGN KEY (Cno) REFERENCES Course(Cno)
);
```

**规范化前后对比**：

| 指标 | 规范化前 SCD | 规范化后 4 张表 |
|------|------------|---------------|
| 数据冗余 | 严重（姓名、院系重复） | 无 |
| 插入异常 | 有 | 无 |
| 删除异常 | 有 | 无 |
| 更新异常 | 有 | 无 |
| 查询复杂度 | 简单（单表查询） | 较高（多表连接） |

### 总结

- 函数依赖是规范化的理论基础，分为平凡/非平凡、完全/部分、传递依赖。
- 范式层次：1NF（原子性）→ 2NF（消除部分依赖）→ 3NF（消除传递依赖）→ BCNF（每个决定因素含码）。
- 规范化解决四大问题：数据冗余、插入异常、删除异常、更新异常。
- 实际工程中通常达到 3NF 即可，BCNF 在主属性依赖复杂时考虑。
- **关键要点**：1NF 是关系的最低要求，2NF 针对复合码，3NF 针对传递依赖，BCNF 是 3NF 的强化。
- **常见误区**：盲目追求高范式导致过度分解、查询性能下降；忽视反规范化在 OLAP 场景中的必要性。

## 第 10 讲：数据库设计实践

### 概念

**数据库设计** 是指对于一个给定的应用环境，构造优化的数据库模式，建立数据库及其应用系统，使之能有效地存储和管理数据，满足用户的应用需求。数据库设计是软件工程的重要分支，其质量直接影响系统的性能、可维护性和扩展性。

数据库设计的六个阶段：

1. **需求分析**：调查用户需求，明确数据需求和处理需求。
2. **概念结构设计**：将需求抽象为独立于 DBMS 的概念模型（ER 图）。
3. **逻辑结构设计**：将概念模型转换为特定 DBMS 的逻辑模型（关系模式）。
4. **物理结构设计**：选择存储结构和存取方法（索引、聚簇等）。
5. **数据库实施**：用 DDL 建库建表，加载数据，编写应用。
6. **数据库运行与维护**：监控性能，调整优化，备份恢复。

### 原理

**1. 需求分析的方法**

需求分析的核心是数据字典和数据流图（DFD）。数据字典详细描述数据项、数据结构、数据流、数据存储和处理过程。需求分析要充分调研，避免"边设计边改"导致返工。

**2. 概念设计的策略**

- **自顶向下**：先全局框架，再逐步细化。适合需求清晰的项目。
- **自底向上**：先局部 ER 图，再合并。适合需求分散的大型项目。
- **混合策略**：先自顶向下规划范围，再自底向上设计。

**3. 逻辑设计的优化**

将 ER 图转换为关系模式后，需进行规范化处理（达到 3NF 或 BCNF）。同时考虑：
- 是否合并某些关系（如 1:1 联系可合并到任一端）。
- 是否保留必要的冗余（如统计字段）以提升查询性能。
- 是否增加派生属性（如总价 = 单价 × 数量）。

**4. 物理设计的考量**

- **索引设计**：高频查询条件列、连接列、排序分组列建索引；写多读少的表少建索引。
- **聚簇**：将相关数据物理上相邻存储，提升范围查询性能。
- **分区**：大表按范围、列表、哈希分区，提升并行处理能力。
- **存储引擎选择**：MySQL 的 InnoDB（事务安全）vs MyISAM（查询优先）。

### 例子

**完整案例**：设计一个在线书店数据库。

**1. 需求分析**

- 用户可注册、浏览图书、下单、支付、评价。
- 管理员可管理图书、订单、用户。
- 需统计销量、库存、用户消费等。

**2. 概念设计（ER 图核心要素）**

实体：用户、图书、订单、订单明细、分类、评价
联系：
- 用户—下单—订单（1:N）
- 订单—包含—图书（M:N，通过订单明细）
- 图书—属于—分类（N:1）
- 用户—评价—图书（M:N，带评分和评论）

**3. 逻辑设计（关系模式）**

```sql
-- 用户表
CREATE TABLE users (
    user_id    BIGINT PRIMARY KEY AUTO_INCREMENT,
    username   VARCHAR(50) NOT NULL UNIQUE,
    password   VARCHAR(64) NOT NULL,
    email      VARCHAR(100) UNIQUE,
    phone      VARCHAR(20),
    address    VARCHAR(200),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 分类表（自引用，支持多级分类）
CREATE TABLE categories (
    category_id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name        VARCHAR(50) NOT NULL,
    parent_id   BIGINT,
    FOREIGN KEY (parent_id) REFERENCES categories(category_id)
);

-- 图书表
CREATE TABLE books (
    book_id     BIGINT PRIMARY KEY AUTO_INCREMENT,
    title       VARCHAR(100) NOT NULL,
    author      VARCHAR(50),
    isbn        VARCHAR(20) UNIQUE,
    price       DECIMAL(10,2) NOT NULL,
    stock       INT DEFAULT 0,
    category_id BIGINT,
    description TEXT,
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (category_id) REFERENCES categories(category_id),
    INDEX idx_title (title),           -- 书名索引
    INDEX idx_category (category_id)   -- 分类索引
);

-- 订单表
CREATE TABLE orders (
    order_id    BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id     BIGINT NOT NULL,
    total_amount DECIMAL(10,2) NOT NULL,
    status      VARCHAR(20) DEFAULT 'pending',  -- pending/paid/shipped/done
    address     VARCHAR(200),
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(user_id),
    INDEX idx_user (user_id),
    INDEX idx_status_created (status, created_at)
);

-- 订单明细表（订单与图书的M:N联系）
CREATE TABLE order_items (
    order_id BIGINT,
    book_id  BIGINT,
    quantity INT NOT NULL,
    price    DECIMAL(10,2) NOT NULL,  -- 下单时价格快照
    PRIMARY KEY (order_id, book_id),
    FOREIGN KEY (order_id) REFERENCES orders(order_id),
    FOREIGN KEY (book_id) REFERENCES books(book_id)
);

-- 评价表（用户与图书的M:N联系）
CREATE TABLE reviews (
    review_id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id   BIGINT NOT NULL,
    book_id   BIGINT NOT NULL,
    rating    TINYINT CHECK (rating BETWEEN 1 AND 5),
    content   TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(user_id),
    FOREIGN KEY (book_id) REFERENCES books(book_id),
    UNIQUE (user_id, book_id)  -- 一个用户对一本书只能评一次
);
```

**4. 设计要点说明**

- **价格快照**：order_items 中存储下单时的 price，避免图书价格变动影响历史订单。
- **复合索引**：`idx_status_created (status, created_at)` 支持"按状态和时间查询订单"。
- **自引用外键**：categories 表的 parent_id 支持多级分类树。
- **唯一约束**：reviews 的 (user_id, book_id) 唯一，防止重复评价。
- **软删除考虑**：实际项目可增加 `is_deleted` 字段实现软删除，避免物理删除导致外键冲突。

### 总结

- 数据库设计六阶段：需求分析 → 概念设计 → 逻辑设计 → 物理设计 → 实施 → 运行维护。
- 概念设计用 ER 模型，逻辑设计转换为关系模式并规范化，物理设计考虑索引、分区、存储引擎。
- 设计要兼顾规范化和性能：3NF 为基础，必要时适度反规范化。
- 关键设计技巧：价格快照、复合索引、自引用外键、软删除、唯一约束。
- **关键要点**：需求分析是设计的基石，投入 30% 时间在需求分析上能节省 70% 的返工成本。
- **常见误区**：跳过需求分析直接建表；忽视索引设计导致查询慢；过度规范化导致多表 JOIN 性能差；忘记存储历史快照导致数据不一致。

# 第 4 章 数据库内部原理

理解数据库内部原理是成为高级数据库工程师的必经之路。本章深入讲解存储结构、索引、查询优化、事务并发控制和恢复机制，揭示数据库"黑盒"背后的工作机制。

## 第 11 讲：存储结构与索引

### 概念

**存储结构** 是数据库在磁盘上组织数据的方式。数据库以**页（Page）** 为基本存储单位（MySQL InnoDB 默认 16KB，PostgreSQL 默认 8KB），页是磁盘 I/O 的最小单位。页组成**区（Extent）**（通常 1MB），区组成**段（Segment）**。

**索引（Index）** 是一种独立于表数据的辅助数据结构，用于加速查询。索引的本质是"用空间换时间"，通过维护有序的索引项，将查找从 O(n) 降为 O(log n) 甚至 O(1)。

索引的主要类型：

- **B+树索引**：最常用的索引结构，所有数据存储在叶子节点，叶子节点用链表相连，支持范围查询。
- **哈希索引**：基于哈希表，只支持等值查询，不支持范围查询和排序。
- **全文索引**：用于文本搜索，支持分词和倒排索引。
- **空间索引（R-Tree）**：用于地理空间数据查询。
- **聚簇索引（Clustered Index）**：数据按索引键的顺序物理存储，一张表只能有一个。
- **非聚簇索引（Secondary Index）**：索引存储主键值，需"回表"查询数据。

### 原理

**1. B+树的结构与优势**

B+树是 B 树的变种，是关系数据库索引的主流结构。其特点：

- 所有数据都存储在叶子节点，非叶子节点只存储索引键用于路由。
- 叶子节点通过双向链表相连，支持高效的范围查询和排序。
- 树的高度通常为 3-4 层，即可存储千万级数据，每次查询只需 3-4 次磁盘 I/O。

以 InnoDB 为例，假设主键为 BIGINT（8 字节），指针 6 字节，每页 16KB 可存约 1170 个索引项。三层 B+树可存储 1170 × 1170 × 16 ≈ 2000 万行数据。

**2. 聚簇索引 vs 非聚簇索引**

- **聚簇索引**：叶子节点直接存储整行数据。InnoDB 的主键索引就是聚簇索引，"索引即数据"。一张表只能有一个聚簇索引。
- **非聚簇索引（二级索引）**：叶子节点存储索引键和主键值。查询时若需要的列不在索引中，需用主键回表查询聚簇索引。

**3. 索引的代价**

- **空间代价**：每个索引都是一棵 B+树，占用磁盘空间。
- **写入代价**：INSERT/UPDATE/DELETE 需同步维护索引，降低写性能。
- **优化器代价**：索引过多会增加优化器选择执行计划的成本。

**4. 索引失效的常见场景**

- 在索引列上使用函数或运算：`WHERE YEAR(date_col) = 2024`
- 隐式类型转换：字符串列用数字查询 `WHERE str_col = 123`
- 使用 `LIKE '%xxx'`（前导通配符）
- 使用 `OR` 连接非索引列
- 不符合最左前缀原则（复合索引）

### 例子

**1. 创建各类索引**

```sql
-- 创建表时定义主键（自动创建聚簇索引）
CREATE TABLE employees (
    emp_id     BIGINT PRIMARY KEY,           -- 聚簇索引
    emp_name   VARCHAR(50) NOT NULL,
    dept_id    INT,
    salary     DECIMAL(10,2),
    hire_date  DATE,
    email      VARCHAR(100)
);

-- 创建唯一索引
CREATE UNIQUE INDEX idx_email ON employees(email);

-- 创建普通索引
CREATE INDEX idx_name ON employees(emp_name);

-- 创建复合索引（注意列顺序，遵循最左前缀原则）
CREATE INDEX idx_dept_salary ON employees(dept_id, salary);

-- 创建前缀索引（长字符串列）
CREATE INDEX idx_email_prefix ON employees(email(10));

-- 创建函数索引（MySQL 8.0+ / PostgreSQL）
CREATE INDEX idx_hire_year ON employees((YEAR(hire_date)));
```

**2. 复合索引的最左前缀原则**

复合索引 `(dept_id, salary)` 的 B+树先按 dept_id 排序，相同 dept_id 内按 salary 排序。因此：

```sql
-- 能命中索引
SELECT * FROM employees WHERE dept_id = 10;
SELECT * FROM employees WHERE dept_id = 10 AND salary > 5000;
SELECT * FROM employees WHERE dept_id = 10 ORDER BY salary;

-- 不能命中索引（缺少最左列dept_id）
SELECT * FROM employees WHERE salary > 5000;

-- 部分命中（dept_id命中，salary因范围查询后无法用索引排序）
SELECT * FROM employees WHERE dept_id > 10 AND salary > 5000;
```

**3. 覆盖索引避免回表**

```sql
-- 复合索引 idx_dept_salary(dept_id, salary)
-- 查询1：需要回表（SELECT * 需要所有列）
SELECT * FROM employees WHERE dept_id = 10;
-- 执行：查idx_dept_salary得到主键 → 回表查聚簇索引得到整行

-- 查询2：覆盖索引（只需索引列）
SELECT dept_id, salary FROM employees WHERE dept_id = 10;
-- 执行：直接从idx_dept_salary获取结果，无需回表
```

**4. 用 EXPLAIN 分析索引使用**

```sql
EXPLAIN SELECT * FROM employees WHERE dept_id = 10 AND salary > 5000;
```

输出关键字段：

| 字段 | 含义 | 关注点 |
|------|------|--------|
| type | 访问类型 | system > const > eq_ref > ref > range > index > ALL |
| key | 实际使用的索引 | NULL 表示未用索引 |
| rows | 预估扫描行数 | 越小越好 |
| Extra | 额外信息 | Using index（覆盖索引）、Using filesort（额外排序）、Using temporary（临时表） |

### 总结

- 数据库以页为基本存储单位，B+树是索引的主流结构，3-4 层即可存储千万级数据。
- 聚簇索引"索引即数据"，一张表只有一个；非聚簇索引需回表查询。
- 复合索引遵循最左前缀原则，列顺序应按"等值查询列 → 范围查询列 → 排序列"排列。
- 索引有空间和写入代价，不是越多越好，需根据查询模式设计。
- **关键要点**：覆盖索引能避免回表，是性能优化的利器；EXPLAIN 是分析 SQL 执行计划的必备工具。
- **常见误区**：在索引列上使用函数导致索引失效；为所有列建索引忽视写入代价；忽视复合索引列顺序。

## 第 12 讲：查询处理与优化

### 概念

**查询处理** 是 DBMS 执行 SQL 语句的过程，包括解析、优化、执行三个阶段。**查询优化** 是其中最关键的环节，目标是选择代价最小的执行计划。

查询处理的三个阶段：

1. **解析（Parser）**：词法分析、语法分析、语义检查，将 SQL 转换为解析树。
2. **优化（Optimizer）**：基于规则（RBO）或代价（CBO）选择最优执行计划。
3. **执行（Executor）**：按执行计划调用存储引擎接口获取数据。

**查询优化器** 分为两类：

- **基于规则的优化器（RBO, Rule-Based Optimizer）**：根据预设规则选择执行计划，如"有索引就用索引"。简单但不够智能。
- **基于代价的优化器（CBO, Cost-Based Optimizer）**：估算不同执行计划的代价（CPU + I/O），选择代价最小的。现代数据库主要采用 CBO。

### 原理

**1. 关系代数等价变换**

优化器利用关系代数的等价变换规则重写查询，常见规则：

- **选择下推**：将选择操作尽可能下移到叶子节点，提前过滤减少数据量。`σ_F(R ⋈ S) = σ_F(R) ⋈ S`（当 F 只涉及 R 时）。
- **投影下推**：尽早投影减少列数。
- **连接顺序优化**：多表连接时选择最优连接顺序，n 个表有 n! 种顺序。
- **子查询展开**：将相关子查询重写为连接。

**2. 连接算法**

- **嵌套循环连接（Nested Loop Join）**：对外表每行扫描内表全部。简单但慢，适合小表驱动大表。
- **块嵌套循环（Block Nested Loop）**：按块读取外表，减少内表扫描次数。
- **索引嵌套循环（Index Nested Loop）**：内表有索引时，用索引查找代替全表扫描。
- **哈希连接（Hash Join）**：构建小表的哈希表，扫描大表探测。适合等值连接，无索引时性能好。
- **归并连接（Merge Join）**：两表按连接键排序后归并。适合已排序数据。

**3. 代价估算模型**

CBO 估算代价主要考虑：

- **I/O 代价**：磁盘读取页数。
- **CPU 代价**：记录处理、比较、计算成本。
- **统计信息**：表的行数、列的基数（不同值数量）、直方图、索引高度等。

代价 = I/O 代价 + CPU 代价。优化器选择总代价最小的计划。

**4. 执行计划的数据访问方式**

从优到劣：`const`（主键/唯一索引等值）> `eq_ref`（连接使用主键/唯一索引）> `ref`（非唯一索引等值）> `range`（索引范围扫描）> `index`（索引全扫描）> `ALL`（全表扫描）。

### 例子

**1. 选择下推示例**

查询：查询计算机系学生选修数据库课程的成绩。

```sql
-- 原始写法（优化器自动下推）
SELECT s.Sname, c.Cname, sc.Grade
FROM Student s
JOIN SC ON s.Sno = sc.Sno
JOIN Course c ON sc.Cno = c.Cno
WHERE s.Sdept = '计算机' AND c.Cname = '数据库';
```

优化器等价变换为：

```
σ_Sdept='计算机'(Student)  ⋈  σ_Cname='数据库'(Course)  ⋈  SC
```

先过滤再连接，大幅减少连接的数据量。

**2. 连接顺序优化**

查询：3 张表连接，A(100行)、B(10000行)、C(1000000行)。

```
方案1: A ⋈ B ⋈ C  → 100 × 10000 × 1000000 = 10^12 次比较
方案2: A ⋈ C ⋈ B  → 100 × 1000000 × 10000 = 10^12 次比较
方案3: (A ⋈ B) ⋈ C → 先A⋈B得小结果集，再与C连接
```

优化器会选择"小表驱动大表"的顺序，先连接小表。

**3. 用 EXPLAIN 分析执行计划**

```sql
EXPLAIN
SELECT s.Sname, sc.Grade
FROM Student s
JOIN SC ON s.Sno = sc.Sno
WHERE s.Sdept = '计算机' AND sc.Grade > 80;
```

可能的输出：

```
+----+-------------+-------+------+---------------+---------+---------+-------------------+------+-------------+
| id | select_type | table | type | possible_keys | key     | key_len | ref               | rows | Extra       |
+----+-------------+-------+------+---------------+---------+---------+-------------------+------+-------------+
|  1 | SIMPLE      | s     | ALL  | PRIMARY       | NULL    | NULL    | NULL              | 1000 | Using where |
|  1 | SIMPLE      | sc    | ref  | PRIMARY       | PRIMARY | 5       | school.s.Sno      |   10 | Using where |
+----+-------------+-------+------+---------------+---------+---------+-------------------+------+-------------+
```

分析：Student 表全表扫描（type=ALL），SC 表用主键索引（type=ref）。若 Student 表大，应在 Sdept 上建索引。

**4. 常见优化技巧**

```sql
-- 优化1：避免 SELECT *，只查需要的列
-- 慢
SELECT * FROM employees WHERE dept_id = 10;
-- 快
SELECT emp_id, emp_name FROM employees WHERE dept_id = 10;

-- 优化2：用 IN 替代 OR（OR可能导致索引失效）
-- 慢
SELECT * FROM employees WHERE dept_id = 10 OR dept_id = 20;
-- 快
SELECT * FROM employees WHERE dept_id IN (10, 20);

-- 优化3：用 LIMIT 限制结果集
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20;

-- 优化4：分页优化（深分页用延迟关联）
-- 慢（深分页扫描大量行）
SELECT * FROM orders LIMIT 1000000, 20;
-- 快（先用索引查主键，再关联）
SELECT * FROM orders o
JOIN (SELECT order_id FROM orders ORDER BY created_at LIMIT 1000000, 20) t
ON o.order_id = t.order_id;

-- 优化5：用 EXISTS 替代 IN（大表场景）
-- 慢
SELECT * FROM orders WHERE user_id IN (SELECT user_id FROM vip_users);
-- 快
SELECT * FROM orders o WHERE EXISTS (SELECT 1 FROM vip_users v WHERE v.user_id = o.user_id);
```

### 总结

- 查询处理三阶段：解析 → 优化 → 执行，优化器是核心。
- 优化器分 RBO（规则）和 CBO（代价），现代数据库主要用 CBO。
- 关系代数等价变换（选择下推、投影下推、连接顺序优化）是优化的理论基础。
- 连接算法：嵌套循环（小表驱动）、哈希连接（等值无索引）、归并连接（已排序）。
- **关键要点**：用 EXPLAIN 分析执行计划，关注 type、key、rows、Extra 四个字段。
- **常见误区**：认为"有索引就一定快"（索引可能失效）；忽视统计信息更新导致 CBO 选错计划；深分页直接 LIMIT 导致性能问题。

## 第 13 讲：事务与并发控制

### 概念

**事务（Transaction）** 是数据库操作的逻辑执行单位，由一组 SQL 语句组成，要么全部执行成功，要么全部不执行。事务是数据库保证数据一致性的核心机制。

事务的 **ACID 特性**：

- **原子性（Atomicity）**：事务是不可分割的工作单位，要么全做要么全不做。
- **一致性（Consistency）**：事务执行前后，数据库从一个一致状态变为另一个一致状态。
- **隔离性（Isolation）**：多事务并发执行时，一个事务的执行不应影响其他事务。
- **持久性（Durability）**：事务提交后，对数据的修改是永久的，即使系统故障也不丢失。

**并发控制** 是 DBMS 管理多事务并发执行的机制，主要解决三类问题：

- **丢失修改（Lost Update）**：两个事务同时读同一数据并修改，一个事务的修改覆盖另一个。
- **脏读（Dirty Read）**：事务读到其他事务未提交的数据。
- **不可重复读（Non-repeatable Read）**：同一事务两次读同一数据，结果不同（其他事务修改了数据）。
- **幻读（Phantom Read）**：同一事务两次执行同一查询，结果集行数不同（其他事务插入/删除了数据）。

### 原理

**1. 事务的隔离级别**

SQL 标准定义了四种隔离级别，隔离性从低到高：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|----------|------|
| 读未提交（Read Uncommitted） | 可能 | 可能 | 可能 |
| 读已提交（Read Committed） | 避免 | 可能 | 可能 |
| 可重复读（Repeatable Read） | 避免 | 避免 | 可能 |
| 串行化（Serializable） | 避免 | 避免 | 避免 |

MySQL InnoDB 默认可重复读，并通过 MVCC + 间隙锁在可重复读级别下也避免了幻读。

**2. 封锁协议**

- **共享锁（S锁，读锁）**：事务读数据时加 S 锁，其他事务可读不可写。
- **排他锁（X锁，写锁）**：事务写数据时加 X 锁，其他事务不可读不可写。
- **三级封锁协议**：
  - 一级：写数据前加 X 锁，事务结束释放——避免丢失修改。
  - 二级：一级 + 读数据前加 S 锁，读后立即释放——避免丢失修改和脏读。
  - 三级：一级 + 读数据前加 S 锁，事务结束释放——避免丢失修改、脏读、不可重复读。

**3. MVCC（多版本并发控制）**

MVCC 通过为每行数据维护多个版本，实现"读不阻塞写，写不阻塞读"。InnoDB 的 MVCC 实现：

- 每行数据隐藏两列：`DB_TRX_ID`（创建/修改它的事务ID）、`DB_ROLL_PTR`（指向 undo log 的指针）。
- 读取时根据事务隔离级别和 Read View 判断哪个版本对当前事务可见。
- 读已提交：每次 SELECT 都生成新 Read View。
- 可重复读：第一次 SELECT 时生成 Read View，整个事务复用。

**4. 死锁与处理**

死锁是两个或多个事务互相等待对方释放锁。处理方式：

- **预防**：一次性封锁法（事务开始时锁定所有需要的数据）、顺序封锁法（按固定顺序加锁）。
- **检测与解除**：等待图检测环，选择代价最小的事务回滚。InnoDB 默认开启死锁检测。

### 例子

**1. 事务的基本使用**

```sql
-- 显式事务
START TRANSACTION;

UPDATE accounts SET balance = balance - 100 WHERE account_id = 'A';
UPDATE accounts SET balance = balance + 100 WHERE account_id = 'B';

-- 检查转账是否合法
SELECT balance FROM accounts WHERE account_id = 'A';
-- 若余额为负，回滚
-- ROLLBACK;

-- 提交事务
COMMIT;
```

**2. 并发问题演示**

设 accounts 表中 A 账户余额为 1000。

**脏读示例**（读未提交级别）：

```
时刻  事务T1                          事务T2
t1    BEGIN;
t2    UPDATE accounts SET balance=balance-100 WHERE id='A';  -- 余额变900
t3                                    BEGIN;
t4                                    SELECT balance FROM accounts WHERE id='A';  -- 读到900（脏读）
t5    ROLLBACK;                       -- 余额恢复1000
t6                                    -- T2基于900做的决策就错了
```

**丢失修改示例**：

```
时刻  事务T1                          事务T2
t1    BEGIN;                          BEGIN;
t2    SELECT balance WHERE id='A';    -- 1000
t3                                    SELECT balance WHERE id='A';  -- 1000
t4    UPDATE balance=balance+100;     -- 1100
t5                                    UPDATE balance=balance+200;   -- 1200（覆盖了T1的修改）
t6    COMMIT;                         COMMIT;
-- 结果：余额1200，丢失了T1的+100
```

**3. 隔离级别设置**

```sql
-- 查看当前隔离级别
SELECT @@transaction_isolation;

-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET GLOBAL TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

**4. 用 SELECT ... FOR UPDATE 加锁**

```sql
-- 行级排他锁，防止并发修改
START TRANSACTION;
SELECT balance FROM accounts WHERE account_id = 'A' FOR UPDATE;
-- 此时其他事务的 FOR UPDATE 会被阻塞
UPDATE accounts SET balance = balance - 100 WHERE account_id = 'A';
COMMIT;
```

**5. 死锁示例**

```
时刻  事务T1                          事务T2
t1    UPDATE accounts SET balance=1 WHERE id='A';  -- 锁A
t2                                    UPDATE accounts SET balance=1 WHERE id='B';  -- 锁B
t3    UPDATE accounts SET balance=1 WHERE id='B';  -- 等待T2释放B
t4                                    UPDATE accounts SET balance=1 WHERE id='A';  -- 等待T1释放A
-- 死锁！InnoDB检测到后回滚代价小的事务
```

### 总结

- 事务是数据库操作的逻辑单位，ACID 是其核心特性。
- 四种隔离级别：读未提交 < 读已提交 < 可重复读 < 串行化，隔离性越高并发性越低。
- 并发问题：丢失修改、脏读、不可重复读、幻读，由低到高级别逐步解决。
- MVCC 实现读写不阻塞，是现代数据库并发控制的主流方案。
- **关键要点**：MySQL 默认可重复读 + MVCC 避免了幻读；锁粒度越小并发越高但开销越大。
- **常见误区**：长事务持锁导致阻塞；忽视死锁检测；误以为可重复读能解决所有并发问题。

## 第 14 讲：恢复与备份

### 概念

**数据库恢复** 是指在系统发生故障后，将数据库从错误状态恢复到某一已知正确状态的过程。恢复机制是数据库保证**持久性**和**一致性**的关键。

**故障类型**：

- **事务故障**：事务内部的逻辑错误或系统错误（如除零、死锁回滚），事务无法继续执行。
- **系统故障**：系统停止运转（如断电、OS 崩溃），内存数据丢失但磁盘数据完好。需重启后回滚未提交事务、重做已提交未落盘事务。
- **介质故障**：磁盘损坏，物理数据丢失。需用备份恢复。
- **计算机病毒**：恶意破坏数据。

**备份类型**：

- **物理备份**：复制数据库文件，速度快，但依赖数据库版本和平台。分为冷备份（停机备份）和热备份（运行中备份）。
- **逻辑备份**：导出 SQL 语句（如 mysqldump），速度慢但跨平台。
- **全量备份**：备份所有数据。
- **增量备份**：只备份自上次备份后变化的数据。
- **日志备份**：备份事务日志，用于点恢复。

### 原理

**1. 日志机制**

- **重做日志（Redo Log）**：记录事务对数据的修改，用于崩溃后重做已提交事务。InnoDB 的 Redo Log 是顺序写，性能高。WAL（Write-Ahead Logging）原则：先写日志再写数据。
- **撤销日志（Undo Log）**：记录修改前的数据，用于回滚未提交事务和实现 MVCC。
- **二进制日志（Binlog）**：MySQL Server 层的日志，记录所有写操作，用于主从复制和点恢复。

**2. 恢复算法**

**ARIES（Algorithm for Recovery and Isolation Exploiting Semantics）** 是经典恢复算法，三阶段：

1. **分析阶段**：扫描日志，确定恢复起点，构建活跃事务表（ATT）和脏页表（DPT）。
2. **重做阶段（REDO）**：从最后一个检查点开始，重做所有事务的修改，恢复到崩溃前的状态。
3. **撤销阶段（UNDO）**：回滚所有未提交事务，保证原子性。

**3. 检查点（Checkpoint）**

检查点机制定期将内存中的脏页刷盘，并在日志中记录检查点。崩溃恢复时只需从最近检查点开始，大幅缩短恢复时间。

**4. 备份策略**

经典策略：**全量备份 + 增量备份 + 日志备份**。

- 每周一次全量备份（如周日 2 点）。
- 每天一次增量备份（周一至周六 2 点）。
- 每小时一次日志备份。

恢复时：恢复最近全量 → 依次恢复增量 → 应用日志到指定时间点。

### 例子

**1. 使用 mysqldump 逻辑备份**

```bash
# 全库备份
mysqldump -u root -p --single-transaction --routines --triggers \
    --all-databases > full_backup.sql

# 单库备份
mysqldump -u root -p --single-transaction school > school_backup.sql

# 仅备份结构
mysqldump -u root -p --no-data school > schema.sql

# 仅备份数据
mysqldump -u root -p --no-create-info school > data.sql
```

`--single-transaction` 保证 InnoDB 一致性备份（使用可重复读快照）。

**2. 恢复逻辑备份**

```bash
# 恢复全库
mysql -u root -p < full_backup.sql

# 恢复单库
mysql -u root -p school < school_backup.sql
```

**3. 使用 Percona XtraBackup 物理热备份**

```bash
# 全量备份
xtrabackup --backup --target-dir=/backup/full -u root -p

# 准备备份（应用日志使其一致）
xtrabackup --prepare --target-dir=/backup/full

# 增量备份
xtrabackup --backup --target-dir=/backup/inc1 \
    --incremental-basedir=/backup/full -u root -p

# 恢复（需停机）
xtrabackup --copy-back --target-dir=/backup/full
```

**4. 基于时间点恢复（PITR）**

场景：误删了一张表，需恢复到删除前。

```bash
# 1. 恢复最近的全量备份
mysql -u root -p < full_backup_20240114.sql

# 2. 查看binlog确定误操作位置
mysqlbinlog --start-datetime="2024-01-15 00:00:00" \
            --stop-datetime="2024-01-15 10:00:00" \
            /var/lib/mysql/mysql-bin.000123 > recovery.sql

# 3. 应用binlog到误操作前
mysql -u root -p < recovery.sql
```

**5. 自动化备份脚本示例**

```bash
#!/bin/bash
# /home/z/my-project/scripts/backup.sh
BACKUP_DIR=/backup/mysql
DATE=$(date +%Y%m%d_%H%M%S)
KEEP_DAYS=7

# 全量备份
mysqldump -u root -p${MYSQL_PWD} --single-transaction --all-databases \
    | gzip > ${BACKUP_DIR}/full_${DATE}.sql.gz

# 清理过期备份
find ${BACKUP_DIR} -name "full_*.sql.gz" -mtime +${KEEP_DAYS} -delete

# 加入crontab: 0 2 * * * /home/z/my-project/scripts/backup.sh
```

### 总结

- 数据库恢复保证持久性和一致性，应对事务故障、系统故障、介质故障三类故障。
- 日志机制：Redo Log（重做）、Undo Log（回滚）、Binlog（复制和点恢复），遵循 WAL 原则。
- ARIES 恢复算法三阶段：分析 → REDO → UNDO。
- 备份策略：全量 + 增量 + 日志，配合检查点缩短恢复时间。
- **关键要点**：定期演练恢复流程，"未测试的备份等于没有备份"。
- **常见误区**：只备份不测试恢复；忽视 binlog 备份导致无法点恢复；备份文件与数据库同机存储。

## 第 15 讲：存储过程、触发器与函数

### 概念

**存储过程（Stored Procedure）** 是一组预编译的 SQL 语句集合，存储在数据库中，可通过名称调用。存储过程接受输入参数、返回输出参数，可包含流程控制语句（IF、WHILE、CASE 等），是数据库端的编程单元。

**函数（Function）** 与存储过程类似，但必须返回一个值，且可在 SQL 语句中直接使用（如 `SELECT func(col) FROM t`）。函数不能执行 DML 操作（部分数据库限制），适合计算和转换。

**触发器（Trigger）** 是与表事件（INSERT、UPDATE、DELETE）关联的特殊存储过程，在事件发生时自动执行。触发器常用于审计日志、级联操作、复杂约束检查。

三者的对比：

| 特性 | 存储过程 | 函数 | 触发器 |
|------|---------|------|--------|
| 调用方式 | 显式 CALL | 嵌入 SQL | 事件自动触发 |
| 返回值 | 可多个 OUT 参数 | 必须返回单值 | 无 |
| 能否执行 DML | 能 | 通常不能 | 能 |
| 使用场景 | 复杂业务逻辑 | 数据转换计算 | 审计、级联、约束 |

### 原理

**1. 存储过程的优势与劣势**

优势：
- **预编译**：首次执行时编译并缓存执行计划，后续调用直接执行，减少解析开销。
- **减少网络流量**：客户端只需传名称和参数，无需传整段 SQL。
- **封装业务逻辑**：复杂业务在数据库端实现，应用层简化。
- **安全控制**：可授权用户执行存储过程而不暴露表。

劣势：
- **可移植性差**：不同数据库的存储过程语法差异大。
- **调试困难**：数据库端调试工具不如应用层丰富。
- **扩展性受限**：业务逻辑集中在数据库，难以水平扩展。
- **版本控制复杂**：存储过程代码管理不如应用代码规范。

**2. 触发器的执行时机与级别**

- **BEFORE**：在事件发生前触发，可修改 NEW 值，用于数据校验和预处理。
- **AFTER**：在事件发生后触发，用于审计和级联操作。
- **行级（FOR EACH ROW）**：每行受影响都触发一次。
- **语句级（FOR EACH STATEMENT）**：每条语句触发一次（MySQL 不支持，PostgreSQL 支持）。

**3. 触发器的注意事项**

- 触发器可能导致递归触发（A 触发 B，B 触发 A），需设置递归深度限制。
- 触发器隐藏了业务逻辑，增加调试难度。
- 大量触发器会降低 DML 性能。
- 触发器中不能使用 COMMIT/ROLLBACK（事务由调用者控制）。

### 例子

**1. 存储过程示例**

```sql
DELIMITER //

-- 转账存储过程
CREATE PROCEDURE TransferFunds(
    IN from_account CHAR(10),
    IN to_account   CHAR(10),
    IN amount       DECIMAL(10,2),
    OUT result      VARCHAR(100)
)
BEGIN
    DECLARE from_balance DECIMAL(10,2);
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SET result = '转账失败：系统异常';
    END;

    START TRANSACTION;

    -- 查询转出账户余额并加锁
    SELECT balance INTO from_balance
    FROM accounts
    WHERE account_id = from_account
    FOR UPDATE;

    -- 检查余额
    IF from_balance < amount THEN
        ROLLBACK;
        SET result = '转账失败：余额不足';
    ELSE
        UPDATE accounts SET balance = balance - amount
        WHERE account_id = from_account;
        UPDATE accounts SET balance = balance + amount
        WHERE account_id = to_account;

        -- 记录转账日志
        INSERT INTO transfer_log(from_acct, to_acct, amount, created_at)
        VALUES (from_account, to_account, amount, NOW());

        COMMIT;
        SET result = '转账成功';
    END IF;
END //

DELIMITER ;

-- 调用存储过程
CALL TransferFunds('A001', 'A002', 500.00, @result);
SELECT @result;
```

**2. 函数示例**

```sql
DELIMITER //

-- 计算学生GPA的函数
CREATE FUNCTION CalculateGPA(p_sno CHAR(5))
RETURNS DECIMAL(3,2)
READS SQL DATA
DETERMINISTIC
BEGIN
    DECLARE gpa DECIMAL(3,2);
    SELECT ROUND(AVG(
        CASE
            WHEN Grade >= 90 THEN 4.0
            WHEN Grade >= 80 THEN 3.0
            WHEN Grade >= 70 THEN 2.0
            WHEN Grade >= 60 THEN 1.0
            ELSE 0.0
        END
    ), 2) INTO gpa
    FROM SC
    WHERE Sno = p_sno AND Grade IS NOT NULL;

    RETURN IFNULL(gpa, 0.00);
END //

DELIMITER ;

-- 在SQL中使用函数
SELECT Sno, Sname, CalculateGPA(Sno) AS GPA
FROM Student
WHERE Sdept = '计算机';
```

**3. 触发器示例**

```sql
DELIMITER //

-- BEFORE INSERT 触发器：数据校验
CREATE TRIGGER trg_check_age
BEFORE INSERT ON Student
FOR EACH ROW
BEGIN
    IF NEW.Sage < 15 OR NEW.Sage > 60 THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = '年龄必须在15-60之间';
    END IF;
    IF NEW.Sname IS NULL OR NEW.Sname = '' THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = '姓名不能为空';
    END IF;
END //

-- AFTER UPDATE 触发器：审计日志
CREATE TRIGGER trg_audit_student
AFTER UPDATE ON Student
FOR EACH ROW
BEGIN
    INSERT INTO student_audit(
        Sno, old_name, new_name, old_age, new_age,
        action, action_time, operator
    )
    VALUES (
        NEW.Sno, OLD.Sname, NEW.Sname, OLD.Sage, NEW.Sage,
        'UPDATE', NOW(), CURRENT_USER()
    );
END //

-- AFTER DELETE 触发器：级联归档
CREATE TRIGGER trg_archive_student
AFTER DELETE ON Student
FOR EACH ROW
BEGIN
    INSERT INTO student_archive(Sno, Sname, Sdept, Sage, archived_at)
    VALUES (OLD.Sno, OLD.Sname, OLD.Sdept, OLD.Sage, NOW());
END //

DELIMITER ;
```


### 总结

- 存储过程是预编译的 SQL 集合，适合封装复杂业务逻辑；函数必须返回值且可在 SQL 中使用；触发器在表事件时自动执行。
- 存储过程优势：预编译、减少网络流量、封装逻辑、安全控制；劣势：可移植性差、调试困难。
- 触发器分 BEFORE/AFTER 时机和行级/语句级粒度，常用于审计、级联、约束。
- **关键要点**：现代架构趋势是将业务逻辑放在应用层，存储过程和触发器谨慎使用，避免过度依赖。
- **常见误区**：滥用触发器导致逻辑分散难调试；在触发器中执行耗时操作阻塞主事务；忽视存储过程的版本管理。

## 第 16 讲：数据库安全与权限管理

### 概念

**数据库安全** 是指保护数据库免受未授权访问、恶意攻击、数据泄露和破坏的措施与机制。数据库安全是信息安全的重要组成部分，涉及数据机密性、完整性和可用性。

数据库安全的多个层面：

- **身份认证（Authentication）**：验证用户身份，"你是谁"。常用用户名/密码、证书、LDAP、Kerberos 等。
- **访问控制（Authorization）**：控制用户能做什么，"你能做什么"。通过权限授予和角色管理实现。
- **数据加密（Encryption）**：保护数据机密性，包括传输加密（TLS/SSL）和存储加密（TDE 透明数据加密）。
- **审计（Auditing）**：记录用户操作，便于追溯和合规。
- **数据脱敏（Masking）**：对敏感数据部分隐藏，如手机号显示为 `138****5678`。

**SQL 提供两种授权机制**：

- **GRANT**：授予权限。
- **REVOKE**：撤销权限。

权限粒度从大到小：服务器级 → 数据库级 → 表级 → 列级。

### 原理

**1. 自主访问控制（DAC）与强制访问控制（MAC）**

- **DAC（Discretionary Access Control）**：用户可将自己拥有的权限授予他人。SQL 的 GRANT/REVOKE 属于 DAC。灵活但易导致权限扩散。
- **MAC（Mandatory Access Control）**：系统强制执行安全策略，用户不能改变权限。数据有安全级别（如机密、秘密、公开），用户有许可级别，只能访问级别不高于自己的数据。安全性高但灵活性低。

**2. 角色机制**

角色是权限的集合，将角色授予用户相当于授予角色所有权限。角色简化权限管理：先定义角色，再授予用户。当职责变化时，只需调整角色而非逐个用户。

**3. 视图与安全**

视图是数据库安全的重要工具：
- **列级安全**：通过视图只暴露部分列，隐藏敏感列（如薪资）。
- **行级安全**：通过视图 WHERE 条件限制可见行（如只看本部门数据）。
- **WITH CHECK OPTION**：防止通过视图插入/更新超出视图范围的数据。

**4. SQL 注入防护**

SQL 注入是常见攻击，攻击者通过输入恶意 SQL 篡改查询。防护措施：
- **参数化查询（预编译语句）**：使用占位符，SQL 结构与数据分离。
- **输入验证**：校验输入格式和长度。
- **最小权限原则**：应用账户只授予必要权限。
- **ORM 框架**：使用 ORM 自动参数化。

### 例子

**1. 用户与权限管理**

```sql
-- 创建用户
CREATE USER 'app_user'@'%' IDENTIFIED BY 'StrongP@ssw0rd!';
CREATE USER 'report_user'@'192.168.1.%' IDENTIFIED BY 'R3p0rt!';

-- 修改用户密码
ALTER USER 'app_user'@'%' IDENTIFIED BY 'N3wP@ssw0rd!';

-- 锁定/解锁用户
ALTER USER 'app_user'@'%' ACCOUNT LOCK;
ALTER USER 'app_user'@'%' ACCOUNT UNLOCK;

-- 设置密码策略（MySQL）
SET GLOBAL validate_password.policy = 'STRONG';
SET GLOBAL validate_password.length = 12;
```

**2. 权限授予与撤销**

```sql
-- 服务器级权限
GRANT SELECT, INSERT, UPDATE, DELETE ON school.* TO 'app_user'@'%';

-- 表级权限
GRANT SELECT ON school.Student TO 'report_user'@'192.168.1.%';

-- 列级权限（只允许查询特定列）
GRANT SELECT (Sno, Sname, Sdept) ON school.Student TO 'public_user'@'%';

-- 存储过程执行权限
GRANT EXECUTE ON PROCEDURE school.TransferFunds TO 'app_user'@'%';

-- 撤销权限

-- 查看用户权限

```

**3. 角色管理**

```sql
-- 创建角色

-- 授予角色权限

GRANT SELECT, INSERT, UPDATE, DELETE ON school.* TO 'writer';

-- 撤销角色
REVOKE 'writer' FROM 'app_user'@'%';
```

**4. 视图实现安全**

```sql
-- 列级安全：隐藏薪资列
CREATE VIEW employee_public AS
SELECT emp_id, emp_name, dept_id, hire_date
FROM employees;

-- 行级安全：只看本部门数据
CREATE VIEW my_dept_employees AS
SELECT * FROM employees
WHERE dept_id = (
    SELECT dept_id FROM employees WHERE emp_id = CURRENT_USER_ID()
)
WITH CHECK OPTION;

```

**5. SQL 注入防护对比**

```python
# 危险：字符串拼接（易受SQL注入）
import mysql.connector

def login_dangerous(username, password):

    # 攻击者输入 username = "admin' --"，密码任意
    # 实际SQL: SELECT * FROM users WHERE username='admin' --' AND password='xxx'
    # 绕过密码验证！
    cursor.execute(sql)

# 安全：参数化查询
def login_safe(username, password):

    cursor.execute(sql, (username, password))  # 数据与SQL结构分离
```

### 总结

- 数据库安全包括身份认证、访问控制、数据加密、审计、数据脱敏五个层面。
- SQL 通过 GRANT/REVOKE 实现自主访问控制，角色机制简化权限管理。
- 视图是安全利器，实现列级和行级访问控制。
- SQL 注入是常见威胁，必须用参数化查询防护。
- **关键要点**：遵循最小权限原则，应用账户只授予必要权限；定期审计权限，清理过期账户。
- **常见误区**：应用使用 root 账户连接数据库；忽视参数化查询导致注入；权限授予过宽。

## 第 17 讲：分布式数据库与 NoSQL

### 概念

**分布式数据库** 是数据分布在计算机网络多个节点上的数据库，对用户呈现单一数据库视图。分布式数据库兼顾扩展性、高可用性和地理位置分布需求。

**NoSQL（Not Only SQL）** 是非关系型数据库的统称，针对关系数据库在特定场景（海量数据、灵活模式、高并发）的局限而设计。NoSQL 牺牲部分一致性换取扩展性和性能。

**CAP 定理** 是分布式系统的基本定理：一致性（Consistency）、可用性（Availability）、分区容错性（Partition Tolerance）三者不可兼得，最多满足两个。由于网络分区不可避免，实际是在 CP 和 AP 之间选择。

**BASE 理论** 是 CAP 在实践中的妥协：基本可用（Basically Available）、软状态（Soft State）、最终一致性（Eventually Consistent）。大多数互联网系统选择 BASE 而非 ACID。

NoSQL 的四大类型：

- **键值数据库**：Redis、DynamoDB。数据以键值对存储，简单高效。
- **文档数据库**：MongoDB、CouchDB。存储 JSON/BSON 文档，灵活模式。
- **列族数据库**：HBase、Cassandra。按列族存储，适合宽表和聚合。
- **图数据库**：Neo4j、JanusGraph。存储节点和边，适合关系密集场景。

### 原理

**1. 分布式数据库的关键技术**

- **数据分片（Sharding）**：将数据分散到多个节点。分片方式有范围分片、哈希分片、一致性哈希。
- **数据复制（Replication）**：数据多副本存储，提升可用性和读性能。分为主从复制（单主）和多主复制。
- **分布式事务**：跨节点事务，常用两阶段提交（2PC）、三阶段提交（3PC）、Saga、TCC 等协议。
- **一致性协议**：Paxos、Raft 保证多副本一致性。

**2. 两阶段提交（2PC）**

2PC 是分布式事务的经典协议：

- **准备阶段**：协调者询问所有参与者能否提交，参与者锁定资源并回应。
- **提交阶段**：若所有参与者同意，协调者发提交命令；否则发回滚命令。

2PC 的问题：同步阻塞、协调者单点故障、数据不一致风险。3PC、TCC、Saga 是改进方案。

**3. NoSQL 的数据模型**

- **键值模型**：`key → value`，value 可以是任意格式。简单但查询能力弱。
- **文档模型**：`key → document`，document 是结构化 JSON。支持嵌套和数组，灵活。
- **列族模型**：`row_key → {column_family: {column: value}}`。适合稀疏数据和聚合查询。
- **图模型**：节点（Vertex）+ 边（Edge）+ 属性。适合社交网络、推荐系统。

**4. NewSQL**

NewSQL 兼具 NoSQL 的扩展性和关系数据库的 ACID，代表产品：Google Spanner、TiDB、CockroachDB、OceanBase。NewSQL 是分布式数据库的发展方向。

### 例子

**1. Redis 键值数据库示例**

```python
import redis

r = redis.Redis(host='localhost', port=6379, db=0, decode_responses=True)

# 字符串
r.set('user:1001:name', '张三', ex=3600)  # 1小时过期
name = r.get('user:1001:name')

# 哈希（适合存储对象）
r.hset('user:1001', mapping={'name': '张三', 'age': 20, 'dept': '计算机'})
user = r.hgetall('user:1001')

# 列表（适合消息队列）
r.lpush('tasks', 'task1', 'task2', 'task3')
task = r.rpop('tasks')  # 先进先出

# 集合（适合标签、去重）
r.sadd('student:cs', 'S01', 'S02', 'S03')
r.sadd('student:math', 'S02', 'S04')
```

## 第 18 讲：数据库性能调优

### 概念

**数据库性能调优** 是通过分析、诊断和优化，使数据库系统在响应时间、吞吐量、资源利用率等指标上达到最优的过程。性能调优是数据库工程师的核心技能，贯穿系统全生命周期。

性能调优的层次（从上到下）：

1. **SQL 与应用层**：优化 SQL 语句、连接池配置、缓存策略。投入产出比最高。
2. **数据库设计层**：表结构、索引、分区、反规范化。
3. **数据库配置层**：内存参数、连接数、日志配置。
4. **操作系统层**：文件系统、I/O 调度、内核参数。
5. **硬件层**：CPU、内存、磁盘（SSD/NVMe）、网络。

性能指标：

- **响应时间（Latency）**：单次请求的处理时间，越小越好。
- **吞吐量（Throughput）**：单位时间处理的请求数（QPS/TPS），越大越好。
- **并发数（Concurrency）**：同时处理的请求数。
- **资源利用率**：CPU、内存、磁盘 I/O、网络的使用率。

### 原理

**1. 性能调优方法论**

- **基准测试（Baseline）**：调优前先建立基准，量化当前性能。
- **瓶颈定位**：用监控工具找到瓶颈所在（CPU/内存/IO/锁/SQL）。
- **假设验证**：针对瓶颈提出优化假设，小范围验证。
- **逐步迭代**：一次只改一个变量，观察效果，避免"改了不知道哪个起作用"。
- **回归测试**：优化后验证功能正确性和性能提升。

**2. 慢查询分析**

慢查询是性能问题的首要来源。MySQL 通过 `slow_query_log` 记录执行时间超过阈值的 SQL。结合 `EXPLAIN` 分析执行计划，定位全表扫描、临时表、文件排序等问题。

**3. 索引优化策略**

- **高频查询列建索引**：WHERE、JOIN、ORDER BY、GROUP BY 涉及的列。
- **复合索引遵循最左前缀**：列顺序按等值 → 范围 → 排序。
- **覆盖索引减少回表**：将查询列都放入索引。
- **避免索引失效**：不在索引列用函数、隐式转换、前导通配符。
- **定期清理冗余索引**：未使用的索引浪费空间和写入性能。

**4. 配置参数调优**

- **innodb_buffer_pool_size**：InnoDB 缓冲池大小，建议物理内存的 60%-80%。
- **innodb_log_file_size**：Redo Log 大小，影响写入性能和崩溃恢复时间。
- **max_connections**：最大连接数，根据业务并发设置。
- **query_cache_size**：查询缓存（MySQL 8.0 已移除，因并发冲突反而降低性能）。

### 例子

```sql
-- EXPLAIN: type=range（索引生效）
```

### 总结

- 性能调优分五层：SQL/应用 → 设计 → 配置 → OS → 硬件，从上层入手投入产出比最高。
- 方法论：基准测试 → 瓶颈定位 → 假设验证 → 逐步迭代 → 回归测试。
- 慢查询日志 + EXPLAIN 是诊断 SQL 性能问题的核心工具。
- 索引优化是最有效的手段：覆盖索引、复合索引、避免索引失效。
- **关键要点**：调优一次只改一个变量；先定位瓶颈再优化，避免盲目调参；监控是调优的前提。
- **常见误区**：盲目加索引忽视写入代价；过度依赖配置调优忽视 SQL 优化；忽视监控导致无法定位问题。

## 第 19 讲：主流数据库对比

### 概念

市场上数据库产品众多，各有特色。本讲对比主流关系数据库和 NoSQL 数据库，帮助您根据场景选型。

**主流关系数据库**：

- **MySQL**：最流行的开源关系数据库，Web 应用首选。简单易用，生态丰富。
- **PostgreSQL**：功能最强大的开源关系数据库，支持复杂查询、自定义类型、地理空间数据。
- **Oracle Database**：商业数据库霸主，功能全面，企业级特性强，价格昂贵。
- **SQL Server**：微软出品，与 Windows 生态集成紧密，企业级支持好。
- **SQLite**：嵌入式数据库，无需服务器，适合移动端和小型应用。

**主流 NoSQL/NewSQL**：

- **Redis**：内存键值数据库，性能极高，适合缓存、会话、排行榜。
- **MongoDB**：文档数据库，灵活模式，适合内容管理、日志、物联网。
- **Elasticsearch**：搜索引擎，全文检索和聚合分析强，适合日志和搜索。
- **TiDB**：NewSQL，兼容 MySQL 协议，水平扩展，HTAP（混合事务分析）。

### 原理

**1. MySQL vs PostgreSQL**

| 维度 | MySQL | PostgreSQL |
|------|-------|-----------|
| 定位 | 简单高效的 Web 数据库 | 功能丰富的企业级数据库 |
| SQL 标准 | 部分遵循 | 高度遵循 |
| 存储引擎 | 多引擎（InnoDB/MyISAM） | 单引擎（堆表） |
| 索引 | B+树、Hash、全文 | B树、Hash、GiST、GIN、BRIN |
| 复杂查询 | 较弱 | 强（窗口函数、CTE、递归） |
| 数据类型 | 基础类型 | 丰富（JSONB、数组、范围、地理） |
| 扩展性 | 插件有限 | 丰富扩展（PostGIS、pg_partman） |
| 复制 | 异步/半同步 | 流复制、逻辑复制 |
| MVCC | Undo Log 实现 | 多版本元组实现 |

**2. 关系数据库 vs NoSQL 选型**

| 维度 | 关系数据库 | NoSQL |
|------|----------|-------|
| 数据模型 | 结构化二维表 | 键值/文档/列族/图 |
| 模式 | 固定模式（Schema-on-Write） | 灵活模式（Schema-on-Read） |
| 事务 | 强 ACID | BASE（最终一致） |
| 扩展 | 垂直为主 | 水平扩展 |
| 查询 | SQL 标准化 | 各自查询语言 |
| 适用 | 事务型业务 | 海量数据、灵活模式 |

**3. 选型决策树**

```
是否需要强事务一致性？
├─ 是 → 数据规模？
│       ├─ 单机够用 → MySQL/PostgreSQL
│       └─ 需要扩展 → TiDB/OceanBase (NewSQL)
└─ 否 → 数据模型？
        ├─ 键值/缓存 → Redis
        ├─ 文档/灵活 → MongoDB
        ├─ 全文搜索 → Elasticsearch
        ├─ 时序数据 → InfluxDB/TDengine
        └─ 关系网络 → Neo4j
```

### 例子

```python
import redis
import mysql.connector
import json

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

def get_user(user_id):
    cache_key = f"user:{user_id}"

    # 1. 先查缓存
    cached = r.get(cache_key)
    if cached:
        return json.loads(cached)

    # 2. 缓存未命中，查数据库
    cursor = db.cursor(dictionary=True)
    cursor.execute("SELECT * FROM users WHERE user_id = %s", (user_id,))
    user = cursor.fetchone()

    if user:
        # 3. 写入缓存，设置过期时间
        r.setex(cache_key, 3600, json.dumps(user, default=str))

    return user

def update_user(user_id, data):
    # 1. 更新数据库
    cursor = db.cursor()
    cursor.execute("UPDATE users SET ... WHERE user_id = %s", (user_id,))

    r.delete(f"user:{user_id}")
```

## 第 20 讲：新一代数据库技术

### 概念

随着人工智能、物联网、大数据的发展，数据库技术不断演进，涌现出一批面向特定场景的新一代数据库。本讲介绍向量数据库、时序数据库、图数据库、HTAP 数据库和云原生数据库。

**新一代数据库的代表**：

- **向量数据库**：Milvus、Pinecone、Weaviate。存储和检索高维向量，是 AI 和大模型应用的基础设施。
- **时序数据库**：InfluxDB、TDengine、TimescaleDB。专为时间序列数据优化，适合 IoT、监控、金融行情。
- **HTAP 数据库**：TiDB、OceanBase、SingleStore。同时支持 OLTP 和 OLAP，打破事务与分析的壁垒。
- **云原生数据库**：Aurora、PolarDB、Snowflake。存算分离，弹性伸缩，按需付费。
- **流数据库**：RisingWave、Materialize。处理实时数据流，支持物化视图。

### 原理

**1. 向量数据库与近似最近邻搜索（ANN）**

向量数据库存储 AI 模型生成的向量嵌入（Embedding），通过相似度检索实现语义搜索。核心算法是近似最近邻搜索（ANN）：

- **HNSW（Hierarchical Navigable Small World）**：分层图结构，查询复杂度 O(log n)，召回率高。
- **IVF（Inverted File）**：聚类倒排，先找簇再找近邻。
- **PQ（Product Quantization）**：向量压缩，减少内存占用。

应用场景：RAG（检索增强生成）、推荐系统、图像搜索、去重。

**2. 时序数据库的优化**

时序数据特点是"写多读少、按时间排序、旧数据冷存储"。时序数据库的优化：

- **列式存储**：按列存储，压缩率高，聚合快。
- **时间分区**：按时间自动分区，旧数据可降采样或冷归档。
- **LSM-Tree**：写入先到内存 MemTable，再合并到磁盘 SSTable，写入性能高。
- **降采样（Downsampling）**：将高频数据聚合为低频，如 1 秒粒度聚合为 1 分钟。

**3. HTAP 的架构**

HTAP（Hybrid Transactional/Analytical Processing）同时支持事务和分析：

- **行存 + 列存**：TiDB 的 TiKV（行存，OLTP）+ TiFlash（列存，OLAP），通过 Raft 同步。
- **读写分离**：事务走行存节点，分析走列存节点，互不干扰。
- **实时性**：数据写入后立即可分析，无需 ETL 延迟。

**4. 云原生数据库的存算分离**

传统数据库存储和计算耦合，扩容时需同时扩存储和计算。云原生数据库将存储和计算分离：

- **共享存储**：计算节点无状态，共享分布式存储（如 S3、EBS）。
- **弹性计算**：计算节点可按需增减，秒级扩缩容。
- **Serverless**：按使用量计费，闲置时不收费（如 Aurora Serverless）。

**1. 向量数据库（Milvus）实现语义搜索**

```python
from pymilvus import connections, FieldSchema, CollectionSchema, DataType, Collection

# 连接Milvus
connections.connect(host='localhost', port='19530')

# 创建集合（类似表）
fields = [
    FieldSchema(name='id', dtype=DataType.INT64, is_primary=True),
    FieldSchema(name='embedding', dtype=DataType.FLOAT_VECTOR, dim=768),
    FieldSchema(name='text', dtype=DataType.VARCHAR, max_length=512)
]
schema = CollectionSchema(fields, '文本向量集合')
collection = Collection('documents', schema)

# 创建向量索引（HNSW）
collection.create_index('embedding', {
    'index_type': 'HNSW',
    'metric_type': 'COSINE',
    'params': {'M': 16, 'efConstruction': 200}
})

# 插入向量（由Embedding模型生成）
embeddings = embed_texts(["数据库是信息系统的核心", "SQL是关系数据库的标准语言"])
collection.insert([
    [1, 2],                    # id
    embeddings,                # embedding
    ["数据库是信息系统的核心", "SQL是关系数据库的标准语言"]  # text
])

# 语义搜索：找最相似的文档
query_embedding = embed_texts("什么是数据库?")[0]
results = collection.search(
    data=[query_embedding],
    anns_field='embedding',
    param={'metric_type': 'COSINE', 'params': {'ef': 64}},
    limit=5,
    output_fields=['text']
)
for hit in results[0]:
    print(f"相似度: {hit.score:.4f}, 文本: {hit.entity.get('text')}")
```

**2. 时序数据库（InfluxDB）存储监控数据**

```python
from influxdb_client import InfluxDBClient, Point, WriteOptions

client = InfluxDBClient(url='http://localhost:8086', token='xxx', org='myorg')
write_api = client.write_api(write_options=WriteOptions(batch_size=500))

# 写入时序数据（CPU监控）
points = [
    Point('cpu_usage')
        .tag('host', 'server01')
        .tag('region', 'us-east')
        .field('value', 75.5)
        .time('2024-01-15T10:00:00Z'),
    Point('cpu_usage')
        .tag('host', 'server01')
        .field('value', 82.3)
        .time('2024-01-15T10:01:00Z'),
]
write_api.write(bucket='monitoring', record=points)

# 查询：过去1小时CPU平均使用率（Flux语法）
query_api = client.query_api()
query = '''
from(bucket: "monitoring")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "cpu_usage")
  |> filter(fn: (r) => r.host == "server01")
  |> aggregateWindow(every: 5m, fn: mean)
'''
result = query_api.query(query)
for table in result:
    for record in table.records:
        print(f"{record.get_time()}: {record.get_value():.2f}%")
```

**3. HTAP 数据库（TiDB）实时分析**

```sql
-- TiDB 兼容 MySQL 协议，直接用 MySQL 客户端连接

-- OLTP：高并发写入订单
INSERT INTO orders(order_id, user_id, amount, created_at)
VALUES (1001, 5001, 199.00, NOW());

-- OLAP：实时分析（TiFlash列存加速）
-- 添加列存副本
ALTER TABLE orders SET TIFLASH REPLICA 1;

-- 复杂聚合分析（自动路由到TiFlash）
SELECT
    DATE(created_at) AS dt,
    COUNT(*) AS order_count,
    SUM(amount) AS total_amount,
    AVG(amount) AS avg_amount
FROM orders
WHERE created_at >= '2024-01-01'
GROUP BY DATE(created_at)
ORDER BY dt DESC;

-- 分析与事务同时进行，互不阻塞
```

**4. 云原生数据库（Aurora）架构示意**

```
传统数据库：

Aurora云原生：
[应用] → [计算节点1] ─┐
```

### 总结

- 向量数据库是 AI 应用的基础设施，基于 ANN 算法实现语义检索，支撑 RAG 和推荐系统。
- 时序数据库针对时间序列数据优化，采用列存、LSM-Tree、时间分区，适合 IoT 和监控。
- HTAP 数据库同时支持 OLTP 和 OLAP，行存 + 列存分离，实时分析无需 ETL。
- 云原生数据库存算分离，弹性伸缩，按需付费，是云时代的主流形态。
- **关键要点**：新一代数据库针对特定场景优化，选型时先明确数据特征和访问模式。
- **常见误区**：盲目追新技术忽视成熟度；忽视向量数据库的召回率与延迟权衡；HTAP 不是万能的，超大规模分析仍需专用 OLAP。
